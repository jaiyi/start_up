## 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| DSH 无 server/唤醒能力，唤醒架构不成立 | **高** | spike 先行；工单已由后端落库，退化只需 DSH 轮询扫描 alert_events |
| rc 版 API 变动导致返工 | 高 | 锁定版本；插件层薄、核心逻辑在后端与 Postgres，可整体迁移 |
| 全盘替代工作量被低估（UI、飞书、工单流全要新建，且目前单人执行） | **高** | 首交付物收敛为「后端 + PG + 假告警落库 + 单事件诊断链跑通」（不依赖 UI/飞书/ops/完整 integration）；UI 与 ops 治理其后补 |
| **平台化变成第二种过度设计**（通用引擎/注册表在只有一个 profile 时空转） | 中高 | 「为复用而结构化，不为复用而实现」（02 §9）：归属/目录/schema 现在定，通用化实现等第二 profile 或首个真实连接触发 |
| **平台资产版本纪律缺失**（spc 升级平台包静默破坏未来 profile） | 中 | 平台包独立版本号 + changelog，profile 声明依赖范围，破坏性变更走 major（00 §3.6）；从第一天起立 |
| 工作台前端成为新的"跨仓对齐"负担（违背初衷） | 中 | 前端薄：优先只做 gate 推进 + 回放对比，复杂分析仍在 Agent 会话内 |
| 迁移文件与 plugin-ops runner 的版本漂移 | 中 | checksum 记录；迁移文件随 profile 同仓同发布；schema 域分目录独立演进 |
| 唤醒投递丢失（后端 POST 失败且重试耗尽） | 中 | 工单已在库不丢；投递状态落库 + 死信记录 + 运维告警；DSH 恢复后补唤醒（Q10） |
| `alert_events` 列级共享写（后端写事实列 / DSH 写状态列）误越界 | 低 | 写权限 owner 矩阵（04 §6）入迁移注释；platform-core db 层按 owner 约束写路径 |
| 专家审批环节成为发布瓶颈 | 中 | 调试模式回放对比降低审批心理成本；审批可批量 |
| 单人依赖（目前设计-实现集中于一人） | 低 | 本文档集即为知识沉淀 |

## 已识别但暂不处理

- 旧四仓的处置（封存/归档）时机——等新体系 MVP 跑通后再定。
- 旧系统线上数据是否迁移——当前旧链路无线上流量（e2e NOT RUN），暂无迁移对象。
