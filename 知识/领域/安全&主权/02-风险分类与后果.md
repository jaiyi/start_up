# 02 风险分类与后果

> 编写日期：2026-10-28；读者：业务负责人、架构、开发、安全、隐私/法务。范围：企业 Agent 在读、答、写、调用工具和长任务中的风险识别与排序；不提供具体企业的风险评级或法律意见。本文中的矩阵是分析工具，不是标准原文；官方资料已作入口可达性与部分正文抽样核对，具体分类版本和条款仍需复查。

## 风险不等于一次“答错”

以**机密性**（不应见者看见数据）、**完整性**（数据/结论/操作被不当改变）、**可用性**（合法任务受阻）、**可控性**（人在授权范围和停止机制上仍有实效控制）、**可审计性**（事后能关联主体、决策和实际回执）、**合法性**（处理、传输、使用满足适用法律、合同及组织义务）六个维度描述后果。前三项源自通用信息安全分析，后三项是本篇为 Agent 决策和治理增加的观察视角，并非某个官方框架的统一六维定义。隐私是面向可识别个人的处理风险，可能与机密性重叠，却不能只用“有没有泄漏”判断；合法性还取决于地域、目的、供应商和期限，需法务结合现行文本认定。

按失效路径区分：**误答**（无足够证据却给出确定结论）、**误读**（读到未授权对象/跨租户内容）、**误执行**（调用错误动作、对象或金额）、**持续渗透**（投毒知识/记忆或篡改工作流，影响未来任务）。同一次事件可属于多类，如跨租户召回后引用错资料，再把结果写入客户档案；统计时分别记录入口、权限失效和最终损失，不只打一个“幻觉”标签。

```text
输入/资料/记忆 ─→ 检索与权限决策 ─→ 模型建议 ─→ 策略/审批 ─→ 工具实际动作
     │                    │                 │                │             │
 来源与分类            对象 ACL          证据充分度       目的/范围       系统回执
     └───────风险线索可能跨层传播；权威状态应从原件/业务系统取得────────┘
              检测：关联身份、来源、版本、决策和回执；响应：阻断、撤权、补救
```

## 用资产—路径—后果矩阵排序

先写清“什么业务不能出错”，再评估场景，不采用脱离情境的统一提示注入概率。下面例子均为**假设情境的工程分析**，非实际事故统计：

| 失效场景 | 主要维度 | 需查的后果证据 | 首要控制责任点 |
|---|---|---|---|
| 向无权员工摘要合同附录 | 机密性、隐私、合法性 | 原件级 ACL、接收者、已展示文本 | 检索/原件服务端 |
| 把旧报价写成现行报价 | 完整性、可审计性 | 文档版本、有效期、原始报价 | 知识版本管理与业务确认 |
| 无审批自动提交采购单 | 可控性、完整性 | 审批记录、请求参数、订单回执 | 工具端授权和业务审批 |
| 重试风暴耗尽接口配额 | 可用性、可控性 | 调用计数、配额、熔断记录 | 任务编排/网关 |
| 未知第三方留存个人数据 | 隐私、合法性、可审计性 | 合同、实际数据流、删除证据 | 数据治理与采购 |

**评估步骤**：确定资产敏感度和可替代性；描述攻击者/偶然触发者的先决能力，如只能修改供应商文档还是拥有工具令牌；识别错误能否跨入执行系统；评价暴露面、频率、检测时间和补救可行性；记录现有控制的实际测试证据与未知项。风险优先级可采用组织既有量表，但不要用一个“高/中/低”替代“哪一项权限失效、是否造成实际发送”。高影响、不可逆且可自动批量执行的路径，即使发生率未知，也值得先收缩能力。

**事实与推导边界**：NIST AI RMF 提供治理、映射、测量和管理 AI 风险的框架；OWASP GenAI 汇集应用层风险类别；MITRE ATLAS 用于整理对抗技术。这些来源是分类和研究入口；上述六维、路径及矩阵是为本目录提出的操作性模型，不能据此宣称完全覆盖框架或满足监管要求。

## 两个不同失效案例（合成示意）

1. **看似“只是答错”却伤害完整性**：客服 Agent 根据检索片段回答某退款规则；片段来自过期版本、缺失生效日期，模型给出肯定答复。员工复制进业务系统，造成多笔错误承诺。即使无攻击者，也存在索引刷新、引用、人工复核和系统写入间的边界。仅纠正模型答案无法改掉已提交记录；需要按业务记录定位受影响交易并补救。
2. **回答正确却构成越权**：内部助手准确总结某员工并无权查看的另一团队薪酬草案，原因是向量索引采用服务账号检索、原件 ACL 未在候选返回时复核。正确性评分甚至很高，但机密性和合法性风险仍存在。即使模型不显示原文，只要可推断敏感事实就不能视为“没有泄露”。责任点是检索和原件服务的租户/对象过滤，不是让模型学会保密。

## 分层预防、检测与响应

- **预防**：数据治理侧为原件和衍生索引统一标分类、所有者、目的和时限；宿主把高风险任务默认设为草稿，列出准许的工具和对象；检索服务按请求主体在服务端强制 ACL/租户过滤并对原件二次核权；写入工具在服务器端校验动作范围、审批状态和幂等键，必要时限制配额。界面在建议、待审批、已执行之间使用不同状态。分类标签会过期或标错，审批也可能被社会工程误导。
- **检测**：抽样核对引用与原件版本；告警监控跨租户命中、异常出站、高频重试、缺审批回执写入；关联请求身份、政策版本、模型/索引版本、业务对象和最终状态。记录必要元数据而非全量敏感提示词，日志欠缺时不能“证明未发生”。监控对未知新型失败可能失明。
- **响应**：冻结受影响任务/工具或索引批次、撤销令牌、按业务系统回执盘点读/写/发范围；对错误承诺做人工更正，对数据暴露联系隐私和法务评估适用通知义务。删除输出副本与下游传播不一定可行，不能以“已下线模型”宣称后果已消除。

## 在测试租户做负例

用虚构合同和两个隔离身份：把正确但无权的薪酬片段放入索引，验证召回、摘要、引用和工具读取均不能越权；把旧版与新版退款规则混合，验证冲突/日期未知时请求原件核对而非自动写入；构造无审批订单、重复提交和连续失败重试，预期被拒绝、只产生零笔真实订单，并记录幂等/配额证据；撤掉日志中的正文后确认仍可串起主体与服务端回执。测试环境需禁用对外发送或仅连接模拟收件端，检查假阴性与误拦成本。

**误区和残余风险**：准确率不是授权率；“高危提示词”不一定比老旧 ACL 缺陷优先；人审若看不到动作对象和差异可能只是盖章；一套通用分类不能替代行业数据分类、司法辖区判断和合同核验。业务链路跨组织时，责任分界和外部留存有时难以直接观测，应记录为未知并通过协议、接口和演练补证。
