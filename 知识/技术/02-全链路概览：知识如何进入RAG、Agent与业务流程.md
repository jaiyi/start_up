# 02 · 全链路概览：知识如何进入 RAG、Agent 与业务流程

> 目标：如果你暂时还不了解大语言模型，也能先看懂一个知识复利系统的整体链路：业务知识从哪里来，怎么被整理，怎么被 AI 找到，怎么进入模型上下文，怎么让 Agent 做事，最后怎么通过反馈变成下一次更好的知识。

---

## 1. 先用一句话讲明白

一个知识复利系统，本质上是在做这件事：

```text
把人和业务现场里的经验，整理成机器能调用的知识；
让大模型在做任务时能找到这些知识；
让 Agent 在有边界的流程里使用这些知识；
再把使用结果反馈回来，修正下一次判断。
```

如果用最直白的话说：

```text
知识工程：把经验整理成材料；
RAG：帮模型临时查资料；
Prompt：告诉模型这次要怎么干活；
大模型：负责理解、总结、生成、推理；
Agent：不只回答，还能按步骤调用工具做事；
Workflow：把任务拆成固定流程；
Harness：把知识、模型、工具、权限、流程、日志、反馈都接起来；
评测和反馈：判断这次做得好不好，并让系统下次变好。
```

你可以先记住一个类比：

```text
知识库像仓库；
RAG 像仓库管理员；
Prompt 像任务说明书；
大模型像会读会写会推理的员工；
Agent 像能拿工具干活的员工；
Workflow 像标准作业流程；
Harness 像整个办公室 / 工厂的制度、工具、权限和质检系统；
反馈闭环像复盘机制。
```

---

## 2. 为什么需要这一章

如果直接从“知识工程”跳到“RAG 链路”，很容易陷入技术名词：

```text
Embedding 是什么？
Chunk 怎么切？
向量库怎么选？
Reranker 怎么用？
GraphRAG 和 LightRAG 有什么区别？
Agent 和 Workflow 又是什么关系？
```

这些问题都重要，但对初学者来说，先要建立整体图景：

```text
知识资产不是终点；
RAG 不是终点；
Agent 也不是终点；
真正的目标是让知识进入真实业务流程，并通过反馈持续变好。
```

否则很容易出现三种误解：

```text
误解一：把资料上传到知识库，就等于完成知识管理；
误解二：能基于文档问答，就等于完成 AI 应用；
误解三：Agent 能自动调用工具，就等于可以替人工作。
```

更准确的理解是：

```text
资料上传只是开始；
问答只是中间环节；
自动执行必须有流程、权限、确认和反馈；
真正重要的是系统能不能越用越好。
```

所以这一章不追求技术细节，而是先回答：

```text
一个知识复利系统到底是怎么跑起来的？
每一类技术在链路中处于什么位置？
为什么知识库、RAG、Agent、Harness、评测和反馈不能割裂理解？
```

---

## 3. 最重要的一张总图

先把整条链路看成这样：

```text
业务现场
  ↓
一手信息
  ↓
知识资产
  ↓
知识存储
  ↓
文档解析与切块
  ↓
索引
  ↓
检索
  ↓
上下文组装
  ↓
Prompt / 任务协议
  ↓
大模型理解与生成
  ↓
Agent / Workflow 执行
  ↓
人工确认与业务结果
  ↓
反馈回流
  ↓
知识更新
```

这张图先不要急着全部理解。你可以把它看成“从食材到出餐再到顾客评价”的过程：

```text
业务现场：真实厨房和顾客需求
一手信息：食材、订单、顾客口味
知识资产：整理好的菜谱、禁忌、经验
知识存储：菜谱本、库存表、厨房系统
索引：给菜谱做目录
检索：按需求找到合适菜谱
上下文组装：把这次做菜需要的资料放到厨师面前
Prompt：告诉厨师这次要做什么菜、有什么限制
大模型：理解需求并给出方案
Agent：按步骤执行，比如查库存、列菜单、生成清单
Workflow：固定出餐流程
人工确认：厨师长或顾客确认
反馈：吃完觉得太咸、太硬、不合口味
知识更新：下次调整菜谱
```

---

## 4. 每个环节到底是什么意思

### 4.1 业务现场：知识不是凭空产生的

业务现场就是事情真实发生的地方。

例如：

```text
销售和客户聊天；
客服处理投诉；
项目经理协调交付；
财务分析成本；
家庭里每天做饭、吃饭、反馈；
医生、老师、律师、工程师做专业判断。
```

知识复利的源头不是文档，而是这些真实场景。

如果没有业务现场，AI 系统只能学到表面材料：

```text
制度写得很好，但不知道实际怎么变通；
SOP 写得很完整，但不知道哪里最容易出错；
菜谱写得很好，但不知道家里人真实爱不爱吃；
客户画像写得很漂亮，但不知道客户真实顾虑是什么。
```

所以第一步不是买系统，而是问：

```text
我们到底想让 AI 帮哪个真实场景变好？
```

---

### 4.2 一手信息：最有价值的原材料

一手信息是从现场直接产生的信息。

它比二手总结更有价值。

例如家庭营养师 Agent 里，一手信息包括：

```text
孩子说牛肉太硬；
老人说晚餐太油；
这周冰箱还有西兰花；
今天实际没有做推荐的菜；
某个菜做了三次，家人都不爱吃；
某个成员最近要控糖；
某个食材会过敏。
```

企业里，一手信息包括：

```text
客户原话；
工单处理记录；
销售跟进备注；
项目延期原因；
质量异常描述；
复盘会里的争议点；
业务负责人对某个方案的真实判断。
```

这些信息如果不被捕获，很快就会消失在人脑、聊天记录和会议里。

---

### 4.3 知识资产：把原材料加工成可复用的东西

一手信息还不是知识资产。

它需要被整理成可复用形式。

比如一句原始反馈：

```text
孩子说番茄牛肉汤里的牛肉太硬了。
```

可以整理成几类知识：

```text
事实：某次晚餐孩子反馈牛肉太硬；
偏好：孩子不喜欢口感偏硬的牛肉；
规则：儿童版本牛肉菜需要更软烂；
菜谱改进：牛肉切小块、延长炖煮时间；
反馈记录：番茄牛肉汤儿童适配评分下降。
```

这一步就是知识工程。

它的核心不是“写得多”，而是把信息整理成：

```text
能被检索；
能被判断；
能被复用；
能被更新；
能被 Agent 安全调用。
```

---

### 4.4 知识存储：知识应该放在哪里

知识整理好以后，要放到合适的地方。

不同知识适合不同载体。

| 知识类型 | 更适合放哪里 | 例子 |
|---|---|---|
| 长文本经验 | Markdown / Wiki | 项目复盘、案例分析、操作说明 |
| 稳定规则 | 结构化 Markdown / 表格 | 禁忌规则、审批规则、报价规则 |
| 对象状态 | 表格 / 数据库 | 库存、客户状态、成员偏好 |
| 复杂关系 | 知识图谱 | 谁和谁有关、什么影响什么 |
| 临时上下文 | Agent Memory / 会话状态 | 本次对话目标、当前任务进度 |

一个简单原则：

```text
给人长期阅读的，放文档；
需要筛选、排序、统计的，放表格或数据库；
需要表达关系网络的，放图谱；
只在当前任务中临时有用的，放工作记忆。
```

---

### 4.5 文档解析与切块：把大文档拆成 AI 能用的小片段

大模型一次能看的内容有限。

如果你把一本几百页的手册直接丢给模型，它不一定能稳定使用。

所以 RAG 系统通常会先做两件事：

```text
解析：把 PDF、Word、网页、Markdown 变成机器可处理的文本；
切块：把长文档拆成一段一段的小块。
```

这就像读书时做摘抄卡片：

```text
不是每次都把整本书搬出来，
而是把相关段落、章节、卡片拿出来用。
```

但切块很重要。

切得太碎：

```text
上下文不完整，模型看不懂。
```

切得太大：

```text
噪声太多，模型抓不住重点。
```

所以后面的 RAG 模块会专门讲：

```text
Chunk 怎么切；
标题、层级、元数据怎么保留；
表格、图片、PDF 怎么处理；
怎么避免把完整语义切断。
```

---

### 4.6 索引：给知识建“地图”和“目录”

索引就是让系统以后能快速找到知识。

可以类比图书馆：

```text
书放进图书馆以后，必须有目录、分类号、关键词；
否则书虽然在那里，但没人找得到。
```

AI 知识系统里的索引通常有几种：

```text
关键词索引：按词匹配，比如搜“牛肉”“过敏”；
向量索引：按语义相似度匹配，比如搜“孩子嚼不动肉”，能找到“牛肉太硬”；
标签索引：按人工标签匹配，比如“儿童友好”“高蛋白”；
图谱索引：按实体关系匹配，比如“番茄牛肉汤 -> 包含 -> 牛肉”。
```

对小白来说，可以先记住：

```text
索引不是知识本身，索引是为了让知识能被找到。
```

---

### 4.7 检索：从知识库里找出这次任务相关的内容

检索就是当用户提问或 Agent 做任务时，系统去知识库里找资料。

例如用户问：

```text
这周给家里安排几顿高蛋白、适合孩子和老人吃的晚饭。
```

系统可能要检索：

```text
家庭成员偏好；
老人饮食禁忌；
孩子不爱吃的菜；
高蛋白菜谱；
冰箱库存；
最近一周吃过什么；
饭后反馈记录。
```

普通搜索像是在找关键词。  
语义检索像是在找意思相近的内容。  
混合检索就是两者都用。

RAG 里的“R”，Retrieval，就是检索。

---

### 4.8 上下文组装：把找到的资料整理成模型能理解的一包材料

检索到资料以后，不能直接一股脑塞给模型。

还要做上下文组装。

这一步像秘书给老板准备材料：

```text
不是把所有文件都搬到桌上，
而是把这次决策最相关的资料整理成一份简明材料包。
```

上下文组装要决定：

```text
哪些资料最重要？
哪些资料只是背景？
哪些资料互相冲突？
哪些资料过期了？
哪些资料必须引用来源？
哪些资料不应该给模型看？
```

这一步做不好，模型就会：

```text
看错资料；
引用过期知识；
忽略关键约束；
把个别案例当成通用规则。
```

---

### 4.9 Prompt / 任务协议：告诉模型这次到底要怎么工作

Prompt 不是简单的一句话问题。

在知识复利系统里，Prompt 更像“任务协议”。

它要告诉模型：

```text
你是谁；
这次任务是什么；
你可以使用哪些知识；
你必须遵守哪些规则；
输出格式是什么；
哪些事情不能擅自决定；
什么时候需要请人确认。
```

例如家庭营养师 Agent 的任务协议可以是：

```text
你是家庭营养师助手。
目标是生成一周晚餐建议。
必须遵守过敏和禁忌规则。
优先使用库存食材。
不要连续三天推荐同类主菜。
输出包括菜名、适合成员、注意事项。
如果涉及新食材采购，只能提出建议，不能自动下单。
```

Prompt 的作用不是让模型“更听话”这么简单，而是把业务任务翻译成模型能稳定执行的格式。

---

### 4.10 大模型：会读、会写、会总结、会推理，但没有天然组织记忆

大模型可以理解成一个很强的语言和推理引擎。

它擅长：

```text
读懂自然语言；
总结材料；
改写表达；
根据上下文推理；
生成方案；
写代码或文案；
模拟不同角色分析问题。
```

但它不天然知道你的组织知识。

它不知道：

```text
你家的孩子不吃香菜；
你们公司某客户刚刚投诉；
某个 SOP 上周已经改了；
某个老规则已经废弃；
这个流程里哪一步必须人工确认。
```

所以不能只说：

```text
我用了 DeepSeek / Qwen / GPT，所以就有知识系统了。
```

模型只是“大脑能力”。

知识复利系统还要给它：

```text
资料；
任务；
工具；
边界；
反馈。
```

---

### 4.11 RAG：让模型“开卷考试”

RAG 可以用一个非常简单的比喻理解：

```text
不让模型闭卷瞎猜，
而是先帮它从资料库里找相关资料，
再让它带着资料回答。
```

RAG 的基本过程是：

```text
用户提出问题；
系统理解问题；
系统去知识库检索相关内容；
把相关内容放进上下文；
模型基于这些上下文回答；
答案最好能引用来源。
```

所以 RAG 解决的是：

```text
模型不知道你的私有知识；
模型容易凭记忆胡说；
模型需要基于资料回答；
答案需要可追溯。
```

但 RAG 不自动解决：

```text
资料是否准确；
资料是否过期；
资料是否适合当前场景；
回答是否真的有效；
回答之后有没有行动；
行动之后有没有反馈。
```

---

### 4.12 Agent：不只是回答，还能按目标做事

Chatbot 更像“你问一句，它答一句”。

Agent 更像“你给它一个目标，它能拆步骤、查资料、调用工具、推进任务”。

例如：

```text
Chatbot：告诉我番茄牛肉汤怎么做。
Agent：根据家里库存、成员偏好和营养目标，安排本周晚餐，并标出需要人工确认的地方。
```

Agent 可能会做这些事：

```text
读取家庭成员偏好；
检索菜谱库；
检查过敏规则；
查询库存；
生成菜单；
询问用户确认；
记录用户反馈；
更新下一次推荐偏好。
```

但 Agent 越能做事，越需要边界。

否则它可能：

```text
引用错误知识；
擅自执行高风险动作；
把临时偏好写成长期规则；
把一次失败案例泛化成通用经验。
```

---

### 4.13 Workflow：把任务拆成稳定步骤

Workflow 是工作流。

它适合那些步骤相对固定的任务。

例如每周菜单生成可以拆成：

```text
1. 读取家庭成员信息；
2. 检查过敏和禁忌；
3. 读取库存；
4. 检索候选菜谱；
5. 按营养目标筛选；
6. 生成菜单；
7. 请用户确认；
8. 记录实际执行和反馈。
```

Workflow 的价值是稳定。

它不是让 AI 完全自由发挥，而是告诉 AI：

```text
这类任务通常按这些步骤走；
每一步输入是什么；
每一步输出是什么；
哪些地方要停下来问人。
```

---

### 4.14 Harness：把模型接入真实工作环境

Harness 这个词可以理解成“连接和约束系统”。

如果大模型是发动机，Harness 就是：

```text
车架；
方向盘；
刹车；
仪表盘；
安全带；
导航；
油门限制；
维修记录。
```

没有 Harness，模型只是一个能力很强的聊天窗口。

有了 Harness，模型才能进入真实业务环境：

```text
知道当前用户是谁；
知道能访问哪些知识；
知道能调用哪些工具；
知道哪些动作需要审批；
知道任务执行到哪一步；
知道失败后怎么恢复；
知道结果如何记录；
知道反馈如何回流。
```

所以 DeepSeek Harness 这类概念，重点不是 DeepSeek 模型本身，而是：

```text
如何把 DeepSeek 放进一个可用、可控、可追踪、可迭代的业务运行环境。
```

---

### 4.15 人工确认：不是所有事情都应该自动化

知识复利系统不是追求“完全无人”。

更合理的是：

```text
低风险、高频、可逆的事情，可以让 Agent 自动做；
高风险、低频、不可逆的事情，必须让人确认。
```

例如家庭营养师 Agent：

```text
可以自动推荐菜单；
可以自动总结反馈；
可以自动标记候选规则；
但不应该未经确认就永久修改家庭成员健康规则；
也不应该未经确认就下单购买食材。
```

企业里也是一样：

```text
可以自动生成客户跟进建议；
可以自动总结会议纪要；
可以自动检查合同风险；
但不应该未经授权就给客户发正式报价；
不应该自动审批高风险事项。
```

这就是从 human in the loop 到 human on the loop 的关键：

```text
人不必操作每一步，
但人要定义边界、监督过程、确认关键动作、承担最终责任。
```

---

### 4.16 评测：判断系统是不是真的变好了

评测就是给系统考试。

如果没有评测，你只能凭感觉说：

```text
好像回答不错；
好像变聪明了；
好像能用了。
```

但知识复利系统需要更明确地知道：

```text
检索有没有找到正确资料？
答案有没有引用事实？
有没有编造？
有没有违反规则？
Agent 步骤有没有走对？
用户是否采纳？
业务结果有没有改善？
```

对家庭营养师 Agent，可以评测：

```text
是否避开过敏食材；
是否符合高蛋白目标；
是否优先使用库存；
是否考虑老人和孩子口味；
用户最终是否采纳；
饭后满意度是否提高。
```

评测不是最后才做的装饰，而是系统能不能持续进步的仪表盘。

---

### 4.17 反馈回流：知识复利真正发生的地方

反馈回流是最关键的一步。

没有反馈，系统只是一次性回答。  
有了反馈，系统才会从每次使用中学习。

反馈可以包括：

```text
用户点赞 / 点踩；
人工纠错；
任务是否完成；
结果是否有效；
客户是否成交；
菜是否被吃完；
投诉是否减少；
成本是否下降；
效率是否提高。
```

反馈回流不是简单保存一句“用户不满意”。

更重要的是判断：

```text
是知识错了？
是检索错了？
是 Prompt 没写清楚？
是模型理解错了？
是流程设计错了？
是工具调用错了？
还是用户目标本身变了？
```

这叫错误归因。

没有错误归因，反馈只是情绪记录。  
有了错误归因，反馈才能变成系统改进。

---

### 4.18 知识更新：把一次经验变成下一次能力

知识更新不是把所有反馈都塞进知识库。

要区分：

```text
一次性反馈；
短期偏好；
长期偏好；
稳定规则；
异常案例；
需要复核的假设。
```

例如：

```text
今天孩子不想吃鱼
```

不一定要变成长期规则。

但如果连续多次反馈：

```text
孩子不喜欢刺多的鱼
```

就可以沉淀为偏好知识。

如果涉及健康风险：

```text
孩子对某种鱼过敏
```

就应该沉淀为高优先级规则。

知识更新的难点不是“能不能写入”，而是：

```text
什么反馈应该进入正式知识；
什么反馈只保留为历史记录；
什么反馈需要人确认；
什么反馈应该触发规则修改。
```

## 5. 用一个例子理解：家庭营养师 Agent

假设目标是做一个“家庭营养师 Agent”。

不要一开始就问：

```text
我要用哪个大模型？
我要不要做知识图谱？
我要不要微调？
```

更好的问题顺序是：

```text
家里有哪些稳定对象？
哪些信息会反复影响推荐？
哪些规则不能违反？
哪些反馈会改变下一次推荐？
Agent 什么时候可以自动做，什么时候必须问人？
```

一条简化链路如下：

```text
家庭成员、偏好、禁忌、菜谱、库存、饭后反馈
  ↓
整理成知识卡片、规则卡片、反馈记录
  ↓
存入 Markdown / WeKnora / 表格
  ↓
建立索引，支持检索
  ↓
用户问：这周晚饭怎么安排？
  ↓
RAG 找到相关菜谱、禁忌、偏好、库存信息
  ↓
Prompt 把任务说清楚：目标、约束、输出格式、确认点
  ↓
模型生成候选菜单
  ↓
Agent 检查禁忌、库存、营养目标
  ↓
用户确认实际做了哪些菜
  ↓
饭后反馈进入反馈库
  ↓
更新菜谱适配性和家庭成员偏好
```

这里每一步都对应一个技术模块，但它们服务的是同一个业务循环。

## 6. 再用一个企业例子理解：销售跟进 Agent

假设目标是做一个销售跟进 Agent。

它不是简单帮销售写话术，而是要进入完整链路：

```text
客户沟通记录
  ↓
提取客户对象、需求、异议、预算、决策人
  ↓
整理成客户知识卡片和案例库
  ↓
存入 CRM / Wiki / 知识库
  ↓
销售准备跟进前，系统检索相关客户信息和相似案例
  ↓
模型生成跟进建议和沟通话术
  ↓
Agent 提醒销售下一步动作
  ↓
销售确认并执行
  ↓
记录客户反馈和成交结果
  ↓
更新客户画像、话术效果和案例库
```

这个例子说明：

```text
AI 的价值不只是生成一段话，
而是让历史经验进入下一次销售判断，
再让下一次结果反过来修正经验。
```

## 7. 知识库、RAG、Agent、Harness 的区别

这几个词很容易混在一起。

| 概念 | 最直白解释 | 它解决什么 | 它不解决什么 |
|---|---|---|---|
| 知识库 | 放资料的地方 | 知识存放和管理 | 不自动判断、不自动执行 |
| RAG | 帮模型查资料 | 让模型基于资料回答 | 不保证资料正确，也不负责行动 |
| Prompt / 任务协议 | 给模型的任务说明书 | 约束模型怎么回答、怎么输出 | 不负责数据治理和工具权限 |
| 大模型 | 会读写和推理的大脑 | 理解、总结、生成、推理 | 不天然知道你的私有知识 |
| Agent | 能按目标推进任务的助手 | 查资料、调用工具、分步骤执行 | 不天然知道边界和责任 |
| Workflow | 固定任务流程 | 稳定、可控、可复用 | 不适合完全开放的问题 |
| Harness | 业务运行环境 | 接知识、模型、工具、权限、日志、反馈 | 不是某个单一模型或工具 |
| 评测 | 考试和体检 | 判断系统有没有变好 | 不自动修复问题 |
| 反馈闭环 | 复盘和改进机制 | 把结果变成下一次知识 | 需要治理，不是简单存日志 |

可以这样理解：

```text
知识库：材料仓库
RAG：取材料和配料
Prompt：菜谱说明
模型：厨师的大脑
Agent：能按目标做菜的人
Workflow：固定出餐流程
Harness：厨房、工具、制度、权限、记录和质检系统
反馈闭环：顾客吃完后的评价和改进
```

---

## 8. 为什么不是“有知识库就够了”

知识库只解决：

```text
知识放在哪里；
人或系统能不能找到它。
```

但知识复利还需要：

```text
知识是否进入任务；
知识是否影响判断；
知识是否产生业务结果；
结果是否回流修正知识；
知识是否被治理和淘汰。
```

所以一个常见误区是：

```text
搭了知识库 = 做了知识管理
接了大模型 = 做了 AI 应用
能问答 = 有了知识复利
```

更准确地说：

```text
知识库只是库存；
RAG 只是调用；
Agent 只是执行；
反馈和治理才让知识产生复利。
```

---

## 9. 为什么不是“有 RAG 就够了”

RAG 能解决模型不知道组织知识的问题，但它通常不自动解决这些问题：

```text
知识本身是否可信；
知识是否过期；
知识之间是否冲突；
检索结果是否适合当前任务；
回答是否真的改善业务结果；
错误回答如何回流修正；
哪些动作必须人工确认。
```

普通 RAG 偏向回答：

```text
根据已有资料，答案是什么？
```

知识复利系统还要继续追问：

```text
这个答案能不能用于当前场景？
如果用于行动，风险是什么？
执行后结果如何？
这次结果是否应该更新知识？
```

这就是为什么后面必须学习评测、Prompt、Harness 和反馈闭环。

---

## 10. 为什么不是“有 Agent 就够了”

Agent 看起来很强，因为它能：

```text
理解任务；
调用工具；
分步骤执行；
根据结果继续下一步。
```

但 Agent 如果没有可靠知识和边界，就会变成“行动能力很强的幻觉放大器”。

一个可用的 Agent 至少需要：

```text
清楚的任务协议；
可信的知识来源；
可控的工具权限；
明确的人工确认点；
失败恢复机制；
执行日志；
反馈和评测。
```

所以 Agent 的核心不是“能不能自动做”，而是：

```text
它在什么边界内可以自动做；
什么时候必须请人确认；
做错了如何追溯；
结果如何沉淀为新知识。
```

## 12. 一条面向落地的学习路径

后面的模块可以按这个顺序理解：

```text
01 知识工程：先知道什么知识值得沉淀
02 全链路概览：先看懂知识如何进入 AI 系统
03 RAG：学习知识如何被检索和组织进上下文
04 评测：学习如何判断系统是否真的有效
05 Prompt / 任务协议：学习如何让模型稳定理解任务
06 Harness：学习模型如何进入流程、工具、权限和协作
07 框架对比：比较 WeKnora、LightRAG、Reme 等具体方案
08 知识图谱：理解 GraphRAG、关系检索和实体推理
09 大模型：理解 DeepSeek、Qwen、GLM 等底层模型能力
10 私有化部署：理解部署、压缩、权限、治理和成本
```

这条路径不是从底层算法开始，而是从“知识如何在真实业务中产生价值”开始。

## 13. 判断一个系统是否形成知识复利

最后可以用一个检查清单判断：

```text
是否有明确的业务对象？
是否知道哪些知识值得沉淀？
是否有稳定的知识表达格式？
是否能检索到正确知识？
是否能把知识组织进任务上下文？
是否能让模型按任务协议输出？
是否能进入真实流程或工具？
是否有人工确认和权限边界？
是否记录结果反馈？
是否用反馈更新知识？
是否淘汰过期知识？
```

如果答案只停留在：

```text
可以上传文档；
可以聊天问答；
可以生成内容；
```

那它还只是 AI 工具。

如果答案进一步变成：

```text
能进入流程；
能产生反馈；
能修正知识；
能改善下一次判断和行动；
```

它才开始具备知识复利。
