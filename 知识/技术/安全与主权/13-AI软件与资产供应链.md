# 13｜AI 软件与资产供应链：从来源到撤回的闭环

> 调研/复核：2026-10-28。适用：采购、模型平台、数据、研发、安全、法务与发布运营团队。讨论可复用的防御流程，不对任何供应商、模型或许可证作安全/法律保证；实际义务须复核具体版本、合同与司法辖区。

## 定义、对象与信任图

供应链不止软件包：还包括基础模型权重与微调适配器、分词器/推理代码、训练/评测数据、嵌入模型、系统 Prompt、Skill、插件、MCP 服务、容器镜像及其依赖和远程更新。**来源（provenance）**回答“由谁、在何环境、从哪些输入构建/发布”；**完整性**回答“交付与批准内容是否一致”；**授权使用**还要问权利、用途、隐私、留存和撤回。签名能证明与某可信身份的密钥/构建流程关联，不能证明内容无害；许可证检查也不能替代权限和数据来源审查。

```text
上游发布者/模型仓库/数据提供方/插件作者（外部边界）
                 ↓ 来源、版本、哈希、条款和依赖清单
      隔离引入区 → 格式/内容/行为审查 → 审批与签名/证明验证
                                      ↓ 固定不可变版本
         内部注册表/模型库/Skill 库 → 分阶段部署 → Agent 装载/工具调用
                                      ↓                │
                         撤回、停用、回滚 ← 运行告警/审计回执
数据、权重和远程 MCP 的运营方可能具有不同的更新与撤回权，均需留痕。
```

资产台账应至少关联：提供者及法律主体、用途与数据分类、固定版本与哈希、签名/证明验证状态、许可证/合同评审结果、上游依赖、部署范围、负责人、到期/复核时间、升级与撤回路径。软件物料清单对代码依赖有帮助，无法天然覆盖训练语料与不断变化的远程服务；需要扩展或另立 AI 资产清单。

## 两类以上无害失效示例

1. **同名 Skill 的内容变化**：一个用于整理会议纪要的测试 Skill 初次审核通过，后来远程“最新版本”修改了工具调用描述。装载器只比对名称，不核对不可变版本/摘要；Agent 在测试空间开始提出原先未批准的写入动作。即便代码仓库受保护，加载时不重新验明版本仍可失守。
2. **数据集来源与授权不清**：团队下载公开标注数据用于模型评测，数据包含不适合该用途的虚构个人字段或许可不允许的再分发内容；仅看页面“可下载”便让数据进入日志、缓存或训练流程，后续删除和证明范围都很困难。没有证据不能断言具体数据合法或违法，须交由数据/法务复核。
3. **远程工具依赖变化**：通过 MCP 连接到供应商测试服务，接口名未变但服务端实现或鉴权策略更新，原有安全评审只覆盖客户端固定版本。供应链审核若只在安装时进行，运行中的服务侧变化、令牌范围和第三方停服仍会影响系统安全与可用性。

## 机制、分层控制与限制

- **选型/采购层**：先定资产分类、业务目的和可接受的更新控制权；核对模型和数据许可、再分发/商用/微调限制、数据处理、第三方转移、审计可见性、服务停用及退出条款。合同条款不证明技术控制已部署；版本与地区不同必须重核原文。
- **引入/构建层**：只从批准来源引入，保存原始下载凭据链、内容哈希和清单；优先验证发布者签名、构建证明与可复现或受控构建，对依赖和权重加载/脚本运行做隔离审查。检查签名时还要验证信任根、证书身份、版本和期望项目；“有签名”可能只是错误来源签了恶意产物。高风险格式不得在审查机上直接执行。
- **AI 内容层**：对数据做用途/个人信息/授权来源/污染样本抽查，区分事实材料和可执行指令；对模型、Prompt 与 Skill 检查工具权限宣称、隐含联网/下载行为和不可信内容如何引用。静态扫描无法充分推断模型行为，人工审核也会漏掉动态依赖和长尾输入，需隔离运行评测与后续监控。
- **发布/运行层**：不可变版本晋级，部署前比对批准摘要，按租户/任务最小授予工具和网络权限，灰度发布、回滚、kill switch 和紧急撤回；对远程 MCP/托管模型记录服务身份、约定版本或变更通知、可观察响应及替代方案。动态服务若无法固定内容，就把“持续变更”列为剩余风险并提高隔离与监控。生产日志记录版本和决策，不留无必要的敏感原文。
- **持续复核层**：跟踪漏洞公告、依赖更新、许可变更与来源声誉；定期复核清单与部署实态差异，演练从发现到停止装载、撤销令牌、回滚并定位受影响任务。立即撤回可能与可用性冲突，须预先约定失败模式和替代能力。

## 非生产负例验证

| 合成测试条件 | 预期结果与可追溯证据 |
|---|---|
| 与已批准 Skill 同名但摘要/版本不同的测试资产 | 装载拒绝或重新进入审核；审计能标识原始与候选版本 |
| 测试工件虽有签名但签名身份不在预期信任根 | 验签策略拒绝，不把“签名存在”误判为“已批准” |
| 数据集清单缺少许可/用途字段或包含虚构受限字段 | 进入隔离待核队列，不流入训练/检索；能定位已经关联的下游版本 |
| 模拟远程 MCP 接口权限声明或响应模式变化 | 停止高风险调用、复核权限并保留审计；旧任务不能静默继承新范围 |
| 测试版本被标记撤回后发起新任务/运行恢复任务 | 加载失败或回滚到批准版本，后台和缓存不得复活已撤回资产 |

这些是验收设计而非运行过的实验。应分别测试供应商事故通报延迟、离线部署无法查询签名服务以及模型托管方无法提供细粒度版本的问题。

## 误区、残余风险与来源

“开源=可商用”“有 SBOM=包含数据来源”“签名=可信内容”“已审核=以后都不变”都不成立。权重中的未知训练内容、提供方内部过程不透明、依赖停服、合法签名被误用、上游撤权与动态模型更新等仍需用替代性监控和退出机制处理。

**一手资料与证据边界**：2026-10-28 官方入口经公开只读 URL 可达性/标题抽查；未对某一具体资产的签名、许可或来源作核验。[NIST SP 800-218 SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) 用于安全开发过程；[NIST SP 800-204D](https://csrc.nist.gov/pubs/sp/800/204/d/final) 用于 CI/CD 供应链安全背景；[SLSA v1.2 规范](https://slsa.dev/spec/v1.2/) 用于构建证明与来源验证的框架；[Sigstore 官方文档](https://docs.sigstore.dev/) 用于签名工具背景；[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 用于 AI 生命周期治理。本文所列 AI 资产台账是实践建议，不表示 SLSA 覆盖模型或数据集的全部来源/权利问题。
