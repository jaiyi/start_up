# 15 · Agent 记忆管理：决定上下文、经验与长期知识如何沉淀

> 目标：先建立 Agent 记忆管理的知识框架。后续再扩写具体机制、工具选型、供应链案例、评测方法和治理细节。

---

## 1. 一句话定义

Agent 记忆管理不是“把聊天记录存起来”，而是管理 Agent 在跨轮对话、跨任务、跨流程、跨时间协作中形成的上下文资产。

它要回答：

```text
什么值得被记住？
记到哪里？
谁可以读取？
什么时候使用？
如何更新？
如何遗忘？
如何避免错误记忆长期污染系统？
如何让一次执行结果变成下一次改进的经验？
```

一句话：

> 记忆管理决定 Agent 能不能从“临时会话助手”变成“长期协作的数字员工”。

---

## 2. 为什么记忆管理重要

普通 Chatbot 更像：

```text
每次对话从零开始。
```

数字员工应该更像：

```text
知道用户是谁；
知道当前任务做到哪一步；
知道历史上发生过什么；
知道哪些偏好长期有效；
知道哪些经验值得复用；
知道哪些内容必须遗忘；
知道哪些记忆不能跨权限使用。
```

没有记忆管理，Agent 会出现：

```text
多轮对话断片；
跨会话无法延续；
重复询问同样信息；
无法复用历史案例；
无法沉淀专家经验；
把临时信息误当长期事实；
把错误推断长期污染系统；
越权使用不该看到的历史信息。
```

所以记忆管理是 Agent 从“会聊”走向“能长期工作”的基础设施。

---

## 3. 记忆管理不等于 RAG

很多人会误以为：

```text
有向量库 = 有记忆。
```

这是不准确的。

RAG 更偏：

```text
从外部知识库中检索相关资料。
```

Memory 更偏：

```text
管理 Agent 与用户、任务、工具、流程交互过程中形成的上下文、经验和状态。
```

对比：

| 能力 | 主要解决什么 | 举例 |
|---|---|---|
| RAG | 检索已有知识 | 制度、手册、SOP、历史文档 |
| Memory | 记录和复用交互经验 | 用户偏好、历史任务、失败案例 |
| Workflow State | 记录流程进度 | 采购申请等待主管审批 |
| Knowledge Graph | 记录实体关系 | 供应商 A 供应物料 M1 |
| Ontology | 定义语义结构 | 什么是供应商、物料、订单 |
| Audit Log | 记录发生过什么 | 谁在什么时候调用了什么工具 |

所以更准确地说：

```text
Memory = 可治理的上下文资产管理系统。
```

## 4. Agent 记忆的类型

后续扩写时，可以按照以下类型展开。

### 4.1 短期记忆 Short-term Memory

当前对话窗口里的上下文。

包括：

```text
用户刚刚说了什么；
上一轮模型回答了什么；
当前正在讨论哪个对象；
用户刚补充了哪些字段。
```

解决问题：

```text
多轮对话不要断片。
```

---

### 4.2 工作记忆 Working Memory

当前任务的结构化状态。

例如：

```json
{
  "task": "purchase_request",
  "status": "collecting_fields",
  "filled_fields": {
    "item_name": "显示器",
    "quantity": 2,
    "unit_price": 1200
  },
  "missing_fields": ["reason"],
  "waiting_for": "user_input"
}
```

解决问题：

```text
任务做到哪一步；
还缺什么字段；
下一步该做什么；
用户确认了什么；
哪些工具已经调用过。
```

---

### 4.3 长期用户记忆 Long-term User Memory

用户长期稳定的信息和偏好。

例如：

```text
用户常用中文回答；
用户偏好表格输出；
用户负责供应链计划；
用户默认关注上海工厂数据；
用户希望报告先给结论再给证据。
```

解决问题：

```text
减少重复沟通；
提升个性化协作体验。
```

---

### 4.4 语义记忆 Semantic Memory

可复用的业务知识和专家经验。

例如：

```text
某类缺料问题常见原因；
某个供应商历史上经常延期；
某个指标口径的解释；
某类客户投诉常见处理方案。
```

通常会沉淀到：

```text
知识库；
案例库；
知识图谱；
本体实例；
规则库；
评测集。
```

---

### 4.5 情节记忆 Episodic Memory

记录过去发生过的具体事件和案例。

例如：

```text
9 月 12 日供应商 A 延期 5 天；
影响了生产订单 P001；
计划员采取替代料方案；
最终 2 天后恢复；
复盘认为原因是供应商排产不足。
```

解决问题：

```text
相似案例检索；
复盘；
责任追踪；
经验迁移。
```

---

### 4.6 程序性记忆 Procedural Memory

记录“怎么做某件事”。

例如：

```text
如何分析缺料原因；
如何处理供应商延期；
如何生成周报；
如何完成质量异常初筛。
```

通常体现为：

```text
Skill；
Prompt Template；
Workflow；
Playbook；
SOP；
Tool 使用说明。
```

---

### 4.7 组织记忆 Organizational Memory

团队、部门或企业可以复用的知识资产。

例如：

```text
供应链异常案例库；
采购谈判经验；
质量问题根因库；
客户投诉处理库；
项目复盘库；
流程改进记录；
专家审核结论。
```

这是知识复利系统最核心的长期目标之一。

---

## 5. 记忆生命周期

一个成熟的记忆系统，不只是存储，还要管理完整生命周期。

```text
写入
  ↓
存储
  ↓
检索
  ↓
使用
  ↓
更新
  ↓
遗忘
  ↓
审计
```

每个阶段都要回答不同问题。

---

### 5.1 写入

要回答：

```text
什么值得被记住？
谁决定写入？
模型是否可以自动写入？
哪些记忆必须用户确认？
哪些记忆必须专家审核？
```

---

### 5.2 存储

要回答：

```text
记忆存在哪里？
是文本、结构化字段、向量、图谱还是流程状态？
是否需要分用户、分角色、分组织、分租户？
是否需要加密？
```

---

### 5.3 检索

要回答：

```text
什么时候需要读取记忆？
按语义检索、关键词检索、图谱路径检索还是结构化查询？
是否需要权限过滤？
是否需要重排？
```

---

### 5.4 使用

要回答：

```text
记忆应该如何进入 Prompt？
哪些记忆只用于排序或推荐？
哪些记忆可以展示给用户？
哪些记忆只能内部使用？
```

---

### 5.5 更新

要回答：

```text
记忆如何被修正？
新事实和旧事实冲突时怎么办？
是否保留历史版本？
是否记录来源和置信度？
```

---

### 5.6 遗忘

要回答：

```text
哪些记忆应该过期？
用户能否删除？
管理员能否删除？
权限变化后如何回收？
错误记忆如何撤销？
```

---

### 5.7 审计

要回答：

```text
谁写入了记忆？
谁读取了记忆？
记忆影响了哪次回答或决策？
记忆是否被修改或删除？
```

## 6. 记忆存储方式

不同记忆适合不同存储方式。

| 存储方式 | 适合记什么 | 示例 |
|---|---|---|
| Conversation Summary | 长对话摘要 | 当前项目背景、用户目标 |
| Key-Value Profile | 稳定偏好 | 用户偏好、默认工厂、常用格式 |
| Relational Memory | 结构化任务记录 | 任务状态、字段、责任人 |
| Vector Memory | 语义相似经验 | 历史对话、案例、复盘 |
| Graph Memory | 实体关系和事件链 | 供应商-物料-订单-异常 |
| Workflow State | 流程实例状态 | 等待确认、审批中、已完成 |
| Case Library | 可复用案例 | 缺料处理案例、质量异常案例 |
| Audit Log | 操作记录 | 谁在什么时候调用了什么工具 |

核心原则：

```text
不要把所有记忆都塞进向量库；
不同记忆应该进入不同存储层；
关键业务状态不能只存在 Memory 里。
```

## 7. Memory 与 RAG 的关系

RAG 常检索的是外部知识：

```text
制度；
文档；
SOP；
产品手册；
案例库。
```

Memory 常检索的是交互和经验：

```text
用户偏好；
历史任务；
历史决策；
执行结果；
失败案例。
```

但工程技术可能相似：

```text
向量库；
关键词索引；
图谱；
metadata filter；
reranker；
hybrid search。
```

区别在治理：

```text
RAG 知识通常更稳定；
Memory 更动态、更个性化、更敏感；
RAG 更像图书馆；
Memory 更像工作笔记和经验档案。
```

---

## 8. Memory 与 Ontology 的关系

本体定义记忆应该怎么组织。

没有本体时，记忆可能是：

```text
用户之前说供应商 A 有问题。
```

有本体后，可以结构化为：

```json
{
  "type": "SupplierRiskObservation",
  "supplier": "Supplier_A",
  "risk_dimension": "delivery",
  "evidence": "近 30 天延期 5 次",
  "confidence": 0.86,
  "source": "supplier_monthly_report",
  "observed_at": "2026-09-16"
}
```

关系是：

```text
Ontology 定义记忆类型；
Memory 保存具体记忆；
Graph 连接记忆对象；
RAG 检索相关记忆；
Agent 使用记忆完成任务。
```

---

## 9. Memory 与 Workflow 的关系

Workflow State 和 Memory 很容易混淆。

| 类型 | 解决什么 | 例子 |
|---|---|---|
| Workflow State | 当前流程实例走到哪一步 | 采购申请等待主管审批 |
| Memory | 跨任务、跨会话可复用的信息 | 用户偏好、历史案例、专家经验 |
| Audit Log | 记录发生过什么 | 谁在几点确认了申请 |
| Knowledge Base | 稳定知识资产 | 采购制度、SOP、案例总结 |

原则：

```text
流程状态不要只存在 Memory 里；
关键业务状态必须由 Workflow / 数据库管理；
Memory 可以帮助解释和推荐，但不能成为唯一事实源。
```

---

## 10. Memory 与 Tool / Trace / Audit Log 的关系

工具调用会产生大量可记忆信息：

```text
查了什么；
返回了什么；
用户采纳了什么；
动作是否成功；
失败原因是什么；
后续结果如何。
```

但不是所有工具结果都要记。

需要判断：

```text
是否可复用；
是否已确认；
是否有业务价值；
是否涉及敏感信息；
是否会过期；
是否应该进入案例库。
```

例如：

```text
query_inventory 返回当前库存，只适合短期上下文；
supplier_delay_resolution 的最终复盘，适合进入长期案例记忆。
```

---

## 11. 记忆治理

记忆系统最危险的地方是：它跨时间、跨会话、跨任务。

必须治理：

```text
权限；
隐私；
租户隔离；
过期；
冲突；
纠错；
删除；
审计；
敏感信息；
用户同意。
```

记忆写入时要区分来源：

```text
confirmed：已确认；
inferred：模型推断；
observed：工具观察；
user_stated：用户陈述；
expired：已过期；
deprecated：已废弃。
```

一句话：

> 记忆可以增强 Agent，但不能成为绕过权限、流程和事实校验的捷径。

## 12. 供应链场景里的记忆设计

供应链数字员工可以有这些记忆。

### 12.1 用户偏好记忆

```text
某计划员默认关注上海工厂；
某采购经理偏好先看供应商维度汇总；
某用户希望报告先给结论再给证据。
```

### 12.2 任务记忆

```text
某个缺料分析正在等待 IQC 反馈；
某个供应商延期流程已经升级到经理；
某个采购订单催办任务尚未关闭。
```

### 12.3 案例记忆

```text
上次类似缺料是因为质检未放行；
某供应商连续三次延期都和产能不足有关；
某类物料的缺料通常要先检查冻结库存和替代料。
```

### 12.4 组织记忆

```text
供应链异常标准处置流程；
专家审核过的风险判断模板；
供应商整改案例；
采购策略复盘结论。
```

## 13. 开源框架和工具候选

| 类型 | 工具 | 说明 |
|---|---|---|
| Agent Memory | Mem0、Zep、Letta | 面向 Agent 的长期记忆、用户画像、历史上下文管理 |
| Workflow Checkpoint | LangGraph Checkpoint、Temporal | 管理任务状态、恢复和长流程上下文 |
| Vector Memory | pgvector、Qdrant、Milvus、Weaviate | 存储语义相似记忆、历史案例和对话摘要 |
| Graph Memory | Neo4j、Apache AGE、Graphiti | 存储实体关系、事件链和长期关系记忆 |
| Session / Cache | Redis | 短期会话、缓存、临时状态 |
| Relational State | PostgreSQL、MySQL | 结构化任务状态、用户偏好、权限字段 |
| Trace / Audit | Langfuse、LangSmith、OpenTelemetry | 记录模型输入输出、工具调用和记忆使用过程 |

后续扩写时可以进一步比较：

```text
Mem0 vs Zep vs Letta；
Vector Memory vs Graph Memory；
Workflow State vs Agent Memory；
短期记忆压缩策略；
长期记忆写入策略；
企业权限和合规要求。
```

## 14. 评测方法

记忆系统至少要评测：

```text
记忆写入准确率；
记忆检索命中率；
记忆使用正确率；
过期记忆过滤率；
错误记忆纠正率；
权限过滤正确率；
跨会话任务延续成功率；
用户偏好采纳率；
历史案例复用率；
对最终业务结果的改善。
```

记忆评测不能只看“有没有找到相似内容”。

更重要的是：

```text
找出来的记忆是否应该被用；
用它是否改善了任务结果；
是否违反权限和隐私；
是否引入了过期或错误信息。
```

## 15. 常见错误和避坑

### 15.1 把聊天记录全部长期保存

这会带来噪声、隐私和错误污染问题。

### 15.2 把向量库当完整记忆系统

向量库只能解决语义检索，不解决权限、过期、版本、冲突和审计。

### 15.3 把流程状态存在 Memory 里

关键业务状态必须由 Workflow / 数据库管理。

### 15.4 把模型推断当事实

模型推断必须标注来源和置信度，关键记忆要人工确认。

### 15.5 不支持遗忘

不能删除、过期、撤销的记忆系统不适合企业。

## 17. 最终判断

Agent 记忆管理的核心不是“存更多内容”，而是：

```text
把对话、任务、工具、流程和业务结果中真正有复用价值的信息，
转化成可治理、可检索、可更新、可遗忘、可审计的上下文资产。
```

最终可以这样记：

```text
RAG 解决外部知识如何检索；
Prompt 解决当前任务如何理解；
Ontology 解决记忆如何结构化；
Workflow 解决流程状态如何可靠推进；
Tool 解决真实系统如何被调用；
Memory 解决 Agent 如何跨时间积累经验。
```
