# 04 · 评测：决定回答和检索是否真的有效

> 目标：作为初学者，先建立模型 / RAG / Agent 评测的整体知识框架。评测不是“打个分”这么简单，而是要回答：系统到底有没有找对资料、有没有答对问题、有没有遵守规则、有没有完成任务、有没有改善业务结果，以及出了错以后应该改知识、改检索、改 Prompt、改模型，还是改流程。

---

## 1. 先用最简单的话理解评测

评测就是给 AI 系统做考试和体检。

如果没有评测，我们只能凭感觉判断：

```text
好像回答不错；
好像比之前聪明；
好像能用了；
用户好像满意。
```

但真正做知识复利系统，不能只靠感觉。

我们需要能回答：

```text
这次有没有找到正确资料？
回答有没有基于资料？
有没有编造？
有没有违反规则？
Agent 有没有按流程做事？
工具有没有调用正确？
用户最后有没有采纳？
业务结果有没有改善？
如果错了，错在哪里？
```

所以评测的核心不是为了证明系统“很厉害”，而是为了：

```text
发现问题；
定位问题；
持续改进；
防止退化；
建立可信度。
```

可以用一个类比：

```text
RAG / Agent 是学生；
评测集是试卷；
评测指标是评分标准；
Trace 是答题过程草稿；
人工反馈是老师批注；
回归测试是下次升级后重考；
业务结果是这套能力在真实工作中有没有用。
```

---

## 2. 为什么评测是知识复利的核心

知识复利系统不是一次性项目。

它应该越用越好。

但“越用越好”必须有衡量方式。

没有评测会出现几个问题：

```text
不知道改动有没有提升；
不知道错误来自哪里；
不知道新版本是否把旧能力改坏；
不知道用户不满意是因为知识错、检索错、Prompt 错还是流程错；
不知道系统是否真的改善了业务结果。
```

评测和反馈在知识复利系统中的位置是：

```text
知识库 / RAG / Agent 输出
  ↓
真实使用
  ↓
结果记录
  ↓
反馈采集
  ↓
错误归因
  ↓
修正知识 / 检索 / Prompt / 流程 / 工具 / 模型
  ↓
回归评测
  ↓
下一轮使用
```

也就是说：

```text
没有评测，就没有稳定改进；
没有反馈，就没有知识复利；
没有错误归因，反馈也无法变成改进。
```

## 3. 初学者先建立三层评测框架

不要一开始就陷入各种工具和指标。

可以先按三层理解：

```text
第一层：组件评测
第二层：链路评测
第三层：业务结果评测
```

| 层级 | 评测对象 | 典型问题 |
|---|---|---|
| 组件评测 | 检索、生成、工具调用、分类、抽取等单个环节 | 这个模块本身准不准？ |
| 链路评测 | RAG 链路、Agent 流程、多步骤任务 | 整条链路能不能稳定完成任务？ |
| 业务结果评测 | 用户采纳、效率、成本、转化、风险 | 系统是否真的带来业务价值？ |

一个简单例子：家庭营养师 Agent。

```text
组件评测：能不能检索到正确菜谱？
链路评测：能不能根据偏好、库存、禁忌生成可用菜单？
业务结果评测：家人是否采纳？饭后满意度是否提升？浪费是否减少？
```

企业销售 Agent：

```text
组件评测：能不能找到客户历史沟通和相似案例？
链路评测：能不能生成合适的下一步跟进建议？
业务结果评测：销售是否采纳？客户回复率是否提高？转化是否改善？
```

## 4. 评测对象一：模型回答评测

模型回答评测关注的是：

```text
模型生成的答案本身好不好。
```

常见维度包括：

| 维度 | 直白解释 | 示例 |
|---|---|---|
| 正确性 | 答案是否对 | 推荐了不含过敏食材的菜单 |
| 完整性 | 有没有漏掉关键点 | 既考虑高蛋白，也考虑老人和孩子 |
| 相关性 | 是否回答了用户问题 | 没有跑题去讲营养学理论 |
| 忠实性 | 是否基于给定资料 | 没有编造知识库里没有的菜谱反馈 |
| 可解释性 | 是否说明为什么 | 说明推荐依据来自库存、偏好和营养目标 |
| 可执行性 | 用户能不能照着做 | 菜单清晰、步骤明确、限制明确 |
| 安全性 | 是否避免高风险建议 | 不给出不合适的健康建议 |
| 格式稳定性 | 输出是否符合约定格式 | JSON / 表格 / 清单字段完整 |

对于初学者，可以先用四个问题判断：

```text
答没答到点上？
有没有事实错误？
有没有编造？
用户能不能直接用？
```

## 5. 评测对象二：RAG 检索评测

RAG 不是只评估最终回答。

更重要的是先评估检索有没有找对资料。

因为很多 RAG 错误不是模型生成错，而是前面检索错。

### 5.1 检索评测关心什么

检索评测主要回答：

```text
正确资料有没有被找出来？
正确资料排在第几位？
无关资料多不多？
有没有找到过期资料？
有没有漏掉关键规则？
有没有违反权限？
```

### 5.2 常见检索指标

| 指标 | 直白解释 | 适合判断 |
|---|---|---|
| Recall@K | 前 K 个结果里有没有包含正确资料 | 有没有找出来 |
| Precision@K | 前 K 个结果里有多少是真的相关 | 噪声多不多 |
| MRR | 第一个正确结果排得有多靠前 | 排序是否友好 |
| nDCG | 相关结果整体排序质量 | 多个相关文档排序好不好 |
| Hit Rate | 是否命中至少一个正确结果 | 基础可用性 |

不用一开始深究公式，先记住：

```text
Recall 看“有没有找全”；
Precision 看“找出来的是不是干净”；
MRR / nDCG 看“排序好不好”。
```

### 5.3 RAG 检索常见错误

```text
没找出来：知识没入库、切块差、query 太模糊；
找错了：embedding 不适合、关键词缺失、元数据不足；
排太后：没有 reranker、排序策略差；
噪声太多：chunk 太大、过滤不足；
找了旧版本：没有有效期、没有版本状态；
权限泄露：检索前没有做权限过滤。
```

## 6. 评测对象三：RAG 生成评测

检索找对了，不代表最终回答一定对。

RAG 生成评测关注：

```text
模型有没有正确使用检索到的资料。
```

常见维度：

| 维度 | 说明 |
|---|---|
| Faithfulness / 忠实性 | 回答是否忠于上下文，不编造 |
| Answer Relevance / 回答相关性 | 是否回答用户问题 |
| Context Relevance / 上下文相关性 | 给模型的上下文是否有用 |
| Context Utilization / 上下文利用率 | 模型是否真正使用了关键上下文 |
| Citation Accuracy / 引用准确性 | 引用是否对应答案内容 |
| Abstention / 拒答能力 | 资料不足时是否知道说不知道 |

一个高质量 RAG 回答应该做到：

```text
基于资料；
引用来源；
不夸大；
不乱补；
说明边界；
资料不足时明确提示。
```

## 7. 评测对象四：Prompt / 任务协议评测

Prompt 不是一次写完就不变的。

它也需要评测。

Prompt 评测主要看：

```text
同样的问题，输出是否稳定？
输出格式是否符合要求？
是否遵守约束？
是否在边界场景下拒答？
是否会遗漏关键字段？
是否能正确使用工具和上下文？
```

例如你要求模型输出：

```json
{
  "menu": [],
  "reason": "",
  "risk_warning": "",
  "need_human_confirm": true
}
```

Prompt 评测就要检查：

```text
字段是否完整；
类型是否正确；
风险提醒是否存在；
是否错误地把 need_human_confirm 写成 false；
是否输出了 JSON 之外的废话。
```

常见工具：

```text
Promptfoo
DeepEval
自定义脚本
结构化输出校验
```

---

## 8. 评测对象五：Agent Trace 评测

Agent 不只是生成答案，它会分步骤做事。

所以不能只看最终答案，还要看过程。

这个过程通常叫：

```text
Trace / 轨迹 / 执行日志
```

Agent Trace 评测关注：

```text
任务有没有拆对？
工具有没有选对？
工具参数有没有传对？
中间结果有没有被正确理解？
有没有重复调用工具？
有没有越权调用？
有没有在该停下问人的地方继续执行？
失败后有没有恢复策略？
```

一个 Agent 任务可能长这样：

```text
用户：帮我安排这周晚餐。

Step 1：读取家庭成员偏好。
Step 2：查询库存。
Step 3：检索高蛋白菜谱。
Step 4：过滤过敏和禁忌。
Step 5：生成候选菜单。
Step 6：请求用户确认。
Step 7：记录反馈。
```

Trace 评测不是只问：

```text
最后菜单好不好？
```

还要问：

```text
每一步是否正确？
有没有跳过禁忌检查？
有没有使用过期偏好？
有没有未经确认写入长期规则？
```

---

## 9. 评测对象六：工具调用评测

Agent 经常会调用工具，例如：

```text
查知识库；
查数据库；
调用搜索；
写入表格；
发消息；
创建任务；
调用 API。
```

工具调用评测关注：

```text
是否选择了正确工具；
参数是否正确；
调用时机是否正确；
调用结果是否被正确解释；
失败后是否重试或降级；
是否遵守权限和人工确认边界。
```

例如家庭营养师 Agent：

```text
可以查库存；
可以生成候选菜单；
可以记录用户反馈；
但不能未经确认自动下单；
不能未经确认修改过敏规则。
```

工具调用越强，评测越重要。

因为错误不再只是“答错一句话”，而可能变成“做错一个动作”。

---

## 10. 评测对象七：业务结果评测

最终，知识复利系统不是为了评测指标好看，而是为了改善真实结果。

业务结果评测关注：

```text
系统是否真的让任务变快、变好、变稳、风险更低。
```

不同场景的业务指标不同。

| 场景 | 可能业务指标 |
|---|---|
| 家庭营养师 Agent | 菜单采纳率、饭后满意度、食材浪费减少、重复决策减少 |
| 客服 Agent | 首次解决率、平均处理时长、转人工率、投诉率 |
| 销售 Agent | 跟进采纳率、客户回复率、转化率、成交周期 |
| 工单 Agent | 处理时长、返工率、升级率、SLA 达成率 |
| 企业知识库 | 查找时间、新人培训时间、重复提问减少、知识复用次数 |

业务结果评测的难点是归因。

例如销售转化提升，可能不是 Agent 一个因素导致的。

所以更合理的是结合：

```text
离线评测；
在线反馈；
A/B 测试；
业务指标趋势；
人工复盘。
```

---

## 11. 离线评测与在线评测

评测可以分成两大类：

```text
离线评测：上线前或版本迭代时，用固定测试集评估；
在线评测：上线后，在真实使用中采集反馈和指标。
```

| 类型 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 离线评测 | 可重复、可回归、风险低 | 不一定代表真实使用 | 版本上线前、Prompt 改动、RAG 策略对比 |
| 在线评测 | 贴近真实业务 | 噪声大、归因难、有风险 | 已上线系统、业务效果跟踪 |

初学者可以先做离线评测。

例如先维护一个：

```text
20-50 条高价值测试问题
```

等系统开始真实使用，再逐步增加在线反馈和业务指标。

## 12. Golden Dataset：评测集是什么

Golden Dataset 可以理解成：

```text
一套精心准备的标准测试题。
```

它通常包括：

```text
用户问题；
正确答案或判断标准；
应检索到的资料；
适用场景；
难度；
标签；
评测维度；
人工确认点。
```

一个 RAG 评测样例可以这样设计：

```yaml
id: rag_recipe_001
question: 这周有哪些适合孩子和老人的高蛋白晚餐？
expected_sources:
  - 高蛋白饮食原则
  - 家庭成员偏好
  - 饭后反馈记录
  - 菜谱库
expected_answer_points:
  - 避开过敏食材
  - 至少包含 3 个高蛋白菜谱
  - 说明适合孩子和老人的原因
  - 标明需要用户确认的地方
tags:
  - 家庭营养师
  - RAG
  - 菜谱推荐
difficulty: medium
```

Golden Dataset 不是越大越好。

早期更重要的是：

```text
问题真实；
覆盖关键场景；
能暴露风险；
每条都能解释为什么对或错。
```

## 13. 评测集从哪里来

评测集可以从四类来源构造。

### 13.1 真实用户问题

最有价值。

例如：

```text
这周晚饭怎么安排？
孩子最近不爱吃肉怎么办？
这个客户下次该怎么跟进？
这个合同条款有没有风险？
```

优点：贴近真实使用。  
缺点：早期数量少，表达混乱。

### 13.2 历史案例和工单

从过去发生过的真实案例中抽题。

优点：有业务背景和结果。  
缺点：需要脱敏和整理。

### 13.3 专家设计问题

让业务专家设计典型题、边界题、风险题。

优点：能覆盖关键规则和高风险场景。  
缺点：可能不够贴近日常用户问法。

### 13.4 合成数据

用 LLM 根据知识库自动生成问题。

优点：扩充快。  
缺点：可能太理想化，需要人工抽检。

一个较好的组合是：

```text
真实问题 50%
历史案例 30%
专家设计 15%
合成问题 5%
```

比例不是固定的，关键是不要只用模型自动生成的题。

---

## 14. 评测用例应该覆盖哪些类型

一个好的评测集不能只有简单问题。

至少要覆盖：

| 类型 | 目的 | 示例 |
|---|---|---|
| 简单事实题 | 测基础检索 | 番茄牛肉汤包含哪些食材？ |
| 规则判断题 | 测规则调用 | 对牛肉过敏的人能吃这道菜吗？ |
| 多条件约束题 | 测综合能力 | 适合老人、孩子、高蛋白、低油的晚餐有哪些？ |
| 边界题 | 测拒答和谨慎性 | 这个饮食方案能治疗糖尿病吗？ |
| 冲突题 | 测冲突处理 | 菜谱推荐牛肉，但成员对牛肉过敏怎么办？ |
| 过期知识题 | 测版本治理 | 旧版规则和新版规则冲突时用哪个？ |
| 权限题 | 测安全边界 | 普通成员能否查看全部健康记录？ |
| Agent 流程题 | 测多步骤执行 | 生成菜单并记录反馈，但不要自动下单 |
| 反事实题 | 测稳健性 | 如果冰箱没有牛肉，推荐如何调整？ |
| 业务结果题 | 测实际有用性 | 推荐是否被采纳、反馈是否改善？ |

## 15. LLM-as-judge：让模型当评委

LLM-as-judge 是指：

```text
用一个大模型来评价另一个模型或系统的输出。
```

它适合批量评测：

```text
回答是否相关；
是否忠实于资料；
是否完整；
是否违反规则；
格式是否正确。
```

优点：

```text
成本比人工低；
速度快；
可以批量跑回归；
适合开放式答案。
```

风险：

```text
评委模型也会错；
不同模型标准不一致；
评分可能受表达风格影响；
可能偏爱长答案；
对专业领域判断不一定可靠。
```

所以 LLM-as-judge 不应该完全替代人工。

更合理的用法是：

```text
低风险、大批量：LLM 初评；
高风险、关键样本：人工复核；
争议样本：专家仲裁；
长期指标：和业务结果对齐。
```

## 16. 人工评审：什么时候必须要人看

以下场景建议保留人工评审：

```text
高风险业务；
新系统上线前；
评测标准还不成熟；
LLM-as-judge 分歧大；
涉及专业判断；
涉及合规、安全、健康、财务、法律；
需要评估用户体验和业务可用性。
```

人工评审不要只问“好不好”。

要设计结构化表单，例如：

```yaml
answer_correct: true
answer_complete: false
grounded_in_context: true
has_hallucination: false
citation_correct: true
violates_policy: false
usable_for_task: true
needs_human_confirm: true
error_type:
  - missing_key_constraint
comment: 没有考虑老人低盐要求。
```

结构化反馈才能进入后续分析。

## 17. 错误归因：评测最关键的一步

评测不是只打分。

真正重要的是：

```text
错了以后知道该改哪里。
```

一个 AI 应用出错，可能原因很多。

| 错误位置 | 表现 | 应该改什么 |
|---|---|---|
| 知识源错误 | 文档本身错、过期、冲突 | 改知识库和治理 |
| 文档解析错误 | PDF 表格丢失、乱码 | 改解析工具和清洗流程 |
| Chunk 错误 | 语义被切断 | 改切块策略 |
| 检索错误 | 正确资料没找出来 | 改 query、embedding、检索策略 |
| Rerank 错误 | 无关资料排前面 | 改重排模型或特征 |
| 上下文组装错误 | 关键规则没放进去 | 改 context packing |
| Prompt 错误 | 模型没遵守任务要求 | 改任务协议和输出约束 |
| 模型能力不足 | 推理、理解或格式能力不够 | 换模型或拆任务 |
| 工具调用错误 | 工具选错、参数错 | 改 tool schema 和调用逻辑 |
| 流程设计错误 | 该人工确认的没确认 | 改 workflow / harness |
| 权限错误 | 访问了不该看的知识 | 改权限过滤和审计 |
| 用户目标变化 | 用户需求和知识不一致 | 更新偏好和业务对象状态 |

可以记住一句话：

```text
没有错误归因的评测，只是打分；有错误归因的评测，才能驱动迭代。
```

---

## 18. 回归测试：防止越改越坏

AI 系统会频繁改：

```text
换模型；
换 embedding；
改 chunk；
加 reranker；
改 Prompt；
换知识库；
加工具；
改流程。
```

每次改动都可能带来新问题。

回归测试就是：

```text
每次改动后，用同一批重要测试题重新测一遍，确保旧能力没有坏掉。
```

例如：

```text
旧版本能正确避开过敏食材；
新版本加了菜单多样性后，不能把过敏规则弄丢。
```

回归测试特别适合进入 CI / 自动化流程：

```text
改 Prompt 后自动跑评测；
改检索策略后自动比较 Recall@K；
换模型后自动比较关键问题通过率；
低于阈值就不允许上线。
```

---

## 19. 评测指标不要迷信单一分数

很多评测工具会给出一个分数。

但单一分数很危险。

例如：

```text
平均分 85 分，但所有高风险问题都错了；
检索 Recall 很高，但答案不可用；
用户满意度不错，但系统偶尔泄露权限；
模型回答很完整，但引用是错的。
```

所以要分维度看。

一个更好的评测仪表盘可以包括：

```text
检索命中率；
引用准确率；
幻觉率；
规则违反率；
拒答正确率；
格式通过率；
Agent 步骤成功率；
工具调用成功率；
人工确认触发率；
用户采纳率；
业务结果指标。
```

对知识复利系统来说，尤其要关注：

```text
错误是否能被发现；
反馈是否能回流；
知识是否因此更新；
下一次同类问题是否变好。
```

## 20. 评测闭环：从反馈到系统改进

一个完整评测闭环可以这样设计：

```text
收集真实问题
  ↓
构造评测样例
  ↓
运行 RAG / Agent
  ↓
记录答案和执行 Trace
  ↓
自动评测 + 人工抽检
  ↓
错误归因
  ↓
修正知识 / 检索 / Prompt / 工具 / 流程
  ↓
回归测试
  ↓
上线
  ↓
继续采集在线反馈
```

这里最容易缺失的是两步：

```text
错误归因；
回归测试。
```

很多团队只收集“点赞 / 点踩”，但没有追问为什么。

这会导致反馈无法转化成系统改进。

## 21. 可观测性：先记录下来，才评测得了

评测依赖日志和 Trace。

如果系统没有记录过程，就很难知道错在哪里。

至少需要记录：

```text
用户问题；
改写后的 query；
检索到的文档和 chunk；
rerank 排序；
最终进入上下文的内容；
Prompt 版本；
模型版本；
模型输出；
工具调用过程；
Agent Trace；
用户反馈；
人工修改；
最终业务结果。
```

这就是 LLM Observability。

常见工具：

```text
Langfuse
LangSmith
Phoenix / Arize
Helicone
Opik
TruLens
OpenTelemetry
```

对于初学者，可以先不用复杂平台。

最简单也可以先用表格记录：

```text
问题
答案
引用来源
是否满意
错误类型
应该怎么改
```

## 23. 家庭营养师 Agent 的第一版评测集

如果以你的家庭营养师 Agent 为例，第一版可以先做 20-30 条。

### 23.1 样例类型

```text
事实查询：某菜谱包含哪些食材？
规则判断：过敏成员能不能吃某菜？
推荐任务：给孩子和老人推荐晚餐；
多约束任务：高蛋白、低油、库存优先；
反馈更新：用户说牛肉太硬后，下次推荐如何变化；
拒答边界：能不能给医疗治疗建议；
流程边界：能不能自动下单买菜；
```

### 23.2 一个测试样例

```yaml
id: family_menu_001
question: 给这周安排 5 顿适合孩子和老人的高蛋白晚餐。
expected_sources:
  - 家庭成员偏好
  - 高蛋白饮食原则
  - 菜谱库
  - 饭后反馈
checks:
  - 避开过敏食材
  - 考虑老人低油低盐
  - 考虑孩子口感偏好
  - 至少 3 道菜有高蛋白来源
  - 标明需要用户确认的地方
  - 不自动生成采购订单
error_if:
  - 推荐过敏食材
  - 声称能治疗疾病
  - 忽略已有负反馈
  - 无依据编造家庭偏好
```

### 23.3 第一版指标

先不用复杂指标，直接用：

```text
是否命中正确知识；
是否违反禁忌；
是否回答完整；
是否可执行；
是否需要人工确认；
用户是否采纳。
```

## 24. 小团队知识库的评测起点

小团队可以从 50 条真实问题开始。

建议分类：

```text
20 条高频 FAQ；
10 条制度 / SOP 问题；
10 条案例类问题；
5 条权限边界问题；
5 条冲突 / 过期知识问题。
```

每条问题至少记录：

```yaml
question: 用户真实问题
expected_source: 应该引用的文档或知识条目
expected_answer_points:
  - 必须包含的要点
forbidden:
  - 不能出现的错误回答
risk_level: low / medium / high
owner: 业务负责人
```

上线后继续收集：

```text
用户点踩问题；
人工改写过的答案；
转人工处理的问题；
重复提问的问题；
高风险错误问题。
```

这些会成为下一版评测集。

## 25. 企业级评测体系长什么样

企业级通常需要四层：

```text
离线 Golden Dataset
  +
自动化回归测试
  +
线上 Trace / Feedback
  +
业务指标联动
```

更完整的体系包括：

```text
模型版本管理；
Prompt 版本管理；
知识库版本管理；
检索策略版本管理；
评测集版本管理；
Trace 留存；
人工审核队列；
风险分级；
上线门禁；
A/B 测试；
业务结果复盘。
```

这就是为什么评测不只是算法问题，而是治理问题。

## 26. 初学者学习评测的推荐顺序

建议按这个顺序学：

```text
1. 先理解评测不是打分，而是发现问题和驱动迭代；
2. 理解模型回答评测、RAG 检索评测、Agent Trace 评测的区别；
3. 手工做 20-50 条 Golden Dataset；
4. 学会给错误分类，而不是只记“答错了”；
5. 学会做回归测试，防止越改越坏；
6. 学会用 LLM-as-judge 做辅助评测；
7. 学会记录 Trace 和用户反馈；
8. 再引入 Ragas、DeepEval、Promptfoo、Langfuse 等工具；
9. 最后把评测和业务结果连接起来。
```

不要一开始就追求完整平台。

早期最有价值的是：

```text
真实问题；
明确标准；
错误归因；
持续回归。
```

## 27. 与其他模块的关系

- 评测 01 知识工程是否提供了可用知识；
- 评测 03 RAG 是否找对资料、引用正确；
- 评测 05 Prompt / 任务协议是否稳定约束模型；
- 评测 06 Harness 中 Agent 是否遵守流程、权限和人工确认点；
- 评测 08 知识图谱 / GraphRAG 是否真的提升关系检索和推理；
- 评测 09 大模型选型是否适合当前任务；
- 评测 10 私有化部署后性能、成本、延迟和稳定性是否可接受；
- 反馈结果反向驱动知识治理和系统迭代。
