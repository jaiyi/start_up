# 03 · RAG：决定知识如何被检索和组织进上下文

> 目标：作为初学者，先建立 RAG 的整体知识框架。不要一上来就陷入 Embedding、向量库、Reranker、GraphRAG 等名词，而是先理解：RAG 为什么存在，它在知识复利系统里解决什么问题，一条完整 RAG 链路由哪些环节组成，每个环节分别影响什么。

---

## 1. 先用最简单的话理解 RAG

RAG 的全称是：

```text
Retrieval-Augmented Generation
检索增强生成
```

直白地说：

```text
先查资料，再让大模型回答。
```

如果没有 RAG，大模型很多时候是在“凭记忆”和“凭语言能力”回答。

如果有 RAG，系统会先从你的知识库里找相关材料，再把这些材料交给大模型，让它基于材料回答。

可以把 RAG 理解成：

```text
让大模型开卷考试。
```

不是让模型闭卷瞎猜，而是：

```text
用户提问
  ↓
系统去资料库查相关资料
  ↓
把资料整理好放到模型面前
  ↓
模型根据资料回答
  ↓
最好还能告诉你依据来自哪里
```

---

## 2. RAG 到底解决什么问题

大模型虽然很强，但它有几个天然限制。

### 2.1 它不知道你的私有知识

比如它不知道：

```text
你家的孩子不吃香菜；
你们公司最新的报价规则；
某个客户上周刚投诉；
你的 WeKnora 知识库里有哪些菜谱；
公司内部 SOP 昨天刚更新；
某个项目实际延期原因是什么。
```

这些知识不在通用模型训练数据里。

RAG 的第一个价值是：

```text
把私有知识临时提供给模型。
```

---

### 2.2 它可能会编

大模型很擅长生成自然语言，但如果没有依据，它可能会生成看起来很合理、但实际上不准确的内容。

这就是常说的：

```text
幻觉。
```

RAG 的第二个价值是：

```text
让模型基于资料回答，降低胡编概率。
```

但注意：RAG 只能降低幻觉，不是彻底消灭幻觉。

如果检索到的资料本身错了，或者上下文组装错了，模型仍然可能答错。

---

### 2.3 它的上下文窗口有限

大模型一次能看的内容有限。

你不能总是把整个知识库都塞给它。

所以需要先检索出与当前问题最相关的材料。

RAG 的第三个价值是：

```text
从大量知识中挑出本次任务最相关的一小部分。
```

---

### 2.4 它需要可追溯依据

在家庭娱乐聊天里，答案没有引用也许问题不大。

但在企业场景、专业场景、知识复利系统里，必须知道：

```text
这句话依据是什么？
来自哪个文档？
是哪条规则？
是否是最新版本？
是否适用于当前对象？
```

RAG 的第四个价值是：

```text
让答案可以引用来源、便于审查和纠错。
```

---

## 3. RAG 在知识复利系统中的位置

RAG 不是知识复利系统的全部。

它位于这条链路中间：

```text
知识工程
  ↓
知识存储
  ↓
RAG 检索与上下文组装
  ↓
Prompt / 任务协议
  ↓
大模型生成
  ↓
Agent / Workflow 执行
  ↓
评测与反馈
  ↓
知识更新
```

换句话说：

```text
01 知识工程：决定什么知识值得沉淀；
02 全链路概览：看懂知识如何进入 AI 系统；
03 RAG：决定知识如何被找到，并组织给模型使用。
```

RAG 的核心不是“上传文档后能问答”。

更准确地说：

```text
RAG 是知识资产被模型和 Agent 调用的通道。
```

如果知识工程做得差，RAG 只会更快地暴露混乱。  
如果 RAG 做得差，再好的知识也可能找不到、找错、用错。  
如果评测和反馈缺失，RAG 是否真的有效就无法判断。

---

## 4. 一条完整 RAG 链路

可以先记住这条最核心的链路：

```text
用户问题 / Agent 任务
  ↓
Query 理解与改写
  ↓
检索召回
  ↓
Rerank / 过滤 / 剪枝
  ↓
上下文组装
  ↓
Prompt 注入
  ↓
模型生成回答 / 执行动作
  ↓
引用溯源
  ↓
评测与反馈
```

每一步都可能影响最终效果。

| 环节 | 直白解释 | 如果做不好会怎样 |
|---|---|---|
| Query 理解 | 先看懂用户到底想问什么 | 问题理解错，后面全错 |
| Query 改写 / 扩写 | 把模糊问题改成更适合检索的问题 | 可能引入用户没说的意思 |
| 检索召回 | 从知识库里多找一些可能相关的材料 | 找不到关键资料 |
| Rerank | 从候选材料里重新排序，挑出最相关的 | 把无关材料排前面 |
| 过滤 / 剪枝 | 去掉过期、低质、无关、无权限材料 | 噪声太多或误删关键内容 |
| 上下文组装 | 把材料整理成模型能读懂的一包上下文 | 模型看不懂、看漏、看混 |
| 生成回答 | 模型基于上下文生成答案 | 幻觉、遗漏、表达不清 |
| 引用溯源 | 标明答案依据来自哪里 | 无法审查和纠错 |
| 评测反馈 | 判断这次 RAG 是否有效 | 系统无法持续变好 |

---

## 5. 用一个简单例子理解 RAG

假设你的家庭知识库里有这些材料：

```text
1. 番茄牛肉汤菜谱
2. 高蛋白饮食原则
3. 家庭成员偏好
4. 饭后反馈记录
5. 冰箱库存记录
```

用户问：

```text
这周能不能安排几顿适合孩子和老人的高蛋白晚餐？
```

RAG 系统要做的不是直接让模型回答，而是：

```text
第一步：理解问题
- 这是菜单推荐问题；
- 涉及孩子和老人；
- 目标是高蛋白；
- 场景是晚餐；
- 时间范围是一周。

第二步：检索知识
- 找高蛋白原则；
- 找适合晚餐的菜谱；
- 找孩子和老人的偏好；
- 找禁忌和过敏规则；
- 找最近吃过的菜；
- 找饭后反馈。

第三步：过滤和排序
- 去掉不适合老人的菜；
- 去掉孩子反馈差的菜；
- 优先保留高蛋白、低风险、做过且反馈好的菜。

第四步：组装上下文
- 把相关菜谱、规则、偏好、反馈整理给模型。

第五步：生成回答
- 模型基于这些资料生成菜单建议。

第六步：引用和反馈
- 标明为什么推荐这些菜；
- 用户吃完后记录反馈，影响下一次推荐。
```

这就是 RAG 的基本思想。

## 6. RAG 的输入不是“文档”，而是“可检索知识”

很多人以为 RAG 是：

```text
上传 PDF -> 问答
```

这只是最粗糙的 RAG。

真正有效的 RAG 更关心：

```text
知识是否结构清楚；
文档是否有标题和层级；
规则和案例是否分开；
知识是否有元数据；
是否标注更新时间；
是否标注适用范围；
是否能按权限过滤；
是否能追溯来源。
```

也就是说，RAG 的效果很大程度取决于前面的知识工程。

可以记住一句话：

```text
RAG 不会自动把混乱知识变成高质量知识，它只会把混乱知识检索出来。
```

---

## 7. 文档接入：从原始资料到可检索材料

RAG 的第一段工程通常叫：

```text
Ingestion / 数据接入 / 文档入库
```

它包括：

```text
文档收集；
格式解析；
清洗去噪；
切块；
添加元数据；
生成索引；
入库。
```

### 7.1 文档解析

不同文档处理难度不同：

| 文档类型 | 难度 | 常见问题 |
|---|---|---|
| Markdown | 低 | 结构清楚，适合 RAG |
| 网页 HTML | 中 | 导航、广告、脚注噪声多 |
| Word | 中 | 表格、标题层级可能丢失 |
| PDF | 高 | 版面、页眉页脚、表格、扫描件复杂 |
| 图片 / 扫描件 | 高 | 需要 OCR，错误率更高 |
| Excel / 表格 | 中高 | 语义依赖行列结构，不能简单转文本 |

常见工具：

```text
Unstructured
Docling
Marker
MinerU
LlamaIndex Readers
LangChain Document Loaders
```

### 7.2 清洗去噪

原始文档里经常有噪声：

```text
页眉页脚；
目录重复；
水印；
版权声明；
导航菜单；
格式乱码；
重复段落；
过期版本。
```

如果不清洗，RAG 很容易把无关内容检索出来。

### 7.3 添加元数据

元数据是描述知识的“标签和身份证”。

常见元数据包括：

```yaml
document_id: recipe_001
title: 番茄牛肉汤
source: 家庭菜谱库
type: recipe
owner: lijiayi
created_at: 2026-09-16
updated_at: 2026-09-16
valid_until: 2027-03-16
tags:
  - 高蛋白
  - 晚餐
  - 儿童适配
permissions:
  - family
```

元数据可以帮助 RAG 做：

```text
权限过滤；
时间过滤；
类型过滤；
对象过滤；
版本控制；
引用溯源。
```

## 8. Chunk：为什么要切块

大模型不能每次都读完整知识库。

所以文档通常要切成一个个片段，叫：

```text
Chunk
```

可以把 Chunk 理解成：

```text
知识卡片；
摘抄段落；
小章节；
检索的最小材料单元。
```

### 8.1 切太小的问题

如果切得太小，模型可能看不懂上下文。

例如：

```text
“需要炖 40 分钟。”
```

单独看这句话，不知道是谁需要炖 40 分钟。

### 8.2 切太大的问题

如果切得太大，一个 chunk 里有太多无关内容。

例如一个 chunk 同时包含：

```text
番茄牛肉汤；
清炒西兰花；
红烧鱼；
购物清单；
家庭反馈；
```

检索出来后，模型可能抓不住重点。

### 8.3 常见切块策略

| 策略 | 说明 | 适合场景 |
|---|---|---|
| 固定长度切块 | 每 N 个字切一块 | 快速验证，简单文档 |
| 按标题切块 | 按章节、标题、段落切 | Markdown、手册、SOP |
| 语义切块 | 按语义完整性切 | 案例、长文、复杂说明 |
| 滑动窗口 | 相邻 chunk 保留重叠内容 | 避免上下文断裂 |
| Parent-child chunk | 小块用于检索，大块用于回答 | 长文档、制度、报告 |

初学者可以先记住：

```text
好的 chunk 应该既足够完整，又足够聚焦。
```

## 9. Embedding：把文字变成可以比较的数字

Embedding 是 RAG 里最容易让初学者困惑的概念。

直白地说：

```text
Embedding 是把一段文字变成一串数字，让计算机能判断两段文字意思像不像。
```

例如：

```text
“孩子嚼不动牛肉”
“牛肉口感太硬”
```

这两句话用词不同，但意思接近。

关键词搜索不一定能匹配上，但 Embedding 可以把它们放到语义上相近的位置。

可以这样理解：

```text
每段文字都会被放到一个“语义地图”里；
意思相近的文字距离近；
意思不相关的文字距离远。
```

常见中文 / 多语言 Embedding 模型：

```text
BGE / FlagEmbedding
Qwen Embedding
E5
text-embedding 系列模型
```

Embedding 影响的是：

```text
能不能把意思相近但用词不同的内容找出来。
```

## 10. 向量库：存放语义索引的地方

当很多 chunk 都变成 Embedding 向量后，需要一个地方存起来，并支持快速查找。

这就是向量库。

可以理解成：

```text
普通数据库存表格；
搜索引擎存关键词索引；
向量库存语义坐标。
```

常见向量库：

```text
Milvus
Qdrant
Weaviate
Chroma
pgvector
```

选型时需要关注：

```text
数据量多大；
是否需要权限过滤；
是否支持元数据过滤；
部署复杂度；
中文生态；
备份和迁移；
团队运维能力。
```

个人和小团队不一定一开始就要上重型向量库。

很多时候：

```text
WeKnora / RAGFlow / Dify / LlamaIndex / Chroma / Qdrant
```

已经足够做验证。

## 11. 检索：如何把相关知识找出来

检索是 RAG 的核心。

常见检索方式有三类。

### 11.1 关键词检索

关键词检索就是按词匹配。

适合：

```text
制度编号；
产品型号；
客户名称；
合同编号；
固定术语；
专有名词。
```

优点：

```text
精确、可控、容易理解。
```

缺点：

```text
用户换个说法，可能搜不到。
```

---

### 11.2 向量检索

向量检索是按语义相似度查找。

适合：

```text
自然语言问题；
表达方式多样；
用户不知道准确术语；
需要找意思相近的内容。
```

优点：

```text
能理解相似意思。
```

缺点：

```text
对编号、短词、专有名词可能不如关键词检索。
```

---

### 11.3 混合检索

混合检索就是关键词 + 向量一起用。

企业知识库通常更适合混合检索。

因为企业文档里既有：

```text
自然语言描述；
```

也有：

```text
编号、术语、客户名、制度名、产品型号。
```

所以很多生产系统会采用：

```text
BM25 / Elasticsearch / OpenSearch
+
Embedding / Vector Search
+
Reranker
```

## 12. Query 处理：用户问法通常不适合直接检索

用户的问题经常很短、很口语、很模糊。

例如：

```text
这个能吃吗？
上次那个客户咋处理？
这个流程怎么走？
帮我排一下这周菜单。
```

系统需要先理解并改写问题。

### 12.1 Query Rewrite：问题改写

把用户问题改得更明确。

例如：

```text
原问题：这个能吃吗？
改写后：当前菜谱中的食材是否符合家庭成员的过敏、禁忌和营养目标？
```

### 12.2 Query Expansion：问题扩写

补充可能相关的检索词。

例如：

```text
用户问：高蛋白晚餐
扩写：高蛋白、晚餐、牛肉、鸡蛋、豆制品、鱼、儿童适配、老人适配
```

### 12.3 Multi-query Retrieval：多路问题检索

同一个问题拆成多个检索角度。

例如：

```text
这周安排适合孩子和老人的高蛋白晚餐
```

可以拆成：

```text
高蛋白菜谱有哪些？
哪些菜适合儿童？
哪些菜适合老人？
最近饭后反馈差的菜有哪些？
冰箱库存适合做哪些菜？
```

这样召回更全面。

但风险是：

```text
扩写过度会引入用户没有表达的意图。
```

所以 Query 处理要有边界。

---

## 13. Reranker：从“可能相关”里挑出“最相关”

第一轮检索通常是召回。

召回的目标是：

```text
宁可多找一点，不要漏掉关键资料。
```

但召回多了会有噪声。

Reranker 的作用是：

```text
把候选材料重新排序，把真正最相关的排到前面。
```

可以类比招聘：

```text
第一轮检索：先从简历库里筛出 100 份可能合适的简历；
Reranker：再认真比较，挑出最适合面试的 10 份。
```

常见 reranker：

```text
bge-reranker
Cohere Rerank
Qwen / BGE 相关重排模型
Cross-encoder reranker
```

Reranker 通常能显著提升 RAG 质量，但会增加：

```text
延迟；
成本；
工程复杂度。
```

---

## 14. 过滤与剪枝：不是检索到的都应该给模型

检索出来的内容，还要过滤。

常见过滤包括：

```text
权限过滤：用户有没有权限看；
时间过滤：是否过期；
类型过滤：只要规则，不要闲聊记录；
对象过滤：只看当前客户 / 当前家庭成员；
质量过滤：只使用已验证知识；
重复过滤：去掉重复 chunk；
冲突处理：发现规则互相矛盾时提示人工确认。
```

Context Pruning 是剪枝。

它的目标是：

```text
在有限上下文窗口里，只保留最有用的信息。
```

风险是：

```text
剪错会丢掉关键依据。
```

所以剪枝不只是压缩文本，而是判断：

```text
哪些内容对当前任务最关键？
```

---

## 15. 上下文组装：把资料变成模型能用的“材料包”

上下文组装叫：

```text
Context Packing / Context Assembly
```

它不是简单把检索结果拼起来。

好的上下文组装要考虑：

```text
先放任务目标；
再放必须遵守的规则；
再放当前业务对象信息；
再放相关案例和参考资料；
最后放输出要求和引用要求。
```

例如：

```text
任务：生成一周家庭晚餐建议。

必须遵守：
- A 成员对花生过敏；
- 老人晚餐低油低盐；
- 本周目标是高蛋白。

当前库存：
- 牛肉、鸡蛋、西兰花、豆腐。

相关反馈：
- 孩子不喜欢牛肉太硬；
- 番茄牛肉汤上次评分 2/5，原因是口感偏硬。

候选菜谱：
- 番茄牛肉汤；
- 西兰花炒鸡蛋；
- 豆腐虾仁汤。

输出要求：
- 给出 5 顿晚餐；
- 标明适合成员；
- 标明注意事项；
- 引用依据。
```

这种上下文比随机拼接更稳定。

## 16. 生成与引用：答案要基于资料，而不是看起来像答案

RAG 最终还是要让模型生成回答。

但高质量 RAG 回答应该做到：

```text
回答用户问题；
引用检索到的资料；
区分事实和推测；
遇到资料不足时说不知道；
说明适用边界；
给出下一步建议；
必要时请求人工确认。
```

低质量回答常见问题：

```text
看起来很流畅，但没有依据；
引用了无关文档；
把旧规则当新规则；
把案例当成通用原则；
明明资料不足，却强行回答；
没有说明风险和边界。
```

引用溯源非常重要。

因为它能让人检查：

```text
答案依据是否正确；
检索是否找对；
知识是否过期；
系统错在哪里。
```

## 17. RAG 的常见形态

RAG 不是一种固定架构，而是一类方法。

常见形态包括：

| 类型 | 特点 | 适合场景 |
|---|---|---|
| Naive RAG | 文档切块 -> 向量检索 -> 拼上下文 -> 回答 | 个人验证、简单知识库 |
| Advanced RAG | Query 改写、混合检索、Rerank、过滤、引用 | 小团队 / 企业知识库 |
| Modular RAG | 检索、重排、生成、评测等模块可组合 | 复杂业务系统 |
| Agentic RAG | Agent 根据任务多轮检索和调用工具 | 需要推理和任务执行的场景 |
| GraphRAG | 用实体关系和图结构增强检索 | 关系复杂、需要全局理解 |
| Multi-modal RAG | 文本、图片、表格、音频等多模态检索 | 图纸、票据、医疗、工业文档 |

初学者建议先理解：

```text
Naive RAG -> Advanced RAG -> GraphRAG / Agentic RAG
```

不要一开始就追求最复杂方案。

## 18. GraphRAG 和 LightRAG 在 RAG 体系里的位置

### 18.1 GraphRAG

GraphRAG 可以理解成：

```text
普通 RAG 主要按文本相似度找资料；
GraphRAG 还会利用实体、关系、社区和路径来找资料。
```

适合：

```text
人物、组织、项目、客户、设备之间关系复杂；
需要回答“谁影响谁”“为什么”“上下游关系是什么”；
单段文本检索不够，需要全局结构理解。
```

例如：

```text
某客户投诉和哪些项目、交付团队、产品模块有关？
某个家庭成员的饮食禁忌影响哪些菜谱？
某个供应商质量问题影响哪些订单和客户？
```

GraphRAG 横跨两个模块：

```text
03 RAG：它是一种检索增强生成方法；
08 知识图谱：它依赖实体、关系、图结构。
```

### 18.2 LightRAG

LightRAG 可以理解成一种轻量图增强 RAG 方案。

它的重点通常在于：

```text
用较轻量的方式抽取实体和关系；
建立文本块与实体关系之间的索引；
同时支持局部检索和全局检索；
让回答既能利用具体片段，也能利用关系结构。
```

它适合放在：

```text
07 框架对比：和 WeKnora、Reme 等具体方案比较；
03 RAG：理解它的检索链路；
08 知识图谱：理解它的关系增强能力。
```

## 19. RAG 评测：怎么知道它真的有效

RAG 不评测，就只能凭感觉。

RAG 评测至少分三层。

### 19.1 检索评测

看系统有没有找到正确资料。

常见问题：

```text
该找的没找出来；
找出来的排得太靠后；
找出来很多无关内容；
找到了过期内容；
权限过滤失败。
```

常见指标：

```text
Recall@K：正确资料是否出现在前 K 个结果里；
Precision@K：前 K 个结果里有多少是真的相关；
MRR：第一个正确结果排在多前；
nDCG：排序质量。
```

初学者不用先深究公式，先理解问题：

```text
有没有把正确资料找出来，并排在前面？
```

### 19.2 生成评测

看模型基于资料回答得好不好。

关注：

```text
是否忠于资料；
是否回答完整；
是否有幻觉；
是否引用正确；
是否表达清楚；
是否知道资料不足时拒答。
```

### 19.3 业务评测

看回答是否真的有用。

例如家庭营养师 Agent：

```text
用户是否采纳菜单；
是否避开禁忌食材；
饭后满意度是否提高；
是否减少重复决策成本。
```

企业知识库：

```text
客服是否更快解决问题；
销售跟进是否更有效；
工单处理是否减少返工；
新人学习成本是否下降。
```

这才是知识复利最关心的评测。

## 20. RAG 常见失败模式

### 20.1 找不到

```text
原因：文档没入库、切块不合理、索引差、query 太模糊。
```

### 20.2 找错了

```text
原因：embedding 不适合中文业务、关键词缺失、元数据不足、混合检索缺失。
```

### 20.3 找到了但没用好

```text
原因：上下文组装差、Prompt 没约束、模型忽略关键规则。
```

### 20.4 引用了过期知识

```text
原因：没有版本、没有有效期、没有 deprecated 状态。
```

### 20.5 答案看起来对，但无法追溯

```text
原因：没有 citation、没有 source id、没有文档片段记录。
```

### 20.6 权限泄露

```text
原因：检索阶段没有做权限过滤，或者过滤只在展示层做。
```

### 20.7 评测缺失

```text
原因：没有 golden dataset，没有真实问题集，没有人工反馈闭环。
```

## 21. RAG 与权限、安全和治理

企业和团队场景里，RAG 不能只看效果，还要看治理。

关键问题包括：

```text
用户是否有权检索这份文档？
Agent 是否有权读取这个知识库？
检索结果是否包含敏感信息？
日志里是否保存了不该保存的内容？
向量库里是否能删除指定数据？
知识更新后旧索引是否同步更新？
离职员工权限是否及时撤销？
```

权限最好在检索阶段就生效，而不是生成完答案后再过滤。

否则模型可能已经看到了不该看的内容。

## 24. 初学者学习 RAG 的推荐顺序

建议按这个顺序学：

```text
1. 先理解 RAG 是“开卷考试”
2. 理解文档如何被解析、切块、入库
3. 理解 Embedding 和向量检索
4. 理解关键词检索和混合检索
5. 理解 Query 改写和多路检索
6. 理解 Reranker 为什么重要
7. 理解上下文组装和 Prompt 约束
8. 理解引用溯源和 Grounding
9. 理解 RAG 评测
10. 再看 GraphRAG、LightRAG、Agentic RAG
```

不要一开始就纠结：

```text
到底哪个向量库最好？
哪个 embedding 模型排名最高？
GraphRAG 是不是一定比普通 RAG 强？
```

先问：

```text
我的知识是什么类型？
用户会怎么问？
正确答案依赖哪些资料？
资料能不能被稳定检索出来？
回答有没有引用依据？
错了以后能不能反馈修正？
```

## 25. 与其他模块的关系

- 依赖 01 知识工程提供高质量知识源；
- 承接 02 全链路概览中的“索引、检索、上下文组装”；
- 需要 04 评测模块判断召回和生成质量；
- 需要 05 Prompt / 任务协议约束模型如何使用上下文；
- 是 06 Harness 中 Agent 调用企业知识的主要通道；
- 可与 08 知识图谱结合做 GraphRAG；
- 需要 10 私有化部署与治理模块解决权限、审计、成本问题。
