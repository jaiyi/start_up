# 01 · 知识工程与知识资产设计

> 目标：理解知识复利系统的“原材料工程”。在模型、RAG、Agent 之前，先回答：什么知识值得沉淀，如何沉淀，如何治理，如何让它被人和 Agent 持续使用并不断变好。

---

## 1. 这个模块解决什么问题

知识复利系统的起点不是模型，而是知识资产设计。

一个组织里最有价值的知识，往往不是已经整理好的正式文档，而是散落在这些地方：

```text
一线沟通
会议纪要
项目复盘
客户反馈
工单备注
销售跟进
老板点评
专家经验
失败案例
SOP 之外的变通做法
```

这些内容如果没有被组织起来，就只是“经验”。

只有当它们被结构化、可检索、可引用、可反馈、可更新、可治理，并能被人和 Agent 在真实流程中调用，才会变成“知识资产”。

这个模块回答：

```text
什么知识值得进入系统？
知识应该如何分类、结构化、治理和更新？
如何让知识既能被人阅读，也能被 Agent 调用？
什么知识应该放文档，什么知识应该放表，什么知识应该进图谱？
如何避免知识库变成新的知识坟场？
```

如果知识本身没有被设计好，RAG 和 Agent 只会更快地暴露混乱。

---

## 2. 它在知识复利系统中的位置

知识工程位于所有 AI 应用之前，是把组织经验变成可复用资产的前置层。

```text
业务现场
  ↓
一手信息 / 数据证据 / 经验案例
  ↓
知识资产设计
  ↓
RAG / 图谱 / Agent / Workflow
  ↓
真实使用
  ↓
反馈修正
  ↓
知识资产继续更新
```

如果没有这一层，后面的技术都会变成“在混乱材料上做自动化”。

典型问题包括：

```text
文档过期，RAG 仍然引用；
知识没有负责人，错了没人改；
经验只存在老员工脑子里；
规则和例外混在一起；
案例没有结果反馈；
数据表能说明发生了什么，但不能解释为什么；
Agent 调用了知识，却不知道这条知识是否可信、是否适用于当前场景。
```

因此，知识工程不是“多写文档”，而是设计一套让知识进入生产循环的机制。

---

## 3. 核心概念

### 3.1 数据、信息、知识、判断、行动

知识复利系统里，不能把所有内容都叫“知识”。

可以先按五层区分：

```text
数据：发生了什么
信息：数据被整理后表达了什么
知识：这件事意味着什么
判断：基于知识应该怎么选择
行动：下一步应该怎么做
```

例如：

```text
数据：某客户连续 3 次推迟付款。
信息：该客户账期异常。
知识：该行业客户在资金紧张时通常会先拖延非核心供应商付款。
判断：这个客户存在回款风险。
行动：暂停追加授信，并由销售负责人发起回款沟通。
```

知识工程要做的，不是把所有材料都存起来，而是把这些层次之间的关系整理清楚。

---

### 3.2 业务对象

业务对象是知识系统的骨架。

常见业务对象包括：

```text
客户
订单
项目
合同
产品
菜谱
家庭成员
供应商
设备
工单
指标
风险
异常
```

如果没有业务对象，知识库就会变成一堆文档。

有了业务对象，知识才能围绕对象沉淀：

```text
这个客户有哪些历史沟通？
这个订单有哪些风险？
这个供应商有哪些质量问题？
这个菜谱适合哪些家庭成员？
这个工单属于哪类异常？
```

---

### 3.3 事实、规则、案例、流程、反馈

知识资产至少可以分成五类：

| 类型 | 说明 | 示例 |
|---|---|---|
| 事实 | 已发生、可核验的记录 | 客户 A 上月采购 20 万；孩子反馈牛肉太硬 |
| 规则 | 稳定约束或判断标准 | 毛利率低于 20% 需要复核；过敏食材不得推荐 |
| 案例 | 一次完整情境和处理结果 | 某客户异议如何处理并成交 |
| 流程 | 一组可重复执行的步骤 | 新客户跟进流程；周菜单生成流程 |
| 反馈 | 对结果的评价和修正依据 | 这次推荐不适合老人；该话术转化率低 |

这五类知识不能混在一起。

如果规则和案例混在一起，Agent 会把个案当通用规律。  
如果事实和观点混在一起，系统会把主观判断当客观依据。  
如果流程和反馈断开，知识就无法迭代。

---

### 3.4 知识资产与知识债务

不是所有沉淀都会形成复利。

高质量知识资产通常具备：

```text
来源清楚
适用场景清楚
负责人清楚
更新时间清楚
使用方式清楚
反馈入口清楚
可被检索
可被引用
可被修正
可被下游流程调用
```

知识债务则表现为：

```text
过期但没人删；
重复但没人合并；
冲突但没人裁决；
来源不明但被引用；
只有结论没有依据；
只有经验没有边界；
只有文档没有使用场景；
只有知识库没有反馈机制。
```

知识复利工程师需要同时做两件事：

```text
增加知识资产；
减少知识债务。
```

---

## 4. 知识复利的专业理论框架

这一部分是知识工程的核心。否则很容易把“知识库建设”理解成资料整理，把“知识复利”理解成文档越多越好。

真正的知识复利系统，至少要同时理解以下几组框架：

```text
知识层次框架：数据、信息、知识、判断、行动
知识转化框架：隐性知识如何显性化、结构化、流程化
知识生命周期框架：知识从产生到退役的全过程
知识质量框架：如何判断一条知识是否可信、可用、可复用
知识治理框架：谁负责、谁审核、谁使用、谁更新
知识反馈框架：知识是否真的改善了业务结果
知识成熟度框架：一个组织的知识能力处在哪个阶段
```

---

### 4.1 DIKW-A 框架：从 Data 到 Action

传统知识管理里常见 DIKW：

```text
Data -> Information -> Knowledge -> Wisdom
数据 -> 信息 -> 知识 -> 智慧
```

但在知识复利工程里，更适合改造成 DIKJA 或 DIKW-A：

```text
Data -> Information -> Knowledge -> Judgment -> Action
数据 -> 信息 -> 知识 -> 判断 -> 行动
```

因为企业和个人最终需要的不是抽象“智慧”，而是能不能在特定上下文里做出更好的判断和行动。

| 层级 | 关注问题 | 典型载体 | Agent 使用方式 |
|---|---|---|---|
| Data 数据 | 发生了什么 | 表格、日志、交易、行为记录 | 查询、统计、证据引用 |
| Information 信息 | 数据表达了什么 | 报表、摘要、指标解释 | 概括、聚合、异常提示 |
| Knowledge 知识 | 这意味着什么 | 规则、案例、经验、SOP | 解释、匹配、推理 |
| Judgment 判断 | 应该如何选择 | 决策标准、风险权重、优先级 | 给出建议、比较方案 |
| Action 行动 | 接下来做什么 | 工作流、任务、审批、消息 | 执行、调用工具、生成任务 |

知识复利工程师要避免两个误区：

```text
只停在 Data / Information：系统只能回答“发生了什么”，不能指导行动；
直接跳到 Action：Agent 可以执行动作，但没有足够知识依据，风险很高。
```

更好的设计是：

```text
数据提供证据；
知识解释意义；
判断给出取舍；
流程约束行动；
反馈修正下一次判断。
```

---

### 4.2 显性知识与隐性知识：SECI 转化框架

组织中最有价值的知识，常常是隐性知识。

隐性知识包括：

```text
老员工知道但说不清的判断；
业务专家在现场形成的直觉；
销售面对客户时的微妙分寸；
厨师知道“差不多就行”的火候；
项目经理判断风险时依赖的经验模式。
```

经典知识管理理论里，Nonaka 提出过 SECI 模型，用来描述隐性知识和显性知识之间的转化：

```text
Socialization：社会化，隐性知识 -> 隐性知识
Externalization：外化，隐性知识 -> 显性知识
Combination：组合，显性知识 -> 显性知识
Internalization：内化，显性知识 -> 隐性知识
```

放到知识复利工程中，可以这样理解：

| 阶段 | 原始含义 | 在知识复利系统中的含义 | 典型动作 |
|---|---|---|---|
| Socialization 社会化 | 人与人之间通过共事传递经验 | 新人跟着专家做事，观察专家判断 | 跟单、旁听、师徒制、复盘会 |
| Externalization 外化 | 把隐性经验表达出来 | 把专家判断拆成规则、案例、边界和例外 | 访谈、案例卡片、决策树、SOP |
| Combination 组合 | 把显性知识重新组织 | 把分散文档、数据、规则、案例组合成知识资产 | 知识库、图谱、索引、标签体系 |
| Internalization 内化 | 人通过使用显性知识形成能力 | 人或 Agent 在流程中使用知识并形成新经验 | 任务执行、Agent 推荐、培训、反馈 |

知识复利的关键不是只做 Externalization，把专家经验写成文档；而是形成完整循环：

```text
专家经验
  ↓ 外化
规则 / 案例 / SOP
  ↓ 组合
知识资产体系
  ↓ 使用
业务流程 / Agent 协作
  ↓ 反馈
新的经验和修正
```

如果只外化、不使用，知识会变成静态文档。  
如果只使用、不反馈，知识会逐渐过期。  
如果只反馈、不治理，知识会越来越混乱。

---

### 4.3 知识生命周期框架

知识不是一次性创建的内容，而是有生命周期的资产。

一个完整的知识生命周期可以分成九个阶段：

```text
识别 -> 捕获 -> 结构化 -> 验证 -> 发布 -> 嵌入 -> 使用 -> 反馈 -> 更新 / 退役
```

| 阶段 | 核心问题 | 产物 | 风险 |
|---|---|---|---|
| 识别 | 哪些经验值得沉淀 | 知识需求清单 | 把低价值材料也纳入系统 |
| 捕获 | 从哪里获取一手知识 | 访谈、纪要、案例、数据记录 | 只捕获二手转述 |
| 结构化 | 用什么格式表达 | 卡片、表格、图谱、流程 | 只有文本，没有元数据 |
| 验证 | 是否准确可信 | 审核记录、证据链 | 未经验证就被 Agent 调用 |
| 发布 | 谁可以看到和使用 | 知识库条目、版本 | 权限不清、误用知识 |
| 嵌入 | 进入哪个业务流程 | RAG、Agent、Workflow、SOP | 只存不用 |
| 使用 | 是否被真实任务调用 | 引用记录、任务日志 | 使用不可观测 |
| 反馈 | 使用后效果如何 | 纠错、评分、结果反馈 | 反馈没有回流 |
| 更新/退役 | 是否继续有效 | 新版本、归档、删除 | 过期知识持续污染系统 |

知识复利工程师需要特别关注三处断点：

```text
捕获断点：一线知识没有进入系统；
嵌入断点：知识存在，但没有进入流程；
反馈断点：知识被使用，但效果没有回流。
```

这三个断点决定了一个知识库是“资料仓库”，还是“复利系统”。

### 4.4 知识半衰期框架

不同知识的有效期不同。

知识半衰期指：一条知识从“高度可信 / 高度有用”衰减到“需要复核 / 可能失效”的时间。

| 知识类型 | 半衰期特征 | 示例 | 治理方式 |
|---|---|---|---|
| 基础事实 | 相对稳定 | 家庭成员出生年月、客户统一社会信用代码 | 低频复核 |
| 偏好知识 | 中速变化 | 孩子近期不爱吃牛肉、客户偏好线上沟通 | 定期确认 |
| 业务规则 | 取决于制度变化 | 审批规则、报价规则、饮食禁忌 | 版本管理 + 责任人 |
| 市场判断 | 快速变化 | 竞品策略、客户预算倾向 | 高频复盘 |
| 流程 SOP | 中速变化 | 工单处理流程、菜单生成流程 | 按反馈优化 |
| 案例经验 | 价值长期存在，但适用边界会变 | 某次客户异议处理 | 保留上下文和边界 |
| 模型 / 工具用法 | 快速变化 | 某个框架的最佳实践 | 标注版本和时间 |

因此，知识资产需要有 `review_cycle` 和 `valid_until`，而不是只有 `created_at`。

一个简单判断：

```text
如果一条知识会影响 Agent 的判断或行动，它就必须有有效期和复核机制。
```

### 4.5 知识质量评估框架

不是所有知识都应该进入高优先级知识库。

可以用七个维度评估知识质量：

| 维度 | 问题 | 低质量表现 | 高质量表现 |
|---|---|---|---|
| 准确性 | 是否真实可靠 | 来源不明、未经核实 | 有证据、有审核 |
| 完整性 | 是否缺关键上下文 | 只有结论，没有条件 | 有场景、边界、例外 |
| 时效性 | 是否仍然有效 | 多年前规则仍被引用 | 有更新时间和复核周期 |
| 可解释性 | 能否说明为什么 | 只说“应该这样做” | 有原因、依据、案例 |
| 可操作性 | 能否指导行动 | 抽象口号 | 可转成步骤、规则、检查项 |
| 可检索性 | 能否被找到 | 标题混乱、无标签 | 有对象、标签、摘要、元数据 |
| 可复用性 | 能否用于相似场景 | 只适合一次性事件 | 有适用范围和迁移条件 |

知识复利工程师应该给重要知识设置质量等级，例如：

```yaml
quality_level: validated
confidence: high
evidence:
  - source: 客户复盘会议
  - source: CRM 成交记录
reviewer: 业务负责人A
last_reviewed_at: 2026-09-16
```

不要让 Agent 平等对待所有文本。

它需要知道：

```text
哪些是正式规则；
哪些是经验建议；
哪些是未经验证的观察；
哪些是历史归档；
哪些是已经废弃的旧知识。
```

### 4.6 知识可信度与证据链框架

在 AI 系统中，知识可信度比“有没有相关文本”更重要。

一条知识最好能追溯到证据链：

```text
结论
  ↓
依据
  ↓
原始事实 / 数据 / 案例
  ↓
来源人 / 来源系统
  ↓
时间和版本
```

可以把知识分成四种可信度状态：

| 状态 | 含义 | 是否可被 Agent 用于行动 |
|---|---|---|
| Draft 草稿 | 尚未验证的记录或想法 | 不建议直接用于行动 |
| Observed 观察 | 来自真实场景，但未总结规律 | 可作为参考，不可作为规则 |
| Validated 已验证 | 被业务负责人确认，可复用 | 可用于建议和流程判断 |
| Deprecated 已废弃 | 曾经有效，现在不再适用 | 不应进入检索结果，或只作历史参考 |

这对 RAG 很关键。

普通 RAG 往往只关心“语义相关”。  
知识复利系统还要关心“治理状态”。

```text
相关但已废弃的知识，不能优先返回；
相关但未经验证的知识，不能被当成正式依据；
相关但适用范围不匹配的知识，不能被泛化使用。
```

---

### 4.7 知识库存与知识流动框架

知识资产有两个状态：

```text
知识库存：已经沉淀下来的知识资产；
知识流动：知识在任务、流程、人和 Agent 之间被使用和更新的过程。
```

很多组织只建设知识库存：

```text
文档数量；
知识库条目数；
上传文件数；
问答对数量。
```

但知识复利更关心知识流动：

```text
哪些知识被使用；
在哪些任务中被使用；
使用后结果是否变好；
哪些知识经常被纠错；
哪些知识长期无人访问；
哪些知识触发了流程改进。
```

可以用一个公式理解：

```text
知识复利 = 高质量知识库存 × 高频真实使用 × 有效反馈更新
```

只增加库存，不增加流动，知识会沉淀成成本。  
只追求流动，没有高质量库存，Agent 会把噪声放大。  
只有反馈回流，知识才会持续增值。

---

### 4.8 单环学习、双环学习与三环学习

知识反馈不只是“这条回答对不对”。

组织学习理论里可以分成三层：

| 类型 | 关注问题 | 示例 |
|---|---|---|
| 单环学习 | 这次做错了什么，怎么修正动作 | 菜谱太咸，下次减少盐 |
| 双环学习 | 原来的规则或假设是否错了 | 原来按成人口味设计晚餐，不适合孩子 |
| 三环学习 | 我们学习和更新知识的机制是否有效 | 是否需要新增饭后反馈表和菜谱版本机制 |

对应到知识复利系统：

```text
单环：修正具体知识条目；
双环：修正规则、流程、分类体系；
三环：修正知识治理机制本身。
```

如果只有单环学习，系统会不断打补丁。  
如果能形成双环学习，系统会改进判断框架。  
如果能形成三环学习，组织会改进自己的学习方式。

知识复利工程师真正要推动的是后两层。

### 4.9 知识成熟度模型

可以用 0-5 级判断一个组织的知识复利能力。

| 等级 | 状态 | 典型表现 | AI 应用风险 |
|---|---|---|---|
| L0 无意识 | 知识只在人脑中 | 靠老员工、靠口口相传 | Agent 无知识可用 |
| L1 文档化 | 有文档，但分散 | 飞书、Word、PDF、群消息 | RAG 检索噪声大 |
| L2 结构化 | 有模板、标签、对象 | 知识卡片、SOP、案例库 | 可做基础 RAG |
| L3 流程化 | 知识进入业务流程 | 工单、销售、菜单、审批中可调用 | Agent 可辅助任务 |
| L4 反馈化 | 使用结果反向更新知识 | 纠错、评分、复盘、版本更新 | Agent 能持续改进 |
| L5 治理化 / 复利化 | 有负责人、指标、权限、评测 | 知识质量和业务结果联动 | 可建设企业级 harness |

一个关键判断：

```text
没有到 L3，不适合谈复杂 Agent；
没有到 L4，很难形成知识复利；
没有到 L5，规模化后会出现知识污染和治理失控。
```

---

### 4.10 知识资产负债表框架

可以像看财务一样看知识。

| 类别 | 说明 | 示例 |
|---|---|---|
| 知识资产 | 能反复使用并改善结果的知识 | 已验证 SOP、专家案例、规则库、反馈库 |
| 知识负债 | 未来会造成误导和维护成本的知识 | 过期文档、冲突规则、重复问答 |
| 知识现金流 | 新知识产生、使用和更新的速度 | 每周复盘、饭后反馈、客户复盘 |
| 知识折旧 | 知识随时间失效 | 市场信息、工具教程、偏好变化 |
| 知识投资 | 为未来复利而做的沉淀 | 建模板、建标签、建评测集、建反馈机制 |

这套框架的价值在于，它能让知识工程从“整理资料”变成“经营资产”。

可以问：

```text
我们现在增加的是知识资产，还是知识负债？
这些文档未来会减少重复劳动，还是增加维护成本？
哪些知识正在折旧？
哪些知识产生了真实业务回报？
```

---

### 4.11 任务嵌入框架：知识必须进入工作流

知识不进入任务，就不会产生复利。

知识进入任务通常有四种方式：

| 方式 | 说明 | 示例 |
|---|---|---|
| 检索嵌入 | 人或 Agent 在需要时检索 | 查询菜谱、查询 SOP |
| 决策嵌入 | 知识影响判断和推荐 | 根据禁忌规则过滤菜谱 |
| 流程嵌入 | 知识成为流程节点 | 生成菜单前必须检查库存 |
| 反馈嵌入 | 任务结果反向更新知识 | 饭后反馈更新菜谱适配性 |

很多知识库只做到检索嵌入，所以价值有限。

知识复利系统至少要做到：

```text
检索嵌入 + 决策嵌入 + 反馈嵌入
```

如果面向企业级 Agent，还需要流程嵌入。

---

### 4.12 知识治理框架：Owner、Steward、User、Agent

知识治理不是大企业才需要。只要知识会影响判断，就需要治理。

可以把角色分成四类：

| 角色 | 职责 | 示例 |
|---|---|---|
| Knowledge Owner | 对知识正确性和业务结果负责 | 业务负责人、家庭决策者 |
| Knowledge Steward | 维护知识结构、标签、版本、质量 | 知识复利工程师、运营人员 |
| Knowledge User | 在任务中使用知识 | 销售、客服、家庭成员 |
| Agent Consumer | 自动检索和调用知识的 Agent | 菜单 Agent、销售 Agent、工单 Agent |

Agent 的出现会放大治理要求。

过去错误文档只是“没人看”。  
现在错误知识可能被 Agent 自动引用、总结、执行，影响真实流程。

因此知识治理至少要明确：

```text
谁有权创建正式知识？
谁有权修改规则？
谁有权废弃旧知识？
Agent 可以读取哪些知识？
Agent 可以基于哪些知识采取行动？
哪些知识只能供参考，不能自动执行？
```

## 5. 知识资产的基本类型

### 5.1 业务对象卡片

用于描述一个稳定存在的业务对象。

适合：客户、产品、供应商、菜谱、设备、项目、合同等。

建议字段：

```yaml
id: customer_acme_001
name: 某客户
type: 客户
owner: 销售A
status: 重点跟进
source: CRM / 会议纪要 / 销售记录
updated_at: 2026-09-16
related_objects:
  - 合同X
  - 项目Y
  - 竞品Z
key_facts:
  - 近三个月采购额下降
  - 对交付稳定性敏感
risks:
  - 回款周期变长
open_questions:
  - 是否存在预算收缩
```

---

### 5.2 规则卡片

用于描述稳定约束、判断标准和硬规则。

适合：合规规则、业务判断阈值、饮食禁忌、审批规则、风控规则。

建议字段：

```yaml
rule_id: nutrition_allergy_001
rule_name: 过敏食材禁止推荐
scope: 家庭营养师 Agent
priority: high
condition: 家庭成员对某食材过敏
action: 禁止推荐包含该食材的菜谱
source: 用户显式偏好 / 医嘱
owner: lijiayi
status: validated
confidence: high
review_cycle: 每 6 个月
valid_until: 2027-03-16
```

关键点：规则必须有适用范围、优先级、可信度和复核周期。否则 Agent 很容易把局部规则泛化。

---

### 5.3 SOP / 流程卡片

用于描述一组可重复执行的动作。

适合：客户跟进流程、工单处理流程、周菜单生成流程、复盘流程。

建议字段：

```yaml
process_id: weekly_menu_generation
name: 每周菜单生成流程
trigger: 每周日晚上
inputs:
  - 家庭成员偏好
  - 本周库存
  - 营养目标
  - 历史反馈
steps:
  - 检查禁忌和过敏
  - 读取库存和常用菜谱
  - 生成候选菜单
  - 检查营养均衡
  - 请求用户确认
outputs:
  - 周菜单
  - 需要补充的食材
human_confirmation:
  - 最终菜单确认
  - 新菜谱加入知识库
feedback_points:
  - 是否实际执行
  - 家庭成员是否满意
  - 是否需要调整菜谱
```

---

### 5.4 案例卡片

用于沉淀一次真实情境、处理过程和结果。

适合：销售异议处理、客户成功案例、质量异常、菜谱反馈、项目复盘。

建议字段：

```yaml
case_id: case_20260916_001
case_type: 客户异议处理
context: 客户担心部署周期过长
actions:
  - 提供类似行业案例
  - 拆分一期和二期范围
  - 明确上线验收标准
result: 客户接受一期方案
lessons:
  - 对周期敏感客户要先降低首期范围
  - 案例比功能清单更有说服力
applicable_to:
  - 中小企业客户
  - 首次 AI 项目
not_applicable_to:
  - 已有成熟 AI 团队的大客户
evidence:
  - 会议纪要
  - CRM 成交记录
```

案例卡片的重点不是“发生过什么”，而是要沉淀：

```text
这个案例对下一次有什么帮助？
在什么边界内可以复用？
在哪些场景下不应该复用？
```

---

### 5.5 反馈卡片

用于记录知识或 Agent 输出在真实使用后的效果。

适合：菜谱反馈、销售话术反馈、RAG 回答纠错、Agent 任务执行结果。

建议字段：

```yaml
feedback_id: feedback_20260916_001
related_object: 番茄牛肉汤
related_task: 晚餐推荐
user_feedback: 孩子觉得牛肉太硬
result_rating: 2/5
reason: 口感不适合孩子
suggested_update:
  - 牛肉切小块
  - 延长炖煮时间
  - 儿童版本减少纤维感
update_required: true
learning_type: single_loop
```

反馈卡片是知识复利的核心。没有反馈，知识只会堆积，不会进化。

## 6. 典型技术路线

| 路线 | 适合场景 | 优点 | 风险 |
|---|---|---|---|
| 结构化 Markdown | 个人 / 小团队知识库、家庭知识库、轻量 SOP | 简单、可读、可导出、Git 友好 | 依赖人工规范，规模大后治理成本上升 |
| Wiki / 文档系统 | 团队知识沉淀、流程规范、培训材料 | 协作和权限较好 | 容易变成没人看的文档库 |
| 表格 / 数据库 | 业务对象、清单、状态、指标、反馈记录 | 结构化强、便于统计 | 容易割裂文本语境 |
| 知识卡片 | 菜谱、案例、问题、方案、规则等可复用单元 | 易复用、易进入 RAG 和 Agent | 需要设计模板和元数据 |
| 知识图谱 | 实体关系复杂、需要关系查询和路径解释 | 关系表达强，可解释性好 | 容易过度设计 |
| Agent Memory | 个性化、长期偏好、任务状态 | 适合个体偏好和上下文连续性 | 容易和正式知识库边界混乱 |

一个实用判断：

```text
稳定规则和 SOP：优先结构化 Markdown / Wiki；
业务对象状态：优先表格 / 数据库；
复杂关系和路径：考虑知识图谱；
短期上下文和个性化偏好：考虑 Agent Memory；
需要人长期阅读和协作：优先 Wiki / 文档系统。
```

## 8. 知识资产设计的基本原则

### 8.1 先业务对象，后文档目录

不要先问：

```text
文档应该放在哪个文件夹？
```

而要先问：

```text
这个业务里有哪些关键对象？
围绕这些对象，会发生哪些任务、规则、案例和反馈？
```

例如家庭营养师 Agent 里，关键对象不是“文档”，而是：

```text
家庭成员
菜谱
食材
库存
餐次
营养目标
饭后反馈
禁忌规则
```

---

### 8.2 先高频场景，后完整知识库

不要一开始追求“大而全”。

优先沉淀高频、反复发生、能反馈的场景：

```text
每周菜单生成；
菜谱适配老人/孩子；
库存食材消耗；
饭后反馈影响下次推荐。
```

这些场景会不断产生反馈，最容易形成复利。

---

### 8.3 先可维护，再智能

知识资产必须先可维护，再谈智能调用。

如果知识没有负责人、没有更新时间、没有适用范围，Agent 调用得越多，风险越大。

每条重要知识至少要有：

```text
来源
负责人
适用范围
更新时间
是否仍有效
反馈入口
```

---

### 8.4 区分正式知识和工作记忆

正式知识适合进入知识库：

```text
规则
SOP
稳定案例
已验证经验
长期偏好
```

工作记忆适合进入 Agent Memory 或任务状态：

```text
本次对话上下文
临时任务进度
短期偏好
尚未验证的观察
```

如果把短期工作记忆直接沉淀为正式知识，会制造知识污染。

---

### 8.5 每个知识条目都要考虑反馈路径

知识条目不是写完就结束。

每个知识资产都要能回答：

```text
谁使用了它？
在哪个任务中使用？
结果好不好？
有没有被质疑？
是否需要更新？
更新由谁负责？
```

没有反馈路径的知识，很难产生复利。

## 9. 适合个人 / 小团队 / 企业的落地方式

| 场景 | 推荐起点 | 不建议一开始做什么 |
|---|---|---|
| 个人验证 | Markdown 知识卡片 + Obsidian / Git 管理 + 轻量 RAG | 不急着上复杂权限和图数据库 |
| 家庭知识库 | 结构化 Markdown + 标签 + 反馈记录 | 不把所有家庭信息混成一个大文档 |
| 小团队组织记忆 | Wiki / WeKnora / RAGFlow + 权限 + 反馈机制 | 不只建 FAQ，不设负责人和更新机制 |
| 企业知识复利系统 | 知识资产模型 + 数据证据 + 权限治理 + RAG / Agent / 评测闭环 | 不把核心组织记忆锁死在不可导出的 SaaS 里 |

## 10. 与其他模块的关系

- 是 RAG 链路的知识源；
- 是知识图谱建模的输入；
- 是 Agent 任务执行的上下文；
- 是评测集构造的依据；
- 是治理和权限设计的对象；
- 是数据证据化的承载结构。
