# 09 · 知识图谱工程：DeepKE / Nebula Graph / Neo4j

## 1. 这个模块解决什么问题

知识图谱不是为了“看起来高级”，而是为了解决实体关系复杂、上下文依赖强、需要关系追踪和可解释展示的问题。

这个模块回答：

```text
什么时候需要知识图谱？
如何从文本中抽取实体、关系和事件？
图数据库在知识复利系统中到底承担什么角色？
```

---

## 2. 它在知识复利系统中的位置

```text
非结构化知识 / 业务数据
  ↓
实体、关系、事件抽取
  ↓
图数据库 / 图谱结构
  ↓
GraphRAG / 关系查询 / 路径解释
  ↓
Agent 调用 / 人工分析 / 可视化
```

知识图谱位于“知识资产结构化”和“RAG / Agent 增强”之间。

## 4. 典型技术路线

| 路线 | 适合场景 | 风险 |
|---|---|---|
| LLM 抽取 | 快速从文本中抽实体关系 | 稳定性、成本、幻觉 |
| DeepKE / NLP 抽取 | 专业抽取任务、可训练模型 | 数据标注和训练成本 |
| 规则抽取 | 格式稳定、规则明确 | 泛化能力弱 |
| Neo4j | 中小规模图谱、生态成熟、可视化友好 | 商业版能力、扩展成本 |
| Nebula Graph | 大规模图存储和图计算 | 运维和学习成本更高 |
| GraphRAG | 复杂关系增强检索 | 构图质量决定效果，成本较高 |

## 7. GraphRAG 检索架构：图谱用于组织证据，不是替代证据

图谱增强检索的核心，不是把实体、关系和更多节点直接塞给模型，而是利用图结构组织更相关、更完整、可校验的检索上下文。一个更稳妥的检索链路是：

```text
Query 解析：实体 / 车型或版本 / 时间 / 高低层关键词
  ↓
并行召回：Entity TopK | Relationship TopK | Chunk TopK
  ↓
关系扩展 → 证据融合 → 去重与排序
  ↓
车型版本 / 来源 / 生效时间校验
  ↓
Context 构建 → LLM 生成答案
```

### 7.1 三条证据通道

| 通道 | 主要作用 | 不能替代什么 |
|---|---|---|
| Entity TopK | 找到问题涉及的实体、别名、实体类型和候选版本 | 不能单独证明实体之间的事实关系 |
| Relationship TopK | 找到实体之间的关系、路径、上下游和影响范围 | 不能完整提供原始文本中的条件、例外和细节 |
| Chunk TopK | 返回原始文档片段、表格、说明和上下文 | 不能单独承担复杂多跳关系扩展 |

实体和关系召回用于缩小范围、扩展上下文和组织证据；原文 Chunk 仍然是不可缺少的证据通道。图谱抽取不完整、关系方向错误或属性遗漏时，原文可以补足细节，也可以作为最终回答的引用依据。

### 7.2 关系扩展与证据融合

初始召回后，不应简单地把所有节点和文本拼接给 LLM，而应经过一轮确定性的上下文整理：

1. **关系扩展**：从高置信实体出发，按允许的关系类型和 hop 数扩展；
2. **证据融合**：将实体属性、关系事实、原始 Chunk 和来源元数据绑定在一起；
3. **去重**：合并同一事实的重复节点、重复关系和相邻文本片段；
4. **排序**：综合查询相关性、关系路径、来源可信度、时间有效性和证据完整度排序；
5. **保留溯源**：每个进入 Context 的事实都尽量保留来源文档、片段、版本和抽取状态。

这一步的目标是提高证据密度和结构清晰度，而不是无上限增加上下文长度。更多节点不等于更多有效信息，关系扩展也可能把无关邻居和过期事实带入答案。

### 7.3 实体归属与版本校验应前置

实体消歧、车型 / 产品归属、版本和生效时间校验应尽可能发生在召回和 Context 构建阶段，而不是等答案生成后再用 Prompt 要求模型“忽略其他版本”。例如用户明确询问“2025 款”时，检索链路应优先完成：

```text
识别目标实体
→ 解析车型 / 产品归属
→ 解析版本、年份和生效时间
→ 过滤不匹配或已失效事实
→ 再进行关系扩展和文本召回
```

如果版本信息无法确认，应输出“版本待确认”或保留多个候选并要求用户澄清，而不是静默混合 2025 款和 2026 款信息。版本校验至少应覆盖：

- 实体所属车型、产品线或业务对象；
- 年款、软件版本、配置版本或文档版本；
- 事实的生效时间和失效时间；
- 来源文档发布时间、更新状态和权威等级；
- 同名实体、别名和跨版本实体的消歧结果。

### 7.4 图谱增强收益的正确理解

GraphRAG 的收益应来自**更高质量的证据组织**，而不是单纯增加上下文数量：

- 用实体召回解决“找谁”；
- 用关系召回解决“如何关联”；
- 用原文 Chunk 解决“具体依据是什么”；
- 用版本和来源校验解决“这个依据是否适用于当前问题”；
- 用证据融合和排序解决“哪些内容值得交给模型”。

因此，评测 GraphRAG 时不能只比较召回节点数或 Context 长度，还应评估实体归属准确率、关系路径准确率、版本过滤准确率、证据覆盖率、来源可追溯性、答案引用正确率和无关上下文比例。

## 8. 与其他模块的关系

- 依赖知识工程定义业务对象和关系类型；
- 可增强 RAG 的召回和上下文组织；
- 可为 Agent 提供关系查询工具；
- 需要评测模块验证图谱是否真的提升结果；
- 需要治理模块管理图谱版本、权限和质量。

## 9. 后续要验证的问题

- 家庭菜谱知识库是否真的需要图谱？
- WeKnora 的图谱抽取是否足够，是否需要 DeepKE？
- Neo4j 和 Nebula Graph 哪个更适合个人 / 小团队阶段？

- Entity / Relationship / Chunk 三路召回的 TopK 如何分配，是否需要按问题类型动态调整？
- 关系扩展的最大 hop 数、关系类型白名单和去重策略如何确定？
- 车型、产品版本和文档生效时间的实体归属校验由图谱、检索器还是业务规则层负责？
- 如何评测版本过滤错误、跨版本污染和原文证据缺失？
