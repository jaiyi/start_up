# 理想汽车：工艺设计合规性智能评审系统

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：林颖，Level 2，研发运营，2026-08-04，板块：实战案例 · 工具分享，203 阅读）
>
> **一句话**：把 SE（同步工程）工程师"拿数模 → 在 CATIA 里手动测量焊点间距/定位孔距离/边宽 → 翻纸质 MR 标准手册对照 → 手动记不合格项 → 手动建 ECR 工单"的全流程自动化——LLM Agent 编排 + 本体知识图谱（30+ SE 对象、规则形式化为五元组）+ MR 标准库自动解析 + CATIA V5 直连自动化（CAA 插件 TCP + CLI 双通道）+ 不合格项自动转 ECR，全程 SSE 流式反馈。**这是案例七（CATIA 装配校核）的同域对照案例：同样"让 CATIA 做判断、让 AI 做编排"，但从"生成宏人执行"走到了"Agent 直连工具"，且判定规则形式化到五元组——十二案例中工程要素最全的一篇。**
>
> **顾问点评**：知识形式化的最高形态——MR 标准从纸质手册到五元组 `{对象类型, 几何属性, 约束类型, 阈值, 单位}`，LLM 自由裁量被压到最小；CAA TCP + CLI 双通道互备是生产级工具链的成熟度标志；自动转 ECR 让闭环落到执行系统而不停在报告。三个待补点：其一，**五元组表达力的极限未被诚实标注**——工艺语言里"便于操作""避免过约束"这类模糊性约束无法五元组化，这批规则仍靠人，其占比决定了系统覆盖率的真实上限，文中未披露；其二，**误报率 / 漏报率数据缺失**——工程师对自动结论的信任校准没有依据，误报过多会导致"AI 报的都当噪音"的狼来了效应；其三，**规则库的扩充机制未设计**——新材料、新连接方式出现时五元组规则谁来加、走什么流程，决定了系统的生命周期。**建议打通**：与案例十三的大白话共创方法论结合——NL 输入 → AI 编译为五元组 → 人确认入库，正好补齐规则扩充的低成本通道；跟踪自动检出不合格项的修复闭环率，作为系统价值的硬指标。

## 1. 案例来源与背景

- 来源：公司内部技术社区文章，作者林颖（Level 2 见习伙伴，研发运营），2026-08-04，阅读量约 203；
- 业务域：整车研发 · SE 同步工程（工艺性评审）；
- 痛点（原文"SE 工程师的深夜噩梦"）：新车型的零件数模要做工艺合规检查（焊点间距、定位孔距离、边宽等）——手动测量每一项 → 翻纸质 MR（制造要求）标准手册对照阈值 → 逐条记录不合格项 → 手动创建 ECR 工单走流程；**一个零件几百个检查项，一套白车身几十个大总成**；
- 文体偏宣传（"黑科技""酸爽懂的都懂"），但技术要素具体、架构完整。

## 2. 解决什么问题

把"工程师经验和耐心"驱动的工艺评审，变成"机器自动找茬 + 一键转单"：

- 检查项覆盖：焊接 SE **11 大检查类别**（规范性 / 装配性 / 点焊 / SPR 铆接 / FDS 螺钉 / 螺柱焊 / 弧焊 / 涂胶 / 凸焊 / 激光焊 / 包边折边）；
- 标准对照：MR 标准库自动解析（不再是纸质手册）；
- 出口：不合格项自动生成 ECR（工程变更请求）进入流程。

## 3. 任务流拆解

### 3.1 一句话到 ECR 的 7 步智能流程

用户输入（自然语言）："检查左前门外板的点焊和 SPR 铆接，车型 Model-X，P0 阶段"

```text
1. se_resolve_part("左前门外板", ["点焊", "SPR"])
   → 本体推理，识别零件涉及的 SE 对象（焊点、定位孔、翻边……）
2. se_match_rules(se_objects) → 命中 12 条规则
3. 通知用户：涉及焊接/尺寸/冲压 3 个专业
4. catia_run_welding_check(ci_numbers, level=20) → 触发 CATIA 执行检查
5. catia_get_welding_results → 实时轮询（SSE 流式推送进度）
6. auto_sync_to_se_module → 同步到分析模块
7. se_results_to_ecr_batch → 不合格项自动批量转 ECR
```

前端实时可见：连接 CATIA → 触发检查 → 等待进度（10s/20s…）→ 结果汇总（如"总计 156 条 | 合格 142 | 不合格 14"）→"已自动生成 14 条 ECR"。

### 3.2 判定规则的形式化（本体知识图谱）

基于 30+ SE 领域对象（焊点、定位孔、翻边、涂胶轨迹、操作空间……）构建形式化规则库，**每条规则是一个五元组**：

```text
{ 对象类型, 几何属性, 约束类型, 阈值, 单位 }

焊点   → 距定位孔距离 → ≥ → 10 → mm
SPR铆接 → 边宽       → ≥ → 8  → mm
翻边   → 折弯半径    → ≥ → 3  → mm
```

**跨工艺关联检测**：规则之间可以联动——

```text
焊点规则 #023 与定位孔规则 #007 存在跨工艺关联
  └─ 焊点需距离定位孔 ≥ 10mm
  └─ 当前实测值 8.2mm → ❌ 不合格
```

### 3.3 双通道 CATIA 通信

| 通道 | 协议 | 场景 | 特点 |
|---|---|---|---|
| CAA 插件 | TCP Socket | 主检查流程（11 类检查） | 高可靠 |
| catia-cli | 子进程 CLI | 辅助操作 | 轻量，参数查询/测量 |

两通道互备，系统自动检测可用状态并在界面显示 TCP / CLI 绿灯。

### 3.4 系统形态

PyQt6 桌面应用 + Web SPA；首页工作台（零件参数配置 + CI 检查项选择 + 实时进度 + 阶段指示器：准备→触发→CATIA 执行→入库→ECR 转单→完成 + 统计看板 + ECR 列表 + 历史运行记录）+ AI 聊天（自然语言执行 CATIA 工具调用）。

## 6. 可信度判断

**判断：系统真实且工程完成度高，宣传文体但技术细节可交叉验证；效果无量化、评审准确性未验证。**

可信的部分：

- CAA 是达索官方真实 API、TCP Socket + CLI 双通道互备是做过 CATIA 自动化的人才有的设计（单通道会踩坑：CAA 插件掉线、CLI 覆盖面不足）；
- 五元组规则形式化 + 跨工艺关联检测有具体规则编号和实测值示例（8.2mm < 10mm），是真实规则库的颗粒度；
- 11 大检查类别清单具体（点焊/SPR/FDS/螺柱焊/弧焊/涂胶/凸焊/激光焊/包边折边——完整的焊接工艺族谱）；
- 7 步流程每步有函数名（se_resolve_part / se_match_rules / catia_run_welding_check / se_results_to_ecr_batch），是真实代码结构的暴露；
- 有飞书 wiki 详细文档（内链）。

需要保留的部分：

- 无效率量化（对比案例五 CAE 给了 100min→10min）；
- **评审准确性未验证**：CATIA 几何测量是精确的，但风险在两头——MR 标准自动解析的准确率（纸面标准翻译成五元组会不会错）、本体推理识别 SE 对象的召回率（漏识别的检查项 = 漏检）；
- 无使用规模（多少 SE 工程师在用、多少车型项目跑过）；
- 跨工艺关联检测"自动发现关联"的机制没讲清（规则内写死还是图推理）；
- 自动转 ECR 的边界：误判的不合格项会不会污染 ECR 流（对应案例四的设变管理下游）。

结论：**工程真实、架构完整；准确率与规模是缺的两块证据。**

## 7. 对我们当前项目的启发

### 7.1 与案例七的正面对照：CATIA 自动化的两极（本案例最有价值的分析）

同为"AI + CATIA 几何判定"，两个案例几乎站在光谱两端：

| | 案例七（装配路径校核） | 本案例（工艺合规评审） |
|---|---|---|
| 判定依据 | Clash 精确计算（单次全量） | 五元组规则库（批量检查项） |
| AI 与 CATIA | 生成宏 → **人执行** → 读报告 | Agent **直连**（TCP/CLI）+ 轮询 + 流式 |
| 结论形态 | 四态（含 UNVERIFIED） | 合格/不合格二值 + 自动转 ECR |
| 验证纪律 | 命令—读回—审计五步协议 | 未提及（几何测量本身精确） |
| 适合任务 | 探索式单问题 | 高并发批量规则检查 |

**判据更新（合并案例八）**：探索式任务 → 脚本式人执行；高并发确定性批量 → 直连自动执行；两者都需要读回审计。本案例实际上完全符合案例七的"让 CATIA 做判断，让 AI 做编排"原则——判定是五元组规则 + CATIA 几何计算，LLM 只做对象识别和流程编排。三个 CATIA/硬件案例（七、八、十二）已把专业工具控制的设计空间标定完整。

### 7.2 五元组规则：制度知识形式化的最高形态（对应案例二/九）

制度知识资产化的三级台阶在十二案例中已完整出现：

```text
案例二（流程库）：文件态 → AI 可读（诊断时检索）
案例九（品类管理）：文件态 → 框架态（四象限/阈值法，AI 按框架判定）
本案例（工艺评审）：文件态 → 规则态（五元组，机器直接执行，AI 只做路由）
```

MR 标准手册从纸质 → 可解析标准库 → 五元组规则——**形式化程度越高，LLM 的自由裁量越小，系统越可靠**。对 12 系列的直接启示：质量标准（spec、检验规范、判定准则）的资产化终点是可执行规则（五元组或等价物），而不是 RAG 文档。芯片侧的 CP/FT spec、供应商质量协议条款，理想形态都是规则态。

### 7.3 跨工艺关联检测：规则库从"清单"到"图"（对应 12-02）

单条规则是清单，规则间关联是图——焊点规则受定位孔规则影响、当前实测 8.2mm 触发跨工艺不合格。这与 12-02 的失效关联分析同构：**失效模式之间的关联（如边缘品 × retest-pass × stress delta）需要图结构表达，清单式规则抓不住组合风险**。规则库设计的下一步是关联语义（冲突/依赖/触发），本案例率先做了一小步。

### 7.4 闭环进入流程系统：ECR 出口（对应案例四，跨案例链路形成）

不合格项自动转 ECR，意味着评审结果直接进入工程变更流程——而案例四正是设变（ECN）断点的端到端监控平台。跨案例链路已经能串起来：

```text
本案例：数模评审发现不合格 → 自动建 ECR
   ↓（ECR 批准后成为 ECN）
案例四：设变断点监控 → MBOM 差分 / 到货修正断点 / 责任人图谱催办
   ↓（量产后）
案例十一：市场质量智能体 → TS 工单 / 车云信号 / 故障率预测
```

**研发→制造→售后的质量数据链在理想内部已经由不同的团队分别自动化，缺的只是横向打通**——这正是 12-03 体系视角的实证：每个环节都有人做了工具，但端到端 genealogy 还没连起来（和 Fabless 侧的问题一模一样）。

### 7.5 最值得抄的设计

1. **双通道互备 + 状态灯**（CAA TCP 主通道 / CLI 备用，界面显示可用状态）——专业工具直连的可用性工程，比单通道方案可靠一个档次；
2. **五元组规则结构**（对象/属性/约束/阈值/单位）——任何合规检查类标准的形式化模板；
3. **7 步流程函数化**：每步有明确函数名和输入输出（se_resolve_part → se_match_rules → catia_run → ... → se_results_to_ecr_batch），Agent 编排的可审计形态；
4. **SSE 流式进度**：长时检查任务（CATIA 执行 10-20 秒以上）的体验必需品，避免"黑盒等待"；
5. **阶段指示器**（准备→触发→执行→入库→转单→完成）：把 Agent 多步执行显式可视化，用户随时知道卡在哪一步；
6. **专业通知**（"涉及焊接/尺寸/冲压 3 个专业"）：规则命中后先告诉用户影响面再执行，给人干预窗口。

## 8. 后续想实测 / 追问的问题

- MR 标准自动解析的准确率：纸质/文档标准翻译成五元组的过程有多少人工校对，错误规则的发现机制；
- 本体推理的召回率：有没有"该检但没识别到 SE 对象"的漏检（对比人工评审做过 A/B 验证吗）；
- 自动转 ECR 的误报率：14 条不合格 ECR 里几条最终被判定有效，误报对 ECR 流的污染；
- 跨工艺关联的机制：规则间关联是人工定义还是自动发现；
- 与案例七的能力合流可能：几何判定引擎共用（同一个 CAA/TCP 通道），规则库互相引用；
- 使用规模与车型覆盖：几个项目在用，单零件检查的实际耗时对比人工；
- 12 系列平移：芯片侧 DfM（可制造性设计）评审规则（密度、线宽、叠层、热）能否五元组化 + 工具直连（EDA API）——本案例是 DfM 自动评审的整车版样板。
