# 理想汽车：耐久仿真计算与后处理自动化平台

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：贺宏伟，Level 1，研发运营，2026-09-08，板块：实战案例 · 工具分享）
>
> **一句话**：把 CAE 疲劳耐久仿真的"HPC 提交 → 监控 → 下载 → 后处理 → 标准评判 → 报告生成"整条链路装进一个平台（网页端统一入口 + 客户端驱动本机仿真软件 + 数据存储），单次 SBA 工况分析从 100 分钟压到约 10 分钟。**与案例四同物种：AI Coding 造出来的业务自动化工具，系统本体无 LLM Agent**；且作者是 Level 1 新手、研发运营岗——佐证了一个正在发生的结构性变化：工具开发能力正在从 IT 部门下放到业务岗。
>
> **顾问点评**：客户端驱动本机 license 软件的架构选择解了真实约束（license 服务器争抢），SBA 工况 100 分钟 → 10 分钟量化干净，Level 1 业务岗做出平台级工具本身就是"AI 下放工具开发能力"的最强佐证。三个待补点：其一，**平台自动化的是"执行"不是"判断"**——标准评判和报告虽然自动生成，但结果异常（网格质量差、求解不收敛、评判边界情形）时仍需专家介入，这类例外占比多少未披露，它决定了平台的真实提效上限；其二，多用户后的**模板 / 脚本治理缺设计**——谁改了评判模板、影响谁的报告、要不要审批，无版本管理则平台规模化即混乱；其三，仿真结果数据目前是"用完即走"，没有回流沉淀。**建议打通**：引入案例七式"读回—审计—判定"纪律对结果做自动分级（通过 / 失败 / 需专家）；与 PLM 直连消除手工导模型；仿真结果按"工况 × 设计方案 × 寿命结论"结构化入库，几年后就是耐久设计知识库——这是这个平台最被低估的潜在资产。

## 2. 解决什么问题

| 痛点 | 具体表现 |
|---|---|
| 流程割裂 | HPC 提交、监控、下载、后处理、报告生成分散在多个设备、存储、平台，无统一入口 |
| 效率低下 | 工程师手动刷 HPC 页面确认状态、手动下载大文件（下载期间无法操作）、手动后处理、按标准手写报告——高频重复 |
| 数据孤岛 | 各专业分析模块结果分散存储，跨项目、跨阶段横向对比困难，难追溯 |

典型场景（座椅仿真某阶段一轮分析，外援同学提交计算后）：

- 作业处理：无监控及自动下载，需反复刷新 HPC 页面等作业完成后手动下载；
- 后处理：需反复查找及调用工具（Hypermesh/ANSA、Hyperview/META），根据数据状态和模型参数手动操作；
- 评判：手动撰写报告，根据标准初步评判结果是否存在风险。

## 3. 任务流拆解

### 3.1 平台架构（三模块）

```text
网页端（统一用户入口）
   负责各功能模块联通：HPC / 客户端 / 数据库 / 存储服务 / 用户反馈
客户端
   只接收平台任务，调用用户电脑上的仿真软件执行后处理、报告生成
数据存储
   大规模仿真数据存储 + 用户意见收集 + 数据库
```

**关键设计：客户端驱动本机商业软件。**Hypermesh/ANSA、Hyperview/META 是绑定 license 的桌面软件，平台不迁移、不替换，而是通过客户端程序驱动用户本机已装软件执行操作——绕开了商业 CAE 软件无法上云/无法 API 化的约束。

### 3.2 功能范围

① 仿真计算/后处理全流程自动化：HPC 提交、监控、下载自动化；结果提取及输出自动化；标准评判及报告生成自动化；

② 模型与材料参数版本管理：提交 HPC 作业时记录模型文件版本；材料参数配置文件版本管理与历史对比；历史作业与模型版本关联，支持追溯；

③ 数据看板与问题反馈：汇总各项目、各阶段仿真任务数量、使用率、处理次数；内置问题反馈与智能迭代功能。

### 3.3 单次任务流对比（SBA 工况）

```text
原流程（100 min，5 个软件）：
  作业上传提交 → 人工监控 → 等待下载 → 手动后处理
  （位移/云图/扭矩/螺栓力/失效判定等提取）→ 手动撰写报告
  工具：FileZ、HPC、Hypermesh/ANSA、Hyperview/META、PPT

自动化流程（约 10 min，1 个平台）：
  作业上传提交 → 配置自动后处理 → 检查结果
  工具：耐久智能仿真平台
```

### 3.4 产品设计原则（作者自述）

用户是每天与 LS-DYNA、META、HPC 打交道的 CAE 工程师，第一原则是贴近工作场景、降低学习成本：工业深色风格、信息密度优先、操作即反馈、复用已有认知。

## 6. 可信度判断

**判断：真实存在的早期项目，落地深度浅，单点数字可信但样本极小。**

可信的部分：

- 痛点是 CAE 行业通病，描述精确到"下载大文件期间只能耐心等待无法操作"这种一线细节；
- 架构描述具体（网页端/客户端/存储三模块、客户端驱动本机软件），且"驱动本机 license 软件"这个设计只有真做过的人才会这么选；
- 100 min → 10 min 是单一工况的对比，口径清晰（操作步骤、涉及软件都列了），没有夸大成平台级 ROI。

需要保留的部分：

- Level 1 新手作者 + 65 阅读 + 篇幅短——更像个人/小组项目的首次分享，不是组织级平台发布；
- 只有 SBA 一个工况的数字，其他工况（不同载荷类型、不同零部件）的后处理复杂度是否同样可自动化未知；
- "标准评判"只有一句"初步工况标准评判能力"，覆盖多少评判条目、误判率如何完全没讲；
- 版本管理、数据看板、问题反馈都停留在功能清单层面，无实际运行数据。

结论：**真实、早期、薄。作为"AI Coding 下放开发能力"的趋势样本收录，作为方法论参考价值有限。**

## 7. 对我们当前项目的启发

### 7.1 五案例合看：AI Coding 正在把工具生产下放到业务岗（最重要）

| 案例 | 作者职级 | 岗位 | 造出的东西 |
|---|---|---|---|
| 案例四 设变断点监控 | Level 2 见习 | 制造 | 数仓 + 规则引擎 + 飞书自动化平台 |
| 案例五 耐久仿真自动化 | Level 1 新手 | 研发运营 | CAE 工作流自动化平台 |
| 案例一 LI-PAS | 资深工程团队 | 整车效能 | 多 Skill Agent 工作流 |
| 案例三 EHS | Level 3 | 制造安全 | 五场景 Agent 闭环 |
| 案例二 流程库 | Level 3 | 研发运营 | 流程拟制 + 反向诊断平台 |

**规律：职级越低的作者，做的东西越偏"确定性自动化工具"；职级越高，越偏"Agent + 知识资产"。**这不是能力差异，是问题性质决定的——新手能拿到的是重复性操作（下载、后处理、比对），资深者才有权动知识库和方法论。

对 04-06 的增量判断：AI Coding 的真正影响不在"AI 应用层"，而在**降低 L2 工具连接层的生产成本**——过去接一个 HPC + 桌面软件 + 存储的工作流要排 IT 队伍，现在业务岗自己就能造。这会带来一波"业务岗自制工具"的爆发，而 04-06 里通用基建（L0-L6）的价值恰恰是给这波自制工具提供统一底座，否则会变成新的烟囱。

### 7.2 客户端驱动本机商业软件：工具连接的一个务实模式（对应 04-06 L2）

CAE/EDA 类专业软件 license 绑定桌面、无开放 API，是所有自动化方案的老大难。本案例的解法：

```text
不迁移软件、不破解 license、不要求厂商开放接口
→ 平台只下发任务，客户端程序驱动本机已装软件执行
```

这个模式适用于一切"贵、老、闭源但必须用"的专业工具（EDA、结构仿真、专业测试设备上位机）。代价是后处理必须排队等工程师的电脑在线。对应到芯片侧（12 系列）：测试机台、探针台、EDA 工具链的自动化连接可以参考这个分层——云上管调度和数据，本机客户端管工具执行。

### 7.3 版本管理 + 作业关联 = 仿真数据资产化的最小闭环（对应 02 / 04-05）

"提交作业时记录模型版本 + 材料参数版本管理 + 历史作业与版本关联追溯"——这三件事凑起来，仿真结果才能跨项目横向对比。这正是 02 里"纵向四资产"中数据资产的最小形态：**没有版本关联的结果文件只是文件，有了版本关联才成为可复用的资产**。芯片侧同构：仿真/测试结果必须和 PDK 版本、工艺版本、测试程序版本关联，否则跨批次对比无意义。

### 7.4 标准评判先做规则，不做 LLM（再次印证"用对物种"）

耐久结果的风险评判有明确标准（位移限值、失效判定条目），案例用规则做"初步评判"。和案例四的结论一致：**判定逻辑确定时，规则引擎是正解**。但注意作者说的是"初步"——标准覆盖不了的边缘情况（异常波形、非标工况）才是将来 LLM 层的切入点，和 12-02 里"out-of-family 检测"的定位相同。

### 7.5 最值得抄的设计

1. **客户端驱动本机软件**的架构模式（见 7.2）；
2. **提交作业时顺手记录模型版本**：版本信息在任务发起时捕获，而不是事后补录——数据治理嵌进流程而非附加流程；
3. **内置问题反馈与智能迭代**：工具自带反馈回路，用户意见进入迭代——哪怕早期也要埋；
4. **产品设计四原则**（深色工业风、信息密度优先、操作即反馈、复用已有认知）：面向专业用户的工具 UI 准则，B 端产品通用。

## 8. 后续想实测 / 追问的问题

- 平台当前覆盖哪些工况类型（除 SBA 外），各工况后处理自动化的覆盖率；
- "初步工况标准评判"的规则条目数量和误判情况，工程师对自动评判的采信度；
- 客户端驱动本机软件的稳定性（软件版本升级后脚本失效怎么办）；
- 使用规模：多少 CAE 工程师在用，日均任务量；
- AI Coding 在开发中的实际占比（多少代码生成、多少人工调试），开发总投入多少——文章标签提了但没讲，这是本案例最有信息量的缺失项；
- 仿真结果数据是否已支撑跨项目横向对比（7.3 的闭环是否真的跑起来了）；
- 后续是否有计划把 LLM 引入（异常工况归因、历史相似案例检索）——目前平台完全没有 LLM，标准之外的情况怎么处理。
