# 理想汽车：供应链品类管理知识助手

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：姜沛佐，Level 1，供应链，2026-08-10，板块：工具分享，145 阅读）；Skill 发布在内部 AI Market
>
> **一句话**：把采购品类管理的制度知识体系（品类树/品类定位/资源池/变更管理/系统操作五板块，原本散落在 ISC 文件里）做成一个可问答、可辅助判定的 Skill——既回答"品类怎么划分"，也接收真实参数做品类定位判断（如"单车 650 元、2 家 AVL 供应商占 90% 份额、绩效最高，这个品类定位是什么"）。**物种：制度知识库 + 领域判定框架，是九案例中最轻的一档（无 Agent 编排、无工具链，纯知识 Skill），但"把制度文件变成可判定的框架"这一步与案例二（流程库）同构。**
>
> **顾问点评**：走 AI Market 组织级分发而非私有工具，是知识型 Skill 的正确路径；"制度文件 → 可判定框架（四象限 / 阈值法 / 评分法）"的形式化跨越与案例二同构，采购制度这种"人人要用、没人爱读"的资产正是 AI 知识库的最佳靶子。三个关键缺口：其一，**判定建议的责任边界只提问未回答**——AI 给出的品类定位判断若被采购决策引用后出问题，责任在用户、在 Skill 作者还是在制度 owner？这必须有明文制度而非默契，否则组织级分发本身在放大风险；其二，**知识更新治理缺失**——ISC 制度改版后 Skill 谁同步、多久同步、不同步的后果是什么，无机制则 Skill 会与制度静默脱钩，且比纸面过时更危险（用户默认它是最新的）；其三，判定框架无准确率校准数据。**建议打通**：判定结果回流做偏差统计（框架判定 vs 人工最终判定的偏差及原因），持续校准框架；与品类主数据系统打通让判定直接落系统而非停在对话里；Skill 内容版本与 ISC 制度版本强制绑定。

## 2. 解决什么问题

**痛点：品类管理制度知识散落在 ISC 文件体系里，翻文件费时、口径难找、新人上手慢。**

Skill 覆盖的典型使用场景：

| 角色 | 典型场景 |
|---|---|
| CMT-PTC | 品类树设定原则、品类定位原则、资源池划分与看板制作审查、品类拆分/合并/禁用原则、系统操作与底层数据修正 |
| CMT-采购 / CMT-研发 | 新建品类依据、零件发包原则、零件号与品类绑定流程 |
| CMT-PSM | 供应风险判断依据、成熟供应资源评估标准 |
| 新人 | 快速了解品类管理体系框架和核心规则，"替代翻 ISC 文件" |

## 3. 任务流拆解

### 3.1 知识库结构（五板块）

| 板块 | 核心内容 |
|---|---|
| ① 品类树管理 | 大/中/小三层结构、CMT 定义与组成、Tn 物料四种管控方式、命名原则（功能+应用或技术+工艺，**禁用"其他"类命名**） |
| ② 品类定位管理 | **两维四象限框架、非半导体阈值法、半导体评分法、校准规则完整版** |
| ③ 品类资源池管理 | 供应商两层四分类、KCP01-03 路径矩阵、资源看板 V2.4 完整 12 项健康度 |
| ④ 品类变更管理 | 8 种变更类型规则、决策层级（一级/二级定点会）、品类变更真实案例 |
| ⑤ 系统及问题解决 | DPCM/SMP/SDM 三系统关系、零件绑定问题处理、AVL 勚误正式流程 |

### 3.2 两种使用模式

```text
模式 1：知识问答
  "品类是怎么划分的？" / "零件号和品类之间是什么关系？"
  / "品类定位的划分标准是什么？如何判断一个物料是否具有供应风险？"
  / "品类资源看板的更新节奏是什么？"
  → 基于知识库精准回答（替代翻 ISC 文件）

模式 2：材料审核（更有价值的模式）
  "制作品类资源看板时，输入关键技术和关键工艺要注意什么？"
  "我有 1 个品类想拆分为 3 个，怎么申请、注意什么？"
  "电驱动零部件下级品类，单车采购金额 650 元，看板中有 2 家成熟 AVL 供应商
   都在大陆、无跨品类和潜在；但这 2 家已占 90% 市场份额，过去 1 年绩效最高、
   合作良好——这个品类的定位是？"
  → 接收真实业务参数，套用定位框架（两维四象限 + 阈值法/评分法）给出判定建议
```

### 3.3 内嵌资源（不只是文档知识）

- 📄 品类变更管理模板、品类资源看板模板 V2.4；
- 📄 品类管理指引（"表达更加通俗，易上手"——为 Skill 重写的版本，不是原始制度文件）；

## 4. 用到的能力

- 知识库 RAG（五板块制度知识 + 指引 + 模板 + 制度原文）；
- 结构化知识框架（四象限、阈值法、评分法、路径矩阵、12 项健康度——**判定逻辑是显式规则，不是 LLM 自由发挥**）；
- 实时数据表关联（品类树/AVL/绑定关系的活数据）；
- 发布在内部 AI Market（组织级 Skill 分发渠道，其他人可直接安装）。

无 Agent 编排、无工具调用链、无代码——九案例中技术形态最轻。

## 6. 可信度判断

**判断：Skill 真实存在（AI Market 上架 + 示例完整），但文章是产品介绍而非实践复盘，落地深度无法从文中判断。**

可信的部分：

- 知识库结构化程度高且具体：两维四象限、非半导体阈值法/半导体评分法、KCP01-03 路径矩阵、看板 V2.4 的 12 项健康度、8 种变更类型——这些是真实品类管理体系才有的颗粒度，编不出来；
- 内嵌**实时数据表**和**为 Skill 重写的通俗版指引**——这两件事说明作者真的懂"文档知识 ≠ 可用知识"，做了治理；
- 模式 2 的第三个示例参数完整（650 元、2 家 AVL、90% 份额、绩效最高），是真实业务问题形态。

需要保留的部分：

- 纯功能介绍文体：无踩坑、无边界声明（对比案例七"明确不做"清单和案例三"口径自注"，本文完全缺席）；
- 判定的正确性无背书：模式 2 里 Skill 给出的品类定位建议，是框架的确定性计算还是 LLM 的推断？错了谁负责？文章未讨论；
- 知识库的维护机制未说明：品类树实时数据怎么同步、制度变更后 Skill 多久更新、谁负责校准规则的版本；
- 无使用量与反馈数据，145 阅读不等于被采用。

结论：**知识资产化方向正确、知识库结构化质量高，但可信度只能打到"真实存在、深度未知"。**

## 7. 对我们当前项目的启发

### 7.1 与案例二同构：制度文件 → 可判定框架（对应 02 纵向资产）

```text
案例二（流程库）：流程文件库 → AI 可查询 + AI 反向诊断流程资产
本案例（品类管理）：ISC 制度文件 → AI 可问答 + 按框架辅助判定
```

两个案例处理的是同一类资产——**组织制度知识**（流程/品类规则），共同的转化路径是：原文档 → 结构化框架（四象限/阈值/矩阵/层级）→ 可问答 → 可判定。02 里纵向四资产的"知识资产"生命周期在这两个案例里得到完整展示：**第一步不是上 Agent，是把制度知识从"文件态"炼成"框架态"**——一旦框架显式化（阈值法、评分法、路径矩阵），判定就变成确定性计算，LLM 只负责交互和解释。

### 7.2 最小技术形态往往是最先规模化的一档（对应 04-06 分层）

本案例在 04-06 分层里只占 L3（知识检索）+ L8（领域任务模板），无 L4 编排。但注意它的分发方式：**AI Market 上架，组织内一键安装**——九个案例里这是唯一走"组织级 Skill 市场分发"的。技术越轻、越容易复制，分发渠道的价值越大。这提示 04-06 L8（领域任务模板 Skill）层的正确产品形态：**框架显式化的知识 Skill + 市场分发**，它可能比重 Agent 更早形成规模。

### 7.3 与 12-03 的交叉：品类定位框架是 SQM 的采购侧镜像

品类定位（两维四象限 + 阈值法/评分法）本质是采购风险分级的框架，其中"半导体评分法"单列——半导体物料的风险维度（供应集中度、技术门槛、生命周期）与普通物料不同。这与 12-03 供应商分层（Tier 0/1/2）是同一件事的两面：

- 12-03 管的是**质量视角**的供应商分层（数据权利、lot release 严格度）；
- 品类定位管的是**采购视角**的品类分层（资源池策略、看板健康度）；
- 两者共享底层数据（AVL 供应商、绩效记录、市场份额）——**理想的品类定位 Skill 应该同时接入质量绩效数据**，而本案例的看板 12 项健康度里是否含质量维度值得追问。

### 7.4 判定建议的责任边界是这类 Skill 的真问题

模式 2 里 Skill 对真实参数给出定位建议——但文章没有回答：**建议错了算谁的？**对比案例七（终点接触交给工程师确认设计意图）和案例三（两轮定稿），凡涉及判定的 Skill 都应有"建议 + 依据 + 人裁决"的显式结构。品类定位的判定框架是显式的，理论上 Skill 可以给出"依据 XX 阈值法，金额 650 元落在 XX 象限，但 90% 份额触发 XX 校准规则"的可审计推理链——文章示例没展示这个层次，这是该 Skill 从"知识助手"进化到"可信判定助手"的关键一步。

### 7.5 最值得抄的设计

1. **为 Skill 重写通俗版指引**：不直接喂原始制度文件，而是把制度语言重写成 AI 友好、用户易读的版本——知识治理里常被忽略的一步；
2. **知识库挂实时数据表**：品类树/AVL/绑定关系是活数据，回答"我管理的品类现状"类问题不会过期；
3. **五板块 + 每板块核心内容清单**的知识库组织法：先列"这个领域必须回答的问题清单"，再组织知识；
4. **禁用"其他"类命名**这类具体规则进知识库——制度里真正防错的是这种颗粒度的条款，不是大道理；
5. **AI Market 分发**：Skill 做完挂组织级市场，比自己推广的触达效率高一个量级。

## 8. 后续想实测 / 追问的问题

- 模式 2 判定的推理链：Skill 给定位建议时是否展示依据（阈值/象限/校准规则的引用），还是只给结论；
- 建议错了的责任边界和使用者采信度——CMT 用户把它当"参考"还是"定论"；
- 品类树实时数据表的同步机制（频率、字段、谁维护）；
- 制度变更后 Skill 的更新 SLA：校准规则改版后多久知识库跟上；
- 看板 12 项健康度里是否包含供应商质量绩效维度（与 12-03 的数据打通情况）；
- 使用量数据：AI Market 安装量、周问答次数、哪个板块问得最多（暴露哪块制度最不清晰）；
- 有没有把模式 2 再往前推一步：直接读实时数据表自动生成品类资源看板初稿——从"辅助判定"到"辅助产出"。
