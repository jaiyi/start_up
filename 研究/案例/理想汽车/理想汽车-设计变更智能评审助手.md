# 理想汽车：设计变更智能评审助手

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：宋浩，Level 1，制造，2026-07-27，板块：实战案例，104 阅读）
>
> **一句话**：制造侧设变评审的 AI Agent 化——把 40 余项评审规则提炼成 Skills 注入"小龙虾"（OpenClaw 智能评审机器人），自动从数仓抓取信息、交叉比对、把高危事项精准推给干系人、消灭手工台账；杀手锏是**业务人员用大白话共创规则**（"帮我加个规则：车型既有 X11 新项目又有 X01 旧项目时，提醒核查新旧是否同步设变"——一句话生效）。**与案例四（设变断点监控平台）同域不同解法：案例四是数仓+规则引擎的确定性路线，本案例是 AI Agent+自然语言规则的敏捷路线，两案对照构成"规则确定性 vs 规则敏捷性"的完整张力谱。**
>
> **顾问点评**：大白话共创规则是全部案例里最优秀的采纳机制设计——"一句话生效"把规则建设成本压到近零，业务人员从使用者变成共建者，这个机制值得全公司复制。但有一处**合规红线级的灰区必须最先处理**：浏览器插件 iframe 穿透 + RPA 绕过系统鉴权取数，技术上聪明、组织上危险——绕过鉴权本身就是审计事件，且供应商系统一次升级通道即失效，应立即收编进官方数据网关走正门鉴权。另有两个缺口：其一，**40+ 条自然语言规则之间无冲突检测**——互相矛盾的提醒会同时触发，规则越多信噪比越差，需要规则的语义化登记与冲突检查（哪怕人审）；其二，**与案例四同域两套系统并存，规则资产分裂**——制造设变的判定知识散在两个系统里。**建议打通**：与案例四合并为设变规则中台——大白话共创做输入层（参照案例十二的 NL → 五元组编译路线）、规则引擎 / 代码做执行层；评审拦截数据回流，统计"拦截的设变若放行会造成什么损失"，给系统算出 ROI 硬账。

## 1. 案例来源与背景

- 来源：公司内部技术社区文章，作者宋浩（Level 1，制造），2026-07-27，阅读量约 104；
- 工具：Claude Code 辅助开发 + OpenClaw（内部智能体平台，昵称"小龙虾"）；
- 业务域：制造 · 设计变更（设变）评审——**与案例四同一业务域的另一个团队**；
- 背景：设变评审是防止风险外溢至工厂端的关键防线，每天依靠 **40 余项规则**在 BOM 等多个系统全面排查。"零件不互换却未更改件号"这类疏漏曾导致**产线批量错装、停线缺件、上百台车返修**；
- 体量：人均日处理 **13 份以上**评审，单份包含 **300+ 条数据**（含 30% 非结构化文本）。

三大痛点：

1. **认知超载易漏判**：跨系统"人肉"找茬比对，疲劳导致漏看错判；
2. **深陷流程泥沼**：优质工程人力被手工台账和低效沟通消耗；
3. **传统程序水土不服**：传统 IT 硬编码过死，无法适应项目规则的动态微调。

---

## 2. 解决什么问题

范式转变：**从"人找数据"变成"系统找人"**——用户一键调用，小龙虾自动去数仓抓取信息、交叉比对、把高危注意事项精准推送给干系人，手工台账消失。

注意第三条痛点是本案例区别于案例四的关键：设变规则随项目动态微调，硬编码规则（案例四的 19 维差分）跟不上规则变化，所以选择了"规则即自然语言"的 AI 路线。

## 3. 任务流拆解

### 3.1 四大能力

```text
① 智能评审引擎（核心支撑）
   自动调用 Skill 分析 DCA，智能检查设变计划合理性与切换类型准确性，自动完成数据留存
② 风险可视化分析（宏观防线）
   实时监控 AI 拦截率，生成异常分布看板和高风险预警雷达图，宏观捕捉风险趋势
③ 自然语言敏捷进化（杀手锏）
   规则对业务全面开放，摒弃硬编码：
   "帮我加个规则，如果涉及车型既有 X11 等新项目，又有 X01 等旧项目，
    重点提醒我核查新旧是否同步设变。"
   → 一句话，一条业务防线生效
④ （第四项在原文中未展开，为数据获取通道，见 3.2）
```

### 3.2 业务数据获取的三种方式（原文"拓展思考"，很有工程价值）

| 方式 | 优点 | 缺点 |
|---|---|---|
| 数仓获取设变系统数据 | 快、稳定 | 数据不全，图片等信息较难获取 |
| Python 插件爬取设变系统 | 实现路径简单 | 需不定时鉴权，openclaw 登录设变系统困难 |
| 浏览器插件在页面直接获取 | 无需鉴权、交互直接 | 暂无 |

浏览器插件的两个深挖能力：

- **深度网页穿透提取（iframe 穿透）**：针对高安全性系统的多层 iframe 嵌套结构，无视页面层级深入底层 DOM 树，精准抓取被隐藏或保护的核心文本数据；
- **模拟人工的 RPA 自动化流程**：内置 RPA 引擎，用户指定页面菜单列表后，插件自动模拟"鼠标按下、抬起、点击"，在不同页面（Tab）间自动切换。

### 3.3 与案例四的链路关系

```text
本案例（评审侧）：设变申请 → 40+ 规则 AI 评审 → 拦截/放行 → 高危提醒推送干系人
案例四（执行侧）：设变批准 → 断点台账自动刷新 → MBOM 差分 / 到货监测 / 超期催办
案例十二（上游）：数模工艺评审 → 自动建 ECR → 进入设变流程
```

同一业务域（设变）现在有上游触发（案例十二 ECR）、入口评审（本案例）、执行监控（案例四）三段自动化——设变全生命周期工具链已在内部拼齐。

## 6. 可信度判断

**判断：痛点与方案真实，但效果全靠截图、正文零量化，可信度档位：真实存在、深度与效果未知。**

可信的部分：

- 痛点有具体事故案例（件号不互换致百台返修）和真实体量（13 份/人/日 × 300 条 × 30% 非结构化）——这是一线评审工程师的日常颗粒度；
- "传统 IT 硬编码无法适应规则动态微调"是对案例四路线局限的诚实认知——设变规则随项目频繁变化，硬编码维护成本真实存在；
- 数据获取三种方式的优劣对比是真踩过坑的工程权衡（数仓不全、爬虫鉴权难、插件免鉴权）——这段"拓展思考"的信息密度比效果演示高；
- 自然语言共创规则的示例具体可验证（新旧项目同步设变核查）。

需要保留的部分：

- 正文无任何拦截率、效率、准确率数字（对比案例十一的单周遥测明细，本文效果全在截图里）；
- **"零漏判"的宣称无验证机制**：AI 评审的召回率（漏检）和误报率（乱拦）是这类系统的生死线，文中未提任何抽检或对照；
- 自然语言规则的执行一致性：同一句大白话规则，AI 每次执行是否一致？规则冲突（新旧大白话规则打架）如何检测？
- "绝不遗漏"的 iframe 穿透宣称是营销语言；
- 浏览器插件绕过鉴权直接抓取"被隐藏或保护的数据"，在安全合规上是一个值得警惕的灰色做法（内部系统内的工程便利 vs 安全边界）。

结论：**方向真实、工程思考扎实；效果证据为零，需打折看。**

## 7. 对我们当前项目的启发

### 7.1 与案例四同域对照：设变评审的两条技术路线（本案例最大价值）

同一个业务域、两个团队、两种物种，十三案例中首次出现：

| | 案例四（设变断点监控） | 本案例（设变评审助手） |
|---|---|---|
| 运行时 | 规则引擎 + 数据工程，**零 LLM** | AI Agent + Skills，LLM 在运行时 |
| 规则形态 | 硬编码（19 维差分等） | **自然语言**（大白话共创） |
| 规则变更成本 | 高（改代码） | 低（说一句话） |
| 执行确定性 | 完全确定、可审计 | 依赖 LLM 解释，一致性待验证 |
| 适合 | 稳定的、高频的、需要审计的判定 | 动态的、随项目微调的、半结构化文本判定 |
| 数据获取 | 数仓 ESB 直连 | 数仓 + 浏览器插件（iframe/RPA） |

**收敛判断（可进 04-05/04-06）：规则的确定性和敏捷性是一对真实张力——稳定的红线规则应形式化（案例十二的五元组），动态的探索性规则可自然语言化（本案例），一个成熟系统应该是两者混合：NL 作为规则的编写接口，编译/沉淀为形式化规则后确定性执行。**本案例缺的正是"大白话规则 → 形式化沉淀"这一步编译层。

### 7.2 与案例十二对照：规则形态谱系的三级（完整收敛）

```text
案例四：  规则 = 代码（硬编码，最确定，最不敏捷）
案例十二：规则 = 五元组（形式化，确定且结构化，需维护规则库）
本案例：  规则 = 自然语言（最敏捷，AI 解释执行，一致性最弱）
```

谱系的理想终态：**自然语言输入 → AI 编译为形式化规则（五元组/SQL/校验逻辑）→ 人确认 → 确定性执行 → 执行结果回流**。这样既保留共创敏捷性又获得可审计性。这直接回答了 04-05 任务闭环里"规则资产"应有的生命周期，也和案例十一的"蒸馏剧本"同构（对话调优 → 沉淀可执行物）。

### 7.3 "系统找人"与元监控（对应 04-06 L5）

- "从人找数据到系统找人"与案例四（自动建群催办）、案例六（卡片精准触达）是同一范式第 N 次验证；
- **AI 拦截率监控 + 风险雷达是 L5 治理层的自觉**：不只监控业务风险，还监控 AI 系统自身的行为分布——这是把 AI 当作被观测对象（而不只是工具）的意识，值得写进 04-05 的平台指标设计。

### 7.4 数据获取三通道：遗留系统集成的现实图谱（对应 04-06 L2）

数仓不全、爬虫鉴权难、浏览器插件免鉴权——这三条通道是所有大企业做 AI 工具连接时的真实约束图谱。浏览器插件（iframe 穿透 + RPA）本质是**没有 API 时代的逆向集成**，工程上务实，但合规上灰色（"抓取被隐藏或保护的数据"的说法尤其需要安全侧审视）。对 04-06 L2 的启示：**工具连接层的最大瓶颈不是协议（MCP 已解决），而是遗留系统根本没有可用 API**——正式解法是推动系统开放接口，插件/RPA 是过渡期的民间解法，企业治理层应正视这个 gap 而不是假装它不存在。

### 7.5 OpenClaw 的跨案例出现

案例六（外观认可跟催）的作者曾尝试 openclaw 托管失败后转向多维表格；本案例 OpenClaw 成功承载了评审机器人。同一平台在不同场景的成败差异，印证了案例六的结论：**平台原生能力覆盖度决定成败**（表单协同流 → 多维表格赢；跨系统取数+规则推理 → Agent 平台赢）。OpenClaw 是理想内部的 Agent 运行时底座（相当于 04-06 L4），案例六和本案例分别是它不适用和适用的边界样本。

### 7.6 最值得抄的设计

1. **自然语言规则共创的交互设计**：一句话加一条防线，业务人员零学习成本——规则变更的摩擦降到底（代价是确定性，需配编译层）；
2. **数据获取三通道按场景组合**：数仓（稳定批量）+ 插件（实时页面）+ RPA（需要"动手"的操作）——遗留系统集成工具箱；
3. **AI 拦截率作为平台元指标**：监控 AI 自己的拦截行为分布，异常漂移可见；
4. **事故驱动的规则叙事**：用"百台车返修"的真实代价论证每类规则的存在意义——规则库不是清单而是事故史（对应案例三 EHS 的隐患台账逻辑）。

## 8. 后续想实测 / 追问的问题

- AI 评审的漏判率/误拦率：有没有与人工评审的对照验证，拦截结论的抽检机制；
- 自然语言规则的执行一致性：同一规则多次执行结果是否稳定，规则冲突如何检测；
- 大白话规则有没有向形式化沉淀的机制（还是每次都靠 LLM 现场解释）；
- 浏览器插件绕过鉴权抓取数据的合规边界：信息安全部门是否知情认可；
- 与案例四的系统关系：两套设变工具是否互补共存、数据是否互通，还是同域竞争重复建设；
- AI 拦截率的基线：拦截多少算正常、多少算 AI 过度保守，拦截率变化有没有告警；
- DCA 分析的 30% 非结构化文本理解准确率（这是 LLM 真正超过硬编码的部分）。
