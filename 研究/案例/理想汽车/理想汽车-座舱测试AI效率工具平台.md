## 1. 背景：座舱测试中的重复劳动

座舱测试的典型链路为：

```text
产品提需求
→ 测试用例梳理（脑图 / 用例）
→ 编写自动化脚本
→ 车辆预约与合规流程
→ 车辆整备与实车测试
→ 发现问题并提报 Jira
→ 抓取日志
→ 转交开发分析
→ 回归并关闭问题
```

材料认为，大量环节并不需要复杂判断，却消耗测试工程师大量时间：

| 工作环节 | 传统耗时 / 方式 | 主要问题 |
|---|---|---|
| 手写测试用例与脑图 | 2～3 天 / 模块 | 依赖个人经验，容易漏项，格式难统一 |
| 提报 Jira | 3～5 分钟 / 条 | 20+ 个字段逐项填写，还要手动附日志、截图等附件 |
| 获取日志 | 5～10 分钟 / 次 | 多平台切换，抓取、导出、解密、打包、上传流程长 |
| 车机操作验证 | 一个操作需要多条指令或多个步骤 | 指令和方法分散，执行容易出错 |

平台的建设思路不是先规划一个大而全的系统，而是从最痛的重复节点开始，用小工具逐步嵌入测试日常工作流。

## 3. 重点工具价值详解

### 3.1 Jira 智能提报

#### 传统痛点

工程师通常需要：

1. 打开云端日志平台，手动填写 VIN、环境和问题时间，或在车机本地拉日志；
2. 下载、压缩、改名并上传日志；
3. 打开 Jira，逐字段填写 20+ 个字段；
4. 上传图片、视频和其他附件。

完整流程通常需要 3～5 分钟，日志处理还可能需要 5～10 分钟或更长。

#### 处理流程

```text
发送 Jira 号或 VIN
→ 机器人读取工单中的 VIN / 环境 / 问题时间
→ 触发日志下载
→ 自然语言描述问题
→ AI 识别 Jira 字段
→ 弹出可编辑预览
→ 人工确认
→ 创建工单并上传附件
```

材料称系统支持 32+ 种日志类型，包括 HU Android、Kernel、ANR/Crash、XCU、5G 等；在 Demo 规划中，还会将日志与 AI 初步分析结论一起交给开发。

#### 来源材料中的量化数据

| 指标 | 材料给出的结果 |
|---|---|
| 单次日志获取 | 5～10 分钟 → 约 10 秒触发，节省 95%+ 时间 |
| 单次 Jira 提报 | 3～5 分钟 → 一句话触发，人工复核后约 20 秒内确认提交 |
| 累计提报 | 约 1850 次 |
| 累计节省 | 约 7400 分钟，即约 123 小时 |
| 2026-04 提报量 | 147 个 |
| 2026-05 提报量 | 200 个，环比 +36% |
| 2026-06 提报量 | 301 个，环比 +51% |
| 2026-07 提报量 | 618 个，环比 +51% |

以上为案例材料自述，统计口径、去重规则、实际人工耗时和工具服务边界待核验。

### 3.2 日志获取及问题分析

#### 处理流程

```text
飞书发送 Jira 号
→ 自动读取 VIN / 环境 / 时间
→ 默认获取问题时间前后 1 小时的日志
→ 按需设置 range=2h 或 from / to 时间窗
→ 拉取 32+ 种日志
→ Web 端筛选、解密、预览和打包
→ 飞书发送或下载 zip1 格式日志
```

主要能力包括：

- 支持 HU Android、Kernel、ANR/Crash、XCU、5G、QNX、蓝牙等 32+ 种日志；
- 支持自定义时间窗口；
- 日志云端过期时，可用“回读”关键词触发车端重新上传；
- Web 端支持文本、gzip、ZIP、CLP 等格式预览；
- 以 ⭐ 标记距离问题时间最近的文件，并支持按类型筛选和选择性打包；
- 自动重命名，规避飞书发送限制。

| 步骤 | 传统方式 | 日志助手 |
|---|---|---|
| 获取 VIN / 环境 / 时间 | 打开 Jira 手动查找 | 自动从工单读取 |
| 下载日志 | 登录日志平台逐步填写参数并等待 | 机器人直接拉取并打包 |
| 日志解析 | 另找工具解密或本地打开 | Web 端在线预览 |
| 过期日志 | 获取困难 | 自动降级为远程回读 |

材料称单次日志获取可从 5～10 分钟缩短到约 10 秒触发；AI 根因分析仍属于后续规划或 Demo 能力，当前没有独立埋点数据。

### 3.3 HUclaw：车机远程智能控制

#### 传统痛点

截图、投屏、导日志、验证语音、刷版本和修改配置通常要求工程师连接电脑、操作车机并执行多条命令，难以支持出差、居家或远程台架场景。

#### 已实现能力（按材料描述）

| 飞书指令示例 | 车机动作 |
|---|---|
| `SS4 截图` | 抓取车机屏幕并将图片发送到飞书 |
| `SS4 播放音乐` | 模拟语音输入“播放音乐”，走 ASR → NLU → 执行链路，并返回 TTS 结果 |
| `SS4 刷今天主线版本` | 下载对应软件包并完成刷写 |
| `SS4 查版本` | 返回 HU / MCU / 5G 格式化版本信息 |
| `SS3 切 R 档` | 发送 ADB 信号切换档位 |
| `SS4 投屏` | 本地弹出 scrcpy 实时镜像，支持鼠标操作 |
| `抓最近半小时的 Android 日志` | 获取并导出对应时间范围的日志，自动压缩和重命名 |

系统支持 SS2 / SS3 / SS4 双架构自动路由，并可按设备名称分发指令，支持多设备并行管理。

材料称单次操作可从多条指令或步骤缩短到一句话、约 10 秒内完成，节省 90%+ 时间。后续规划包括自然语言测试指令、定时巡检与告警、与日志机器人联动、多人协作以及 CI/CD 触发车机操作。

> **安全提醒**：切换档位、刷写版本、远程控制车机和多设备并行操作均可能影响真实硬件或测试环境。本文没有证明目标确认、权限分级、操作审计、误操作防护和回滚机制已经具备。

### 3.4 SysTest Helper Cloud：Web 化车机测试工具

#### 解决的问题

车机测试依赖大量 ADB 命令，不同 EEA 架构命令格式不同；配置字需要手动进行十六进制计算；设备投屏需要额外客户端，环境配置复杂。

#### 能力对比

| 能力 | 传统方式 | SysTest Helper Cloud |
|---|---|---|
| ADB 指令 | 手敲多条 `adb shell` 命令 | 点击按钮并即时查看结果 |
| 模拟信号（SOA / CAN 等） | 记忆命令格式并逐条输入 | 按分类菜单填写并一键发送 |
| 车辆配置字 | 手动解析和计算十六进制字节 | 50+ 字段可视化点选，自动 CRC8 校验 |
| 投屏、截图、录屏 | 安装 scrcpy 等工具 | 浏览器内实时投屏，支持 H.264 与截图双模式、鼠标操控 |
| 日志 | 手动获取，跨平台解密和打包 | 云端与本地日志自动抓取、解密、打包 |

材料称该工具访问量位居平台 Top 4，是车机操作类工具第一名；详细功能使用量尚未埋点。

### 3.5 台架远程控制及共享平台

该平台有两条主线：

1. **去电脑、去线缆**：车机通电并连接内网 Wi-Fi 后，直接用浏览器投屏、操控和调试；
2. **台架资源池化**：台架不再专属于个人，支持不同车型和版本设备共享，点击即可切换。

目标是减少硬件成本和繁琐接线，提升跨地域协作和测试调试效率。台架控制权限、资源占用冲突、远程断连处理、设备隔离和操作审计待核验。

## 4. 统一导航平台：工具集合平台

案例材料认为，再好的工具如果入口分散，也容易被遗忘。因此建设统一工具集合平台：

- 20+ 个工具统一以卡片形式展示，按类别筛选，快速找到目标工具；
- 提供 AI 聊天助手“理想同学”，用自然语言帮助用户选择工具；
- 每个工具提供视频演示和帮助文档；
- 内置 UV、PV、工具点击热度等行为埋点，用真实使用数据支持后续建设优先级。

这一层的价值不是新增单点能力，而是降低发现、学习和采用工具的成本，并为平台迭代提供使用反馈。

## 7. 核心竞争力与方法论

### 7.1 场景理解

平台不是通用 AI 工具，而是围绕座舱测试的具体对象和流程构建：Jira 需要填写哪些字段、日志目录在哪里、用例模板有多少列、不同架构设备如何操作等领域知识都被嵌入工具。

### 7.2 流程嵌入

通过飞书机器人、Web 工具和统一导航平台，把能力放到工程师原本就在使用的工作流中，减少额外登录、学习和切换成本。

### 7.3 数据驱动迭代

通过 UV、PV、工具点击和业务埋点观察用户真正使用什么，再决定下一步优先级，而不是凭感觉建设平台。

### 7.4 生产环境优先

案例总结的迭代方式是：

```text
找到真实痛点
→ 做最小可用版本
→ 小范围进入生产环境
→ 收集真实反馈
→ 持续迭代
```

### 7.5 从单点解法到系统能力

平台并非先画出完整蓝图，而是解决一个个具体问题；随着工具增多，能力自然覆盖测试大部分链路，并从团队内部扩展到跨部门。

案例的核心判断是：

> AI 不只是替工程师省时间，也让领域专家具备过去只有软件专家或资深测试专家才能拥有的实现能力；最终沉淀的不是一组工具，而是可复用、可传承、可持续进化的 AI 工程化基础设施。

## 8. 任务流与技术能力抽象

### 8.1 典型任务流

```text
业务人员 / 测试工程师提出自然语言需求
→ 平台识别工具和业务上下文
→ RAG 检索内部文档、SDK、规范或知识库
→ LLM 生成用例、脚本、字段草稿或操作计划
→ 调用飞书、Jira、日志平台、ADB、Jenkins、Artifactory、车辆系统等工具
→ 生成结果或执行候选
→ 人工确认高影响动作
→ 返回日志、工单、版本、报告或知识条目
→ 通过埋点和反馈持续迭代
```

### 8.2 主要能力组件

- **LLM**：自然语言理解、字段提取、用例生成、脚本生成、问题总结和初步分析；
- **RAG**：检索 LiAT SDK 文档、测试规范、FAQ 和内部知识；
- **Agent / 工具调用**：连接 Jira、飞书、日志平台、车辆运维系统、Jenkins、Artifactory 和车机设备；
- **ADB / Web / 轻量桥接服务**：将浏览器、聊天机器人和真实车机连接起来；
- **埋点与数据分析**：统计 UV、PV、服务量、工具热度并指导迭代；
- **知识资产化**：将测试经验、规范和 FAQ 沉淀为可检索知识；
- **多设备路由**：根据车型、架构和设备名称选择目标车机。

## 9. 效果与可信度判断

### 9.1 材料自述的效果

- Jira 智能提报：累计约 1850 次，材料称节省约 123 小时；
- 日志获取：5～10 分钟缩短至约 10 秒触发；
- Jira 字段填写：3～5 分钟缩短为一句话触发，人工复核后约 20 秒内确认；
- 车机远程操作：多条命令缩短为一句话，约 10 秒完成；
- SmartScript：材料称编写效率提升 80%，调试时间降低 60%；
- LiAT Visual Builder：材料称脚本构建效率提升 3～5 倍；
- 车辆运营助手：材料称每月节省 4 人天；
- 平台整体：服务 313 人、累计服务 10000 余次。

### 9.2 可信度分层

**较有支撑的部分**：

- 工具名称、覆盖链路和使用场景描述具体；
- Jira 提报、日志下载等工具提供了累计调用量和月度趋势；
- 平台地址和跨部门合作信息可作为后续核验入口；
- 工具从单点痛点逐步扩展的建设逻辑前后一致。

**需要保留的部分**：

- 提效比例缺少基线、样本量、统计方法和对照组；
- 20+ 工具中哪些已生产运行、哪些仍是 Demo，边界需要逐项确认；
- 313 人和 10000 余次是否去重、是否包含自动任务，口径待核验；
- AI 日志根因分析、自然语言自动测试、自动刷写等能力部分仍处于规划或 Demo 阶段；
- 对真实车辆控制、版本刷写、车辆运营审批等高影响操作，材料没有给出完整权限、审计和回滚证据。

**当前判断**：平台和工具矩阵具有较强的真实业务实践特征，Jira 提报和日志获取等高频工具的采用度相对更有数据支撑；效果数字属于来源自述，不应直接当作经过独立测量的绩效结论。整体状态建议标记为“内部案例 / 部分能力已使用 / 生产范围与治理机制待核验”。

## 10. 安全与责任边界

### 10.1 业务与数据风险

- Jira、日志、VIN、车辆版本和问题信息可能包含内部敏感数据；
- 日志下载、解密、打包和自动上传需要明确访问范围、留存期限和脱敏策略；
- 飞书群消息中的自然语言输入可能包含误操作指令或提示词注入内容；
- 车辆运维、预约、临牌、保险和审批信息需要身份认证、最小权限和完整审计。

### 10.2 真实车辆与车机风险

- ADB 控制、切档、远程投屏、语音触发、刷写版本和配置字写入都可能改变真实设备状态；
- 多设备并行路由必须确认目标设备，避免误发到其他车型、版本或正在使用的台架；
- 车辆预约、整备和合规检查不能仅以 AI 生成结果替代业务责任人的确认；
- 自动刷写、自动触发车辆动作和 CI/CD 联动，在补齐授权、隔离、审批、读回校验和恢复机制前，只能在隔离测试环境使用。

### 10.3 建议的权限分级

| 级别 | 示例 | 默认要求 |
|---|---|---|
| 只读 | 查版本、查车辆信息、读取日志、查询 Jira | 登录认证、范围控制、访问审计 |
| 生成候选 / 草稿 | 生成用例、Jira 字段、JQL、测试脚本、车辆预约信息 | 人工检查后才能提交或执行 |
| 低风险执行 | 触发日志下载、导出报告、发送非敏感通知 | 幂等、状态反馈、失败重试和审计 |
| 敏感写入 / 不可逆操作 | 创建工单、修改配置字、切档、刷写、提交审批、远程控制车辆 | 目标确认、逐次显式确认、前后状态读回、责任人和回滚方案 |

### 10.4 必须补齐的审计字段

每次工具调用至少应记录：

- 操作者和身份；
- 目标车辆 / 设备 / 工单 / 环境；
- 工具版本、模型版本和 Skill / 规则版本；
- 原始自然语言指令与解析后的参数；
- 执行前状态、实际命令、执行后状态和读回结果；
- 人工确认记录；
- 成功、失败、超时、重试和补偿动作；
- 相关日志、附件和数据访问记录。

### 10.5 禁止直接迁移项

- 不得将“自然语言一句话控制车机”直接视为生产车辆控制授权；
- 不得让 AI 在没有明确目标确认和人工门槛的情况下刷写版本、切换档位或写入配置；
- 不得将日志 AI 初步分析当作开发根因确认、质量定责或安全结论；
- 不得将车辆合规检查结果直接等同于审批完成；
- 不得把 Demo、来源自述的提效数字或工具调用量当作生产安全和业务效果的充分证据。

## 11. 对其他项目的启发

1. **从高频痛点切入，而不是先做“大平台”**：Jira 提报、日志获取和配置字操作属于重复、高频、规则相对明确的任务，适合优先自动化。
2. **工具接入比模型能力更决定落地价值**：真正的效率来自 AI 与飞书、Jira、日志系统、ADB、Jenkins、车辆系统的连接，而不只是聊天问答。
3. **把人工确认设计成流程节点**：对低风险动作可以自动执行，对真实硬件、审批、写入和刷写等高影响动作必须保留显式确认。
4. **用埋点验证采用度**：平台应同时记录工具访问、成功率、失败原因、人工改动比例和任务完成时间，不能只统计调用次数。
5. **自然语言入口要落到确定性执行器**：LLM 适合解析意图、生成候选和解释；设备命令、字段校验、状态机、权限和回滚应由确定性代码负责。
6. **知识沉淀应与实际工作流绑定**：测试规范、SDK、FAQ、日志经验和问题处理路径只有进入工具和任务流，才能形成持续复用的组织能力。
7. **平台化的关键是复用连接能力**：统一导航、飞书入口、埋点、权限和工具调用框架可以成为基础设施，业务工具则围绕具体痛点快速迭代。

- 平台实际部署环境、访问控制、用户组织范围和数据隔离方式；
- 20+ 工具逐项的状态：Demo、内测、部门生产或跨部门正式服务；
- Jira 提报和日志下载的真实成功率、平均耗时、人工修改率和失败重试率；
- 1850 次提报、10000 余次服务的统计口径和去重规则；
- VIN、日志、录音、车辆信息和内部工单的脱敏、留存与删除机制；
- ADB、配置字、切档、刷写及多设备路由的权限模型、目标确认和回滚设计；
- 车辆预约、整备和合规检查是否保留业务 owner 审批；
- AI 日志根因分析的样本、误报率、漏报率和开发采纳率；
- SmartScript 生成脚本的沙箱、依赖隔离、代码审查和执行权限；
- 跨部门合作的服务边界、数据授权和平台责任主体；
- “理想同学”工具推荐的命中率、用户满意度和不适用场景；
- 工具与知识、Skill、规则的版本管理、owner 审核、撤回和回滚机制。
