# 理想汽车：被动安全部门知识共享助手

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：王兴阳，Level 2，整车电动，2026-07-22，板块：实战案例 · 知识充电 · 观点碰撞，195 阅读）
>
> **一句话**：从"个人 AI 外挂"升级为"部门团宠"——被动安全部门 9 名工程师按专业分工（气囊/ACU/安全带/法规/缝纫/发泡/仿真），每人把自己"压箱底"的文档喂给同一个 OpenClaw 机器人（内部昵称"盾盾"），通过"准备 → @机器人投喂 → **当场提问验证理解** → 归档标注来源"四步流程，建成 21 大章、约 2000+ 行结构化知识库；实现了跨领域知识融合、新人 5 秒出配置对比表、**离职员工知识精确留存**（"双针平缝避免重复踩针，缝纫边距 5±2mm，来源：张工《SAB 气袋设计》"）。**十四案例中"知识资产化"最纯粹、组织侧实践最完整的一篇——02 纵向四资产里知识资产的全生命周期（贡献→验证→治理→融合→传承）都有了实证。**
>
> **顾问点评**：十七案例中唯一覆盖知识资产全生命周期（贡献 → 验证 → 治理 → 融合 → 传承 → 激励）的实证，"当场提问验证"是知识质检的标准答案，来源标注 + 贡献排行同时解决信任与激励，六个坑的坑表本身就能当知识库治理手册用。四个待补点：其一，**9 人规模是未经压力测试的规模**——审核会、贡献排行这些机制在百人部门的运转成本完全不同，跨部门复制时"知识联邦制"的 owner 制度必须先行；其二，**知识交叉发现是被动的**——EDR 新旧规矛盾靠喂文档时偶然发现，应引入定期的全库跨文档一致性检查，把碰撞从运气变成机制；其三，**隐性知识覆盖不了**——手感和直觉判断文档化不了，AI 分身覆盖的只是显性知识，对其边界要有清醒预期；其四，回答准确率无长期追踪。**建议打通**：与 PLM / 设变数据联动防知识过时（车型配置变更时自动标记受影响知识条目）；用案例十七的蒸馏管线把群聊存量讨论挖出来补进知识库；融合回答的准确性做季度抽检，防止"看似有据实则错误"的多人知识混合结论。

- 业务域：整车电动 · 被动安全（气囊系统设计、零部件选型及全专业方向）；
- 平台：OpenClaw（开源 AI 智能体平台，**第三次跨案例出现**：案例六托管失败、案例十三评审成功、本案例知识库成功）。

**升级动机（作者的核心洞察）**：

> 我的知识边界，就是它的知识边界。

个人版 AI 助手再好用，也只覆盖一个工程师的知识面。被动安全领域太大：有人是 ACU 控制器的活字典、有人做了十几年 SAB 气袋有布料选型的手感经验、有人管法规认证条款张口就来——这些"压箱底"的文档散落在各自飞书空间。新人入职得挨个去问，跨项目支持得翻半天群聊。

解法：**每个人把自己最懂的那块喂给同一个 AI——每人只贡献最擅长的部分，所有人用整个团队的完整知识库。**

## 3. 任务流拆解

### 3.1 架构：一个人的种子，长成一棵树

```text
被动安全部门管家机器人（"盾盾"）
├── 基础层：角色设定（被动安全专家人设）
│          + 回答风格（专业严谨、引用数据、标注来源）
│          + 飞书对接（群聊 + 私聊，@ 即用）
├── 知识层：Skill 技能包
│   ├── passive-safety-knowledge 主知识库（SAB/CAB/PAB/DAB/ACU/
│   │   安全带/方向盘/法规认证/设计校核 Checklist/售后案例库，每节标注来源人）
│   ├── 各项目零部件选型配置（24-26 款全车型）
│   └── 专项知识（气帘生锈标准、零重力座椅安全带…）
└── 工具层：飞书文档读写 / 多维表格查询 / 群聊消息搜索 / 文件处理
```

### 3.2 平台选型（为什么是 OpenClaw 而不是 Coze/Dify）

部门级共享的三个核心需求：多人投喂互不干扰、知识交叉融合（不是简单堆砌）、飞书里随时可用。

大模型平台自带知识库功能的限制：知识库更新需重新发布（不灵活）、**无法直接读飞书文档/多维表格/群聊消息**、对话能力受模板限制。

OpenClaw 的优势：直接接飞书（群里 @ 就能用）、Skill 机制让知识库像插件一样叠加、多人通过飞书对话无需额外账号。

### 3.3 协作投喂四步流程（标准化）

```text
① 准备文档：飞书文档/PDF/表格均可，AI 能读甚至图片里的文字
② @机器人发链接："学习一下这个文档 https://li.feishu.cn/docx/xxx"
③ 验证理解（最关键）：当场提问，确保 AI 真的"吃进去了"而不是"看了一眼"
   例：张工喂完 SAB 气袋设计后问——
   "SAB 泄气孔 slit 形式和开孔形式各有什么优劣？周圈 Pin hole 问题怎么解决？"
   答不对就补充说明让它修正
④ 归档：验证通过后自动归档到对应知识库并标注来源，
   回答时能告诉你"这个知识来自张工的《SAB 气袋设计与折叠》"
```

### 3.4 分工：每人认领"责任田"

9 人 × 34 份文档，按专业方向认领（ACU 控制器 4 份、SAB 气袋 3 份、CAB 气帘/发生器 4 份、PAB/安全带 3 份、法规认证 5 份、仿真 2 份、缝纫工艺 2 份、发泡工艺 3 份、整体架构/选型配置 8 份）——没有开会动员，按最懂的人自然分工。

## 5. 效果与证据

| 指标 | 数据 |
|---|---|
| 参与投喂人数 | 9 人 |
| 投喂文档总数 | 34 份 |
| 知识库规模 | 21 大章，约 2000+ 行结构化知识 |
| 覆盖专业方向 | 气囊 / ACU / 安全带 / 方向盘 / 法规 / 缝纫 / 发泡 / 售后 |
| 覆盖车型 | 24/25 款 10 车型 + 26 款 8 车型 |
| 日均使用次数 | 15-25 次 |
| 典型场景 | 方案查询 / 配置对比 / 工单分析 / 会议纪要 / 新人培训 / 技术协议审核 |

三个真实场景（有具体细节佐证）：

1. **跨领域融合**：问"X11 项目的 ACU 回路数量够不够？加远端气囊需要怎么调整？"——一个回答融合了许工的 ACU 回路知识和李工的远端气囊物理防错要求；
2. **新人上手**："对比 X04 和 X11 的 SAB 配置差异"——5 秒出对比表，以前要翻 3 份 Excel、2 份飞书文档或打电话，至少半天；
3. **经验不随人走**：离职同事的知识留存案例——历史遗留问题，机器人直接给出根因（导气袋固定线连孔）、方案（双针平缝避免重复踩针、缝纫边距 5±2mm）和来源（张工《SAB 气袋设计》）。

**意外收获——知识交叉发现**：许工的 ACU 流程文档提"EDR 数据记录满足 GB 39732-2020"，李工的法规文档指出 2024 新规对 B 级数据元素的额外要求——**两份文档单独看都没问题，汇聚对比才发现时间节点差异**。这种"知识碰撞"只在知识汇聚时发生。

## 6. 可信度判断

**判断：十四案例中叙事最完整、可信度最高的一档（与案例三、七并列）——小规模但全生命周期真实跑通。**

可信的部分：

- 人名（张工/许工/孟工…9 人分工表）、文档名（《SAB 气袋设计与折叠》《零重力座椅安全带注意事项》…34 份）、数字（21 章/2000+ 行/日均 15-25 次）全部具体可核对；
- 技术细节精确到工艺参数（双针平缝、边距 5±2mm、周圈 Pin hole、GB 39732-2020 与 2024 新规）——编不出来的领域颗粒度；
- **坑表比成绩单更有价值**：六个坑（知识冲突/重复投喂/质量参差/权限/过时/白嫖顾虑）每个都有对应治理动作，是真实运营过的痕迹；
- 日均 15-25 次是诚实的量级（没有夸大到"全员日百次"）；
- 续篇性质（前作已被社区验证，本篇是响应真实需求），非孤证。

需要保留的部分：

- 9 人部门、34 份文档的规模尚小——治理机制（审核会/贡献排行）在这个规模能运转，到百人部门是否还成立未知；
- "知识碰撞"目前是被动的（喂的时候偶然发现），没有主动的跨文档一致性检查机制；
- 验证理解靠人工提问，没有系统化的知识质量评估（问多少个问题算验证通过？）；
- 回答准确率的长期追踪未提及（AI 融合多人知识时会不会产生"看似有据实则错误"的混合结论）。

结论：**真实、完整、可复制；规模待验证。**

## 7. 对我们当前项目的启发

### 7.1 知识资产的完整生命周期首次全部实证（对应 02 / 04-05）

十四案例中"经验→资产"模式已出现六次，但本案例是唯一覆盖**全生命周期**的：

```text
贡献（责任田分工）→ 验证（当场提问）→ 治理（审核/去重/版本/冲突对齐）
→ 融合（跨领域知识在回答中合并）→ 传承（离职留存）→ 激励（来源标注+贡献排行）
```

其中**治理环节**（坑表里的六项）正是案例九（品类管理 Skill）缺失的部分——谁维护、怎么防过时、怎么解决"谁的知识"。02 的纵向四资产中，知识资产的运营手册可以直接以本案例的坑表为底稿。

### 7.2 "知识变活"是对传统知识管理的根本颠覆（对应 04-06 L3/L7）

作者的结语值得原文记录：

> 以前我们说"知识管理"，通常意味着建一个文档库、写一堆 wiki、搞一套分类体系。但说实话，那些东西建完之后就很少有人去翻了。现在不一样——知识变成了"活的"。你问它一个问题，它给你一个融合了 9 个人经验的答案，还告诉你"这条经验来自谁、出自哪份文档"。

传统知识管理失败于**只写不读**（建完没人翻）；AI 知识库活于**按需生成 + 来源可溯**。对 12-03 的直接映射：Fabless 的失效分析知识、供应商审核经验、8D 报告库——这些组织内同样"散落在各人手里"的资产，本案例的四步投喂 + 责任田分工就是落地模板。

### 7.3 知识交叉发现：反向诊断的知识层形态（对应案例二）

两份各自正确的文档，汇聚后暴露矛盾（EDR 新旧规时间节点）——这是案例二"AI 反向诊断流程资产"在知识维度的自然涌现。目前是被动的，**主动化方向明确：定期让 AI 对全库做跨文档一致性检查（参数值冲突、时间节点失效、口径不一致）**，把"知识碰撞"从偶然变成机制。这与 12-02 的失效关联分析同构：单点都对，组合起来有矛盾。

### 7.4 验证理解：知识投喂的质检环节（对应案例三/七的校准模式）

第三步"当场提问验证 AI 真的吃进去了"是喂文档这个动作的质检——与案例三（两轮定稿）、案例七（读回审计）、案例十（AI 校验人）同一族的"执行后必须验证"铁律，第十四次以不同形态出现。**投喂 → 提问验证 → 修正**本质就是 LI-PAS 的知识库反污染规则在建设期的应用。

### 7.5 组织采纳战术：五条建议全部可复用

1. **先让一个人跑通再推广**（种子用户搭框架跑流程）；
2. **找对第一个投喂者**（知识最全、文档最齐、愿意折腾的"什么问题都问他"的人，不需要是领导）；
3. **场景驱动代替任务驱动**（"下周 XX 评审，把相关知识喂一下"而不是"每人喂 5 份"）；
4. **定期晒效果**（群里分享机器人答得好的案例，拉动未参与者）；
5. **知识要有主人**（联邦制——各管各的专业领域 + 领域负责人审核，不是谁都能改的维基）。

第 5 条与 04-06 L7（业务对象语义）的 owner 机制、12-03 的组织设计直接呼应：**知识资产必须有领域 owner，无主的知识库必然腐烂。**

### 7.6 平台选型判断：OpenClaw 三案例收敛（对应案例六/十三）

```text
案例六（表单协同流）：OpenClaw 失败 → 多维表格胜出
案例十三（跨系统取数+规则推理）：OpenClaw 成功
本案例（多人知识库+飞书生态）：OpenClaw 成功，胜在能直读飞书文档/多维表格/群聊
```

OpenClaw 的适用边界清晰：**活在飞书生态里、需要 Skill 叠加和多人对话的场景**。对比项（Coze/Dify 知识库）败于"更新要重新发布 + 读不了飞书原生数据"——数据在哪个生态，Agent 就得长在哪个生态。

### 7.7 最值得抄的设计

1. **四步投喂流程**（含验证理解）——知识建设期的标准作业程序；
2. **责任田分工表**：按专业方向认领 + 文档数 + 代表性文档，贡献透明可统计；
3. **来源标注 + 贡献排行**：回答必带"来自谁/哪份文档"——既解决信任问题又解决激励问题（对"白嫖"顾虑的制度回应）；
4. **三要素文档质量标准**（是什么/为什么/怎么做）：太简略的补充后再喂；
5. **已投喂清单**防重复；
6. **给机器人起名**（"盾盾"）：降低工具感的采纳细节，与案例十三"小龙虾"同路数。

## 8. 后续想实测 / 追问的问题

- 主动的跨文档一致性检查有没有做（把知识碰撞从被动变机制）；
- 验证理解的标准化：问几个问题、什么深度算通过，有没有题库；
- 融合回答的准确性追踪：AI 融合多人知识时会不会生成"看似有据实则错误"的结论，有没有发现过；
- 治理成本：审核会/定期更新实际执行频率，知识过时的发现滞后多久；
- 规模化测试：其他部门复制的情况（文中说"其他部门在观望"），到 30 人/百人部门治理机制是否还运转；
- 离职留存的边界：手感和判断（隐性知识）文档化不了的部分占比多少，AI 能覆盖的只是显性知识的那部分；
- 知识库和系统数据（配置表、BOM）的关系：选型配置知识会随工程变更过时，与案例四的设变监控有没有联动预警。
