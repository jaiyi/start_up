# 应用案例

本目录用于持续积累看到的 AI 应用介绍：真实落地案例、产品使用案例、客户场景、公开分享的应用实践。

与 `../` 下其他目录的区别：

- 其他目录按"产品类型 / 能力形态"分析产品本身；
- 本目录关注**具体应用场景里 AI 是怎么被用的**：谁在用、解决什么问题、任务流怎么组织、效果如何、哪些是真实落地、哪些只是宣传。

## 收录范围

- 企业内真实 AI 应用案例（设备维修、质量闭环、供应质量、采购、客服等）；
- 厂商公开的客户案例 / 白皮书 / 发布会演示；
- 个人或团队的高质量 AI 使用实践分享；
- 值得借鉴的 Agent / 工作流 / 知识库实际用法；
- 反面案例（demo 花哨但落地失败）同样有价值。

## 每篇案例建议记录

1. 案例来源（链接 / 截图 / 公开资料）；
2. 一句话：谁在什么场景用 AI 解决什么问题；
3. 任务流拆解：输入 → AI 参与 → 人工确认 → 执行 → 反馈；
4. 用到的能力：模型、RAG、Agent、工具调用、MCP、SFT 等；
5. 效果与证据：有没有量化指标，是实测还是宣传口径；
6. 可信度判断：真实落地 / 疑似 demo / 无法验证；
7. 对自己项目的启发；
8. 后续想实测或追问的问题。

## 案例治理与安全边界

案例材料同时包含来源原文、研究者判断、设计蓝图和个人推演，不能仅因为写入本目录就当作已经生产落地。横向比较和高风险案例的统一登记见 [`案例治理矩阵.md`](./案例治理矩阵.md)。

每篇案例后续复核至少要回答：

- 来源与证据等级：是公开代码、内部文章、用户提供材料，还是二手转述？
- 当前状态：来源描述、设计蓝图、试点、已验证运行，还是生产落地未知？
- 业务影响：错误结论可能影响工程数据、真实硬件、生产部署、作业安全、质量或合规的哪一层？
- AI 边界：AI 是检索、分析、生成草稿、编排工具，还是能够触发真实系统动作？
- 工具权限：只读、低风险执行、生成候选，还是敏感写入/不可逆操作？
- 人工门槛：谁确认、谁审批、谁执行、谁承担最终责任？
- 审计与恢复：是否保留输入、命令、读回结果、版本、审批、失败补偿和回滚记录？
- 未决风险：哪些内容尚未核验，哪些能力不能直接迁移到生产环境？

统一治理原则：

1. “iframe/RPA 绕过鉴权”“自动转 ECR”“AI 自主烧录/写寄存器”“自动审批”等表述，若没有授权、权限和审计证据，只能记录为来源描述或待核验风险，不能当作推荐方案。
2. 确定性专业工具负责几何、统计、测试或硬件事实；AI 负责编排和表达。每个工具调用应尽量具备命令、状态确认、读回、预期比对和异常降级。
3. 生产部署、真实硬件写入、工程变更发布、作业许可和现场安全决策保留人工责任主体；“生成结果”不等于“批准执行”。
4. 经验、规则和 Skill 的自动沉淀必须经过 owner 审核、验证、版本登记和可回滚设计，失败路径不能无审核升级为组织规则。

案例状态和安全字段缺失时，统一填写“待核验”，不根据宣传语补写为已落地事实。

## 横向治理入口

- [`案例治理矩阵.md`](./案例治理矩阵.md)：覆盖当前案例的证据、权限、人工责任、审计恢复和禁止直接迁移项。
- [`横向专题/README.md`](./横向专题/README.md)：按设变链路、专业工具接入和经验资产化进行跨案例比较，保留未决问题与验证任务。
- `理想汽车-设备维修全生命周期管理系统.md`：设备维修案例正文及其原始截图，保持与其他单篇案例一致。

## 文档命名建议

案例文档名统一用中文，少用字母代称，要能直接看出系统是干什么的：

```text
<公司或领域>-<系统功能总结性描述>.md
```

例如：

```text
理想汽车-车载性能稳定性问题分析助手.md
美的-质检视觉AI案例.md
```

不要用内部代号或英文缩写作文件名（如 LI-PAS、MIP 之类），代号写在文档正文里即可。

同一来源多个案例可建子目录：

```text
application-cases/理想汽车/
application-cases/OpenAI客户案例/
```

## 累积判断维度

随着案例增多，后续可以做横向归纳，例如：

- 哪些场景是真实高频刚需（每天用）；
- 哪些场景只在发布会里出现；
- 人机分工的常见形态（AI 建议 + 人确认）；
- 数据 / 知识 / 工具 / 权限四个基建里，案例实际缺哪块；
- 案例背后的任务闭环 schema 是否可以抽象复用。
