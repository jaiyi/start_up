# 理想汽车：防再发知识库与 Agent 数模校核实践

> 收录日期：2026-10-16 · 来源：用户提供的理想汽车内部案例材料（原文作者：李书博，Level 4 - AI 达人，整车电动；发布时间：2026-09-11 14:07:11；板块：工具分享 / 知识充电 / 实战案例）
>
> **一句话**：围绕室内灯数模校核，把 Checklist、DMU 规则、DFMEA、历史问题案例和 DTS 标准整理为随插件分发的工程知识基座，再由 Agent 调用确定性几何解析与规则引擎生成带依据和置信度的校核报告；系统同时支持 STEP 文件预扫和 CATIA V5 直连，目标是把依赖供应商排期和人工逐条核对的校核，变成工程师可快速复核的前置检查。

## 1. 背景：数模校核的三个痛点

案例聚焦室内灯等零部件的结构和装配校核。传统流程大致是：

```text
拿到供应商数模
  → 导出 STEP
  → 发给供应商 / CAE
  → 等待排期
  → 获取校核报告
  → 人工逐项比对
```

原文归纳了三个问题：

### 1.1 费时费力

导出、传递、排期和报告比对构成等待链路。项目并行时，单个零件的校核可能成为研发节奏的阻塞点。

### 1.2 规则和案例容易漏项

校核依据分散在 900 多条 Checklist、DMU 规则、DFMEA、历史问题聊天记录和 DTS 标准中。人工逐条检查容易遗漏，尤其在项目赶进度时，漏检会把风险推迟到更晚阶段。

### 1.3 判定容易因人而异

间隙、壁厚、重量和安装点等判断如果主要依赖个人经验，不同工程师可能给出不同结论。没有结构化规则和统一阈值，校核质量难以复现。

这三个问题叠加后，形成：

```text
等待时间长 + 规则覆盖不稳定 + 判定不一致
  → 校核效率低、质量波动、风险后移
```

## 2. 核心解法：防再发知识库驱动的校核

案例的关键不只是“能读 STEP”或“能连接 CATIA”，而是把工程知识组织成 Agent 可以查询和规则引擎可以调用的结构化资产。

### 2.1 知识基座构成

| 资产 | 来源自述规模 | 作用 |
|---|---:|---|
| Checklist | 906 条 | 覆盖外观、法规、间隙、面差等校核项 |
| DMU 规则 | 11 类灯种 | 间隙阈值、面差要求、安装点规范、目标重量 |
| DFMEA | 748 条 | 失效模式与严重度评级，提示高风险位置 |
| 问题案例 | 355 条 | 真实项目问题、原因分析和规避方案 |
| DTS 标准 | 7 类灯种 / 17 条 | 灯具与周边件的外观间隙、面差和公差定义 |

这些内容被打包进插件的 `data/knowledge.db`，并配套 `data/rules/*.json`。来源描述为安装后即可查询，不依赖外部知识服务。

### 2.2 知识资产的作用边界

知识库不是把文档简单塞进 RAG，而是为不同类型的判断提供不同依据：

```text
Checklist → 应该检查什么
DMU 规则 → 用什么阈值和条件判断
DFMEA → 哪些失效模式风险更高
历史问题 → 过去哪里出过问题、如何规避
DTS 标准 → 外观与公差的专项约束
几何解析 → 当前模型实际测到了什么
```

Agent 负责把灯种、TG 阶段、项目和数模数据路由到对应规则；确定性几何工具负责提取尺寸、体积、质心、零件数量和间距；规则引擎负责比较和分类；报告生成器负责组织证据与表达结果。

### 2.3 置信度和证据标注

报告为结论附带置信度：

| 标记 | 含义 | 典型内容 |
|---|---|---|
| 🎯 高 | 几何参数直接测量或确定性计算，无需额外估算 | 包围盒、实测间距、零件数量 |
| 🔍 中 | 依赖近似或估算，建议工程师复核 | 缺内部结构时的重量估算、包围盒初筛间距 |
| ⚠️ 低 | 依赖知识匹配或经验推断，需要工程师判断 | DFMEA 关联、历史问题匹配 |
| 🔵 需数据 | 当前数据不足，不能形成有效判断 | 单零件无法判断装配间隙、缺装配体 |

这比只输出“通过 / 不通过”更接近工程使用：用户能够区分确定性测量、近似分析和知识提示。

## 3. 两种接入模式

### 3.1 模式 A：STEP 文件校核

| 项目 | 内容 |
|---|---|
| 入口 | 飞书发送文件给 Agent，或命令行执行 |
| 数据来源 | `.stp` / `.step` 文件 |
| 几何解析 | `cadquery` / Open CASCADE |
| 适合场景 | 供应商来件、批量预扫、离线筛查 |
| 前置动作 | 需要从 CATIA 或其他 CAD 工具导出 STEP |

典型触发语句是“校核这个 STEP，室内顶灯，TG2，项目 W05”。Agent 依次完成几何解析、规则校核、知识匹配和 Markdown 报告生成。

### 3.2 模式 B：CATIA V5 直连

| 项目 | 内容 |
|---|---|
| 入口 | Windows 桌面 GUI 插件 |
| 数据来源 | 当前 CATIA V5 中打开的 CATPart / CATProduct |
| 几何读取 | `pywin32` / COM 接口 |
| 适合场景 | 工程师边改数模边校核 |
| 前置动作 | CATIA V5 已启动并加载目标模型 |
| 主要收益 | 不需要反复导出 STEP，修改后可直接重新校核 |

该模式解决了“改一版数模就要重新导 STEP”的摩擦。原文提到整车合并件可能达到 392MB，直接读取当前 CATIA 文档也可以绕开文件传输和机器人下载限制。

### 3.3 两种模式的选择

```text
供应商文件 / 批量筛查 → STEP 模式
工程师本地设计 / 边改边校 → CATIA 直连模式
```

两者共享知识库、规则引擎和报告结构，但输入数据、权限和失败模式不同，不能把 STEP 预扫结果直接等同于 CATIA 装配体中的完整工程结论。

## 4. 三步流水线

### 4.1 几何提取

**STEP 模式**使用 cadquery / Open CASCADE 解析：

- 尺寸和包围盒；
- 体积、表面积和质心；
- 零件数量；
- 装配体零件间最小间距；
- 单零件有效壁厚的估算。

**CATIA 模式**通过 COM 读取：

- 包围盒；
- 体积、表面积和重心；
- 装配体结构；
- 零件间最小间距。

几何工具只负责“当前模型测到了什么”，不负责把测量值解释成最终工程批准。

### 4.2 数据预处理

真实数模往往不是干净的单灯零件，需要先确定测量对象和分析范围。

| 场景 | 处理方案 | 主要边界 |
|---|---|---|
| 收到总成数据 | 优先让用户单独导出灯体；或按零件号筛选；也可用质心空间聚类粗略识别灯体 | 聚类只是估计，必须让用户确认筛选结果 |
| 文件超过 32MB | 飞书云空间发链接；CATIA 轻量导出；ZIP 压缩 | 飞书机器人下载上限、用户身份上限和压缩效果需按环境核验 |
| 大装配体 DMU 超时 | 精简为灯体 + 安装面；先用 AABB 包围盒筛候选，再对候选对做精确计算 | 包围盒嵌套或重叠可能误报间距为 0，只适合初筛 |

预处理的核心不是追求自动化率，而是先确认“量的是谁”。

### 4.3 规则引擎

提取参数与知识基座比对：

```text
实测几何参数 + 灯种 + TG 阶段 + 项目
  → DMU / Checklist / DFMEA / DTS 规则
  → pass / warning / fail / information / needs-data
```

来源中列出的检查包括：

- DMU 间隙：实测间距与阈值比较；
- 壁厚：例如 1.5～4.0mm 合理范围；
- 重量：体积 × 密度与目标重量比较；
- 包围盒：标注测量对象是单零件还是整个文档；
- Checklist：按灯种和 TG 阶段关联校核项；
- 历史问题：匹配相似问题、原因和规避方案。

### 4.4 报告生成

报告以 Markdown 为主，可直接贴入飞书文档或群聊，也支持 `.md`、`.txt`、`.json` 导出。示例结构包括：

```text
校核报告 [插件版本 v7.1]
灯种 / TG 阶段 / 项目

校核概览：通过 / 不通过 / 信息 / 需数据
Checklist 匹配数量
历史问题关联数量

逐项校核结果：
  结论 + 测量值 + 阈值 + 位置 + 置信度

关联历史问题：
  问题现象 + 原因 + 规避方案
```

一个重要设计是：间隙不通过时给出两个零件、坐标和间距，而不是只给一个红色状态；包围盒结果标出测量口径，避免把整车合并件的数值误当作单个灯具的数值。

## 5. 效果与证据口径

### 5.1 来源给出的对比

| 指标 | 传统方式 | Agent 校核 |
|---|---|---|
| 耗时 | 2～3 天（对比表） | 3 分钟（对比表） |
| 漏项风险 | 人工逐条，风险较高 | 全量扫描，理论上降低漏项 |
| 结论一致性 | 因人而异 | 规则化、可复现 |
| 知识覆盖 | 依赖个人经验 | 906 条 Checklist、748 条 DFMEA、355 条案例 |
| 是否导 STEP | 需要 | CATIA 直连模式不需要 |

案例标题另给出“从 2h 到 20min”的表述。两组数字的任务范围和计时口径没有说明，可能对应不同版本、不同零件或是否包含人工复核的不同流程。因此本文只记录为来源自述，不将其合并为“平均提效 6 倍”或“固定 20 分钟”的结论。

### 5.2 更可信的工程价值

在缺少对照实验时，案例的价值不应只用分钟数衡量，还包括：

- 把分散的规则和历史问题变成可查询资产；
- 把校核项、阈值、测量值和结论统一留痕；
- 把“需数据”与“高置信度结论”明确区分；
- 把单零件、装配体、近似测量和精确测量的边界写入报告；
- 让问题更早暴露，而不是等供应商或后续评审阶段才发现。

实际提效仍需补充：基线任务定义、样本数量、零件复杂度、人工复核时间、失败率、误报率、漏报率和不同版本的可比性。

## 6. 运行、部署与版本纪律

### 6.1 CATIA V5 插件环境

来源说明的模式 B 环境：

- Windows；
- CATIA V5 已启动并加载模型；
- Python 3.8+；
- `pywin32`；
- `scripts/` 与 `data/` 必须保持同级；
- `data/knowledge.db` 和规则 JSON 必须随插件分发。

启动后选择当前 CATIA 文档，设置灯种、TG 阶段和项目，再执行校核。报告带插件版本号，使用者应在发送报告前确认版本，避免旧目录与新文件混装。

### 6.2 版本、资产和数据边界

```text
插件版本
+ knowledge.db 版本
+ rules/*.json 版本
+ CATIA 版本
+ 模型版本
+ 项目 / 灯种 / TG 阶段
  → 才能解释一次校核报告
```

只留一份最终 Markdown 报告是不够的。至少应能够追溯输入模型、知识库和规则版本、测量口径、调用方式、执行人、运行时间、人工修正和最终确认结果。

## 7. 关键工程坑与方法论沉淀

### 7.1 大文件与性能

STEP 面数和零件数量增加后，逐零件遍历可能超时。来源采用面数和零件数阈值进行降级：面数过多时跳过壁厚估算，零件数过多时跳过逐对精确间距计算。降级必须在报告中显式说明，不能静默地把“没检查”写成“通过”。

### 7.2 C++ 错误输出

Open CASCADE 的错误可能直接写入操作系统文件描述符，Python 的 `redirect_stdout` 无法拦截。来源通过 OS 级重定向处理噪声。这是工程实现细节，但也说明专业几何库的异常不能只按 Python 层日志设计。

### 7.3 单零件不能假装有装配间隙

单个 CATPart 没有与另一个零件共同的装配坐标上下文，不能得出真实 DMU 间隙。报告应写“🔵 需装配体”，而不是猜一个数字。

### 7.4 口径优先于单位

案例曾出现单盏灯估重 1030kg 的荒谬结果。根因不是单位换错，而是当前文档是整车合并件，测量对象错了。对应处理是：

- 优先使用零件自身 CATPart；
- 对名字含 `AllCATPart` 的整车合并件排除重量估算；
- 在报告中说明排除原因；
- 所有有歧义的结果标注测量对象。

> 看到荒谬数字，先问“量的是谁”，再问“单位是否正确”。

### 7.5 间距必须使用装配上下文

体积、表面积和重心是形体自身属性；间距是两个零件之间的相对关系，必须通过 CATIA Selection 获取带完整装配路径的引用。来源从 v6 到 v7.0 才解决这一问题，说明“能取到几何对象”不等于“取到了正确的装配实例”。

### 7.6 区分方法不存在和参数错误

COM 调试中，`AttributeError` 通常说明方法不存在，继续替换参数没有意义；`com_error` 才更可能是参数或上下文问题。先区分错误类型可以减少盲目试错。

### 7.7 绝不渲染“全 0 的正常报告”

如果规则引擎没有产出有效结果，格式完整但数字全 0 的报告会被误认为校核通过。v7.1 的处理是拿不到有效结果就报错退出，不生成报告。

这条原则应推广到所有工程 Agent：

```text
没有有效证据 → 报错或 UNVERIFIED
不能把空结果渲染成通过
```

## 8. 适用边界

### 8.1 适合

- 供应商数模的快速预扫；
- 人工校核前的 Checklist 全量检查；
- CATIA 中边改边校；
- 历史问题和 DFMEA 的关联提示；
- 在明确规则和输入范围内生成带证据的报告。

### 8.2 不替代

- 精确 CAE 应力、热、光学分析；
- A 面曲面质量和造型判断；
- 正式 DMU 评审、工程签字和设计放行；
- 装配体缺失时的真实间隙结论；
- 需要工程师确认的复杂结构、设计意图和异常结果。

这个工具更准确的定位是：**知识驱动的数模校核预扫和报告生成器**，不是自动签核系统。

## 10. 对当前项目的启发

### 10.1 “知识基座 + 确定性引擎 + Agent 编排”

这个案例与 CATIA 装配路径校核、工艺设计合规评审形成互补：

```text
结构化工程知识
  → Agent 识别场景、匹配规则和组织任务
  → CAD / 几何引擎测量事实
  → 规则引擎执行确定性比较
  → Agent 组织证据和报告
  → 工程师复核、确认和反馈
```

LLM 不应承担几何事实判断；几何库不应承担业务规则解释；知识库不应未经审核自动升级为组织标准。

### 10.2 防再发库不是历史案例搜索框

真正有价值的“防再发”闭环应是：

```text
发现问题
  → 记录原始数模、测量值和上下文
  → 形成问题案例与原因分析
  → 提炼为 Checklist / DMU 规则 / DFMEA 条目
  → 在后续项目和版本中自动匹配
  → 人工确认是否命中
  → 记录复发、误报、漏报和规避效果
  → 更新规则或撤回错误资产
```

相似历史案例只能提供提示，不能直接证明当前问题相同。案例版本、车型、灯种、TG 阶段、设计状态和适用条件都需要参与匹配。

### 10.3 “口径优先于数字”是通用工程原则

整车合并件导致 1030kg 的例子说明，很多 AI 工程错误不是算术错误，而是对象、版本和范围错误。所有输出都应同时说明：

- 测量对象；
- 数据来源；
- 版本和时间；
- 计算或近似方法；
- 是否跳过了某些检查；
- 结论是否需要人工确认。

### 10.4 生成报告不等于批准执行

即使 Agent 能生成完整 Markdown 报告，正式 DMU 评审、供应商反馈、设计变更、工程签核和量产放行仍应有责任人。高风险结论必须携带证据和状态，不应只给一个看似确定的红绿灯。

---

## 安全与责任边界

- **AI 边界**：Agent 负责知识检索、任务编排、规则匹配和报告表达；cadquery、CATIA 和规则引擎负责几何测量及确定性比较。
- **知识边界**：Checklist、DFMEA、问题案例和 DTS 标准必须有来源、版本、owner、审核和撤回机制；候选案例不能自动变成正式规则。
- **模型边界**：单零件不能给出真实装配间隙；整车合并件不能直接作为单灯重量口径；缺数据时输出“需数据”或“未验证”。
- **人工责任**：工程师负责模型选择、项目参数、规则适用性、异常结果和正式校核确认；Agent 不替代设计签核或供应商认可。
- **系统权限**：CATIA 直连、文件读取、知识库更新和报告分发应按最小权限配置；现有材料未证明具备完整身份、审计和隔离机制。
- **审计恢复**：应记录模型、规则、知识库、插件、CATIA、执行人、运行时间、输入参数、工具调用、读回结果、人工修正和报告版本；失败、超时和部分完成应可追溯。
- **禁止直接迁移**：不能将来源自述的“2h→20min”或“2～3 天→3 分钟”直接视为普遍生产指标；不能把预扫报告直接作为正式 DMU 签字或质量放行依据。
