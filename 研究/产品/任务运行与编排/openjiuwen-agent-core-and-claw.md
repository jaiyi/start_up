# openJiuwen（agent-core / JiuwenClaw）产品矩阵调研

## 1. 调研对象与资料来源

- 调研对象：GitHub 组织 `openJiuwen-ai` 下的产品矩阵，重点是 `jiuwenswarm/JiuwenClaw`（约 5.9k stars，Apache-2.0）与 `agent-core`（约 444 stars，Python SDK）。
- 资料来源：GitHub 仓库 README 与官方文档。README 中出现华为云 MaaS 生态徽标、"小艺"通道等强华为系信号，但**组织与华为的正式归属关系未在 README 中明示，待验证**——本文按"华为系开源生态"的保守口径描述。
- 调研日期：2026-09-29。

---

## 2. 一句话定位

openJiuwen 是一个**覆盖"Agent 运行时 SDK → 个人 AI 管家 → 可视化编排 → 记忆 → 推理服务"全栈的开源 Agent 产品矩阵**，对标方向是 OpenClaw / Manus 类个人 Agent 加企业 Agent 平台的组合。

```text
agent-core 是发动机（运行时），JiuwenClaw 是整车（端到端管家），其余是配件厂。
```

---

## 3. 产品背景

openJiuwen 的产品切分方式值得注意：它不是一个大仓库，而是**按层拆成一组可独立使用的开源项目**，每一层都单独开源、单独有 stars。这本身就是一个"平台供给分层"的样本，和我们 04-06 里"公共品底座 + 场景模板"的思路可对照。

---

## 4. 核心能力拆解

### 4.1 agent-core：异步工作流运行时 SDK

Python SDK，定位是"高性能 Agent 运行时"。关键能力：

- **异步并行图执行**：工作流按 DAG 组织，节点并行调度；
- **多工作流跳转 + checkpoint 中断恢复**：长任务可暂停、恢复、从断点续跑——这是 17 个案例里普遍缺失、我们平台设计里排在"状态管理"下的能力，它做成了 SDK 原语；
- **prompt 自动优化**：内置 prompt 优化回路；
- **全链路可观测**：trace / 状态 / 成本贯穿执行全程。

### 4.2 JiuwenClaw：个人 AI 管家

定位 "Your On-Call AI Butler"，约 5.9k stars。能力面：

- **多通道入口**：小艺通道（华为语音助手）、飞书通道、Web 前端；
- **定时心跳任务**：常驻型主动 Agent（cron + 心跳唤醒），不是被动问答；
- **Skill 自演进**：Skill 在使用中自动演化升级；
- **记忆系统**：内置长期记忆；
- **浏览器自动化**：可直接操作网页完成任务；
- **上下文压缩卸载**：长会话的上下文管理策略。

形态上与理想内部的 OpenClaw + 个人分身（案例十七）高度同类。

## 5. 与相邻产品的差异

| 相邻产品 | 差异 |
|---|---|
| OpenClaw（理想内部） | 形态几乎同构（飞书通道 + Skill + 心跳任务）；openJiuwen 的差别在运行时（agent-core 的 checkpoint 恢复）是独立 SDK，且背靠华为云 MaaS 的模型供给 |
| LangGraph / 主流编排框架 | agent-core 的差异化卖点是 checkpoint 中断恢复 + prompt 自动优化 + 可观测打包成默认能力，而不是需要自己拼 |
| Manus 类闭源 Agent | 全链路开源、可私有化，且每一层可单独取用 |
| Dify / Coze 类平台 | 后者是"画布式应用搭建平台"；openJiuwen 更偏运行时 + 管家形态，agent-studio 才与其对标 |

## 6. 优势

1. **分层开源的产品化思路**：运行时、记忆、协议、推理各自独立项目，企业可以按层采纳而不是整体绑定；
2. **checkpoint 中断恢复是稀缺能力**：长任务的断点续跑在开源 Agent 栈里普遍缺位，它做成了运行时原语；
3. **入口策略务实**：小艺 + 飞书 + Web 三通道，覆盖"个人助手"的主要触达面，与 04-06 "入口在飞书/终端而不在工作台"的判断一致；
4. **生态背书**：华为云 MaaS 提供模型供给，私有化路线对国内企业友好；
5. **Skill 自演进方向正确**：把"经验→资产"的自动通道做进产品，而不是靠人工投喂。

---

## 7. 短板与未验证点

1. **Skill 自演进无质检**：README 未描述自演进的评审、测试、回滚机制——这与理想 17 案例中"Skill 越积越多、无人负责腐烂"是同一类风险，甚至更尖锐（自动演化 + 无治理 = 漂移加速器）；
2. **治理面整体偏薄**：权限、审计、成本在 README 中着墨少，企业级 RBAC / 动作审批未验证；
3. **个人管家定位的授权边界**：浏览器自动化 + 定时主动任务 + 记忆，组合起来后"它替你做了什么"的可解释性存疑；
4. **归属关系待验证**：华为系背景如果坐实，需评估其与华为云商业产品的边界（哪些会保持开源、哪些是引流面）；
5. **agent-core 444 stars**：与 JiuwenClaw 的热度差距大，运行时本体的社区成熟度需单独评估；
6. 多项目的**版本协同与长期维护承诺**未见说明。

---

## 8. 适用场景

- 需要可私有化、可二次开发的企业 Agent 运行时底座（用 agent-core 替代自研状态管理）；
- 个人 / 部门级常驻助手（JiuwenClaw 直接对标我们的个人分身类需求）；
- 长流程任务的断点恢复场景（审批中断、跨天任务、人工介入后续跑）；
- 华为云技术栈企业的模型供给 + Agent 栈一体化选型。

## 9. 对我们当前项目的启发

**（1）运行时原语清单可以直接抄。** agent-core 的"异步并行图执行 + 多工作流跳转 + checkpoint 恢复 + 全链路可观测"几乎就是我们 04-05 Task 对象设计里状态管理一节的开源实现参考。自研前先评估直接采纳或包一层。

**（2）它是 OpenClaw 的开源镜像，用来做差距分析。** 理想内部的 OpenClaw 生态（案例里的飞书管家、消息蒸馏、Skill 社区）与 JiuwenClaw 同构。对比两边的取舍，能看出理想这套是"生态选择"还是"生态妥协"——特别是 openJiuwen 把 checkpoint 恢复做成了原语而理想案例里没有出现这个能力，这是一处可量化的差距。

**（3）Skill 自演进 = 平台治理的试金石。** openJiuwen 和理想社区都走向"Skill 自动演化 / 开放上载"，两边都没有解决质检。这进一步支持 04-06 的判断：资产注册 + owner + 遥测不是可选项，是这类生态能否不腐烂的前提。可以在文档中把它记为外部佐证。

**（4）分层供给的产品策略样本。** openJiuwen 按层拆仓、每层独立开源的做法，是"公共品底座 + 场景模板"分层供给的一个真实参照：底座层（运行时/协议/推理）追求被集成，场景层（管家/studio）追求被使用。

---

## 10. 后续需要实测的问题

1. agent-core 的 checkpoint 恢复在真实长任务（跨审批节点、跨天）中的可靠性，恢复后上下文是否完整；
2. JiuwenClaw 的飞书通道接入成本与 OpenClaw 的对比（权限模型、消息回调、文件交互）；
3. Skill 自演进的实际机制：触发条件、变更范围、有没有任何评审或回滚；
4. agent-memory 的记忆提取 / 检索质量，与我们案例十七的"蒸馏双管线"对比；
5. 华为云 MaaS 依赖的解耦程度：脱离华为云能否完整私有化运行；
6. openJiuwen 组织与华为的关系确认（官方公告 / 媒体信息），以判断开源承诺的可信度。
