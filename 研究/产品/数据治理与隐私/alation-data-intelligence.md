# Alation 数据目录与数据智能平台调研

## 0. 调研边界说明

本文基于对 Alation 公开产品定位的通用认知，以及我们当前的数据治理 / AI 原生数据平台分析框架整理。由于当前会话没有直接联网检索官网能力，具体产品版本、套餐、最新功能和客户案例需要后续用官方资料复核。

本文重点判断 Alation 在 AI 原生数据平台中的角色。

---

## 1. 一句话定位

Alation 是以数据目录、数据搜索、数据治理和数据智能为核心的数据治理平台。

在 AI 原生数据平台里，它更像：

```text
帮助人和 AI 找到可信数据、理解数据语义、追溯数据来源的数据智能层。
```

---

## 2. 产品背景

Alation 早期是数据目录和数据搜索领域的重要厂商，核心问题是：

```text
企业数据很多，但用户不知道该用哪个、是什么意思、是否可信、谁在维护。
```

随着企业数据平台复杂化，数据目录不再只是目录，而要结合：

- 数据治理；
- 数据血缘；
- 数据质量；
- 查询行为；
- 业务术语；
- 数据协作；
- 政策与合规。

AI 时代，这些能力会进一步成为 LLM / Agent 使用企业数据前的上下文基础。

---

## 3. 核心能力拆解

### 3.1 数据目录与搜索

Alation 的基础能力是数据目录和搜索。

典型能力包括：

- 搜索表、字段、查询、报表、Dashboard；
- 查看数据说明、owner、标签、认证状态；
- 识别常用数据集；
- 基于使用行为推荐数据；
- 提供数据资产详情页。

这解决的是数据发现问题：

```text
业务用户和分析师如何找到正确的数据？
```

### 3.2 数据智能与使用行为

Alation 的一个特色是利用用户查询行为和协作信息增强数据发现。

例如：

- 哪些表最常被使用；
- 哪些查询模式被复用；
- 哪些数据集被专家认可；
- 哪些字段经常一起出现；
- 哪些用户或团队是某个主题的数据专家。

这类行为元数据对 Agent 也有价值。

Agent 生成 SQL 或选择数据源时，不应该只看字段名，还应该参考：

```text
使用频率、专家背书、认证状态、历史查询模板、业务说明和质量信号。
```

### 3.3 业务术语与治理

Alation 通常支持业务 glossary、policy、stewardship 等能力。

这对 AI 原生数据平台非常重要，因为 LLM 需要理解：

- 业务术语；
- 指标定义；
- 同义词；
- 禁用字段；
- 敏感数据；
- 数据使用政策；
- 可信数据集。

如果没有这些上下文，Agent 很容易：

- 用错表；
- 混淆指标；
- 查询敏感字段；
- 生成看似合理但业务错误的答案。

### 3.4 血缘、质量与影响分析

Alation 的治理能力通常会覆盖血缘和质量集成。

重点问题包括：

```text
这个报表来自哪些表？
这个字段改动影响哪些下游？
这个数据集质量是否可靠？
谁负责修复这个数据问题？
```

在 AI 时代，这些问题会扩展为：

```text
AI 结论引用了哪些数据？
Agent 的判断是否基于可信数据集？
模型输入是否包含敏感字段？
生成结果是否可以回溯到数据源？
```

---

## 4. 与 AI 原生数据平台的关系

| AI 原生数据平台维度 | Alation 相关能力判断 |
|---|---|
| 计算 | 不负责底层计算 |
| 供给 | 不直接存储数据，但增强数据发现和取用 |
| 治理 | 数据目录、政策、术语、血缘、质量、合规是核心 |
| 语义 | 业务 glossary、指标解释、认证数据集较关键，本体深度需验证 |
| AI / Agent | 可为 Agent 提供可信数据上下文和治理规则 |
| 安全 | 数据政策、敏感数据、权限可见性，运行时控制需依赖底层系统集成 |

Alation 不是完整 AI 原生数据平台，但可以成为其中的“数据智能和语义发现层”。

---

## 5. 优势

1. **数据发现能力强**：适合解决企业数据资产难找、难懂、难信的问题。
2. **行为元数据有价值**：历史查询和使用行为可以帮助判断数据可信度。
3. **治理与业务术语结合**：有助于降低 AI 用错数据或混淆指标的风险。
4. **适合多工具环境**：作为横跨多个数据源和 BI 工具的治理层。
5. **对 Agent 选数有启发**：Agent 可以借助数据目录选择更可信的数据集。

## 6. 短板 / 未验证点

需要继续验证：

- 是否已支持 AI 模型、Prompt、向量、Agent 等 AI 资产治理；
- 是否有面向 LLM / Agent 的 API 或上下文服务；
- 业务语义层是否能升级为本体关系，而不只是 glossary；
- 权限和政策是否能在 Agent 工具调用时实时生效；
- 是否支持私有化和高合规行业部署；
- 与 Atlan、Collibra、OpenMetadata、DataHub 相比的差异化。

---

## 7. 适用场景

更适合：

- 数据资产多、使用者多、找数困难的大中型企业；
- 需要规范业务术语、指标口径和数据政策的组织；
- 多 BI、多数仓、多团队协作环境；
- 希望为 AI / Agent 提供可信数据上下文的企业。

不一定适合：

- 没有数据平台基础的小团队；
- 需要完整 AI 开发、模型训练和 Agent Runtime 的平台；
- 主要问题是底层湖仓建设而非数据发现和治理的企业。

---

## 8. 对我们当前项目的启发

### 8.1 对家庭营养师 Agent

Alation 的启发是：Agent 推荐前要知道哪些数据“可信”。

家庭营养师项目可以简单实现：

- 明确哪些菜谱是已确认；
- 哪些家庭偏好是长期有效；
- 哪些反馈只是临时意见；
- 哪些库存数据是最新；
- 哪些推荐历史需要避免重复。

### 8.2 对连山产品

连山工业 Agent 需要类似数据目录和行为元数据：

- 哪些工艺参数表被专家常用；
- 哪些质量指标是认证口径；
- 哪些历史案例被多次复用；
- 哪些诊断结论被证明有效；
- 哪些数据源存在质量风险。

这能让 Agent 从“能查数据”走向“知道哪些数据值得信”。
