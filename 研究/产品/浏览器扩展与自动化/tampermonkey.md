# Tampermonkey 产品调研

> 调研日期：2026-10-16
> 产品：Tampermonkey（油猴）
> 产品类型：Userscript Manager / 网页层可编程扩展运行时
> 资料口径：基于 Tampermonkey 官方网站、官方 GitHub 仓库元数据与 README、公开产品说明整理；未安装扩展、未执行任何第三方用户脚本，也未对当前闭源版本源码做内部实现推断。
> 重要边界：官方 GitHub 仓库 README 明确说明该仓库只包含截至 2.9 版本的源码，更新版本采用专有许可证。因此，本文将历史开源代码、当前官网能力和推断出的产品模型分开记录。

## 0. 一句话定位

**Tampermonkey 是一个跨浏览器 Userscript Manager：它在用户授权的网页上下文中加载、管理并运行 JavaScript 用户脚本，让用户可以在不修改网站源代码的情况下，给网页增加按钮、修改界面、自动填表、读取或处理页面信息，并通过元数据、权限 API、更新机制和 Dashboard 管理脚本生命周期。**

它不只是一个“装脚本的浏览器插件”，更准确地说，是：

```text
网页匹配规则
+ 用户脚本运行时
+ 浏览器扩展权限桥接
+ 脚本安装 / 更新 / 启停控制面
+ 用户脚本生态入口
```

## 1. 产品背景与解决的问题

浏览器页面通常是用户访问业务系统、内容网站和在线工具的统一界面，但网站未必提供用户所需的每一个小功能：

- 重复填写表单、点击按钮和切换页面；
- 页面信息展示不符合个人工作习惯；
- 站点没有提供批量操作、快捷入口或额外字段；
- 某些站点需要将多个页面上的信息组合起来处理；
- 用户希望快速试验一个页面增强，而不必等待站点官方改版。

Tampermonkey 将“改网页”从修改站点源代码或开发完整浏览器扩展，降低为编写一个带元数据头的 JavaScript 文件：

```text
写一个用户脚本
→ 声明匹配哪些页面
→ 声明需要哪些权限 / 依赖
→ 安装到 Tampermonkey
→ 页面匹配时自动注入执行
→ 在 Dashboard 中启停、编辑、更新和排查
```

其核心价值不是生成代码，而是提供一个稳定的**网页层脚本分发与执行容器**。

## 2. 典型用户与使用场景

### 2.1 典型用户

- 具有一定 JavaScript 能力的个人用户；
- 希望快速改造网页的前端开发者；
- 需要在内部网页上补充快捷入口和重复操作自动化的业务人员；
- 维护公共用户脚本的脚本作者和社区贡献者；
- 用浏览器作为主要工作界面的测试、运营、内容处理和研究人员。

### 2.2 适用场景

| 场景 | 典型做法 | 适用程度 |
|---|---|---|
| 页面增强 | 添加按钮、快捷菜单、样式和字段展示 | 很适合 |
| 重复操作 | 自动点击、填表、翻页、筛选和批处理 | 适合，但需控制频率和站点规则 |
| 个人工作台 | 在内部系统页面上叠加计算、查询和快捷操作 | 适合，需经过企业授权 |
| 页面信息提取 | 读取 DOM、整理字段、导出结果 | 适合，需尊重隐私与访问规则 |
| 跨网站流程 | 在多个站点之间传递信息 | 可实现，但跨域、身份和合规风险较高 |
| 高可靠业务自动化 | 订单、审批、财务、生产写入等关键流程 | 不应仅依赖用户脚本 |
| 复杂桌面 / 设备控制 | 本地文件、真实设备或操作系统级自动化 | 不是其主要定位，应使用专门工具并显式治理 |

## 3. 核心工作流

### 3.1 从安装到运行

```text
发现或编写用户脚本
→ 安装 Tampermonkey
→ 安装脚本（URL、脚本站点或本地编辑）
→ 解析用户脚本元数据块
→ 根据 @match / @include / @exclude 判断页面是否命中
→ 创建用户脚本执行上下文
→ 注入脚本并提供声明的 GM_* 能力
→ 页面加载、交互或菜单事件触发脚本逻辑
→ 通过 Dashboard、Popup、通知和日志观察状态
```

### 3.2 脚本开发闭环

```text
识别网页任务
→ 编写最小脚本
→ 限定 URL 匹配范围
→ 只申请必要权限
→ 在测试页面运行
→ 检查页面状态、异常和副作用
→ 发布新版本或个人同步
→ 发现站点变化后维护 / 回滚 / 禁用
```

### 3.3 用户脚本的基本形态

用户脚本通常包含一个元数据块和 JavaScript 主体。下面是**抽象示例**，不应直接用于真实业务系统：

```javascript
// ==UserScript==
// @name         Example Page Helper
// @namespace    https://example.invalid/
// @version      0.1.0
// @description  Add a local helper to an authorized test page
// @match        https://example.invalid/*
// @grant        GM_registerMenuCommand
// @grant        GM_notification
// ==/UserScript==

(() => {
  'use strict';

  GM_registerMenuCommand('Show helper', () => {
    GM_notification({
      title: 'Example Page Helper',
      text: 'This is a local test action.',
    });
  });
})();
```

真正的生产或内部业务脚本还需要经过目标站点授权、代码审查、数据保护和回滚验证。

## 4. 产品能力拆解

### 4.1 脚本管理 Dashboard

官方产品介绍强调，Dashboard 用于集中查看和管理已安装脚本，通常包括：

- 脚本列表和启用状态；
- 新建、编辑和删除脚本；
- 最近更新时间、脚本主页等信息；
- 排序和脚本概览；
- 更新检查、脚本设置和配置模式。

这使 Tampermonkey 从“一次性脚本加载器”变成了一个有生命周期的脚本控制面。

### 4.2 工具栏 Popup

Popup 让用户在当前页面快速查看和控制脚本：

- 查看当前页面正在运行的脚本数量或状态；
- 启用或禁用脚本；
- 触发更新检查；
- 不离开当前页面调整脚本行为。

对于日常使用，这比进入完整 Dashboard 的操作成本更低；对于故障排查，也提供了“当前页面究竟有哪些脚本生效”的入口。

### 4.3 自动更新

官方说明将用户脚本自动更新作为核心能力之一。更新的价值包括：

- 获取脚本作者发布的修复和新功能；
- 适应目标站点 DOM 或交互变化；
- 及时获得安全补丁。

但自动更新也引入供应链风险：脚本更新可能改变权限、匹配范围、远程依赖和数据处理逻辑。因此，自动更新适合低风险个人脚本；对于企业内部脚本，应配合固定版本、变更审查、发布源控制和回滚机制。

### 4.4 多配置模式

官网列出 Novice、Beginner 和 Advanced 三种配置模式。其产品逻辑是：

- 新手看到较少的复杂选项，降低上手成本；
- 熟练用户可以进入更多细节配置；
- 高级用户能够管理权限、脚本行为和调试相关能力。

这是一个典型的“按用户能力分层暴露复杂度”设计，而不是把所有扩展选项一次性展示给所有用户。

### 4.5 跨浏览器支持

官网列出支持：

- Google Chrome；
- Microsoft Edge；
- Firefox；
- Safari；
- Opera Next。

具体可用功能、安装方式、浏览器扩展平台限制和版本兼容性会随浏览器与 Tampermonkey 版本变化，实际部署前需要按目标浏览器单独验证。

### 4.6 脚本发现与生态接入

Tampermonkey 让用户可以安装他人编写的用户脚本，产品官网也强调了发现和安装脚本的便利性。生态通常由以下角色组成：

```text
脚本作者
→ 发布脚本 / 更新元数据 / 维护主页
→ 脚本分发站点或直接 URL
→ 用户安装并授权
→ Tampermonkey 解析、匹配、运行和更新
```

因此 Tampermonkey 的网络效应主要来自用户脚本生态，而不是来自扩展本身的复杂业务模板。

## 5. 技术模型

### 5.1 用户脚本元数据块

元数据块是 Tampermonkey 识别脚本的声明式入口。常见字段包括：

| 字段 | 作用 | 治理关注点 |
|---|---|---|
| `@name` | 脚本名称 | 应清晰表明用途和作者 |
| `@namespace` | 脚本命名空间 | 防止不同脚本名称冲突 |
| `@version` | 版本号 | 支持更新和回滚判断 |
| `@description` | 脚本描述 | 不能代替代码审查 |
| `@match` | 精确声明匹配的 URL 范围 | 应尽量收窄，避免误注入 |
| `@include` | 更宽松的 URL 匹配规则 | 过宽会扩大数据和操作暴露面 |
| `@exclude` | 排除特定页面 | 应检查是否覆盖敏感页面 |
| `@require` | 加载外部 JavaScript 依赖 | 是重要的供应链入口 |
| `@resource` | 声明外部资源 | 要检查来源、完整性和用途 |
| `@grant` | 声明需要的 GM_* API 权限 | 应遵循最小权限原则 |
| `@run-at` | 指定脚本运行时机 | 越早运行越可能影响页面初始化 |
| `@connect` | 声明跨域请求的允许域名 | 应严格限制并审计数据流 |
| `@noframes` | 控制是否在 iframe 中运行 | 防止意外扩散到嵌套页面 |

字段支持和具体语义需以目标版本的官方 Metadata 文档为准；不同 Userscript Manager 之间也可能存在兼容差异。

### 5.2 隔离执行与页面上下文

用户脚本同时面对两种上下文：

1. **网页上下文**：页面自身的 DOM、事件和 JavaScript；
2. **扩展 / 用户脚本上下文**：Tampermonkey 提供的管理、存储、通知、菜单、跨域请求等能力。

为了让脚本访问页面，同时减少与页面自身代码的直接冲突，Userscript Manager 通常需要处理隔离世界、脚本注入时机和页面上下文通信。Tampermonkey 的具体隔离实现会随浏览器架构和版本演进，本文不把历史开源代码直接等同于当前闭源版本实现。

### 5.3 GM_* API

官方仓库 README（对应早期开源版本）列出包括以下类型的能力：

- `GM_registerMenuCommand`：注册用户脚本菜单；
- `GM_getResourceText` / `GM_getResourceURL`：读取声明的资源；
- `GM_notification`：展示通知；
- `GM_*` 存储、网络、菜单和资源 API；
- `unsafeWindow`：访问页面窗口对象的高风险能力。

不同版本可能同时支持旧式同步 API 和较新的异步 / Promise 形式，不能仅依据旧 README 判断当前完整 API。对实际项目，应锁定版本并阅读相应 API 文档、验证权限和测试行为。

### 5.4 页面操作能力

用户脚本可以根据页面授权和浏览器限制：

- 查询、修改和创建 DOM 元素；
- 监听点击、输入、路由或网络相关页面事件；
- 添加快捷按钮、菜单和提示；
- 自动填写表单、筛选内容和辅助导航；
- 调用声明的 GM API；
- 在受限条件下读取资源或发起跨域请求。

这类能力足以完成很多“浏览器内 RPA”任务，但它依赖页面结构和站点行为：页面改版、异步加载、前端框架更新、登录态变化和反自动化策略都可能使脚本失效。

## 6. 与相邻产品的边界

| 产品形态 | 主要抽象 | 优势 | 局限 / 边界 |
|---|---|---|---|
| Bookmarklet | 浏览器书签触发一段 JavaScript | 安装简单，手动触发明显 | 权限和生命周期弱，代码管理与更新能力有限 |
| Tampermonkey Userscript | 按 URL 规则自动注入的网页脚本 | 快速开发、匹配精细、生态成熟、可声明 GM 能力 | 依赖网页结构，第三方脚本风险高，企业治理弱于专门平台 |
| 浏览器扩展 | 完整扩展包、后台、内容脚本和权限 | 生命周期、权限和产品化能力更完整 | 开发、发布和维护成本更高 |
| RPA | 面向业务流程的桌面 / 浏览器操作编排 | 流程、调度、凭证和企业治理更完整 | 成本较高，开发与维护较重，灵活试验速度较慢 |
| 浏览器 Agent / MCP 工具 | 模型生成意图并调用浏览器工具 | 自然语言交互，适合探索式任务 | 模型不确定性、权限、确认、回滚和页面状态验证要求更高 |
| Agent Skill | 可复用的任务方法、规则和工具编排 | 能沉淀经验、便于跨任务复用 | 需要运行时、权限、工具和版本治理，不等同于浏览器脚本 |

### 6.1 Tampermonkey 的独特位置

Tampermonkey 处在“低成本网页改造”和“正式浏览器扩展”之间：

```text
Bookmarklet
  ← 更轻、更临时
Tampermonkey Userscript
  ← 个人 / 小团队网页自动化的高杠杆区
浏览器扩展
  ← 更完整、更可产品化
RPA / 企业自动化平台
  ← 更强治理、更重交付
```

它的关键产品判断是：**把网页当作用户可编程的执行面，而不是把所有自动化都上升为完整软件产品。**

## 8. 安全、权限与供应链风险

### 8.1 用户脚本本质上是不可信代码执行

安装第三方用户脚本通常意味着允许其在匹配页面上读取页面内容、修改页面行为，并可能调用额外的 GM API。脚本可能接触：

- 页面中的账号信息、工单、客户资料和业务数据；
- Cookie 可见信息、Token、表单输入或内部链接；
- 页面 DOM 中未显式展示但已加载的数据；
- 外部网络请求返回的数据；
- 脚本配置、同步数据和本地存储内容。

因此，Tampermonkey 的安全边界不是“是否安装了扩展”，而是“安装的每个脚本在什么页面、以什么权限、从哪些依赖和更新源执行”。

### 8.2 主要风险清单

| 风险 | 典型原因 | 控制建议 |
|---|---|---|
| 过宽匹配 | `@include` 或 `@match` 覆盖整个域名 | 使用最小 URL 范围，排除登录、支付、生产管理页面 |
| 权限过大 | 申请不必要的 `@grant`、`unsafeWindow` 或跨域访问 | 逐项解释权限，默认拒绝高风险能力 |
| 远程依赖投毒 | `@require` 指向可变 URL 或未经审查的库 | 固定版本、来源白名单、完整性校验和代码审查 |
| 自动更新引入恶意变更 | 更新源被接管或作者账号被盗 | 固定版本、变更审批、签名 / 哈希、回滚 |
| 跨域数据外传 | `@connect` 和网络 API 访问外部域名 | 域名白名单、敏感字段脱敏、请求和响应审计 |
| 页面上下文污染 | 注入页面变量或与站点脚本混用 | 尽量使用隔离 API，严格校验输入和消息来源 |
| 业务误操作 | 自动点击、提交、删除或批量更新 | 预览、幂等、二次确认、状态读回和撤销 |
| 站点改版导致误执行 | DOM 选择器仍能命中但含义已变化 | 版本探测、关键字段校验、异常即停、人工复核 |
| 凭据与个人数据暴露 | 脚本读取页面或本地存储 | 最小数据读取、脱敏、保留期限和访问日志 |
| 违反站点规则 | 脚本绕过交互限制或高频请求 | 明确授权、遵守服务条款和速率限制 |

### 8.3 企业治理基线

若在企业内部使用，建议建立脚本登记和发布流程：

```text
脚本提交
→ 记录 owner、用途、目标域名、数据范围和权限
→ 静态检查元数据与外部依赖
→ 测试环境运行
→ 关键操作预览 / 人工确认
→ 审核后发布固定版本
→ 监控错误、访问和副作用
→ 发现问题时禁用、回滚并保留审计
```

最低登记字段应包括：

- 脚本名称、owner、仓库和联系方式；
- 版本、发布日期和变更说明；
- `@match` / `@include` / `@exclude` 范围；
- 每项 `@grant`、`@connect`、`@require` 和 `@resource`；
- 可访问的数据类型；
- 是否会点击提交、删除、审批、发消息或修改业务字段；
- 测试环境、回滚方式和失效条件；
- 最后审查人和下一次复核日期。

## 9. 产品优点

1. **开发门槛低**：熟悉 JavaScript 的用户可以绕过完整扩展工程，快速改造网页。
2. **反馈周期短**：保存脚本、刷新页面即可看到结果，适合小步试验。
3. **匹配机制直接**：通过元数据声明脚本在哪些页面运行，便于形成场景边界。
4. **生态复用强**：脚本作者可以将网页增强能力分享给大量用户。
5. **渐进式复杂度**：Popup、Dashboard 和多配置模式覆盖从普通用户到高级用户的不同需求。
6. **能力组合灵活**：DOM 操作、菜单、通知、资源、存储和跨域能力可以组合成轻量工作流。
7. **接近用户工作面**：不必新建系统，直接在用户已有的网页界面上增加能力。

## 10. 产品局限

1. **依赖页面实现细节**：DOM、路由、组件和接口变化都会破坏脚本。
2. **权限和供应链风险集中**：第三方脚本、外部依赖和自动更新可能带来隐蔽变化。
3. **企业治理能力有限**：个人脚本的灵活性很强，但默认并不等于团队级审核、审计和回滚系统。
4. **可靠性不适合关键流程默认自动化**：网络延迟、登录态、异步渲染和页面弹窗都会导致操作不确定。
5. **跨浏览器行为不完全一致**：浏览器扩展 API、Manifest 版本和安全策略会影响功能。
6. **用户数据边界容易被忽略**：脚本往往运行在业务页面上，用户可能低估其可见数据范围。
7. **当前版本开源边界不清晰**：历史开源仓库很有研究价值，但不能代表当前官方版本全部实现。

## 11. 对 Agent、RPA 和本项目的启发

### 11.1 网页自动化的四层分工

Tampermonkey 说明网页自动化可以拆成四层：

```text
意图层：用户想完成什么
→ 规划层：选择页面、字段和动作
→ 脚本层：确定性 DOM / API / 事件操作
→ 治理层：权限、确认、审计、版本和回滚
```

AI Agent 适合参与意图理解和候选脚本生成，但执行关键业务动作时，应由确定性脚本和治理层负责，而不能让模型直接自由点击。

### 11.2 “脚本就是 Skill 的一部分，但不是完整 Skill”

Userscript 可以看作一种很薄的执行资产：

- 元数据块类似输入范围和权限声明；
- JavaScript 主体类似确定性执行步骤；
- `@match` 类似触发条件；
- `@grant` 类似工具权限；
- Dashboard 类似个人级资产控制面。

但一个可治理的 Agent Skill 还需要 owner、输入输出契约、前置条件、失败处理、人工门槛、审计、版本和回滚。不能因为脚本能自动操作网页，就把它直接当作经过治理的 Skill。

### 11.3 从 Tampermonkey 借鉴什么

- 用声明式元数据明确脚本的页面范围、版本和权限；
- 让脚本有独立的启停、更新、禁用和回滚入口；
- 用 Popup 提供当前页面生效能力的即时可见性；
- 用 Dashboard 管理脚本资产，而不是让脚本散落在个人电脑中；
- 把第三方依赖、更新源和脚本主页作为一等信息展示；
- 将“只读增强”和“会提交 / 写入 / 删除”的动作分级。

### 11.4 不应直接照搬什么

- 不应把自动更新直接用于高影响内部业务脚本；
- 不应让自然语言生成的脚本直接进入生产页面；
- 不应允许脚本默认覆盖整个企业域名；
- 不应以“用户自己安装”替代权限审批、数据保护和审计；
- 不应把页面操作成功当作业务状态变更成功，必须读取后端或页面状态确认。

## 12. 可信度与验证边界

### 已核验或有明确来源支持

- Tampermonkey 官方站点将其定位为跨主流浏览器的 Userscript Manager；
- 官方站点说明了用户脚本可用于增加或修改网页功能；
- 官方页面展示了 Popup、Dashboard、配置模式和自动更新等产品能力；
- 官方 GitHub 仓库公开了历史版本说明、早期功能、README 和 GPLv3 元数据；
- 官方仓库 README 明确说明 2.9 以前源码与更高版本许可证边界不同。

### 待验证

- 当前稳定版具体版本号、各浏览器商店版本差异和完整 API 支持矩阵；
- 当前闭源版本的隔离世界实现、同步服务、数据处理和遥测细节；
- 企业策略、集中部署、管理员控制和浏览器管理模板支持情况；
- 当前自动更新协议、脚本来源验证、签名或完整性保护细节；
- Safari、Firefox 与 Chromium 系列之间的 GM API 和安全策略差异；
- 具体脚本生态站点的审核、举报和下架机制。

**总体判断**：Tampermonkey 的“网页层可编程运行时”定位和产品工作流可信；其当前内部实现、企业治理能力和闭源版本细节不应从历史开源仓库直接推断。对于个人网页增强，它是高杠杆工具；对于企业流程和 AI Agent 接入，真正需要补齐的是脚本资产治理和高影响动作安全边界。

## 14. 后续实测问题

- 在 Chrome、Edge、Firefox、Safari 上分别安装当前版本，比较安装、更新和权限提示；
- 用隔离测试域名验证 `@match`、`@include`、`@exclude` 和 `@run-at` 的实际行为；
- 对 `@grant`、`@connect`、`@require`、`@resource` 和 `unsafeWindow` 做权限矩阵测试；
- 测试页面改版、SPA 路由切换、iframe 和登录态变化时脚本是否误运行；
- 验证脚本更新、固定版本、禁用、回滚和多设备同步能力；
- 调查浏览器企业策略是否可以禁止第三方脚本安装、限制目标域名或统一分发脚本；
- 对内部业务场景仅使用合成数据，验证“生成候选 → 人工确认 → 确定性执行 → 读回审计”的 Agent + Userscript 组合架构。
