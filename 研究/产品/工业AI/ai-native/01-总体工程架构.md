# 01. AI Native 任务闭环平台总体工程架构

## 1. 一句话定位

AI Native 任务闭环平台不是替代 ERP、MES、EAM、PLM、CRM、OA、飞书、BI、数仓和知识库的新业务系统，而是在这些权威系统之上增加一层可复用的任务控制面：统一业务对象、任务状态、AI Skill、知识调用、工具权限、反馈学习和经营归因，让高价值业务流从“人找系统、AI 写建议”升级为“任务驱动、人机协同、过程留痕、结果回写、价值可算”。

## 2. 平台边界

### 2.1 平台负责什么

平台负责跨系统任务闭环，不负责吞掉所有原系统能力。

核心职责：

1. 把业务事件转成结构化任务。
2. 为任务绑定业务对象、责任人、SLA、权限、AI Skill 和知识资产。
3. 在任务过程中组织人机协同、AI 建议、人工采纳 / 驳回 / 修改。
4. 通过受控工具读取上下文、写入平台状态、必要时写回业务系统。
5. 记录工具调用、数据来源、知识引用、AI 输出、人审动作和最终结果。
6. 把任务执行反馈转化为知识资产、Skill 评测样本和经营归因数据。

### 2.2 平台不负责什么

平台第一版不应承担以下职责：

1. 不替代 ERP / MES / EAM / PLM / CRM 等系统的主流程页面。
2. 不把业务系统数据库整库搬进平台。
3. 不让 Agent 直接写业务系统数据库。
4. 不把动态状态只维护在 Markdown 或 Wiki 里。
5. 不让 AI 自动发布正式 SOP、关闭重大工单、确认质量结论或触发财务归因。
6. 不在第一阶段建设全企业本体、全量知识图谱和全场景平台。

## 3. 总体分层

```text
使用入口层
├── 任务工作台
├── AI Copilot / Agent 面板
├── 治理运营台
└── 价值归因看板

平台控制面
├── 场景模板中心
├── 任务流引擎
├── 业务对象与本体中心
├── AI Skill / Agent 注册中心
├── 知识资产与 GraphRAG 层
├── 反馈学习层
└── 经营归因层

受控执行层
├── MCP 工具网关
├── Connector / Adapter Runtime
├── 权限策略与风险分级
├── 幂等、审计与失败补偿
└── 写回审批与人工确认

权威系统层
├── ERP / MES / EAM / PLM / CRM / HR / OA
├── 飞书 / 企业微信 / 邮件 / IM
├── 数仓 / BI / 指标平台
├── 文档库 / Wiki / WeKnora / 对象存储
└── 平台自身 Postgres 动态状态库
```

## 4. 核心运行链路

以设备维修任务为例，第一版应跑通下面这条链路。

```text
1. 业务事件进入
   MES 产生设备故障报警，或人工在工作台创建异常事件。

2. 连接层读取上下文
   MCP / Connector 读取设备台账、历史工单、SOP、排班、技能、备件、指标口径。

3. 语义层绑定业务对象
   把报警映射为设备、产线、工序、故障码、人员、SOP、历史案例和经营指标。

4. 任务层创建 Task
   生成维修处理任务，设置责任人、SLA、状态机、AI Skill、工具权限和复盘规则。

5. AI Skill 生成建议
   相似案例检索、诊断建议、风险提示、备件提醒、复盘草稿等 Skill 在任务上下文内执行。

6. 人类确认与执行
   维修人员采纳、修改或驳回 AI 建议；高风险动作进入主管或专家审批。

7. 受控写回
   平台先写入自身任务状态和反馈；必要时通过 MCP / Connector 写回 EAM 工单、飞书文档、知识库候选条目或数仓快照。

8. 反馈学习
   记录建议是否有效、人工改了什么、故障是否复发、哪条 SOP 被引用、是否需要更新知识或 Skill。

9. 经营归因
   计算 MTTR、停机损失、复发率、知识复用率、AI 建议采纳率等指标变化。
```

这条链路里的关键不是“Agent 聊天”，而是 Task 作为运行主轴，所有 AI 调用、工具调用、人工动作、知识引用和结果回写都挂在同一个任务上下文下。

## 5. 核心工程模块

### 5.1 场景模板中心

场景模板用于定义某类业务任务流的标准结构。

第一版字段：

| 字段 | 说明 |
|---|---|
| `template_id` | 模板唯一 ID |
| `template_key` | 例如 `equipment_repair`、`quality_8d` |
| `name` | 模板名称 |
| `business_object_types` | 任务涉及的对象类型 |
| `trigger_event_types` | 可触发该模板的事件类型 |
| `state_machine_ref` | 对应状态机版本 |
| `roles` | 责任人、协作人、审批人、观察者 |
| `required_skills` | 默认启用的 AI Skill |
| `tool_policy_ref` | 工具权限策略 |
| `knowledge_scope` | 可检索知识资产范围 |
| `sla_policy` | SLA 规则 |
| `review_policy` | 人审与审批规则 |
| `value_model_ref` | 经营归因模型 |

第一阶段只需要实现 1 个模板，例如设备维修或质量异常；第二阶段再迁移到相邻场景。

### 5.2 业务对象与本体中心

业务对象中心把企业里的实体变成平台和 Agent 都能理解的对象。

最小对象模型：

```text
BusinessObject
├── object_id
├── object_type
├── display_name
├── source_system
├── source_ref
├── owner_team
├── permission_level
├── attributes
├── relation_refs
├── document_refs
├── metric_refs
└── updated_at
```

第一版不需要复杂本体编辑器，可以先维护：

1. 对象类型字典，例如设备、产线、工序、产品、缺陷、故障、工单、人员、技能、SOP、指标。
2. 来源系统映射，例如 MES 设备 ID、EAM 工单 ID、HR 人员 ID、知识库文档 ID。
3. 关系类型字典，例如设备属于产线、工序影响质量、人员具备技能、SOP 适用于设备型号。
4. 字段口径说明，例如停机时长、MTTR、复发率、质量损失金额。

### 5.3 任务流引擎

任务流引擎是平台控制面的核心。

最小任务对象：

```text
Task
├── task_id
├── task_type
├── template_id
├── title
├── status
├── priority
├── trigger_event_ref
├── business_object_refs
├── expected_outcome
├── human_owner
├── participant_refs
├── ai_skill_refs
├── tool_policy_ref
├── input_context_refs
├── evidence_refs
├── output_artifact_refs
├── feedback_summary_ref
├── value_impact_refs
├── created_at
└── updated_at
```

任务流引擎不需要第一版就支持任意 BPMN。更稳妥的做法是：

1. 先为每个高价值场景定义显式状态机。
2. 每个状态只允许有限动作。
3. 每个动作都通过命令接口执行。
4. 每次状态变化写入事件日志。
5. AI 只能生成建议或草稿，不直接越权改状态。

### 5.4 AI Skill / Agent 注册中心

Skill 注册中心管理可复用 AI 能力，不是简单 Prompt 列表。

最小注册信息：

| 字段 | 说明 |
|---|---|
| `skill_id` | Skill 唯一 ID |
| `skill_key` | 稳定技术名 |
| `version` | 版本 |
| `owner` | 业务或技术负责人 |
| `supported_task_types` | 适用任务类型 |
| `input_schema` | 输入结构 |
| `output_schema` | 输出结构 |
| `tool_allowlist` | 可调用工具 |
| `knowledge_scope` | 可检索知识范围 |
| `risk_level` | 输出风险等级 |
| `review_required` | 是否必须人工确认 |
| `eval_dataset_ref` | 评测集 |
| `status` | draft / approved / deprecated |

第一版可以只支持 2-3 个 Skill：相似案例检索、诊断建议、复盘草稿生成。每个 Skill 必须纳入评测和采纳率统计。

### 5.5 知识资产与 GraphRAG 层

知识层负责稳定知识，不负责动态状态 source of truth。

资产类型：

1. SOP。
2. 历史案例。
3. 复盘报告。
4. 故障模式。
5. 质量标准。
6. 检查清单。
7. Prompt / Skill 说明。
8. 评测集。

每个知识资产至少要有：

```text
KnowledgeAsset
├── asset_id
├── asset_type
├── title
├── source_uri
├── version
├── owner
├── status
├── applicable_object_refs
├── applicable_task_types
├── sensitivity_level
├── quality_level
├── effective_from
├── expires_at
└── usage_stats
```

GraphRAG 的第一版可以不追求完整知识图谱，而是先做三类关系：

1. 文档片段 ↔ 业务对象。
2. 案例 ↔ 任务类型 / 故障 / 缺陷 / 设备。
3. SOP ↔ 适用对象 / 风险点 / 检查步骤。

### 5.6 连接层与 MCP 工具网关

连接层负责所有外部系统访问。详细设计见 `02-连接层与MCP工具网关.md`。

总体原则：

1. Agent 不直接连接业务数据库。
2. Agent 不直接持有业务系统密钥。
3. 所有工具有输入 schema、输出 schema、权限策略、风险等级和审计日志。
4. 写动作必须具备幂等键、人工确认策略和失败补偿机制。
5. 高风险动作必须走人审或审批。

### 5.7 反馈学习层

反馈层记录 AI 是否真的改善任务结果。

最小反馈对象：

```text
FeedbackRecord
├── feedback_id
├── task_id
├── skill_run_id
├── actor_id
├── feedback_type
├── original_output_ref
├── human_revision_ref
├── accepted
├── rejection_reason
├── result_after_action
├── knowledge_update_candidate_ref
├── eval_sample_candidate
└── created_at
```

第一阶段只要求记录采纳 / 驳回 / 修改；第二阶段把高价值修改进入评测集；第三阶段再做经验蒸馏和知识发布。

### 5.8 经营归因层

经营归因层从第一天就要留字段，但第一天不追求财务审计级精度。

最小归因对象：

```text
ValueImpact
├── value_impact_id
├── task_id
├── business_object_refs
├── metric_key
├── baseline_value
├── actual_value
├── delta_value
├── attribution_level
├── contributor_refs
├── confidence_level
├── confirmation_status
└── created_at
```

设备维修可先从 MTTR、停机时长、复发率、AI 建议采纳率、知识复用率开始。质量异常可先从缺陷复发率、8D 关闭周期、质量损失金额、整改按期完成率开始。

## 6. 最小可运行架构

第一版不需要大平台，只需要把一条任务流端到端跑通。

```text
Web 工作台
  ↓
Task API
  ↓
Postgres 动态状态库
  ↓
MCP 工具网关
  ↓
Connector / Adapter
  ↓
外部系统 API / 知识库 / 数仓 / 协同工具

AI Runtime / Agent
  ↕
Task Context Builder
  ↕
Skill Registry + Tool Registry + Knowledge Retrieval
```

第一版服务拆分建议：

| 服务 | 职责 | 可先合并吗 |
|---|---|---|
| `task-service` | 任务、状态机、事件日志、反馈 | 可以 |
| `mcp-gateway` | MCP tool 暴露、鉴权、schema、审计 | 建议独立 |
| `connector-runtime` | 外部系统 adapter、重试、失败补偿 | 可以先合并到 gateway |
| `ai-runtime` | Skill 编排、上下文构建、模型调用 | 可以先轻量实现 |
| `knowledge-service` | 检索、知识元数据、引用 | 可先接现有知识库 |
| `governance-service` | 权限、策略、审计、敏感字段 | 第一版可内嵌策略表 |
| `value-service` | 价值归因、指标快照 | 第一版可只写归因表 |

## 7. 第一版技术栈建议

| 层 | 建议 |
|---|---|
| 动态状态 | Postgres |
| 服务框架 | TypeScript / Node.js 或团队现有后端栈 |
| 工具协议 | MCP over HTTP / SSE，内部也可保留 REST command API |
| Schema | Zod / JSON Schema / OpenAPI |
| 权限 | 用户身份 + 角色 + 任务上下文 + 工具策略 |
| 审计 | Postgres append-only event / audit log |
| 幂等 | `idempotency_key` + request hash + result cache |
| 知识检索 | 现有知识库 / WeKnora / 向量库 / GraphRAG 逐步接入 |
| 观测 | trace_id / task_id / tool_call_id 全链路透传 |

## 8. 分阶段交付

### Phase 0：场景和对象定版

输出物：

1. 选择一个任务流，例如设备维修或质量异常。
2. 定义业务对象字典。
3. 定义任务状态机。
4. 定义 2-3 个 AI Skill。
5. 定义只读工具和平台内部写入工具。

验收标准：

- 业务 owner 能确认任务流是真实高价值任务。
- 工程团队能基于对象和状态机建表。
- 每个工具都有清晰输入、输出、权限和风险等级。

### Phase 1：平台内部闭环

输出物：

1. Postgres 任务表、事件表、工具调用表、反馈表。
2. Task API。
3. MCP 网关最小工具。
4. 工作台最小页面。
5. AI Skill 输出写入任务上下文。

验收标准：

- 能创建任务。
- 能读取上下文。
- 能生成 AI 建议。
- 能人工采纳 / 驳回 / 修改。
- 能记录工具调用和状态流转。

### Phase 2：受控写回业务系统

输出物：

1. 至少一个业务系统 Connector。
2. 写回命令 API。
3. 幂等、重试、失败补偿。
4. 人工确认和审批策略。
5. 审计日志查询页面。

验收标准：

- 能在人工确认后写回工单状态、复盘文档或候选知识。
- 重复请求不会产生重复写入。
- 写回失败能进入补偿队列。
- 审计记录可追溯到任务、用户、工具和外部系统响应。

### Phase 3：反馈学习与归因

输出物：

1. 采纳率、修改率、失败案例池。
2. 复盘候选知识审核流。
3. Skill 评测样本沉淀。
4. 基础经营归因看板。

验收标准：

- 能看到 AI 建议是否被采纳。
- 能看到哪些知识资产被引用并产生结果。
- 能形成下一版 Skill / SOP / 任务模板改进清单。

## 9. 关键工程风险

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 平台先行过重 | 做了很多抽象模块但没有真实任务流 | 先选择一个高价值场景，所有抽象来自真实闭环 |
| 连接层只读 | 只能问答和分析，不能推动任务状态 | 从第一版就设计平台内部写入和后续业务系统写回 |
| AI 越权写入 | Agent 绕过人审直接改业务系统 | 工具风险分级、人工确认、审批、策略引擎 |
| 知识和状态混淆 | 用文档维护库存、工单、反馈等动态事实 | 动态状态进 Postgres，知识资产进知识库 |
| 无法追溯 | AI 输出、工具调用、数据来源无法复盘 | task_id / trace_id / tool_call_id 全链路日志 |
| 反馈不可用 | 只有点赞，没有业务结果 | 反馈绑定任务结果、知识引用和指标变化 |
| 归因过早复杂化 | 第一版想做财务级 ROI | 先留字段和简单指标，再逐步提高可信等级 |
