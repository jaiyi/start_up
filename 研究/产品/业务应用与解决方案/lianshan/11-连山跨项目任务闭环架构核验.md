# 11 · 连山跨项目任务闭环架构核验

> 分析日期：2026-11-16
> 输入：用户提出的 `dsproject / dsruntime / dsclaw / dsbase` 分工、两级 BPMN 与锡焊异常协作设想。
> 口径：下文分别标记**目标设计**、**源码／契约可见**、**待联调／生产验收**。产品名、部署单元与代码仓名未必一一对应；查到实现入口不等于该业务链已运行，更不等于客户现场已验收。本文只读核对同级研究文档和本地相邻实现仓，未运行测试或部署。

## 1. 想解决的不是“再造一个 Agent”，而是跨项目任务如何闭环

用户提出：`dsproject` 内完成所属业务领域的取数、计算和内部流程；`dsruntime` 统一组织多个项目的上下文、能力与跨项目状态；`dsclaw` 运行连小山 Agent 的“左右脑”；`dsbase` 是面向人的控制面。项目自己的确定性能力优先解决确定的问题，开放式 Agent 在能力边界之外分析、补全参数、请求人工协助，而不是替代领域算法或未经授权操控现场。

这是一套**目标产品分工**，不是声称已有四个完全按此切好的进程。它延续了 [02 · lads](./02-lads.md) 所述 `dsproject → lads 编译 → Bundle → runtime 消费` 和 [10 · AI Native 任务闭环诊断](./10-AI-Native任务闭环平台视角下的连山产品诊断.md) 的“任务／能力／证据”思路，但把跨项目能力发现、编排权属和失败时的部分闭环进一步说清楚。

| 位置 | 目标职责 | 边界与当前证据 |
|---|---|---|
| `dsproject` | 领域数据处理与内部工作流的交付单元；纯 PPL 流程可在项目内闭环；需要跨项目使用的 workflow，经版本化能力契约**选择性**对外提供。项目内 BPMN 定义和本地执行由该领域负责。 | 项目是否需要暴露取决于业务契约，不是“有 BPMN 就自动暴露 MCP”。`lads` 有本地 Spiff BPMN runner，项目工作流有版本化声明；具体 PPL 是否能独立完成某场景需按项目核验。[02 · lads](./02-lads.md)、`lads/lads/framework/workflow/_application/runner.py:24-110`、`lads/lads/framework/contracts/_contracts/coldpath/workflow_definitions.py:337-439`。 |
| `lads` | 冷路径验证、编译和交付 Bundle／声明，连接 dsproject 和 runtime。 | `lads run` 默认交付已构建 App＋Bundle，首次或结构变化需先 `lads bundle build`；它不是收到异常就调用任意业务 workflow、也不是自动生成跨项目 BPMN 的命令。`lads/lads/cli/_commands/run.py:141-215`、`lads/lads/cli/_composition/_workflow_release.py:80-185`。 |
| `dsruntime` | 以统一业务对象和关联 ID 组织结构化数据、非结构化文件／证据及各阶段状态的**授权视图**；管理已发布能力目录、事件匹配、跨项目编排实例、审计和 HITL 交接；向连小山提供受控 MCP／能力接口。 | 现有 runtime 具备热路径、工作流执行和内部 MCP discovery 基础，不等于所有项目上下文已统一建模、任意 workflow 都可直接对外发布。原始数据与领域事实仍由各自系统／dsproject 负责，runtime 负责索引、关联、授权投影和跨项目任务真相。[03 · dsruntime](./03-dsruntime.md)、`dsruntime/lisen_runtime_core/control_plane/api/routes/discovery_mcp.py:163-224`。 |
| `dsclaw`／连小山 | Agent 工作站、人机协同入口及 LLM 工具循环。“左脑”优先发现／调用已声明的确定性 workflow，必要时对话补齐参数；“右脑”处理流程外开放问题，结合已授权的 Skill／工具提出候选分析和下一步。 | 左右脑是**产品决策路径**，不是核实过的两个物理模块。已有发现客户端、工单桥、工具循环和部分人审流程；当前 Agent 关系检查还会拒绝跨 dsproject 的直接关系，不能把“Agent 自由互调”当作既有能力。[04 · workstation-iclaw](./04-workstation-iclaw.md)、`workstation-iclaw/backend/app/core/permissions.py:161-204`。 |
| `dsbase` | 按用户新定义的面向人控制面：授权范围内查询 PG 中的业务投影、展示证据／工作流状态、操作内置应用，并承载待办与审核入口。 | 当前 runtime 已有 Workbench、RAG、MinerU 等人用页面，dsclaw 也有人工评审入口；尚不能据此证明 `dsbase` 已是唯一人审、身份与授权归属。需明确 UI 名称、服务归属和责任人；“代理 PG”须按身份、租户、业务对象、字段及审计进行授权查询，**绝不是任意 SQL／裸库透传**。 |

```text
项目 A：视觉事件／证据 ─┐
项目 B：SPC 归因能力 ──┼─ 已发布契约／受控事件 → dsruntime（跨项目任务与能力目录）
项目 C：参数推荐能力 ─┘                                  │
                           ┌─────────────────────────────┴────────────────────────┐
                           ↓                                                      ↓
                    连小山 / dsclaw：发现、补参、分析、协同              dsbase：人审、查询、运营
                           └────────── 经审核的动作、回执与复验回写 ───────────────┘
```

**接口不是消息总线**：MCP 适合发现能力、查询带权限的上下文、调用已授权 query／command；异常事件仍应走可恢复的事件／队列和精确订阅，BPMN／任务实例负责可追溯状态，不能仅靠一轮 Agent 对话或一次 MCP 请求保证长事务完成。`dsruntime` 现有 `POST /api/v1/mcp/discovery` 及固定工具目录，包括 `capability.list/get/query/command`、语义查询和相似经验检索；调用需契约摘要、release、主体权限和能力可用性等条件，不能从这个入口推断已有通用任意工具网关。参见 `dsruntime/lisen_runtime_core/control_plane/discovery/mcp.py:240-320`、`dsruntime/lisen_runtime_core/control_plane/api/routes/discovery_mcp.py:105-142,218-224`。

## 2. 两级 BPMN：按业务所有权分，不按代码库里是否有引擎分

| 层次 | 定义／版本归属 | 执行与状态真相源（目标） | 不应做的事 |
|---|---|---|---|
| 项目内流程 | 由领域 dsproject 定义、测试并随 Bundle 或项目契约发布；如需外用，声明输入输出、失败和权限语义。 | 项目内部执行所属计算和局部状态，对外返回带关联 ID 的结果／事件；跨项目端不直接篡改局部流程。 | 把内部 BPMN 文件当 MCP 工具原样裸露，或由另一个项目绕过发布版本直接调用。 |
| 跨项目人机协同 | 由平台以稳定业务对象、能力契约、补偿策略和人工关口定义、审查并发布编排版本。 | `dsruntime` 管跨项目实例的任务状态、因果链、超时／重试／补偿、HITL 和最终审计；`dsclaw` 承担授权的 Agent 推理／协作和人机交接，不另记一份冲突的任务终态。 | 让两个引擎同时拥有同一实例的状态，或每次异常都让 LLM 在线改写生产 BPMN。 |

**源码现状与目标权属并不相同**：`lads/lads/framework/workflow/_application/runner.py:24-110` 能在本地跑 BPMN；runtime 的 `lisen_runtime_core/hot_path/runtime/executors/bpmn_executor.py:27-45,75-139` 又能从 PG 取 BPMN XML 调 `lads` runner（缺连接或依赖时会 `skipped`）；runtime 的 `lisen_runtime_core/control_plane/orchestration_runtime/service.py:194-303` 还有依 release 启动实例的编排服务。故“BPMN 只存在或只运行在 dsproject”与现有源码**实质不符**；目标应明确**谁拥有哪类流程定义和实例**，而非强行删除一端执行器。也不能仅因两端有引擎，就宣称现已跑通任意跨项目 BPMN。

项目 A、B 的 `config/workflow_definitions.yaml` 可以作为各自声明来源，经过 Bundle digest 校验、release 和受管事件源接入 runtime；但 `lads run` 后“runtime 自动读取两份声明、依据异常结果动态规划／刷新多 Agent BPMN 并立即执行”**不是目前已证明的调用链**。现有 `lads/lads/cli/_composition/_workflow_release.py:80-185` 处理预检与发布身份；`dsruntime/lisen_runtime_core/hot_path/handlers/workflow_event_selection.py:52-109` 按项目、workflow、事件源、Agent 实例、事件类型和声明 digest 严格匹配，并非异常广播给所有 Agent。声明需要补充可组合性：能力输入／输出 schema、业务对象与异常语义、适用设备和工艺、版本、可用性、租户授权、幂等及失败语义；跨项目关联须有产线／设备／批次／工单等可验证 join key，不能凭同一“锡焊”标签猜出来。建议先由人审核候选编排并版本化发布，再让运行时在已批准路径中按事件动态选择、补参和暂停／恢复；若要在线重规划，须单独设计审批、回滚和安全边界。

## 3. 锡焊问题：用于验收设计的场景，不是已上线声明

以“视觉发现锡焊异常 → SPC 从人机料法环分析 → 参数推荐 → 人审后设备下发 → 视觉复验”为**拟验证流程**。视觉项目、SPC 项目和参数推荐项目只提供各自声明并经过发布，不假设三者现在已经打通。视觉边缘推理节点可处理推理请求并回传结果，但不单独拥有任务闭环；已有 [07 · SPC](./07-demos-spc.md) 的“采判报诊值”及 [08 · 参数推荐](./08-demos-param-opt.md) 的推荐／人审框架，也不能证明这条特定锡焊链路和真实设备下发已完成。参见 [05 · edge-inference](./05-edge-inference.md)、[07 · SPC](./07-demos-spc.md)、[08 · 参数推荐](./08-demos-param-opt.md)。

1. **发现**：视觉项目产生告警、置信度、图像／检测结果引用与时间，附产线、设备、产品／批次、工单／异常 ID；runtime 建立唯一跨项目任务实例，保留原始证据和算法／Bundle 版本。
2. **发现并调用 SPC**：按租户／项目权限及发布契约筛选可处理该场景的 SPC 能力；连小山先取必要上下文、对话补齐缺失字段，再请求人机料法环候选归因。记录 SPC 所需数据是否充分、证据出处和不确定性；候选根因不得冒充已确认结论。
3. **推荐与复核**：符合能力和参数边界时请求参数建议，保存输入、约束、模型版本、建议值、拒绝原因；危险操作设人工审批，审批人、时间与结果入账。缺少数据、权限或超范围时保持待处理／升级人工。
4. **下发与复验**：仅由授权的设备／MES 命令通道执行，回执含目标设备、参数版本、幂等键、执行状态与失败原因；不能把“已建议”当“已下发”。再次视觉检测并由责任人确认异常是否消除；失败则转人工处置或重试，成功才按业务口径关闭。所有步骤共享关联 ID、因果关系和审计，尤其要区分视觉误报、SPC 无结论、未获审批、执行失败、复验仍异常与真正解决。

**缺少 SPC 的分支——部分结果也应可见**：视觉告警仍生成卡片，但不能显示“已找到根因／已解决”。建议卡片示意：

> 锡焊异常：视觉检测已告警（附证据与定位）。当前未发现**在本产线／权限范围内可调用的 SPC 人机料法环分析能力**，因此无法继续自动归因与处理；状态：**待人工处理／仅视觉告警**。建议核对 SPC 是否未接入、未发布、不可用、无权限或不适用于该工艺；确认接入条件后再启用后续分析。

实际产品应呈现查到的**精确原因**：能力不存在、版本未发布、不可用、无权限、工艺不适用、数据不充分、调用报错彼此不同。若是无权限，不应泄露不可见能力的敏感元信息；对用户可以只说明“当前不可用”，把细因留给有权限的运营者。卡片由 runtime 提供**可核验的能力判定／任务状态**，连小山以人能理解的话表达，不以 LLM 自行猜测“找不到 SPC”。“建议启用 SPC”只是产品建议，是否形成销售机会须另经客户需求与价值验证；无 SPC 时也允许人工处置视觉告警，不凭空声称整个生产处理已经停止。现有 dsclaw 对目标 Agent 缺失／停止等有拒绝逻辑，但**未核实**此跨项目缺 SPC 推卡与部分闭环的端到端实现。

## 4. 关键设计逻辑及与现有实现的冲突

| 设计逻辑／主张 | 核验结论 | 影响与建议 |
|---|---|---|
| 领域内确定性计算自治，平台只消费已发布能力 | **有基础，但目标须限定**：Bundle 和工作流声明／release 已存在；项目内闭环与对外接口应分别验收。 | 保留领域主权，外用只暴露受控能力契约，而非项目数据库和所有私有流程。 |
| `dsproject` 有内部 BPMN，`dsruntime` 另有跨项目 BPMN | **所有权设计合理；“BPMN 仅在项目内执行”有源码冲突**：runtime 同时已有热路径执行器和 release／instance 服务。 | 清楚划分定义、执行、实例台账和版本来源，逐步收敛重复执行路径。 |
| `lads run` 后自动生成／刷新跨项目 Agent 流程 | **与现有命令语义冲突，动态规划未核实**：`run` 是 Bundle 交付，事件精确绑定；没有本次可证的 A/B 声明自动合成流程证据。 | 区分冷路径声明发布与热路径编排；先做经审核的可组合流程与动态路由，另立自动生成能力的测试与审批门槛。 |
| 项目 workflow 需要外用就通过 MCP 暴露 | **方向可行，通用自动暴露未核实**：已有固定 discovery MCP 和受控 query／command，不等于任意项目 workflow 自动注册成 MCP。 | 明确 workflow 封装、契约版本／授权／可用性；事件触发和长事务状态依然独立于 MCP。 |
| runtime 统一建模结构化／非结构化／阶段状态 | **方向相容，完整统一模型未核实**：runtime 有 PG、语义、经验和任务状态能力，但跨项目业务主键和证据权限需落地。 | 先定义统一异常／任务／证据 ID、来源 ACL、可见范围与事实归属，不复制第二份领域事实。 |
| `dsbase` 是人的统一控制面，`dsclaw` 只跑左右脑 | **命名和职责存在需要裁定的冲突**：当前 dsclaw 也承载人机入口与人审，runtime 自身亦有人用面板。 | 约定审核入口、权限判断、实例状态真相源及写回责任；UI 可以多处出现，但不能两个系统各自批准同一动作。 |
| 自动串起视觉／SPC／推荐／设备／复验；缺 SPC 时透明告知 | **拟验证目标**：现有场景组件和部分缺能力判定不足以证明特定锡焊全链或卡片已上线。 | 逐跳拿到事件、权限决策、诊断证据、审批、真实下发回执、复验和终态，演练无能力／无权限／调用失败分支。 |

**另一条产品路线的区别**：[SPC × DeepSeek Harness 设计稿](../../../../项目/SPC-DeepSeek-Harness/设计/00-总体概览.md) 明写“讨论稿，未实施”，并提出替代现有 runtime／dsClaw 工单链。它和本文件的“在现有 runtime／dsClaw 分工上扩展”是不同方案，不能把该设计稿当成已部署的兼容实现。若决定切换路线，须重新裁定编排、人审和任务台账归属。

## 5. 下一步最小验证

- 选一条真实授权产线，定义视觉异常、SPC 归因、参数建议的同一业务键和跨项目 ACL；先做**只读／人审不下发**的正向链路，留存每跳原始事件、能力契约与版本、调用／审批回执。
- 分别演练无 SPC 能力、未发布、无权、数据不足和服务故障，确认卡片不误报解决、任务不丢失、支持人工接管；对无权能力不泄露敏感信息。
- 单独验收设备写入的授权、回滚、幂等、物理边界及真实下发和复验；未通过前停留在建议与模拟／人工操作，不发布“自动调整参数”的成果口径。
- 由产品和工程共同敲定 `dsbase` 与 `dsclaw` 的审核和身份职责，以及两类 BPMN 各自的实例真相源；以一条经审核、可回滚的跨项目编排版本证明运行路径，而不是把“动态规划”先写成实现事实。
