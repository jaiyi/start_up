# 视源制造专业日主题分享大纲｜讨论稿 V1

> **仅供内部与分享嘉宾讨论，不是对外发布稿。**拟用于 2026 年 11 月 20 日视源股份制造专业日的 30–40 分钟主题分享。依据活动背景及现有连山产品研究整理；客户项目状态、可公开名称、实际效果和展示素材须由项目负责人及客户确认后，才能进入正式 PPT。本文不包含客户业务原文、生产数据或未核实的收益数字。

## 一、分享定位

- **活动主题：**AI+自动化，加速制造竞争力
- **建议演讲题目：**《从发现异常到持续改善：企业 AgentOS 如何推动制造竞争力》
- **主要听众：**制造一线员工，兼顾质量、工艺、售后、管理及相关团队。
- **建议时长：**约 38 分钟，预留主办方安排的问答时间。

**这场分享希望让听众记住的一句话：**

> AI 的价值不止是让某个人更快完成一项工作，而是让制造现场的问题被发现后，有依据地诊断、有人负责地处理，并把经验证的经验带进下一次改善。

**叙事顺序：**工具断层与组织提效困惑 → 连山 AgentOS 如何接住任务 → 连山在制造场景的重点应用 → 视源已有试点及已核实效果 → 下一步合作与 AI-Native 里程碑。

**篇幅取舍：**四阶段框架只是引入，控制在前 6 分钟内；五个诊断维度不单独展开成一堂方法论课。制造应用是主体，视源案例承担落地证明，合作里程碑承担收束。

## 二、逐页大纲（约 12 页／38 分钟）

| 页 | 时间 | 页面主张 | 推荐画面与讲述方式 |
|---|---:|---|---|
| 1. 共鸣：两种 AI 感受 | 2 分钟 | 管理者担心跟不上变化，一线却可能还在不同工具之间搬运信息；两者都指向“任务没有连起来”。 | 对照两种日常感受，避免说教，也不要把它写成对视源现状的判断。 |
| 2. 一张图看四阶段 | 2 分钟 | 人是中台 → Agent 是中台 → Agent 靠人的经验进步 → 走向能受控持续优化的企业 AgentOS。 | 同一件制造质量任务，展示每一步是谁在衔接工作；第四阶段是演进方向，不能讲成已经实现自主进化。 |
| 3. 为什么光换工具不够 | 2 分钟 | 任务能走多远，取决于人、协作、数据、基建、语义层中最薄弱的环节。 | 一张“五块短板”示意图，迅速转场到“连山如何补齐任务链”。不按 L0/L1/L2 给现场员工贴标签。 |
| 4. 连山 AgentOS：接住一项任务 | 3 分钟 | 连山要连接的是“发现 → 判断 → 人工确认 → 处理 → 反馈”，不只是提供一个问答窗口。 | 用**示意性质量异常**做任务流图；标注哪些环节由人作出最终决定。不要把示意图称为客户现网流程。 |
| 5. 背后需要什么能力 | 3 分钟 | 数字基底提供数据、模型与工具；业务知识中枢组织产品、工艺、故障知识；任务协同让 Agent 与岗位共同推进处理。 | 从上一页任务反推三层能力。AgentOS 作为支撑这些应用的能力体系介绍，不在此处堆叠技术名词或作完整上线承诺。 |
| 6. 主应用：制造质量改善 | 7 分钟 | 从“检测到异常”走向“定位、处理、验证、复盘”，把单点 AI 转成可追踪的质量任务。 | 以一件虚构但贴近现场的异常贯穿 AOI／过程质量诊断／故障树／措施建议；逐段标明已有能力、可连接环节与待共同验证环节。详见第三节。 |
| 7. 应用延伸：设备与产线效率 | 3 分钟 | 状态感知和异常提示只是起点，还需要维护判断、责任分派及效果复核。 | 设备故障预警或 OEE 瓶颈作为**合作方向示意**；无经确认项目证据时不称为视源落地成果。 |
| 8. 应用延伸：售后反馈回制造 | 3 分钟 | 售后工单不应只被“处理完”，确认后的故障原因还应帮助产品与制造团队改善。 | “现象 → 测试与证据 → 人工确认 → 质量改进建议”示意；区分已开展售后诊断与尚待验证的制造反馈贯通。 |
| 9. 为什么能复用，而非三个孤立项目 | 2 分钟 | 单个场景之外，更重要的是复用任务方式、受控工具、业务知识和经审核的经验。 | 一张“共性能力 × 场景”的简图；不声称这些场景已经在视源合为一套运行中的闭环。 |
| 10. 视源合作：试点与实际变化 | 5 分钟 | 用视源合作项目回答“哪些已经开始做、带来什么可确认的变化、下一步缺哪一段”。 | 对照 AOI 视觉检测、IPU 产品故障树、售后质量诊断 Agent。优先展示一项获得授权的完整任务故事，另外两项简述；具体效果留待项目证据填入。详见第四节。 |
| 11. 下一步合作与 AI-Native 里程碑 | 5 分钟 | 从单点可用，到任务打通、经验复用、受控持续优化，每一步都有可核验的标志。 | 四级阶梯图；与视源共同选择一个有责任人、有数据、有验收口径的高价值任务作为下一步。详见第五节。 |
| 12. 收束与邀请 | 1 分钟 | 让每次发现的问题都有下一棒，让解决方法留在组织里。 | 邀请现场提出“最值得打通的一次工作交接”，不以抽象平台愿景收尾。 |

## 三、第 6 页重点故事：一项质量问题的接力棒

用**合成／示意案例**讲解，不代入未经授权的视源订单、设备、工艺参数或图片。

1. **发现：**视觉检测或过程数据提示异常。说明 AI 与自动化怎样让线索更早出现，同时提醒“告警不等于真实缺陷”。
2. **理解：**关联产品、批次、工序及经审核的知识，给出可核查的线索，而不是直接宣布根因。
3. **诊断：**利用故障树、历史经验或领域模型提出排查步骤；缺少测试结果时要求补证据，不编造现场事实。
4. **处理：**把建议交给质量／工艺责任人确认，必要时进入工单和措施执行；高风险操作不由 Agent 绕过授权自行下发。
5. **复核：**观察后续质量表现、误报与复发情况，再决定此次措施是否有效。
6. **沉淀：**将专家确认过的经验转为下一次可引用的规则、知识或技能；自动提出新假设也须经过验证、审核和受控发布。

**这一段的核心台词方向：**“我们不是让 AI 替一线拍板，而是让每个人接到问题时，更快找到依据、更清楚地把任务交给下一棒。”

**画面边界：**已有场景能力、拟连接的流程、客户实际已运行的链路要使用三种清晰标记。产品研究中的 SPC、FTA、参数推荐与边缘推理提供不同环节的工程与场景材料，但不能据此认定它们已在视源打通完整闭环。

## 四、视源案例页：从“已开展”到“成功案例”的证据门槛

目前活动背景列出三项在视源开展／上线的合作：**AOI 视觉检测、IPU 产品故障树、售后质量诊断 Agent**。下表仅确定叙事位置；上线范围、交付主体及效果须逐项核实。

| 合作触点 | 在演讲中的角色 | 正式案例页需要补充的事实 |
|---|---|---|
| AOI 视觉检测 | 展示“异常从哪里被发现、结果怎样交给人复判”。 | 实际检测对象及工序、上线地点与使用岗位、真实取图与复判流程、获准展示的截图／图像、按确认口径计算的误漏检或处理时间。 |
| IPU 产品故障树 | 展示“专家如何把排查路径变为可使用的业务知识”。 | IPU 具体场景范围、故障树由谁维护、实际使用流程及记录、人工确认点、可核实的排查前后变化。不得挪用其他客户的故障树数字。 |
| 售后质量诊断 Agent | 展示“售后现象怎样转成有依据的分析”。 | 实际接入的信息、上线岗位和使用量、建议如何被审核、是否已有经确认的制造侧反馈、可引用的使用评价或效果。 |

建议优先选**证据最完整、获客户授权展示**的一个项目，按照“此前怎么做 → 现在怎样完成任务 → 人在哪一步判断 → 可核实变化是什么”讲透；另两个项目用简图说明。若尚无可公开的前后对比，则只说“合作试点／上线场景与流程”，不写“节省 X%”“良率提升 X%”“准确率达到 X%”或“三项目已全面贯通”。项目详情和客户素材需要单独确认披露权限。

## 五、下一步合作：走向 AI-Native 的四级里程碑

| 里程碑 | 与视源共同推进的工作 | 可观察、可验收的标志 |
|---|---|---|
| 1. 单点可用 | 核实三项现有合作各自解决的任务、使用人及人工确认点。 | 使用岗位、输入输出、运行范围和实际使用记录清楚。 |
| 2. 任务打通 | 选择一类高价值质量问题，把发现、诊断、责任分派、处理与复核连接起来。 | 一次任务可以追溯由谁处理、依据是什么、处理结果如何；稳定运行并有问题台账。 |
| 3. 经验复用 | 把一线纠错、工艺判断和售后排查经验经审核沉淀。 | 同类问题再出现时能引用到经确认的经验，并评价它是否改善了工作。 |
| 4. 受控持续优化 | 让 Agent 根据反馈提出新的模式或流程改进建议，在验证后迭代。 | 新建议经过测试、人审、灰度及效果复核，才进入正式流程；不是让 Agent 自主接管产线。 |

**合作落点建议：**会上不要要求听众认可一张“大一统平台”蓝图；邀请视源制造、质量、工艺和售后团队共同挑选**一项最值得打通的交接**，明确现状、责任人、数据来源、人工关口和验证指标，再确定是否扩展复制。

## 六、与赵总讨论时优先确认

1. **主案例选谁？**三项视源合作中，哪一项有获准展示的现场流程、真实画面、客户反馈或前后对比？
2. **成果能说到哪一级？**“已上线”的具体范围是什么；哪些运行记录、业务效果或数字经过客户确认，哪些只能说是试点或建设中？
3. **主推应用的侧重？**质量异常闭环为主是否契合赵总想表达的连山优势；设备效率和售后反馈各保留多少篇幅？
4. **合作邀请要具体到哪里？**更适合提出一项质量任务打通试点，还是先共同梳理 AOI、故障树、售后三项之间的数据与岗位交接？
5. **外部展示权限：**客户名称、项目名称、界面截图、图像、工单、指标及其他客户案例是否分别获准在活动现场展示、会后传播？现场演讲与 PPT 对外流转可能不是同一授权范围。

## 七、内部参考与口径边界

- [连山产品体系诊断](./09-current-product-diagnosis.md)：能力分层与制造质量主线属于产品研究判断，不替代客户项目验收。
- [AgentOS 定位与分阶段证据建议](./10-AI-Native任务闭环平台视角下的连山产品诊断.md)：以场景闭环为对外语言；运行、业务、组织和财务效果需分别核实。
- [边缘推理研究](./05-edge-inference.md)：有视觉结果生产链路的研究证据，不证明相机采集、人工复判、设备动作及质量效果完整闭环。
- [FTA 场景研究](./06-demos-fta.md)：故障树资产与运行桥接的研究，不应移植为视源 IPU 项目的实际数据或收益。
- [SPC 场景研究](./07-demos-spc.md)、[参数推荐研究](./08-demos-param-opt.md)：包含场景样板、设计目标与待验证环节；不能把目标值当作生产成绩。

**对外措辞原则：**始终分清“连山产品可支持”“其他场景的研究／样板”“视源已开展合作”“视源已验证效果”“双方下一步设想”这五种不同证据等级。正式 PPT 完成前，请项目方逐页核对事实、数字与披露权限。
