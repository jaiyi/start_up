# ZooWork：交付型企业 Agent 平台

> 信息依据：ZooWork 官网首页与开发文档入口，未注册、未购买、未接入企业数据。官网场景和效果数字属于**厂商示意/主张**，不是我们测得的效果。定位为 Agent 平台/交付工作台，既涉及 Harness 又涉及团队知识和办公工作流；主报告按端到端业务任务交付归在业务应用与解决方案，避免重复归档。

## 1. 定位与产品构成

官网将 ZooWork 称为面向 FDE 和领域专家的 **AI agent delivery platform**，主张把岗位知识、方法、SOP 和交付标准包装成 Agent Skills，再交付持续执行任务的 Agent。首页列出 Agent Builder、Managed Agent API、Enterprise AI Stack 和 ZooData 等入口；不应把它仅理解为“文档里的 AI 助手”或“通用聊天机器人”。

| 官方展示的组成 | 解决的问题 | 仍需核实 |
|---|---|---|
| Agent Builder / 模板 | 对话配置角色、目标、知识、SOP、交付标准和工具权限，预览再发布 | 配置的版本控制、回滚、迁移和评测机制 |
| Agent Runtime / Harness | 任务拆分、工具调用、审批门；官网还提到 Python/Shell/Browser 沙箱、可观测性和反馈回流 | 真正的隔离级别、操作边界、故障恢复及策略落点 |
| Managed Agent API | 应用通过 API 调用 Agent | [开发文档](https://zoowork.ai/docs/)当前标为 **Developer Preview**，API 可能在正式发布前变化 |
| 企业接入与协作 | 官网展示 Slack/Teams 等聊天入口、业务系统连接器及嵌入式 Agent | 实际连接器能力、鉴权授权粒度、地区可用性 |
| ZooData | 官网主张把网页/行业数据转为 Agent 可用结构 | 数据许可、来源、刷新、覆盖范围与质量 |

## 2. 官网场景如何解读

官网用门店缺货和补货为例展示“读库存 → 预测 → 准备变更 → 人工批准 → 写 WMS/ERP → 复查”的端到端流程。这是很有价值的**产品交互示例**，但演示画面并不能证明它在我们环境中已连接 WMS、能完成事务一致的写入或达到网站展示的时效。官网明确说明部分场景和指标具有示意性质，不能把页面上的时长、效率和覆盖数字写成独立测评结果。

官网还宣称 SSO/RBAC、最小权限、运行时策略检查、不可信内容检查、租户隔离/加密、零保留和审计回放。上述都是**待核查的厂商安全主张**：合同、数据处理条款、部署地域、真实的审批强制性、日志/备份保留与独立测试报告，必须在正式使用前逐一确认。

## 3. 与团队知识工程/SPC 的对应

```text
稳定知识、专家方法与 SOP → 经授权导入的角色 Skill/Agent 配置
业务实时状态 → 受控 API / 工具（系统仍是 source of truth）
任务执行 → 计划、工具调用、人工审批、写回回执
结果 → 审阅、评测、反馈和可追溯的知识更新建议
```

可以借鉴其“**角色定义 + 交付标准 + 权限声明 + 审批门**”组织方式，特别是将 SPC 诊断的证据、适用条件、风险分级和专家审批显式化。但 WeKnora 中已有的知识不能仅因被检索就自动获得业务系统写权限；真实动作必须由本地受控工具执行并记录回执。厂商的“自我改进”话术也不应直接对应自动发布 Skill，评测与人审仍需分离。

## 4. 试点前问题清单

1. Agent 的系统指令、Skill、模型路由和工具策略由谁持有、如何版本化与导出？
2. 人工审批是否在服务端工具执行前强制拦截？能否防止绕过前端审批直接调用 API？
3. 对网页、附件、工具返回的提示注入和敏感输出如何阻断？沙箱能看到哪些网络、凭据和文件？
4. 日志/回放是否包含敏感原文；“零保留”与审计回放、备份如何同时成立？
5. Developer Preview API 的变更、SLA、失败恢复、幂等和计费边界是什么？
6. 用合成的门店与 SPC 场景逐步验证只读查询、审批后的写入和失败补偿，不使用真实团队资源。
