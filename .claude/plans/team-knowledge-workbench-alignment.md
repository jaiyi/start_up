# 团队知识工程：工作台产品形态对齐方案

## 判断

当前方案的治理与架构骨架基本正确，但产品主语仍是“知识与 Skill 双资产管理平台”。需要改成用户能直接理解的“以工作台为入口，把资料变成知识、把工作方式变成 Skill，并把已发布能力带到任务执行中的 AI 工作台”。

不推翻 Git、WeKnora、SkillHub、DSH 的权责边界；先重排产品叙事和用户对象，再让现有治理能力成为后台支撑。

## 目标产品形态

工作台同时提供三类体验：

1. **知识工作台**：拖入会议纪要/资料，Agent 先梳理，再与用户讨论、校正、确认，最后形成知识资产并提交到 knowledge-assets Git 仓库、触发 WeKnora 建立 Wiki/索引。
2. **Skill 工作台**：用户用自然语言描述固化工作方式，Agent 通过追问补齐输入、步骤、判断、例外、工具、输出和成功标准，生成完整 Skill 包（说明、脚本、资源、测试集/评测集），用户用例子试跑，确认后提交 Git 并发布 SkillHub。
3. **任务执行入口**：工作台外的 Agent/任务执行界面可以选择已发布 Skill，按固定版本挂载 Skill、知识范围和工具权限，运行结果可追溯并反馈到知识或 Skill 的修订流程。

## 用户可见的核心对象

- Workspace：团队/个人工作空间
- Workbench session：一次围绕资料、工作流或任务的协作会话
- Source material：会议纪要、文件、粘贴文本、链接等原始材料
- Knowledge draft / Knowledge asset：知识候选与正式知识
- Workflow draft：用户描述的工作过程及其结构化草稿
- Skill draft / Skill release：可测试、可发布的 Skill 包及固定版本
- Test case / Evaluation run：示例输入、期望结果、实际结果和评测结论
- Run / Feedback：执行记录、引用、人工修正和后续改进

## 端到端主叙事

```text
进入工作台
  ├─ 放入会议纪要/资料
  │   → 摘要与结构化梳理
  │   → 识别事实、决策、规则、行动项、争议和待确认项
  │   → 用户逐项讨论/确认
  │   → 知识资产预览
  │   → 提交 knowledge-assets Git
  │   → WeKnora Wiki/索引同步
  │
  └─ 描述一个重复工作流
      → Agent 追问和建模
      → 生成 Skill 草稿及脚本/资源/测试集
      → 用样例运行和比较结果
      → 用户修改、确认
      → 提交 knowledge-assets Git
      → 发布到 SkillHub

离开工作台执行任务
  → 选择已发布 Skill 固定版本
  → 挂载授权知识与工具
  → Agent 执行
  → 查看产物、引用、版本和反馈
  → 反馈回到知识或 Skill 工作台
```

## 关键产品原则

1. **工作台是协作与产物生成界面，不是 Git/CI/索引任务后台的可视化壳。** 用户只需确认内容、测试效果、点击提交/发布；Git commit、MR、CI、WeKnora ingest、SkillHub publish 由系统代办并展示证据。
2. **对话不是最终产物。** 每次会话都要收敛成可查看、可编辑、可比较、可确认的结构化草稿和文件产物。
3. **用户确认是主交互，不是末尾审批按钮。** Agent 每次抽取/生成都要标注依据、置信度、待确认项和变更差异。
4. **Knowledge 与 Skill 分开，但共享一个工作台。** Knowledge 回答“应该知道什么”；Skill 回答“如何完成任务”；Skill 可以声明依赖 Knowledge 和 Tool。
5. **工作流是 Skill 生成的中间建模对象。** 早期不必建设通用工作流编排平台，但应把步骤、判断、输入、输出、例外和人工节点结构化，避免只生成一段 SKILL.md。
6. **发布后才能在外部执行时挂载。** 草稿、测试版本、已发布版本严格区分；运行固定 Skill version/digest，不能使用漂移的 latest。
7. **Git 是正式源，WeKnora 是知识索引，SkillHub 是 Skill 注册/发布分发，DSH/Agent runtime 是执行宿主。** 工作台负责编排这些动作、展示状态和保留证据。

## MVP 建议

先做一个真正可感知的垂直切片，而不是先做资产后台：

1. 上传一份会议纪要；
2. Agent 生成摘要、决策、规则、行动项和知识候选；
3. 用户逐条讨论/修改/确认；
4. 点击提交后生成 Git 变更并同步 WeKnora；
5. 在同一工作台描述一个重复工作流；
6. Agent 生成 Skill 草稿、脚本/资源和 3–5 个测试用例；
7. 用户运行样例、查看结果、修改并确认；
8. 点击发布后提交 Git 并发布 SkillHub；
9. 在外部任务执行入口选择该 Skill 的固定版本并看到运行追踪。

MVP 暂不要求：完整可视化流程编排、开放 Plugin 市场、多租户、复杂跨团队 Agent 联邦和全自动高风险写入。

## 验收标准

- 非程序员不需要操作 Git，就能从会议纪要得到可审阅的知识资产草稿并提交。
- 用户能在工作台看到每条知识候选的来源、依据、待确认项和变更差异。
- 用户能通过自然语言把重复工作方式完善为包含说明、脚本/资源和测试集的 Skill 包。
- 用户能用真实样例试跑 Skill，看到输入、输出、失败原因和评测结果。
- 确认后，知识确实进入 Git 且在 WeKnora 可检索；Skill 确实进入 Git 且在 SkillHub 可发布/查询。
- 外部任务执行能挂载固定 Skill 版本，并记录 Skill、知识、工具和运行结果。
- 任何运行反馈都能明确进入知识修订、Skill 修订、分发故障或平台故障之一，而不是停留在聊天记录里。
