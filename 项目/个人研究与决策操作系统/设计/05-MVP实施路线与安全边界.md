# 05 · MVP 实施路线与安全边界

## 1. 分阶段路线

### 阶段 0：设计归档

当前阶段只固化目标、对象、状态、边界和设计原则，不连接外部服务，不运行自动抓取。

### 阶段 1：收件箱与人工分流

建立低成本的原始输入格式和候选队列。输入可以是链接、文字、截图说明或语音转写；系统负责提取来源、主题、初始关联和下一步建议，个人负责确认是否进入研究。

### 阶段 2：公开信号雷达

优先接入公开且稳定的来源，例如 GitHub Release、公开仓库元数据、官方 Blog/RSS、项目 Changelog 和公开融资/投资公告。资本信号先记录投资方、产品方向和公开投资逻辑，再补充产品、采用和生态动量证据，最后生成候选报告；不自动修改正式研究或洞察。资本与生态信号的详细规则见 [`06-资本与生态信号雷达.md`](./06-资本与生态信号雷达.md)。

### 阶段 3：研究草稿与对比

针对确认的候选对象生成研究草稿，要求引用官方来源、区分事实和推断，并自动关联已有对象、研究、洞察和项目。研究草稿需要人工检查后才能成为正式研究文档。

### 阶段 4：洞察候选与 Tutor

按周期生成跨研究对比、冲突证据、洞察候选和思考题。个人可以采用、修改、暂缓或拒绝，系统记录选择原因，作为后续教育反馈的依据。

### 阶段 5：项目上下文包

项目启动或重大设计任务发生时，按项目目标生成上下文包，整理研究、洞察、知识、历史决策和未决问题，减少重复提问和上下文遗漏。

### 阶段 6：项目反馈回流

从项目计划、测试、实验、Issue、运行记录和复盘中提取验证结果，形成知识候选和对既有判断的影响记录。知识候选经人工审核后才进入 `知识/`。

## 2. 推荐的最小实现顺序

```text
收件箱格式
  → 候选对象与研究队列
  → GitHub/官方发布/资本信号雷达
  → 研究草稿模板
  → 洞察候选模板
  → 项目上下文包
  → 验证反馈模板
```

先做文件和状态约定，再做脚本和 Agent；先做公开信息和人工确认，再做复杂平台集成。这样即使自动化暂时不可用，系统也仍然能靠人工继续运行。

## 3. 安全边界

- 融资金额、投资机构声望或媒体报道不作为产品成熟度的单独证明；
- 资本叙事必须与产品能力、采用证据和生态动量分开记录；
- 不使用付费数据库或非公开信息绕过访问权限；
- 不把资本信号自动升级为正式洞察或项目架构决策；
- 不自动执行项目命令、业务写回、部署、删除或发布；
- 不自动覆盖正式洞察、研究正文或长期知识；
- 原始证据、研究结论和个人判断分层保存；
- 每次自动运行都应有运行记录、失败记录和可追溯输入；
- 删除或合并对象前必须保留历史路径和变更理由。

## 4. 评估指标

MVP 不以“自动生成文档数量”为指标，优先观察：

- 外部信号捕获到队列的时间；
- 候选对象的有效率和重复率；
- 研究与已有内容的关联命中率；
- 洞察候选被采用、修改和拒绝的比例；
- 项目上下文包中有用输入的比例；
- 项目验证结果成功回流的比例；
- 个人每周实际获得的高价值问题、实验和学习输入；
- 自动化误报、隐私越界和错误升级次数。

## 5. 失败时的降级策略

任何外部 API、模型服务或自动任务不可用时，系统都应退回到：

```text
手动捕获 → 本地 Markdown → 人工确认 → 后续再处理
```

自动化是加速器，不应成为知识沉淀链的单点故障。
