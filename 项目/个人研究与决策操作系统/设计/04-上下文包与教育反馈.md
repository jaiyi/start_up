# 04 · 上下文包与教育反馈

## 1. 项目上下文包

进入项目设计阶段时，不应依赖个人重新回忆“之前调研过什么”。系统应根据项目目标生成上下文包，作为架构讨论的输入索引，而不是复制所有原文。

一个上下文包至少包括：

```text
项目目标与当前问题
相关已确认洞察
高相关外部研究
已验证知识
历史项目决策
不能直接采用的模式
当前未决问题
建议实验和验收指标
```

上下文包需要标注每条输入的来源和成熟度：

- `fact`：外部事实；
- `inference`：工程推断；
- `insight`：已确认个人判断；
- `assumption`：项目假设；
- `validated`：项目已验证方法；
- `open_question`：仍待回答的问题。

系统应优先提供高相关且高可信的内容，不能因为语义相似就把所有相关文档堆进上下文。

## 2. 关联排序

上下文关联可以综合：

1. 项目目标和业务对象的直接匹配；
2. 当前设计问题与研究中的机制匹配；
3. 已确认洞察的适用范围；
4. 研究证据等级和更新时间；
5. 过去项目的验证结果；
6. 与当前假设的冲突程度。

对“支持当前判断”和“挑战当前判断”的材料都应保留，避免系统只返回确认偏见。

## 3. Tutor 教育反馈

Tutor 不是摘要机器人，而是帮助个人形成判断的认知教练。它应定期输出：

- 最近值得理解的三个趋势；
- 两条挑战既有判断的证据；
- 一个可形成洞察的跨对象连接；
- 一个可以在项目中验证的小实验；
- 推荐阅读顺序；
- 需要本人先回答的思考题。

推荐采用“先提问、后揭示”的形式：

```text
问题：为什么 Agent Runtime、Control Plane、Knowledge Base 不能简单合并为一个产品？
请先写下你的判断、证据和反例。
随后系统再提供对比材料和参考答案。
```

## 4. 周期性反馈

每周摘要不应只是新闻列表，而应回答：

```text
这周外部世界发生了什么变化？
它和我已有的哪些研究、洞察、项目有关？
它支持、修正还是挑战了哪些判断？
我下一步应该读什么、问什么、实验什么？
```

每月可以进一步生成：

- 主题关注变化；
- 研究队列积压；
- 洞察候选的确认率；
- 项目验证对既有判断的影响；
- 新增和淘汰的知识；
- 雷达遗漏或误报复盘。

## 5. 认知安全

教育反馈必须明确区分事实、解释和建议，不能用确定口吻掩盖证据不足。对于争议性结论，应同时给出支持证据、反例和未决问题，让个人保留判断空间。
