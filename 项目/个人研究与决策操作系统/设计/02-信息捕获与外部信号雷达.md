# 02 · 信息捕获与外部信号雷达

## 1. 两类输入

### 人工捕获

微信小视频、小红书、同事分享、会议信息、截图、语音转写和没有完整上下文的链接，都允许先以原始形式进入收件箱。捕获时只要求记录来源和当下想法，不要求立即判断归属。

推荐的最小记录：

```yaml
id: signal-YYYYMMDD-序号
captured_at: 时间
source_type: colleague-share | social | video | github | article | conversation | capital
source_url: 可选
raw_content: 原文、转写或摘要
initial_thought: 当下为什么觉得值得记录
privacy: public | internal | personal | restricted
status: captured
```

捕获阶段不应强迫个人完成分类，否则会让输入成本过高，最终重新依赖记忆。

### 系统发现

系统可以定期关注以下公开来源：

- GitHub 项目 Star、Fork、Issue、PR、Release 和贡献者变化；
- GitHub Topics、代码搜索和指定组织的新仓库；
- 官方 Blog、Changelog、技术文档、RFC 和 Roadmap；
- Hugging Face、npm、PyPI 等公开生态信号；
- 投资机构官网、基金公开投资组合、融资方公告、公司新闻稿和公开投资逻辑；
- 已确认主题下的新产品、案例和技术路线。

资本和融资信号只能作为方向线索。它必须与产品实际能力、客户/用户采用证据和开源/社区/招聘等生态动量交叉验证，不能因为投资机构知名或融资金额较高就直接提高产品结论的可信度。

趋势判断不能只依赖总 Star 或单笔融资。应关注一段时间内的增长速度、活跃度、版本变化、真实使用证据、资本持续下注情况和与你当前项目的关联程度。

资本信号的专门数据结构、优先级和反误判规则见 [`06-资本与生态信号雷达.md`](./06-资本与生态信号雷达.md)。

## 2. 关注主题

初始主题可包括：

```text
agent-runtime
agent-harness
agent-control-plane
agent-memory
mcp
coding-agent
industrial-ai
knowledge-base
ontology
aI-native-enterprise
manufacturing-ai
equipment-maintenance
quality-engineering
spc
```

主题清单不是永久分类。项目验证和个人兴趣变化后，应记录主题增删原因，避免雷达只追逐短期热点。

## 3. 分流状态

```text
captured      已捕获
triaging      正在分流
watching      暂时观察
researching   正在研究
researched    事实研究完成
insight_candidate 洞察候选
project_input 项目输入
verified      项目已验证
archived      已归档
```

状态表示内容成熟度，不表示价值高低。一个高价值对象也可能暂时处于 `watching`，因为证据不足。

## 4. 候选优先级

候选对象的优先级由以下因素共同决定：

- 与当前项目的相关性；
- 新颖性和变化速度；
- 资本信号强度与投资逻辑的清晰度；
- 产品、采用和生态动量证据的完整度；
- 证据可获得性；
- 对既有判断的挑战程度；
- 可能产生的项目实验价值；
- 研究成本；
- 隐私、版权和访问风险。

推荐输出三种动作，而不是强行二元判断：

```text
立即研究：相关性高且证据足够
持续观察：可能重要但当前证据不足
暂不处理：相关性低或重复度高
```

## 5. 去重与关联

候选分流时应尝试关联：

- 已有研究对象和同类产品；
- 既有洞察及其支持/反例；
- 相关项目、设计文档和未决问题；
- 已验证知识和失败记录。

关联是推荐，不是自动合并。不同来源可能描述同一对象，也可能只是名称相似，最终归并仍需检查证据。

## 6. 隐私边界

社交平台内容、同事分享和内部信息默认不自动发送到外部服务。系统应先标记隐私级别，只有公开内容或经过明确授权的摘要才能进入外部研究流程。原始资料与研究结果分开保存，避免把内部信息误写成公开事实。
