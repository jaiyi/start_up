# 03 · 研究、洞察、项目与知识流转

## 1. 四类内容的职责

```text
研究：外部对象是什么？有哪些事实、证据和不确定性？
洞察：基于研究和实践，我如何理解、取舍和行动？
项目：如何把判断转成设计、实现和验证？
知识：哪些方法已经被验证，可以跨项目复用？
```

系统必须保持这四种内容的边界，不能因为自动关联方便，就把产品宣传直接写成知识，把研究摘要直接写成洞察，或把项目假设当作已验证方法。

## 2. 转换契约

### Signal → Research Candidate

触发条件：信号指向一个可识别的外部对象、技术路线、案例或趋势。

必须保留：原始来源、捕获时间、原文/截图、个人初始想法、隐私级别和来源可信度。

### Research Candidate → Research

触发条件：对象有足够公开证据，且研究价值高于研究成本。

研究结果至少包含：

- 官方事实；
- 代码或产品行为观察；
- 工程机制推断；
- 与既有对象的比较；
- 证据等级和未决问题；
- 对当前项目的潜在影响。

### Research → Insight Candidate

触发条件：多个研究对象之间出现可解释的共同模式、差异、矛盾或对个人项目有明确影响。

洞察候选必须包含：

```text
候选判断
支持证据
反例或冲突证据
对已有判断的修改
可能影响的项目
需要本人回答的问题
```

洞察候选不得直接替代正式洞察，必须标记为待确认。

### Insight → Project Input

触发条件：洞察与某个项目目标相关，并能转译成设计问题、架构选项、实验假设或验收指标。

项目输入应说明：

- 参考来源；
- 可直接采用的部分；
- 仍需验证的部分；
- 不适用的边界；
- 预计用什么实验验证。

### Project Validation → Knowledge Candidate

触发条件：项目实验、测试或运行结果对某个方法形成了可重复证据。

必须记录：原始假设、实现方式、测试条件、实际结果、失败情况、适用条件和限制。只有经过人工审核后，才能进入 `知识/`。

## 3. 反馈类型

项目结果不只有“成功/失败”，应区分：

- `supported`：支持原始判断；
- `refined`：判断成立但适用条件被补充；
- `contradicted`：实验结果推翻原判断；
- `inconclusive`：证据不足，不能下结论；
- `reusable`：已形成跨项目可复用方法；
- `retired`：旧方法应停止推荐。

## 4. 不允许的自动升级

以下内容不得自动升级为正式长期知识：

- 单一产品的营销描述；
- 没有来源的二手转述；
- 只在一次实验中偶然成立的结果；
- 未标注推断性质的架构猜测；
- 未经本人确认的价值判断；
- 涉及内部数据但未完成脱敏的项目经验。

## 5. 每个节点必须有下一步

节点完成后必须产生一个明确动作：

```text
继续研究 / 对比对象 / 提出问题 / 请求确认 / 纳入项目 / 设计实验 / 形成知识候选 / 观察 / 归档
```

“文档已完成”不是一个足够的流程状态。系统要推动的是认知和实践继续向前，而不是文件数量继续增加。
