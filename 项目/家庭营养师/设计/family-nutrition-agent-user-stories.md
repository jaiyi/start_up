# 家庭营养师 Agent 用户故事

> 目标：先把用户如何使用产品说清楚，再倒推 WeKnora Agent、Skill、Prompt 和知识库配置。本文描述第一版 MVP，不包含自动下单、医疗级营养诊断和复杂多人权限。

## 1. 产品一句话

家庭营养师 Agent 是一个通过微信或 WeKnora 对话入口使用的家庭饮食助手。它基于家庭成员画像、饮食规则、菜谱库、当前库存、近期菜单和饭后反馈，帮助家庭每天决定吃什么，并持续沉淀更懂这个家庭的饮食知识。其中稳定知识由 Git Markdown + WeKnora 知识库管理，库存、菜单、反馈等动态状态由独立 Docker Postgres + MCP 服务管理。

核心不是“生成一道菜”，而是形成闭环：

```text
采购 / 库存录入
  ↓
日常推荐 / 周末清库存
  ↓
执行做饭
  ↓
默认扣减库存
  ↓
饭后反馈
  ↓
更新菜谱注意事项、成员偏好和推荐规则
  ↓
下一次推荐更准
```

## 2. 用户角色

### 2.1 家庭饮食负责人

通常是家里负责安排吃什么的人。

关注点：

```text
少纠结；
少浪费；
宝宝能吃；
老人能吃；
爸爸妈妈吃得健康；
阿姨能执行；
菜谱越来越贴合家里。
```

### 2.2 做饭执行者

可能是阿姨、家人或老人。

关注点：

```text
今天到底做什么；
怎么做；
哪些给宝宝单独处理；
哪些少盐少油；
哪些能留晚餐复热；
做完后要反馈什么。
```

### 2.3 家庭成员反馈者

可能是妈妈、爸爸、老人，也可能是妈妈代宝宝反馈。

关注点：

```text
一句话反馈即可；
系统能理解是谁不喜欢、为什么不喜欢；
下次不要重复犯错；
好的做法能沉淀下来。
```

### 2.4 菜谱收集者

通常是刷小红书、视频号、B站或公众号时看到新菜谱的人。

关注点：

```text
这个菜谱适不适合我家；
能不能改成宝宝版；
老人能不能吃；
是否值得入库；
以后推荐时能不能用上。
```

## 3. 产品形态

第一版采用：

```text
一个前台 Agent
+
多个后台 Skill
```

用户只感知一个入口：

```text
家庭营养师 Agent
```

后台能力包括：

```text
1. meal-recommender：日常推荐和周末清库存
2. inventory-manager：库存新增、库存扣减、临期提醒和采购建议
3. recipe-collector：新菜谱收集、适配判断和标准化
4. feedback-learner：饭后反馈理解和知识更新建议
5. knowledge-maintainer：用户确认后沉淀稳定知识到 Wiki / Markdown；动态状态写入交给 MCP 工具
```

## 4. 核心产品原则

### 4.1 一个入口

用户不需要判断该找哪个 Agent。所有问题都可以先发给“家庭营养师 Agent”。

例如：

```text
今晚吃什么？
周末帮我清库存。
今天买了这些菜。
宝宝今天没怎么吃。
这个小红书菜谱帮我看看能不能收。
确认写入。
```

### 4.2 库存是强状态

推荐必须通过 MCP 读取 Postgres 中的当前库存。如果 MCP 返回库存缺失或不确定，Agent 必须先问，不要假设。

### 4.3 推荐时生成计划消耗

推荐菜品时，Agent 必须同步生成“预计库存消耗”，但只有用户确认后才通过 MCP 写入计划消耗。

推荐本身不等于已经做饭，因此第一步记录为计划消耗：

```text
推荐菜单
  ↓
生成 planned consumption 建议
  ↓
等待用户确认后写入 MCP / 等待执行
```

### 4.4 饭后无反馈视为正常

如果用户已经确认执行某个推荐菜单，且饭后没有额外负面反馈，则默认：

```text
本餐执行正常；
没有新增口味/做法问题；
通过 MCP 按计划消耗扣减库存；
通过 MCP 写入 meal event；
菜谱推荐权重不做负向调整。
```

如果用户补充反馈，则以反馈为准通过 MCP 修正库存，并生成偏好/菜谱更新建议。

### 4.5 新增菜谱必须人工确认

菜谱收集 Agent 可以生成标准菜谱 Markdown，但不能直接入库。必须经过用户确认：

```text
可以入库。
确认写入。
按这个收录。
```

### 4.6 知识写入必须确认

涉及修改以下内容时必须用户确认：

```text
recipes/*.md
family/member-preferences.md
family/dietary-rules.md
agent-rules/*.md
Postgres 动态状态：inventory、purchase、planned consumption、meal events、feedback
```

确认前只输出建议更新内容。稳定知识确认后写入 Markdown / Wiki；动态状态确认后通过 MCP 工具写入 Postgres。

## 5. 用户故事 P0

### 5.1 今晚吃什么

用户输入：

```text
今晚吃什么？
```

系统行为：

```text
1. 读取家庭成员画像和饮食规则；
2. 通过 MCP 读取当前库存；
3. 通过 MCP 读取最近 2 周推荐/实际吃过的菜单；
4. 检索菜谱库；
5. 排除最近频繁出现的菜；
6. 生成宝宝版和成人/老人共用版；
7. 生成预计库存消耗；
8. 询问是否按此执行。
```

理想输出：

```text
今晚建议：
1. 虾仁豆腐羹
2. 西兰花鸡蛋
3. 冬瓜汤

为什么适合：
- 使用库存里的虾仁、豆腐、西兰花、冬瓜；
- 虾仁豆腐羹适合宝宝做软烂版；
- 冬瓜汤适合老人晚餐复热；
- 这几道菜最近 2 周没有高频出现。

宝宝版：
- 虾仁剁碎；
- 豆腐切小块；
- 不放盐或极少盐。

成人/老人版：
- 少油少盐；
- 老人晚餐可复热冬瓜汤。

预计消耗：
- 虾仁约 150g；
- 豆腐 1 盒；
- 西兰花半颗；
- 冬瓜一小块。

需要补买：
- 无。

如果确认今晚就做这套，我会把它记为计划菜单，并在饭后默认按计划扣减库存。
```

验收标准：

```text
必须说明用了哪些库存；
必须说明宝宝版和成人/老人版；
必须生成预计库存消耗；
必须规避近 2 周高频菜单；
不能在库存缺失时编造食材。
```

### 5.2 周末清库存

用户输入：

```text
周末帮我清库存。
```

系统行为：

```text
1. 读取当前库存和采购记录；
2. 找出上周采购后仍未消耗的食材；
3. 标记易坏食材；
4. 检索可组合消耗多种库存的菜谱；
5. 生成周末 2 天菜单；
6. 尽量少补买；
7. 生成预计库存消耗和剩余食材。
```

理想输出：

```text
本周末清库存重点：

优先消耗：
1. 豆腐：建议 1 天内用完；
2. 小油菜：容易蔫，优先今天；
3. 蘑菇：适合搭配鸡蛋/牛肉；
4. 虾仁：如果已解冻，今天用完。

周六午餐：
- 虾仁豆腐羹
- 小油菜鸡蛋

周六晚餐：
- 蘑菇牛肉烩饭

周日早餐：
- 鸡蛋蔬菜饼
- 酸奶水果碗

需要补买：
- 鸡蛋 6 个
- 肉末 200g

暂时不动：
- 土豆
- 胡萝卜
- 冬瓜
```

验收标准：

```text
必须列出优先消耗食材；
必须说明哪些食材可以暂时不动；
补买项必须尽量少；
不能为了清库存牺牲宝宝/老人安全。
```

### 5.3 每周采购后更新库存

用户输入：

```text
今天买了：西兰花、鸡蛋、虾仁、牛肉、豆腐、冬瓜。
```

系统行为：

```text
1. 解析新增食材；
2. 归类为蔬菜、蛋白质、豆制品、根茎、耐放食材等；
3. 判断优先消耗顺序；
4. 生成采购入库和库存优先级的结构化变更；
5. 等待用户确认后，通过 MCP 写入 Postgres。
```

验收标准：

```text
不能直接覆盖库存；
必须生成结构化更新建议；
必须标注优先消耗顺序；
必须等待用户确认。
```

### 5.4 每天做完饭后默认扣减库存

触发条件：

```text
用户明确确认执行过推荐菜单；
且饭后没有额外反馈或修正。
```

系统行为：

```text
1. 读取本餐 planned consumption；
2. 将计划消耗转为实际消耗；
3. 通过 MCP 扣减或修正库存；
4. 通过 MCP 记录 meal event；
5. 不更新负向偏好；
6. 如果有剩菜，记录可复热状态。
```

用户输入示例：

```text
今天就按你推荐的做了。
```

系统输出：

```text
收到，默认本餐执行正常。

将按计划扣减库存：
- 虾仁：减少约 150g；
- 豆腐：减少 1 盒；
- 西兰花：减少半颗；
- 鸡蛋：减少 2 个。

菜单记录：
- 虾仁豆腐羹
- 西兰花鸡蛋

没有负面反馈，本次不调整成员偏好和菜谱权重。

是否确认通过 MCP 写入库存和菜单记录？
```

验收标准：

```text
没有反馈不等于没有执行；
用户确认执行后，默认按计划扣减库存；
没有负面反馈时不调整偏好；
仍需确认写入。
```

### 5.5 饭后反馈学习

用户输入：

```text
今天这个西兰花鸡肉饼宝宝没怎么吃，爸爸觉得还行，老人觉得有点干。
```

系统行为：

```text
1. 识别菜品、成员和反馈类型；
2. 判断是菜谱问题、做法问题、成员偏好问题还是偶发问题；
3. 生成菜谱注意事项更新建议；
4. 生成成员偏好更新建议；
5. 生成推荐权重调整建议；
6. 同步判断库存实际消耗；
7. 等待用户确认后，通过 MCP 写入动态状态；稳定知识变更另行生成 Markdown 建议。
```

验收标准：

```text
必须区分一次性反馈和长期偏好；
不能因为宝宝一次没吃就全家禁用；
必须输出可写入的 Markdown 更新建议；
必须处理库存实际消耗。
```

### 5.6 新菜谱人工确认入库

用户输入：

```text
这个小红书菜谱帮我看看能不能收。
```

系统行为：

```text
1. 读取用户提供的链接、文案或截图；
2. 必要时使用 Web Search 补充信息；
3. 根据家庭画像和饮食规则判断适配性；
4. 生成标准菜谱 Markdown；
5. 等待用户确认入库。
```

验收标准：

```text
新增菜谱必须人工确认；
必须区分原始做法和家庭改造版；
必须写宝宝版和成人/老人共用版；
必须写不推荐情况。
```

## 6. 用户故事 P1

### 6.1 一周菜单规划

用户输入：

```text
帮我安排下周工作日午餐。
```

系统行为：

```text
1. 读取库存和近期菜单；
2. 避免近 2 周重复；
3. 生成 5 天菜单；
4. 标出可复热菜；
5. 标出需要补买清单；
6. 生成 weekly-menu-log.md 更新建议。
```

### 6.2 阿姨可执行说明

用户输入：

```text
明天阿姨来，帮我整理一份能直接发给她的做饭说明。
```

系统输出必须包括：

```text
菜名；
食材；
步骤；
宝宝版处理；
成人/老人版处理；
复热注意；
做完后反馈什么。
```

### 6.3 最近重复规避

用户输入：

```text
最近老吃番茄鸡蛋了，换点别的。
```

系统行为：

```text
1. 通过 MCP 的 list_recent_meals 读取近期菜单；
2. 降低近 2 周已推荐或已执行菜品；
3. 区分“推荐过但没做”和“实际做过”；
4. 给出替代方案。
```

## 7. 近期菜单滚动记录

为了避免菜品频繁出现，第一版在 Postgres 维护近期菜单滚动状态，并通过 MCP 读取。

动态状态保留范围：

```text
最近 14 天推荐菜单；
最近 14 天实际执行菜单；
每道菜最近推荐日期；
每道菜最近执行日期；
是否有负面反馈；
是否适合近期再次推荐。
```

建议数据对象：

```text
meal_plans：推荐和计划菜单；
meal_plan_items：每餐菜品明细；
planned_consumptions：计划消耗；
meal_events：实际执行菜单；
meal_feedback：饭后反馈。
```

推荐规则：

```text
近 3 天执行过：默认不推荐，除非用户明确要求。
近 7 天执行过：降低推荐。
近 14 天多次推荐或执行：明显降低推荐。
推荐过但未执行：轻微降低，不等同于吃过。
负面反馈菜品：按反馈严重程度降低。
```

`meals/recent-menu-log.md` 可作为 Postgres 导出的可读快照，用于 Git 归档、人工审阅和 WeKnora 索引摘要。不要在每道菜谱 frontmatter 中高频维护 `last_recommended_at` / `last_cooked_at`，避免频繁改动大量菜谱文件。

## 8. PostgreSQL、MCP 与动态状态管理

WeKnora 自身有 PostgreSQL，用于平台数据、用户、知识库、任务、索引相关元数据等。家庭营养师不直接在 WeKnora 内部库里建业务表，而是部署一个独立的同机 Docker Postgres，并通过 MCP 服务暴露受控工具。

原因：

```text
1. WeKnora 内部数据库属于平台实现细节，直接改表会影响升级和维护；
2. 库存、菜单、反馈是高频动态状态，需要事务、幂等和审计；
3. Markdown 文件适合稳定知识、人工审阅和归档，不适合频繁扣减库存；
4. MCP 工具可以限制 Agent 只能执行业务动作，不能执行任意 SQL；
5. 同机 Docker Postgres 成本低、网络简单，后续可迁移到托管 Postgres。
```

动态状态 source of truth：

```text
独立 Postgres：
- inventory_items
- inventory_events
- purchase_records
- purchase_items
- meal_plans
- meal_plan_items
- planned_consumptions
- meal_events
- meal_feedback
- preference_observations
- audit_log
```

Markdown 文件的新定位：

```text
inventory/current-inventory.md
inventory/purchase-log.md
inventory/planned-consumption-log.md
meals/recent-menu-log.md
meals/meal-feedback-log.md
```

这些文件保留，但作为 Postgres 导出的可读快照、Git 归档和 WeKnora 索引摘要，不再作为实时事务状态源。

MCP 工具第一版：

```text
get_current_inventory
get_inventory_risks
list_recent_meals
list_pending_planned_consumptions
get_meal_feedback_summary
record_purchase_after_confirmation
create_planned_consumption
confirm_meal_execution
record_meal_feedback
adjust_inventory_after_feedback
export_state_snapshot_to_markdown
```

所有写入工具必须要求用户确认、结构化参数、`idempotency_key` 和审计记录。

## 9. P0 验收清单

```text
1. 用户可以只使用一个“家庭营养师 Agent”入口。
2. Agent 能根据库存和家庭规则推荐一餐。
3. Agent 能在推荐时生成预计库存消耗。
4. 用户确认执行且无反馈时，Agent 能默认按计划扣减库存。
5. Agent 能根据饭后反馈生成偏好、菜谱和库存更新建议。
6. Agent 能处理每周采购后的库存新增。
7. Agent 能做周末清库存菜单。
8. Agent 能避免近 2 周频繁重复推荐。
9. 新菜谱入库必须人工确认。
10. 知识写入必须可追踪、可回滚。
```
