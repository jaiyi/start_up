# 个人从 0 部署 WeKnora 设计方案

> 日期：2026-09-16  
> 主题：个人 AI 爱好者从租服务器开始部署 WeKnora，用于个人知识库、办公知识库、生活知识库，以及后续手机端 / 微信 / WorkBuddy 入口扩展。

---

## 1. 背景与目标

用户是个人 AI 爱好者，希望从 0 开始部署 WeKnora。这里的“从 0”包括：

```text
租云服务器
初始化服务器
部署 WeKnora
配置模型服务
创建个人知识库
手机端、桌面端、网页端访问
后续可能通过微信 / WorkBuddy 作为入口
```

第一阶段目标不是构建复杂 AI 平台，而是跑通最小闭环：

```text
租服务器
  ↓
部署 WeKnora
  ↓
接入 LLM / Embedding
  ↓
创建分区知识库
  ↓
导入低敏资料
  ↓
完成 RAG / Wiki / Agent 问答
  ↓
手机和电脑都能访问
  ↓
建立备份和导出习惯
```

成功状态：

```text
用户可以随时打开网页或手机浏览器，
查询自己的生活、办公、AI 学习资料，
回答有引用，
资料不混库，
系统能备份，
后续能扩展到 WorkBuddy / 微信入口。
```

---

## 2. 已确认设计决策

本设计基于以下已确认选择：

```text
部署位置：公网云服务器
服务器地区：中国大陆
第一阶段访问方式：公网 IP + WeKnora 端口
第一阶段登录方式：WeKnora 自带账号密码
域名：第一阶段先不用域名
HTTPS：第一阶段暂不做，第二阶段补
知识隔离：一个 WeKnora 实例，多个知识库
知识范围：办公 + 生活 + AI 学习
手机端：第一阶段用手机浏览器访问
微信 / WorkBuddy：后续阶段再接入
本地大模型 / vLLM：第一阶段不使用，先用外部模型 API
```

---

## 3. 第一阶段总体架构

采用最小可行架构：

```text
手机浏览器 / 桌面浏览器
  ↓
http://服务器公网IP:WeKnora端口
  ↓
WeKnora 登录页
  ↓
账号密码
  ↓
WeKnora
  - 知识库
  - Wiki Mode
  - RAG
  - Agent Chat
  - 模型调用
  - 引用来源
  - 权限隔离
  ↓
数据库 / 向量库 / 文件存储
  ↓
手动或自动备份
```

第一阶段暂不做：

```text
域名
HTTPS
微信机器人
WorkBuddy 集成
本地大模型
vLLM
复杂多用户协作
高度敏感资料入库
```

这样可以把变量降到最低，优先验证 WeKnora 是否适合作为个人知识底座。

## 4. 服务器设计

### 4.1 推荐起步配置

```text
云服务器：中国大陆节点
系统：Ubuntu 22.04 LTS
CPU：4 核
内存：16 GB
磁盘：200 GB SSD
带宽：3–5 Mbps
公网 IP：需要
GPU：第一阶段不需要
```

适合：

```text
个人 PoC
少量知识库
20–40 个低敏测试文件
少量问答并发
手机和桌面浏览器访问
```

### 4.2 更稳妥配置

如果预算允许，推荐直接使用：

```text
CPU：8 核
内存：32 GB
磁盘：500 GB SSD
```

适合：

```text
长期个人使用
更大的知识库
更频繁的 Wiki / RAG 任务
更从容的 Docker 服务运行空间
```

### 4.3 规格选择原则

```text
短期 PoC：4 核 16G
准备长期使用：8 核 32G
不本地跑大模型：不需要 GPU
本地跑模型：另行规划 GPU 服务器和 vLLM
```

## 5. 访问与账号密码设计

### 5.1 第一阶段访问方式

电脑端：

```text
浏览器访问 http://公网IP:端口
```

手机端：

```text
手机浏览器访问 http://公网IP:端口
添加到浏览器收藏
如页面体验可接受，可添加到手机主屏幕
```

### 5.2 登录方式

第一阶段使用 WeKnora 自带账号密码。

管理员账号密码规则：

```text
密码长度至少 16–24 位
使用大小写字母 + 数字 + 符号
使用密码管理器生成
不要复用其他网站密码
不要使用 admin/admin、123456、手机号、生日
```

推荐密码管理器：

```text
1Password
Bitwarden
iCloud Passwords
KeePass
```

### 5.3 账号设计

第一阶段可以只创建一个实际使用账号：

```text
admin / owner：用户本人
```

但设计上预留后续账号：

```text
personal-user：个人生活知识使用者
work-user：办公知识使用者
future-workbuddy-api：未来给 WorkBuddy 调用 WeKnora 的 API 账号
```

## 6. 基础安全设计

第一阶段公网 IP + HTTP 有安全风险，所以必须把暴露面降到最低。

### 6.1 最小安全措施

```text
1. SSH 使用强密码或密钥登录
2. 优先使用 SSH key 登录
3. 最好关闭 root 密码登录
4. 云安全组只开放必要端口
5. 数据库 / Redis / 向量库端口不暴露公网
6. WeKnora 登录页必须使用强密码
7. 第一阶段不要上传高度敏感资料
8. 不要在公共 Wi-Fi 登录
9. 尽快在第二阶段补 HTTPS 或 VPN
```

### 6.2 端口策略

开放：

```text
22：SSH，最好限制来源 IP
WeKnora Web 端口：例如 8080，以官方部署文件为准
```

关闭公网访问：

```text
数据库端口
Redis 端口
向量库端口
对象存储内部端口
其他 Docker 内部服务端口
```

### 6.3 HTTP 阶段使用限制

因为第一阶段暂不启用 HTTPS，所以：

```text
不要上传身份证、银行卡、密码、API key、合同原件等高敏资料
不要在陌生公共网络登录
不要长期停留在 HTTP 方案
一旦 PoC 成立，应升级到域名 + HTTPS 或 VPN / Tailscale
```

## 7. 知识库结构设计

采用一个 WeKnora 实例，多个知识库：

```text
00-inbox
01-personal-life
02-work-public
03-work-private
04-ai-learning
```

### 7.1 00-inbox

`00-inbox` 是临时收集箱 / 待整理区。

用途：

```text
未分类资料
手机端随手保存内容
待整理 PDF / 网页 / 笔记
还没判断敏感级别的材料
```

规则：

```text
新资料先进入 inbox
每周整理一次
正式问答 Agent 默认不查 inbox
知识整理助手可以查 inbox
整理后移动到正式知识库
```

价值：

```text
降低收集成本
避免正式知识库变成杂物堆
减少敏感资料误入正式库
给未来知识整理 Agent 提供缓冲区
```

### 7.2 01-personal-life

生活知识库。

包括：

```text
旅行
家庭设备
健康科普
消费决策
保险学习
生活 SOP
个人计划
```

第一阶段不建议放入医疗原始报告、身份证件、银行卡、完整合同等高敏资料。

### 7.3 02-work-public

办公通用知识库。

包括：

```text
公开产品资料
行业资料
销售 SOP
客户常见问题
通用话术
公开竞品资料
```

这部分未来可以比较容易接入 WorkBuddy 或微信入口。

### 7.4 03-work-private

办公私有知识库。

包括：

```text
脱敏客户记录
会议纪要
项目复盘
跟进记录
个人工作方法
```

注意：

```text
第一阶段不要上传公司高度保密资料
不要上传未脱敏客户隐私
不要上传违反公司合规要求的办公材料
```

### 7.5 04-ai-learning

AI 学习知识库。

包括：

```text
WeKnora 部署笔记
LLM Wiki 方法论
Agent 框架资料
Prompt 模板
模型评测记录
开源项目调研
```

## 8. Agent 设计

第一阶段只创建 5 个 Agent：

```text
个人生活助手
办公公共知识助手
办公私有助手
AI 学习助手
知识整理助手
```

### 8.1 Agent 与知识库绑定

```text
个人生活助手：
  只访问 01-personal-life

办公公共知识助手：
  只访问 02-work-public

办公私有助手：
  访问 02-work-public + 03-work-private

AI 学习助手：
  只访问 04-ai-learning

知识整理助手：
  访问 00-inbox + 目标知识库
```

### 8.2 Agent 设计原则

```text
每个 Agent 只做一类事
每个 Agent 只访问必要知识库
不要让所有 Agent 都能查所有资料
不要让生活 Agent 查办公资料
不要让办公 Agent 查生活资料
```

第一阶段重点验证：

```text
Agent 能否绑定指定知识库
回答是否引用正确资料
办公和生活是否不混库
Agent 是否能明确说“不知道”
```

## 9. 模型设计

第一阶段需要两类模型：Chat LLM 和 Embedding。

### 9.1 Chat LLM

用于：

```text
问答
总结
Wiki 生成
Agent 推理
知识整理
```

可选：

```text
Claude
GPT
Gemini
DeepSeek
Qwen
Moonshot
腾讯混元
```

第一阶段建议使用外部 API 模型，不建议本地跑大模型。

### 9.2 Embedding 模型

用于：

```text
文档向量化
RAG 检索
相似内容召回
```

建议选择中文效果较好的 embedding 模型。

### 9.3 Reranker

第一阶段可不配。

当出现以下问题时，再考虑添加 reranker：

```text
能搜到，但排序很差
相关片段排在后面
答案引用噪音大
```

### 9.4 vLLM 的定位

vLLM 是开源大模型的推理服务框架，用于把 Qwen、DeepSeek、Llama 等模型部署成可调用 API。

本方案第一阶段不使用 vLLM，原因是：

```text
当前目标是先跑通 WeKnora 知识库闭环
普通 CPU 云服务器不适合跑大模型推理
vLLM 需要 GPU 服务器和额外运维
外部模型 API 更适合快速验证
```

后续在以下情况再考虑 vLLM：

```text
希望自部署开源模型
不希望敏感资料发送到外部模型 API
调用量很大，需要评估长期成本
想实验 Qwen / DeepSeek / Llama 等开源模型
```

## 11. 备份与导出设计

第一阶段至少做手动备份。

### 11.1 备份对象

```text

Wiki Markdown
问答日志
用户反馈
Agent 配置
WeKnora 配置文件
数据库 dump
```

### 11.2 备份频率

```text
每周导出一次 Wiki / 日志 / 配置
每周备份一次原始资料
重要调整前手动备份
```

### 11.3 备份位置

```text
本地电脑
移动硬盘
对象存储
私有 Git 仓库
```

目标：

> 即使服务器损坏、迁移云厂商，或者以后不用 WeKnora，核心个人知识和组织记忆也能迁移出来。

## 12. 手机端与未来入口设计

### 12.1 第一阶段手机端

```text
手机浏览器访问 WeKnora
添加浏览器收藏
必要时添加到手机主屏幕
```

### 12.2 第二阶段入口演进

后续可选升级：

```text
域名 + HTTPS
微信入口
WorkBuddy 入口
VPN / Tailscale
```

入口定位：

```text
WeKnora 自用入口：
  适合知识治理、Wiki 编辑、Agent 调试

微信入口：
  适合手机快速提问、轻量查询

WorkBuddy 入口：
  适合把 WeKnora 能力包装成日常 Agent 工作台
```

长期原则：

```text
核心知识资产留在 WeKnora / 可导出层
微信或 WorkBuddy 只做入口
不要把唯一组织记忆锁在入口平台里
```

## 13. 分阶段路线图

### 13.1 阶段 0：准备期，0.5–1 天


产出：

执行：

```text
拉取 WeKnora
```

产出：

执行：


```text

能引用

能回滚
```

执行：


产出：


根据使用情况决定是否升级：

```text

WorkBuddy 入口

Reranker
更细权限
```

## 14. 风险与应对

### 14.1 风险：HTTP 暴露公网

应对：

```text
强密码
最小端口开放
不上传高敏资料
尽快升级 HTTPS / VPN
```

### 14.2 风险：资料太乱导致效果差

应对：

```text
先少量低敏高质量资料
先用 00-inbox
每周整理
定义 Wiki 页面模板
```

### 14.3 风险：模型调用涉及隐私

应对：

```text
第一阶段不上传高敏资料
办公资料先脱敏
确认模型服务商数据政策
必要时后续切换私有模型
```

### 14.4 风险：知识库变成垃圾堆

应对：

```text
00-inbox 不作为默认问答源
每周整理 inbox
错答样本必须回流修正
定期删除过期资料
```

### 14.5 风险：手机端使用率不高

应对：

```text
先用浏览器收藏
如果使用频繁，再做微信 / WorkBuddy
不要一开始把入口集成复杂化
```

## 15. 验收标准

第一阶段完成后，至少通过以下检查：

```text
1. 电脑浏览器可以访问 WeKnora
2. 手机浏览器可以访问 WeKnora
3. 管理员账号可以登录
4. 未登录用户不能查看知识库
5. 数据库 / Redis / 向量库没有暴露公网
6. 能创建 5 个知识库
7. 能导入第一批测试资料
8. 能基于资料问答
9. 回答有引用来源
10. 办公和生活资料不会混用
11. Agent 能绑定指定知识库
12. 能导出或备份 Raw / Wiki / 配置 / 日志
```

## 16. 最终设计结论

最小可行方案：

```text
中国大陆云服务器
  +
Ubuntu 22.04
  +
Docker / Compose
  +
WeKnora
  +
公网 IP 临时访问
  +
账号密码登录
  +
5 个分区知识库
  +
5 个轻量 Agent
  +
外部 API 模型
  +
每周备份导出
```

第一阶段要验证的是：

```text
WeKnora 能不能成为个人知识底座
手机和电脑能不能方便访问
办公和生活知识能不能隔离
RAG / Wiki / Agent 是否真的能节省时间
数据是否能导出和迁移
```

第一阶段不解决所有问题，但必须为后续演进留出路径：

```text
域名 HTTPS
微信入口
WorkBuddy 入口
自动备份
更细权限
vLLM / 自部署模型
```
