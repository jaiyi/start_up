# 2. 把判断变成组织能力，难在哪里

[前一篇](01-什么是组织知识工程为什么要做.md)提出：组织反复为已处理过的问题查找资料、解释背景和确认适用性；知识工程要让上一轮判断成为下一轮工作的可靠起点。平台要解决的不是“怎么存更多文件”，而是让判断在不同的人和任务之间流转时，不丢掉依据、边界和责任。

## 先看判断如何在组织中流动

一条判断通常不是从“写知识”开始的，而是有人在工作中碰到问题：查资料、和同事对齐，请专家处理例外，最后在某个范围内作出决定。后来的人还要能发现它、判断能否沿用、在使用中指出不合适之处，再由有责任的人修订。

可以把循环简化为：**遇到问题 → 形成判断 → 保留依据和边界 → 在新任务中找到并核对 → 使用或请人处理 → 反馈变化 → 再确认。** 任何一段断掉，都不会有稳定的复用：存了却找不到、找到了不敢用、用了不知已过期，都只会把成本移到别处。

## 第一处断点：选什么留下、留下到什么程度

组织每天产生的信息远多于可长期维护的判断。临时联系人、当前工单状态、闲聊中的建议和经确认的处理原则，不能进入同一种“权威知识”池。决定是否投入，应先看重复频率、重新确认的代价、误用风险，以及能否说清适用范围；一次性问题可能只需及时解决，不必做成资产。

这里需要区分**资料、待确认说法、经确认的知识、可重复执行的步骤**。Agent 从纪要提取出的结论可以是待核实的草稿，不因表达通顺就成为正式知识。只有步骤稳定、边界与失败处理清楚、可测试，才值得进一步考虑受控的 Skill；“常被问到”不等于“允许自动执行”。

## 第二处断点：新任务里如何判断“这次适用吗”

假设旧纪要说某类项目按 A 清单办理，现有模板却是 B 版。这不是一个搜索排序问题：两份材料可能针对不同情境，也可能已有一份失效。只展示一个答案，会掩盖使用者真正需要知道的东西——来源、确认者、适用条件、例外与当前版本。

平台应能把“有资料可参考”“AI 整理了可能的说法”“某人确认了某版本结论”清楚地区分；员工看不清证据或没有查看权限时，不能用看似完整的摘要绕开访问控制。遇到缺条件、冲突或过期迹象，可信的结果可以是“目前无法确认，下一步找谁”，而不是编一个统一口径。

## 第三处断点：谁有权判断，谁有能力维护

使用者想快点拿到答案；专家却要核对材料、处理例外、确认修订，还要完成本职工作。若每次提问都形成审核任务，团队效率可能只是向专家转嫁了负担。专家担心被替代，也可能是在担心自己过去的判断被系统无限泛化，出了问题仍要由自己负责。

必须让判断权与责任一致：专家能限定范围、要求补证、暂缓、拒绝或撤回结论；草稿变化后不能继续沿用旧确认。维护压力、无人接手或长期积压由业务负责人决定投入、缩小范围或保留人工咨询。产品可以让负担可见、把重复解释变成一次可复用的工作，不能凭空创造人手，也不能拿个人提问与处理速度做绩效排名。

## 第四处断点：使用与纠错有没有发生在工作里

员工遇到问题时是在完成任务，不是在参加“知识建设活动”。如果必须另开后台、先选分类再写一篇文档，他们大概率继续发消息问熟人。使用入口要让人在具体问题旁看到已有判断或待确认信息；指出“资料冲突”“这次不适用”“规则变了”也应比写完整知识容易。

反馈之后还要能回访：有人受理了吗？是改善展示、修改结论，还是新问题需要当前业务决策？“已收到”不等于“已解决”。培训与分享有助于形成共同语言，但替代不了低负担的入口、明确的责任人与可见的处理结果。

## 第五处断点：有没有学到什么，而不只是数了多少

发布数、问答次数和培训人数只能证明发生过活动，不能证明工作变好。初版要能区分：找不到已有内容；找到但看不懂或不敢用；使用后发现不适用或过期；错误根本来自选错了要沉淀的问题。不同症状对应不同的修改，不能都归为“知识不够多”。

将来有真实使用时，才有条件对照同类任务：员工从提问到可用判断的耗时、必要人工确认是否正确发生、专家新增维护时间、误用和返工。没有反馈不等于没有错误；样本不足或无法观察业务结果就说“还不知道”。目前这些是**准备观察的信号，不是已经测得的效果**。

## 平台该统一什么，领域又必须自己决定什么

上面的断点遍布各领域，但处理每个领域的具体规则不同。产品初版可先把分工划清：

| 参与者 | 应承担的事 | 不应替别人做的事 |
| --- | --- | --- |
| 平台 | 让来源、权限、适用范围、确认状态、版本、维护责任和反馈去向可表达、可追踪；提供跨场景一致的使用方式 | 规定所有领域“正确答案”是什么，替人批准业务行为 |
| 领域人员与业务负责人 | 决定哪些判断值得留下、内容是否成立、谁有权确认和维护；对当前业务决定负责 | 把未经确认的材料当作自动可用的正式答案 |
| Agent | 在授权范围内查找、比较、整理、指出缺口并帮助呈现 | 自行确认结论、越权查阅或扩大执行权限 |
| 原业务系统 | 保留实时状态、任务办理、业务审批与执行记录 | 依靠知识条目替代其当前状态与责任链 |

Workbench 是平台给人处理这些判断与反馈的工作界面，不是知识工程的全部。平台性也不是“同一模板强制覆盖所有领域”：如果每接入一个新领域都要重造来源、确认、反馈和权限机制，说明共性还没找对；如果统一过度，抹掉领域例外，则平台可能更危险。先以一套可适配机制设计初版，再观察不同场景是否真的能复用它。产品蓝图见[下一篇](03-Workbench如何解决.md)。
