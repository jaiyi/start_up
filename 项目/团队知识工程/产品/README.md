# 产品论证：先回答为什么，再决定怎么做

本目录回答团队知识工程的**用户问题、价值主张、资产判别、日常使用、共同认知与人的成长**，然后用具体任务检验 Workbench 是否值得建设。它不是已完成的用户访谈报告，也不是第二套系统规格。当前未选定实际试点团队、任务、人工基线或收益目标；文中的“项目交接材料核对”均为**假设性贯穿示例**，不代表任何团队的现行制度或真实试点结果。

## 建议阅读顺序

1. [用户问题与价值主张](01-用户问题与价值主张.md)：谁有问题、替代方式是什么、为何值得投入、何时应该停止。
2. [日常知识与技能判别](02-日常知识与技能判别.md)：在真实工作中，哪些值得留成知识，哪些才值得做成 Skill。
3. [日常工作嵌入与正反馈](03-日常工作嵌入与正反馈.md)：从原任务发现问题到有人修复、下次工作真的更顺畅。
4. [共同认知与试点运营](04-共同认知与试点运营.md)：通过培训、使用、分享与复盘，让贡献和治理不靠一次性运动。
5. [Workbench 体验与验证](05-Workbench体验与验证.md)：沿用户旅程设计屏幕任务与可用性验证，而非只列功能页。
6. [专家自主权与共同成长](06-专家自主权与共同成长.md)：把专家裁量、贡献认可、维护容量、员工成长和非监视式管理变成可检验的产品机制。

## 文档如何决策

- **本目录是产品论证输入**：记录拟解决的问题、可选解法、用户任务、价值假设、交互假设和试点要证伪的问题。带“拟”“假设”“建议”的机制尚非确定需求；没有访谈或实测数据就不写成用户已经认可。
- **[方案总览](../方案/00-方案总览与关键决策.md)是当前范围与权责决策摘要**；[资产模型](../方案/03-知识资产与生命周期.md)、[治理机制](../方案/04-角色、治理与运营机制.md)、[工作台信息架构](../方案/09-工作台信息架构与核心对象.md)分别约束正式资产、审核责任和 IA/状态；[MVP 验收](../方案/08-MVP实施、验证与验收.md)规定开发与成熟度门禁。产品论证若提出不同做法，应标为待决策差异，不能暗中覆盖上述方案。
- **[验证材料](../验证/README.md)回答外部能力的证据问题**。产品上的“用户看到了发布”必须以特定版本的 Git/Provider 读回为依据；真正使用和业务改善还需另行验证，不能从发布/安装推导。

## 一个贯穿示例（假设，不是业务事实）

某团队在日常**项目交接材料核对**中，执行者反复询问“该用哪版清单、特殊情况找谁确认”；贡献者可能拿到一份经授权的旧纪要和现行模板，先留下版本冲突候选，steward 核验适用范围，再考虑形成带来源的知识；若核对流程经常重复且输入、输出、例外与人工确认点稳定，再考虑把流程建模为 Skill。此处不预设实际清单内容、审批规则、节省时间或系统接入。若试点业务侧选定别的场景，替换示例和观察脚本，而不把本例当需求来源。

## 从论证到建设的门槛

先由业务流程 Owner 指定单一低风险高频场景、第一用户、第一受益者、审核责任人与业务结果确认者；观察他们目前在何处查找、谁解释规则、如何纠错，并留下基线、样本和权限说明。再比较“只把现有资料整理好”与“增加 Workbench”的成本和收益；只有增量价值和持续维护能力有证据，才扩大建设范围。未知外部集成、低反馈覆盖、小样本或无人负责复核时，结论保持待验证或暂停。
