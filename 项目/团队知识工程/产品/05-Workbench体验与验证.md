# Workbench 体验与验证：从任务到屏幕

本页是**产品交互意图与验证脚本**，不是已实现的 UI、视觉设计稿或第二套信息架构。导航、对象字段、角色门禁、低保真线框、发布/未知/失败状态的权威规格见[工作台信息架构与核心对象](../方案/09-工作台信息架构与核心对象.md)；技术成熟度见[MVP 实施与验收](../方案/08-MVP实施、验证与验收.md)。本页先问“用户要完成什么、看到什么才敢继续”，再决定界面如何证明这一点。

## 1. 三个入口，不要把 Workbench 当全部日常工作

1. **原任务的使用入口**：执行者在既有文档/检索/业务流程中找带来源的内容；是否能从该处就地反馈依赖试点接入。若无接入，提供经授权的临时检索/反馈入口并注明该限制。Workbench 不复制 Harness Session 或生产业务操作。
2. **Workbench 首页**：给贡献者、steward、审核者看“需我处理、等待谁、最后确定到哪一步”，其次才是“从资料创建知识”“从工作流创建 Skill”。首次进入要解释不同入口的产物及谁来确认；无权限、无绑定、列表读取失败不能都写成空白。
3. **已发布资产与反馈**：让被授权的人回查正式版本、来源/适用范围、复核日期、发布证据、可验证的使用范围以及问题处理路径，而非浏览一张资产数量排行榜。

假设性贯穿任务：交接核对时发现新旧模板冲突；消费者留下最小引用；领域专家回访工作台核对版本并提交知识修订；审核人退回过一次；再次审核/读回后消费者在下次核对中验证。它用于设计测试，不意味着团队已有产品原型或真实问题样本。

## 2. 用户旅程与应呈现的决策线索

| 时刻 / 屏幕 | 用户要问的问题 | 首屏可见信息与主要动作 | 下一步及不得误导之处 |
|---|---|---|---|
| 消费入口：找答案 | “适用这次任务吗？” | 题目、来源、适用/不适用范围、版本和最近复核情况；找不到/错误/过期的反馈入口（接入未知时标注临时入口） | 引用不适用时回原任务人工判断；不能显示草稿为正式答案 |
| 首次进 Workbench | “我为什么要用？是整理资料还是描述工作方式？” | 两个启动动作附一行期望产物和责任，当前团队/资产空间绑定状态；示例候选与审核路径；权限申请/联系责任人 | 不要求先学 Git；无授权不可创建跨团队会话 |
| 创建知识会话 | “旧纪要和新模板冲突，应该留下什么？” | 材料来源、原文定位、事实/推断、冲突、适用范围、待确认人；保存/暂停与阻断项 | 最小保存先保证问题不丢；待确认不能提交正式发布 |
| 返回首页/会话 | “上次做到哪一步、谁在等我？” | 上次阶段、草稿修订、保存时间、需本人处理/等待他人、原证据入口 | 点击“继续”回原上下文；本地未保存与已保存分开 |
| 审核退回 | “具体哪里不对，如何修？” | 被退回的修订、差异、审核人意见/原因、来源与范围、返回原会话动作 | 修改产生新修订并重走门禁；旧批准不自动延用 |
| 提交后等待/未知 | “版本已经对别人可用了吗？” | Git MR/CI、人工审核、指定版本 Provider 操作、最近已证实步骤、责任人、下一次检查/对账入口 | `queued` 和 `unknown` 不显示绿色已发布；禁止盲目重复提交 |
| 资产发布详情 | “谁确认、哪一版、哪里能用？” | 正式版本/commit、知识索引/检索或 Skill release/digest 读回、权限/复核日与交接状态 | 发布与下游安装/加载/真实任务执行分开展示 |
| 反馈队列与再消费 | “问题有人处理吗？修好后仍适用吗？” | 候选状态、关联旧版、新版修订/读回、处理人、误报/延期理由与回访时间 | 反馈关闭不等于业务改善；真实后续任务由受益者/结果 Owner 另行确认 |

屏幕层的空、保存中、未保存、等待、驳回、失败、未知、成功与权限不足的布局和按钮条件不要在此重复造规范，按[方案 09 的逐屏线框与跨屏状态](../方案/09-工作台信息架构与核心对象.md#12-屏幕规格与低保真线框设计说明)实现。文案始终回答：**影响哪个对象和版本 → 已证实到哪里 → 为何还没完成 → 谁能处理 → 我现在能做什么**。

### 2.1 原任务查找与反馈的概念流程（非现有集成）

下面只说明消费者需要完成的动作；实际入口可能是经授权的试点检索页或人工登记，不代表已嵌入 IM/业务系统。跨屏跳转、自动携带引用及回访通知均待目标系统授权与契约验证。

```text
原任务：查交接规则（当前任务不离开原业务系统）
  → 有结果：显示正式版本/来源/适用范围 → [查看依据]
       ├─ 不适用/过期 → [报告问题]：类别、资产版本、最小脱敏引用
       └─ 可用 → 回原任务执行；是否改善留待业务结果验证
  → 无结果：显示“当前授权范围未找到” → [报告缺失]：问题描述/来源线索
  → 无权限：显示“无法查看该资产” → [申请授权/找资产 owner]
       （不展示敏感标题、片段，也不按无结果提交内容纠错）
  → 报告提交：返回可追踪编号与“待核验/责任角色/回访入口”
       → 回访：已分流/待确认/延期或拒绝及原因/新版本读回
       → 没有真实任务结果时只显示“修订已生效，效果尚未验证”
```

若消费者无权查看原资产版本，只能登记“权限/检索问题”和最小脱敏线索，由授权责任人核对版本；不能借反馈入口绕过 ACL。结果、失败、权限拒绝、无法确认提交结果分别呈现；提交超时先查询原请求编号，不能诱导重复创建。此流程中的反馈提交/回访若试点无线上能力，先由授权人员登记并回传编号，显式标为人工路径。

## 3. 两段“最小成功”路径

**知识贡献者的第一步**：从一份获授权的纪要/模板只选一个有问题的条目，标明来源和待确认人，保存后离开；回来能找到它，看到仍为候选而非“已入库”。这条路径可以先用脱敏 fixture 测理解和操作摩擦。后续人审、Git 合并及 WeKnora 读回是另一段成功，不以“保存完成”替代。

**消费者的第一步**：在实际任务能看到带适用范围和来源的批准版本；若不适用，能用极少动作留下问题，获得“待核验/负责角色/回访位置”。若只能通过演示入口完成，记录为受控试用，而非已融入原工作。业务层的成功需再次使用和与人工基线比较。

若试点只测首用却没人回访待办、核验反馈或在下次任务再用，产品即使看起来顺滑，也尚未论证“知识工程”持续有效。

## 4. 原型与可用性验证任务

实际试点场景由业务侧另行确认。先用纸面/低保真原型测理解，再用具备权限与读回证据的可操作原型测流程；不可用模拟状态宣称真实 Provider 完成。每个任务留记录：角色、任务前提、资料授权/版本、预期动作、实际操作/犹豫点、求助、用时、错误、是否完成、证据、后续复访。

| 脚本 | 给受试者的任务（以虚构材料起步） | 观察与判定 |
|---|---|---|
| U1 首次判断 | “现有两份交接模板冲突；你要让下次同事查到可靠说法。你会怎么开始？” | 能解释为什么先保存候选、选择知识入口、找到来源和责任人；不把旧纪要直接认定为规则 |
| U2 保存与回访 | “先离开，稍后继续上次那条候选。” | 找回原会话、未解决冲突及保存修订；不会误以为已发布或再创建重复资产 |
| U3 审核退回 | “审核者指出适用范围不完整，修订后重新提交。” | 能看出被退回的是哪一修订、为什么退回，按新修订重新提交审核；审核者辨认差异 |
| U4 检索与反馈 | “执行者找不到适用版本，或者发现已发布规则过期。” | 能找到来源或注明查不到，留下最小引用；不会复制敏感原文；能回访责任人和状态 |
| U5 异步与未知 | “索引/SkillHub 提交超时，当前结果无法确认。” | 识别最后可信步骤、负责人及对账入口；不会连续点击发布或把未知称失败/成功 |
| U6 何时用 Skill | “有人说把整个交接流程做成 Skill。” | 能说明触发、输入/输出、例外、人工节点、测试和维护成本；不把静态清单直接当可自动运行能力 |
| U7 创建与测试 Skill | “用已批准的核对知识版本和脱敏样例，建立一个对稳定交接流程给出结构化检查建议的 Skill 草稿；一条边界样例失败了。” | 能从第二启动动作创建独立 Workflow Draft，填写触发/输入/步骤/例外/人工节点与期望输出；找到固定知识依赖、测试差异和失败原因，修订后复测并预览提交与审核门禁；不会把能力声明当实际授权、把试跑当正式发布 |
| U8 再次使用和结果 | “一周后同类任务出现，检查新版本并报告是否省了反复沟通。” | 能核对实际版本、记录真实任务结果和维护时间；样本/覆盖不足时不报告改善 |
| U9 专家拒绝与补证据 | “Agent 将旧纪要当成现行规则，来源冲突尚未裁决。” | 授权 steward 可拒绝或待核验、要求补来源并写适用范围；页面保留其理由与下次复核，不会默认确认或直接改已发布版本 |
| U10 容量不足与归因纠错 | “三条相似反馈积压且你不是该领域责任人；另一条已发布修订错误地把你标为确认者。” | 能在有权范围内合并线索并转交/升级或延期、注明原因与新责任人；本人能申请纠正错误归因，不靠清零待办伪装解决 |
| U11 团队资源决策 | “这个月看似发布很多内容，但反馈覆盖不足，专家复核耗时上升。” | 授权管理者能看到任务级基线、覆盖率、未知和维护负担，选择缩小范围/分配工时/暂停并记录理由；无法找出员工速度榜或反推单人的消费路径 |

观察至少跨第一用户、受益者、审核者和结果 Owner；角色兼任要分别执行对应任务。用**完成与否、误解类型、操作步数/用时、求助和二次使用**描述体验；不预设“3 步完成”“满意度 ≥X”之类未经基线确认的指标。U1–U7、U9–U11 可先用脱敏 fixture 或权限原型评估理解、拒绝/转交/归因纠错与管理摘要的可用性及隐私，U8 的真实价值必须在业务侧认可的样本、窗口和基线下观察。具体的人类裁量、维护容量与非监视要求见[专家自主权与共同成长](06-专家自主权与共同成长.md)。

## 5. 产品尚未决定的问题

- 执行者真正的入口在哪里，是否允许从原任务携带资产版本和脱敏引用？若无 API/授权，先试点临时入口，切勿宣称已集成。
- 首页待办是按“本人需做”还是“当前团队风险”排序最有效？在真实权限下测试，不能泄露别的团队资产。
- 对首次使用者，知识/Skill 两种启动动作是否过早？若误选频繁，可加入选择引导，但不改变正式会话/审核门禁。
- 何种证据与解释能让审核者快速判断来源、推断和适用范围，而不增加审核负担？
- 分享案例/复训能否改变实际分类和纠错行为，还是必须先修正入口和责任链？

试点失败不等于立即加功能：先确认是否选错了任务、缺少内容维护人、证据不可用，或用户只是被迫多填一次表。把实测问题返回[用户价值主张](01-用户问题与价值主张.md)、[共同认知运营](04-共同认知与试点运营.md)与方案验收，而不是把低保真线框视为终版产品。
