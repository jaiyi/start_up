# 共同认知与试点运营

团队对“知识”和“技能”看法不一时，先通过**真实、低风险任务的共同演练和回访**达成可用共识，而非要求大家先学完一个理论体系。培训是试点服务的一部分，不另建培训平台；签到、测验分数和分享场次不等于业务价值。分类与边界以[日常知识与 Skill 判别](02-日常知识与技能判别.md)为练习依据，正式职责与治理以[方案的角色与运营机制](../方案/04-角色、治理与运营机制.md)为准。

## 1. 首期要达成的共同语言

每位试点参与者至少能用自己的任务回答四句：

1. **我在做什么工作**：现在要核对、决定或产出什么，若做错谁承担后果？
2. **我要留下什么**：这是来源材料、待核验候选、可引用知识、可建模 Workflow、可测试 Skill，还是该留在业务系统的实时事实？
3. **谁能确认**：来源是否获授权，何种适用范围/例外需要 steward、Skill owner 或审核者确认？
4. **下次怎么看出有用**：同类任务能否少查、少问、少返工？谁记录人工基线和维护成本？

贯穿演练可用**虚构的项目交接核对材料**：一份旧纪要、一份现行模板、一次例外和一条模糊报错。学员要判定旧纪要为何不能直接成为正式规则、临时联系人为何不能入普适知识、什么时候先留 Workflow 而非直接造 Skill。演练使用虚构或脱敏数据，不拿生产敏感材料做公共分享。

## 2. 分角色上手：教的是动作与边界

| 对象 | 10–20 分钟的最小演练（时长为建议，待试点调整） | 演练后应能说清/做出的事 |
|---|---|---|
| 一线执行者/第一受益者 | 用一条带版本引用完成核对；试一次“找不到/来源不适用”的最小反馈 | 何时相信引用、何时找人确认；反馈不等于自动改规则；原业务任务仍由原系统完成 |
| 贡献者/第一用户 | 从授权材料里只提一条候选，标注来源、推断、适用范围并暂停/恢复 | 保存候选与正式发布有何不同；遇到冲突可以待确认，不必须当天“生产知识” |
| steward/Skill owner | 对同一例子分别做知识确认、Workflow 步骤判断、Skill 可测试性判别 | 知识责任与执行契约责任不同；允许拒绝/延期并留下理由 |
| 审核人 | 看草稿差异、来源与例外；模拟退回并看修改后重新审核 | 人审不是确认 Agent 自信度；旧修订批准不等于新修订批准 |
| 推动者/结果 Owner | 为一类任务定义人工基线、维护预算、停止条件 | 索引/安装/培训人数不是结果；未知和低反馈覆盖率如何解释 |
| 平台/运营支持 | 模拟 Provider `unknown`、越权或无人认领反馈 | 读回/对账、权限和升级归谁；不能让用户重复点击发布试运气 |

角色可兼任但演练记录必须分别覆盖其责任。若工作台尚无可操作原型，使用纸面任务卡或低保真线框；此时只验证概念理解，不报告产品易用性通过。

## 3. 培训、使用、分享三段循环

| 节奏（建议） | 形式与最小产物 | 责任与安全边界 |
|---|---|---|
| 入组时 | 一页式任务卡：目标、来源/版本判断、最小反馈、应找谁；记录参与者的困惑和预测 | 试点推动者确定场景，领域专家核实示例，平台不替业务判断事实 |
| 第一次真实使用后 | 针对一次找不到、候选冲突或审核驳回的短答疑；同步修改示例或入口文案 | steward/Skill owner 判断内容，产品负责人观察摩擦；不得在公开群粘贴敏感来源 |
| 每周复核时 | 用一条“从反馈到修复”或“为什么拒绝沉淀”的脱敏案例分享，连同维护耗时 | 资产 owner/审核者审阅引用与 ACL；反馈若仍未闭环，注明“待验证” |
| 每月业务复盘 | 展示原任务结果、覆盖率、维护成本和失败案例，决定继续、缩小、调整或停止 | 业务结果 Owner 确认指标和基线；避免挑选单个成功演示推广全团队 |

**分享卡片模板**（在已有文档/会议里即可）：

```text
任务：<一类任务，不贴真实业务原文>
发现：<找不到/错误/例外/重复劳动>
当时做了什么：<引用或最小反馈，标注人工登记/真实事件>
证据：<经权限允许的来源、资产版本、审核/读回状态>
下次任务结果：<实测结果；没有就写尚未验证>
维护成本与教训：<确认、审核、回访耗时；错误分流/不入库原因>
可分享范围与责任人：<团队/资产 ACL，复核日期>
```

不要以排行榜鼓励无来源上传、刷反馈或自动生成 Skill。贡献认可首先是让贡献者看见问题被处理、消费者复用及结果反馈；是否设置工时保障或其他激励，需要试点 Owner 依据维护负担与组织制度决定，不在本页预设积分或奖励。

### 从使用中形成专家主导的学习路径

Workbench 可在本人授权视图里提供自愿的下一步练习：一线员工先练习判断来源与不适用范围，再从一个脱敏错例提出可核验反馈；领域专家带着同事说明**为何拒绝或限制一条 Agent 建议**，示范如何处理例外而非展示“产出了多少知识”；有意承担 Workflow/Skill 职责的人再学习固定依赖、边界测试和人工批准。分享卡要注明提出线索、整理、核验、审核与后续纠错由不同人完成，不把案例全部归功于 Agent 或单一作者；纠错与拒绝也是值得复盘的贡献。

管理者在月度复盘中应明确重复劳动减少后拟投入哪类改进/培养工作，并留给专家相应的复核时间；若无时间预算或员工不愿参与，先缩小试点。产品只提供按授权资产追踪贡献、纠错申请与本人学习记录的体验假设，不与人事系统自动连接，也不从这些记录生成绩效分数。设计细节与失败信号见[专家自主权与共同成长](06-专家自主权与共同成长.md)。

## 4. 如何判断“形成共识”，何时改变教法

观察同一批参与者能否在不被提示的情况下：正确区分原始材料/候选/正式知识/Workflow/Skill；为冲突找到责任人并允许不发布；找到实际版本与来源；提交不泄露原文的最小反馈；指出发布、实际使用与业务成功的区别。记录完成情况、错误类型、求助位置、用时和复访情况，而不是只问“满意吗”。

失败信号：演练通过却在真实任务中仍找旧模板；贡献者不会暂停，误把候选当正式事实；审核人只能靠私聊找来源；反馈长时间无人接；专家维护时长超过推动者许可。如果在这些情况下反复加培训仍无改善，要改入口、样本、责任安排或缩小试点，不能把所有问题归因于“用户没学会”。

与[任务观察及验收](../方案/08-MVP实施、验证与验收.md)同步留证：首次理解、回访、纠错、驳回和未知状态须用逐步操作记录或经授权的脱敏录屏验证；真实业务收益另需业务 Owner 的基线对照。
