# 日常工作嵌入与正反馈

核心不是要求每个人每天进入“知识建设”页面，而是在完成本来要做的事时，遇到缺失、冲突和重复判断，**少走一步就能留下可核验线索**；后续由有责任的人确认、发布并在下一次任务里验证。这里描述的是拟验证的服务体验，不承诺 IM、会议系统或业务系统已完成接入。正式审核/发布以[端到端工作流](../方案/02-端到端知识工作流.md)、[治理机制](../方案/04-角色、治理与运营机制.md)和[实施验收](../方案/08-MVP实施、验证与验收.md)为准。

## 1. 用户是在什么时候想到这件事的

| 原任务触发 | 当事人的一句话 | 当次最小动作 | 不强迫当事人做什么 |
|---|---|---|---|
| 查规则/答疑 | “这条说法是哪一版、适用我吗？” | 查来源/范围/版本；查不到就提交“找不到”与问题引用 | 不要求判定该建哪个知识目录 |
| 会后处理纪要 | “这次决定跟旧模板不一样” | 在已授权材料里标出决定、差异、待确认人，保存候选 | 不把整份纪要自动入正式知识 |
| 实际执行发现例外 | “清单没覆盖这种情况” | 保留任务侧脱敏引用和例外类别，请有权者确认 | 不让反馈代替当前业务审批或运行时批准 |
| Skill 结果不符合预期 | “输入没问题但输出漏了条件” | 附固定 Skill 版本/digest 与最小结果引用 | 不在反馈中复制完整 Prompt/业务原文 |
| 定期复核或规则变化 | “这份内容可能过期” | 标记原版本、触发来源、影响范围和 owner | 不自动把所有旧资产定为错误或立即覆盖 |

试点前先观察这些动作现在哪些系统发生，再选最低摩擦入口。如果现有应用暂不能集成，允许授权人员通过 Workbench 临时入口/人工登记来源；标明“人工登记、未核验真实消费”，不能写“用户已在原系统一键反馈”。

## 2. 一条服务蓝图：假设的项目交接核对

| 时刻 | 执行者/消费者看到什么 | 背后的人负责什么 | 可核验证据与失败处理 |
|---|---|---|---|
| 当次查找 | 打开可用的检索/试点入口；看到答案、来源、适用范围、版本；找不到时记录最小问题 | 当前交接业务仍由执行者和现有系统处理 | 找不到/无权限/版本不明分别显示；无需拿草稿充答案 |
| 当天或下一次进入 | 贡献者从待办找回问题，关联授权模板与纪要，保存候选，可暂停 | steward 对事实、冲突、适用范围和受理负责；无法认领则升级到 asset owner | 可见“已保存/待核验/责任人/下次检查”，不是“已经修复” |
| 每周复核 | 贡献者/审核者看到待处理项与原任务引用 | steward 处理知识问题，Skill owner 处理步骤/契约，平台 owner 处理权限、检索和版本故障 | 重复报告可合并但保留来源；误报、拒绝、延期均记录理由和回访点 |
| 审核与发布 | 贡献者看到差异、测试、审核和读回的各自进度 | 有权人员审核、Git 合并，Worker/Provider 读取指定版本并对账 | CI/人工门禁、Git commit、知识索引/检索或 Skill release/digest；`unknown` 时禁止报“已生效” |
| 下次同类任务 | 执行者看到适用的新版本并判断是否解决；若仍不适用继续反馈 | 业务结果 Owner 将同口径任务与基线比较，专家评估额外维护成本 | 有真实引用/消费与结果才谈采用/价值；低覆盖率或无结果记未知 |

这里的“当天/每周”是**建议的服务节奏**，不是系统承诺的 SLA；由试点业务 Owner 指定可用的人手、到期升级规则和停止条件。业务结果、生产写入和 Harness Session 保持在原系统，Workbench 只管候选、批准版本及最小引用。

## 3. 正反馈的阶梯，而不是一条绿色完成条

| 用户能看到的反馈 | 这一步实际证明了什么 | 还没有证明什么 |
|---|---|---|
| “找到了有来源、范围与版本的内容” | 有机会完成一次核对 | 对当前任务确实适用或减少了时间 |
| “问题已保存，待某责任人核验” | 线索未丢，可回访，有下一步 | 内容是事实、问题已解决 |
| “候选被确认/审核通过” | 对某份草稿某个修订已明确负责 | 指定版本已发布可检索 |
| “指定版本发布并读回、检索/固定包验证” | 技术上可供授权下游消费 | 有人使用，业务任务完成 |
| “真实任务使用/反馈且可归因到版本” | 出现采用或可追查的问题 | 一定带来收益；没反馈也可能是没接入 |
| “业务 Owner 确认同类任务改善，成本可接受” | 在该场景与观察窗口支持继续试点 | 全团队普适有效或未来无需治理 |

`queued`、`publishing`、fallback、`unknown`、无回执、反馈覆盖不足都不能用绿色“成功”掩盖。首次使用的正反馈最好来自可靠答案或不确定问题有人接手；长期正反馈来自**下次任务少查/少返工**且维护没有吞噬收益，而非知识条数、培训签到数或安装数。

## 4. 不断新增、迭代、治理为什么不会变成第二份工作

- **发现与确认分工**：消费者只标一个缺口，不担任 taxonomy 管理员；贡献者整理素材，steward 判断事实/过期与适用范围，Skill owner 判断流程/测试，审核者决定是否批准。平台排查检索、授权和版本故障，不能让错误全部变成“用户知识不完整”。
- **定期队列而非随时催办**：根据下一复核日期、使用中暴露的问题、规则变更和重复反馈排队，按影响范围优先处理；小修订仍走同一审核链。看板要有 owner、期限、上次进展和“拒绝/延期”出口，避免候选无限堆积。
- **回到原工作验证**：修订和发布之后邀请原报告人在下一次同类任务核对，若没有后续使用就记“尚未验证”；不主动发送可泄露敏感资产的广域通知。保留旧版本/问题引用以便复盘与回滚。
- **有容量和停止条件**：每周记录专家/审核投入、积压、超期/无人认领及误报比例；若问题多而人力不足，先缩小目录或试点，不将积压解释为成功发现了更多知识。

试点清单：一个明确的高频低风险任务、当前入口与人工基线、授权材料、第一用户/受益者名单、steward 与审核人、复核时段、低覆盖率展示与故障接管方式。只有真实使用和责任容量同时成立，才将该方式推广。相关实测任务见[Workbench 体验与验证](05-Workbench体验与验证.md)。
