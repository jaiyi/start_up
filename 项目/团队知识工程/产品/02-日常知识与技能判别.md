# 日常知识与 Skill：如何判断值得沉淀什么

本页是**普通用户的判别指南**，不是对正式资产 schema 的替换。正式 Knowledge、Workflow、Skill 的对象与状态仍以[资产模型](../方案/03-知识资产与生命周期.md)和[Workflow 到 Skill](../方案/10-Workflow到Skill的生成、测试与发布.md)为准。刚发生的事情、模型生成的摘要和同事的经验，都可以成为候选，不自动成为“团队已批准的知识”。

## 1. 从正在做的任务而非文件格式出发

- **原始材料**：会议纪要、聊天记录、邮件、模板、工作产物；它们证明“有人在某时说过/做过”，不保证现在仍适用。
- **日常工作中值得留下的知识**：能被下一位同事再次查到和核验的事实、规则、决定、适用条件、例外或已复盘案例；有来源、责任人、有效范围和复核触发条件。一个操作清单中的稳定判断依据是知识，未经核实的一次口头说法只是候选。
- **Workflow（工作流草稿）**：用户如何完成一类任务的描述，包含触发、输入、步骤/判断、人工节点、例外、产出与完成标准。即使有 SOP，它也可能尚未稳定或无法自动化。
- **Skill（可发布能力包）**：对足够稳定、重复的 Workflow，定义边界、固定知识依赖、输入/输出契约、必要工具和权限请求、脱敏测试、版本及回滚的受控执行能力。不是“一段 Prompt”，更不是绕开人审去自动操作业务系统。

动态工单状态、实时测量值等**业务事实**应留在其业务系统；个人偏好可留个人工作笔记；未获授权的会议原文和敏感文件不得因“有用”就进入共享资产。Knowledge 回答“在何条件下知道什么、根据什么”；Skill 回答“这类任务如何依约执行、何时停下来问人”。

## 2. 五问分流：先做最小正确动作

```text
在原任务中发现一条信息/一种做法
  ├─ 无权分享、涉及敏感原文或无法定位来源？
  │    → 留在原系统/申请授权；只登记脱敏的问题类型，不上传正文。
  ├─ 仅一次性、短时动态状态或私人偏好？
  │    → 回写原业务系统/个人笔记；不建立正式知识资产。
  ├─ 下一位同事也需要核验的事实、规则、决定或例外？
  │    → 留来源、适用范围、责任人 → Knowledge Candidate → 人工核验/审核。
  └─ 反复执行一类任务且步骤与成功条件可写清？
       → 先形成 Workflow Draft；如果例外可控、收益足够、能测试/回滚，
          再建设 Skill（固定已批准的知识依赖）；否则保留工作流/人工清单。
```

不必一开始就做对所有分类：消费者只要指出“找不到/可能错/版本不符”，贡献者可以保存候选，steward/Skill owner 分流。**没有证据时留下待确认，比把不确定内容变成正式答案更有价值。**

## 3. 用同一个假设场景判别

假设性“项目交接材料核对”，不代表真实团队制度：

| 发现 | 先留下什么 | 为什么还不能直接发布 |
|---|---|---|
| 旧纪要写“使用 A 版清单”，现行模板显示 B 版 | 两份材料的授权来源、时间、原文定位、冲突点和需要确认的人；进入知识候选 | 旧纪要可能是当时适用而非当前规则；要有人确定生效范围及替代关系 |
| 一次具体项目的负责人正在休假 | 在原项目/业务系统更新联系人或找替代责任人 | 属于动态个案，不能写成普适团队规则 |
| 领域专家确认“某类交接需要两项凭证，特殊情况升级审核” | 经确认的来源、适用对象、例外、owner/复核日，可提交 Knowledge 草稿 | 正式发布还需 Git、CI、人审、WeKnora 对指定版本读回 |
| 操作员每周按同样步骤收集材料、检查缺失、出清单 | Workflow 草稿：输入、顺序、判断、遇到例外时谁接手、输出和完成条件 | 频繁不等于适合自动化；仍要看边界、风险、测试和维护收益 |
| 流程在多个脱敏样例中稳定，且例外有人审 | 可提出 Skill 草稿、固定知识版本、契约、测试与权限需求 | 测试通过不等于实际业务成功；发布、交接、运行都各需证据 |

内容看起来像步骤但只是告诉人“如何核对”的静态清单，可以先作为带适用范围的知识；需要根据输入稳定地产生结果并处理例外时，才考虑 Skill。**一项知识可被多个 Skill 依赖，一项 Skill 也可引用多项固定版本知识**；不要复制正文制造两套真相。

## 4. 候选进入治理的最小信息

消费者的报错只要求：发生在什么任务/入口、看到的资产与版本（能核验时）、问题类别、可授权的来源引用；可不知道该归 Knowledge 还是 Skill。贡献者/owner 整理时再补：适用与不适用范围、事实与推断分界、敏感等级、待确认人、复核日期。Skill 提案另需稳定触发/输入/输出、人工节点、例外、风险、代表性和边界样例、何时停止执行。不能提供这些信息时允许暂停和延期，记录原因与下次复核时间。

| 何时不要升级 | 更安全的下一步 |
|---|---|
| 来源互相矛盾，领域责任人无法确认 | 保留冲突候选，提示暂不引用旧说法；找 steward 裁决 |
| 规则有效期短、按实时状态变化 | 查业务系统的当前状态，只把稳定的判读原则写成知识 |
| 很少重复、每次依赖大量主观判断 | 保持人工作业和可引用清单，积累例子后再评估 Workflow |
| 流程需要高风险操作或不可测试权限 | 留下人工批准和业务系统职责，Skill 仅建议或停止，不擅自执行 |
| 没有知识维护人、审核时间或回滚路径 | 暂停正式发布；先落实责任和复核周期 |

知识/Skill 发布后的新版本也不是覆盖旧事实：问题先成为反馈候选，从指定资产版本发起新 Creation Session，经同样审核与读回后才可提示“已修复”。详见[日常嵌入与反馈](03-日常工作嵌入与正反馈.md)。
