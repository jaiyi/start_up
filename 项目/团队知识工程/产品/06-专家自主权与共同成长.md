# 专家自主权与共同成长：把承诺变成 Workbench 的动作

> 本页是**待验证的产品设计**，不是现有 Workbench 功能清单，也不是对岗位或待遇的承诺。产品可以让人掌握判断、看见贡献和负担；是否提供受保护的工时、转岗与晋升路径，必须由业务负责人和组织管理共同决定。正式权限、审核、指标口径仍以[方案治理](../方案/04-角色、治理与运营机制.md)、[工作台规格](../方案/09-工作台信息架构与核心对象.md)和[验收](../方案/08-MVP实施、验证与验收.md)为准。

## 1. 不回避“被替代”的担心

资料搬运、初稿和重复答疑可能被 Agent 减少；如果专家仍承担同样的原有工作量，还要无偿确认所有生成内容，产品只是把隐形劳动转给专家。若管理者用个人调用量或产出速度考核员工，使用者也不会放心报告模型错误。因此产品与组织需要一同验证：专家是否拥有实质裁量和被保障的复核时间；员工是否能从重复执行转向判断、处理例外与改进流程；管理者是否将省下的时间用于质量、培养和新问题，而非直接提高个人定额。

**产品能提供证据和选择，不能替业务方决定岗位安排。** 业务流程 Owner 在试点前确认可投入的专家/审核工时、超载时优先级和停止条件；负责人向参与者说明数据用途、谁能看、如何纠错和退出试点。若不提供这些前提，只验证受控原型，不把“员工获得成长”作为已实现收益。

## 2. 担忧、产品机制与决定权

| 担忧/工作目标 | Workbench 拟提供的动作与可见反馈 | 谁作决定、如何防止失控 | 可观察的失败信号 |
|---|---|---|---|
| “Agent 会把我的经验当已确认事实” | 在候选旁并排展示来源定位、模型推断、适用/不适用范围和差异；专家可采纳、修改、拒绝、标记待核验、要求补证据或提议限制旧版使用；显示其理由和后续责任人 | 授权 steward 确认事实/范围；发布由有权审核者和 Git/CI 门禁决定；旧版停止使用/退役按原治理流程审批并读回，不能单击覆盖正式资产 | 专家只能按“确认”，或拒绝后仍自动入库 |
| “大家都来报错，我每天只是在清待办” | 本人待办显示影响范围、重复线索、必要证据、建议优先级、预计需谁确认；可按权限接单、转交、拒绝不属本域、延期或升级，给报告人可回访解释 | asset owner/业务推动者为未认领和超载队列分派资源；延期不是自动批准；明确复审时间与停收条件 | 积压持续增长，专家被迫在原工作之外处理，平台只加催办 |
| “成果被算成 Agent 或某位作者的产量” | 版本页按资产记录提出问题、整理、事实确认、测试/审核、后续修订及分享等不同贡献；本人可看贡献链与被验证的复用，能申请更正错误归因 | 来源于经权限验证的真实责任事件与人工确认；贡献归因不等于业务成功或绩效结论，敏感资料按 ACL 隐藏；多角色共同贡献不强制单一功劳人 | 模型生成量被当个人贡献，纠错者看不到后续状态，出现排名/刷量 |
| “员工要比 Agent 更快才算有价值” | 在原任务提供带来源的辅助判断、何时不适用与如何升级；从反馈案例学习识别例外，参与自愿的知识确认/Workflow 测试与改进 | 管理者决定成长时间与岗位机会，员工不被强迫成为 Skill 开发者；Workbench 不评估个人与 Agent 的速度比赛 | 只有培训签到、使用次数或个人完成速度，没有质量/成长体验 |
| “管理者不知道投入是否值得” | 授权的团队/任务聚合卡并列展示真实任务改善、覆盖率、错误/unknown、专家审核和维护负担；支持记录继续/调整/增配资源/暂停的理由 | 业务结果 Owner 确认基线和收益，team asset owner 协调复核容量；小样本抑制，不显示个人消费轨迹或员工排名 | 只展示上传/发布数或所谓节省人头，未算维护成本与样本覆盖 |

表中“可接单/转交/负担卡/归因纠错/管理决策卡”均为**产品提案**，未指定已有后端能力或外部人事系统集成。即便 Agent 生成了高质量内容，也只能提出依据与建议，不能抢占事实确认、审核发布或下游运行时批准权。

## 3. 一次交接核对中的正向体验（虚构示例）

执行者发现旧纪要与新模板冲突，登记脱敏线索。steward 在待办中看到两份资料的授权引用，而不是一个要求“确认 AI 答案”的勾选框；可标记旧纪要只适用于某时期、要求补充生效依据，或说明无法确认并暂缓发布。确认范围后，贡献者起草正式修订，审核者核对其差异；读回成功后，原报告人在下一次核对中能看到已生效的版本，若仍不适用继续反馈。专家在自己有权查看的版本/反馈中看到自己对范围和例外的判断如何被采纳；管理者看见同类问题减少或仍存在、实际复核耗时，却看不到员工“发问最多/最慢”榜。

如果事实无法核实或队列无人维护，第一步的正反馈只是“线索保留并注明待核验”；**不得虚构已解决**。即使有新版本，也只有真实任务、同口径基线和结果 Owner 确认才可说团队效率改善。

## 4. 专家本人、员工、管理者的屏幕建议

- **专家工作区：判断与边界**。候选卡上“来源 / Agent 推断 / 已确认事实 / 适用范围 / 反例 / 证据不足”分栏；“采纳、修改、拒绝、待核验、请求补证据”是不同动作，必须保留理由、对象修订和何时再看。针对已发布内容的疑似严重错误，只能提报风险、提示授权用户谨慎引用并按治理授权升级/退役，不能绕过旧版的正式权限和发布链。
- **我的待办与容量**。列表明确“需我判断”和“等待他人”，按影响和到期时间展示；转交/延期/升级需填写原因、下次处理日期及责任对象，不以标记 `deferred` 清零积压。只汇总团队队列健康与预计可用复核时段，个人视图服务于本人行动，不对主管输出个人速度排名。
- **我的贡献与学习**。本人可按其有权限的资产版本查看“我提出的问题被谁核验、参与了哪种判断、后续有无经验证的复用”，也能对归因提出更正；提供“从识别不适用→提出证据→确认事实/范围→编写边界测试→带领案例复盘”的自愿练习入口。没有受控下游事件时写“复用未验证”，不可因演练推出业务成功。
- **管理者团队决策卡**。列当前试点任务、原人工基线、窗口、来源和覆盖率；并列用户收益与维护成本、未知/积压及资源缺口；允许记录“追加复核时间/缩小范围/暂停试点”的决定及复审日期。非授权角色不可查看；小团队或单例场景应合并/隐藏可反推个人的数据。

这些屏幕复用现有 Workbench 首页、创作区、发布资产与反馈队列；不新建员工行为监控后台或 Harness 执行控制台。本人贡献面板应依据可验证的操作链展示，**不能复用消费者 `actor_ref` 的调用数据制作个人画像**。

## 5. 首期如何验证，何时停止

先用低保真任务测：专家是否能独立拒绝不适用结论、指出界面错误归因并知道如何更正；员工能否区分“用 Agent 做初稿”和“由人决定边界”；经理能否在低覆盖率/高维护成本时选择暂停而不是追发布量。再在获授权的单场景试点里观察实际判断用时、待办积压、纠错关闭、经证实的再使用、第一用户维护时间与一线结果；询问参与者是否感觉裁量与成长空间增加，不把满意度当客观业务收益。

触发暂停/缩小范围的信号：专家拒绝无效，确认负担无工时保障；资料冲突长期无人认领；贡献归因频繁错误且无法申诉；团队级聚合可反推个人；管理层要求个人产量/速度榜；下游使用或结果证据不足仍称“减少人力”。此时先修组织承诺、权限和工作方式，不用更多培训或 Agent 自动化掩盖问题。
