# 07 · Skill 创作会话（拟议页面规格）

> 供 PM 与团队评审的设计提议，不代表已实现、已验证宿主能力或已上线的业务流程。页面按“创作一条可复用工作方式”的任务组织，不按创作者、审核人另拆页面。返回[页面索引](README.md)。依据：[产品蓝图](../03-Workbench如何解决.md)、[初版假设](../04-初版假设与迭代.md)、[交互原型](../可视化原型/index.html)及[Workflow 到 Skill 的边界](../../方案/10-Workflow到Skill的生成、测试与发布.md)。

## 场景与目的

本团队成员先走[工作台](02-Workbench工作台.md)的同一四步材料主路：导入来源 → 事实梳理 → 经验总结 → 加入知识库。事实和经验两步各以桌面约 2/3 当前项待核稿／评论、1/3 已有知识准确版本对照呈现，移动端对照接在本项之后；数字的报表口径与 Tool 授权条件在事实梳理中就地核，不另设一步。「加入知识库」预览独立去向并条件性比较合成 Skill/人工写法。「加入知识库」时仅在确有已有 Skill 的质量缺口，或无适用旧版且流程重复稳定可复测时，才进入本 Skill 深层工作区；从[团队资产](10-资产与发布.md)的已有版只读详情也能有权精准进入。不存在独立「能力体检」页/按钮或从首屏直达 Skill 深层的默认捷径。当前静态示例的 SK-01 v1 周报整理 Skill 及“实际／预计”问题均为虚构。成员也可在 DSH 主动运行[任务复盘 Skill](12-任务复盘Skill.md)，先核对任务过程与实际使用证据，再讨论复用/特例，并手动复制用户确认、脱敏的**候选结论**；这不证明既有 Skill 曾加载、执行或失败。仅当没有适用的已有版本，且从[团队知识骨架](13-团队知识骨架与工作记录.md)的描述性方法或真实工作流找到稳定、合法、可复测步骤时，才考虑新建。描述性经验可以独立存在，不为凑 Skill 而封装。正式产品要将已有版的改进或真正新增绑定可核来源、版本/基线及样例，形成 Workflow Draft、Skill Draft 和真实脱敏测试证据后才受控提交；这不是从[DSH 对话与任务](01-DSH对话与任务.md)的一次推荐直接生成、安装、加载或运行 Skill。流程不稳定、依赖当前逐次审批时停在人工路径；静态原型只演示质量核对，不提供上述真实执行或发布。

## 从统一意图到已有／新 Skill 的质量核对（拟设计）

工作台的「给出获准材料／描述某类任务需要的能力」不另设体检流程：「导入来源 → 事实梳理 → 经验总结 → 加入知识库」中，事实和经验两步各以当前待核稿与评论为主、对照已有知识准确版本，标清已核／来源自述待核／冲突／未取得／不适用及出处；数字只在事实梳理中核指标口径，且仅在用途、身份、对象/字段、时间窗和只读通道获授权时就地用 Tool 核证，否则回有权报表与人工。「加入知识库」**在同一工作区**预览去向，并列比较合成 Skill 写法与合成人工写法；正常/边界/异常 fixture 展示误用风险、人工停止点及版本依赖，不宣称已试跑或证明某一方优胜。它先给出「引用既有版／补证或修订指定版／维持人工／建议评估新增」的条件性去向；只有成员有权且确有缺口，才跳本深层会话，不通过看过对比自动建 Skill。进入本会话时显示限定任务、判断点、期望输出、合法输入/材料格式及实际可读范围；无法确认文件授权、解析能力或页段锚点时保留最小线索，不拿模拟文件做真实测试。逐个核对可访问的**已有 Skill 的准确版本/digest**、所依知识版本与有效起止、触发/输入/停止条件、正常/边界/异常样例质量、维护 owner、反馈与失效信号；把“已有但条件不适用/依赖断开/未安装”与“真正缺 Skill”分开。优先修订指定版本、补测试/安装验证或保持人工路径，仅当稳定步骤确有空缺且有 owner 与脱敏样例时提出新 Skill Draft；需要实时数据的 Tool 依赖仅为需求声明，不等于可调用或应封装审批。

与[场景评估卡](11-候选能力地图.md)关联时，卡片明示场景 owner、Skill 维护 owner、核证/审核责任人与待指派、适用范围及生效/复核/到期依据；材料描述、Agent 建议与本地设计清单只能是「暂定／待补证」。草稿质量合格须有绑定修订、输入及依赖版本的真实脱敏试跑、期望与实际断言、失败和停止条件；发布须 Git/CI/有权人批准、SkillHub 固定 digest 读回。发布、目标安装、DSH profile 加载、真实任务执行及业务结果分别展示证据和发生时间，缺一项不得推定下一项。未来数字员工运行也须单独核身份、安装/加载、版本与执行回执；当前静态原型没有模型、子 Agent、Skill 试跑、Tool 调用或这些宿主接入。

## 页面内容

### 条件进入后的深层质量核对清单（非第二条四步主路）

这里仅在「加入知识库」判出已有版具体问题或可核新增理由、并重新授权后，才讨论 Skill 的指定版本/草稿细节；**不是另一次必走的材料流程**，也不能让深层清单取代材料主路「加入知识库」中的合成比较。原型以虚构 SK-01 v1 和人工编写的改进写法演示；正常/边界/异常 fixture 及本地“设计待补”只用于比较，不是真实测试、标准答案或已确认适用。正式产品的保存、真实测试、审核与读回见下文独立拟议状态流程。

| 深层核对点（按条件展开，并非第二次必走四步） | 用户此刻要看／判断什么 | 示意结果 | 未满足时 |
| --- | --- | --- | --- |
| 来源与适用 | 核 SK-01 v1 的可见来源、准确版本、适用任务和“实际／预计”问题线索；材料授权、格式可读范围与有效日期另待核 | 本场景的现有版适用性及不确定点 | 来源或基线不可核，不称已确认已有版质量或断言必须新建 |
| 旧版步骤与依赖 | 查看既有触发、输入、逐步判断、人工停点、输出、知识版本和 Tool 依赖；与当前任务条件逐项对照 | 可保留的步骤和待核的误判/遗漏 | 无稳定步骤、依赖缺权或条件不符，可回人工/补证，不强推封装 |
| 对比的待核差异 | 并排看合成的 Skill 写法与合成人工改进写法，切换正常、边界、异常 fixture，标本地“设计待补” | 对“实际／预计”及停止条件的待核修订点；既有版仍保持原状态 | 这不是模型/Skill 试跑、实际输出、通过记录或有权人的内容确认 |
| 测试与受控共享门槛 | 预览修订既有版本或仅在无适用旧版时新建所需的真实样例测试、审核、SkillHub 读回及下游分发/安装/加载/执行门槛 | 按证据列未完成项和责任人；现阶段仅预览，不能共享/发布 | 权限、测试或版本读回未知则待补/对账，绝不把本地预览当 released |

原型不会自动保存 Skill 包、调用模型/子 Agent/Tool 或产生正式测试证据。新建 Skill 是**没有适用旧版且重复稳定、可复测**时的后续拟议分支；上表只是满足条件后查细节的清单，不要求用户完成第二条四步导航。

- 页面上方（拟设计）：当前团队/资产空间、会话 ID、SK-01 v1 等准确基线（无法核实时标未知）、草稿修订及“整理中／待核对／团队可用／已停用”各自对应的资产版本；深层清单仅作核证索引，不改变正式版本状态。正式产品须服务端重验身份与版本，原型没有该能力。
- 来源与差异区：在有权范围查看已有版的触发、步骤、人工判断点及其知识/Tool 依赖；并列本地合成写法、假设、未确认项和正常/边界/异常 fixture。未来可拟议 Workflow Draft 与 Skill Draft，但 Agent 建议不能静默覆盖原版，来源/复盘线索不能因引用升级为已确认事实。
- 证据与动作区（拟设计）：绑定具体草稿修订的真实脱敏试跑须对照期望、实际、失败断言和依赖版本；审核/发布、SkillHub digest 读回和安装/加载/执行另列。静态页只能展示“设计待补”及门槛预览，不提供真正保存、试跑或发布回执。

暂停不发起新操作；归档/只读只保留查看，分叉产生新会话。已发布 Skill 的修改也在本创作会话基于固定资产版本发起独立修订，而不是在[团队资产](10-资产与发布.md)直接覆盖正式版本；工作台仅在成员对这份修订有明确当前动作时显示待办，创建者在别人审核期间只关注进展，详见[工作台事项规则](02-Workbench工作台.md)。每次保存、提交与异步回调重新校验会话、草稿修订、权限和幂等状态。发布后的分发/安装、DSH profile 加载、真实任务运行与业务成效是**独立状态和权威**；Workbench 不提供宿主运行按钮。失败的业务任务只形成可追溯的反馈候选，不直接改写现有 Skill。本地 `knowledge-compounding` 是用户工作区实例；它的收件箱 `accepted/merged` 回执不代表本页已有团队版、安装或运行。

## 跨页路径

[工作台](02-Workbench工作台.md)的单一材料主路在「加入知识库」时先条件性并列比较合成写法、核已有版本及条件，再按证据缺口进入本 Skill 深层工作区；也可从[团队资产](10-资产与发布.md)的已发布版本只读详情明确选择继续处理。两者都不是「默认从工作流新建 Skill」；只有核实无适用既有版、重复稳定且可复测时才走新建分支。[DSH 对话与任务](01-DSH对话与任务.md)的 Skill 推荐只提示范围与依赖，不能一键视为已有创作会话或已安装。知识引用到[知识创作会话](03-知识创作会话.md)核对来源；需外部只读能力时查看[已开通 Tool](08-已开通Tool.md)或[Tool 广场](09-Tool广场.md)，但目录可见与能力需求均不授予运行时权限；[候选能力地图](11-候选能力地图.md)仅将稳定步骤作为判断点证据。发布/反馈处理仍在本会话的特定修订中进行，而非在团队资产页操作或在宿主运行会话中编辑正式资产。

## 访问与数据边界

每团队独立 Git 仓库、草稿、测试、job 和审核；服务端基于 DSH 身份映射校验 `team_id/asset_space_id/session_id` 与来源 ACL，不能用客户端路径或宿主 ownership 当授权。真实确认、审核、发布责任人和执行服务身份分列。Skill 的 Tool 依赖不等于 Tool 注册、接入、数据授权；提供方/数据责任方与 DSH 运行策略决定可否调用。Git 仅纳入受控脱敏文件与引用，不保存 Token、生产输入、敏感原文或完整 Prompt/Tool Call trace。

## 与当前原型的差距及待确认

原型目标（以实际静态页面验收为准）：材料主路「加入知识库」以虚构 SK-01 v1 的“实际／预计”问题并列合成 Skill 写法与合成人工写法，正常／边界／异常 fixture 仅标本地设计待补；确有旧版质量缺口才按需打开本 Skill 深层工作区核准确版本、来源、步骤及未完成门槛。**没有真实测试、Skill 包保存、通过记录、Tool 调用或证据证明哪种写法是标准答案**；正式审核、SkillHub 读回及分发/安装/加载/执行只能预览所需证据，不实际受控共享。原型没有真实收件箱受理、会话恢复、草稿持久版本、Git/SkillHub 读回或 DSH handoff；上文独立拟议的正式状态流程不是静态页已实现能力。

- 首批哪一类稳定流程确有 owner、合法来源、脱敏测试和可复核成功标准？不满足是否不做 Skill？
- 目标 Skill schema/loader、SkillHub 发布路径与 DSH handoff 哪些已在目标环境验证，哪些应保持管理员 fallback/未知？
- Tool 依赖无法授权、正式基线冲突或无审核容量时，谁决定缩小范围、暂缓或终止？
