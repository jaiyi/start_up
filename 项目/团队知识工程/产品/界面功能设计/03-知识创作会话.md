# 03｜知识创作会话：围绕判断和依据工作，不让草稿冒充版本

> 页面位置：Workbench 左侧一级入口，也可在导航能力验证后由 DSH 结果卡/工作台定位指定内容。这里的“创作会话”是协作整理的工作上下文；经核对、审核并读回的具体内容版本才可供团队引用。以下是拟设计；现有原型主要示意一条已有知识的正文、评论及手工粘贴候选。

## 何时进入，要完成什么

一种进入方式是 DSH 检索到团队知识，成员想知道这条判断**从哪里来、哪一版、什么条件适用**，并针对某句话留意见；另一种是成员主动运行[任务复盘 Skill](12-任务复盘Skill.md)，先回看过程与现有资产证据，讨论额外调整是否可复用，再将用户核对、脱敏的候选结论复制到本页。人仍须在本页选择可访问资产/基线、补查来源；复盘里的“用户确认可复用”不是正式草稿内容确认，也不证明实际检索或调用。报告、PPT 等任务产物可以在具备分享授权且核实资料库入口后**另作来源资料**提交；本页只处理其中值得核查、可长期复用的判断与适用边界，不将整个产物直接变成正式知识，也不修改当前 ERP 库存或采购价格。

## 页面应呈现什么

按[团队知识骨架](13-团队知识骨架与工作记录.md)，本页不仅供新建，还要从业务对象、来源记录和既有正式版本进入**查看、纠错与提炼**。列表/搜索先用团队选择的项目、产品线、专题或关键词定位；每条结果标“业务对象事实／团队经验”、关联对象、来源与最后核实时间、具体版本的“整理中／待核对／团队可用／已停用”，并把团队可用 v1 与整理中的 v2 分开。工作记录应有独立的来源视图和原件版本，不显示为已确认知识；改栏目/关联不会复制正文或改变稳定 ID。

- 明确的团队空间、内容对象 ID、关联项目/产品线、Git 基线版本与草稿修订、具体版本状态、来源权限和更新时间；从 DSH 跳转时显示原任务返回入口，重新鉴权后再显示正文。业务对象页面先展示可核对的当前事实及“截至何时”，再链接来源时间线、经验与 Skill；不能从最新一条纪要自动填“当前”。
- 详情区分**事实**（陈述、生效/截至区间、权威系统/来源及反证、最近核实时间）与**经验**（判断或约定、依据、适用与不适用范围、反例和复核点）；侧栏展示有权查看的来源版本、关联对象、争议/评论与版本历程。原始资料、成员补充、Agent 整理和已确认判断分层；仅有资料或用户口述时标“待核”，不显示“已确认”。人员分工是有时效的事实，不自动授予系统审核或发布权限。
- 对具体资产版本的段落定位、评论与来源线索入口；旧版继续只读，基于旧资产启动修改时须选择精确 Git 基线并另建修订提议/创作会话，草稿差异在[修订提议](05-修订提议.md)中呈现；正式版可同时继续可引用，不能被会话覆盖。
- 新知识候选最小表单：眼前重复的问题或待核的业务对象事实、拟保留的陈述/判断、能查到的来源版本与分享范围、关联项目/产品线（可待定）、有效时间或适用/不适用范围、未决反证和下一步核证动作。可先保存缺口，不迫使使用者编造当前分工、生效时间或负责人。
- **同一创作会话里的发布进度**：对指定修订展示内容确认、Git/CI、人审、发布请求及目标 Provider 版本读回的证据与时间；按状态/权限提供提交审核、处理退回、核对发布、对账等对应动作。页面不提供一个可绕过门禁的「一键发布」，团队成员也不因能贡献内容就拥有审核/发布权。正式版可供引用后只把结果同步到[团队资产](10-资产与发布.md)展示。

## 功能流转

| 功能 / 触发 | 前置与步骤 | 记录、下一步 | 失败与边界 |
| --- | --- | --- | --- |
| 看指定版本：从 DSH“看依据”或直接查找 | 重新核查团队、资产和来源权限；展示传来的确切 Git 版本、确认范围及若有的新版本提醒 | 可回[DSH 任务](01-DSH对话与任务.md)重新核条件，或进入[内容讨论](04-内容讨论.md) | 版本不存在/失权时不以新版替代旧版并冒充当时引用；显示安全退路和申请权限方式，不暴露来源摘要 |
| 选段落提出疑问 | 保存资产 ID、版本、稳定段落定位、选中文字快照及创建时上下文；跳转讨论页后允许编辑意见和来源线索 | 评论绑定该版，可继续补证；旧版锚点遇变更需人工重新定位 | 选择文字只是低负担假设；移动端/键盘不便时用段落级入口。不能没有对应版本却假装“锚定评论” |
| 建立新的候选事实或团队经验 | 从已提交且获准分享的复盘线索、有权访问的工作记录/业务对象或资料开始；先判是否已有同一对象/经验及其版本。事实核原系统、发生与生效时间、反证；经验核重复性、条件、反例和误用风险。填最少陈述、来源与待核问题 | 创建创作会话，按对象或来源关联候选，邀请有权访问材料的成员进入[内容讨论](04-内容讨论.md)；确定可改内容后进[修订提议](05-修订提议.md) | 未提交的粘贴不标“已收到”；有来源不代表来源观点正确。证据不足可留待补，不自动发布；一次性事项/实时事实回原任务或 Tool；无承接者显示待安排，不伪造责任人 |
| 对比历史与当前正文 | 对比明确版本的来源、适用范围、确认和停用记录；指出哪个版本曾被引用 | 可针对相应基线发起修订，发布后旧引用仍留审计线索 | 遇版本冲突不静默覆盖旧评论，已过期内容必须清楚警示并去受控纠错路径 |
| 受控审核、发布与目标读回 | 指定草稿经[修订核对](06-修订核对.md)的有权确认后，在本会话对齐不可变修订 ID、Git 基线和内容差异；具备相应动作权限者按现行策略提交 Git/CI、人审与发布请求，再核对目标 Provider 版本、哈希及授权范围 | 只有通过门禁且目标版本读回一致，才标该版本「团队可用」并在[团队资产](10-资产与发布.md)只读展示；旧版审计与适用范围保留 | 草稿变更撤销旧确认；CI/人审失败返回新修订核证；外部 `unknown` 先对账，不盲目重试、按成功或失败处理；无人有权承接则待安排而非默认批准 |
| 暂存/退出创作会话 | 会话记录草稿与最近操作，不赋予正式知识地位；返回任务保留可失效定位 | 继续该草稿或结束一次性讨论，给发起者可理解的回执 | 存储故障时不能报“已保存”；资料权限变化要及时收敛可见范围 |

### 什么时候不做知识

“这次库存还有几件”是当下事实，应通过获授权的只读 Tool 查询；“按这个库存自动下单”是业务决定/写操作，不能写成知识就绕过审批；“每次按稳定步骤核对两版清单”可能适合作 [Skill 创作](07-Skill创作会话.md)，但要有可测试的停止条件。团队成员可贡献内容，有权确认和正式发布仍是单独动作。

## 跨页与原型差距

进入[内容讨论](04-内容讨论.md)后可补来源、背景，形成[修订提议](05-修订提议.md)；[修订核对](06-修订核对.md)只对特定草稿和范围确认；随后的正式审核、发布、读回与异常对账留在**本知识创作会话**的指定修订流程，完成后到只读[团队资产](10-资产与发布.md)查看版本结果。返回 DSH 时重新核验任务和当前版本，不把新草稿注入已确认结果。

**原型已示意**：虚构 K-01 v1 正文选区、旧版只读、评论跳转、候选手工粘贴的内存回执、业务对象和来源详情的预置卡片，以及本会话中 R-02 审核/读回的本地按钮。**原型未做到**：真实业务对象/记录接入与事实核证、可配置导航、真实候选受理、新建候选、来源权限校验、版本对比、会话恢复和真正的返回定位。**待验证**：创作会话由何种 DSH API/Provider 提供、锚点如何稳定、团队是否愿意维护业务对象的当前事实、在不同类型素材上能否低负担补证。

## 优先讨论

1. 从零建立候选知识前，哪些重复/风险信号足以支持投入维护，而不增加无意义的整理工作？
2. 用选中文字、段落级“提出问题”还是来源引用作为主要交互？需要对真实任务试用。
3. 哪些字段是初次保存必填，哪些应留给核对与正式确认阶段？
