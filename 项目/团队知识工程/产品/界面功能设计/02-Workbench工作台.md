# 02｜Workbench 工作台：帮人找到下一步，不再造一个问答首页

> 页面位置：Workbench 左侧一级入口。工作台负责**导航和待办的可理解去向**，当前业务问题继续在 [DSH 对话与任务](01-DSH对话与任务.md) 中解决。以下是拟设计，既不是角色化的管理驾驶舱，也不是已实现的个人绩效统计。

## 何时进入，要完成什么

从左侧直接进入时，成员可能要找到本团队知识/Skill、继续一项讨论或查看受控发布进度；从 DSH 的“反馈去向”进入时，想知道原问题谁在处理、自己还要补什么。工作台应该让人看懂**我现在该去哪个具体对象做什么**，而不是堆知识数量、提问数或 Agent 调用量。团队存量、本周资产进展、新人了解业务的路径放在[团队资产](10-资产与发布.md)，不把资产大盘误当我的待办。团队负责人也在同一个入口看有权查看的积压与无责任人问题，再去具体对象处理，不另设身份专页。

## 页面应该有的信息

工作台承接[团队知识骨架](13-团队知识骨架与工作记录.md)的**具体行动与进展索引**，不是项目目录或工作记录全集。成员可从搜索/导航按习惯找项目、产品线、来源记录、当前事实或经验，但只有一条记录提出了待核问题、我被明确请求补证等**具体工作项**，才进入下述个人进行中；原件已登记不自动生成全团队待办。

- 当前团队资产空间和 Git 仓库绑定状态；只显示团队与身份允许公开的概况，不展示来源受限内容的标题/摘要。未绑定、不可达、权限失效和真的没有内容是四种不同情形。
- 按行动分类的入口：回 [DSH 任务](01-DSH对话与任务.md) 解决眼前问题；继续本人有权参与的内容讨论/补证；核对某份修订；看正式版本和异常；了解外部 Tool。进行中的事项分为“需要我处理”和“我关注的进展”；每张卡写明出现原因、具体对象与版本、下一步动作以及实际责任人/期限（若可见）。已结束的贡献保留可查，但不常驻进行中。
- 自己发起的问题的回访：已收到、待补充/已分派、人正在判断、有处理结论/不予沉淀、关联新版本可引用；**当前业务问题是否解决**作为另一条线，不由 Workbench 自动填写。
- 入口说明：工作台「带来一份材料／改进已有能力」共用**同一四步材料工作区：导入来源 → 事实梳理 → 经验总结 → 加入知识库**，不保留独立「能力体检」页或按钮；知识与 Skill 的指定版本修订只在确有证据缺口、适用旧版或稳定可测新流程后按条件进入深层工作区，不是先二选一的左侧入口。知识核对用于有依据/边界的判断，Skill 先核准确旧版及质量；Tool 目录用于外部能力与申请去向，实时查询结果不记成团队知识。

## 一个材料／能力意图入口与行动卡（拟设计）

从工作台的同一入口表达「提供获准材料」或「这类任务需要什么能力」，只问限定任务场景、期望判断及可分享的最小材料/定位，不预设知识/Skill/Tool 类型。**工作区仅走四步：导入来源 → 事实梳理 → 经验总结 → 加入知识库。** 导入来源核分享资格、任务及格式能力/未读范围；事实梳理逐项看来源说法、时点和状态，经验总结逐项看完整待核判断、支持与反例。两步桌面均以约 2/3 呈现**当前事实点或经验议题的待核稿与评论**、约 1/3 呈现**已有知识准确版本对照**；移动端对照接在本项之后。每项标「已核／来源自述待核／冲突／未取得／不适用」及依据；固定周报、相似检索或本地看过不能当已核。对影响结论的数字，在事实梳理中先核指标定义、数据时点与权威报表，仅当前身份、用途、字段/对象、时间窗、指标口径和只读通道均获授权时在数字旁核 Tool，未满足则待授权/待核或回原系统，不单设数字步骤。「加入知识库」分别预览来源、事实、经验、已有知识准确版本、Skill、Tool 及逐次人工处理的去向和门禁；在此条件性比较合成 Skill 与人工写法的正常/边界/异常例，不将比较称作真实试跑或胜出，也不另设 Skill 体检页。当前项评论和已有知识对照无需离开事实／经验两步；指定正式知识版本的受控修订或 Skill 深层质量核对仅在确有相应缺口时按需进入；旧版适用先引用/补证，只有可核无适用旧版且稳定可测才考虑新建。未受理粘贴只是本地输入，不能生成待办或假定已运行抽取。

进入个人事项的应是**具体场景评估卡或其证据缺口的明确指派**，不是一张自动生成的“全员待评能力”卡。卡上显示限定任务/判断点、场景 owner 与核证承接人（无人则待指派）、生效起止或待核、证据来源/最后核实和下次复核、当前「暂定／待补证」与可引用正式资产版本的区别，以及各去向独立下一动作。只有真实受理/指派回执才能进入“需要我处理”；创建者可在“我关注的进展”看同一事项，不重复计数。知识引用、Skill 安装/加载/执行、Tool 目录/试参/真实调用各记独立证据和状态；无宿主事件时均显示未知，不用推荐或浏览推算次数。静态原型未提供该真实入口、场景归因或原生 DSH/未来数字员工使用回执；这里仅定义目标界面，不要求其运行模型、子 Agent 或工具。

## 主要功能怎样流转

| 功能 / 触发 | 动作与状态 | 成功下一步 | 异常或不应发生的事 |
| --- | --- | --- | --- |
| 进入团队空间 | 服务端确认团队绑定、当前身份和空间范围；只读汇总授权对象与可执行动作 | 从具体对象继续[知识创作](03-知识创作会话.md)、[Skill 创作](07-Skill创作会话.md)、[Tool](08-已开通Tool.md)或[团队资产](10-资产与发布.md) | 未绑定提示谁/什么流程处理绑定；失联显示“无法核实”，不清空待办、不伪称空团队；撤权后不展示缓存内容 |
| “继续我参与的问题” | 根据问题 ID、当前关系和权限读取受理/补证/处理记录，注明最近更新时间；有明确交给我的补证动作才算我的待办，否则是进展回访 | 进[内容讨论](04-内容讨论.md)补证或读回执；若源任务仍有效，返回 DSH | 处理人未接单时显示待指派而非“已转交”；无法看源内容时仅显示允许公开的状态/联系渠道 |
| “待核对的具体修订” | 仅对当前草稿有**明确指派/已承接的核对动作**且提交时满足确认资格者呈现确认待办；其他获授权成员可从对象页补证 | 有权确认者进[修订核对](06-修订核对.md)；其他有权成员仍可补证 | 没有确认者时提示分派/缩小范围/回人工业务路径；仅有资格、未获指派者不能被批量列为待办 |
| “找资产/看版本” | 搜索本团队可访问的知识、Skill、草稿与正式版本，清晰区分对象类型及状态 | 跳到指定知识/Skill 会话或[团队资产](10-资产与发布.md) | 仅搜到草稿不冒充正式可引用；无结果不冒充没有内容，说明检索范围/连接状态 |
| “现在去处理任务” | 以宿主安全链接打开新任务或返回原任务定位，并重验授权 | 到 [DSH 对话与任务](01-DSH对话与任务.md) | 不复制聊天内容，不在 Workbench 增加一个平行问答器 |

## 生命周期如何变成“我的事项”（拟议规则）

**不要用一条资产的状态直接生成个人待办。** 同一知识 K-01 可以有正式可引用的 v1、仍在核对的 R-02 和关于 v1 的另一条问题；一项 Skill 可以已发布，却还未在目标环境安装。正式版本的真实状态在[团队资产](10-资产与发布.md)，编辑和测试在相应创作会话。工作台只索引与**当前身份有关的具体工作项**，不改写它们的权威状态。

| 跟踪对象 | 状态从哪里核实 | 不能混成什么 |
| --- | --- | --- |
| 来源记录引出的待核事实／经验问题（`source_ref + issue_id`，可关联业务对象及版本） | 来源可见性以原系统/获准引用范围为准，问题受理与补证由[内容讨论](04-内容讨论.md)和[团队知识骨架](13-团队知识骨架与工作记录.md)的对象详情承接 | 记录本身不套知识发布状态；项目分工的历史记录不等于当前事实，也不给记录中提到的人自动分派待办或审核权 |
| 问题／评论 `issue_id`（可关联资产 ID、基线版本及来源锚点；也可没有资产） | [内容讨论](04-内容讨论.md)的受理、补证、实际承接、处理结论和回访 | “有人评论”不等于“该成员负责修订”；问题有结论不等于版本已发布或原业务已解决 |
| 知识候选／修订 `session_id + proposal_id + draft_revision_id` | [知识创作](03-知识创作会话.md)、[修订提议](05-修订提议.md)与[修订核对](06-修订核对.md)的保存、基线、确认记录 | 已发布 v1 与待核对 v2 不是同一个状态；旧草稿确认不能延续到新修订 |
| Skill 候选／修订 `session_id + draft_revision_id`，含固定基线与测试证据 | [Skill 创作](07-Skill创作会话.md)的会话、草稿、测试和受控提交记录 | `tested` 不等于批准；发布不等于安装、加载或运行 |
| 审核／发布／停用或对账 `release_job_id + 目标版本/digest` | Git/CI、人审、Provider/SkillHub 及目标分发系统分别读回并标来源和时间 | 请求成功不等于目标版本可引用；外部 `unknown` 不是成功或失败 |

### 参与、当前责任与展示位置

“我参与过”只是**进入回访的线索**，不赋予查看受限内容、确认或发布的权力。服务端按团队、对象、来源权限与当前身份重新计算关系和可执行动作；没有可核验的身份映射时不生成个人列表。

| 我与工作项的关系 | 进行中显示位置 | 何时需要我行动 |
| --- | --- | --- |
| 我发起问题、留评论、补过来源，或明确订阅有权看的进展 | **我关注的进展**：受理、待分派、别人处理中、等待发布；只显示获准看的必要状态 | 只有处理者明确向我请求补证/澄清，且我仍有访问权，才生成“需要我处理”的补证动作；未回复的普通评论不产生确认义务 |
| 我创建知识／Skill 草稿或提议 | **我关注的进展**：别人核对、审核、发布时；自己已暂停且无下一动作时可从进行中收起 | 草稿未保存、我明确承接完善或被退回补证时，显示指向该会话/草稿的待办；“创建者”不等于永久维护人 |
| 我明确承接处理、维护、补证、定向核对、审核、发布或对账中的一项 | **需要我处理**，条件是动作仍有效、权限仍有效且绑定具体问题/修订/目标版本；待接收的分派邀请标“请决定是否承接”，不标“正在处理” | 具体操作须再次重验资格、来源、草稿修订、基线与责任策略；仅“有资格确认”不向所有人群发核对待办 |
| 我只看过资产、被 Agent 推荐过资产，或已完成历史贡献且无后续动作／关注 | 不进入进行中；需要时去资产页搜索版本或看有权查看的历史回执 | 后来出现新问题、收到明确请求或主动关注，才关联**新的**事项；不会复活旧待办 |

“需要我处理”与“我关注的进展”可以是同一工作项的两个视角，但**同一身份只显示一张主卡**：有真实待办时放前者，卡内保留进展和关注关系；动作结束后若仍有后续进展则移到后者。分派未被接收时，发起者看到“待承接”，受邀者（若被允许）看到“待决定是否承接”，团队有权调配者看到无人接手的安排动作；不得写成已有人负责。责任人的变更、拒绝承接和关注取消均需有回执和时间，不依赖对话推测。

### 状态变化与退出条件

下表的“工作台变化”针对**有权且关联的成员**，不是向全团队广播待办；不同阶段的权威记录可能并存，不用单个 `asset.status` 覆盖全部。

| 对象阶段／事件 | 工作台变化与负责动作 | 退出或接续 |
| --- | --- | --- |
| 发现问题、手工提交候选；已收到但尚未承接 | 发起者可关注受理回执；能调配的人若获明确责任，看到安排处理。仅手工粘贴、未提交时不产生团队事项 | 合并时原问题保留回访定位并指向主问题；关闭/判定不沉淀需说明原因，结束本项，不自动结束业务任务 |
| 待补背景、待完善草稿或 Skill 待建模／待测试 | 被明确请求补证者、已承接的创作者/维护者按具体缺口行动；其他参与者仅看进展。Skill 测试失败指向修订和重测，不暗示已发布 | 补证后形成新草稿修订、更新被指派动作；决定不做资产、撤回或转逐次人工处理时，记录结论，退出活动待办 |
| 某份知识草稿待确认；Skill 草稿测试通过、待审核 | **被定向指派且当前具备确认/审核资格**的人看到具体草稿与范围；提议者关注进展，普通评论者不进入确认队列 | 确认只是进入审核；驳回/退回补证由相应实际承接者处理，旧确认不自动继承。无人可确认时保留“待安排”，不按时间自动通过 |
| Git/CI/人审、Provider 目标版本读回；Skill 发布后目标安装／加载核验 | 有明确发布、对账或目标分发责任且具备相应权限的人处理对应异常；其他关联者看发布进展。Skill 发布后安装/加载可有**单独**事项，不能当作作者的默认待办 | 目标版本及授权读回一致后，发布事项结束；安装/加载状态单独确认，执行/业务效果没有证据则写未知 |
| 正式版可引用／Skill 目标状态验证完成 | 已完成且无后续动作的个人进行中卡退出；有权成员仍能在团队资产查看正式版，在已结束记录查原回执 | 新反馈、过期复核、停止引用或失效的证据建立**新问题/维护事项**并链接正式版本；不把已发布的 v1 改成“待完善” |
| 基线漂移、草稿变化、并行修订或停用旧版 | 指定修订的旧确认失效；有权且实际承接者看到重定基线、对比/合并或停用核验动作；关注者看到不再可按原范围引用的提示 | 不将旧评论或旧确认自动迁至新版；冲突、被拒绝的新草稿与旧版继续可用是三个独立判断 |
| 发布/安装返回 `unknown`、服务不可达、责任无人接手 | 不显示“已发布/已安装/有人处理中”；有授权的对账/调配者看到动作，关联者看到允许公开的未知与最后核实时间 | 对账后以实际结果更新；禁止未知时盲目重复写入或把断联解释为“暂无事项” |

### 卡片、聚合与安全跳转

一张卡至少说明：**为何出现在这里**（我发起/关注/收到具体请求/已承接），**指向什么**（问题 ID 或会话及草稿修订 ID；关联资产 ID、基线 Git 版本、目标发布版本/digest，若适用）、当前阶段和权威来源/最近核实时间、我的下一动作或谁在等谁、目标页面及可用的 DSH 返回定位。一个问题链接多份修订时保留问题回访主卡并标关联数；同一修订的多条评论可合并为摘要，**不同草稿修订、不同目标版本或独立确认请求不得合并成一条可执行动作**。排序优先我能行动的明确请求与阻断，其后是有时间要求的回访和普通关注；期限只有真实设定才展示，不以逾期自动确认。

点击卡片时重验身份、团队、对象与来源 ACL，按动作到[讨论](04-内容讨论.md)、[知识创作](03-知识创作会话.md)/[Skill 创作](07-Skill创作会话.md)、[特定修订核对](06-修订核对.md)或[团队资产](10-资产与发布.md)，不以默认最新版本替换原锚点。撤权后即从个人聚合移除受限标题、摘要和缓存深链，只给获准的联系/申诉去向；请求转给其他有权人，原贡献留在审计而非继续显示为我能处理。同步中断或来源冲突时保留安全的“无法核实、上次核实于何时”占位，不把旧缓存当实时待办、也不显示“全部完成”；恢复后重新核验。来源无可信更新时间、身份或权限核验失败时不展示数量/名称以免侧漏。

### 两个典型例子

- 我评论 K-01 v1 的适用范围：评论受理后在**我关注的进展**；负责成员向我明确请求补充来源时移入**需要我处理**。其后对方提出 R-02，只有对 R-02 获指派且有资格者看到确认待办。我仅凭评论身份不会被要求确认。
- K-01 v1 已可引用，而 R-02 尚在核对：资产页仍展示 v1 正式状态；创作者在负责完善时看到 R-02 待办，已交核对后转关注。R-02 经正式审核和目标读回后这些进行中项结束。日后 v2 有新疑点时创建新的问题/修订事项，不篡改 v1/R-02 历史。Skill 同理，但 `released` 后目标安装及运行另行核证。

### 不应做成 KPI 看板

能汇总“本团队可见的无人承接修订、过期风险、发布状态未知”，但汇总必须带时间范围与授权分母；不允许按人员问答量、处理速度或贡献次数排行。地图只对限定任务的具体判断点作候选盘点，见[候选能力地图](11-候选能力地图.md)。小样本/组合筛选可能反推个人时不展示。

## 跨页与设计取舍

工作台是**动作索引**，不承担内容讨论本身；卡片都指向特定问题/资产/版本而不是“去专家后台”。从 DSH 进来的工作台也应优先保留原问题和返回定位，不能被通用首页吞掉。如果某一类待办只有频繁使用才成立，初版可在相关资产页展示，不强行建设全部聚合能力。

**原型目标示意（以实际静态页面验收为准）**：首屏同一材料工作区走「导入来源 → 事实梳理 → 经验总结 → 加入知识库」；事实与经验分别呈现当前待核稿／评论及已有知识对照，数字的授权及口径在事实梳理中核，「加入知识库」预览独立去向并比较合成 Skill／人工写法，按条件才进入深层工作区；同时保留返回 DSH、讨论/修订/版本/地图快捷入口、模拟“未绑定”及虚构的“需要我处理／我关注的进展”情景卡。所有 fixture、核验状态和对比均为本地演示，**没有真实 Tool 查询、指标校验或 Skill 测试**。**原型未做到**：真实材料/版本/质量检查、任务定位、按身份/责任/生命周期派生和迁移的待办、问题回访、搜索和未绑定原因区分；情景卡不随模拟发布按钮变化。**待验证**：团队最常见的进入动机，是否需要工作台聚合，还是精准深链已经足够。

## 优先讨论

1. 直接进入时，第一眼更需要“继续处理”还是“找到资产”？这要通过试用观察，不靠组织结构推断。
2. 待办里哪些状态是 Workbench 自身可信的，哪些必须依赖 Git/Provider/外部系统读回？
3. 没有任务深链时，怎样最少步骤返回宿主而不误认为“当前问题已解决”？
