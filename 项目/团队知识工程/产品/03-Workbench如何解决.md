# 3. 产品蓝图：把五处难点变成具体交互

[前一篇](02-知识工程难在哪里.md)指出了五处断点：选错要留下的内容、新任务里不知能否适用、专家与维护责任失衡、使用与纠错离工作太远、只统计活动却不知效果。本篇逐项回答：**谁在什么时候进入产品，看到什么，能做什么；无法继续时交给谁，怎样知道处理到了哪一步。** 这是拟设计的体验，不是已上线功能或已验证的用户需求。

Agent 负责在授权范围内找材料、比对并整理疑点；Workbench 让人核对、判断、修订和追踪；实时状态、当前业务审批与执行仍留在原业务系统。产品里至少要区分**来源资料、当前问题/反馈、待确认的候选判断、已确认的特定版本知识、当前业务决定**。一次提问不会自动生成正式知识，引用知识也不等于批准当前业务。

| 第二篇的断点 | 优先设计的触点 | 失败时必须有的去向 |
| --- | --- | --- |
| 选不对要留下什么 | 问题收件箱与候选判断 | 一次性问题回原任务；不值得沉淀也给回执 |
| 新任务不知能否适用 | 员工提问入口与结果卡 | 缺条件、冲突、过期或无权限时明确停下并找人 |
| 专家和维护负担失衡 | 待判断卡与维护队列 | 补证、拒绝、暂缓或无人承接时不自动通过 |
| 工作中用不上、错了难反馈 | 答案旁的轻量反馈与回访 | 受理不冒充修复；任务继续按原流程办理 |
| 无法判断组织学到了什么 | 有范围的能力地图与任务观察 | 未知项保持未知，不用资产数冒充能力或收益 |

## 1. 选什么留下：从问题收件箱到候选判断

员工遇到问题时只需描述**眼前卡在哪里**，或对已有回答选一个原因：没找到、两份说法冲突、这次不适用、疑似过期。能引用原资料的位置就引用位置，不要求他们先选知识分类、编写条目。入口必须在其可访问的工作范围内；涉及敏感材料时只记录完成分派所需的最小信息，不把原文搬进公开队列。

资产负责人打开“问题收件箱”，先看到问题关联的任务类型、已有资料或结论、重复出现的线索、当前处理人及是否正在影响工作。可执行动作是：**关联已有知识并改善呈现；合并同类反馈；建立待核实候选；转交当前业务负责人处理；说明该问题一次性或变化太快，不予沉淀。** Agent 可帮助比较、去重和起草疑点，不能自行判断“这条值得正式发布”。一次性处理和不予沉淀都要给提问者可理解的回执。

只有当问题可能重复、复核成本值得投入、依据和适用条件能说清、维护责任能落实时，才进入候选判断。候选卡保留原问题、来源、尚缺证据、拟适用范围、负责人和下一步；**已保存、已分派、待确认、正式可引用**不能合成一个“完成”状态。若找不到有权确认的人，显示待决定并交业务负责人安排人手或缩小范围，不让积压被默认批准。

## 2. 员工怎样判断“这次能不能用”

员工从获授权的问答入口或任务旁的链接，输入具体问题及自愿提供的必要条件，例如所处理事项的类型和适用时间；未知条件允许留空。Agent 只在员工有权访问的资料中查找，不能把看不到的来源改写成泄露内容的摘要。若业务系统尚未连接，产品**不能假装知道当前任务的实时状态**，必须让员工自行核对或回到原系统。

结果不是一段不分来源的“最终答案”，而是一张可核对的结果卡：

- **当前可参考什么**：已确认结论、对应版本、来源和确认范围；若只有资料或 AI 整理，直接标为“供核对，尚未确认”。
- **要满足什么条件**：适用条件、例外和需重新复核的时间或变化；明确哪些条件已由可靠来源核对、哪些仅由员工填写或尚未知晓。
- **下一步能做什么**：查看有权访问的依据、补充条件、请有权人确认，或报告“这次不适用”。即便全部条件看似满足，也只表示结论在已确认的范围内**可供参考**，不表示当前业务获批。

有相关资料但没有确认结论时，停在“资料可参考，不能据此宣称已确认”；条件缺失时提示补条件或找人；来源冲突、疑似过期或超出适用范围时并列呈现分歧，标明“暂不能据此判断”及负责的处理路径；员工无权看依据时不给泄露内容的答案，提示申请授权或走既有人工渠道。没有有权接手者时，不能显示一个虚构的“已转交专家”，而要提示业务负责人待分派和当前任务仍需按原规则处理。

产品要观察的不是“回答了几次”，而是员工是否在同类任务中更快找到**能核对、适用或明确需要人确认**的结果；员工仍反复找专家时，要区分是入口没找到、结果缺证据，还是该任务本来就必须逐次审批。

## 3. 专家怎样判断，维护负担交给谁处理

专家进入“待判断”时，看见的不是 Agent 草稿排队，而是已经整理好的判断卡：具体争议、可查来源、旧版结论与适用范围、缺失条件、相关反馈，以及自己的确认会影响哪些获授权使用者。原资料的说法、Agent 的推断、此前的人类确认要分层展示；不能让专家替未经核实的摘要承担责任。

专家可以**确认特定版本和范围、缩小范围、要求补证、暂缓、拒绝或指出该事项必须回到业务会议/审批**；每个决定有理由和回执。草稿改动后原确认不沿用；旧版错误需提示停止引用并关联修订，不能直接覆盖历史。必要的会议仍由人召开，Workbench 负责把待决定点和证据准备好、会后记录有权人确认的结论，不替会议作取舍。

“待判断”和“待维护”分开：资产负责人查看即将复核、冲突、无 owner、延期与积压，并可请求转交或升级；无人实际接收时责任不自动转移，版本也不自动发布。业务负责人据此决定投入时间、调整优先级、限制知识适用范围或继续人工处理。专家能看到自己的贡献并申请更正归因，原审核身份仍留痕；管理端不以答题速度、反馈数量或 Agent 使用量评价个人。

要验证这一设计，需同时看重复解释是否减少、专家核对 AI 草稿与维护占用了多少时间、拒绝和补证是否能真实生效。若专家更忙或待办积压，就缩小需正式确认的内容或补维护资源，而不是把“待办清零”当成成功。

## 4. 使用和纠错怎样嵌进日常工作

优先提供获授权的问答入口及结果卡旁的“哪里不对”操作；业务系统暂时无法集成时，先用任务旁链接或责任人登记，明确说明这仍需要离开原任务，不声称已经一键嵌入。反馈按“没找到、看不懂/不敢用、条件不符、资料冲突、疑似过期”选原因，允许补一句非敏感的情境说明，自动关联**员工有权引用的**知识版本或来源，不强制提交完整聊天、完整 Prompt、Tool Call trace 或敏感业务原文。

员工在原入口或回访链接看见“已收到 → 已分派/待补充 → 人正在判断 → 已有处理结论/不予沉淀”，并能区分**问题有了去向、知识版本已更新、当前业务问题已解决**。后两者不是前者的自然结果。若反馈触及当前任务的审批或安全风险，员工仍按原业务流程立即处理，不能等待知识修订代替业务处置。负责人回应“只是展示不清”“需要补依据”“需要重新确认”“这次是例外”“不适合沉淀”时，应说明下一步由谁负责；已修订的结论也要在下一次类似使用中才能检验是否更好。

反馈的访问与分派沿用原资料及团队边界：无权的人不查看敏感来源、他人的工作轨迹或跨团队报告。只有在获授权、最小化且有小样本保护的条件下，才汇总问题类型和后续结果；没有反馈不代表没有错误。

## 5. 管理者怎样看见能力与缺口，而不是看个人排名

这里的**组织能力**是团队在明确情境下完成一类任务的本领，由人的经验、依据、流程、工具和责任共同支撑；**沉淀程度**是其中哪些关键判断能被其他获授权的人可靠复用；**维护容量**才是有无人手和时间持续修订已有内容。十篇文档或三个 Skill 不能直接等于十项或三项组织能力。

第一版先由资产负责人或业务负责人在**一类限定任务**中人工梳理候选能力地图：列任务、典型情境、关键判断点、责任团队，关联已有资料、已确认知识、稳定步骤及仍需逐次人工决定的部分。一个示意任务“设备异常处置”可拆成识别异常、判断影响、选择处置、升级审批和复盘；这是用于设计的拆法，不代表已盘点任何真实团队。地图入口按任务浏览，点击关键判断点进入详情，看“依据在哪、谁能用、确认到哪版、哪些条件不清、谁负责处理”，再选择**补证、请人确认、改入口、安排复核或明确保留人工路径**。没有业务访谈时只能称为“候选地图”。

每个判断点分别显示：完成任务是否有真实结果证据、依据和边界是否可靠、其他获授权的人能否复用、变化后能否更新、投入是否值得；**不合成一个能力分**。缺口状态要能分开：有人会但没留下依据；只有资料没有确认判断；结论缺边界或过期；有内容但找不到或无权使用；可用但缺维护人；已有使用却缺结果证据；以及“这里本就需要逐次人工决定”。管理者看到获授权范围内各状态与未知项，分母必须是**本次已梳理的任务和关键判断点**，不能推成全组织的能力覆盖率。

管理视图还应把任务缺口与问题积压、专家维护负担和业务结果放在一起。管理者可决定先补哪处证据、给哪个团队安排维护时间、何时缩小范围；不能查看个人消费轨迹，不能以 `actor_ref`、提问量、贡献量、处理速度做画像或排名。小样本和筛选组合可能反推个人时应抑制展示。能力地图的价值也待检验：如果内容“覆盖”但真实任务仍卡住，说明判断点拆错、入口不对或所谓覆盖根本没有得到验证。

## 一次贯穿演练：从无法判断到下一次可参考

以下是**虚构的产品演练**，不代表已有真实业务规则或试点：员工在办理任务时从获授权入口问“该用哪版清单”。结果卡列出旧纪要 A 和新模板 B 的出处，标出缺少任务类型与生效时间、目前不能确认；员工补充可共享的条件，仍有冲突，于是选择“请人确认”，原任务继续按既有审批路径进行。

问题收件箱把同类反馈关联为一个候选判断，专家在待判断卡看到两份来源与冲突，可以要求补证、拒绝泛化，或仅确认“A 适用于某类任务、B 自某时起适用于另一类任务”。只有经正式审核、发布并核实可供使用的**特定版本**，才在后续有权限的员工结果卡中作为已确认结论出现；前一位员工可看到受理、确认与实际更新各自的回执。下一次任务的条件若仍未知，产品依旧停在“请核对/请人确认”，而不是因为已有知识就自动批准。能力地图只在对应判断点关联这一版本，不据此宣称整类任务已具备成熟能力。

这个演练用来检查触点和例外路径是否闭合，不能证明使用者会采用、专家会省力或业务结果改善。

## 初版先做什么、暂不做什么

初版只围绕一类低风险、有可查依据的任务：一个获授权入口、区分资料和确认知识的结果卡、简短反馈与回访、问题收件箱、专家待判断卡、限定范围的候选能力地图。不能集成业务系统时允许手工接入，但必须如实显示入口和实时信息的局限。页面可以合并呈现，以上描述的是必要的用户动作和状态差别，不要求首版建设一套大而全的控制台。

不自动把资料升级成知识，不把一句 Prompt 当 Skill，不在 Workbench 重建业务执行器，也不把单次回答、发布、安装或加载计成业务收益。只有步骤稳定、可测试、权限和异常处理清楚时才考虑 Skill。正式资产要有来源、范围、责任、人工审核与可追踪版本；Git 审核、CI、人类批准、Provider 读回及下游权限门禁不能因产品交互而省掉。生产 Token、Cookie、密码、敏感业务原文、完整 Prompt/Tool Call trace 不应进入产品记录；资料、答案、反馈、地图与报表按团队和来源权限隔离。

交互能否让员工少重复确认、让专家不过载，以及能力地图能否指导投入，都是**待真实使用检验的假设**，不是此刻已实现的效果。具体观察和调整办法见[下一篇](04-初版假设与迭代.md)。
