# 3. 产品蓝图：Workbench 怎样承载这项能力

[前一篇](02-知识工程难在哪里.md)讲的是组织能力会在哪里断掉。这一篇把它变成可设计的产品：**Agent 帮人找到、比较和整理；Workbench 让人判断、维护与追踪；原业务系统继续办理具体任务。** 这些都是初版构想，不是已实现的功能或已验证的用户习惯。

## 先定一个完整闭环，不先定一排模块

产品的基本过程是：**工作中提问 → 看到可用依据或明确缺口 → 使用或请人确认 → 低负担反馈 → 专家处理变化 → 有权限的下一位使用者看到新状态。** 当场没有形成可复用结论也可以，员工仍需有明确的下一步。

Workbench 不是要求所有人每天登录的“知识建设后台”。员工更多从问题或反馈进入；专家在这里核对依据、限定范围和处理冲突；资产负责人维护发布后的有效性；管理者看团队在哪类任务上反复受阻、维护能力够不够。前台入口可以与 Agent 对话或工作任务靠近，原业务系统依然保有实时状态、审批和执行权。

初版先明确几种不同的产品对象，避免把一次提问直接变成一条“已发布知识”：**资料**是可核对的来源；**问题与反馈**记录当前工作遇到了什么；**候选判断**是等待人核实的说法；**已确认知识**包含依据、条件、例外、确认与版本；**使用记录**只需说明某版本是否在获授权的任务中被引用、有什么问题，不能采集完整对话或建立个人画像。候选判断不会因 Agent 生成、有人提交或进入队列而自动升级为已确认知识。

| 使用触点 | 谁主要使用 | 要完成的事 | 不能制造的错觉 |
| --- | --- | --- | --- |
| 提问与结果 | 员工 | 在当前问题旁看到出处、适用条件或“暂不能确认”；选择继续查证、请人判断或反馈 | 找到相关文件不等于当前业务已获批准 |
| 反馈与回访 | 员工、资产负责人 | 指出找不到、冲突、例外或过期；看到受理、待判断与实际修复的区别 | 报告被接收不等于知识已经修好 |
| 待判断与修订 | 专家、资产负责人 | 对照证据，补条件、拒绝、暂缓或确认特定版本；分派后续维护 | Agent 草稿或旧版确认不等于新版已获批准 |
| 团队问题视图 | 获授权的负责人 | 看问题集中在哪、待办是否超出维护能力、结果能否核实 | 不提供个人使用排行或未经证实的节省人力数字 |

这些是按角色和任务设计的触点，不意味着初版必须做成四个独立应用；入口与页面可以因接入条件而变，但对象状态和责任不能消失。

## 员工：先解决眼前的事，知道何时不能照用

员工带着具体任务来，可能看见三类结果：有适用于当前条件的已确认结论；只有相关资料或待核实说法；来源冲突、条件不足，需要人进一步判断。交互重点不是一段总能回答的文字，而是**“现在能参考什么、依据在哪、哪些情况不适用、下一步怎么办”**。员工只能看到自己有权查看的内容与出处；不能让摘要泄露看不到的材料。

没找到、看不懂、认为结论不适用或发现规则过期时，应能就当前内容留一个问题，尽量不要求先选知识分类、填写完整文章。反馈应能看到受理状态和回访方式；当前任务若需要业务批准，仍按原流程办理，不能靠 Agent 回答或报错状态跳过。

## 专家：判断证据与边界，不批量给 AI 背书

Workbench 给专家展示的是待判断点：发生了什么、现有来源与旧结论是什么、冲突在哪里、哪些条件未核实、是否反复出现。Agent 可辅助梳理资料，但要清楚区分**来源说了什么、Agent 推断了什么、人确认了什么**。

专家可以补充条件、拒绝、暂缓或要求补证；确认针对特定内容与版本，改动后需要重新确认。必要时组织会议解决分歧，工作台先准备待决定问题，事后由有责任的人记录结论与边界。旧版本有问题要能标记并追踪修订，不能静默改写。专家的贡献应可查看、可申请更正归因，原审批记录仍保留；审核队列积压时要能向业务负责人呈现负担，而不是把未处理事项伪装成已解决。

## 资产负责人和管理者：维护能力，而不是监控个人

资产负责人需要知道哪些内容即将复核、哪些反馈有冲突、哪条结论无维护人、哪些旧内容应停止使用。负责人负责明确归属、发起修订和处理无人接手情形；平台帮助追踪，不替他们决定业务规则。

管理者需要的是获授权范围内的团队问题类型、积压、维护投入与任务结果，以便决定投入资源或缩小覆盖范围。不得以个人问答次数、反馈量、`actor_ref` 或处理速度排名推断绩效；小样本、交叉筛选能反推个人时应抑制展示。让专家愿意参与，既要看得到劳动的贡献，也要保证他们能说“不”、能指出边界、不会被当作无限审核资源。

## 用一个示意过程检验闭环

下面是**虚构的产品演练**，不是经过访谈确认的业务事实或已选定的试点：有人在办理任务时看到旧纪要要求 A 清单，新模板却是 B 清单。Agent 不选择一个更像答案的版本，而是列出两份材料的出处，提示当前无法确认适用关系。员工标出冲突、留下不含敏感原文的必要背景；Workbench 把问题交给有权处理的人。专家核实后可能确认“某类任务从某日开始用 B，另一类仍用 A”，也可能认为依据不足、要求上会。被确认且完成正式审核的版本可供有权限的下一位同事引用；若新情况不满足条件，仍提示再确认。

这段过程不是为了证明“采购场景成立”，而是检查平台共同机制是否齐全：来源、权限、版本、适用条件、人的决定、反馈去向和下一次使用。换成设备处置或设计决策时，具体判断由领域人员决定，上述机制是否仍可复用，才是平台性的待验证假设。

## 初版需要什么，刻意不做什么

初版先围绕一类低风险、可追溯的判断任务打通使用与反馈：呈现资料和已确认结论的差别，显示适用条件和不确定性；允许就一次使用提交问题；给专家提供依据、裁量和修订入口；让有权限的人看见当前状态与历史变化。首次接入即便需要人工登记反馈，也要如实说明，不宣称已有无缝业务集成。

不把所有资料自动升级为正式知识，不把一句 Prompt 当成 Skill，不在 Workbench 重造任务执行器，也不从调用数自动推算节省人力。只有在步骤稳定、可测试、权限和异常处理清楚时，才考虑让 Skill 辅助执行；发布后的安装、加载或队列受理与实际使用、业务效果都要分开看。

正式资产必须有来源、范围、责任、人工审核与可追踪版本；不能把草稿、等待处理或技术请求成功称为“可用”。Git 审核、CI、人类批准、发布后的 Provider 读回和下游权限边界不能由产品体验跳过。工作台不应收集生产 Token、Cookie、密码、敏感业务原文或完整 Prompt/Tool Call trace；资料、答案、反馈与统计均须按来源和团队权限隔离。

这些产品取舍为什么合理、以后用什么反馈改变它们，见[下一篇](04-初版假设与迭代.md)。具体工程状态、接口与验收仍由方案另行定义，本篇不将产品意图当成已交付事实。
