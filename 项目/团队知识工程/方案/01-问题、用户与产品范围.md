# 问题、用户与产品范围

## 1. 业务问题

团队并不是没有资料，而是资料没有形成可持续使用的组织资产：

- 会议、复盘、案例和规则散落在不同位置；
- 使用者不知道哪些内容可信、适用到什么范围；
- Agent 能生成回答，却不一定能说明依据、版本和例外；
- 内容更新没有明确 owner，错误反馈不能回到修订流程；
- 过早建设大平台，反而增加维护成本和使用门槛。

因此产品的核心不是“让模型回答更多问题”，而是让团队能够持续生产和维护可靠知识。

## 2. 角色与责任

| 角色 | 需要完成的动作 | 不要求具备 |
|---|---|---|
| 贡献者 | 提交资料、确认草稿、补充来源、反馈结果 | Git、JSON、命令行 |
| 领域 steward | 确认事实、范围、例外、敏感等级和复核时间 | 编程能力 |
| 审核人 | 审核跨域、敏感或高风险内容的发布 | 维护系统代码 |
| 平台 owner | 维护模板、门禁、权限、发布、故障处理和 coding agent 任务 | 让每个人学习底层工具 |
| 使用者 | 查询、查看引用、报告错误和过期 | 了解内部实现 |

早期平台 owner 可以只有 1 人，但每个知识域必须有 steward 和备份 steward。

## 3. 首期核心场景

首期只选一个场景，优先满足“低风险、频繁发生、结果可回放”：

1. **流程问答**：把经过确认的流程、规则和例外整理成可引用条目。
2. **项目复盘沉淀**：从复盘资料生成事实、问题、决策和后续动作候选。
3. **研究资料整理**：把来源、结论、适用范围和未知项整理成证据卡片。

场景选择必须写清：输入来源、责任人、正式产出、使用者、失败代价和人工 fallback。

## 4. MVP 必须有

- 收件箱：接收资料、会议记录、复盘和反馈；
- 知识卡片：Agent 生成，但人确认事实和范围；
- 变更包：平台生成 Git 分支/MR，不要求业务人员操作 Git；
- 确定性门禁：schema、来源、敏感信息、链接和重复检查；
- 审核发布：steward/审核人批准后才形成正式版本；
- 索引确认：WeKnora 读回真实版本、来源和权限状态；
- 检索引用：使用者看到来源、版本和适用范围；
- 反馈复核：错误、过期、无帮助和正向样本进入任务队列；
- 最小审计和故障补偿。

## 5. 明确不做

- 不让模型直接把回答写成正式知识；
- 不让 Agent 直接 push 或 merge `main`；
- 不在首期建设多租户微服务、Agent 市场和完整 Plugin 平台；
- 不以 SkillHub 网页自动化作为正式发布接口；
- 不把 Bot Memory、群聊结论或运行日志当作正式知识；
- 不把 WeKnora 改造成知识治理系统；
- 不在没有安全 owner、审批和回滚证据时做生产写入。

## 6. 价值与退出标准

首期价值由实际使用证明，而不是文档数量证明。至少观察：

- 重复提问和重复整理是否下降；
- 有效引用率和用户纠正率；
- 从草稿到发布的耗时；
- 过期内容和复核任务关闭时间；
- 故障是否能被发现、解释和人工接管。

如果一个场景连续使用后不能减少重复劳动，应停止扩展，先重新评估场景，而不是继续堆平台能力。
