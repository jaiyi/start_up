# 问题、用户与产品范围

## 1. 业务问题

团队不只是缺少知识，也缺少把知识稳定转成 Agent 能力的机制：

- 资料、会议、复盘和规则散落，内容无法持续维护；
- Agent 能回答问题，却不一定能说明依据、版本和适用范围；
- 同一类任务反复依赖个人经验和临时 Prompt，无法复用；
- Skill 没有输入输出契约、权限边界、测试和版本，运行结果不可控；
- 反馈不能判断应该修知识、修 Skill、修权限还是修流程；
- 一开始建设大平台，复杂度超过团队维护能力。

因此目标是**让业务知识变成可引用资产，让高频任务变成可运行 Skill**。

## 2. 用户与责任

| 角色 | 主要动作 | 负责什么 |
|---|---|---|
| 贡献者 | 提交资料、提出任务、确认草稿、反馈结果 | 输入事实和业务需求 |
| 领域 steward | 确认知识事实、范围、例外和复核周期 | 知识正确性 |
| Skill owner | 定义任务边界、契约、测试、依赖和预期结果 | Skill 行为和质量 |
| 审核人 | 审核跨域、敏感、高风险知识或 Skill | 发布责任 |
| 平台 owner | 维护模板、门禁、profile、权限、发布、故障和 coding agent | 平台可靠性 |
| 使用者 | 查询知识、选择 Skill、确认结果、报告问题 | 使用效果和反馈 |

早期平台 owner 可以只有 1 人，但每个知识域至少有 steward/备份 steward，每个生产 Skill 必须有 owner/backup owner。

## 3. 首期核心场景

选择一个“低风险、频繁发生、结果可回放”的任务，例如：

- 研究资料初筛：Skill 检索已批准知识，整理来源和证据卡片；
- 流程规则检查：Skill 根据业务输入和知识规则生成检查结果；
- 项目复盘整理：Skill 把复盘材料整理成知识候选和行动项。

场景选择必须写清输入、知识依赖、Skill 产出、使用者、失败代价、人工 gate 和 fallback。

## 4. MVP 必须有

### 知识能力

- 收件箱和知识卡片；
- 来源、证据、适用范围和复核日期；
- Git/CI 变更包、审核和回滚；
- WeKnora 索引、ACL、来源和版本引用；
- 反馈和复核任务。

### Skill 能力

- Skill 需求登记和模板化创建；
- input/output schema；
- 知识依赖、工具需求、effects 和风险等级；
- golden cases、回归测试和确定性门禁；
- Git/CI 版本、review、digest 和变更记录；
- 非生产 profile 装载、运行、反馈和回滚；
- SkillHub 不可用时的管理员发布 fallback。

### 运行能力

- 一次运行同时记录 knowledge version、skill version/digest、profile、run、工具调用和人工确认；
- 结果可以反馈到知识复核或 Skill 回归，不自动修改正式资产。

## 5. 明确不做

- 不让模型直接发布知识或 Skill；
- 不让 Skill 自行获得工具权限或扩大数据范围；
- 不把 WeKnora 当作 Skill Registry；
- 不把 Bot Memory、群聊结论或运行日志当正式资产；
- 不在首期建设多租户微服务、Agent 市场和高风险生产写入；
- 不以 SkillHub 网页自动化绕过审批；
- 不因为一个 Skill 在一次任务中成功就自动晋升 stable。

## 6. 价值与退出标准

观察：有效引用率、Skill 任务成功率、人工纠正率、重复提问/整理下降、从草稿到可用版本的耗时、过期率、回滚时间和复核关闭时间。

如果知识或 Skill 不能减少重复劳动、返工或交接成本，应停止扩展，先重新评估场景。
