# 端到端知识工作流

> 本文描述业务如何把知识和任务能力变成可运行资产。数据字段见[数据、状态与可追溯性](./06-数据、状态与可追溯性.md)，发布门禁见[发布、安全与故障处置](./07-发布、安全与故障处置.md)。

## 1. 两条生产线

### 知识生产线

```text
资料/会议/复盘
  → 收件箱
  → Agent 生成候选知识卡片
  → 贡献者确认事实和来源
  → steward 确认范围、例外和敏感等级
  → Git 变更包/MR
  → CI + 审核
  → WeKnora 索引确认
  → 可引用知识
```

### Skill 生产线

```text
任务需求/重复劳动
  → Skill 需求卡
  → Agent 生成 Skill 草稿
  → owner 确认输入、输出、边界和预期结果
  → 声明知识依赖、工具需求、effects、风险和 profile
  → 契约/安全/golden/regression 检查
  → Git 变更包/MR
  → 审核
  → 非生产 profile 装载
  → 可回放运行
  → beta/stable 或退回修改
```

## 2. 两条线如何汇合

```text
用户任务
  → 选择 profile 和固定 Skill digest
  → Skill 调用 WeKnora 检索已授权知识
  → DSH 执行工具和人工确认
  → 返回结果、知识引用、Skill 版本和运行状态
  → 用户/业务结果反馈
  → 知识复核任务 或 Skill 回归任务
```

Skill 不复制知识正文；运行时必须获得结构化的 `knowledge_id/version/source`。知识版本变化、Skill 契约变化和 profile 变化都应能从一次 run 中识别。

## 3. 每一步的责任和证据

| 步骤 | 责任人 | 输出 | 最低证据 |
|---|---|---|---|
| 收件/需求 | 贡献者 | 原始资料或 Skill 需求 | 来源/任务、捕获人、时间 |
| 生成草稿 | 模型/平台 | 知识或 Skill 草稿 | 输入引用、生成 run |
| 业务确认 | 贡献者/steward/owner | 已确认草稿 | 差异、确认人、待解决项 |
| 确定性验证 | 脚本/CI | 门禁结果 | schema、secret、测试和依赖结果 |
| 审核 | steward/审核人 | approved 变更 | approval、版本、理由 |
| 发布/装载 | worker/管理员 | published 或 loaded/异常 | index job、release、digest、profile |
| 运行 | 使用者/DSH | 结果和运行记录 | run、knowledge、skill、tool、人工 gate |
| 反馈 | 使用者 | 复核或回归任务 | 上下文、版本、差异和业务结果 |

## 4. 反馈分流

- 知识事实、范围、例外或引用错误 → 知识复核；
- Skill 输入输出、步骤、工具调用或结果质量错误 → Skill 回归/修订；
- 权限、敏感性或 profile 错误 → 权限治理任务；
- 运行基础设施失败 → 平台故障任务；
- 业务需求发生变化 → 新的 Skill/知识需求。

反馈不能直接覆盖正式资产。一次成功运行也不能自动形成知识规则或 stable Skill。

## 5. 非程序员体验

业务人员只需要理解：**提交、确认、审核、选择、运行、反馈**。分支、commit、MR、pipeline、index job、package digest 和 profile 细节可以查看，但由平台 owner 和 coding agent 维护，不要求业务人员手工操作。

## 6. 异常分支

来源不足停在 candidate；契约或测试失败停在 validating；审核退回停在 authoring/reviewing；索引或装载失败进入补偿；provider 超时进入 unknown/reconciling；高风险动作没有 approval 则拒绝；所有异常保留人工流程。
