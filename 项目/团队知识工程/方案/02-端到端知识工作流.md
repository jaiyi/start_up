# 端到端知识工作流

> 本文只描述业务如何流转。系统字段和实现细节见[数据、状态与可追溯性](./06-数据、状态与可追溯性.md)，发布门禁见[发布、安全与故障处置](./07-发布、安全与故障处置.md)。

## 1. 主流程

```text
资料/会议/复盘
  → 收件箱
  → Agent 整理成候选卡片
  → 贡献者确认事实和来源
  → steward 确认范围、例外和敏感等级
  → 生成 Git 变更包
  → CI 检查 + 审核
  → 合并正式源
  → WeKnora 索引并读回确认
  → 使用者检索和引用
  → 反馈
  → 复核任务
  → 新一轮变更
```

## 2. 每一步的责任和证据

| 步骤 | 主要责任人 | 输入 | 输出 | 最低证据 |
|---|---|---|---|---|
| 收件 | 贡献者 | 原始资料或链接 | 收件箱记录 | 来源、捕获人、时间 |
| 整理 | 模型/平台 | 收件箱记录 | 候选知识卡片 | 输入引用、生成 run |
| 事实确认 | 贡献者 | 候选卡片 | 已确认草稿或退回 | 确认人、差异、缺口 |
| 范围确认 | steward | 草稿和来源 | 待审核变更 | 适用范围、例外、复核日期 |
| 发布审核 | steward/审核人 | Git diff、CI 结果 | approved 版本 | approval、commit、CI |
| 索引 | worker/管理员 | approved 版本 | published 或异常 | index job、真实读回 |
| 使用 | 使用者/DSH | 查询问题 | 带来源的结果 | document、version、ACL |
| 反馈 | 使用者 | 结果和业务上下文 | 反馈记录 | run、版本、差异 |
| 复核 | steward | 反馈任务 | 新 MR、延期或拒绝 | 决策、owner、下一步 |

## 3. 哪些内容可以自动做

模型可以做 OCR、转写、摘要、分类、字段提取、重复候选和草稿；脚本可以做 schema、路径、链接、secret、依赖和版本检查；worker 可以做索引任务、状态轮询、重试和提醒。

自动化不能替代：事实确认、适用范围和例外判断、敏感性判断、正式发布、撤回、退役、回滚以及任何生产写入。

## 4. 反馈如何回流

反馈先分类为错误、过期、无帮助、权限问题、重复内容、工具失败或正向样本。反馈必须关联当时使用的知识版本或运行记录，随后由 steward 决定：

- 生成新的知识变更；
- 生成 Skill 回归样本；
- 标记待复核或延期；
- 拒绝并记录原因；
- 触发冻结、回滚或风险升级。

反馈不能直接覆盖正式正文。一次运行成功也不能直接变成组织规则。

## 5. 异常分支

- 来源不足：停在 candidate，要求补充证据；
- 事实或范围有争议：退回 reviewing，不发布；
- CI 失败：不允许合并；
- provider 超时：进入 unknown/reconciling，不猜测结果；
- WeKnora 索引失败：保留旧索引，创建补偿任务；
- 回调丢失：通过轮询或人工读回对账；
- 反馈显示业务结果恶化：冻结、回滚并复盘；
- 任一系统不可用：回到人工 MR、管理员索引或人工复核。

## 6. 非程序员看到的体验

业务人员只需要理解五个动作：**提交、确认、审核、查询、反馈**。分支、commit、MR、pipeline、index job 和 trace 可以查看，但不要求业务人员手工执行。平台 owner 承担技术动作和故障补偿。
