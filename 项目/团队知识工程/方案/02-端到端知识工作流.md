# 端到端工作台工作流

> 本文描述用户如何在工作台中把资料变成知识、把工作方式变成 Skill，并把已发布资产交给 DeepSeek Harness。工作台不承载发布后的会话执行。

## 1. 一张总图

```text
工作台首页
  ├─ 从资料创建知识
  │   → Knowledge Creation Session
  │   → 材料 → 梳理 → 确认 → 提交 → 发布
  │
  └─ 从工作流创建 Skill
      → Skill Creation Session
      → 描述 → 建模 → 生成 → 测试 → 发布

资产与发布
  → 已发布知识 / Skill
  → 发布记录与 handoff
  → Feedback Candidate
  → 新的 Creation Session

DeepSeek Harness 会话工作台（下游）
  → discovery/load 已发布 Skill
  → 在自己的 Workspace/Session 中执行任务
  → 按自身工具、权限和人工批准策略运行
  → 返回结构化 feedback reference
```

“从资料创建知识”和“从工作流创建 Skill”都是启动动作。每次启动创建独立的会话、草稿和异步操作；知识与 Skill 会话可以并行，不能共享可变上下文。工作台里的 Creation Session 不等于下游 Harness Session。

## 2. 生产线一：会议/资料到知识

### 2.1 进入知识创作会话

用户点击“从资料创建知识”，平台创建独立的 `Knowledge Creation Session` 和 `Knowledge Draft`，然后在同一会话内接入材料。用户可以暂停、恢复或并行打开其他会话；材料、草稿、待确认项和异步操作不会串线。

用户可以上传会议纪要、粘贴文本、导入文件或提交已授权的资料链接。平台保存原始材料引用、捕获人、时间、workspace、来源类型和敏感等级。

原始材料不是正式知识，只能作为候选生成的依据。业务原文按权限和保留策略存放，不写入模型长期 Memory 或公开日志。

### 2.2 Agent 梳理

Agent 对材料做结构化梳理，至少区分事实、决策、规则/定义、行动项、争议、冲突和待确认事项。每一条候选都要带原文定位或来源引用。模型推断必须标为推断，不能伪装成原文事实。

### 2.3 讨论与确认

用户可以逐条接受、修改、合并、拆分或拒绝候选。Agent 可以解释抽取依据、提出更清楚的表达并提醒冲突，但不能替用户完成事实确认。

确认界面至少展示候选内容、原文证据、Agent 推断、用户差异、适用范围、例外、owner、steward 和复核日期。

### 2.4 提交和索引

```text
Knowledge Draft
  → schema/source/ACL 校验
  → Git branch/commit/MR
  → CI + steward review
  → approved revision
  → WeKnora ingest
  → index/Wiki 读回和引用验证
  → published knowledge
```

工作台展示已提交、审核中、已批准、索引中、可检索、失败待处理等状态；Git commit、MR、index job 和 provider receipt 作为展开证据。WeKnora 只接收已批准版本；索引失败时保留上一个可用版本并生成补偿任务。

## 3. 生产线二：工作流到 Skill

### 3.1 进入 Skill 创作会话

用户点击“从工作流创建 Skill”，平台创建独立的 `Skill Creation Session` 和 `Workflow Draft`。用户可以直接描述工作流、粘贴 SOP/模板、上传历史产物，或从 Feedback Candidate fork 出新的修订会话。Agent 的追问、建模、Skill 生成和测试都必须绑定当前 `session_id` 和 `draft_revision_id`。

### 3.2 描述工作方式

用户在 Skill 创作会话中用自然语言描述触发时机、输入、步骤、判断、例外、工具/知识依赖、输出和成功标准。

### 3.3 Agent 追问和建模

Agent 主动发现输入校验、输出结构、步骤依赖、边界条件、建议与执行的区别、知识依赖、工具需求、人工确认点和测试构造缺口。工作台将结果保存为 Workflow Draft。Workflow 是业务过程模型，不等同于最终 Skill。

### 3.3 生成 Skill 包

```text
skill/
├── SKILL.md                 # 用途、边界、步骤、输入输出、依赖
├── skill.yaml               # id、版本、owner、风险、effects、权限需求
├── schemas/                 # input/output 和配置契约
├── scripts/                 # 可选的确定性处理脚本
├── references/              # 可选模板、规则和示例
└── tests/
    ├── golden/              # 代表性样例和期望结果
    ├── boundary/            # 缺失、超范围和歧义输入
    ├── regression/          # 历史失败和人工纠正
    └── security/            # 越权、敏感数据和提示注入
```

实际目录和字段以目标 SkillHub/DSH 能力验证结果为准，不能把尚未验证的 loader 约定当成集成事实。

### 3.4 样例试跑和评测

用户将真实但已脱敏的样例放入测试区，查看输入、输出、知识引用、工具需求声明、期望与实际差异、失败原因、脚本/契约/权限门禁和版本比较。试跑只产生评测结果，不自动发布，也不会把样例中的新事实直接写成正式知识。

### 3.5 提交和发布

```text
Skill Draft
  → input/output/schema 校验
  → permission/effects/security 校验
  → golden/boundary/regression/security 测试
  → 用户确认
  → Git branch/commit/MR
  → review + CI
  → package + immutable digest
  → SkillHub release
  → 真实发布状态读回
  → DSH handoff metadata
```

一次成功的试跑不能自动晋升 stable。发布必须有 owner、审核和版本证据。SkillHub 不可用时可以走管理员 fallback，但必须明确实际发布路径和状态。

## 4. 发布交接协议

本项目对下游只交接**已批准资产的引用和完整性信息**，不交接一个自建运行时。最小交接记录包括：

```yaml
source_commit: <approved-git-commit>
asset_type: knowledge | skill
asset_id: <asset-id>
asset_version: <semantic-or-domain-version>
package_digest: sha256:...
knowledge_dependencies: []
required_capabilities: []
compatible_targets: []
distribution_status: published | fallback | unknown
handoff_target: <dsh-provider-or-admin-path>
```

交接状态只能说明版本是否已提交给目标适配器或管理员处理，不能替代 Harness 的 `loaded`、`running` 或 `succeeded`。目标 Harness 环境应自行验证 discovery/load，并返回可关联的 feedback reference。

## 5. 反馈分流

```text
Harness/业务系统反馈
  ├─ 事实、范围、来源或引用错误 → 知识复核候选
  ├─ 步骤、契约、输出或质量错误 → Skill 回归/修订候选
  ├─ 工作流步骤、人工节点或完成条件错误 → Workflow 修订候选
  ├─ 发布、安装、版本漂移或读回错误 → 分发故障候选
  └─ Harness/provider/业务运行问题 → 下游平台协作任务
```

反馈只作为候选或任务，不直接覆盖正式资产。模型可以整理反馈，人和 CI 决定是否进入正式生产线。

## 6. 责任与证据

| 步骤 | 责任人 | 用户可见产物 | 最低证据 |
|---|---|---|---|
| 接收材料 | 贡献者 | 原始材料卡片 | 来源、捕获人、时间 |
| Agent 梳理 | 模型/平台 | 候选卡片 | 原文引用、生成记录 |
| 知识确认 | 贡献者/steward | 已确认知识草稿 | 修改差异、确认人、待解决项 |
| Workflow 建模 | 贡献者/Skill owner | 工作流草稿 | 输入、步骤、判断、例外、成功标准 |
| Skill 生成 | 模型/平台 | Skill 文件包 | schema、依赖、生成记录 |
| 试跑评测 | 用户/CI | 测试结果 | 样例、版本、输出差异、门禁 |
| 提交审核 | owner/reviewer | MR/release | commit、approval、理由 |
| 索引/发布 | worker/provider | WeKnora/SkillHub 状态 | receipt、版本、digest、读回 |
| 下游交接 | 分发/运行 owner | handoff record | target、package digest、状态 |
| 反馈 | Harness 使用者/owner | 修订候选或协作任务 | 版本引用、问题分类和必要证据 |

## 7. 非程序员体验

业务人员只需要理解：

```text
放入材料 → 讨论确认 → 提交
描述工作 → 试跑修改 → 发布
发布交接 → 在 DeepSeek Harness 会话中消费 → 反馈
```

Git、commit、MR、pipeline、index job、package digest 和 handoff record 可以查看，但不要求业务人员手工操作。Workspace、Session、工具调用和运行时人工批准由 DeepSeek Harness 界面负责。
