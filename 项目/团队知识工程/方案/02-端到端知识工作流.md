# 端到端知识工作流

> 本文描述业务如何把知识和任务能力变成可运行资产。数据字段见[数据、状态与可追溯性](./06-数据、状态与可追溯性.md)，发布门禁见[发布、安全与故障处置](./07-发布、安全与故障处置.md)。

## 1. 两条生产线

### 知识生产线

```text
资料/会议/复盘
  → 收件箱
  → Agent 生成候选知识卡片
  → 贡献者确认事实和来源
  → steward 确认范围、例外和敏感等级
  → Git 变更包/MR
  → CI + 审核
  → WeKnora 索引确认
  → 可引用知识
```

### Skill 生产线

```text
任务需求/重复劳动
  → Skill 需求卡
  → Agent 生成 Skill 草稿
  → owner 确认输入、输出、边界和预期结果
  → 声明知识依赖、工具需求、effects、风险和 profile
  → 契约/安全/golden/regression 检查
  → Git 变更包/MR
  → 审核
  → 非生产 profile 装载
  → 可回放运行
  → beta/stable 或退回修改
```

## 2. Plugin 能力线（长期扩展）

Plugin 不是业务任务 Skill，而是向平台提供工具或外部系统适配能力。首期只预留契约和运行归因，不建设开放 Plugin 市场；待双资产稳定后，先以一个低风险、受控的适配器验证管理闭环：

```text
外部系统/工具需求
  → Plugin manifest/适配器草稿
  → owner 确认 tools、权限、数据范围和兼容性
  → 安全/依赖/SBOM/沙箱/超时幂等检查
  → Git 变更包/MR
  → 审核和打包 digest
  → 安装/启用/health 读回
  → profile 注册工具
  → Skill 调用并记录 tool call
  → 禁用、撤回或回滚
```

Plugin 提供工具能力，Skill 组合工具完成业务任务；一个 Plugin 可以被多个 Skill 复用，一个 Skill 也可以依赖多个 Plugin。Plugin package 可以捆绑 Skill，但安装单位和业务能力单位仍然分离。

## 3. 分发与同步线（Skill/Agent）

分发线只处理已经通过治理和发布门禁的版本，不决定知识事实、Skill 质量或 Plugin 权限：

```text
批准变更
  → package/digest
  → SkillHub、TeamAI distribution adapter 或管理员流程
  → 目标 dsh/profile 安装或注入
  → 实际版本/文件清单/profile 读回
  → beta/stable 生效
  → run 关联 installed revision
```

TeamAI 通过团队 Git 仓库提供 `init`、`pull`、变更分支上的 `push`、版本切换和本地 dsh 注入能力。它适合解决多人本地配置同步、新人接入、版本一致性、回滚和跨团队 Agent 包复用，但不是首期硬依赖。

安全约束：

- `teamai push` 只能推送个人分支或变更请求，不得直达 protected `main`；
- Hook 可以降低同步成本，不得绕过 CI、人工审核、版本 pin、权限授予或稳定发布；
- 自动同步只同步已批准版本，不能让未审核内容立即全员生效；
- pull/install 半成功、版本漂移、删除清理失败和状态未知必须进入对账，不得显示为成功；
- 外网或跨安全域环境只允许脱敏/公开样本，不能自动同步生产凭据、敏感正文或高风险工具。

TeamAI 未验证或不可用时，使用 SkillHub 或管理员发布；分发实现可替换，但 package、digest、profile、安装读回和回滚语义不能丢失。

## 4. Agent Manifest 的后续复用

Agent Manifest 是多个 Skill、知识 Profile、模型/运行策略和工具依赖的组合/分发包，适合将一个团队开发的 Agent 复用到其他团队：

```text
Agent Manifest
  → 引用固定 Skill/version/digest
  → 引用知识 profile/version
  → 声明模型、工具和运行策略
  → 依赖审核通过
  → 分发到目标 dsh/DS Bot
  → 运行时仍按 Skill、知识和 Plugin 各自归因
```

它不是新的 canonical source，也不能替依赖资产审批；一个 Agent 包不能绕过 Skill 回归、知识 ACL、Plugin 权限或人工 gate。跨团队数字员工属于 P3 以后或更远期场景，不阻塞单团队 MVP。

## 5. 两条线如何汇合

```text
用户任务
  → 选择 profile 和固定 Skill digest
  → Skill 调用 WeKnora 检索已授权知识
  → DSH 执行工具和人工确认
  → 返回结果、知识引用、Skill 版本和运行状态
  → 用户/业务结果反馈
  → 知识复核任务 或 Skill 回归任务
```

Skill 不复制知识正文；运行时必须获得结构化的 `knowledge_id/version/source`。知识版本变化、Skill 契约变化和 profile 变化都应能从一次 run 中识别。

## 6. 每一步的责任和证据

| 步骤 | 责任人 | 输出 | 最低证据 |
|---|---|---|---|
| 收件/需求 | 贡献者 | 原始资料或 Skill 需求 | 来源/任务、捕获人、时间 |
| 生成草稿 | 模型/平台 | 知识或 Skill 草稿 | 输入引用、生成 run |
| 业务确认 | 贡献者/steward/owner | 已确认草稿 | 差异、确认人、待解决项 |
| 确定性验证 | 脚本/CI | 门禁结果 | schema、secret、测试和依赖结果 |
| 审核 | steward/审核人 | approved 变更 | approval、版本、理由 |
| 发布/装载/分发 | worker/管理员/TeamAI adapter | published、loaded 或异常 | index job、release、digest、distribution target、installed revision、profile |
| 运行 | 使用者/DSH | 结果和运行记录 | run、knowledge、skill、tool、人工 gate |
| 反馈 | 使用者 | 复核、回归或分发故障任务 | 上下文、版本、差异和业务结果 |

## 7. 反馈分流

- 知识事实、范围、例外或引用错误 → 知识复核；
- Skill 输入输出、步骤、工具调用或结果质量错误 → Skill 回归/修订；
- Plugin API、凭据、安装、兼容性、健康或运行时错误 → Plugin/平台故障任务；
- 分发同步失败、版本漂移、安装读回失败、Hook 冲突或删除清理失败 → 分发故障任务；
- 权限、敏感性或 profile 错误 → 权限治理任务；
- 运行基础设施失败 → 平台故障任务；
- 业务需求发生变化 → 新的 Skill/知识需求。

反馈不能直接覆盖正式资产。一次成功运行也不能自动形成知识规则或 stable Skill。

## 8. 非程序员体验

业务人员只需要理解：**提交、确认、审核、选择、运行、反馈**。分支、commit、MR、pipeline、index job、package digest 和 profile 细节可以查看，但由平台 owner 和 coding agent 维护，不要求业务人员手工操作。

## 9. 异常分支

来源不足停在 candidate；契约或测试失败停在 validating；审核退回停在 authoring/reviewing；索引或装载失败进入补偿；provider 超时进入 unknown/reconciling；高风险动作没有 approval 则拒绝；所有异常保留人工流程。
