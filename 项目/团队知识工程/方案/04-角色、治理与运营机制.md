# 角色、治理与运营机制

## 1. 三类责任

```text
模型：提取、摘要、分类、起草、发现冲突、生成测试候选
脚本/CI：校验 schema、权限、依赖、secret、回归和差异
人：确认事实、范围、任务边界、风险、批准发布和高风险动作
```

## 2. RACI

在原有角色之外，平台 owner 负责可复用的 `team-knowledge-workbench` 产品包和宿主市场交付；team asset owner 负责本团队 `team-knowledge-asset` 的 Git/WeKnora/ACL/taxonomy；WeKnora space admin 负责索引空间和权限读回；distribution/runtime owner 负责 DSH/SkillHub/TeamLab 交接。多个团队可安装同一 Workbench，但不能共享可变草稿、资产授权或审计上下文。当前用户身份通过 DSH Desktop 认证上下文进入工作台；后端负责映射 `principal_id`、团队成员和角色，并重新校验 asset-space ACL。


| 活动 | 平台 owner | Distribution/runtime owner | 贡献者 | 知识 steward | Skill owner | Plugin/integration owner | 审核人 |
|---|---|---|---|---|---|---|---|
| 模板和门禁 | A/R | C | C | C | C | C | I |
| 提交资料/工作流需求 | I | I | R | C | C | C | I |
| 生成知识/Skill 草稿 | A | C | C | C | C | C | I |
| 确认知识事实和范围 | I | I | R | A/R | C | I | C |
| 确认 Skill 契约和预期结果 | I | C | C | C | A/R | C | C |
| 权限/effects/兼容性审核 | A/R | C | I | C | R | C | A |
| CI、安全和回归检查 | A/R | C | I | I | C | C | I |
| 发布知识/Skill | C | R | I | R | R | R | A |
| DSH 交接与能力验证 | C | A/R | I | C | R | C | I |
| 反馈分流 | R | R | C | A（知识） | A（Skill） | A（Plugin/平台） | C |
| 退役/回滚 | R | R | I | A（知识） | A（Skill） | A（Plugin/分发） | A |

merge event、outbox/worker、provider read-back 和 TeamAI/DSH 安装读回由平台 owner/Distribution owner 分别承担技术执行责任，业务 steward/Skill owner 仍承担内容和质量责任。任何 read-back 不完整时，不能由平台 owner 单方面将状态改为 published、released 或 loaded。

早期一人可以兼任多个角色，但知识责任、Skill 责任和分发责任必须分别明确，不能因为同一个人兼任就把审核、发布和安装读回混为一类。

### Creation Session 责任

每个会话必须有明确的 `owner_id`。owner 负责会话目标、输入材料、草稿推进、暂停/恢复、分叉和提交动作；协作者只能在授权范围内编辑当前会话。会话权限与正式资产权限分开：能编辑 Draft 不等于能批准 Asset Revision，能批准资产也不等于能批准下游 Harness 运行。

- **Session owner**：管理会话上下文、成员、待确认项和会话状态；
- **Session collaborator**：在会话范围内补充材料、修改草稿或运行测试；
- **Knowledge steward / Skill owner**：对正式知识事实或 Skill 契约、测试和质量负责；
- **Reviewer / publisher**：审批正式修订和发布；
- **Distribution/runtime owner**：负责 handoff 读回和下游能力验证；Harness runtime approval 由下游负责。

同一正式资产的并行会话发生 `base_revision` 冲突时，由 owner/steward 或 Skill owner 人工合并；不能由平台按最后写入者覆盖。


### 知识

事实、来源、适用范围、例外、敏感等级、跨域可见性、复核日期和是否足以形成通用规则。

### Skill

任务是否值得固化、输入输出是否完整、失败态和例外、知识依赖是否正确、工具/effects 是否必要、风险等级、测试结果、profile 兼容性、beta/stable、撤回和回滚。

### Plugin

Plugin owner 必须确认工具 manifest、外部系统边界、权限和凭据需求、宿主兼容性、依赖/SBOM、沙箱或进程隔离、超时/重试/幂等、health、禁用和回滚。Plugin 只能声明能力需求，不能自行授予权限或把 provider 响应变成系统指令。

### 分发

TeamAI 或其他 distribution adapter 的目标仓库、分支保护、版本 pin、SkillHub release/digest 一致性、profile 兼容、secret 扫描、Hook 限制、删除清理、安装读回、回滚和审计。平台 owner 还必须人工确认 merge commit、WeKnora read-back、SkillHub release digest、TeamAI target/installed digest 和 DSH profile/loaded digest 是否分别与批准版本一致。Agent Manifest 必须逐项引用已批准的 Skill、知识 profile 和工具权限，不能用组合包绕过任何依赖资产门禁。

### 共同

任何生产写入、不可逆动作、对外发送、权限扩大和数据范围扩大。发布交接也必须经过批准版本、目标范围确认和实际状态读回。下游 Harness 的运行时人工批准由 Harness/业务系统负责。

## 3. 审核与责任边界

业务责任人与技术执行人必须分开记录。`created_by`、`confirmed_by`、`approved_by`、`released_by` 和 `owner_id` 指向真实 DSH 用户或团队角色；`executed_by` 和 `service_identity_id` 指向实际执行 Git、WeKnora、SkillHub 或 TeamLab 外部调用的受控服务身份。Git bot 可以作为 commit author/committer，但 MR、commit trailer、asset metadata 和审计必须关联真实提交人、审核人和发布人。Agent 可以起草、测试和解释结果，不能作为唯一批准人，也不能使用个人长期 Token。

Git、WeKnora、SkillHub 和 TeamLab 可以复用内部服务接入配置，但每个团队的 asset-space、资源 ACL、操作范围和审计记录必须独立。DSH launch token 和 `desktopWorkbenchOwnership` 不能替代后端授权或作为其他组件的通用 credential。

## 4. 风险等级与 gate

| 级别 | 示例 | 默认控制 |
|---|---|---|
| L0 | 只读检索、证据卡片 | 可自动执行，记录审计 |
| L1 | 摘要、候选、草稿 | 可自动执行，标记未验证 |
| L2 | 隔离环境计算和回放 | 限资源、网络和数据范围 |
| L3 | 创建任务、修改临时状态 | 范围校验和可恢复记录 |
| L4 | 敏感读取、业务写入 | 人工确认、最小权限、读回比对 |
| L5 | 生产、不可逆或现场动作 | 强制 gate、双人审批、急停和回滚 |

Skill 只能声明能力需求，实际权限由 DSH profile、tool policy、用户、workspace、环境和运行时授权共同决定。

## 5. Skill 治理门禁

一个 Skill 进入 beta 前必须有：契约、知识依赖、effects/权限声明、golden cases、回归结果、owner、固定版本和非生产 profile。

进入 stable 前还必须有：真实任务证据、失败和人工纠正记录、依赖和 SBOM、digest、运行归因、回滚 pin、下一次复核日期和明确批准。

禁止：模型自动标 stable、相似度自动合并 Skill、Skill 自行增加工具、用一次成功运行替代回归、用 `latest` 代替固定版本。

## 6. Plugin 治理门禁（P4 起）

一个 Plugin 进入 `enabled` 前必须有：manifest、工具 input/output schema、最小权限和数据范围、Secret Manager 引用、依赖/许可证/SBOM、宿主兼容性、health/readback、安装审计、失败清理和回滚 pin。涉及敏感数据、网络写入或不可逆动作时，必须增加沙箱、人工确认、限流、幂等和读回比对。

Skill 质量治理与 Plugin 运行时治理分开：Skill 关注任务结果、知识依赖和回归；Plugin 关注工具安全、外部系统兼容性和运行可靠性；分发治理关注版本到达、目标一致性和交接证据。下游 Harness 负责会话运行和运行时权限，本工作台只接收必要反馈引用。

## 7. 运营节奏


知识 steward 检查事实/范围；Skill owner 检查契约/测试/effects；Plugin owner 检查 manifest/权限/兼容性/health；平台 owner 检查 CI、权限和发布证据。

### 每周复核队列

分别处理知识错误/过期/引用失效、Skill 失败/纠正率/契约冲突、Plugin API/health/权限/兼容性问题、profile 权限异常、索引/装载失败、merge event 丢失、outbox backlog、SkillHub release unknown、TeamAI digest mismatch、DSH handoff failure 和人工补偿任务。

### 每月质量回顾

同时看：有效知识引用率、Skill 任务成功率、Skill 调用次数、活跃用户数、技术/契约/业务成功次数、Badcase 报告数、已确认 Badcase 数、受影响调用数、反馈覆盖率、Plugin 可用率/故障率、分发同步成功率、版本漂移率、安装失败率、merge 到最终 read-back 的端到端时延、outbox backlog、worker retry/dead-letter、WeKnora index unknown、SkillHub release unknown、TeamAI digest mismatch、DSH handoff failure、新人接入耗时、跨团队复用率、人工纠正率、运行成本/延迟、版本回滚、过期率、复核关闭时间和重复劳动下降情况。

消费指标必须按实际 `skill_id/version/package_digest` 统计，并同时展示统计窗口、分母、unknown 数量、数据覆盖率、最后同步时间和最后对账时间。Skill owner 解释 Skill 质量和 Badcase；平台/分发 owner 解释版本、安装和交接数据；业务系统负责业务成功事实。不能把 SkillHub release、TeamAI install、DSH load 或无反馈推断为 Skill 使用或成功。

## 8. 反馈分流

| 反馈 | 进入的治理任务 |
|---|---|
| 事实、范围、引用错误 | 知识复核/MR |
| 输入输出不匹配 | Skill 契约修订 |
| 步骤或结果质量错误 | Skill 回归/MR |
| Plugin API、凭据、健康或兼容性错误 | Plugin 禁用/回滚和平台故障 |
| 分发同步、版本漂移、安装读回或删除清理错误 | 分发故障、回滚和人工对账 |
| 业务规则变化 | 知识和依赖 Skill 联合复核 |
| 运行基础设施失败 | 平台故障和补偿 |

反馈不直接覆盖正式知识或 Skill。试点先选择 5–8 名高频使用者和一个知识域/任务，证明双资产闭环有价值后再扩展。
