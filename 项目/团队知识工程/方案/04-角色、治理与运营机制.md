# 角色、治理与运营机制

## 1. 基本分工

```text
模型：提取、摘要、分类、起草、发现冲突
脚本：校验、扫描、计算、比较、阻断
人：确认事实、承担范围责任、批准发布、高风险决策
```

## 2. RACI

| 活动 | 平台 owner | 贡献者 | 领域 steward | 审核人 |
|---|---|---|---|---|
| 模板和门禁 | A/R | C | C | I |
| 提交原始资料 | I | R | C | I |
| 生成知识草稿 | A | C | C | I |
| 确认事实与来源 | I | R | A | C |
| 确认范围与例外 | I | C | A/R | C |
| CI 和安全检查 | A/R | I | I | I |
| 发布批准 | C | I | R | A |
| 反馈分级 | R | C | A | C |
| 退役/回滚 | R | I | A | A |

早期一人可以兼任多个角色，但责任不能因为自动化而消失。

## 3. 必须人工确认

- 原始事实是否被正确理解；
- 规则的适用范围、例外和反例；
- 敏感等级和跨域可见范围；
- 反馈是否足以形成通用知识；
- Skill 是否扩大工具能力或数据范围；
- 批准、撤回、退役和回滚；
- 任何生产写入、不可逆动作和对外发送。

## 4. 风险等级与 gate

| 级别 | 示例 | 默认控制 |
|---|---|---|
| L0 | 只读检索 | 可自动执行，记录审计 |
| L1 | 摘要、候选、草稿 | 可自动执行，标记未验证 |
| L2 | 隔离环境计算 | 限资源和网络，可自动执行 |
| L3 | 创建任务、改变临时状态 | 范围校验和可恢复记录 |
| L4 | 敏感读取、业务写入 | 人工确认、最小权限、读回比对 |
| L5 | 生产、不可逆或现场动作 | 强制 gate、双人审批、回滚/急停 |

Skill 只能声明需求，实际权限由 DSH profile、plugin/tool policy 和运行时授权共同决定。

## 5. 运营节奏

### 每次提交

贡献者确认来源、事实、适用范围、敏感等级和未知项；steward 确认责任、例外和复核日期。

### 每周复核队列

steward 处理新反馈、索引失败、过期内容、纠正率升高、无人负责条目和人工补偿任务。

### 每月质量回顾

平台 owner 统计发布耗时、有效引用率、纠正率、过期率、复核关闭时间、使用场景和故障记录，只选择 1–2 个高价值问题改进。

## 6. 反馈晋升条件

反馈要形成正式知识候选，至少具备：原始任务和上下文、当时使用的知识/Skill 版本、实际和预期结果、人工纠正或业务结果、适用/不适用范围、风险、owner 和下一次复核日期。

不满足条件的反馈停留在复核任务或实验记录。

## 7. 质量信号处置

| 信号 | 处理 | 禁止动作 |
|---|---|---|
| 引用失效 | 标记 stale，创建复核任务 | 自动删除 |
| 纠正率升高 | steward 复核规则/检索 | 自动改成任意旧版本 |
| 索引失败 | 重试/人工补偿，保留旧索引 | 报告成功 |
| 90 天零使用 | 提醒 owner 判断 | 自动退役 |
| 权限异常 | 冻结相关资产，升级 owner | 继续扩大范围 |
| 业务结果恶化 | 暂停、回滚和复盘 | 用模型解释替代事实 |

## 8. 试点采用

先选择 5–8 名高频使用者和 1 个知识域，不要求 40 人一次性迁移。贡献者只看到提交、确认、审核、查询、反馈五个动作；平台 owner 承担技术复杂度。试点证明减少重复劳动后，再扩展第二个知识域。
