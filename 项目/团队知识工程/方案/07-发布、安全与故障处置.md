# 发布、安全与故障处置

## 1. 一次知识发布

```text
生成变更包
  → 服务端校验路径、内容和幂等键
  → 创建分支和 MR
  → CI 门禁
  → steward/审核人批准
  → 合并受保护 main
  → 生成 release manifest
  → WeKnora ingest
  → 真实读回 index/document/version
  → 标记 published
```

业务人员不需要手工执行 branch、commit、MR 或 pipeline；这些动作由平台 owner 维护的工作流完成。

## 2. CI 门禁

P1 至少检查：Markdown/frontmatter/schema、ID 和路径、来源、owner、steward、敏感等级、复核日期、secret/个人敏感信息、重复 canonical key、链接、CODEOWNERS 和 protected main。

CI 只能判断机器可验证的事实，不能替代 steward 判断业务规则是否正确。

## 3. 审核规则

- 结构和格式变更：至少 1 名 steward；
- 事实、范围、敏感等级变更：steward + 领域审核人；
- 跨域、机密、权限和高风险动作：双人审核或平台 owner 额外批准；
- 合并前重新检查 head SHA、CI 和 approval；
- 紧急撤回可先冻结/退役，再补齐变更和复盘。

## 4. 权限和风险

Skill 只能声明能力需求，不能自行获得权限。实际权限由用户、workspace、DSH profile、tool policy、环境和运行时授权共同决定。

L0/L1 只读和候选生成可以自动执行；L2 隔离计算限制资源；L3 创建任务需要范围校验；L4 敏感读取和业务写入需要人工确认；L5 生产或不可逆动作必须人工 gate、双人审批、可回滚或急停。

高风险工具默认不暴露给普通 Agent。任何工具调用都要重新校验 schema、ACL、风险等级和 approval。

## 5. 数据和审计

- Git 只保存脱敏内容、样本和引用；
- WeKnora 按文档、空间、用户和业务域过滤权限；
- Secret 只通过 Secret Manager/受控运行时提供，不进入 Prompt、Skill、Git 或 trace；
- 审计至少记录 actor、action、resource、version、source commit、profile、request、reason、result 和时间；
- 审计需要能关联 Git MR、CI、WeKnora index job、approval、run 和最终状态。

## 6. 故障处置

- CI 失败：不发布；
- WeKnora 索引失败：保留旧索引，进入补偿；
- provider 超时：状态标记 unknown，读回或人工对账；
- Webhook 丢失：轮询或人工确认，不能仅凭请求响应更新状态；
- 权限服务不可用：敏感工具拒绝执行；
- SkillHub 不可用：继续使用已 pin 版本或停止新任务；
- 回滚失败：冻结后续发布并升级人工处理。

## 7. 回滚

```text
定位错误版本
  → 冻结/退役错误版本
  → Git 回到上一有效版本
  → 重新索引
  → 读回并检查检索结果
  → 记录审计和复盘任务
```

WeKnora、DSH 或 SkillHub 不可用时，Git approved 版本和人工发布流程仍然是 fallback。

## 8. 未来协议的边界

未来如果引入 Webhook、MCP 或 Gateway：事件必须验签、去重、落库、异步处理和可补偿；MCP 工具必须按权限过滤和重新授权。它们是实现手段，不改变 Git、WeKnora、DSH 和人工审核的权威边界。
