# 家庭营养师 Agent 最小 POV Spec：Weknora 知识库 + 微信交互

> 状态：POV Spec 草案  
> 来源：基于 `ideas/01-家庭营养师Agent.md` 的最小可验证版本拆解  
> 核心判断：先验证“家庭饮食知识能否通过 Markdown + Weknora + 微信形成持续变准的推荐闭环”，而不是一开始做完整 App、自动下单或厨房视觉系统。

---

## 1. POV 一句话定义

**家庭营养师 Agent 最小 POV**：用 Markdown 沉淀家庭成员偏好、菜谱、做菜博主来源、饮食规则、Prompt 和 Skill 文档；用独立 Docker Postgres 管理当前库存、采购、计划消耗、近期菜单和饭后反馈等动态状态；通过 WeKnora 知识库检索稳定知识，并通过 MCP 工具完成动态状态读写。

它要验证的不是：

```text
AI 能不能随便生成一道菜；
AI 能不能替代专业营养师；
AI 能不能自动管理厨房；
AI 能不能全自动下单采购。
```

而是验证：

> 当 Agent 拥有家庭画像、菜谱库、做菜博主来源、当前库存和每餐反馈后，它是否能持续推荐更适合这个家庭、且真的能做出来的菜。

---

## 2. 最小闭环

POV 的最小闭环是：

```text
家庭成员与偏好建档
  ↓
扁平 Markdown 菜谱库
  ↓
家庭做菜博主 / 菜谱来源库
  ↓
小票 / 采购清单 / 手动文本通过 MCP 写入 Postgres 库存
  ↓
微信询问“今晚吃什么”
  ↓
Agent 基于 Weknora 检索 + MCP 当前库存推荐菜品
  ↓
饭后微信反馈
  ↓
写入 Postgres 动态状态，并在需要时生成 Markdown / Wiki 摘要
  ↓
下一次推荐更准
```

这个 POV 的关键是把家庭饮食从“一次性问答”变成“知识复利系统”。

---

## 3. 产品边界

### 3.1 POV 阶段做什么

| 模块 | POV 做法 |
|---|---|
| 家庭成员信息 | 用 Markdown / YAML 维护成员、目标、忌口、偏好 |
| 菜谱库 | 采用扁平 `recipes/` Markdown 文件，不按子文件夹细分 |
| 菜谱标签 | 写入每个菜谱文件的 frontmatter 和正文标签 |
| 博主库 | 维护家庭喜欢和当前 popular 的家庭做菜博主来源 |
| 新菜谱收集 | 用户通过微信转发链接、文案、截图，Agent 抽取并生成候选菜谱 |
| 库存 | 通过 MCP 写入独立 Postgres，以小票识别、采购清单录入、文本修正为主 |
| 推荐 | 基于家庭偏好、库存、菜谱标签、历史反馈推荐下一餐 |
| 饭后反馈 | 微信自然语言反馈，更新菜谱、权重和家庭偏好 |
| 知识库 | Markdown 文件进入 Weknora，支撑微信检索与问答 |

### 3.2 POV 阶段不做什么

| 暂不做 | 原因 |
|---|---|
| 完整 App | 微信已经足够验证低摩擦交互 |
| 自动下单 | 履约、平台 API、责任边界复杂，后置 |
| 厨房摄像头实时指导 | 技术和场景复杂，不是当前最小闭环 |
| 智能冰箱全自动识别 | 识别不稳定，且不如小票 / 清单录入可靠 |
| 精准营养素计算 | POV 先验证家庭适配和执行闭环 |
| 医疗级饮食建议 | 涉及合规和专业责任，暂不承诺 |
| 全网自动爬虫 | 先用人工选择来源 + 半自动抽取 |
| 复杂多人权限 | 先验证一个家庭内部的使用闭环 |

## 4. 架构定位

### 4.1 四层分工

```text
微信 / WeKnora 对话入口
  = 日常交互入口

Git Markdown
  = 稳定知识、规则、Prompt、Skill、模板和导出快照的 source of truth

WeKnora
  = 知识库检索、Wiki 可视化和 Agent 推理入口

独立 Docker Postgres + MCP
  = 库存、采购、计划消耗、近期菜单和饭后反馈等动态状态的 source of truth
```

Agent 服务负责：

```text
意图识别；
检索 WeKnora 知识库中的稳定知识；
通过 MCP 工具读取当前库存和近期菜单；
生成推荐；
抽取新菜谱；
在用户确认后通过 MCP 写入动态状态；
在用户确认后生成稳定知识的 Markdown 更新建议；
定期导出状态 Markdown 快照供 Git 归档和 WeKnora 索引。
```

### 4.2 为什么 recipes/ 不按文件夹细分

POV 阶段不采用：

```text
recipes/
  快手晚餐/
  儿童友好/
  减脂友好/
  周末改善/
```

而采用扁平结构：

```text
recipes/
  番茄鸡蛋虾仁.md
  西兰花蒸蛋.md
  虾仁豆腐羹.md
  土豆炖牛腩.md
  空气炸锅黑椒鸡腿排.md
```

原因：

```text
一道菜往往同时属于多个分类；
文件夹只能表达一个主分类，标签可以表达多维属性；
Weknora 更适合基于全文、标签和元数据检索；
微信查询更自然，例如“儿童友好 + 20 分钟 + 有虾仁”；
后续推荐权重、家庭反馈、来源信息都应该跟随菜谱文件本身。
```

所以，子文件夹分类改为菜谱文件内部标签。

## 6. 核心数据文件设计

### 6.1 家庭画像：family/family-profile.md

示例：

```markdown
---
type: family_profile
family_id: my_family
last_updated: 2026-09-20
---

# 家庭饮食画像

## 家庭成员

| 成员 | 角色 | 饮食目标 | 忌口 / 限制 | 口味偏好 |
|---|---|---|---|---|
| 妈妈 | 决策者 | 少油、省心、工作日快手 | 无 | 清淡、蒸菜、快手菜 |
| 爸爸 | 用餐者 | 控制体重、增加蛋白 | 无 | 味道可以稍重 |
| 孩子 | 用餐者 | 多吃蛋白质和蔬菜 | 暂无 | 喜欢番茄味、鸡蛋、虾，不喜欢大块绿叶菜 |

## 家庭整体目标

- 工作日晚餐尽量 30 分钟以内。
- 少油少盐，但不能牺牲孩子接受度。
- 每周至少 3 次高蛋白菜。
- 优先减少外卖和临时决策压力。

## 做饭条件

- 常用设备：炒锅、蒸锅、空气炸锅、电饭煲。
- 工作日可做饭时间：20–40 分钟。
- 周末可尝试复杂菜。
```

示例：

```markdown
---
type: dietary_rules
last_updated: 2026-09-20
---

# 家庭饮食规则

## 通用规则

- 工作日晚餐优先推荐 40 分钟以内的菜。
- 儿童餐避免辣味、重油、明显刺激性调料。
- 推荐时优先考虑当前库存中需要尽快消耗的食材。
- 最近 3 天吃过的主菜默认降权。

## 安全规则

- 过敏和忌口信息必须优先于推荐分数。
- 涉及慢病或医疗限制时，只做执行提醒，不做医疗诊断。
- 不确定的库存变化必须向用户确认。
```

## 7. 菜谱 Markdown 模板

菜谱文件放在扁平 `recipes/` 目录下，每道菜一个 Markdown 文件。

示例：`recipes/番茄鸡蛋虾仁.md`

```markdown
---
type: recipe
recipe_id: recipe_番茄鸡蛋虾仁
title: 番茄鸡蛋虾仁
tags:
  - 快手晚餐
  - 儿童友好
  - 高蛋白
  - 少油可做
  - 工作日
  - 20分钟以内
main_ingredients:
  - 番茄
  - 鸡蛋
  - 虾仁
suitable_for:
  - 孩子
  - 全家
not_suitable_for: []
source_type: 自建
source_name: 家庭改良
source_url:
family_fit_score: 0.86
recommendation_weight: 0.88
last_updated: 2026-09-20
---

# 番茄鸡蛋虾仁

## 一句话说明

一道适合工作日晚餐的快手高蛋白菜，孩子接受度高，做法简单，适合搭配米饭。

## 标签

- 快手晚餐
- 儿童友好
- 高蛋白
- 少油可做
- 工作日
- 20 分钟以内
- 家庭常备食材

## 适合我们家的原因

- 孩子喜欢番茄味和鸡蛋。
- 虾仁提供优质蛋白。
- 做法简单，适合工作日晚餐。
- 油盐可以控制，不需要重调味。

## 不适合的情况

- 如果家里没有虾仁，可以换成鸡胸肉丁或豆腐。
- 如果当天已经吃了很多蛋类，可以减少鸡蛋数量。

## 食材

| 食材 | 用量 | 是否核心 | 可替代 |
|---|---:|---|---|
| 番茄 | 2 个 | 是 | 番茄罐头 |
| 鸡蛋 | 2 个 | 是 | 无 |
| 虾仁 | 150g | 是 | 鸡胸肉丁 / 豆腐 |
| 葱花 | 少量 | 否 | 可省略 |

## 做法

1. 番茄切块。
2. 鸡蛋打散，少油炒熟后盛出。
3. 番茄炒软出汁。
4. 加入鸡蛋。
5. 虾仁最后放，快速翻炒至变色。
6. 少盐调味，给孩子吃不要加辣。

## 家庭改良版本

- 给孩子吃：少盐，不放辣，番茄炒软一点。
- 减脂版本：少油，鸡蛋可以减少一个蛋黄。
- 如果虾仁容易老：最后 1–2 分钟再放。

## 历史反馈

| 日期 | 反馈 | 处理 |
|---|---|---|
| 2026-09-20 | 孩子喜欢，但虾仁有点老 | 做法改为虾仁最后放 |
| 2026-09-21 | 爸爸觉得味道略淡 | 成人份可以单独加黑胡椒 |

## 推荐逻辑

这道菜适合在以下情况下推荐：

- 工作日晚餐时间少于 30 分钟；
- 家里有番茄、鸡蛋、虾仁；
- 孩子需要高蛋白晚餐；
- 最近没有连续吃番茄鸡蛋类菜；
- 用户希望少油、简单、稳定成功。

## 降权条件

以下情况减少推荐：

- 最近 3 天已经吃过番茄鸡蛋类菜；
- 家里没有虾仁且没有合适替代；
- 用户反馈当天不想吃酸甜口；
- 孩子近期对虾仁接受度下降。
```

## 9. 库存状态设计

### 9.1 库存定位

库存不是完整 ERP，只需要回答三个问题：

```text
现在大概有什么；
哪些食材需要优先消耗；
推荐菜时哪些能做、哪些还缺。
```

### 9.2 动态状态存储：独立 Postgres + MCP

库存、采购、计划消耗、实际做饭和反馈属于动态状态，第一版正式 MVP 直接使用独立 Docker Postgres 作为 source of truth。Agent 不直接写 SQL，而是通过 MCP 工具读写。

```text
WeKnora Agent
  ↓ MCP tools
Family Nutrition MCP Service
  ↓
独立 Docker Postgres
```

核心原则：

```text
1. current inventory 以 Postgres 查询结果为准；
2. purchase log 以 Postgres 采购事件为准；
3. planned consumption 以 Postgres 计划消耗记录为准；
4. recent menu 以 Postgres 推荐/执行记录为准；
5. Markdown 文件只作为导出快照、人工审阅和 Git 归档；
6. 不直接修改 WeKnora 内部 PostgreSQL。
```

### 9.3 当前库存导出：inventory/current-inventory.md

示例：

```markdown
---
type: current_inventory
last_updated: 2026-09-20 20:00
---

# 当前库存

| 食材 | 数量 | 单位 | 分类 | 状态 | 来源 | 备注 |
|---|---:|---|---|---|---|---|
| 鸡蛋 | 8 | 个 | 蛋奶 | 正常 | 手动录入 | 常备 |
| 番茄 | 4 | 个 | 蔬菜 | 优先消耗 | 小票识别 | 2–3 天内吃 |
| 虾仁 | 300 | g | 水产 | 冷冻 | 小票识别 | 一袋 |
| 西兰花 | 1 | 颗 | 蔬菜 | 优先消耗 | 小票识别 | 孩子不爱大块 |
| 牛奶 | 2 | 瓶 | 蛋奶 | 正常 | 采购清单 | 早餐用 |

## 库存规则

- 绿叶菜和鲜蔬优先消耗。
- 冷冻肉类不强制优先，但推荐时可作为蛋白来源。
- 数量不确定时，推荐前询问用户确认。
```

|---|---:|---|---|

### 9.5 库存作为强状态

需要注意：Weknora 适合检索知识，但当前库存是强状态。

因此：

```text
Postgres 是库存、采购、计划消耗和实际消耗的 source of truth；
MCP 工具是 Agent 读写动态状态的唯一受控入口；
库存更新必须支持用户确认、幂等、防重复扣减和审计；
不要只依赖 RAG 检索库存，避免召回旧版本；
current-inventory.md 仅作为 Postgres 导出的可读快照，不作为事务权威。
```

## 10. 每餐反馈设计

### 10.1 反馈入口

用户通过微信自然语言反馈：

```text
今晚番茄鸡蛋虾仁孩子很喜欢，但虾仁还是有点老，爸爸觉得味道淡。
```

Agent 需要抽取：

```text
菜品；
谁吃了；
谁喜欢 / 不喜欢；
执行难度；
口味问题；
做法问题；
是否愿意复吃；
是否需要改做法；
是否调整推荐权重。
```

### 10.2 反馈日志：meals/meal-feedback-log.md

示例：

```markdown
---
type: meal_feedback_log
last_updated: 2026-09-20
---

# 每餐反馈记录

## 2026-09-20 晚餐：番茄鸡蛋虾仁

原始反馈：

> 今晚番茄鸡蛋虾仁孩子很喜欢，但虾仁还是有点老，爸爸觉得味道淡。

结构化记录：

| 维度 | 结果 |
|---|---|
| 孩子接受度 | 高 |
| 成人接受度 | 中高 |
| 问题 | 虾仁偏老；成人觉得偏淡 |
| 做法调整 | 虾仁最后 30–60 秒放；成人份可加黑胡椒或少量生抽 |
| 推荐权重 | 儿童友好权重上调；工作日推荐保持 |
| 下次提醒 | 做饭步骤中强调虾仁最后放 |
```

### 10.3 反馈更新目标

每次反馈后，Agent 至少尝试更新：

```text
Postgres meal_feedback 事件；
Postgres meal_events / inventory_events 中的实际消耗修正；
preference_observations 中的偏好观察；
对应 recipes/*.md 的历史反馈建议；
family/member-preferences.md 的长期偏好建议。
```

其中 Postgres 动态状态通过 MCP 工具写入；菜谱和家庭偏好属于稳定知识，必须经用户确认后再沉淀到 Markdown。

## 11. 推荐规则最小版

文件：`agent-rules/recommendation-rules.md`

### 11.1 推荐评分

最小版不需要复杂模型，先用规则评分：

```text
总分 =
家庭偏好匹配分
+ 库存匹配分
+ 时间匹配分
+ 健康目标匹配分
+ 历史反馈分
+ 来源可信分
- 忌口冲突惩罚
- 执行复杂度惩罚
- 最近吃过惩罚
```

建议权重：

| 因子 | 权重 |
|---|---:|
| 家庭偏好匹配 | 0.25 |
| 库存匹配 | 0.25 |
| 时间匹配 | 0.15 |
| 健康目标匹配 | 0.15 |
| 历史反馈 | 0.15 |
| 来源可信 | 0.05 |

### 11.2 推荐输出要求

每次推荐不要只给菜名，要输出：

```text
推荐菜；
为什么适合我们家；
命中了哪些库存；
还缺什么；
预计时间；
适合哪些家庭成员；
上次反馈后的做法调整；
备选方案。
```

示例：

```markdown
## 今晚首选：番茄鸡蛋虾仁

推荐理由：

1. 家里有番茄、鸡蛋和虾仁，不需要额外采购。
2. 孩子之前喜欢番茄味和虾仁。
3. 预计 20 分钟完成，适合工作日晚餐。
4. 上次反馈虾仁偏老，这次建议最后 30–60 秒再放。

缺少食材：无。

注意事项：

- 给孩子少盐。
- 成人份可以单独加黑胡椒。

备选：

- 西兰花蒸蛋：更清淡，但孩子对大块西兰花接受度一般。
- 虾仁豆腐羹：更软嫩，但需要确认家里是否有嫩豆腐。
```

## 12. 微信交互意图

### 13.1 推荐晚餐

用户：

```text

```

Agent：

```text
今晚优先推荐：番茄鸡蛋虾仁。

2. 孩子之前反馈喜欢番茄味；

- 西兰花蒸蛋：更清淡，但孩子对大块西兰花接受度一般；
- 虾仁豆腐羹：更适合孩子和老人，但需要确认有没有嫩豆腐。
```

### 13.2 采购清单入库

用户：

```text
今天买了鸡蛋一盒、番茄 4 个、虾仁一袋、西兰花 2 颗、牛奶 2 瓶。
```

Agent：

```text
我识别到这些库存更新：

- 鸡蛋：1 盒
- 番茄：4 个
- 虾仁：1 袋
- 西兰花：2 颗
- 牛奶：2 瓶

```

### 13.3 饭后反馈

用户：

```text
今晚番茄鸡蛋虾仁孩子很喜欢，但虾仁还是有点老，爸爸觉得味道淡。
```

Agent：

```text
已记录这次反馈：

- 孩子：喜欢，儿童接受度提高；
- 虾仁：仍然偏老，下次建议最后 30–60 秒再放；
- 爸爸：觉得偏淡，成人份可以单独加黑胡椒或少量生抽。

我会继续把这道菜保留为儿童友好高权重菜，并在做法里强化“虾仁最后放”的提醒。

用户转发菜谱文案：

- 高蛋白；

```

## 14. Weknora 使用策略

### 14.1 适合放入 Weknora 的内容

```text
菜谱 Markdown；
家庭画像；
成员长期偏好；
饮食规则；
博主来源库；
推荐规则；
历史反馈总结；
菜谱改良记录。
```

### 14.2 不应该只依赖 Weknora 的内容

```text
当前库存；
刚刚更新的采购记录；
需要覆盖的状态字段；
用户刚确认或撤销的变更；
敏感的原始小票或家庭隐私信息。
```

这些内容可以导出成 Markdown 摘要，但 Agent 推荐前应通过 MCP 读取 Postgres 最新状态，而不是只依赖知识库召回。

### 14.3 同步原则

```text
Git Markdown 是稳定知识、规则、Prompt、Skill、模板和导出快照的 source of truth；
Postgres 是库存、采购、计划消耗、实际做饭和反馈等动态状态的 source of truth；
Weknora 是检索索引和 Agent 对话入口；
MCP 是 Agent 读写动态状态的唯一受控边界；
微信是低摩擦交互入口。
```

## 16. 成功指标

### 16.1 知识资产指标

| 指标 | 目标 |
|---|---:|
| 家庭画像文件 | 3 个以上 |
| 初始菜谱 Markdown | 30 道以上 |
| 做菜博主 / 来源 | 5–10 个 |
| 带完整标签的菜谱比例 | 90% 以上 |
| 有家庭适配说明的菜谱比例 | 90% 以上 |

### 16.2 使用行为指标

| 指标 | 目标 |
|---|---:|
| 每周微信推荐请求 | ≥ 3 次 |
| 每周饭后反馈 | ≥ 3 次 |
| 每周库存更新 | ≥ 2 次 |
| 每周新增 / 修改菜谱 | ≥ 3 道 |
| 实际照推荐做饭 | ≥ 2 次 / 周 |

### 16.3 价值指标

| 指标 | 判断方式 |
|---|---|
| 推荐命中率是否提高 | 第二周推荐比第一周更符合家庭偏好 |
| 决策压力是否下降 | 用户是否少问“今晚到底吃什么” |
| 库存浪费是否减少 | 是否能优先消耗临期 / 鲜蔬 |
| 家庭接受度是否提升 | 孩子 / 家人喜欢的菜被更多推荐 |
| 持续维护意愿 | 用户是否愿意继续通过微信反馈和录入 |

最关键的判断：

> 连续两周后，用户是否觉得：这个 Agent 比自己临时刷菜谱、翻冰箱、想菜单更懂我家。

## 18. 最终结论

这个最小 POV 的核心不是“做一个菜谱 App”，而是验证家庭饮食知识是否能形成复利：

```text
每一道菜谱都沉淀成知识；
每一次采购都更新库存；
每一顿饭都产生反馈；
每一次反馈都调整做法和推荐权重；
每一次推荐都更理解这个家庭。
```

一句话总结：

> 微信负责低摩擦交互，Weknora 负责知识检索，Markdown 负责家庭饮食知识沉淀，库存和反馈负责让推荐持续变准。
