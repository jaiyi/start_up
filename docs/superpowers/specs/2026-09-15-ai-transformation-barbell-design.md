## 3. 目标读者与企业画像

### 3.1 `05` 的目标读者

`05` 面向所有正在思考企业 AI 转型的人，回答：

```text
为什么企业 AI 转型不能只买工具、不能只靠中台、也不能放任全员野生使用？
为什么杠铃结构是更合理的组织原则？
```

### 3.2 `05-01` 的目标企业画像

`05-01` 面向大型制造、能源、汽车、高端装备企业，默认画像：

- 已有 IT / 数据 / 数字化团队；
- 已有 ERP / MES / QMS / PLM / 数据平台等基础系统；
- 已有局部 AI 试点、工具采购或一线野生 agent；
- 但还没有组织级反馈闭环、收编机制、经营归因和 P&L 对齐。

它回答：

```text
大企业如何从今天的 AI 混乱状态，一步步落地杠铃结构？
```

### 3.3 `05-02` 的目标企业画像

`05-02` 面向中小制造企业、供应商型制造企业，默认画像：

- 有真实制造、供应链、质量、排产问题；
- 可能有 ERP / MES / QMS 的一部分，但系统不完整；
- IT 团队很小，更多承担运维或实施支持；
- 没有专门 AI 团队；
- 老板知道要转型，但容易被外部供应商卖工具、卖大屏、卖 demo。

它回答：

```text
中小企业撑不起完整杠铃时，如何借助外部垂直 AI-native 运营商，同时不丢掉数据主权？
```

## 4. 核心设计选择

### 4.1 采用“两篇路线图 + 一个总论入口”

采用方案 A：两篇都写成“路线图 + 操作表”。

原因：

- `05` 已经很长，继续堆细节会降低可读性；
- 大企业和中小企业的组织答案不同，强行放在一篇里会混乱；
- 路线图形式既保留洞察感，又能回答“怎么落地”；
- 操作表、RACI、checklist 可作为路线图中的工具，而不是全文主形态。

### 4.2 大企业主线：从黑洞场景启动

`05-01` 不从“先建平台 / 先改组织 / 先发工具”开始，而从一个高价值黑洞场景开始。

核心公式：

```text
黑洞场景 = 经营价值 × 数据闭环 × 组织可推动性
```

三个维度：

| 维度 | 判断问题 |
|---|---|
| 经营价值 | 能不能挂到库存、延期、产能、良率、报废、返工、客诉、现金流？ |
| 数据闭环 | 有没有输入、决策、执行、结果、反馈？反馈周期多快？ |
| 组织可推动性 | 有没有明确业务 owner？是否能改流程？跨部门阻力有多大？ |

重点例子覆盖：

- 供应链管理；
- 排产 / 计划优化；
- 生产良率 / 质量闭环。

### 4.3 中小企业主线：托管杠铃，但守住数据主权

`05-02` 的核心不是鼓励中小企业自建 AI 平台，而是强调：

```text
AI 能力可以外包，经营数据和反馈轨迹不能外包。
```

中小企业的托管杠铃结构：

```text
外部垂直 AI-native 运营商
  承担部分顶部平台能力 + 部分底部试错能力

企业自己
  保留业务 owner + 数据主权 + 经营判断
```

必须守住四件事：

1. 数据落在企业自己的库；
2. schema 不用供应商私有格式；
3. 决策理由与人工修正必须沉淀；
4. 退出权写进合同。

## 6. `05-01` 详细设计

建议文件名：

```text
docs/insights/05-01-大企业AI转型的杠铃结构落地路径.md
```

### 6.1 章节结构

```markdown
# 05-01 · 大企业 AI 转型的杠铃结构落地路径

## 0. 这篇回答什么
## 1. 起点不是组织架构，而是黑洞场景
## 2. 三类优先黑洞场景
## 3. 90 天启动：先跑通一个最小闭环
## 4. 12 个月扩展：从试点到杠铃结构
## 5. 3 年目标态：AI-native 组织常态
## 6. 三类场景的落地路线差异
## 7. 行动清单
```

### 6.2 核心论点

一句话结论：

```text
大企业 AI 转型不要从“建平台 / 改组织 / 买工具”开始，而要从一个高价值黑洞场景开始，用真实经营结果反推组织、平台、考核和 P&L。
```

### 6.3 黑洞场景选择

`05-01` 的第一个工具是黑洞场景选择表：

```text
黑洞场景 = 经营价值 × 数据闭环 × 组织可推动性
```

三个重点场景：

| 场景 | 价值 | 难点 | 建议定位 |
|---|---|---|---|
| 供应链管理 | 库存、交付、现金流、停线风险 | 跨部门、跨公司、责任复杂 | 12 个月扩展重点 |
| 排产 / 计划优化 | 产能、交付、库存、计划稳定性 | 约束复杂、现场真实约束难结构化 | 第一批黑洞场景，可从局部开始 |
| 生产良率 / 质量闭环 | 良率、报废、返工、客诉 | 根因归因、现场经验外化 | 最适合作为 90 天启动场景之一 |

### 6.4 90 天启动路线

90 天目标不是“上线一个 AI”，而是判断某个场景有没有资格成为组织级黑洞。

阶段：

1. **第 0–2 周：选场景**
   - 用三因素打分；
   - 只选一个场景；
   - 明确业务 owner；
   - 明确一个经营指标；
   - 明确数据范围；
   - 输出“黑洞场景立项单”。

2. **第 3–6 周：建最小反馈闭环**
   - 梳理输入数据；
   - 梳理当前人工决策过程；
   - 记录 AI / 人的建议；
   - 记录执行结果；
   - 记录实际业务结果；
   - 记录人工修正理由。

   关键数据链路：

   ```text
   输入 → 判断/推理 → 建议动作 → 人工修正 → 执行结果 → 业务结果
   ```

3. **第 7–10 周：引入 Agent / 工作流**
   - 先做人机协同；
   - 再做局部自动；
   - 最后再提高 AI 自主运营比例；
   - 每个 agent 都标清决策权限、人类监督档位、失败兜底、数据记录方式和业务指标。

4. **第 11–12 周：做 EVI 复盘**
   - 经营指标是否变化；
   - 哪些收益可归因；
   - 哪些只是相关不是因果；
   - 哪些流程必须改变；
   - 哪些 agent / 工具值得收编；
   - 哪些不值得继续。

### 6.5 12 个月扩展路线

12 个月目标是从试点进入杠铃结构。

重点模块：

1. **收编机制**
   - 把野生 agent 分成个人效率工具、小团队工作流、影响业务决策的 agent、影响经营结果/风险/合规的 agent；
   - 处理流程为：发现 → 登记 → 评分 → 加固 → 产品化 → 复用 → 下放。

2. **薄顶部平台团队成型**
   - 管数据标准、agent 登记、权限、审计、评估、复用组件、可观测、收编流程、EVI 方法论；
   - 不替业务想需求，不承包所有交付，不用工单量证明价值。

3. **业务一号位开始背 P&L**
   - AI 转型不是 IT 项目，是业务经营项目；
   - 试点期业务 owner 与顶部平台共担；
   - 扩展期业务一号位背经营结果；
   - 常态期 AI 能力变成业务部门自己的生产方式。

4. **考核从个人产出改为人机系统贡献**
   - 新增人机联合产出、审核质量、拦截率/漏审率、兜底成功率、反馈数据贡献、agent 复用贡献、可归因经营增量。

### 6.6 3 年目标态

3 年目标不是“上线很多 AI 应用”，而是形成 AI-native 组织常态：

```text
业务部门自己会发现高价值场景
一线能长出野生 agent
顶部能快速收编
数据能持续反馈
考核奖励人机协同
P&L 能证明 AI 价值
```

可观察指标：

| 指标 | 含义 |
|---|---|
| AI 自主运营比例 | 多少业务动作由 AI 独立或半独立完成 |
| 硅基员工占比 | AI agent 在组织中的有效劳动占比 |
| 黑洞场景数量 | 已经形成反馈飞轮的核心场景数量 |
| Agent 收编率 | 野生 agent 中有多少进入受支持产品 |
| 反馈数据质量 | 是否沉淀输入、推理、动作、结果、修正 |
| 可归因经营增量 | AI 对库存、良率、交付、成本等指标的贡献 |

### 7.2 核心论点

一句话结论：

```text
中小企业不要照抄大企业的 AI 杠铃结构。你养不起顶部平台，也没有足够一线公民开发者密度；更现实的路径是借外部垂直 AI-native 运营商托管试错和治理，但把反馈数据、schema 和退出权留在自己手里。
```

### 7.3 判断是否撑不起自建杠铃

使用判断表：

| 问题 | 如果答案是“否” |
|---|---|
| 是否有 5–10 人以上的数据 / AI / 数字化骨干？ | 顶部平台撑不起来 |
| 是否有多个业务部门愿意试点？ | 底部试错密度不够 |
| 是否有稳定数据平台或至少统一数据库？ | 反馈闭环难以沉淀 |
| 是否有业务 owner 能背经营指标？ | AI 会变成老板工程 |
| 是否能持续投入 12 个月以上？ | 做不出组织复利 |
| 是否有人能管理外部 AI 供应商？ | 容易被供应商锁死 |

如果大部分是否定，就不应该自建完整杠铃。

### 7.4 托管杠铃结构

大企业杠铃是：

```text
顶部薄平台 + 底部业务试错
```

中小企业托管版是：

```text
外部垂直 AI-native 运营商
  承担部分顶部平台能力 + 部分底部试错能力

企业自己
  保留业务 owner + 数据主权 + 经营判断
```

### 7.5 数据主权四件套

1. **数据落在企业自己的库**
   - 输入、推理、建议、人工修正、执行结果、业务结果必须写入企业自己控制的数据库 / 数据湖 / 对象存储。

2. **schema 不用供应商私有格式**
   - 主干字段标准化；
   - 领域扩展字段可导出；
   - 业务编码、工序、设备、供应商、缺陷码属于企业资产。

3. **决策理由必须一起沉淀**
   - 记录为什么建议、依据哪些数据、人是否采纳、人为什么修正、实际结果如何。

4. **退出权写进合同**
   - 全量数据导出；
   - 导出格式；
   - 导出周期；
   - 解约后供应商删除副本；
   - 企业保留历史反馈轨迹；
   - 模型 / agent 配置能否导出；
   - 指标口径和 schema 文档归属；
   - 供应商用企业数据训练通用模型必须单独授权。

### 7.6 90 天试用路线

1. **第 0–2 周：选一个小但真痛的场景**
   - 供应商质量风险、排产瓶颈、良率波动、库存/缺料问题；
   - 要求问题够痛、数据够近、owner 明确、周期短。

2. **第 3–6 周：接入最小数据**
   - 不追求完整数据平台；
   - 先打通一个业务对象、一条流程、一个反馈结果。

3. **第 7–10 周：运营商跑服务，企业盯数据沉淀**
   - 企业每天检查数据是否写回自己的库；
   - 人工修正理由是否记录；
   - 实际结果是否回填；
   - 指标口径是否统一；
   - 是否能导出。

4. **第 11–12 周：试点评估**
   - 是否有可归因经营改善；
   - 是否沉淀可复用反馈数据；
   - 是否减少人的重复劳动；
   - 是否暴露流程 / 数据问题；
   - 是否存在供应商锁定风险；
   - 是否值得进入 12 个月合作。

### 7.7 12 个月合作与 3 年目标态

12 个月后，企业至少应拥有：

```text
一个懂业务 + 懂数据的内部 owner
一套自己的反馈数据
一套可导出的 schema
一套供应商管理机制
一套可归因经营指标
```

3 年后目标不是自研 AI 平台，而是形成轻量反脆弱能力：

```text
换供应商不归零
换模型不归零
换系统不归零
核心反馈数据仍在自己手里
业务 owner 能判断 AI 有没有用
```
