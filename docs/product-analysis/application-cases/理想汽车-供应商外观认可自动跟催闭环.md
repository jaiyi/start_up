# 理想汽车：供应商外观认可自动跟催闭环

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：游若水，Level 3，整车电动，2026-09-03，板块：实战案例 · 工具分享，279 阅读）
>
> **一句话**：用 Liwork 智能体在多维表格（bitable）上搭出一套 AAR（外观认可）供应商自动跟催闭环——两张表（零件主看板 + 送样明细表）+ prefill 关联 + 5 条自动化工作流，把"送前自检 → 送样确认 → 评审回传 → 下轮排期"四阶段循环完全脱离人工盯防，**零代码、零服务器、零 Token**。与案例四/五同属确定性自动化物种，但更进一步：连 AI Coding 自研系统都不做，直接长在成熟协同底座上；且明确论证了"业务系统与个人 Agent 解耦"。这是六个案例里工程判断最清醒的一篇。

---

## 1. 案例来源与背景

- 来源：公司内部技术社区文章，作者游若水（Level 3 进阶学员，整车电动），2026-09-03，阅读量约 279（六个案例中最高）；
- 业务域：整车电动 · 硬件产品开发外观认可（AAR）管理；
- 工具：Liwork（理想内部智能体）+ 多维表格；
- 背景：一件产品从开模到封样通常要经历 **7~8 轮甚至更多**外观认可，涉及一级供应商、模具厂/皮纹厂、外观工程师、DRE **四方协同**；几十个零件并行时，人肉盯节点、群里催照片、重点问题跟进占掉每天小半天。

---

## 2. 解决什么问题

**痛点：多方协同 + 固定时序跟催 + 数据证据回填的碎片化流程**

- 送前自检：要供应商提前提交优化说明、自检结论、自检照片；
- 如期送样：要前一天确认是否延后；
- 评审回传：评审当天要结论（OK/Hold/Reject）、问题说明、现场照片；
- 下轮排期：不 OK 就要供应商承诺下一轮送样时间，循环重启；
- 单件 7~8 轮、几十件并行，全部靠人肉催办。

---

## 3. 任务流拆解

### 3.1 四阶段自动循环（状态机）

```text
阶段 1：送前资料确认（送样前 2 天 09:00，监听主看板送样时间触发）
   供应商收群卡片 → 极简表单：填本轮优化说明 + 选自检结论(OK/条件OK/NG) + 相册传自检照片
   → 自动写回明细表，状态 →「待送样确认」
        ↓
阶段 2：送样日期确认（送样前 1 天 09:00）
   单选题：是，如期送样 / 否，延后送样
   → 状态 →「待评审回传」
        ↓
阶段 3：评审结果回传（评审当天 18:00 下班前催办）
   选结论(OK/Hold/Reject) + 填问题说明 + 传评审现场照片
   → 同步更新明细表与主看板：
      OK   →「已闭环」，流程终止
      非OK →「待下轮计划」
        ↓
阶段 4：下轮计划确认（评审后 2 天 09:00，仅非 OK 时触发）
   只填一项：下一轮承诺送样时间
   → 新时间写回主看板「送样时间」，状态重置为「待送前资料」
   → 自动唤醒阶段 1，开启新循环
```

### 3.2 核心架构：两表一引擎

| 模块 | 定位 | 关键字段/功能 | 价值 |
|---|---|---|---|
| 零件主看板 | DRE 宏观驾驶舱 | 件号+名称、零件图示、供应商、当前状态、最新评审结果、送样时间、供应商群 | 一眼掌握所有零件进展 |
| AAR 送样明细表 | 底层证据链存储库 | 批次识别键、每轮优化说明、自检图、是否如期送样、评审结论、现场图、下轮时间、流程阶段 | 单件 7~8 轮认可全生命周期图文证据可追溯 |
| 工作流 5（同步引擎） | 核心中枢（**15 步分支**） | 监听表单新增记录，字段非空识别阶段，双向匹配写回并智能分流 | 替代人工核对录入，评审通过自动封样、未通过自动重启下轮排期 |

**关键设计细节：**

- **prefill 隐藏关联**：供应商点开的表单里，零件与送样时间通过 prefill 预填隐藏字段自动关联——供应商无感、不填错；
- **状态字段识别阶段**：工作流靠"哪个字段非空"判断当前处于哪个阶段，一套引擎路由四种表单回填；
- **面向供应商的交互 = 群卡片 + 极简表单**（选择题为主、相册直传），不要求供应商学习任何系统。

---

## 4. 用到的能力

- **Liwork 智能体**：只在搭建阶段用——把业务痛点和时序规则丢给智能体，让它帮忙配置触发器、分支与字段（AI 当"系统架构师"）；
- **多维表格原生能力**：云端触发引擎、自动化工作流（5 条）、表单 prefill、消息卡片推送、移动端渲染、相册直传；
- **运行时零 LLM、零 Token**：所有定时推送、状态流转、表单回填全部由平台确定性执行；
- 个人 AI 机器人：把多维表格当**只读数据源**，每天定时提炼一份 AAR 日报——LLM 只在这一步出现。

---

## 5. 效果与证据

- 四阶段全自动自循环，"完全脱离人工盯防"；
- 单件 7~8 轮、几十件并行的跟催不再占用人工；
- 同事复用：一键"创建副本"换供应商群链接，30 秒开箱即用。

**注意：全文没有任何量化提效数字**（没有分钟数、没有百分比）——与前几个案例形成鲜明对比。效果以"流程描述 + 截图"呈现，属于"系统跑起来了"的证据而非"省了多少"的证据。

## 6. 可信度判断

**判断：真实落地、工程判断清醒，是六案例里方法论质量与诚实度并列最高的（与案例三相当）。**

可信的部分：

- 流程颗粒度极细（prefill 隐藏关联、15 步分支、字段非空识别阶段、状态机重置唤醒）——只有真搭过的人才写得出来；
- **主动交代失败路径**：先试过 openclaw 托管、codex 手写后台代码部署服务器，"处处碰壁"才回归成熟平台——踩坑史真实；
- 三个核心诉求（不污染个人 Agent 记忆 / 零 Token / 一键复用）都是想清楚了才有的取舍，不是事后包装；
- 279 阅读量为六案例最高，且有截图佐证表单和卡片。

需要保留的部分：

- 无任何量化效果数据，"占掉每天小半天"是痛点描述不是节省额的验证；
- 依赖多维表格平台的自动化能力边界（分支复杂度、并发上限、跨表性能）未讨论——几十零件 × 每件 7~8 轮的记录量下 15 步分支引擎的稳定性待验证；
- 供应商端的配合度（会不会不填卡片、照片质量）没有任何约束能力的说明。

结论：**真实、清醒、可复用；缺量化但不影响其方法论价值。**

## 7. 对我们当前项目的启发

### 7.1 六案例里的"物种谱系"至此完整：运行时用不用 AI 是一个谱，不是一个开关

```text
案例六（本案例）：成熟平台 + 无代码自动化，运行时零 LLM
                 ——LLM 只在搭建期当架构师 + 每日日报提炼
案例四/五：      AI Coding 自研系统，规则引擎运行，零 LLM
案例三（EHS）：   RAG + Prompt，LLM 出初稿人收口
案例一（LI-PAS）：多 Skill Agent 编排复杂分析
案例二（流程库）：LLM 反向管理流程资产
```

六案例收敛出的物种选择判据（可作为 04-05/04-06 的补充定理）：

| 判据 | 选什么 |
|---|---|
| 判定逻辑确定、时序固定、多方表单回填 | 平台自动化（本案例）——零 Token、零运维、天然稳定 |
| 判定逻辑确定但跨系统集成复杂 | 规则引擎 + 数据工程（案例四） |
| 判定逻辑半确定、需要穷举和专业初稿 | LLM 初稿 + 人工复核（案例三） |
| 判定开放、需要多步推理和工具编排 | Agent 工作流（案例一） |
| 对象是制度/知识资产本身 | 反向诊断 Agent（案例二） |

**"确定性流程调用大模型 = 稳定性风险 + 算力成本"（作者原话）——这条应写进 04-06 的设计原则。**

### 7.2 "业务系统与个人 Agent 解耦"：一个重要的架构原则（对应 04-05）

作者的第一个核心诉求值得原文记录：

> AAR 属于强业务流程、弱开放对话的阶段性工作。如果把海量细碎的催办、图片、状态流转硬塞给私人 Agent，会严重挤占大模型的上下文与核心记忆。现在的系统完全自治运行，我的私人机器人只需把它当成**只读数据源**，每天准时给我提炼输出一份 AAR 日报即可。

这给 04-05 任务闭环平台一个明确的设计约束：

```text
确定性状态机 → 独立自治系统（不占 LLM 上下文）
LLM 的角色   → 站在系统之上的只读消费者 + 提炼者（日报/归因/异常摘要）
```

即：**LLM 不该是数据的 first-class 存储和流转层，而应是数据之上的观察者。**这同时回答了"Agent 的记忆该放什么"——放结论和摘要，不放过程态。

### 7.3 "杠杆支点要选在成熟平台上"：AI Coding 时代路径选择的总纲（对应案例四/五的反思）

作者踩坑后的结论直接修正了案例四/五隐含的判断：

| 路径 | 困境 | 结论 |
|---|---|---|
| A：Codex 等从零手写脚本/后台 | 环境配置、进程保活、接口鉴权、断网重连的工程泥潭；强依赖个人电脑无法 24h 在线；同事复用要重配环境 | ❌ 高门槛、重维护、难推广 |
| B：智能体在成熟平台（多维表格）上搭积木 | 业务人员只输出规则；平台原生提供云端托管、移动端、相册直传、卡片推送；一键"创建副本"复用 | ✔️ 零代码、自运行、易复用 |

与案例四/五合看形成完整光谱：**AI Coding 自研（案例四/五）适合集成深度高的场景（数仓/本机软件），平台搭积木（本案例）适合协同表单流场景**——选择依据是"平台原生能力覆盖度"，不是技术潮流。

### 7.4 强映射：AAR 封样闭环 ≈ 12-03 的 Lot Release / 封样管理（对应 12-03）

外观认可（AAR）从开模到封样 7~8 轮、四方协同、每轮留证据链——和 Fabless 侧封样/Lot Release 的结构完全同构：

| 整车 AAR（本案例） | Fabless 封样/Lot Release（12-03） |
|---|---|
| 送前自检（优化说明+结论+照片） | 送样前供应商自查报告 |
| 如期送样确认 | 交期承诺与变更 |
| 评审结论 OK/Hold/Reject + 现场照片 | 封样判定通过/有条件/拒绝 + 判定记录 |
| 非自动重启下轮排期循环 | 未通过重提交循环 |
| 明细表 = 单件 7~8 轮证据链 | genealogy = 单批次全轨迹 |

**给 12-03 的具体增量**：封样/放行跟催不必上重系统——主看板（状态）+ 明细表（证据链）两表分离 + 状态机自动循环 + prefill 表单，这个 schema 可以直接平移到"供应商 Lot Release 状态跟踪"。另外本案例与案例二有交叉锚点：案例二的核心痛点场景正是"封样确认责任主体误判"（PQE vs TPM）——**封样是跨案例反复出现的枢纽业务对象**。

### 7.5 两表分离 + 状态机：轻量系统的 schema 范本

- **主看板（当前态）与明细表（证据链）分离**：宏观驾驶舱只存最新状态，历史全部进明细——这和 04-05 里 TaskTrace（任务轨迹）与业务对象当前态分开是同一个原则；
- **状态机显式化**：待送样确认 → 待评审回传 → 已闭环/待下轮计划 → 重置，每个状态有明确的进入条件和转移动作——15 步分支引擎本质是一个显式状态机路由器；
- **表单即接口**：对供应商暴露的是选择题 + 相册上传，内部键全部 prefill 隐藏——**对外交互降到选择题，对内保留完整结构化数据**，这是跨组织协同的好模式。

### 7.6 最值得抄的设计

1. **prefill 隐藏关联 + 字段非空识别阶段**：一套表单模板 + 一个同步引擎路由多种回填，避免维护多条独立工作流；
2. **业务系统与个人 Agent 解耦，日报作为唯一 LLM 触点**（见 7.2）；
3. **一键"创建副本"复用**：方案能推广的前提是封装在平台内、不依赖环境配置——工具的复用性在设计时就决定了；
4. **失败路径公开**：把 openclaw/codex 的踩坑写成路径对比表，比只讲成功更有信息量；
5. **"任何涉及多方协同 + 固定时序跟催 + 数据证据回填的碎片化流程，都是绝佳的改造场景"**——作者给出的场景识别判据，比"用 AI 提效"精确得多。

## 8. 后续想实测 / 追问的问题

- 几十个零件并行的实际运行数据：工作流触发延迟、15 步分支的误路由率；
- 供应商不响应卡片时的升级机制（有没有超时上报/人工介入兜底）；
- 评审结论的照片如何归档和检索——证据链"可追溯"到什么程度（按零件/按轮次/按问题类型能不能检索）；
- 多维表格的记录量上限和自动化并发限制，到多大规模会需要迁到正经系统；
- LLM 日报的实际效果：提炼质量如何，DRE 真的看吗，有没有进一步做成异常摘要而非全量日报；
- 这套 schema 平移到其他跟催场景（供应商 8D 关闭、PCN 切换跟踪、治具/设备维保）的适配成本；
- Liwork 在搭建中的具体贡献：智能体生成的触发器/分支配置有多少是直接可用的，返工率多少。
