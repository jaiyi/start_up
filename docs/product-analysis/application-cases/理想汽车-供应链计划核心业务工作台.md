# 理想汽车：供应链计划核心业务工作台

> 收录日期 2026-09-30 · 来源：内部汇报材料《PSM 核心业务工作台——从数据分析到决策执行》（汇报人：朱岩滨、陈勇，供应链 PSM，无发布日期/阅读量，为演示型材料而非社区复盘文章）
>
> **一句话**：供应链计划员的"决策准备层"——不替代 O9/SAP 执行系统，而是把原先散落在几十个飞书文档和 Excel 里的分析、模拟、决策准备动作收进一个贴合工作流的系统（主计划排产 / 零件库存 / SIP 产能分析 / EOP 呆滞控制四模块闭环）；AI 分三个角色（求解者 OR-Tools MIP / 分析者 LLM+SSE / 预测者 Agent 沙盒），并提出"范式③ Vibe Coding 定制工具"的三分法。**十五案例中第一份"汇报视角"材料——价值在于它把前十四个案例里散落的选型判断explicitly整理成了三范式框架，且给出了"为什么现在能做"的时序答案（数据治理前置两年）。**
>
> **顾问点评**："决策准备层"的定位判断是全案例集最精确的系统定位——不替代 O9/SAP 而填补分析与决策之间的空白，这比"颠覆 ERP"式的叙事务实一个量级；把能做归因于两年前置的数据治理而非 AI 神力，是汇报材料里罕见的诚实；三范式框架（泛化 Agent / Agent+Skill+知识图谱 / Vibe Coding 定制工具）值得升级为公司级选型标准。三个必须追问的点：其一，**MIP 全局最优的采纳率未回答**——排产优化落地的经典暗坑是"算出来的最优被计划员改掉"，改的理由（隐性约束）如果不回流，优化器永远学不会人的现实，这恰恰是知识图谱最该先记的内容；其二，**汇报视角无使用遥测口径**——PV/UV 只有存在性声明，对照案例十一的单周遥测明细，本材料的"在用"缺证据；其三，知识图谱 / 财务闭环 / MRP 2.0 三项规划全是将来时。**建议打通**：MIP 修改回流强制记录原因并进图谱；MRP 2.0 回写 SAP 的权限分级（查询自动 / 录单人工确认）落在 MCP 工具层而非提示词层（参照案例十六的 prod 硬禁用做法）；"这个决策值多少钱"的财务闭环应作为二期最高优先级——它是唯一能让管理层持续投资的锚点。

## 1. 案例来源与背景

- 来源：内部汇报 PPT（演示型材料，含现场演示环节），汇报人朱岩滨、陈勇，供应链 PSM 域；
- 业务域：供应链 · 交付（D）——PSM（零部件供应管理）核心业务；
- 供应链 AI 全景覆盖五大业务域：Q 质量（PPAP/SPC/MSA）、C 成本、**D 交付（本材料主角）**、P 项目、O 运营；
- 材料性质与前十四个案例不同：**不是"我做了什么"的实践复盘，而是"系统展示 + 未来规划 + 方法论思考"的汇报**——可信度评估须区分"已建成在跑"与"规划中"两部分。

**作者给出的终局图景（2026 → 2028）**：

| 层 | 2026 今天 | 2028 终局 |
|---|---|---|
| 决策层 | 人 | 人 |
| 方案层 | 人 | **AI 生成，人选择** |
| 分析层 | 人 + AI 辅助 | AI 全覆盖 |
| 感知层 | AI 覆盖 | AI 全覆盖 |

"同样的团队，承载更多的业务"——目标不是减人，是人聚焦方案与决策。

## 2. 解决什么问题

| 问题 | 本案例的解法 |
|---|---|
| 决策准备层散落（30+ 飞书文档/Excel，版本混乱手工同步） | 统一工作台四模块，数据闭环 |
| 计划员每次决策前需整合多个文件 | 数仓 + O9/SAP 导出 + 自有规则数据直传，自动汇聚 |
| 交付与经营双底线冲突（上量期足量供应 vs EOP 期呆滞成本） | 四模块把呆滞风险量化为 ROI 锚点 |
| SAP 日常操作占计划员大量时间（查数/录单/跑报表） | MRP 2.0 规划：Agent 经 MCP Server 直连 SAP |

**业务规模**：主计划对象 15 个（25 款国内车型）、生产工单 257 SKU、400+ 供应商、8000+ 零部件、零部件呆滞管控上亿级（以 25 年呆滞预算为例）。

**核心命题**（原文表述）：对的零件 × 对的数量 × 对的时间——在有限的决策窗口内，用最优方案同时守住交付与经营的双重底线。

## 3. 任务流拆解

### 3.1 定位：填补"决策准备层"的空白

```text
系统执行流（不动的底座）          分析决策层（本系统新建）
O9 制定主计划 (W13)
    ↓
SAP-PPDS 生产订单          主计划 ←→ 方案模拟
    ↓                       ↓
SAP-MRP 物料预测    ⇄      库存监控 → 产能分析 → 呆滞控制    MRP2.0 智能采购
    ↓                       ↓ （数据交互）                      订单下达
SAP 采购订单
    ↓
SIP 供应商门户
数据层：O9库 / SAP库 / SIP库 → 数仓平台
```

关键定位声明：**不替代 O9 和 SAP，而是填补从"数据分析"到"上传决策"之间的空白**——计划员在贴合自己工作流的系统里完成分析、模拟和决策准备，再把结论同步回执行系统。

### 3.2 四模块闭环

① 主计划排产（知道造什么、造多少、什么时候停）→ ② 零件库存（有多少、够不够、标准是什么）→ ③ SIP 产能分析（供得上吗、瓶颈在哪、满足率多少）→ ④ EOP 呆滞控制（风险量化 = ROI 锚点）。

### 3.3 四类用户与决策动作

| 角色 | 日常使用场景 | 决策动作 |
|---|---|---|
| 供应计划员 | 看仪表盘 → 发现瓶颈 → 调排产 | 调整日度排产计划 |
| PSM 车型代表 | 收产能预警 → 定位供应商 | 协调供应商产能/交期 |
| PSM 专员 | 监控库存水位 → 识别超储/缺货 | 调整安全库存标准 |
| SMR 供应二级计委 | BI 看板监控 → 审阅计划执行 | 计划的决策和审批 |

### 3.4 AI 三角色分工

| 角色 | 技术 | 场景 | 替代什么 |
|---|---|---|---|
| 求解者 SOLVER | OR-Tools MIP 数学优化 | 产线共线、产能上限多约束下求全局最优，日排产方案自动生成 | 人工试错（只能找局部可行解） |
| 分析者 ANALYST | LLM + SSE 流式 | 中文描述约束自动转参数；瓶颈预警；临时性数据分析 | 固定报表 + 手工规则配置 |
| 预测者 PREDICTOR | Mirofish Agent 沙盒 | 需求预测、EOP 呆滞风险预演 | 经验判断 + Excel 静态模板 |

原文原则："让模型决策，人做判断……最终决策权和责任仍在人手里。"

## 4. 用到的能力

- **求解者**：OR-Tools 混合整数规划（MIP），多约束全局最优——十五案例中第一个真正的**数学优化引擎**进生产链（此前案例的"计算"都是规则引擎或 LLM）；
- **分析者**：LLM 自然语言约束解析 + 大模型读业务数据 + SSE 实时输出；
- **预测者**：Mirofish Agent 沙盒模拟；
- LiWork AI Agent 自动化执行业务模块（替代人工数据搬运）；
- 数据底座：数仓平台 + O9/SAP 导出 + 自有规则数据直传。

**规划中的能力（尚未建成）**：

- Ontology 自进化：OpenClaw 计划小助手自动写 graph.jsonl → Neo4j 知识图谱（增量推送、5 秒实时刷新、ForceAtlas2 可视化）——记录业务实体关联、**决策上下文**（每次排产调整背后的约束条件）、经验规则、**异常模式（历史呆滞/停线事件与前置信号的映射）**；
- 业务 + 财务双闭环：叠加单价/成本/P&L，"打开系统就知道这个决策值多少钱"；
- MRP 2.0：AI Agent × SAP MCP Server——自然语言意图 → Agent 理解执行（查询/录入/报表）→ 自动汇总分析给建议 → 人工确认回写 SAP。

## 5. 效果与证据

- 系统使用数据：材料称有 PV/UV 趋势图与现场演示环节（汇报型展示，具体数值未在文字中给出）；
- 四类角色的决策动作已进入日常工作流（供应计划员日度调排产、PSM 专员调安全库存标准）；
- 建设前后对比有实拍证据：建设前"实际飞书工作表截图"（30+ 个 M3滚动计划/排产模拟/库存水位/EOP 风险清单等文件）vs 建设后统一工作台；
- SAP 操作时长：现状痛点为 2~3 小时/天（MRP 2.0 的预期价值基于此，属规划）。

**注意口径**：本材料的效果部分是演示 + 自述，没有前十四个案例那种"单周遥测明细"（案例十一）或"日均使用 15-25 次"（案例十四）式的诚实量化——它是向上汇报的材料，天然倾向展示最好的一面。

## 6. 可信度判断

**判断：系统主体（四模块工作台 + OR-Tools 求解器）可信度较高；未来规划（知识图谱/财务闭环/MRP 2.0）按"愿景折半"处理；方法论框架（三范式）按高质量个人思考采信。**

可信的部分：

- 业务规模数字（15 主计划对象/257 SKU/400+ 供应商/8000+ 零件/亿级呆滞）是计划域的标准口径，具体且可核对；
- 建设前的"飞书文档 + Excel 决策准备层"现状有实拍截图佐证——这种"建设前证据"是汇报材料里最可信的部分（没人会伪造自己的混乱）；
- "为什么现在能做"的回答诚实：**前两年集成计划建设把 O9/SAP 数据规范化、数仓打通，上层工具才得以快速搭建**——把功劳归于数据治理前置，而不是归于 AI 神力；
- OR-Tools MIP 求解日排产是成熟技术路线（运筹优化 + 确定约束），"替代人工试错只能找局部可行解"的表述专业准确；
- 汇报含现场演示环节（"点击打开系统"）——敢现场跑的系统不会是 PPT 系统。

需要打折的部分：

- 使用数据只有"PV/UV 趋势图"的存在性声明，无数值；
- 未来规划三项（知识图谱"正在建设"、财务闭环、MRP 2.0）全部是将来时，其中"5 秒实时刷新""彻底改变人适应系统"是营销级措辞；
- "2028 终局"四层图是愿景叙事，无路径论证。

需要保留的部分：

- "SAP 操作 2~3 小时/天"的数据来源不明（计划员自估还是实测）；
- 求解者的 MIP 方案与计划员实际采纳率的关系未说明——算出的全局最优有多少被原样执行、多少被人改掉，这是排产优化落地的经典暗坑；
- 知识图谱自动记录"决策上下文"的隐私/审计边界（计划员的每次调整都被记录）未讨论。

## 7. 对我们当前项目的启发

### 7.1 三范式框架：把十四案例的选型判据讲明白了（对应 04-05 / 04-06）

材料第三章的三分法是本案例最大贡献——它恰好是我们前面十四个案例反复提炼的"物种选型判据"的正式版：

| 范式 | 适用 | 对应已有案例 |
|---|---|---|
| ① Agent 处理泛化任务 | 边界模糊、需要推理判断 | 供应商调研、纪要归纳、周报初稿 |
| ② Agent + Skill + 知识图谱 | 专业领域、高质量决策 | 案例九品类管理、案例十四被动安全知识库、本材料的计划小助手 |
| ③ Vibe Coding 定制工具 | **流程明确、规则确定** | 案例五仿真自动化、案例六 AAR 跟催、案例七 CATIA 校核、**本工作台自身** |

原文的旗帜性判断：**"AI ≠ 取代数字化，AI = 加速数字化"**——PSM 工作台属于"流程清晰 × 规则确定 → 用 AI 直接造工具"。这与案例五的"AI Coding 造确定性工具"完全同源，但首次被组织成三分谱系。对 04-06 的分层语言：范式③是 L0-L4 的加速器，范式②是 L7 纵向资产的运营者，范式①是通用层。

### 7.2 "决策准备层"是第四种系统定位（对应 02 / 案例四）

十五案例出现的系统定位谱系：执行系统替代（案例五）、跟催闭环（案例六）、监控底座（案例四）、**决策准备层（本案例）**——"不替代 O9/SAP，填补从数据分析到上传决策之间的空白"。这个定位特别精确地对应 02 的横纵分层：执行层（O9/SAP）不动，在分析层新建贴合工作流的界面，结论回写执行层。**对 12-03 的直接映射：Fabless 的 planning/commit 数据同样活在执行系统里，缺的正是这一层"计划员工作台"。**

### 7.3 "为什么现在能做"：数据治理前置的时序证据（对应 04-01）

原文明确把系统能快速搭建归因于**前两年**的集成计划建设（O9/SAP 数据规范化 + 数仓打通）。至此"数据治理前置约一个月"（小工具级）与"数据治理前置两年"（业务平台级）两个尺度都有了实证——字段级数仓语义字典（案例十一）+ 数仓打通（本案例）构成 AI 应用的真正门槛。写 04-01 时应引用本案例作为"耐心资本"的正面样本。

### 7.4 SAP MCP Server：工具连接层的又一标定（对应案例八/十二/十三）

MRP 2.0 规划的"NL 意图 → Agent 调 SAP MCP Server → 执行 → 人工确认回写"四步，与案例八（TRACE32 MCP 47 工具）、案例十二（CAA TCP 直连 CATIA）构成 MCP 路线的第三样本——从研发工具（调试器/CAD）扩展到**企业核心 ERP**。四步里保留"人工确认回写"与全案例的"AI 建议 + 人确认"分工铁律一致。注意它仍是规划：SAP MCP Server 的工具粒度设计（查询容易、**回写危险**）是落地时真正的难点。

### 7.5 知识图谱自动沉淀：经验→资产的第八样本，且是"自动形态"（对应案例十四 / 12-02）

与前七个样本（LI-PAS → … → 案例十四）相比，本材料的 Ontology 规划有两个新东西：

1. **捕获方式从人工投喂变为自动记录**——案例十四靠 9 人责任田喂文档，本案例靠 Agent 每次操作后自动写 graph.jsonl 增量推送。人工投喂有治理但成本高；自动记录无成本但噪声大（记录了操作≠记录了知识）。两者的真正答案可能是混合：自动记录决策上下文 + 人工提炼经验规则节点；
2. **记录"异常模式与前置信号的映射"**——历史呆滞/停线事件与其前置信号关联，这正是 12-02"难拦截失效要靠前置信号组合识别"的知识形态。

从"经验在人脑里"到"知识在图谱里"——与案例十四"经验不随人走"同一命题、不同技术路线（RAG 知识库 vs 图数据库）。图形态的优势是关系查询（"这个零件历史上出过什么事"），劣势是建设成本远高于文档投喂。

### 7.6 财务闭环："这个决策值多少钱"（对应 04-01 经营账本）

"业务数据闭环（排产→库存→呆滞量）叠加财务数据（单价/成本/P&L）"的方向与 04-01 的经营账本完全同构——呆滞控制模块已经把风险量化为 ROI 锚点，这是从"业务正确"到"经营正确"的迁移起点。供应链域比质量域更接近钱，这个闭环一旦建成就是 04-01 的最佳实证。

### 7.7 方法论金句（值得原文沉淀）

> AI 的能力上限 = 你对问题的清晰程度 + 你对 AI 的驾驭程度。

> 工具时代的瓶颈是人的执行速度；代理人时代的瓶颈是思考清晰度。

> 人从执行者升级为决策者——AI = 承包商，人出需求。

"想得越清楚，AI 做得越准"与案例七"想清楚不做什么比想做什么更重要"互为表里：一个是需求侧的清晰度，一个是范围侧的克制。

## 8. 后续想实测 / 追问的问题

- MIP 排产方案的采纳率：求解者算出的全局最优有多少被计划员原样执行、多少被修改、修改的理由是否回流进知识图谱——这是优化系统是否真的在用的判据；
- "临时性数据分析"（分析者角色）的频率与案例十一的"蒸馏剧本"路径是否会出现（高频临时分析 → 固化为定时任务的演进在供应链域会不会复现）；
- 知识图谱自动记录的噪声率：graph.jsonl 里多少是知识、多少是流水账，有没有人工清洗机制；
- MRP 2.0 回写 SAP 的权限设计：哪些操作敢让 Agent 执行、哪些必须人点确认（查询 vs 录单的分级）；
- 呆滞风险的量化模型口径：上亿级呆滞预算的"风险量化 = ROI 锚点"具体怎么算（EOP 时间点 × 单价 × 剩余库存的贴现？）；
- 汇报系统本身用 Claude Code Vibe Coding 搭建——"用 AI 造汇报 AI 用的系统"的递归是否影响了材料对范式③的偏爱（自证偏差检查）。
