# 理想汽车：质量安全数据分析智能体平台

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：金义，Level 1，质量安全，2026-08-17，板块：实战案例 · 工具分享，50 阅读）
>
> **一句话**：服务全体质量安全 PQE 的数据智能平台——把 100+ 自研看板的分析代码、数仓字段说明、开发者经验注入智能体，配齐数仓/可靠性分析/绘图/飞书读写/车云信号等工具包，实现"分析需求 → 生成代码查数仓 → 预处理 → 注入分析脚本（如 Weibull 可靠性预测）→ 绘图 → 撰写报告"全链路，支持 40 轮复杂分析、用户场景预设、方法蒸馏成剧本、定时任务全自动执行（单个闭环案例已自动跑 1485 例工单分析）。**这是与 12 系列（质量闭环）最直接相关的一篇——市场质量侧的完整任务闭环平台实证，几乎就是 04-05 的一个领域实例。**

## 2. 解决什么问题

| 痛点 | 解决方案 |
|---|---|
| PQE 日常需在公司各类信息/看板/数仓中查询汇总巨量信息，100+ 看板仍不够用 | 把 100+ 看板的分析代码、数仓主要报表字段说明、**开发者的开发经验**全部汇总注入智能体：分析用户需求 → 生成代码查询数仓 → 生成分析脚本 → 绘图 → 返回 |
| 专业工具（minitab、各类算法预测脚本）使用门槛高，数据获取与预处理困难 | 用开源包定制专业分析脚本（如 minitab 常用的 Weibull 可靠性预测），以工具形式接入智能体：取数 → 预处理 → 注入合适脚本 → 绘图 → 归纳总结 |
| 大量线下数据（供应商/门店排查数据、小组工作记录、工程师知识笔记）无系统支持，靠拉会对齐进展 | 飞书 API 数据读写套装接入智能体：按需读取飞书数据，**线上线下数据融合** |

## 3. 任务流拆解

### 3.1 平台能力栈

```text
大模型层：Qwen 3.5 / DeepSeek 4 / GLM5.2 等（理想内部部署，合规安全），支持多达 40 轮复杂分析
工具包层：
  数仓工具包      —— 质量安全自有数仓全量查询，已接入市场质量侧几乎所有数据
  可靠性分析工具包 —— 完整可靠性分析、故障率预测、指标计算
  自定义绘图工具包 —— 任意类型图表
  飞书文件读写    —— 按个人权限读写电子表格/多维表格/文档
  飞书机器人工具包 —— 拉群、群聊分析
  信号工具包      —— 车云信号（DTC 等）快速查询分析
知识层：各类指标/术语/分析逻辑预配置（开箱即用）
        + 场景预设（用户注入自己领域的知识和经验）
        + 蒸馏剧本（对话调优后的分析方法固化为剧本）
交互层：线上智能平台 + 飞书机器人（门店出差、故障现场排查场景）+ 定时推送
```

### 3.2 作者给出的"智能化拆解"公式

```text
智能 = 大模型 + 专业工具 + 智能化的调度 + 专业知识 + 完备的数据 + 合理的交互形式
```

（与 04-06 分层的对应：大模型→L0/L1，专业工具→L2，调度→L4，专业知识→L7/L8，数据→L3，交互→平台层。）

### 3.3 典型闭环案例：50% 无助力分析（转向相关工单）

```text
① 原始数据获取：昨日转向相关全量 TS 工单 + 质量工单，剔除过往已处理，
   找到今日需处理工单，匹配车辆信息，统计入表
② 信号获取分析画图：对存在报警的工单画图（含车速——判断车辆是否行驶中——及 DTC 信号）
③ 对话式调优：与 AI 对话不断调整绘图结构，并对分析方法【蒸馏】
④ 报告撰写：基于当前数据生成报告
⑤ 配置定时任务：全自动执行
→ 7 月上线以来，该问题已全自动执行 1485 例工单分析
```

这条链路的关键结构：**交互式分析（人机对话调优）→ 方法蒸馏成剧本 → 定时任务全自动化**——从"人用 AI"演进到"AI 按剧本自转"。

其他案例：热力图与故障率预测、数据获取与自定义绘图、报告输出前检查（AI 自查报告）。

## 6. 可信度判断

**判断：真实落地且采用度证据充分（十一案例中使用数据最具体的一篇），但分析质量和对业务的实际影响未验证。**

可信的部分：

- **单周使用明细**（2979 次信号查询、1750 次数仓查询、1059 图、437 表、69 报告）是运行系统的真实遥测数字，颗粒度和量级自洽（信号查询多于数仓查询多于绘图多于报告，符合漏斗形态）；
- 时间线完整（6 个月 alpha→1.0）、当前迭代节奏（周 2~3 次）具体；
- 1485 例自动工单分析、140+ 用户自配剧本、60+ 周活——三个数字从不同侧面交叉印证了真实使用；
- 向管理层汇报过、有国家科研项目背书，项目级别不低；
- 痛点描述真实："100+ 看板仍不能满足需求"是对 BI 疲劳的诚实陈述。

需要保留的部分：

- **无任何业务效果数据**：1485 例自动分析避免了多少问题漏判？分析结论的准确率？PQE 工时节省多少？全部缺失——使用量 ≠ 业务价值；
- "预计逐步替代 100+ 看板"是愿景，替代进度未说明；
- 40 轮复杂分析的失败率/中断率未披露（长链路 Agent 的稳定性是普遍软肋）；
- 生成代码查数仓的准确性：SQL 语义错误、字段理解错误会导致错误结论进入报告，是否有校验机制未说明；
- 文章细节有疏漏（模型版本号前后不一致：Qwen 3.5/3.6/3.7 混用），写作严谨度一般。

结论：**平台真实、采用度实证充分；从"用得多"到"用得对"的验证还差一层。**

## 7. 对我们当前项目的启发

### 7.1 与 12 系列最直接相关：市场质量侧的任务闭环实证（对应 04-05 / 12）

12 系列关注的是制造/供应侧质量（CP/FT 良率、供应商、PCN），本案例是**市场质量侧**（TS 工单、车云信号、故障率、消费者投诉）——两者拼起来才是质量闭环全貌。对照 04-05 的任务闭环要素，本案例全部齐备：

| 04-05 要素 | 本案例实现 |
|---|---|
| 数据感知 | 数仓全量 + 车云信号 + 飞书线下数据融合 |
| 专业工具 | Weibull 可靠性、绘图、飞书读写 |
| 知识资产 | 看板代码 + 字段说明 + 开发者经验 + 用户场景预设 |
| 人机协同 | 对话调优 → 蒸馏剧本 |
| 无人化终态 | 定时任务自动执行 1485 例 |
| 触达 | 飞书机器人 + 定时推送 |

**对 12-02/12-03 的直接启示**：芯片质量侧（市场退货 RMA、现场失效）完全可以复用这套结构——RMA 数据库 + 可靠性工具包（Weibull 恰好是 12-02 里的可靠性失效分析手段）+ 失效分析知识注入 + 蒸馏剧本。12-03 的 RMA 反向追溯闭环，其工具形态就是这个案例的样子。

### 7.2 "Agent 吃掉 BI"：100+ 看板的黄昏（对应 04-06）

本案例最重要的架构陈述：**100+ 自研看板仍不能满足分析需求，解法不是做第 101 个看板，而是让 Agent 直接查数仓生成分析**。这是对传统 BI 范式的替代宣言——看板回答的是"预设问题"，Agent 回答的是"任意问题"。

对 04-06 的推论：L3（知识检索）之上会分化出"数据检索 + 代码生成"能力——**数仓字段级元数据（每个报表每个字段的语义说明）是最被低估的基建资产**。本案例把"数仓主要报表的字段说明"当作知识注入，这正是 AI 能正确生成查询的前提。12 系列同理：测试数据库、良率数据的字段级语义字典是质量 Agent 的地基。

### 7.3 经验→资产第六个样本，且首次展示完整三段演进（对应 02）

```text
LI-PAS → 流程库 → EHS → DebugForge → CELN 案例库 → 本案例
```

本案例的独特贡献是把经验资产化的**三段演进**首次完整展示：

```text
第一段：专家经验 → 知识注入（看板代码、字段说明、开发者经验进系统提示词）
第二段：用户经验 → 场景预设（每个工程师描述自己领域的分析，140+ 个）
第三段：对话调优 → 蒸馏剧本 → 定时任务（从人机交互沉淀为全自动执行）
```

特别是第三段：**"蒸馏"发生在人机对话过程中，且蒸出的剧本直接进生产（定时任务）**——这是 04-05 里"专家修正数据回流"的最强实现形态。60 人周活产出 140+ 剧本，说明工程师有真实动机做蒸馏（蒸馏一次，终身自动）。

### 7.4 开发者经验是最被忽略的知识源

"将 100+ 看板的分析代码、数仓字段说明、**开发者的开发经验**全部汇总归纳注入智能体"——大多数组织的知识管理只做文档，而**看板的分析代码本身就是最精确的方法论表达**（代码即知识）。这对任何做数据分析 Agent 的团队都是直接可抄的：先挖自己存量 BI 资产里的代码和口径，而不是从零写知识库。

### 7.5 长链路（40 轮）+ 多模型：工程上值得关注

- 40 轮复杂分析套路说明任务复杂度真实存在（取数→清洗→分析→绘图→报告本来就是多步流程）；
- 多模型并行接入（Qwen/DeepSeek/GLM 内部部署）+ 合规安全——印证 04-06 L1 模型网关判断：模型会换、编排留在平台层。

### 7.6 最值得抄的设计

1. **三段演进路径**（知识注入 → 场景预设 → 蒸馏剧本进定时任务）——见 7.3，Agent 平台的运营主线；
2. **字段级数仓语义字典**作为核心知识资产——AI 生成查询的准确率地基；
3. **分析代码即知识**：把存量看板代码当方法论挖出来注入，冷启动最快路径；
4. **按个人权限读写飞书**：线上线下数据融合时权限跟随个人（与案例三 EHS 权限跟随原系统同构）；
5. **飞书机器人兜底移动场景**（门店出差、故障现场排查）——交互形式跟着工作场景走，不是把人拴在电脑前；
6. **单周使用明细式汇报**：按动作类型分列（查信号/查数仓/绘图/表格/报告）——Agent 平台最诚实的采用度指标口径，比"提效 30%"可信一个量级。

## 8. 后续想实测 / 追问的问题

- 分析质量验证：1485 例自动分析的结论准确率多少？有没有人工抽检机制？错误结论进入报告的拦截手段；
- 生成 SQL/分析代码的校验：字段理解错误的防范（字段语义字典的覆盖率和维护机制）；
- 40 轮长链路的完成率/中断率，失败时如何降级（对比案例七的 UNVERIFIED 设计）；
- "替代 100+ 看板"的实际进度：哪些看板已下线，哪些必须保留（预设问题的固定消费场景仍需要看板）；
- 蒸馏剧本的质量把控：140+ 用户剧本有没有冲突、过时、错误口径，谁负责治理；
- 可靠性预测（Weibull）的参数选择和模型假设由谁确认——统计工具的输出直接进报告，专业性背书机制；
- 市场质量 Agent 与制造质量数据（12 系列的 CP/FT、供应商数据）是否打通——完整质量闭环缺的就是这一横。
