# LI-PAS：理想汽车车载系统性能稳定性问题分析助手

> 收录日期 2026-09-30 · 来源：内部技术分享（作者：南帅波，理想汽车，2026-09-20）
>
> **一句话**：LI-PAS 是面向 SS4 8797 平台车载系统性能与稳定性问题的专属分析助手，把问题受理、日志获取、根因分析、知识复用、知识归档和结果交付串成一套工程化 Agent 工作流，把资深工程师的分析经验沉淀为团队可复用的 Skill 和知识库资产。

## 2. 解决什么问题

### 2.1 现状痛点

8797 平台的性能与稳定性问题来源分散：

- 售后质量工单；
- Jira 缺陷；
- 线上监控告警；
- 用户反馈；
- 崩溃平台；
- 测试环境。

问题类型复杂：

- ANR；
- Watchdog；
- System Server Crash；
- Native Crash / Tombstone；
- 黑屏；
- 异常重启；
- Kernel Panic / Soft Lockup；
- CPU / 内存 / IO / GPU / 内核 / 版本适配。

传统分析高度依赖个人经验：登录日志平台 → 选日志类型 → 等待下载 → 解压公司内部格式（CLP、ZST、lastlog）→ 海量日志中定位关键信息 → 结合代码和历史案例判断根因。简单问题约一小时，复杂问题半天起。

### 2.2 核心痛点与解法对照

| 痛点 | 具体表现 | LI-PAS 解法 |
|---|---|---|
| 日志获取耗时 | 手动平台操作 20~30 分钟 | 按 VIN + 时间自动下载预处理 |
| 分析依赖经验 | 新人不知看什么，老手经验难复制 | 资深分析方法固化为标准 Skill |
| 同类问题重复分析 | 每次从头排查 | 分析中自动检索历史案例 |
| 经验沉淀困难 | 根因散落个人记录和聊天 | 分析完成自动归档为公共知识资产 |
| 工具切换繁琐 | 日志平台 / Jira / OpenGrok / 命令行 / 飞书来回切 | 一个对话入口串联全流程 |
| 日志格式复杂 | CLP、ZST、lastlog 内部格式 | 自动识别、解压、解析、提取证据 |

### 2.3 定位边界

明确不替代工程师做最终定责，而是把工程师从重复劳动中解放出来，精力回到根因确认、修复决策和风险判断。

## 3. 任务流拆解

```text
问题受理
  Jira 号 / 质量工单卡片 / 监控告警 / 群聊引用 / VIN+时间+现象 / 直接发日志文件
  ↓ 自动提取 VIN、故障时间、版本、车型、现象
日志获取与预处理
  按时间窗口自动下载云端日志，处理 CLP / ZST / lastlog 格式
  ↓
标准分析路径（Skill 路由）
  1. 问题识别与上下文补全（信息不全先补齐，不盲目下载）
  2. DropBox 症状提取（判断问题类型、定位早期异常、提取初始堆栈）
  3. Android 日志时间线还原（服务启动、进程死亡、重启、资源变化先后关系）
  4. 按需补充多侧证据（内核、驱动、GPU、PVM、GVM、MCU、资源压力）
  5. 结论校准与结构化输出
  ↓
知识库参与（嵌入分析过程而非事后查询）
  分析前：现象检索热身
  分析中：证据比对（异常类型、调用栈、线程、版本、车型、触发场景）
  分析后：根因精确检索（异常类名、服务名、方法名、驱动名）
  分析完成：结果回写（新问题模式 / 追加历史实例）
  ↓
结果交付
  基本信息、关键证据、时间线、根因链、影响范围、历史案例、待验证项、建议动作
  明确区分：已确认 / 疑似 / 待验证 / 无法确认
```

## 4. 用到的能力

| 能力层 | 职责 | 沉淀结果 |
|---|---|---|
| 问题受理 | 识别 Jira、工单、告警、群聊、VIN 输入 | 统一上下文和问题标识 |
| 工具链 | 日志下载、解压、解析、查询、源码检索 | 可追溯的原始证据 |
| 分析 Skill | 问题路由、专项方法、证据要求 | 稳定的分析路径 |
| 知识库 | 问题模式、历史实例、版本、根因 | 可复用的团队经验 |
| 结果交付 | 卡片、文档、周报、看板 | 可协作可复盘的结论 |

技术要点：

- 知识库检索：向量检索 + 关键字重排的混合召回；
- 知识库结构：双层——问题模式（可复用根因 / 分析方法）+ 历史实例（不同车辆、版本、场景的实际发生情况），可观察版本回归和影响范围变化；
- Skill / 工具链 / Agent 分工：Skill 规定"如何分析"，工具链获取真实数据，Agent 串联输入识别、日志准备、专项路由、分析执行和结果交付。

## 5. 知识库治理亮点（最值得借鉴的部分）

知识库使用有明确边界，这段几乎是"如何防止 RAG 知识库污染"的教科书清单：

- 现象相似不等于根因相同；
- 相似度高不等于可以直接归并；
- 历史版本较旧时不能直接称为当前版本已知问题；
- 同一事件多个 fault addr / grp_id 时，按 VIN 和时间窗口识别 crash loop，避免重复统计；
- 参考文档或日志无法覆盖的现象，保留原始证据并标注无法确认，不自行补全根因。

设计哲学：

> 知识库不是为了让 AI 更容易"猜中答案"，而是为了让每一次结论都能说明依据、适用条件和不确定性。

## 6. 典型实践模式

1. **区分根因与次生现象**：DeadSystemException / 连续崩溃不能直接认定应用是根因，先查更早的 System Server Crash 或 Watchdog；
2. **还原黑屏重启链路**：区分 Android 上层重启、GVM/PVM 异常、MCU 重启、用户盘控重启；盘控重启后的 IO 超时要继续往前查；
3. **识别资源传播链**：形成"资源压力 → 线程阻塞 → 服务超时 → 用户现象"证据链；
4. **文档未覆盖问题的兜底**：先常规排查，再专项兜底，仍无根因则保留原始证据、明确不确定性、把新分析方法沉淀回 Skill 和知识库。

## 9. 对我们当前项目的启发

与我们 insights 体系的映射：

### 9.1 验证了 `04-05` AI Native 任务闭环平台的形态

LI-PAS 几乎是 `04-05` 八层架构的一个真实样例：

| 04-05 平台层 | LI-PAS 对应 |
|---|---|
| 连接层 | 日志平台、Jira、质量工单、崩溃平台、OpenGrok、飞书 |
| 语义层 | VIN、车型、版本、问题类型、现象的统一上下文 |
| 知识层 | 问题模式 + 历史实例双层知识库，向量 + 关键字混合召回 |
| 任务层 | 问题受理 → 分析 → 校准 → 交付的任务流 |
| AI 能力层 | 分析 Skill + 专项路由 |
| 治理层 | 知识库边界规则、结论分四档（已确认/疑似/待验证/无法确认） |
| 反馈层 | 结果回写、纠错闭环（规划中） |
| 经营归因层 | 尚未建设（无量化效率数据） |

### 9.2 验证了 `02` 纵向资产的沉淀形态

LI-PAS 留下来的、换框架也带得走的东西，正是 `02` 说的四类纵向资产：

- 领域知识：问题模式、根因链、分析路径（声明式 Skill，不是代码 if-else）；
- 反馈闭环：问题 → 分析 → 根因 → 实例归档 → 下次比对；
- 领域评价：结论四档区分、归并校准规则、知识库边界规则；
- 标注样本：历史实例（VIN、版本、场景、证据、验证状态）。

### 9.3 与 `11/12` 芯片质量系列同构

LI-PAS 的问题分析模式和我们芯片失效分析框架高度同构：

| LI-PAS | 芯片质量分析 |
|---|---|
| DropBox 症状提取 | CP / FT fail bin 初筛 |
| 时间线还原，找更早异常 | 失效链路分析，区分根因与次生现象 |
| 历史案例比对 | RMA 反向追溯、相似失效模式归并 |
| 版本回归观察 | PCN 前后参数分布对比 |
| 保留证据、标注无法确认 | 证据链要求，不猜根因 |

说明"证据驱动的异常分析 + 案例知识库 + 人工校准闭环"是跨行业通用的任务闭环骨架。

### 9.4 最值得直接抄的设计

1. **知识库双层结构（问题模式 + 历史实例）**：比单纯存文档或单纯存案例都好，能同时复用方法和观察版本回归；
2. **知识库嵌入分析过程**（前热身、中比对、后精确检索、完成回写），而不是分析完再搜一下；
3. **结论四档制**：已确认 / 疑似 / 待验证 / 无法确认——所有 B 端 Agent 输出都应该这样分级；
4. **知识库反污染规则**：现象相似≠根因相同、相似度高≠可归并、旧版本≠当前已知问题；
5. **信息不全先补齐再分析**，不盲目下载和分析。

## 10. 后续想实测 / 追问的问题

- 实际周处理量、平均分析时长、与人工基线的对比数据；
- 知识库条目数、增长速度、归并准确率；

- 纠错闭环落地后的驳回率；
- crash loop 识别（VIN + 时间窗口）具体规则；
- 知识库中"问题模式"的 schema 具体字段定义；
- 是否考虑把人工归并校准的记录用于后续 SFT / reward（正好对应 `04-06` 说的任务轨迹沉淀）。
