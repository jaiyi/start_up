## 3. 任务流拆解

### 3.1 新旧流程对照

```text
旧：产品出需求 → 内审 → 外审 → 技术方案 → 评审 → 开发 → 自测 → 上线预案 → 上线 → 运维
    （每环节人等人）

新：产品 + 研发 + Sage 三方讨论需求（Sage 知道系统现状）
    → Sage 辅助制定方案（brainstorming + 复杂度评估选路线）
    → 人确认方案 → 写入飞书文档关联 Issue（IDD 问题驱动开发）
    → Sage 新拉 feature 分支逐服务开发 → 提交 GitLab
    → cr-agent 代码 Review（逻辑漏洞/边界/并发）
    → Sage 部署 test/ontest（prod 在 Skill 中禁用）→ 人工测试
    → Sage 合并分支 → Sage 生成上线预案
    → 上线后：Sage 巡检 & 问题排查
```

关键设计点：

- **方案确认节点保留人工**："这一环节需要人仔细阅读方案，确认无误后"才写入文档——AI 建议 + 人确认铁律的又一实例；
- **复杂度分流**：根据方案评估需求复杂度，判断直接开发 / superpower / openspec 三条路线——对应"物种选型判据"的代码级实现；
- **风险分级**：test/ontest 环境可 @Sage 直接部署，**prod 环境风险大目前在 Skill 中禁用**——用 Skill 配置做硬权限边界；
- **较大需求建议人工拉代码 check 核心链路**——自动化的范围自知之明。

### 3.2 九个案例场景（全部带前后对比）

| # | 场景 | 传统 | Sage 模式 |
|---|---|---|---|
| 1 | 完整需求开发 | 小需求 2-3 天 / 标准需求 5PD | 0.5 天 / 2PD（核心耗时：方案对齐+人工自测） |
| 2 | 线上问题排查 | 30min（手写 SLS→翻日志→看代码） | 5min 内（NL→自动查询→代码定位→建议修复） |
| 3 | 截图分析陌生系统 | 30min+（翻代码/问同事） | 30 秒（识别字段→知识图谱定位表和 ORM 映射） |
| 4 | 构造测试数据调接口 | 10min（查文档→拼参数→Postman） | 3min（NL→找到服务→解析接口/MQ 定义→生成语义合理数据→直接调用） |
| 5 | 复杂问题定位 | 1 天（多人协作反复猜） | traceId 对比全链路→定位 IDaaS token 失败缓存 10 秒的代码级 Bug→一键生成修复 |
| 6 | 运维操作溯源 | 15min+（多系统拼查询） | NL→lcp-ops skill 查操作日志→定位操作人和时间 |
| 7 | 链路分析 | 人工逐条翻日志拼链路 | traceId→完整调用链+各节点耗时→定位超时接口 |
| 8 | 全量巡检 | 2 人天（逐服务看 Grafana） | 2 分钟（88 服务所有指标+巡检报告异常高亮） |
| 9 | 线上改数据 | 手写 SQL 心惊胆战 | 工单→Agent 准备好 SQL（人执行） |

案例五值得单独记录——这是九个场景中推理深度最高的：

> 线上同样的调用链路一次成功一次失败。Sage 对比两条链路日志发现失败链路 `response: 403, fetch token: Forbidden`；人补充线索"其他 pod 也出现过，不是网络问题"；Sage 跨 pod 搜索 + 结合代码 `LcpTokenUtils` 分析，最终定位根因：**IDaaS token 失败结果被缓存，后续 10 秒内请求直接拿到失败缓存，未重新发起认证请求**。定位后一键生成修复代码，人工验证后合并上线。

这是一个标准的"人机协同诊断"样本：AI 做差异对比和跨源检索，人提供领域直觉（"不是网络问题"），AI 收敛到代码级根因。

## 4. 用到的能力

- **代码知识图谱**：88 服务 / 69K+ 节点，覆盖服务间调用关系（协议）、接口依赖影响链、数据流向（入口到落库完整路径）、实体映射（数据库表 ↔ ORM 类 ↔ 接口字段）——案例十五 Neo4j 知识图谱规划在这里已是运行中的现实，且落在代码域；
- **Skill 架构**：40+ Skill 覆盖 7 大能力域，Skill 间可自动串联编排（查日志→定位代码→生成修复→提交→部署），新能力接入=新增 Skill 不改架构——与案例八 Debug Skills、案例十三 40+ 规则 Skills 同族；
- **工具链**：GitLab / SLS 日志（阿里云）/ Grafana / 飞书 / 融合云部署——"研发在飞书一句话，背后跨 5 个系统"；
- **多模态**：截图识别数据字段→结合知识图谱定位（案例三）——图片输入在研发场景的真实生产力应用；
- **长期记忆 + 自我改进**：记得讨论历史、团队编码规范、系统历史决策；**失败排查路径、有效查询模式、业务特殊逻辑自动沉淀为 Skill 规则**——"越用越准"；
- **测试数据智能生成**：基于代码接口定义或线上真实日志生成符合业务语义的测试数据。

## 5. 效果与证据

- 九个场景全部有前后耗时对比，且量级诚实（标准需求 5PD→2PD 而非"10 倍提速"；瓶颈被如实标注为"方案对齐+人工自测"——**人的环节成了新瓶颈**，这是诚实的信号）；
- 三个带具体日期的真实场景：2026-05-22 截图定位（表名字段说明）、2026-06-01 IDaaS token 缓存 Bug（含完整推理链和 `LcpTokenUtils` 代码名）、2026-06-02 充电枪状态溯源（terminalId 定位）；
- 巡检 88 服务 2 人天→2 分钟，且输出物明确（巡检报告+异常高亮）；
- 文章含大量界面截图（原文 20+ 张 image.png）；
- 准入限制反向证明在真实使用（token 成本高到需要限流）。

**注意口径**：耗时对比均为作者自述，无系统遥测明细（对比案例十一的单周使用量数据）；"Sage 越用越准"无量化（自我改进的效果追踪缺失）。

## 6. 可信度判断

**判断：系统真实、场景真实、推理链可信；效率数字按"自述折半但方向正确"处理；"自我改进/越用越准"按愿景打折。**

可信的部分：

- 三个带日期的案例有完整推理链（尤其是案例五：日志差异→人工线索→跨 pod 检索→代码根因→修复，每步都有具体对象名），这种颗粒度编不出来；
- 诚实的新瓶颈披露："核心耗时：方案对齐+人工自测"——说明作者清楚哪些环节 AI 替代不了，不是全流程神话；
- prod 部署禁用的权限设计、大需求建议人工 check、方案需人确认——**三处保守设计**是真实系统治理的痕迹而非宣传话术；
- token 成本限流是反向证据：免费无限用的多半是演示系统，掐着成本用的才是生产系统；
- IDD（Issue-Driven Development）与飞书文档关联的工作流细节完整可操作。

需要打折的部分：

- 全部效率数字为自述且采样方式不明（最佳案例还是平均水平？）；
- "0.5 天完成小需求"包含的隐含前提（需求是否足够小、Sage 是否已经学过该服务）未讨论；
- 40+ Skill / 69K+ 节点图谱的建设成本和维护成本完全未提——这个图谱谁来建、代码大重构后图谱怎么保持同步，是文章回避的最大问题；
- "长期记忆 + 自我改进"的机制描述停留在理念层（"遇到问题自动更新 Skill 规则"——具体怎么触发、谁审核更新、错误经验会不会也沉淀进去）。

需要保留的部分：

- 九个场景全部来自正面叙事，没有失败案例和踩坑节（**前十五个案例几乎都有坑表，本文没有**——要么作者略去，要么系统太新还没攒够坑）；
- CR 质量（"发现逻辑漏洞、边界条件遗漏、并发问题"）无实例佐证，与业界 CR Agent 的实际水平（发现的多是浅层问题）可能存在落差；
- 自我改进的错误累积风险：失败的排查路径若自动沉淀为规则，可能把错误方法论固化。

## 7. 对我们当前项目的启发

### 7.1 研发域的"任务闭环"完整形态（对应 04-05 / TaskTrace）

前十五个案例覆盖了研发周边（流程拟制/仿真/评审/调试工具），本案例是唯一**贯穿软件研发全生命周期**的 Agent：需求→方案→开发→CR→部署→测试→合并→预案→巡检→排查→修复。对 04-05 任务闭环 schema 的贡献：闭环不必限于单任务域，可以是一条**职业工作流**（计划员工作台案例十五是供应链版，本案例是研发版）——两者的共同结构都是"决策准备层收口 + 执行系统保留人确认"。

### 7.2 知识图谱从规划到现实：代码域先行（对应案例十五）

案例十五的 Neo4j 知识图谱是"正在建设"，本案例的 88 服务/69K+ 节点代码图谱已运行并直接支撑截图定位、影响链分析。**代码域图谱先于业务域图谱落地**的原因值得注意：代码有编译器级别的结构（调用关系/ORM 映射是客观存在），实体和关系可以自动抽取；业务域知识（案例十四）才需要人工责任田投喂。这给 04-06 的分层一个新判断：**知识图谱的可行性排序 = 数据结构化程度排序**（代码 > 配置 > 制度文档 > 口头经验）。

### 7.3 权限分级三实例：Skill 配置做硬边界（对应案例四/六/八）

prod 禁用部署是本案例最重要的工程决策之一——它和案例八（真芯片烧录需人确认）、案例四（审批树责任人）构成权限设计谱系。**用 Skill 配置（而非提示词）做环境级硬禁用**是可复用的模式：Skill 是代码级资产，禁用逻辑随 Skill 分发、不依赖模型自觉。对 12-03 的映射：Fabless 的 Agent 直连供应商门户/ERP 时，"只读自动、写操作分级确认"应按同样思路落在工具层。

### 7.4 人机协同诊断的标准范式（对应 12-02 / 案例八）

案例五的排查过程是"AI 差异对比 + 人领域直觉 + AI 收敛根因"三方协作的教科书样本。与案例八 DebugForge（Agent 自主调试真芯片）对比：Sage 模式更依赖人给关键线索（"不是网络问题"一句直接剪掉了搜索空间）。这提示 12-02 的失效分析 Agent 设计：**不要追求全自动根因定位，把"人给直觉、AI 做穷举验证"作为默认分工**——老工程师的直觉是最贵的信号，AI 的价值是把它快速变成结论。

### 7.5 自我改进的治理缺口（对应案例十四）

"失败排查路径自动沉淀为规则"与案例十四"当场提问验证"形成鲜明对照：人工投喂有验证环节，自动沉淀没有审核环节。**经验→资产的第九个样本，也是第一个没有质检环节的样本**——坑恰好出在这里（错误经验也会固化）。正确形态可能是案例十四与本案例的混合：自动捕获决策上下文（案例十五规划）+ 人工验证后入库（案例十四流程）。这与我们 04-05 里 TaskTrace 的设计判断一致：轨迹自动记录，提炼入库需人确认。

### 7.6 跨案例收敛：研发域四个物种的位图

结合本案例与案例二/八/十二，理想汽车研发域的 AI 位图已完整：

| 物种 | 案例 | 判据 |
|---|---|---|
| 全流程常驻 Agent | 本案例（Sage） | 需求到运维的连续工作流 + 代码知识图谱底座 |
| 工具直连 Agent | 案例八（DebugForge MCP） | 假设-验证循环的深度调试 |
| 规则评审 Agent | 案例十二（五元组） | 制度合规性判定 |
| 流程资产诊断 | 案例二（反向体检） | 存量制度资产的质量问题 |

### 7.7 新瓶颈的诚实披露值得写入方法论

"2PD 的核心耗时：方案对齐 + 人工自测"——AI 接管重复劳动后，瓶颈从执行转移到**人的对齐和验证**。这与案例十五"代理人时代的瓶颈是思考清晰度"互为印证，也是我们 04-06 里"AI Native 转型的真正约束在人侧"判断的第三个证据（案例七需求收敛、案例十五思考清晰度、本案例方案对齐）。

## 8. 后续想实测 / 追问的问题

- 知识图谱的**维护成本**：88 个服务持续迭代，图谱多久同步一次、大重构（服务拆分/合并）后怎么办，有没有自动增量机制（案例十五的 graph.jsonl 自动推送思路在这里是否已用）；
- 自我改进的具体机制：Skill 规则自动更新由什么触发、有没有审核、沉淀过多少条、错误规则出现过吗；
- CR-agent 的实际检出分布：逻辑漏洞/边界/并发的真实占比 vs 格式类问题占比（有没有统计）；
- 九个场景之外的使用数据：日均调用量、周活、被使用最多的 Skill（对照案例十一的遥测明细口径）；
- 40+ Skill 的所有权：谁维护哪些 Skill，有没有像案例十四那样的责任田；
- token 成本的具体量级：限流决策背后的数字（每月多少？单人多少？）——这是所有"为什么不能全员用"问题的答案；
- 截图分析（案例三）的幻觉率：识别错字段时知识图谱会不会将错就错给出错误定位。
