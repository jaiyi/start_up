# 理想汽车：三维装配路径校核工具

> 收录日期 2026-09-30 · 来源：内部技术社区文章（作者：汪文豪，Level 3，整车电动，2026-08-26，板块：工具分享 · 实战案例 · 知识充电，122 阅读）
>
> **一句话**：一名灯具工程师用 Claude Code 做了一个 CATIA 装配路径校核 Skill——输入"待装/已装"两份 .CATProduct 和一个安装方向，Skill 生成 CATScript 宏由工程师在本机 CATIA 里执行，每毫米级逐点做"命令—更新—读回—审计—Clash"五步校核，输出四种结论之一（通过/中间碰撞/需工程师确认终点接触/证据不足）。**"让 CATIA 做判断，让 AI 做编排"——这是七个案例里工程严谨度最高的一篇，而且它本身就是一个 Claude Code Skill，和我们的工具生态直接同构。**

## 1. 案例来源与背景

- 来源：公司内部技术社区文章，作者汪文豪（Level 3 进阶学员，整车电动），2026-08-26，阅读量约 122；
- 业务域：整车电动 · 灯具工程师的装配设计校核（DMU 数字样机）；
- 工具形态：Claude Code Skill（`%USERPROFILE%\.claude\skills\catia-assembly-path-check\`）+ CATScript 宏 + CATIA V5（Assembly Design + DMU Space Analysis 的 Clash 自动化）；
- 痛点：零件"能不能装进去"长期靠工程师脑补、挪模型目测，或等物理样件才发现装不进去。

---

## 2. 解决什么问题

**问题聚焦到一句话**：一个关键件，能否在某个装配姿态下、沿指定方向（+X/+Y/+Z）、保持固定朝向直线推进，从待装状态走到装配到位状态，全程不发生不允许的接触或干涉。

输入三样东西：待装配 .CATProduct、装配完成 .CATProduct、安装方向。输出一个明确的中文结论。

**它明确"不做"什么（作者认为这是整个项目最重要的设计决策）**：

- 不绕开障碍走弯路；
- 不先旋转再推进、不边移动边旋转；
- 不做随机三维路线搜索（RRT、SE(3) 那一套）；
- 不换装配顺序、不临时移走别的零件；
- 不判断负轴或反向安装。

所以"沿 +X 推不进去"的真实含义只是"这个指定方案不行"，不代表零件一定装不上——边界诚实。

## 3. 任务流拆解

### 3.1 校核流程（四步）

```text
① 找出谁在动
   比较两份 Product 的一级零部件：位置朝向没变 = 固定件，变了 = 待装件
   硬性约束：必须恰好只找到一个移动件；多个/对不上/找不到 → 不猜，报告问题向人求证
② 先查起点和终点
   起点有碰撞 → 装配起点不干净，直接停止
   终点有接触/过盈（卡扣、密封、压装）→ 不自作主张认定正常，交给工程师确认是否设计意图
③ 每毫米级逐点试装
   行程约 76mm → 至少检查 77 个姿态（两端都算），每个采样点严格五步：
   命令 CATIA 把零件放到该位置 → 更新装配 → 读回真实位置确认没跑偏
   → 命令位姿与实际位姿偏差 RMS ≤ 0.0001，否则该点判为未验证
   → Clash.Compute 精确检查接触/实体重叠
④ 结论 + 证据留档
```

### 3.2 四种结论（状态机设计）

| 状态 | 含义 |
|---|---|
| HIGH_PRECISION_PATH_PASS | 通过：刚体假设下沿指定方向直推，每毫米级检查无不允许碰撞 |
| PATH_FAIL_INTERMEDIATE_CONTACT_OR_CLASH | 中间碰撞：起终点也许没问题，但中途撞上 |
| NEEDS_TERMINAL_RULE_CONFIRMATION | 终点有接触/过盈，需工程师判断是否设计允许 |
| UNVERIFIED | **证据不足，不代表"没问题"** |

中间碰撞时，记录首次碰撞的完整位置和朝向（12 元素位姿、轴向位置、路径比例、Type/Value 冲突签名写入报告和 CSV），并自动生成"首次干涉查看宏"——运行后 CATIA 把零件停在第一次碰撞位置，用 DMU Space Analysis 的 Clash 和 Sectioning 亲眼看哪块几何体穿透。

### 3.3 使用流程（人的位置）

```text
准备（Windows + CATIA V5 + 两份同根坐标系模型）
→ /catia-assembly-path-check 调用 Skill（填两个 Product 路径 + 安装轴；不填轴会反问，绝不猜）
→ Skill 生成 case 专用 CATScript 宏（Skill 不直接操作 CATIA）
→ 工程师本人在 CATIA 里 Tools → Macro → Run
   （先预检宏：开模型、识别移动件、查起终点冲突、恢复起始位姿；过了再跑高精度校核宏）
→ 回一句"已运行"，Skill 读 case 输出目录报告，给中文结论
→ 纪律：关闭 Product 永远选"不保存"，源模型分毫不动
```

## 4. 用到的能力

- Claude Code Skill（LLM 编排：收集输入、控制阶段推进、静态审查脚本、读报告、生成结论）；
- CATIA V5 精确几何 API（Assembly Design 装配树/实例位姿/Update、DMU Space Analysis 的 Clash.Compute）；
- CATScript 宏生成（AI 生成、静态门禁审查、人本机执行）；
- 可选终态规则（zero-conflict / allowed-contact / allowed-overlap）声明设计意图；
- 报告 + CSV 证据留档 + 干涉位置回放宏。

**分工原则（作者核心论点）**：几何事实的唯一权威是 CATIA——装配树、位姿、Update 成败、Clash 冲突数和类型值全部以精确 API 为准；AI 负责可审计的实验编排，绝不用截图目测、不用两端坐标差猜路径。

> "端点坐标差不是物理装配路径"——这句话贴在工具设计文档最前面。

## 5. 效果与证据

- 把"脑补能不能装进去"变成每毫米级采样、可复现干涉位置、明确报告的工程结论，"可以追溯、敢于签字"；
- 全程不保存不覆盖源模型，分析在临时会话完成，宏结束用起始位姿恢复（恢复 RMS ≤ 0.0001 才算结论有效）。

**注意：全文没有任何量化提效数字**——没有分钟数、没有百分比、没有 ROI。作者明确说最大收获"反而不是 AI 帮我省了多少代码，而是它逼着我把一个模糊的工程直觉，一步步逼成了一套可验证、可复现、边界清晰的方法"。

## 6. 可信度判断

**判断：七案例中工程严谨度最高的一篇，一手实践，可信度最高。**

可信的部分：

- 技术深度真实且可复核：五步采样协议、RMS 容差、12 元素位姿留档、Type/Value 冲突签名——这些细节只有真正实现过才写得出来；
- **主动交代失败成本**：先想做通用运动规划，"几轮折腾烧了上千块 Token"后收窄——踩坑史有具体代价；
- 边界诚实到极致：明确列出五条"不做"、UNVERIFIED 语义澄清（"不代表没问题"）、以及"即使通过了也不能回答卡扣会不会断/压装力/人机工程"的第六节——用一整节讲"它不能回答什么"；
- 无任何 ROI 宣传，结论形态是工程性的（可签字的校核结论）而非管理性的（提效百分比）。

需要保留的部分：

- 单人单场景（灯具工程师），工具对其他零部件类型的适配性未验证；
- 采样粒度固定 1mm——对小间隙特征（密封件唇边、卡扣倒扣）是否够用未讨论；
- 依赖用户遵守"不保存"纪律和正确准备两份模型，误用路径未完全工程化封堵。

结论：**真实、严谨、方法论文本可直接复用；效果未量化但这件事本身（可签字的工程结论）就是效果。**

## 7. 对我们当前项目的启发

### 7.1 "让 X 做判断，让 AI 做编排"——工具连接层的根本原则（对应 04-06 L2）

这是七个案例里对 04-06 L2（工具连接层）最清晰的表述，应该原文进 insights：

```text
几何事实的唯一权威是 CATIA（精确 API）
AI 负责：收集输入、控制阶段推进、静态审查脚本、读报告、生成结论
AI 绝不：截图目测、用两端坐标差猜路径
```

推广成通则：**凡是有确定性计算引擎的领域（CAD/CAE/EDA/测试机台/SPC 统计），LLM 只做编排和表达，判定必须回到引擎的精确 API**。这与案例五（客户端驱动本机软件）、案例六（确定性流程零 Token）共同构成 L2 层的三条设计准则。

### 7.2 "命令—更新—读回—审计"：Agent 驱动工具的验证协议（对应 04-05 TaskTrace）

五步采样协议的精髓：**把"我以为零件在哪"和"零件实际在哪"分开**——命令 CATIA 后必须读回真实位姿核对，偏差超容差即降级为未验证。

这对所有 Agent 工具调用都是通用纪律：AI 下发命令 ≠ 命令被执行 ≠ 执行成功。每个工具调用都应"命令 → 确认状态 → 读回结果 → 与预期比对 → 不符即降级"。当前多数 Agent 实现只做"调用了就算做了"，这正是可靠性差距的来源。写 04-05 的 TaskTrace schema 时，`tool_calls` 字段应包含"命令值 vs 读回值"的审计对。

### 7.3 UNVERIFIED 状态：七案例里第四次出现同一模式（收敛完成）

```text
LI-PAS：        四档结论，含"无法确认"——无法覆盖则标注，不补全
EHS：           两轮定稿，假设与现场不符必须人工标注
流程库：        红线/优化/留观三档分级 + 联合评审
本案例：        UNVERIFIED ≠ 失败 ≠ 没问题，是"证据不足"；异常一律降级，绝不伪装通过
```

四案例四领域，同一铁律：**工程工具最怕的不是失败，是把异常伪装成通过。**"让 AI 心虚的时候就明说心虚"——这应作为 04-05 任务结论状态机的设计规范：结论至少四态（通过/失败/需人裁决/证据不足），异常路径全部显式降级。

### 7.4 需求收敛："想清楚不做什么"比"想做什么"更重要（对应 04-06 纵向资产边界）

作者从"任意三维装配路径自动搜索"（路径空间、旋转参数化、采样稀疏、局部最优、不可复现，**搜不到也证明不了不存在**）收窄到"固定方向直线推进"，换来四个性质：

1. 结论对象明确（绑定坐标系和正轴）；
2. 采样可证明（行程与采样点数是确定关系）；
3. 姿态可审计（每点命令/实际位姿可比对）;
4. 失败可复现（首次碰撞位姿可重放）。

**这是"负结论必须有意义"的教科书案例**：通用运动规划搜不到路径 ≠ 路径不存在，负结论无工程价值；收窄后的"沿 +X 不行"是可签字的确定性负结论。对应 12 系列的质量检测同理——宁可"范围内高置信的负结论"，不要"全范围内无法解释的通过"。

### 7.5 给 AI 生成的代码上门禁（对应 04-06 L5 治理层）

CATScript/VBScript 的坑（标识符全局、不区分大小写、GoTo、非字面量数组边界）AI 会反复翻车，作者的解法是**静态门禁**：宏在交付前必须过规则检查（数组边界字面量化、名字小写去重、只用多行 If、禁 GoTo、位姿回放只用 Position.SetComponents）。

> "跟 AI 协作，验收标准要写得像给实习工程师交代任务一样具体。"

这正是 L5（治理/审计/评测）在工具生成场景的最小实现：**目标语言的危险特性清单 + 静态规则检查 = AI 代码的门禁**。任何"AI 生成 → 人在真实环境执行"的流程都应有这一层。

### 7.6 工程数据安全底线

全程不保存、不覆盖源模型，分析在临时会话，宏结束恢复起始位姿且恢复精度也纳入结论有效性判定。**自动化不碰工程数据安全底线**——这对我们要做的任何写入型 Agent（12 系列的 lot release、PCN）是直接适用的红线设计。

### 7.7 最值得抄的设计

1. **五步采样协议**（命令—更新—读回—审计—判定）+ 容差钉死——见 7.2，Agent 工具调用的通用验证协议；
2. **四态结论 + UNVERIFIED 语义**——见 7.3；
3. **显式不做清单**放在工具定义最前面——边界诚实是可信度的第一来源；
4. **失败现场可重放**（首次干涉查看宏 + 12 元素位姿 + CSV 留档）——把抽象失败结论变成能亲眼检查的事实，证据链思维的最小实现；
5. **AI 生成宏 + 人本机执行 + 报告回读**：LLM 不直接操作专业软件（不可控），生成可静态审查的脚本交给人执行——比案例五的客户端自动驱动更保守、更适合高风险环境；
6. **可选终态规则声明设计意图**（zero-conflict/allowed-contact/allowed-overlap）：把"设计上故意的接触"参数化，避免机器误判人才能裁决的事。

### 7.8 作者的方法论结语（值得原文记录）

> 用 AI 做这个工具最大的收获，反而不是"AI 帮我省了多少代码"，而是它逼着我把一个模糊的工程直觉，一步步逼成了一套可验证、可复现、边界清晰的方法。这大概才是工程师用 AI 最该追求的东西。

## 8. 后续想实测 / 追问的问题

- Skill 的使用频率和覆盖范围：目前是个人工具还是已团队复用，校核过多少零件；
- 1mm 采样粒度的适用边界：小间隙特征（密封唇边、卡扣倒扣）要不要亚毫米级采样，性能代价多大；
- 每毫米级 Clash 的耗时（77 个姿态的墙钟时间），长行程零件的等待体验；
- 静态门禁具体实现（正则规则还是 AST 检查），AI 生成宏的一次通过率；
- 多移动件场景（子装配整体安装）是否在路线图上，如何保持"恰好一个移动件"约束的严谨性；
- 这个 Skill 的结构（输入收集/阶段推进/脚本生成/报告回读）对其他 CAD 工具（NX、Creo）的平移成本——如果 CATIA 版验证有效，EDM/EDA 工具链的同构 Skill 值得直接立项；
- 烧掉的上千块 Token 都花在了哪些失败的尝试上——失败路径的分布比成功路径更有信息量。
