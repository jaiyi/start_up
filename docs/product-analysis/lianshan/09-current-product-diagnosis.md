# 09 · 当前产品体系诊断：工业 AI / Agent 平台的技术、商业化与落地风险

> 分析日期：2026-09-14  
> 分析对象：`docs/product-analysis/01~08` 当前产品分析，以及 `docs/insights/01~05` 的行业判断框架  
> 视角：智能制造转型专家 / 工业 AI 产品顾问  
> 结论口径：本文区分「已有工程证据」「设计/声明」「待生产验证」「待商业验证」，避免把 demo、工程骨架、生产闭环和商业结果混为一谈。

---

## 0. 总体判断

当前连山产品不应被理解为单一应用，而是一套正在成型的 **工业 AI 私有化平台 + Agent 运行体系 + 制造质量/工艺场景样板**。

一句话判断：

> 当前产品的底座工程已经明显超过普通工业 AI demo，尤其是 PG-first、Bundle-first、runtime feedback、HITL、EVI 这些设计具备较强判断力；但商业护城河不在这些横向工程，而在能否把 SPC、FTA、参数推荐等真实制造场景中的纵向知识、人工反馈、生产结果和财务价值持续沉淀下来。

更具体地说：

- **技术上**：已经形成工业 AI Agent 平台雏形，不是简单套壳大模型。
- **产品上**：已经有质量与工艺改善相关的纵向样板，但主线需要进一步收敛。
- **商业上**：EVI 和结果归因方向正确，但还缺客户认可的收益、续费、规模化复制证据。
- **落地上**：最大的风险不是单点技术做不出来，而是体系太重、链路太长、现场交付太复杂、组织承接能力不足。

因此，最优路线不是继续扩大“大平台叙事”，而是优先用一个高频场景——建议是 **SPC 质量异常闭环**——跑出生产证据和商业证据，再让平台能力自然长出来。

## 1. 诊断框架：从 AI 能力诊断转向价值闭环诊断

`docs/insights/01~05` 可以抽象为五张诊断表：

| Insight | 核心问题 | 对当前产品的诊断尺子 |
|---|---|---|
| 01 · 熵增阶段与乱象 | 当前不是模型瓶颈，而是落地落差 | 是否从 demo 进入生产流程，是否有反馈闭环和结果责任 |
| 02 · 横纵分层与迁移形态 | 横向会被抹平，纵向才是护城河 | 换掉横向框架后，哪些资产还留得下来 |
| 03 · 几波力量与 2030 赢家 | 2030 是分层 stack，不是单一赢家 | 当前更像平台、FDE 服务商，还是垂直 AI-native 运营商 |
| 04 · 付费模式与价值归因 | 能卖多贵取决于能归因多实 | 是否有反事实基线、物理指标、成本动因和客户确认 |
| 05 · 企业侧转型 | 企业真正要沉淀隐性经验和经营账 | 是否有人机治理、反馈贡献、IT/业务 P&L 对齐与组织收编机制 |

这个框架提醒我们：

> 诊断产品不应只评估“有没有 AI/Agent”，而应评估：是否沉淀纵向资产、是否能归因价值、是否能组织化运营、是否能形成复利。

## 2. 当前产品完整结构：平台层强，应用层在找突破口

当前产品可分为两大部分。

### 2.1 平台 / 底座层

| 层级 | 产品 / 仓库 | 当前价值 | 初步判断 |
|---|---|---|---|
| 私有化部署底座 | `lisen-infra` | Ansible、Dokku、PG、RustFS、节点管理、应用部署 | 工程证据强，偏横向底座 |
| 冷路径计算 / 编译 | `lads` | dsproject、Bundle、算法 SDK、领域算法、EVI、BPMN / OWL | 横向框架强，领域算法和 EVI 是纵向资产入口 |
| 热路径运行时 | `dsruntime` | runtime events、HITL、feedback、LangGraph、EVI、控制面 | 当前闭环核心，工程证据最强 |
| 数字员工工作站 | `workstation-iclaw` | Agent 工作站、工单评审、SSO、discovery、employee sync | 交互入口有价值，但数字员工产品落地需继续验证 |
| 边缘推理节点 | `edge-inference` | AOI 推理、SQLite bus、模型热加载、shadow / production 结果 | 工程脚手架清晰，但纵向资产较薄 |

这部分说明连山不是只在做单点 demo，而是在做从部署、编译、运行、交互到反馈的完整工程链路。

### 2.2 应用 / 场景层

| 场景 | 产品价值 | 当前定位 |
|---|---|---|
| `demos-fta` | 前灯匹配不良 FTA 诊断 | 专家故障树、测试项、措施方案和工单诊断路径资产化 |
| `demos-spc` | SPC 智能过程管控 | 质量异常从采集、判异、推送、诊断到 EVI 的闭环样板 |
| `demos-param-opt` | 参数推荐 / 调优 | 围绕 NG closure 的工艺参数推荐、采纳、反馈和治理 |

这三类应用共同指向一条更清晰的产品主线：

> **面向制造质量与工艺改善的 AI 闭环系统。**

这比泛泛讲“工业 AI Agent 平台”更容易让客户理解，也更容易与业务指标绑定。

## 3. 主要优点

### 3.1 没有把 Agent 理解成聊天机器人

当前系统不是“知识库问答 + 大模型界面”，而是在尝试打通：

```text
数据接入
→ 事件触发
→ 算法 / Agent 处理
→ 人工确认
→ 工单 / 反馈回写
→ 指标评估
→ 知识和模型迭代
```

这比普通 Agent demo 更接近工业现场真实需求。

尤其是：

- FTA 是工单触发，不是闲聊触发；
- SPC 是质量异常触发，不是用户随便问；
- 参数推荐是 NG 反馈触发，不是凭空生成建议；
- runtime 有 feedback、HITL、EVI、事件留痕。

### 3.2 PG-first 对工业私有化是务实选择

工业现场常见问题是弱网络、弱运维、强私有化、少中间件能力。PG-first 把消息、向量、图谱、配置、事件、反馈等尽量收进 PostgreSQL，对单节点工作站和边缘盒子是务实方案。

优点：

- 部署轻；
- 一致性好；
- 运维门槛相对低；
- 适合弱网络现场；
- 容易备份、审计和私有化交付。

风险在于：多站点、高并发、多模型、多边缘设备时的容量边界仍需压测和生产数据验证。

### 3.3 Bundle-first 让工业应用交付有纪律

`lads` 编译 Bundle，`dsruntime` 消费 Bundle，这个冷热路径边界很重要。

它避免：

- 训练逻辑混进运行时；
- 现场临时改脚本导致不可复现；
- 应用版本无法追踪；
- 反馈无法对应模型、参数和 Bundle 版本；
- 工业客户无法审计变更。

对制造客户而言，可追踪、可回滚、可审计往往比功能炫更重要。

### 3.4 HITL 与 feedback 设计符合工业现实

制造业不能一开始就进入 Human-out-of-the-loop。当前系统大量保留：

- 人工确认；
- review；
- correction；
- alternative；
- approval / deny；
- feedback projector；
- runtime feedback export；
- HITL checkpoint / resume。

这是现实路径。

工业 AI 早期更应强调：

> AI 先做建议，人做审核；系统沉淀审核轨迹；再逐步把低风险动作自动化。

### 3.5 EVI 方向非常关键

很多工业 AI 产品死在“客户觉得有用，但没人说得清值多少钱”。连山把 EVI 放进底层能力，是商业化上的重要判断。

EVI 的正确方向是：

```text
反事实基线
× 可核实物理指标
× 成本动因模型
→ 客户认可的经营价值
```

当前已有 EVI 机制、record、business objective、attribution rule 等设计，这是亮点。但它还需要从工程机制变成客户认可的经营证据。

## 4. 核心风险

### 4.1 横向工程过重，容易稀释护城河

当前横向能力很多：

- Ansible / Dokku 部署；
- workflow 编排；
- Agent 工作站；
- 消息队列封装；
- 模型加载服务；
- schema-driven UI；
- Bundle 生命周期；
- runtime control plane。

这些都重要，但长期会被云厂商、开源框架、大模型平台、工业软件厂商不断压价或替代。

真正的护城河不是“我们有一个 runtime”，而是：

- 工艺规则；
- 真实设备 / 产线 / 工位数据；
- 人工修正；
- 质量异常案例；
- 故障树；
- 参数边界；
- 推荐采纳与拒绝记录；
- EVI 兑现数据。

一句话：

> 横向是杠杆，纵向才是资产。

### 4.2 Demo 证据与生产证据之间仍有距离

当前产品分析中有大量工程证据：

- 文件存在；
- schema 存在；
- worker 存在；
- model artifact 存在；
- workflow 存在；
- capability 存在；
- schedule 存在。

但商业化需要另一类证据：

- 某客户真实上线；
- 连续运行 30 / 60 / 90 天；
- 覆盖多少设备 / 产线 / 工单；
- 触发多少次告警；
- 误报率多少；
- 平均响应时间下降多少；
- NG closure rate 提升多少；
- Cpk 改善多少；
- 返工 / 报废 / 客诉减少多少；
- 客户质量负责人和财务是否认可。

当前更强的是工程证据，不是经营结果证据。

### 4.3 安全债会影响大客户销售

`lisen-infra` 分析中已经指出：

- inventory 明文密码；
- 默认密码；
- auth token 硬编码；
- secret 管理成熟度不足。

大型制造客户尤其关心：

- 私有化部署安全；
- 凭据管理；
- 权限隔离；
- 审计；
- 数据出域；
- 生产网隔离；
- 供应链安全。

如果这块不治理，技术再强也可能卡在 IT / 安全部门。

### 4.4 交付复杂度可能拖垮毛利

当前部署和运行链路包含：

- Ansible；
- Dokku；
- dokku-admin；
- PG 扩展；
- RustFS；
- PGMQ；
- AGE；
- pgvector；
- 私有 PyPI；
- OSS / ACR；
- 多 submodule；
- 多 worker；
- 多 Bundle；
- 多 schema。

这意味着现场交付很复杂。

风险是：

- 每个客户环境不同；
- 每次部署都要专家介入；
- 现场问题难定位；
- 版本组合复杂；
- 平台维护成本高；
- 毛利被交付吞噬。

如果无法把交付过程标准化，产品会滑向重咨询。

### 4.5 数字员工层有“壳强于芯”的风险

`workstation-iclaw` 有工作站、SSO、discovery、工单、employee sync，这些有价值。但数字员工商业价值不在 UI，而在：

- 能拿到什么数据；
- 能调用什么工具；
- 能做什么诊断；
- 能否被人信任；
- 能否沉淀反馈；
- 能否减少业务损失。

如果数字员工只是聊天壳，会被 Dify、Coze、飞书、钉钉、企业微信智能体等通用平台替代。

所以数字员工必须绑定具体闭环：

- SPC 质量诊断员工；
- FTA 故障诊断员工；
- 参数推荐助手；
- 点焊追溯员工。

### 4.6 边缘推理能力需要谨慎包装

`edge-inference` 工程上有价值，但当前更像 AOI 推理节点 / 推理结果生产者：

- CPU 推理证据明确；
- GPU / Jetson 仍待验证；
- 不负责相机采集；
- 不负责执行器；
- 不做 ground truth；
- 不做误检 / 漏检闭环；
- 不做标定和漂移。

因此对外不应过度宣称“完整边缘智能闭环”。完整闭环还需要 collector、runtime、人审、反馈和再训练共同完成。

## 5. 三个应用场景的优先级判断

### 5.1 第一优先级：SPC 质量异常闭环

SPC 是当前最适合商业化突破的场景。

原因：

- 高频；
- 数据结构相对清晰；
- 客户痛点明确；
- 质量负责人听得懂；
- 结果可度量；
- 可从轻闭环做起；
- 容易接入 EVI。

建议卖点不是“SPC 控制图”，而是：

> 质量异常闭环系统。

最短闭环：

```text
真实测量数据
→ SPC 判异
→ 飞书 / 企业微信卡片
→ 一线确认 / 忽略
→ 误报治理
→ 工单闭环
→ 月度 EVI
```

### 5.2 第二优先级：参数推荐 / 参数治理

参数推荐天花板最高，但风险最大。

短期不要讲：

- 自动调参；
- 自动下发；
- 自动优化产线。

更适合讲：

> 工艺工程师辅助推荐 + 参数变更治理 + NG 复盘闭环。

最短闭环：

```text
NG 事件
→ 推荐参数
→ 工程师采纳 / 拒绝
→ 结果跟踪
→ 推荐效果统计
→ 模型 / 规则迭代
```

### 5.3 第三优先级：FTA 专家知识资产化

FTA 很适合做专家经验沉淀，但不一定是最高频场景。

建议定位：

> 把专家故障树、测试项、措施方案、工单路径资产化。

最短闭环：

```text
真实工单
→ 故障树路径推荐
→ 工程师确认
→ 根因 / 措施回写
→ 故障树修订
```

FTA 的价值在方法论，不在一棵前灯树。

## 6. 商业化诊断

### 6.1 当前不宜过度销售“大平台”

客户不会因为 stack 完整而付钱，客户会为明确痛点付钱。

因此对外叙事建议从：

> 工业 AI Agent 平台

收敛为：

> **帮助制造企业建立质量与工艺改善的 AI 闭环：发现异常、诊断原因、推荐措施、跟踪结果、量化收益。**

底层 LADS / runtime / iclaw / infra 可以作为交付能力和可信基础，但不一定是早期主卖点。

### 6.2 付费模式应分阶段

不建议一开始就大规模承诺 gainsharing。建议分阶段：

| 阶段 | 付费方式 | 核心目标 |
|---|---|---|
| 0. 数据与流程诊断 | 固定诊断费 | 判断数据成熟度和场景可行性 |
| 1. MVP | 项目实施费 + 基础订阅 | 跑通最短闭环 |
| 2. 稳定运行 | 年费 / 产线数 / 场景数 | 形成生产证据 |
| 3. 结果验证 | KPI bonus | 对可归因子集计价 |
| 4. 扩展复制 | 多工厂复制费 + 运维订阅 | 平台化复用 |
| 5. 成熟阶段 | shared savings / gainsharing | 只在财务认可时采用 |

### 6.3 EVI 应做成分级产品

建议按可信度分级：

| 等级 | 定义 | 商业用途 |
|---|---|---|
| EVI-L0 | 只有 demo 指标 | 内部演示 |
| EVI-L1 | 有事件、建议、反馈留痕 | 项目验收 |
| EVI-L2 | 有前后对照和人工确认 | 年费续约 |
| EVI-L3 | 有反事实基线和成本动因 | KPI 付费 |
| EVI-L4 | 财务 / 审计认可 | gainsharing |

当前大概率处在 L1~L2，目标应是先稳定做到 L2，再选一个窄场景冲 L3。

## 7. 落地诊断

### 7.1 每个场景都需要最短闭环

不要一开始追求完整平台闭环，而要先跑通最短闭环。

| 场景 | 最短闭环 |
|---|---|
| SPC | 真实数据 → 判异 → 推送 → 人工确认 → 反馈统计 |
| FTA | 真实工单 → 故障树路径推荐 → 工程师确认 → 根因 / 措施回写 |
| 参数推荐 | NG 事件 → 推荐参数 → 工程师采纳 / 拒绝 → 结果回写 |

只有最短闭环稳定后，才逐步叠加数字员工、EVI、自动优化、跨厂复制。

### 7.2 产品必须包含组织运营模板

工业 AI 落地不是只交付软件，还要改变工作方式。

客户需要明确：

- 谁确认告警；
- 谁关闭工单；
- 谁审核 AI 建议；
- 谁维护规则；
- 谁复盘误报；
- 谁批准参数变更；
- 谁每月看 EVI；
- 谁为收益签字。

如果这些没有定义，系统会变成：

- 看板没人看；
- 卡片没人点；
- 反馈没人填；
- 建议没人采纳；
- 工单没人关闭；
- EVI 没人认。

### 7.3 人机权限矩阵必须产品化

建议形成标准矩阵：

| 动作 | AI 权限 | 人的角色 |
|---|---|---|
| 数据读取 / 异常摘要 | 可自主 | 监督 |
| 生成诊断假设 | 可自主，但必须带证据 | 审核 |
| 推荐措施 | 可自主生成 | 确认 |
| 参数建议 | 可生成 | 工艺工程师审批 |
| 参数下发 | 默认不可自主 | 负责人授权 |
| 工单关闭 | 低风险可半自动 | 质量负责人确认 |
| 价值归因 | AI 计算 | 业务 / 财务确认 |

这张表不仅是安全治理，也是销售资产。

## 8. 需要补齐的三类证据

### 8.1 生产运行证据

每个场景都需要回答：

- 连续运行了多久？
- 处理了多少事件？
- 覆盖多少设备 / 产线？
- 平均延迟多少？
- 故障率多少？
- worker / queue / runtime 是否稳定？
- 数据同步成功率多少？

### 8.2 业务效果证据

每个场景都需要回答：

- 告警准确率多少？
- 误报率下降多少？
- 闭环时间减少多少？
- NG closure rate 提升多少？
- 工单定位时间减少多少？
- 参数建议采纳率多少？
- 采纳后效果如何？

### 8.3 财务归因证据

最终要回答：

- 减少了多少报废？
- 减少了多少返工？
- 减少了多少停机？
- 降低了多少客诉？
- 节省了多少人工？
- 这些金额客户财务是否认可？

这决定能否从项目费走向 KPI / outcome / gainsharing。

---

## 9. 建议的下一步路线

### 9.1 对外叙事收敛

不建议主打：

> 工业 AI Agent 平台。

建议主打：

> **制造质量与工艺改善的 AI 闭环系统。**

客户更容易理解，也更容易与业务指标绑定。

### 9.2 内部产品路线收敛

平台层继续做，但必须服务一个主战场：

> SPC / 质量异常闭环。

用这个主战场牵引：

- runtime；
- feedback；
- iWeb；
- EVI；
- digital employee；
- data integration；
- edge inference。

不要让平台能力脱离场景自我膨胀。

### 9.3 建立三列表

每个模块都要标注：

| 能力 | 工程证据 | 生产证据 | 商业证据 |
|---|---|---|---|
| SPC 判异 | 有代码 / 表 / worker | 连续运行 X 天 | 异常闭环时间下降 Y% |
| 参数推荐 | 有模型 / worker | 采纳 X 次 | NG closure 提升 Y% |
| FTA 诊断 | 有故障树 / 工单桥 | 诊断 X 单 | 定位时间下降 Y% |
| EVI | 有表 / 算法 | 客户确认 X 次 | 财务认可金额 Y |

这张表比平台介绍更重要。

### 9.4 安全债优先治理

特别是：

- 明文密码；
- 默认密码；
- auth token；
- secret 管理；
- 部署日志泄露；
- 私有 PyPI 凭据；
- runtime token；
- 客户数据出域；
- RBAC；
- 审计日志。

只要目标是大客户私有化，安全就是销售前置条件，不是后置优化项。

## 10. 最终结论

当前产品的最大价值在于：

> 它已经开始把工业 AI 从“模型能力”推进到“数据—流程—反馈—价值归因”的系统工程。

当前产品的最大风险在于：

> 平台和技术体系已经比较重，但纵向场景的真实生产闭环、财务级价值归因、客户组织承接能力还没有被充分证明。

最优路线是：

1. 不继续扩大平台叙事；
2. 用 SPC / 质量异常闭环打穿一个高频场景；
3. 把 FTA 作为专家知识资产化模块；
4. 把参数推荐作为工艺改善与参数治理模块；
5. 用 EVI 分级逐步建立商业化证据；
6. 最终沉淀成可复利的工业 AI 运营体系。

一句话收束：

> 连山现在最该证明的不是“我们有一套工业 AI Agent 平台”，而是“我们能在真实产线里，稳定发现问题、推动人处理问题、记录结果、沉淀知识，并让客户相信这件事带来了经营收益”。
