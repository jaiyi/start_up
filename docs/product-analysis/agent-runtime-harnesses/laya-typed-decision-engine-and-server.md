# Laya 类型化决策引擎与 Laya Server 调研

## 1. 调研对象与资料来源

- 调研对象：`NandhaKishorM/laya`（GitHub 约 31.7k stars，Apache-2.0，Python，社区活跃度高）及其生态：`laya[serve]`、`laya[mcp]`、`laya-mlx`、`laya-coreml`、`receptron/laya`、`arbiter` 等。
- 资料来源：GitHub 仓库 README 与官方文档（2026 年版本），未做本地部署实测。
- 调研日期：2026-09-29。

---

## 2. 一句话定位

Laya 是一个**非自回归（non-autoregressive）的 System 1 决策引擎**：把 LLM Agent 里"该走哪条分支 / 该调哪个工具 / 风险高不高"这类高频小决策，从生成式模型换成单次前向传播的类型化输出（typed decisions），做到毫秒级、可解析、无幻觉。

```text
LLM 负责理解和生成（System 2），laya 负责高频确定性判定（System 1）。
```

---

## 3. 产品背景

Agent 工程中最普遍的一个浪费是：大量调用 LLM 只是为了得到一个**小而确定的答案**——

```text
该路由到哪个 sub-agent？工具参数选哪组？这条输入要不要人工审核？
```

用自回归 LLM 回答这些问题有三个代价：延迟高（秒级）、成本高（token 计费）、输出不可解析（需要约束解码或重试）。laya 的思路是把这类决策从"文本生成"改造成"结构化分类 / 打分 / 数值输出"，用 encoder 模型一次前向解决。

---

## 4. 核心能力拆解

### 4.1 类型化决策（typed decisions）

laya 不输出文本，而输出三种类型化结果：

```text
choice：从候选集合中选一个（路由、分类、工具选择）
score ：给输入打分（风险分、置信度、优先级）
noul  ：数值输出（回归类任务）
```

因为输出本身是结构化的，**不存在幻觉问题，也不需要输出解析器**。这是它与"用小 LLM 做路由"最本质的差别。

### 4.2 性能形态

- 单次前向约 33ms；T4 GPU 上批量推理约 7.2ms/question；
- Apple Silicon 上有 `laya-mlx`（约 6.8k stars）实现，M3 Max 上 7-14ms，可完全离线；
- 还有 `laya-coreml`（iOS/macOS 原生）和 `receptron/laya`（Node.js + ONNX，浏览器端可跑）。

性能结论：适合放在**每个 Agent 请求都要过一次**的位置，这是 LLM 路由做不到的。

### 4.3 训练方法：RLCD

laya 用 **RLCD（Reinforcement Learning with Contextual Distillation，严格真评分规则强化学习）** 训练：奖励信号来自确定性的规则评分而不是人类偏好打分，训练过程可复现。`laya-typed-decisions` 微调版在官方 benchmark 上把 typed decision 准确率从 base 的约 0.362 提到约 0.766。

### 4.4 模型矩阵与 Router

| 检查点 | 底座 | 参数量 / 上下文 | 定位 |
|---|---|---|---|
| `laya` | ModernBERT-large | 421M / 512 | 英文决策 |
| `laya-multilingual` | mmBERT | 322M / 1024-8192 | 100+ 语言，长上下文 |
| `laya-typed-decisions` | 微调版 | - | typed decision 专项 |

Router 支持多检查点注册和按任务分发。

### 4.5 laya server 与生态

- **`pip install laya[serve]`**：起一个 HTTP 决策服务，支持 `LAYA_EXTRA_MODELS` 注册自有微调检查点——即"决策即服务"的私有化部署形态；
- **`laya[mcp]`**：官方 MCP server，Claude / Cursor 等 Agent 可以直接把 laya 作为一个工具调用——"把高频决策外包给一个 33ms 的确定性引擎"；
- `laya-ts`（npm）、`arbiter`（GPU 服务化，面向 typed-decision 模型的推理服务）、`wdobry/laya-playground`（benchmark + agent skill 形态分发）、`ThinkFlowLab/system1-agents`（System 1/2 混合 Agent 框架）。

## 5. 与相邻产品的差异

| 相邻方案 | 差异 |
|---|---|
| 小 LLM 做路由（如 7B 分类） | 小 LLM 仍是自回归生成，需解析、有幻觉面、秒级延迟；laya 是类型化输出，ms 级 |
| 规则引擎（Drools 类） | 规则引擎要人写全量规则；laya 是数据驱动训练出的判定器，适合规则写不出来但样本存在的场景 |
| 传统 ML 分类器（sklearn） | sklearn 需要自己搞特征工程、部署、Schema；laya 是面向 Agent 场景的成品（MCP / HTTP / 多语言 / 长上下文） |
| LLM 的 structured output / function calling | 那是"让 LLM 努力听话"；laya 是"输出空间天生就是答案空间" |

它真正的位置是在 **Harness 的路由 / 判定层**，与 LLM 是分工而不是替代。

---

## 6. 优势

1. **成本结构颠覆**：高频决策从 token 计费变成一次前向，边际成本近零；
2. **延迟进入实时区间**：33ms 意味着可以放进每个请求的关键路径；
3. **无幻觉、免解析**：typed output 直接可用，消掉了 Agent 工程里一类顽固的脆弱性；
4. **生态位设计聪明**：不做成"又一个 Agent 框架"，而是做成被框架调用的原子能力，且 MCP / HTTP / npm / 浏览器全端覆盖；
5. **RLCD 训练范式可迁移**：用确定性评分规则而不是人类偏好，训练语料可以来自企业自己的历史决策日志。

---

## 7. 短板与未验证点

1. **能力边界**：只能做候选集合已知、可形式化为 choice/score/noul 的决策；开放性判断、多步推理仍然要 LLM——它不解决 System 2；
2. **候选集合依赖**：choice 类决策需要预先定义候选（路由目标、工具列表），候选集合本身漂移时要重训或fallback；
3. **准确率数字待复核**：0.766 vs 0.362 来自官方 benchmark，未见第三方复现，且不清楚在企业私有分布上的表现；
4. **训练数据从哪来**：企业要用起来需要积累"输入→正确决策"的标注数据，冷启动成本没有官方方案；
5. **治理面缺失**：没有看到决策的审计、版本、灰度、回滚机制——这正是我们要在平台侧补的；
6. 仓库 stars 增长快，但**生产级采用案例**未检索到，需验证成熟度。

## 8. 适用场景

- Agent 路由：多 sub-agent 分发、意图分类（每次请求都发生，LLM 路由太贵）；
- 工具选择与参数裁决：候选工具确定、按上下文选一个；
- 风险分级：输入要不要走人工审核（可以和 04-06 的"四态结论铁律"里的 UNVERIFIED 判定结合）；
- 内容 / 输出快速筛查：LLM 生成完，用 laya 做第一道廉价守门，再决定要不要贵模型复核；
- 端侧与离线场景：laya-mlx / coreml 让决策完全脱离云端。

## 9. 对我们当前项目的启发

**（1）它是 04-06 "规则编译器"的机器学习同位体。** 我们在 17 个案例里观察到"大白话规则 = 人肉规则编译器"：业务同学把业务规则写成自然语言让 LLM 执行。laya 提供了另一条路：当规则写不全但历史决策样本存在时，把判定蒸馏成一个毫秒级模型。两者是同一个判定层的两种供给方式——规则态和样本态——平台应该都留位置。

**（2）与 MCP 工具注册中心的呼应。** `laya[mcp]` 证明了"决策能力也可以是一个 MCP 工具"。我们的工具注册中心除了业务系统连接器，应该考虑注册这类"判定类原子能力"，让 Skill 编写者可以声明"这一步用 laya 判、不要用 LLM 判"。

**（3）成本遥测的新口径。** 04-06 的成本遥测模块应该区分"生成成本（token）"和"判定成本（前向次数）"。如果把高频判定从 LLM 迁到 laya，成本看板上应该能看到这一条节省曲线——这本身就是一个可量化的平台价值证明。

**（4）家庭营养师项目。** "这个菜谱适不适合某人"这类高频小判定，可以用类似思路做成本优化，但样本量太小（单一家庭），暂时不值得——记录在案，等数据积累后再评估。

---

## 10. 后续需要实测的问题

1. 用我们的真实路由场景（如飞书消息分流）构造评测集，测 laya vs 小 LLM 的准确率 / 延迟 / 成本三方对比；
2. `laya[mcp]` 接入 Claude 后的实际体验：候选集合变更时如何更新（重训 or 注册新检查点）；
3. `laya[serve]` 私有化部署的稳定性与并发能力，`LAYA_EXTRA_MODELS` 注册自有检查点的微调流程工作量；
4. 中文场景下 `laya-multilingual` 的判定质量（我们场景以中文为主）；
5. RLCD 用企业历史决策日志训练的完整链路成本：需要多少标注样本才能达到可用准确率。
