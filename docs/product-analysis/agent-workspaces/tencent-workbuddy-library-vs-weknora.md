# 01 · 腾讯 WorkBuddy 资料库功能调研：与 WeKnora 的差异、优劣势与启示

> 调研日期：2026-09-23  
> 调研对象：腾讯 WorkBuddy 资料库、WorkBuddy 官方产品页、WorkBuddy 官方文档、现有 WeKnora 家庭营养师落地经验  
> 结论口径：本文基于公开资料与当前项目实践判断。WorkBuddy 属于快速演进产品，具体功能边界需以后续实测为准。

---

## 0. 一句话结论

WorkBuddy 的“资料库”更像一个 **AI 原生协作工作区 + 产物沉淀层**，核心价值是让人和 Agent 在同一棵资料树里共同生产、修改、发布 MD / CSV / HTML / 办公文件；WeKnora 更像一个 **知识库检索与 Agent 问答平台**，核心价值是把已有文档抽取、索引、Wiki 化，并服务检索增强问答。

如果从“知识复利”视角看：

```text
WorkBuddy 资料库：更偏工作产物的持续生产、协作和发布。
WeKnora 知识库：更偏存量知识的结构化检索、Wiki 问答和 Agent 调用。
```

对我们的家庭营养师 / 企业 Agent 产品启示是：

1. **资料库不是传统网盘，也不只是 RAG 知识库**，而应成为“人 + Agent 共同维护的工作资产层”。
2. **文件、表格、页面、任务和 Agent 权限要打通**，否则知识只能被问答，不能被运营。
3. **动态状态仍不适合只放资料库或知识库**，库存、菜单、反馈这类状态仍应进入结构化数据库，再导出摘要给知识层。
4. **WorkBuddy 强在个人/团队办公闭环，WeKnora 强在可私有化知识检索与 Agent 问答底座**；两者不是同一类产品，但在“知识被 Agent 使用”这件事上会发生重叠。

## 1. WorkBuddy 资料库是什么

根据 WorkBuddy 官方文档，“资料库”的定位是：

> 从超级个体到超级团队，让产物沉淀、管理、流转协同。

官方描述里有几个关键点：

```text
资料库是人和 Agent 共同的产物存放地。
Agent 产出的文档可以自动归位。
团队资料集中在同一棵目录树。
任务可以随时把资料库中的内容读进来继续加工。
做好的页面可以变成别人也能打开的链接。
```

这说明它不是单纯的文件上传入口，而是把以下几层能力合在了一起：

| 层级 | WorkBuddy 资料库中的表现 | 产品含义 |
|---|---|---|
| 产物存储 | MD、CSV、HTML、PDF、Word、PPT、Excel 等进入资料库 | AI 产物不再散落在会话里 |
| 上下文复用 | 任务中可读取资料库内容继续加工 | 资料库成为 Agent 的工作上下文 |
| 协作空间 | 我的文档、团队空间、目录树、成员权限 | 从个人 AI 工具升级到团队工作区 |
| 编辑闭环 | MD 审阅、AI 修订、HTML 可视化编辑 | AI 不只是生成一次，而是参与迭代 |
| 轻量发布 | HTML 发布为在线链接，HTML + CSV 形成轻应用 | 从文档产物走向可交付页面或小应用 |

所以，WorkBuddy 资料库的真实定位可以概括为：

```text
AI workspace artifact layer
= 文件管理 + Agent 上下文 + 协作权限 + 轻量内容发布 + 简单数据驱动页面
```

## 2. 资料库的核心能力拆解

### 2.1 内容管理：人和 Agent 共用的资料树

官方文档将内容管理定义为：

> 团队中人和 Agent 的产物一起管理，共享上下文。

主要能力包括：

1. **个人文档与团队资料分区**
   - “我的文档”是个人空间，也是 Agent 产物默认落点。
   - “团队空间”用于项目背景、过程资料、关键结论等多人协作内容。
   - 团队空间支持类似文件夹的嵌套文档树。

2. **两种保存路径**
   - 在会话中让 Agent 保存 MD 文档或 HTML 网页。
   - 通过“分享 / 发布为网站”把产物发布并自动进入资料库。

3. **多格式资料统一管理**
   - AI 三件套：MD / CSV / HTML。
   - 办公与本地文件：PDF / Word / PPT / Excel。

这个设计和传统知识库的差异在于：它强调的是 **产物生命周期**，不是单纯“把文档丢进去问答”。

### 2.2 多人多 Agent 协作：权限即上下文边界

官方文档强调：

> 权限不只决定谁能看，也决定 Agent 能用什么。

关键设计：

1. **团队空间**
   - 可以为一个项目、一个小组或一条业务线新建空间。
   - 资料可通过新建文档/表格、上传本地文件、剪藏网页链接、让 Agent 直接生成进入空间等方式进入。

2. **成员权限**
   - 查看：浏览空间内容，不能修改。
   - 编辑：在空间内新建、修改和整理内容。
   - 管理：管理空间成员与权限。
   - 无权限：不可访问。

3. **Agent 按同一权限读取**
   - 把空间或文档带入任务后，Agent 只读取当前用户有权访问的内容。
   - 人看不到的内容，Agent 也读不到。

4. **审阅模式与 AI 修订**
   - MD 文档支持划词评论和 AI 修订。
   - 改动以修订建议形式呈现，接受后才生效。
   - 这比“AI 直接覆盖知识库文档”更适合团队协作和风险控制。

这一点对企业知识复利很重要：

```text
权限系统不只是安全功能，而是 Agent 上下文治理的一部分。
```

### 2.3 轻量发布：从资料库到可访问页面

官方文档显示，资料库支持把本地 HTML 产物发布为在线链接：

- 本地 HTML 页面可一键上传为在线链接。
- 发布链接使用 `workbuddy.link` 域名。
- 发布为网站是只读访问，邀请协作是参与编辑，两者区分。
- 发布内容会进入资料库，后续可继续修改。
- HTML 可引用 CSV 作为数据源，形成轻应用。

这里最值得注意的是：

```text
WorkBuddy 把 HTML + CSV 视为轻量应用形态。
```

这意味着它不是只做文档问答，而是在向“轻量业务应用生成与托管”延伸。对于非工程用户，这个能力非常有吸引力：过去需要数据库 + 前端 + 部署，现在可以用 HTML + CSV + 发布链接完成一个小型业务看板或运营页面。

### 2.4 数据库与数仓接入边界：表格已确认，系统数仓需验证

这部分需要特别谨慎区分“资料库里的表格数据源”和“企业级数据库 / 数仓连接”。

基于当前公开资料，可以把 WorkBuddy 的数据接入能力分成三层：

| 层级 | 公开资料确认度 | 说明 | 适合场景 |
|---|---:|---|---|
| CSV / Excel / 腾讯文档表格 | 已确认 | 资料库可管理 CSV、Excel 等文件；HTML 页面可引用 CSV；腾讯文档支持表格搜索、预览、引用、回写 | 轻量台账、运营表、页面数据源、一次性数据分析 |
| 外部服务 / API / 自定义连接器 / MCP | 已确认方向，具体系统需实现 | 连接器用于把 WorkBuddy 与外部服务对接，公开文档提到第三方 API、自定义连接器、MCP + CLI，以及“查询数据库 / 从外部数据源获取信息”这类场景 | 企业系统 API、内部服务、定制数据查询工具 |
| 企业数据库 / 数仓 / BI 系统内置直连 | 暂未看到明确公开证据 | 公开资料中没有看到资料库原生直连 Postgres、MySQL、ClickHouse、Doris、Hive、腾讯云数据库、腾讯云数仓或 BI 系统的明确能力清单 | 需要商务确认或实测，不应默认可用 |

因此，更准确的判断是：

```text
WorkBuddy 资料库确认支持“表格型数据源”和“通过连接器扩展外部数据访问”；
但公开资料尚不足以证明“资料库本身就是企业数仓 / 数据库连接层”。
```

换句话说，资料库里的 CSV / Excel / 腾讯文档表格可以承担轻量数据层，但不应直接等同于严肃业务数据库。对于系统数仓，更合理的架构是：

```text
业务库 / 数仓 / BI / 内部系统
→ API / 自定义连接器 / MCP 服务
→ WorkBuddy Agent 执行查询或分析
→ 资料库沉淀报告、页面、CSV 快照、HTML 看板
```

而不是：

```text
WorkBuddy 资料库 CSV / Excel
→ 直接作为企业核心业务状态或数仓 source of truth
```

对我们的判断影响很大：WorkBuddy 的资料库强在“数据产物沉淀和轻量数据协作”，不应被误读成“内置企业数据平台”。如果要做库存、订单、生产质量、工艺参数、客户主数据这类有事务、审计、权限和实时性要求的系统，仍需要独立数据库 / 数仓，并通过 API、MCP 或连接器受控接入。

## 3. WorkBuddy 整体产品定位

从官方产品页看，WorkBuddy 是腾讯出品的全场景 AI 办公工作台，强调：

1. 自然语言理解；
2. 自主规划执行；
3. 多模态任务处理；
4. 本地文件操作；
5. 领域专家；
6. 云端助理；
7. 多 Agent 协同；
8. 项目空间中的专家、Skill、连接器沉淀复用；
9. 腾讯文档、ima 知识库、微信 / 企业微信等腾讯生态连接。

因此，WorkBuddy 不是一个纯知识库产品，而是一个更接近：

```text
面向普通办公人群的 AI Agent 工作台
+ 团队协作空间
+ 办公产物生成和发布系统
+ 腾讯办公生态连接器
```

它的“资料库”是这个工作台里的协作与资产沉淀模块。

## 4. WeKnora 的定位回顾

结合我们当前家庭营养师项目中的使用经验，WeKnora 更适合被理解为：

```text
知识库 / Wiki / RAG / Agent 问答平台
```

它的核心价值在于：

1. **文档上传与知识库索引**
   - 将 Markdown、PDF、文档等内容作为知识源。
   - 通过切片、向量化、检索来支撑问答。

2. **Wiki 化知识管理**
   - 可以围绕知识库生成或维护 Wiki 页面。
   - 适合把复杂知识组织成可读页面。

3. **Agent 配置**
   - 可配置 Agent mode、Agent type、知识库绑定、工具权限、system prompt、memory 等。
   - 适合构建“家庭营养师 Agent”这类知识问答 + 工具调用入口。

4. **MCP 工具接入**
   - 可以把外部状态系统封装为工具，让 Agent 调用。
   - 对我们的家庭营养师项目来说，动态状态走独立 Postgres + MCP 是必要的。

WeKnora 的重要限制也已经在本项目里暴露出来：

```text
Agent 能修改 Wiki 页面，但不能稳定直接编辑知识库源文档。
源文档更新通常需要手动替换或重新上传。
知识库重新索引有延迟。
RAG 召回可能拿到旧版本状态。
```

所以我们已经确定了边界：

```text
稳定知识：Git Markdown + WeKnora 知识库
动态状态：独立 Postgres
状态读写：MCP 服务
对话入口：WeKnora Agent / 微信入口
```

## 5. WorkBuddy 资料库 vs WeKnora：核心差异

| 维度 | WorkBuddy 资料库 | WeKnora 知识库 / Wiki | 判断 |
|---|---|---|---|
| 产品定位 | AI 办公工作台中的资料与产物协作层 | 知识库检索、Wiki、Agent 问答平台 | WorkBuddy 更偏生产协作，WeKnora 更偏知识问答与检索 |
| 核心对象 | Agent 产物、MD、CSV、HTML、办公文件、团队空间 | 源文档、知识库、Wiki 页面、检索结果 | WorkBuddy 把“产物”作为一等公民 |
| 用户行为 | 让 Agent 写、改、保存、发布、协作 | 上传文档、生成 Wiki、问答、配置 Agent | WorkBuddy 更接近日常办公流 |
| 文件生命周期 | 会话产物可直接沉淀进资料库，后续继续加工 | 源文档一般需上传/替换，Wiki 可编辑但不等于源文档 | WorkBuddy 在“持续编辑产物”上更自然 |
| 协作模型 | 我的文档、团队空间、成员权限、评论、修订建议 | 知识库 / Wiki 管理为主，协作能力取决于平台配置 | WorkBuddy 更强调多人协同 |
| Agent 权限 | Agent 按当前用户权限读取空间/文档 | 可通过工具权限、知识库绑定、MCP 权限控制 | WorkBuddy 权限体验更产品化；WeKnora 更平台化 |
| 数据形态 | MD / CSV / HTML 可互相引用，HTML + CSV 可形成轻应用；通过连接器/API/MCP 可扩展外部数据访问，但资料库原生直连数仓未确认 | 文档切片、Wiki 页面、知识检索结果；可通过 MCP 接独立数据库 | WorkBuddy 更适合轻应用和数据产物沉淀；WeKnora 更适合 RAG + 外部受控工具 |
| 动态状态 | CSV / 在线表格可做轻量数据底座，但复杂事务能力有限；系统数仓更可能需要自定义连接器、API 或 MCP 间接接入 | 知识库不适合作为事务状态源，需通过 MCP 接业务数据库 | 二者都不应替代严肃业务数据库；差异在于 WorkBuddy 把表格协作做得更产品化，WeKnora 的受控 MCP 边界更清晰 |
| 发布能力 | HTML 可发布为在线链接 | 更偏知识页面和问答入口 | WorkBuddy 发布能力更强 |
| 私有化与可控性 | 企业版能力需具体确认，强依赖腾讯生态 | 已可自部署 WeKnora，本项目已部署 | WeKnora 对自托管更清晰 |
| 生态绑定 | 腾讯文档、ima、微信/企微、腾讯云生态；连接器支持外部服务、API、自定义 MCP，但数据库/数仓内置连接能力需实测 | 更独立，可接入自有 MCP / DB / 文档库 | WorkBuddy 生态整合强但平台绑定更重；WeKnora 工程边界更可控 |

## 6. WorkBuddy 的优势

### 6.1 更接近真实办公闭环

WorkBuddy 不是只回答问题，而是强调“交付可验收结果”：

```text
提出任务 → Agent 拆解 → 读取资料 → 生成文档/表格/网页 → 保存进资料库 → 协作审阅 → 发布链接
```

这条链路比传统知识库问答更贴近企业日常办公。

### 6.2 资料库是 Agent 原生工作空间

资料库不是旁路系统，而是 WorkBuddy 内的原生能力：

- Agent 可以把产物直接保存进去；
- Agent 可以在任务中读取资料库内容；
- 人和 Agent 在同一份资料上接力；
- 权限决定 Agent 可读范围。

这对“知识复利”很关键，因为复利不只是检索旧知识，还包括持续产出、修改、沉淀和复用。

### 6.3 MD / CSV / HTML 的组合很务实

WorkBuddy 把 MD、CSV、HTML 作为 AI 办公三件套：

```text
MD：承载文本知识和过程结论；
CSV：承载轻量结构化数据；
HTML：承载可视化页面和轻应用。
```

这套组合对非技术用户友好，也更容易从“写报告”过渡到“做一个小应用”。

### 6.4 协作与发布能力明显强于普通 RAG 知识库

WorkBuddy 资料库支持：

- 团队空间；
- 成员权限；
- 链接邀请；
- MD 评论与 AI 修订；
- HTML 多人协同编辑；
- HTML 发布为在线链接。

这使它更像 Notion / 飞书文档 / 腾讯文档 与 Agent 的结合，而不只是一个检索后台。

### 6.5 腾讯生态入口强

官方资料提到 WorkBuddy 与腾讯办公生态连接，包括腾讯文档、ima 知识库、微信/企业微信等入口。对于已经在腾讯生态里的企业，推广成本和用户触达会更低。

## 7. WorkBuddy 的潜在短板

### 7.1 资料库不等于严肃业务数据库

虽然 WorkBuddy 资料库支持 CSV，并且 HTML + CSV 可以搭建轻应用，但 CSV 更适合轻量数据，不适合承担复杂业务状态。公开文档里虽然出现了连接器、第三方 API、MCP 和“查询数据库 / 从外部数据源获取信息”等方向，但没有看到资料库原生直连企业数仓或具体数据库产品的明确能力清单。

例如我们的家庭营养师场景：

```text
库存扣减
采购记录
计划消耗
实际执行
幂等写入
审计日志
多入口并发
权限隔离
```

这些不应该只依赖 CSV 或资料库文件，而应该进入 Postgres 这类事务数据库。

### 7.2 企业数据接入能力需要商务确认或实测

WorkBuddy 的连接器文档确认了外部服务对接、自定义连接器、MCP + CLI 和 API 调用方向，也提到“数据查询 / 查询数据库”这类场景。这说明 WorkBuddy 并不局限于资料库文件本身，理论上可以通过连接器访问外部系统。

但从公开资料看，仍有几个未确认点：

- 是否有开箱即用的 Postgres / MySQL / Oracle / SQL Server 连接器；
- 是否有 ClickHouse / Doris / Hive / MaxCompute / 腾讯云数仓等数仓连接器；
- 是否有 Tableau / Power BI / Superset / FineBI / Quick BI 等 BI 系统连接器；
- 是否支持行列级权限、查询审计、SQL 白名单、敏感字段脱敏；
- 是否支持把查询结果稳定写回资料库中的 CSV / 在线表格 / HTML 看板；
- 是否支持企业私有网络内的数据源访问。

所以，更稳妥的表述不是“WorkBuddy 资料库能挂数仓”，而是：

```text
WorkBuddy 确认支持表格型数据源和连接器扩展；
系统数据库 / 数仓接入需要通过连接器、API 或 MCP 验证具体可行性。
```

### 7.3 平台绑定更强

WorkBuddy 的资料库、发布、协作和腾讯生态连接都很强，但也意味着：

- 数据和工作流更依赖 WorkBuddy 平台；
- 是否能自托管、迁移、导出、接入自有数据库，需要看企业版具体能力；
- 如果要做深度行业系统，可能需要更多平台开放能力。

### 7.4 面向办公泛场景，行业知识工程能力需要验证

WorkBuddy 的定位是办公 Agent 工作台，适合报告、表格、PPT、资料整理、轻应用等任务。

但对于工业、医疗、营养这类领域，需要验证：

- 是否支持精细知识切片和引用溯源；
- 是否支持领域本体、结构化 schema、长期规则管理；
- 是否支持受控工具调用和审计；
- 是否支持私有化部署和企业级数据隔离；
- 是否支持高稳定性的生产状态读写。

### 7.5 “产物协作”强，不代表“知识正确性治理”强

资料库让产物更容易沉淀，但知识质量仍需要机制：

- 来源可信度；
- 版本管理；
- 事实冲突检测；
- 过期内容识别；
- 人工审核；
- 引用和证据链。

这些能力是否系统化，需要进一步实测。

---

## 8. WeKnora 的优势

### 8.1 更适合作为 RAG / Wiki / Agent 问答底座

WeKnora 的核心能力更集中在知识库、Wiki 和 Agent 问答上。对于我们这种已有大量 Markdown 知识资产的项目，它更直接：

```text
上传家庭画像、饮食规则、菜谱、Prompt、Skill 文档
→ 建立知识库索引
→ 配置家庭营养师 Agent
→ 通过 RAG / Wiki 查询回答
```

### 8.2 私有化和自部署路径更清晰

我们已经在腾讯云服务器上部署了 WeKnora，并能够控制：

- Docker Compose；
- 模型并发；
- 知识库上传；
- Agent 配置；
- MCP 外部工具连接。

这对隐私敏感场景更重要。家庭营养数据包含宝宝、老人、健康、饮食偏好等敏感信息，不适合轻易放到无法完全控制的平台里。

### 8.3 MCP 外接动态状态比较适合严肃业务系统

WeKnora 自身知识库不适合直接当库存数据库，但通过 MCP 连接独立 Postgres 后，可以形成更工程化的边界：

```text
WeKnora：检索 + 对话 + 推理入口
MCP：工具边界
Postgres：动态状态 source of truth
Git Markdown：稳定知识 source of truth
```

这比单纯让 Agent 编辑文件或 CSV 更适合需要审计、幂等和事务的系统。

### 8.4 更适合作为“垂直知识 Agent”入口

对于家庭营养师、工业质量诊断、企业知识助手这类场景，WeKnora 的优势是：

- 先把知识库建起来；
- 再用 Prompt 和工具权限约束 Agent；
- 最后接 MCP 做状态读写。

它更像“知识中枢 + Agent 入口”。

## 9. WeKnora 的短板

### 9.1 源文档编辑链路不够顺滑

本项目实践中已经遇到：

```text
Agent 可以修改 Wiki 页面，但不能直接稳定编辑知识库源文档。
源文档需要在知识库管理界面手动更新，或重新上传替换。
```

这导致它不太适合承担“持续共同编辑产物”的角色。

### 9.2 协作和产物发布能力弱于 WorkBuddy

WeKnora 更像知识问答平台，不像 WorkBuddy 那样强调：

- Agent 产物自动归档；
- 团队空间；
- 评论和 AI 修订；
- HTML 可视化编辑；
- 一键发布在线链接；
- HTML + CSV 轻应用。

如果目标是“让普通办公人员每天用 AI 交付文档、表格、页面”，WorkBuddy 的产品完成度更强。

### 9.3 动态状态不能直接托给知识库

WeKnora 知识库会涉及上传、抽取、索引和召回延迟，因此库存、采购、近期菜单、反馈这类状态不能只靠 Markdown 文件实时维护。这也是我们后来引入 Postgres + MCP 的原因。

### 9.4 对非技术用户的低门槛体验可能弱一些

从当前体验看，WeKnora 更偏平台配置：知识库、Agent 类型、工具权限、Wiki、MCP。普通用户要理解这些概念，门槛高于 WorkBuddy 的“资料库 + 助理 + 专家 + 项目空间”。

## 10. 场景适配判断

| 场景 | 更适合 WorkBuddy | 更适合 WeKnora | 原因 |
|---|---:|---:|---|
| 日常办公文档生成 | ✅ | ⚠️ | WorkBuddy 能直接生成、保存、修改、发布办公产物 |
| 表格分析与报告 | ✅ | ⚠️ | WorkBuddy 强调 Excel/CSV、图表、报告交付 |
| HTML 小页面 / 轻应用 | ✅ | ❌ | WorkBuddy 支持 HTML + CSV + 在线发布 |
| 团队协作文档空间 | ✅ | ⚠️ | WorkBuddy 团队空间、权限、评论、修订更产品化 |
| 已有知识库问答 | ⚠️ | ✅ | WeKnora 更偏 RAG / Wiki / 知识检索 |
| 私有化知识库平台 | 待确认 | ✅ | WeKnora 自部署路径更明确 |
| 垂直 Agent + MCP 状态工具 | ⚠️ | ✅ | WeKnora + MCP + Postgres 架构更清楚 |
| 高敏感数据 / 自控部署 | 待确认 | ✅ | WeKnora 当前更可控；WorkBuddy 需看企业版私有化能力 |
| 轻量知识复利 / 个人资料管理 | ✅ | ⚠️ | WorkBuddy 资料库更接近人机共同编辑工作台 |
| 复杂事务状态 | ❌ | ❌ | 两者都不应直接替代 Postgres 等业务数据库 |

## 11. 对家庭营养师项目的启示

### 11.1 当前选择 WeKnora + Postgres + MCP 仍然合理

家庭营养师涉及：

- 宝宝 / 老人 / 健康偏好；
- 库存数量；
- 采购记录；
- 饭后反馈；
- 推荐去重；
- 幂等扣减；
- 审计和可恢复性。

这些需求决定了：

```text
不能把动态状态只放在资料库、Wiki、Markdown 或 CSV 里。
```

因此当前架构仍然正确：

```text
稳定知识：Git Markdown + WeKnora 知识库
动态状态：Postgres
状态工具：MCP
用户入口：WeKnora Agent / 后续微信入口
```

### 11.2 但 WorkBuddy 资料库的“人机共写”值得借鉴

我们后续可以从 WorkBuddy 借鉴三点：

1. **Agent 产物自动归档**
   - 每次菜单推荐、菜谱分析、反馈总结，都应能自动生成可读 Markdown 摘要。
   - 这些摘要可以进入 `exports/markdown/`，再上传或同步给知识库。

2. **修订建议而非直接覆盖**
   - 长期偏好、饮食规则、菜谱修改，不应由 Agent 直接改掉。
   - 应生成“建议修改清单”，用户确认后再进入正式 Markdown。

3. **HTML + CSV 轻应用思路**
   - 家庭营养师可以做一个轻量看板：本周菜单、库存临期、采购建议、宝宝餐安排。
   - 但 CSV 只能作为导出视图，不作为最终状态源；最终状态仍在 Postgres。

### 11.3 如果未来试用 WorkBuddy，可优先验证这些问题

如果我们后续真的拿 WorkBuddy 做家庭营养师或企业知识场景，应重点验证：

1. 资料库内容是否有 API / 导出机制；
2. Agent 是否能稳定写入指定资料库路径；
3. 是否支持自定义 MCP 工具；
4. 企业版是否支持私有化或数据隔离；
5. 权限是否能精确到空间、文档、工具；
6. HTML + CSV 是否支持版本管理和回滚；
7. 是否能接入独立 Postgres，而不是只用 CSV；
8. 是否支持引用溯源和知识更新检测；
9. Agent 修改文档是否有审阅、diff 和人工确认；
10. 移动端 / 微信入口是否能稳定调用资料库和工具。

## 12. 对连山产品分析的启示

WorkBuddy 资料库对连山当前工业 AI / Agent 平台有较强参考价值。

当前连山更强的是：

```text
私有化部署底座
PG-first 数据底座
运行时事件和反馈闭环
HITL
EVI 价值归因
工业质量 / 工艺场景样板
```

WorkBuddy 更强的是：

```text
普通用户入口
Agent 产物管理
团队协作空间
文档/表格/网页三件套
轻量发布
腾讯办公生态整合
```

因此，连山如果要提升产品表达，可以考虑把“Agent 运行体系”往一个更容易理解的对象收敛：

```text
工业现场 Agent 工作台 / 质量改善资料库 / 工艺知识作战空间
```

不是只讲“平台、runtime、workflow”，而是让用户看到：

1. AI 分析出的报告会沉淀在哪里；
2. 专家怎么审阅和修订；
3. 现场数据和知识怎么关联；
4. 已验证的诊断流程如何被复用；
5. 工单、报告、参数建议、EVI 证据如何形成一棵资产树。

换句话说：

```text
WeKnora 给我们知识库与 Agent 问答参考；
WorkBuddy 给我们人机协作资料库与产物沉淀参考；
连山自己的优势应落在工业状态、现场闭环和价值归因。
```

## 13. 初步产品判断

### 13.1 WorkBuddy 资料库的本质

它不是传统知识库，也不只是网盘，而是：

```text
Agentic artifact repository
```

也就是 AI Agent 时代的“工作产物仓库”。它管理的不只是知识，而是：

- 任务产物；
- 可继续加工的上下文；
- 团队协作材料；
- 可发布页面；
- 轻量结构化数据；
- 人和 Agent 共同维护的文件树。

### 13.2 与 WeKnora 的根本差异

```text
WorkBuddy 解决的是：Agent 做出来的东西怎么沉淀、协作、继续改、发布出去。
WeKnora 解决的是：已有知识怎么被检索、问答、Wiki 化、接入 Agent。
```

### 13.3 对我们的行动建议

短期不建议把家庭营养师从 WeKnora 迁到 WorkBuddy，因为当前核心难点是动态状态、MCP 工具、安全边界和可控部署，WeKnora + Postgres + MCP 更符合现阶段架构。

但建议持续跟踪 WorkBuddy 资料库，因为它在以下方面值得借鉴：

1. 人和 Agent 共用同一资料树；
2. Agent 产物自动归档；
3. MD / CSV / HTML 三件套；
4. HTML + CSV 轻应用；
5. 团队空间权限即 Agent 上下文权限；
6. 修订建议机制；
7. 发布与协作分离。

如果未来要做“家庭营养师产品化”或“工业 AI Agent 工作台”，WorkBuddy 资料库是一个很好的参考对象。
