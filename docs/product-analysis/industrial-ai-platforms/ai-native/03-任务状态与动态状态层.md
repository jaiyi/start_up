# 03. 任务状态与动态状态层

## 1. 设计目标

AI Native 任务闭环平台必须有自己的动态状态层。

原因很简单：知识库、Wiki、Markdown、向量库和 GraphRAG 适合承载稳定知识、SOP、案例、规则、复盘和引用证据，但不适合作为任务状态、工具调用、反馈、审批、幂等、库存、工单进度和经营归因的 source of truth。

动态状态层的目标是：

1. 记录任务从触发到关闭的完整状态。
2. 记录 AI 建议、人类决策、工具调用和外部写回。
3. 支持状态机约束和幂等命令。
4. 支持审计、复盘、失败补偿和反馈学习。
5. 为经营归因提供可信事件和指标快照。
6. 为知识更新提供候选材料，但不自动发布正式知识。

## 2. 状态层与知识层分工

| 类型 | 应放在哪里 | 原因 |
|---|---|---|
| 任务状态 | Postgres 动态状态库 | 高频变化，需要事务、查询和审计 |
| 工具调用记录 | Postgres 动态状态库 | 需要幂等、追溯、失败补偿 |
| 人工审批 | Postgres 动态状态库 | 需要明确责任人和状态 |
| AI 建议采纳 / 驳回 | Postgres 动态状态库 | 是反馈学习和评测依据 |
| 工单 / 库存 / 菜单等业务事实 | 权威业务系统或平台状态库 | 需要结构化 source of truth |
| SOP / 案例 / 复盘 | 知识库 + 元数据表 | 稳定知识，适合检索和版本化 |
| 指标口径 | 数仓 / 指标平台 + 语义层 | 需要口径和血缘 |
| 经营归因结果 | 平台状态库 + 数仓快照 | 需要任务级证据和指标级计算 |

一句话：动态事实进数据库，稳定知识进知识库，指标进数仓或经营账本，三者通过业务对象和任务 ID 关联。

## 3. 核心对象

动态状态层至少包括 8 类对象。

```text
TaskTemplate       # 任务模板
Task               # 任务实例
TaskEvent          # 任务事件日志
TaskStateTransition# 状态转移记录
ToolCall           # 工具调用
Approval           # 人工确认 / 审批
FeedbackRecord     # 反馈记录
ValueImpact        # 经营归因记录
```

后续再扩展：

```text
BusinessEvent      # 业务事件
BusinessObjectRef  # 业务对象引用
SkillRun           # AI Skill 执行记录
EvidenceRef        # 证据和引用
Artifact           # 任务产物
CompensationJob    # 失败补偿
KnowledgeCandidate # 候选知识
MetricSnapshot     # 指标快照
```

## 4. 任务状态机

第一版不要做过度通用的流程引擎，应先为目标场景定义显式状态机。

通用任务状态可以从下面开始：

```text
created
  ↓
triaged
  ↓
in_progress
  ↓
waiting_human_confirmation
  ↓
executing_writeback
  ↓
resolved
  ↓
reviewing
  ↓
closed
```

异常状态：

```text
blocked
failed
cancelled
reopened
```

每个状态只允许有限动作。

| 当前状态 | 允许动作 | 下一状态 |
|---|---|---|
| `created` | 分派责任人 | `triaged` |
| `triaged` | 开始处理 | `in_progress` |
| `in_progress` | 生成 AI 建议 | `in_progress` |
| `in_progress` | 提交待确认动作 | `waiting_human_confirmation` |
| `waiting_human_confirmation` | 人工确认 | `executing_writeback` |
| `waiting_human_confirmation` | 驳回 | `in_progress` |
| `executing_writeback` | 写回成功 | `resolved` |
| `executing_writeback` | 写回失败 | `blocked` 或 `failed` |
| `resolved` | 创建复盘 | `reviewing` |
| `reviewing` | 复盘完成 | `closed` |
| `closed` | 重新打开 | `reopened` |

状态机必须由服务端校验，不能相信前端或 Agent 直接传入的目标状态。

## 5. 命令式写入模型

动态状态层不应暴露任意 update。所有写入都应通过命令完成。

示例命令：

```text
CreateTaskCommand
AssignTaskOwnerCommand
AttachContextCommand
RecordAiRecommendationCommand
RecordHumanDecisionCommand
RequestApprovalCommand
ApproveActionCommand
RejectActionCommand
ExecuteWritebackCommand
RecordToolCallResultCommand
RecordTaskFeedbackCommand
CloseTaskCommand
ReopenTaskCommand
```

每个命令都要：

1. 校验输入 schema。
2. 校验 actor 权限。
3. 校验当前状态是否允许。
4. 校验业务对象是否在任务范围内。
5. 写入任务当前状态。
6. 追加事件日志。
7. 必要时写入审计日志。
8. 返回下一步允许动作。

## 7. 上下文构建

Agent 不应自己拼接全部上下文。平台应提供 Task Context Builder。

输入：

```text
BuildTaskContextInput
├── task_id
├── actor_id
├── skill_id
├── requested_context_types
└── max_sensitivity_level
```

输出：

```text
TaskContext
├── task_summary
├── current_status
├── allowed_actions
├── business_objects
├── recent_events
├── relevant_tool_results
├── knowledge_refs
├── metric_snapshots
├── feedback_history
├── permission_scope
└── redaction_notes
```

上下文构建必须做：

1. 权限过滤。
2. 敏感字段脱敏。
3. 任务状态裁剪。
4. 引用来源保留。
5. token 预算控制。
6. 工具可用性声明。

## 8. 事件驱动与事务边界

动态状态层建议使用“当前状态 + 事件日志”的组合。

命令执行事务：

```text
BEGIN
  1. SELECT task FOR UPDATE
  2. validate command
  3. update tasks current status / fields
  4. insert task_events
  5. insert audit_log
  6. insert outbox_events if needed
COMMIT
```

外部写回不要放在同一个数据库事务里直接执行。建议采用 outbox pattern：

```text
1. 命令写入 outbox_events
2. worker 读取 outbox
3. 调用 MCP / Connector
4. 写入 tool_calls 和 task_events
5. 成功则推进任务状态
6. 失败则重试或进入 compensation_jobs
```

这样可以避免数据库事务被外部系统超时拖住，也能保证失败可见。

## 9. 动态状态与外部系统一致性

平台状态和外部系统状态可能短暂不一致。第一版要显式表达一致性状态。

```text
writeback_status
├── not_required
├── pending_approval
├── pending_execution
├── executing
├── succeeded
├── failed_retryable
├── failed_final
└── compensated
```

任务 UI 不应只显示“已处理”，还应显示关键写回是否成功。例如维修任务已形成处理方案，但 EAM 工单备注写回失败，这应对用户可见。

## 10. 反馈闭环

反馈不是点赞，而是任务结果的一部分。

第一版反馈类型：

| 类型 | 含义 |
|---|---|
| `accepted` | 人采纳了 AI 建议 |
| `rejected` | 人驳回 AI 建议 |
| `modified` | 人基于 AI 建议做了修改 |
| `result_positive` | 执行后结果有效 |
| `result_negative` | 执行后结果无效或复发 |
| `knowledge_outdated` | 引用知识过期或错误 |
| `new_knowledge_candidate` | 产生候选知识 |

反馈记录应关联：

1. 哪个任务。
2. 哪个 Skill 输出。
3. 哪条知识引用。
4. 谁做了修改。
5. 实际结果如何。
6. 是否进入评测集或知识审核流。

## 11. 与 AI Skill 的关系

Skill 输出不能直接覆盖任务事实。

推荐处理方式：

```text
Skill 输出
  ↓
保存为 Recommendation / Draft
  ↓
用户采纳 / 修改 / 驳回
  ↓
采纳后生成 Command
  ↓
Command 推进任务状态或写回
  ↓
结果进入 FeedbackRecord
```

这可以避免 AI 把“建议”误写成“事实”。

例如：

- AI 说“可能是传感器异常”只是建议。
- 维修人员确认“更换传感器后恢复”才是处理事实。
- 主管确认“故障关闭”才是闭环事实。
- 复盘审核通过后，才可能成为正式知识。

## 12. 数据保留和归档

动态状态层要考虑数据生命周期。

建议：

1. `tasks` 和 `task_events` 长期保留，至少保留业务和审计要求周期。
2. `tool_calls` 保留脱敏输入输出和引用，不保留密钥或过度敏感原文。
3. 大文本产物放对象存储或文档库，数据库保存引用。
4. 已关闭任务可生成归档快照。
5. 过期的临时上下文可以清理，但不能破坏审计链路。

## 13. 安全和权限

动态状态层的权限至少包括：

1. 任务读取权限。
2. 任务动作权限。
3. 工具调用权限。
4. 审批权限。
5. 反馈编辑权限。
6. 知识候选审核权限。
7. 经营归因查看权限。

常见规则：

```text
用户只能查看自己组织、工厂、项目或被授权对象的任务。
用户只能执行当前状态允许的动作。
Agent 只能通过服务端注入的 actor / task 上下文调用工具。
高风险写回必须有审批。
经营归因数据可能比任务内容更敏感，需要单独授权。
```

## 14. 最小 API 设计

第一版可以提供这些 API：

```text
POST /tasks
  创建任务

GET /tasks/:taskId
  查询任务详情

GET /tasks/:taskId/events
  查询任务事件

POST /tasks/:taskId/commands/:commandName
  执行任务命令

POST /tasks/:taskId/context
  构建 Agent / Skill 上下文

GET /tasks/:taskId/tool-calls
  查询工具调用

POST /tasks/:taskId/feedback
  记录反馈

POST /tasks/:taskId/approvals
  创建审批

POST /approvals/:approvalId/decision
  审批通过或驳回

GET /tasks/:taskId/value-impacts
  查询经营归因
```

命令 API 必须统一返回：

```text
CommandResult
├── success
├── task_id
├── previous_status
├── current_status
├── event_id
├── next_allowed_actions
├── warnings
└── error
```

## 15. 第一版设备维修样例

### 15.1 创建任务

```text
CreateTaskCommand
├── task_type: equipment_repair
├── trigger_event_ref: MES alarm A-1001
├── business_object_refs:
│   ├── equipment:E-001
│   ├── line:Line-A
│   └── fault_code:F-209
├── expected_outcome: 恢复设备运行并记录处理方案
└── priority: high
```

结果：

```text
Task.status = created
TaskEvent = task_created
```

### 15.2 AI 生成建议

```text
RecordAiRecommendationCommand
├── skill: similar_case_diagnosis
├── recommendation: 检查传感器与气压阀
├── evidence_refs: SOP-001, Case-2025-08-18
└── confidence_level: medium
```

结果：

```text
Task.status = in_progress
FeedbackRecord 暂不生成，等待人类决策
```

### 15.3 人类采纳并写回

```text
RecordHumanDecisionCommand
├── decision: modified
├── revision: 先检查传感器接线，再检查气压阀
└── reason: 现场观察传感器灯异常
```

```text
RequestApprovalCommand
├── target_action: append_work_order_note
├── risk_level: L2
└── payload_hash: xxx
```

审批通过后：

```text
ExecuteWritebackCommand
├── tool: append_work_order_note
├── idempotency_key: task-001-note-001
└── approval_id: approval-001
```

结果：

```text
ToolCall.status = succeeded
TaskEvent = external_writeback_succeeded
Task.status = resolved
FeedbackRecord = modified + result_pending
```

### 15.4 复盘和关闭

```text
RecordTaskFeedbackCommand
├── result: 设备恢复，2 小时内未复发
├── ai_helpful: true
├── knowledge_outdated: false
└── candidate_knowledge: 传感器灯异常可作为 F-209 初查项
```

结果：

```text
KnowledgeCandidate.status = pending_review
ValueImpact.metric_key = downtime_minutes
Task.status = reviewing 或 closed
```

## 16. 测试策略

### 16.1 状态机测试

覆盖：

1. 合法状态转移成功。
2. 非法状态转移失败。
3. closed 任务不能被普通命令修改。
4. reopened 必须记录原因。
5. 每次状态变化都生成 task_event。

### 16.2 命令测试

覆盖：

1. 输入 schema 错误。
2. actor 无权限。
3. 业务对象不属于任务。
4. 幂等重复命令。
5. 事件和审计是否一起写入。

### 16.3 集成测试

覆盖：

1. 创建任务 → AI 建议 → 人审 → 写回 → 反馈 → 关闭。
2. 写回失败 → compensation job → 重试成功。
3. 高风险动作缺少审批时被拦截。
4. 上下文构建时敏感字段被过滤。
5. 反馈生成知识候选但不自动发布。

### 16.4 数据一致性测试

覆盖：

1. 并发命令不会造成状态错乱。
2. sequence_no 单调递增。
3. outbox 事件至少一次处理下不会重复外部写回。
4. 同一个 idempotency key 不会生成重复工具调用。

## 17. 第一阶段可执行任务清单

1. 选择一个任务流并画出状态机。
2. 建 `tasks`、`task_events`、`skill_runs`、`tool_calls`、`approvals`、`feedback_records`、`audit_log` 表。
3. 实现 `POST /tasks` 和 `GET /tasks/:taskId`。
4. 实现命令执行框架。
5. 实现状态机 guard。
6. 实现事件追加和审计追加。
7. 实现 Task Context Builder 的最小版本。
8. 接入 MCP 工具调用记录。
9. 实现采纳 / 驳回 / 修改反馈。
10. 实现一个从反馈生成候选知识的流程，但必须停在审核状态。

## 18. 验收标准

动态状态层第一版完成时，应满足：

1. 每个任务都有明确当前状态和完整事件历史。
2. 所有状态变化都来自命令，而不是任意 update。
3. AI 输出和人工确认被明确区分。
4. 工具调用能关联到任务、Skill 和 actor。
5. 写回失败可以被看见、重试或补偿。
6. 反馈能进入后续知识审核或 Skill 评测流程。
7. 经营归因至少有任务级字段和基础指标快照。
