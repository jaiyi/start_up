## 设计原则

1. **厚场景，薄系统**：从设备维修、质量异常、采购降本、项目毛利等高价值任务流切入，不先做无业务入口的大平台。
2. **传统系统不被替代**：ERP、MES、EAM、PLM、CRM、OA、飞书、数仓、BI、知识库仍然是权威系统和动作落点。
3. **平台掌管任务闭环**：AI Native 平台负责跨系统任务对象、AI Skill、知识调用、反馈学习、权限审计和经营归因。
4. **连接层既能读，也能受控写**：读上下文只是第一步，真正闭环必须能在权限、Schema、幂等、审计和人工确认约束下写回状态或动作。
5. **动态状态进数据库，稳定知识进知识库**：任务状态、工具调用、反馈、库存、工单等动态事实不应只靠文档维护；SOP、案例、规则、复盘等稳定知识可以进入知识库和 GraphRAG。
6. **AI 不绕过组织责任**：AI 可以建议、生成、诊断和预警；高风险动作必须有人类责任人确认，所有工具调用和写回都必须可追溯。
7. **先闭环，再智能升级**：第一阶段先跑通状态、工具、任务、审计和反馈，再逐步增强本体、GraphRAG、Skill 评测和经营归因。

## 推荐推进顺序

```text
阶段 0：选定一个高价值任务流
  ↓
阶段 1：定义业务对象、任务对象和最小状态机
  ↓
阶段 2：实现连接层只读工具与平台内部写入工具
  ↓
阶段 3：接入 2-3 个 AI Skill，并把输出纳入采纳 / 驳回 / 修改流程
  ↓
阶段 4：打通业务系统写回、审计、失败补偿和人工确认
  ↓
阶段 5：沉淀知识资产、评测集、反馈学习和经营归因
  ↓
阶段 6：迁移到第二个任务流，抽象为平台能力
```

## 当前边界

本目录只写工程架构和产品技术设计，不写真实部署地址、账号、服务器路径、端口、密钥、Cookie、Token 或任何本地 `.env` 内容。真实部署细节应只进入专门的 deployment runbook，并且不得提交敏感信息。
