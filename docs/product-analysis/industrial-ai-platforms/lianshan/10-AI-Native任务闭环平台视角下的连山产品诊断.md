# 10 · AI Native 任务闭环平台视角下的连山产品诊断

> 分析日期：2026-09-23
> 分析对象：`lisen-infra`、`lads`、`dsruntime`、`workstation-iclaw`、`edge-inference`、`demos-fta`、`demos-spc`、`demos-param-opt` 及当前产品体系诊断。
> 视角：以 `docs/insights/04-05-AI-Native任务闭环平台.md` 的平台愿景，重新评价连山当前产品体系。
> 结论口径：本文区分「平台愿景」「已有工程证据」「场景样板」「生产证据」「商业证据」，避免把完整 stack、demo 样板和可规模化产品混为一谈。

---

## 0. 一句话结论

如果用 AI Native 任务闭环平台的框架看连山，当前连山已经具备了非常罕见的底层雏形：私有化部署、PG-first 数据平面、Bundle-first 交付、runtime feedback、HITL、人机协同、EVI 价值归因、SPC / FTA / 参数推荐等场景样板都已经出现。但连山现在最需要补的不是更多横向工程，而是把这些能力收敛成一个清晰的产品主线：**面向制造质量与工艺改善的高价值任务流闭环平台**。

更直接地说：

> 连山不应该只是做某个点状 AI 应用，也不应该陷入帮客户重造一堆管理系统，而应该做“面向制造企业高价值任务流的 AI Native 闭环平台”；但早期对外销售时，不宜先讲大平台，而应以 SPC 质量异常闭环作为主战场，证明它能在真实产线里发现问题、推动人处理问题、记录结果、沉淀知识，并让客户相信这件事带来了经营收益。

这和 `09-current-product-diagnosis.md` 的判断并不冲突，而是把它进一步放进 AI Native 任务闭环平台的产品架构里：`09` 解决“当前连山像什么、风险是什么、主战场是什么”，本文进一步解决“如果连山要长成 AI Native 任务闭环平台，哪些能力已经具备，哪些能力需要重组，下一阶段应该怎么改”。

## 1. 用 AI Native 任务闭环平台重新看连山

`04-05` 对 AI Native 任务闭环平台的定义是：不要围绕每条业务流重造一套系统，而是在企业现有 ERP、MES、EAM、PLM、CRM、OA、飞书、数仓、BI、知识库之上，建设一层统一的业务对象、语义、本体、任务状态、AI Skill、权限审计、反馈回写和经营归因控制面。

把这套框架放到连山上，关键问题就不是“连山有没有 Agent、有没有模型、有没有 workflow”，而是：

| 诊断问题 | 对连山的含义 |
|---|---|
| 是否有统一业务对象 | 质量异常、工艺参数、设备、产线、工单、缺陷、根因、措施、人员、EVI 是否被统一表达，而不是散在各仓 schema / YAML / OWL / JSONB 中。 |
| 是否有任务闭环状态机 | SPC 告警、FTA 诊断、参数推荐是否都能用统一任务对象表达：触发、分派、诊断、建议、审核、执行、验证、关闭、复盘。 |
| 是否能受控读写现有系统 | 能否读取 MES / 检测数据 / 工艺主档 / 设备层级，并通过 API / MCP / 工单 / 推卡受控写回，不绕过权限、schema、幂等和审计。 |
| 是否沉淀知识资产 | 每次异常处理、人审修正、参数采纳、根因确认、措施有效性是否能回到本体、故障树、案例库、评测集和 Skill。 |
| 是否有可复用 AI Skill | SPC 诊断、点焊追溯、参数推荐、FTA 根因分析是否作为可版本化、可评测、可复用 Skill，而不只是某个 demo 的脚本。 |
| 是否能经营归因 | EVI 是否从工程台账升级为客户业务负责人和财务认可的证据链。 |
| 是否能组织化运营 | 谁确认、谁审批、谁关闭、谁复盘、谁维护知识、谁签字认收益，是否成为产品内置流程，而不是项目交付口头约定。 |

在这个视角下，连山最有价值的地方，是它并没有停留在“知识库问答 + 大模型界面”，而是已经开始把工业 AI 做成一条面向任务闭环的工程链路；最大的风险则是，这条链路目前分散在多个仓库、多个产品面、多个 demo 和大量工程约束中，还没有被压缩成客户容易理解、团队容易交付、场景能够复用的产品形态。

## 2. 当前能力映射：连山已经拥有的平台雏形

### 2.1 平台八层映射

按 AI Native 任务闭环平台八层看，连山已有能力大致如下：

| 平台层 | 连山已有能力 | 当前判断 |
|---|---|---|
| 连接层 | `lisen-infra` 的私有化部署、PG / RustFS / dokku-admin、named datasource、SPC 的 Kafka / CloudQuery / 工艺主档 / 设备层级接入、参数推荐的数据源集成。 | 有工程底座，但对外应产品化为“受控连接器与数据可用性诊断”，而不是只表现为部署脚本和项目配置。 |
| 语义层 | `lads` 的 ontology binding、`dsruntime` 的 AGE / knowledge projection、SPC / FTA / 参数推荐的 OWL、本体、业务对象。 | 有本体与语义资产雏形，但仍分散在场景仓、runtime schema 和 Bundle 制品中，缺统一语义资产台账。 |
| 知识层 | FTA 故障树、SPC diagnosis ontology、glue / weld ontology、参数案例库、knowledge seeds、数字员工 mind。 | 有真实制造知识形态，但需要从“项目内知识文件”升级为可治理、可评测、可迭代的知识资产。 |
| 任务层 | BPMN / DMN、`dsruntime` 的 execution_run / graph_checkpoint / work_order / human_task_decision、SPC 推卡反馈、参数推荐 recommendation_loop。 | 闭环状态机已出现，但不同场景的任务模型还不够统一，客户侧也未形成标准任务运营模板。 |
| AI 能力层 | `lads` domain algorithms、SPC 判异、参数推荐六路算法、LangGraph runtime、数字员工、capability YAML、Agent tools。 | 能力丰富，但需要整理成可注册、可评测、可授权、可组合的 Skill 市场或 Skill Catalog。 |
| 治理层 | Bundle lifecycle、AcceptanceReport、HITL checkpoint、RBAC / audit 方向、数据充分度门禁。 | 有正确意识，但安全债、凭据治理、权限矩阵、受控写回策略还需要作为销售前置能力治理。 |
| 反馈层 | runtime feedback export、human_feedback、SPC alert_feedback、参数推荐采纳 / 拒绝 / NG closure、diagnosis_outcome / info_gain。 | 是连山最有潜力的飞轮，但需要统一反馈口径，避免每个场景各记各的。 |
| 经营归因层 | EVI intelligence record、business objective、attribution rule、SPC EVI、参数 NG closure metric。 | 方向非常对，但商业可信度要从 EVI-L1/L2 走向客户确认的 L3。 |

这个映射说明，连山已经不是简单的“工业 AI demo 集合”。它实际已经长出了 AI Native 任务闭环平台的多个关键器官：连接器、语义、本体、任务状态、AI Skill、HITL、反馈、价值归因都有落点。问题是这些器官还没有形成一个让客户和交付团队都能一眼看懂的“身体”。

### 2.2 平台层与场景层的关系

当前连山体系可以被重新组织成三层：

| 层级 | 当前组件 | 正确产品角色 |
|---|---|---|
| 工业私有化与运行底座 | `lisen-infra`、PG、RustFS、dokku-admin、`dsruntime` 控制面 | 让系统能在客户现场安全、稳定、可审计地跑起来，是可信交付基础，不是客户首先购买的业务价值。 |
| AI Native 任务闭环平台 | `lads` Bundle 编译、runtime feedback、HITL、EVI、ontology、Skill / capability、任务状态机 | 作为跨场景复用的控制面，沉淀业务对象、任务模板、AI Skill、知识资产、反馈和归因。 |
| 制造质量 / 工艺场景产品 | `demos-spc`、`demos-fta`、`demos-param-opt`、边缘推理节点、数字员工工作站 | 面向客户痛点的入口产品，应优先把“质量异常闭环”“参数治理闭环”“故障诊断闭环”讲清楚。 |

这意味着，连山内部可以坚持平台化建设，但对外不能让客户先理解一堆 infra、runtime、Bundle、PG 扩展、Agent 框架。对客户更自然的入口是：质量异常怎么更快发现和闭环、工艺参数怎么更稳地治理、专家故障经验怎么资产化、经营收益怎么被证明。

## 3. 连山已经走对的地方

### 3.1 没有把 AI Native 理解成“聊天入口”

连山最值得肯定的一点，是它没有把工业 AI 做成“用户问一句，模型答一句”。SPC 是测量数据触发，FTA 是工单 / 故障触发，参数推荐是 NG 反馈触发，runtime 是事件流触发。这符合 AI Native 任务闭环平台的基本原则：AI 不应该只站在流程外回答问题，而要嵌入业务对象、任务状态和执行链路中。

### 3.2 PG-first 对工业现场非常务实

工业现场的现实不是云原生中台，而是私有化、弱网络、弱运维、数据出域限制、边缘节点多、客户 IT 资源有限。连山把消息、向量、图谱、配置、事件、反馈、审计尽可能收敛到 PostgreSQL 生态，对单节点工作站和边缘盒子是务实选择。它降低了交付依赖曲面，也让任务闭环平台所需的“状态、知识、事件、反馈、归因”更容易被统一管理。

需要注意的是，PG-first 不是护城河本身。它是让闭环跑起来的工程选择。真正的护城河，仍然来自 PG 里沉淀的制造对象、工艺规则、反馈数据、故障树、参数边界和 EVI 证据。

### 3.3 Bundle-first 给工业 AI 交付建立了纪律

`lads` 编译 Bundle、`dsruntime` 消费 Bundle，这个边界非常重要。工业客户需要可追踪、可回滚、可审计、可验收，不能让现场脚本随意变化。Bundle-first 让模型、规则、本体、DAG、BPMN、edge artifacts、知识投影与发布生命周期绑定，为后续的反馈归因提供了版本基础：哪个 Bundle 处理了哪些事件、产生了什么建议、被谁改过、结果如何。

这与 AI Native 任务闭环平台中的“Skill 可版本化、反馈可归因、知识可迭代”高度一致。

### 3.4 HITL 是工业 AI 的正确起点

制造业不适合一开始就宣称 Human-out-of-the-loop。连山在 runtime、SPC、参数推荐中保留了人工确认、审批、拒绝、修正、反馈投影、checkpoint / resume，这是正确路径。AI 先建议，人来审核；系统记录人怎么改、为什么改、结果有没有改善；再逐步把低风险、高置信、可回滚动作自动化。

这不是保守，而是工业 AI 商业化的必要条件。客户要买的不是“AI 自己乱动设备”，而是“AI 帮人更早发现、更快判断、更少漏掉、更可追责地处理”。

### 3.5 EVI 抓住了商业化核心问题

很多工业 AI 项目做完以后只能说“看起来有效”，不能说“值多少钱”。连山把 EVI 放到底层能力里，是非常重要的产品判断。AI Native 任务闭环平台最终一定要回答经营问题：这个任务闭环减少了多少返工、报废、停机、客诉、人工时间，谁确认，能否续费，能否按结果付费。

当前 EVI 机制、business objective、value_delta、attribution_rule 等工程设计已经出现。下一步要做的不是继续发明更多 EVI 概念，而是选一个窄场景把 EVI 从工程记录做成客户认可的经营证据。

## 4. 核心诊断：与任务闭环平台愿景之间的差距

### 4.1 平台能力分散，客户感知不到统一任务闭环

连山现在有 infra、lads、dsruntime、workstation-iclaw、edge-inference、SPC、FTA、参数推荐等多个组件。每个组件单看都有亮点，但客户很难自然理解它们共同服务于哪条业务闭环。平台能力如果只以技术组件形式出现，就会变成“工程 stack 很强，但客户不知道该买什么”。

改进方向是把底层能力重新组织成任务闭环语言：不是 `lads + runtime + iweb + pgmq + AGE`，而是“质量异常任务如何从检测到关闭”“参数变更任务如何从建议到验证”“故障诊断任务如何从工单到知识更新”。

### 4.2 场景样板还没有完全变成可复制任务模板

SPC、FTA、参数推荐都已经有样板，但任务闭环平台需要的不只是样板，而是可复制模板。模板至少要包含：业务对象、触发条件、任务状态机、角色权限、输入数据清单、AI Skill、工具调用、HITL 节点、回写目标、指标口径、EVI 公式、验收证据、运营 SOP。

当前这些元素分散在 schema、pyproject、YAML、BPMN、DMN、OWL、AGENTS.md 和场景文档里。它们已经存在，但还没有形成一个面向交付和销售的“任务模板包”。如果每次客户交付都要重新读源码、改 YAML、接系统、解释流程，平台复用价值会被交付复杂度吃掉。

### 4.3 语义层还没有产品化为统一资产台账

连山已经有 OWL、本体、AGE、knowledge projection、故障树、SPC dimension、param domain ontology 等资产。但它们目前更像工程实现与项目文件，而不是一个可被客户和实施团队共同治理的语义资产台账。

AI Native 任务闭环平台需要一个更明确的语义产品面：有哪些业务对象、对象之间的关系是什么、哪些字段来自 MES / 工艺主档 / 工单 / 检测数据、哪些概念已经绑定到 AI Skill、哪些知识被人审修正过、哪些规则在生产中有效。否则本体会停留在“技术上有”，而不是“业务上可治理”。

### 4.4 受控写回能力需要标准化

连接层不能只读，也要能编辑 / 录入 / 写回。连山已经有推卡反馈、runtime feedback、人审、工单和参数推荐 workflow，但下一阶段必须把“写回”做成平台标准能力，而不是每个场景各自实现。

标准写回应至少包括：权限检查、schema validation、动作策略判断、人类确认、幂等键、审计日志、失败补偿、敏感动作阻断、回滚或撤销策略。尤其是参数推荐、工单关闭、规则修改、知识库更新、EVI 签字这几类动作，不能只靠业务代码约定。它们应该成为平台治理层的一部分。

### 4.5 数字员工仍有“入口强、任务芯弱”的风险

`workstation-iclaw` 有工作站、SSO、discovery、员工同步、工单评审等产品面，这些是必要入口。但数字员工的长期价值不在入口本身，而在它绑定了什么高价值任务、掌握了什么证据、能调用什么工具、能推动什么状态变化、能沉淀什么反馈。

如果数字员工没有强绑定 SPC 质量诊断、FTA 根因分析、参数推荐、点焊追溯等任务闭环，它就会被通用 Agent 平台替代。正确方向是让数字员工成为任务模板中的角色：质量诊断员工负责证据聚合与根因假设，工艺参数助手负责推荐与风险解释，知识维护员工负责把人审修正转成规则 / 故障树 / 案例更新候选。

### 4.6 EVI 还需要从系统指标变成客户证据

当前 EVI 工程方向正确，但商业化要求更高。客户不会因为系统里有 `evi_record` 就接受收益。他们需要看到连续运行、前后对照、误报治理、人工确认、成本动因、财务认可。

因此 EVI 要分层推进：EVI-L1 记录事件和建议，EVI-L2 有人工确认和前后对照，EVI-L3 有反事实基线和成本动因，EVI-L4 有财务 / 审计认可。连山下一阶段不要急着讲 gainsharing，而应先在 SPC 质量异常闭环里稳定做到 L2，选择一个可核算损失的子场景冲 L3。

### 4.7 安全债会成为大客户销售前置阻碍

`lisen-infra` 里明文密码、默认密码、硬编码 token、secret 管理成熟度不足等问题，不能被当作“后面再优化”。如果目标客户是制造业大客户、私有化部署、生产网环境，安全就是销售门槛。AI Native 任务闭环平台天然会接触业务数据、生产数据、工艺参数、质量问题和人员操作记录，如果权限、凭据、审计、数据出域治理不清楚，很容易在 IT / 安全部门被卡住。

### 4.8 横向工程过重，可能稀释纵向资产

连山当前横向工程很强，但横向工程越多，越容易把团队注意力吸走。Ansible、Dokku、PG 扩展、Bundle、workflow、iWeb、Agent 工作站、edge inference 都重要，但它们最终必须服务纵向制造资产：工艺规则、质量异常案例、参数边界、故障树、人审修正、客户确认收益。

一句话：

> 横向能力是杠杆，纵向闭环资产才是连山真正能复利的东西。

## 5. 产品定位建议：内部做平台，外部卖闭环

### 5.1 内部定位

内部可以把连山定义为：

> 面向制造企业高价值任务流的 AI Native 闭环平台。

这个定义强调的不是“我们有很多 Agent”，而是连山能把制造企业里的高价值任务流变成可配置、可执行、可审计、可反馈、可归因、可迭代的闭环。每次交付都应沉淀任务模板、业务对象、本体、AI Skill、连接器、反馈数据、评测集和 EVI 归因模型。

### 5.2 对外定位

对外早期不要主打“大平台”，建议收敛为：

> 制造质量与工艺改善的 AI 闭环系统：发现异常、诊断原因、推荐措施、推动处理、跟踪结果、沉淀知识、量化收益。

这个表述比“工业 AI Agent 平台”更容易被质量负责人、工艺负责人、生产负责人和财务理解。客户购买的不是 stack，而是异常闭环时间下降、误报减少、定位更快、NG closure 提升、返工 / 报废 / 客诉损失下降。

### 5.3 产品层级

建议把产品包拆成三层叙事：

| 层级 | 客户语言 | 内部能力 |
|---|---|---|
| 场景闭环包 | SPC 质量异常闭环、参数治理闭环、FTA 故障诊断闭环 | 任务模板、数据接入、推送、HITL、报告、EVI。 |
| AI 任务控制面 | 统一任务状态、数字员工、知识沉淀、反馈回写、权限审计 | `dsruntime`、Skill Catalog、workflow、feedback、ontology。 |
| 私有化工业 AI 底座 | 可在客户现场部署、可审计、可回滚、可接现有系统 | `lisen-infra`、PG-first、Bundle-first、RustFS、dokku-admin。 |

销售时从上往下讲，交付时从下往上建，研发时用中间层保证复用。

## 6. 主战场建议：SPC 质量异常闭环优先

`09-current-product-diagnosis.md` 已经建议 SPC 质量异常闭环作为第一优先级。放到 AI Native 任务闭环平台视角，这个判断更明确：SPC 是最适合作为“第一个标准任务模板”的场景。

### 6.1 为什么是 SPC

SPC 具备几个关键条件：数据频率高、业务对象清晰、异常定义相对标准、质量负责人容易理解、反馈按钮简单、误报治理可量化、EVI 容易从返工 / 报废 / 客诉风险切入。它可以先形成轻闭环，再逐步接入数字员工诊断、工单系统、知识更新和经营归因。

### 6.2 SPC 标准任务对象

建议把 SPC 从“控制图应用”升级为“质量异常任务模板”，统一对象如下：

| 对象 | 含义 |
|---|---|
| ObservedSystem | 被监控的产线、设备、工序、窗口、测点或产品族。 |
| QualitySignal | 测量值、控制图判异、Cpk 退化、趋势偏移、规则命中。 |
| AnomalyTask | 一次需要被处理的质量异常任务，拥有状态、责任人、SLA、证据、处理结果。 |
| DiagnosisHypothesis | AI / 规则生成的根因假设，必须带数据证据、历史相似案例和置信度。 |
| HumanDecision | 人的确认、忽略、修正、替代原因、处理措施。 |
| ClosureEvidence | 后续测量是否恢复、是否复发、是否触发工单、是否产生收益。 |
| EVIRecord | 避免损失、减少响应时间、降低误报、改善 Cpk 的价值记录。 |

### 6.3 SPC 最短闭环

早期不要把 SPC 做成大而全平台，先把最短闭环打穿：

```text
真实测量数据 → SPC 判异 → 责任人推送 → 确认 / 忽略 → 误报统计 → 工单或措施记录 → 闭环结果 → 月度 EVI
```

这个闭环看似简单，但只要能连续稳定运行 30 / 60 / 90 天，就能产生比任何平台架构图更有说服力的商业证据。

### 6.4 SPC 需要补齐的证据

SPC 主战场必须形成一张证据表：

| 证据类型 | 必须回答 |
|---|---|
| 生产运行证据 | 连续运行天数、接入设备 / 产线数、每日样本量、判异延迟、worker 稳定性、数据同步成功率。 |
| 业务效果证据 | 告警准确率、误报率、被确认异常数、平均响应时间、闭环时间、复发率、Cpk 改善。 |
| 组织运营证据 | 谁确认、谁处理、谁复盘、谁维护规则、SLA 是否达成、月度例会是否使用报告。 |
| 财务归因证据 | 避免返工 / 报废 / 客诉 / 停线的估算金额、客户业务负责人是否确认、财务是否接受口径。 |

这张证据表应成为 SPC 产品验收、续费和扩展复制的核心材料。

## 7. 平台能力改进方向

### 7.1 建立统一任务模型

建议在 `dsruntime` / 产品文档层形成统一任务对象模型，覆盖 SPC、FTA、参数推荐等场景。最小字段应包括：task_id、task_type、business_object、trigger_event、severity、owner_role、status、evidence_refs、ai_recommendations、human_decisions、actions、writeback_targets、closure_result、feedback_labels、evi_refs、bundle_version、audit_trail。

统一任务模型的价值是：不同场景不再各自解释闭环，而是共享一套任务语言。SPC 异常、FTA 工单、参数推荐都可以被看作高价值任务流的不同模板。

### 7.2 建立 Task Template Catalog

每个可销售场景都应沉淀成任务模板，而不是只沉淀代码仓。建议至少有三类模板：

| 模板 | 当前来源 | 目标形态 |
|---|---|---|
| SPC 质量异常闭环 | `demos-spc` | 高频主模板，包含数据接入、判异、推送、人审、误报治理、EVI。 |
| 参数推荐 / 参数治理闭环 | `demos-param-opt` | 中高风险模板，强调辅助推荐、人审、参数变更治理、NG 结果回写。 |
| FTA 故障诊断闭环 | `demos-fta` | 专家知识资产化模板，强调故障树、测试项、措施、工单路径和知识修订。 |

模板应包含业务说明、数据要求、系统连接要求、角色权限、任务状态机、AI Skill、验收指标、EVI 口径和运营 SOP。这样才能减少每次交付从零解释的成本。

### 7.3 建立 Skill Catalog 与评测机制

把当前分散在 capability YAML、agent mind、domain algorithm、workflow、tools 中的能力整理成 Skill Catalog。每个 Skill 至少要有：输入 schema、输出 schema、可调用工具、权限范围、适用任务、版本、评测集、采纳率、失败案例、回滚策略。

建议优先产品化的 Skill 包括：SPC 异常摘要、SPC 根因假设生成、点焊追溯、胶类缺陷诊断、FTA 路径推荐、参数推荐解释、参数变更风险检查、EVI 事件归因、月度质量复盘报告生成。

### 7.4 建立统一反馈与经验蒸馏链路

当前 feedback 已经很多，但需要统一成平台飞轮。每次任务闭环后，应能沉淀四类反馈：AI 建议是否被采纳、人做了什么修正、结果是否改善、哪条知识 / 规则 / Skill 有效。然后这些反馈进入四个去向：知识库 / 本体候选更新、规则 / 参数阈值候选更新、Skill 评测集、EVI 归因台账。

尤其要避免只把反馈当作日志。反馈必须变成下一轮任务的可用资产。

### 7.5 建立受控写回网关

建议把写回动作统一收敛到平台网关，而不是各场景自行写。写回类型包括：工单创建 / 更新 / 关闭、推卡反馈、知识候选提交、参数建议状态更新、规则阈值调整、EVI 确认、Bundle 状态推进。

每个写回动作都要经过：权限、schema、策略、人审、幂等、审计、失败补偿。这是连山从 demo 进入大客户生产环境的关键能力。

### 7.6 把 EVI 做成分级证据产品

建议把 EVI 明确拆成产品等级：EVI-L1 事件留痕，EVI-L2 人工确认与前后对照，EVI-L3 反事实基线与成本动因，EVI-L4 财务 / 审计认可。每个项目交付时都要明确当前到哪一级、下一阶段要补什么证据。

这样既避免早期过度承诺 gainsharing，也能让客户看到从项目费、年费到 KPI bonus 的演进路径。

## 8. 场景产品改进方向

### 8.1 SPC：从控制图工具升级为质量异常运营系统

SPC 的产品语言应从“智能过程管控 / 控制图 / 判异算法”进一步升级为“质量异常运营系统”。关键不是图画得多漂亮，而是异常有没有被责任人及时处理，误报有没有被治理，处理经验有没有沉淀，月度是否能证明质量收益。

建议补齐：异常任务台账、责任人 SLA、误报原因分类、根因假设证据包、措施有效性验证、月度 EVI 报告、跨产线复制模板。

### 8.2 参数推荐：坚持辅助推荐 + 参数治理，不急于自动控制

参数推荐天花板高，但也是风险最高的场景。短期不要讲自动调参、自动下发、自动优化产线，而应讲“工艺工程师辅助推荐 + 参数变更治理 + NG 复盘闭环”。

建议补齐：参数建议风险解释、工艺窗口 guardrails、审批矩阵、采纳 / 拒绝理由、采纳后效果追踪、参数一致性校验、真实 MES / 检测反馈接入。只有当低风险参数建议在足够多样本中稳定有效，才逐步推进半自动或自动动作。

### 8.3 FTA：把专家经验资产化，而不是只做一棵故障树

FTA 的核心价值是把专家故障树、测试项、措施方案、诊断路径和工单处理经验沉淀下来。它不一定是最高频商业突破口，但非常适合作为“知识资产化模块”。

建议补齐：故障树版本管理、路径命中率、工程师修正记录、措施有效性、相似工单召回、故障树候选修订流程。FTA 的产品重点不是某一棵前灯树，而是企业如何持续把专家经验转成可执行诊断资产。

### 8.4 Edge inference：不要单独包装成完整闭环

`edge-inference` 适合作为推理结果生产者和边缘节点能力，不宜单独包装成完整边缘智能闭环。完整闭环需要 collector、runtime、人审、反馈、ground truth、再训练和 EVI 共同完成。

对外应把它放在质量 / 视觉 / AOI 任务闭环中讲：边缘推理负责及时发现信号，任务闭环平台负责证据聚合、人审处理、结果回写和价值归因。

### 8.5 Workstation / 数字员工：绑定任务角色而不是泛化入口

数字员工工作站应围绕任务角色产品化：质量诊断员工、工艺参数助手、故障树维护助手、质量复盘助手。每个员工都必须明确触发事件、可读数据、可用工具、可写动作、审批边界、输出证据和反馈去向。

如果只做“工业 Agent 工作台”，很容易被通用平台替代；如果绑定高价值制造任务闭环，就能成为连山纵向资产的入口。

## 9. 组织与商业化改进方向

### 9.1 把组织运营模板作为产品组成部分

工业 AI 落地不是只交软件，还要改变任务责任流。每个任务模板都应内置组织运营说明：谁接收告警、谁确认异常、谁处理工单、谁审核 AI 建议、谁维护知识、谁复盘误报、谁批准参数变更、谁每月确认 EVI。

如果这些角色不清楚，系统很容易变成看板没人看、卡片没人点、反馈没人填、建议没人采纳、EVI 没人认。

### 9.2 形成“工程证据 / 生产证据 / 商业证据”三列表

每个能力都要同时记录三类证据：工程证据说明系统做出来了，生产证据说明系统稳定跑了，商业证据说明客户认为有价值。建议所有场景都维护一张三列表：

| 能力 | 工程证据 | 生产证据 | 商业证据 |
|---|---|---|---|
| SPC 判异 | 有 schema / worker / 控制图 / 推卡 | 连续运行 X 天，处理 Y 次异常 | 响应时间下降、误报下降、Cpk 改善。 |
| 参数推荐 | 有模型 / workflow / recommendation_log | 被工程师采纳 X 次，结果回写 Y 次 | NG closure rate 提升，返工减少。 |
| FTA 诊断 | 有故障树 / OWL / 工单路径 | 诊断 X 单，修正 Y 次 | 定位时间下降，专家经验复用。 |
| EVI | 有 record / attribution rule | 客户确认 X 次 | 财务认可金额 Y。 |

这张表比平台介绍更重要，也更适合做续费和复制。

### 9.3 付费模式分阶段推进

建议延续 `09` 的分阶段付费思路：诊断费、MVP 实施费、年费 / 产线数 / 场景数、KPI bonus、多工厂复制费、成熟后 shared savings。区别在于，每一阶段都要绑定任务闭环成熟度，而不是绑定功能清单。

例如 SPC 可以先按产线 / 测点 / 任务模板收费，等运行证据和 EVI-L2 稳定后，再在某些损失可核算的异常类型上尝试 KPI bonus。

### 9.4 安全与权限治理前置

为了进入大客户生产环境，必须把安全与权限治理前置为产品能力。建议优先治理：明文密码、默认密码、硬编码 token、secret 管理、部署日志泄露、私有包源凭据、runtime token、RBAC、审计日志、客户数据出域、供应链安全。

AI Native 任务闭环平台会发起动作、写回状态、记录人员反馈、接触质量和工艺数据。没有安全治理，就无法获得客户 IT、生产、质量、财务多方信任。

## 10. 分阶段路线图

### 阶段 0：收敛产品语言

目标：把“工业 AI Agent 平台”的泛化叙事收敛为“制造质量与工艺改善的 AI 闭环系统”。内部保留平台化目标，对外先讲高价值任务闭环。输出物包括：SPC 质量异常闭环一页纸、任务模板说明、三类证据表、EVI 分级说明、组织角色矩阵。

### 阶段 1：打穿 SPC 最短闭环

目标：在真实或准真实产线中连续跑通测量数据接入、判异、推送、人审、误报治理、任务关闭、月度 EVI。不要追求所有功能一次到位，先证明系统能稳定发现问题、推动处理、记录反馈。

### 阶段 2：平台化 SPC 任务模板

目标：把 SPC 项目经验抽象成可复制模板，包括数据接入清单、业务对象、本体、任务状态机、角色权限、Skill、报告、EVI 口径和交付检查表。这个阶段的成果不是又做一个功能，而是让第二个客户 / 第二条产线交付更快。

### 阶段 3：扩展参数治理与 FTA 知识资产化

目标：在 SPC 主线稳定后，把参数推荐作为工艺改善高价值模块，把 FTA 作为专家知识资产化模块。两者都接入统一任务模型、Skill Catalog、反馈和 EVI，而不是各自长成新烟囱。

### 阶段 4：形成 AI Native 工业任务控制面

目标：把任务模板、Skill Catalog、语义资产台账、受控写回网关、反馈飞轮、EVI 分级、组织运营模板产品化，形成跨质量、工艺、设备、供应链等任务流复用的工业 AI Native 任务闭环平台。

## 11. 最终判断

连山当前最值得坚持的方向，是把工业 AI 从“模型能力”推进到“任务闭环、反馈学习和经营归因”的系统工程。它已经有不少正确的底层选择：PG-first、Bundle-first、HITL、feedback、EVI、ontology、SPC / FTA / 参数推荐样板。这些都与 AI Native 任务闭环平台的愿景一致。

但连山下一阶段最需要避免两种偏差：第一，不要继续放大横向平台叙事，让客户听见一堆技术组件却不知道业务收益；第二，不要每个场景都做成一套独立系统，导致 IT、权限、知识、反馈、EVI 无法横向治理。

最优路径是：

1. 内部坚持做“面向制造高价值任务流的 AI Native 闭环平台”；
2. 对外先卖“制造质量与工艺改善的 AI 闭环系统”；
3. 用 SPC 质量异常闭环打穿第一个高频主战场；
4. 把每次交付沉淀成任务模板、业务对象、本体、Skill、反馈、评测集和 EVI 证据；
5. 再把 FTA、参数治理、边缘推理、数字员工逐步纳入同一个任务控制面。

一句话收束：

> 连山真正要卖的不是“一个 SPC 系统”“一个参数推荐工具”或“一个工业 Agent 工作台”，而是让制造企业把高价值质量与工艺任务流 AI Native 化的能力；但这件事必须从一个真实、高频、可度量、能闭环的场景开始证明。
