# 产品调研 02：Lattice 工程架构反推（从产品形态倒推实现框架）

> 调研日期：2026-10-10
> 前置文档：[01-产品调研.md](./01-产品调研.md)（产品定位/方法论/商业形态）
> 方法：基于公开产品行为描述（触发、自治运行、证据链、拓扑图、Living FMEA diff/审批、防篡改审计）做工程反推。**无任何代码/架构泄露来源，全部为推断**，按置信度分层标注。反推的价值不在"猜中 Lattice 怎么实现"，而在提炼一套可被 SPC 工作台（spc_dsh）直接复用的工程骨架。
> 特别关注两个问题：① 「故障树生长」的机制；② 「UI 上可直接交互的因果拓扑图」的机制——这两点是 Lattice 最值得 SPC 工作台参考的地方。

---

## 1. 为什么这个产品适合反推

Lattice 的公开材料行为描述密度极高：每一句 marketing 背后都对应一个明确的工程机制，没有一句是"玄学 AI"：

| 官网表述 | 锁定的工程机制 |
|---|---|
| claim→evidence 可追溯 + cryptographic provenance + immutable | 内容寻址的证据记录 + hash 链 |
| 调查分 Running / Needs attention 两态 | 调查是**长生命周期状态机**，且有等待外部输入的挂起态 |
| Living FMEA 的 inline diff + Approve All | 知识写回走"提案-审批"管道，不是直写 |
| TIME SAVED 9h48m（到分钟精度） | 每案计时是系统原生字段，非人工填报 |
| "investigation memory compounds" | 旧案结构化沉淀，且可被新案检索复用 |
| 多模态（照片/显微/视频/口述） | 证据平面有多模态归一 schema |

## 2. 总体框架：六个平面

```
┌─────────────────────────────────────────────────────┐
│ F. 价值层：每案计时 + 损失口径计算（TIME SAVED / $）   │
├─────────────────────────────────────────────────────┤
│ E. 记忆/反馈层：调查记忆检索 · 跨案模式挖掘 ·          │
│    Living FMEA（diff 提案 + 审批写回）                │
├─────────────────────────────────────────────────────┤
│ D. 交互平面：因果拓扑 Canvas（控制面，非报告视图）      │
│    + Needs-attention 收件箱                          │
├─────────────────────────────────────────────────────┤
│ C. 调查运行时：Conductor 循环（假设→动作→更新图→收敛） │
├─────────────────────────────────────────────────────┤
│ B. 图数据模型：append-only 拓扑变更日志（图=事件流投影）│
├─────────────────────────────────────────────────────┤
│ A. 证据平面：content-addressed 证据记录 · 多模态归一   │
│    · 向量索引 · 防篡改 hash 链                        │
└─────────────────────────────────────────────────────┘
```

### A 层：证据平面（置信度：直接证据强）

- **每条证据是一条不可变记录**：内容哈希做主键，记录来源系统、采集方式、时间戳、模态。
- **多模态归一**：文本/SQL 结果/图像/视频帧/操作工口述统一为一个 evidence schema（模态字段 + payload 引用），文本侧另建向量索引供检索。
- **防篡改审计链** = 追加写 + hash 链（每条记录指向前一条的哈希）。工程成本极低，与"audit-ready"卖点严格自洽——他们没有理由不做。
- 供应商门户/操作工数据请求到达时，也是作为新 evidence 进入同一平面（异构来源同构化）。

### B 层：图数据模型（置信度：强推断，全反推中最确定的一条）

**图不是存储对象，而是 append-only 变更日志（mutation log）的投影。** 这一个决定同时解决三件事：

1. **审计**：日志本身就是证据链（谁在何时把哪个因子从 candidate 改成 refuted）；
2. **UI 增量更新**：前端只消费事件流，图"实时生长"不需要轮询全量图；
3. **人机并发操作同一张图**：agent 和人的操作都是往同一个日志追加事件，不存在"两份图状态打架"。

不做事件溯源，"tamper-evident"和"实时生长的图"两件事都得另想昂贵办法。

### C 层：调查运行时（置信度：强推断）

Conductor 是被三个机制约束的标准 agentic 循环——三机制都有明确工程落点：

| 机制 | 工程落点 |
|---|---|
| Governance of Priors（0.05 秒灌满 500 加仑罐被流体力学先验否决） | **假设入图前的校验器**：物理/领域约束库；垃圾假设进不了图，但被否决这件事本身记录为一条带理由的假设事件——"垃圾从输入变成调查对象" |
| Active Inference（不确定性驱动的可测试查询） | **动作选择器**：每轮从候选动作（查 SQL / 调 CV / 发数据请求 / 问人）按"期望信息增益 ÷ 成本"排序，选最值得做的下一个。放热曲线 vs 阀门 Closed 物理不自洽 → 生成"验证信号链完整性"的调查目标，就是这个机制的输出 |
| Cross-Modal Verification | **一致性规则引擎**：跨模态断言（电信号/振动/下游压力三角互证）；矛盾不报错，而是生成新的调查目标 |
| Adversarial logic review | **结论自检 pass**：结案前强制一轮"找出推翻本结论所需的最小证据集"，作为报告附录字段 |

**循环骨架**：

```
while 未收敛:
    提出候选因子（来源：调查记忆检索 / 先验库 / 操作工陈述）
    → Prior 校验器过滤（否决的记录在案）
    → 入图为 candidate 节点（初始 confidence）
    → 动作选择器选信息增益最大的动作执行
    → 证据到达 → 贝叶斯式更新节点/边 confidence
    → 收敛检查：后验稳定？症状全覆盖？边际增益低于阈值？
挂起条件（→ Needs attention）：等待外部证据 / 需要人决策 / 置信度不足以结案
```

工具面：schema 感知的 text-to-SQL、CV 模型调用、调查记忆检索、**异步的数据请求**（向供应商/操作工发）。最后一个是异步动作，所以调查运行时必须有挂起态——这直接解释了收件箱的存在。

### D 层：交互平面（置信度：中等推断，详见 §4）

### E 层：记忆/反馈（置信度：强推断）

- **调查记忆 = 结构化的旧案图 + 结论**，不是聊天记录。新案开案时检索相似案例，把旧案拓扑作为先验种子（这是 "compounds" 的工程含义）。
- **跨案模式挖掘**：多张结案图的横向比对（同因子反复出现的弱信号预警）。
- **Living FMEA**：结案时把图与 FMEA 基线做 diff，生成提案（新失效模式 / SEV/RPN 修正），Approve All 走审批后写回。注意：写回的是**它自家的 FMEA 对象**，不是客户 QMS 里的对象（01 调研 §6.5 的判断在这里得到架构侧印证）。

### F 层：价值层（置信度：中等）

- 每案 trigger→closure 计时是系统原生（到分钟精度只能来自自动计时）；基线来自同类案例的历史分布。
- FINANCIAL IMPACT = 配置化损失口径 × 案例参数——与 spc_dsh 计划中"损失口径作为受治理语义配置（loss_basis）"是同一个决策，互相印证。

### 基础设施猜测（置信度：低，仅线索）

前端 Next.js（`_next` 静态 chunk 为直接证据）、app.runlattice.com 独立 SPA；"strict tenant-scoped DB policies" 的措辞像 Postgres RLS；后端大概率为 Python agent runtime；原始证据文件入对象存储。

## 3. 重点一：「故障树生长」的机制

**拓扑不是"加载一棵树然后遍历"，而是"每个案子从种子开始长一张图"。**

**1. 种子**：触发时只有失败描述 + 初始症状节点。先验来自三处——领域约束库、FMEA 库、**调查记忆里相似历史案例的拓扑**。

**2. 生长循环**：即 §2 C 层的循环骨架。生长发生在单案图上，与全局知识库隔离。

**3. 关键设计：refuted 节点不删除**。被否证的假设留在图上、标记状态。理由有三：① 审计要求（排除路径本身是结论的一部分——catheter 案例里"操作工被洗清嫌疑"就是 refuted 节点）；② 防止 agent 重复提出已否证假设（记忆）；③ 下次同类案件的种子更完整（否证经验也是先验）。

**4. 数据模型（可直接复用的部分）**：

```
graph_node:    investigation_id, factor,
               status ∈ {candidate, supported, confirmed, refuted, parked},
               confidence, evidence_refs[]
graph_edge:    investigation_id, cause_id, effect_id,
               confidence, supporting_refs[], refuting_refs[]
graph_mutation: append-only 事件日志
               （增/删/权变/状态变，每条带 hash 指向前一条）
evidence:      content_hash(主键), source, modality, payload_ref, ts
```

evidence 与 spc_dsh 现有的 event_id 血缘语义同构，可复用同一设计。

## 4. 重点二：UI 为什么能「直接交互」

Lattice 的图不是结案后的报告视图——**Canvas 本身是对话的控制面**。反推其交互协议：

1. **用户操作 = 一条 Turn**：
   - 点节点 → "深挖这个因子"成为 agent 下一轮输入；
   - 拖一条证据到节点上 → 关联动作；
   - 把节点标为"错了" → agent 被强制回应：要么接受否证（更新图），要么给出反驳证据。
   - 图上每个手势都进入同一个会话事件流——**人和 agent 操作的是同一张图的同一个 mutation 日志**。

2. **流式生长**：Running 状态下图实时长——新节点出现、边变粗（confidence 上升）、被否证的边变虚线。需要调查运行时到前端的 push channel（SSE/WebSocket）。

3. **Needs attention = 收件箱化的人审点**：agent 主动暂停（等外部证据 / 等决策 / 置信度不够）时，调查进收件箱亮灯；人处理一条，调查恢复运行。**HITL 不是"表单等人批"，是"自治体饿了来讨食"**——单向等待变成双向请求。

4. **概率的视觉语法**：
   - 边的粗细/颜色 = confidence；
   - 虚线 = refuted；
   - 黄色 = 高不确定，对应"数据缺口"节点——**UI 上直接看到"哪里还不知道"**，这是"判别力"的可视化，也是对 GIGO 反驳的产品化表达（数据缺口不阻塞流程，而是变成显式的数据请求）。

## 5. 映射到 SPC 工作台（spc_dsh）

这套架构映射到我们的栈出奇地顺——DSH 的事件流模型和 PG 单库正好接住。

### 5.1 Q20 故障树的角色重定位（最重要的启发）

**Pack 里的故障树不是"答案的容器"，而是先验种子。**

```
工单开单
  → 计算节点把 Pack 树实例化为该工单的调查图（investigation_graph_* 表）
  → 诊断过程中图自由生长（增节点/否证/权重更新）
  → 结案
  → 生长差异 vs Pack 基线 = diff 提案（新失效模式 / 权重修正 / 被否证路径）
  → 五 gate 审批 → 更新 Pack YAML → 管理时重新发布
```

这就是 Living FMEA 的私有部署版，且与 spc_dsh 的"管理时发布"管道完全同构——**feedback 诊断支飞轮的落地形态直接照这个抄**。

### 5.2 Canvas 即对话——DSH 的原生优势

工作台本身就是 DSH 插件：

- 加一个**图渲染插件**订阅图变更事件（连山遗产中的 PGMQ 现成可用作 push channel）；
- 用户在图上的每次操作作为 Turn 写进诊断会话；
- DSH 的 Session/Turn/Step append-only 模型**就是** mutation 日志的同构物（17 号文档分析过的"运行时事件流"，在这里找到了产品级用例）。

### 5.3 相对现有计划的最小增量

计算节点侧：
- 4 张表（graph_node / graph_edge / graph_mutation / evidence；evidence 可与 event_id 血运复用语义）；
- Conductor 式循环里的两个环节：动作选择按信息增益排序、结案前 adversarial 自检。

Pack schema：
- 树节点预留 `parent_factors[]`（为 DAG 化留门，不必现在实现——01 调研 §8.1 的建议在此有了具体落点）。

工作台侧：
- 一个拓扑 Canvas 插件 + Needs-attention 收件箱视图。

### 5.4 fail-open with disclosure 的可视化

数据不充分的节点不阻塞诊断（读侧 fail-open），而是：
- 图上标黄（数据缺口节点）；
- 自动生成数据请求清单（向操作工 / 供应商 / historian 要数）——即 §4.4 的"判别力可视化"。

写回侧仍维持 spc_dsh 既定的 fail-closed，两侧策略不冲突：**读侧带披露地开放，写侧关闭**。

---

## 6. 结论

Lattice 的工程核心可以收束为一句话：

> **图 = append-only 事件流的投影；人和 agent 通过同一个 mutation 流操作同一张图。**

生长、审计、交互、协作四件事被一个数据模型吃掉。SPC 工作台的栈（DSH 事件流 + PG + PGMQ + 管理时发布管道）能把这套全盘接住——缺的只是 4 张表、两个循环环节和一个 Canvas 插件。

附：反推结论对 01 调研未验证点的工程侧补充——"拓扑图是否可导出为机器可读格式"（01 §9.4）从架构上判断大概率可行（图有正式数据模型，导出只是序列化问题），实测时可一并验证。
