## 1. 一句话定位

**Lattice 是面向受监管制造业（医疗器械/制药 GMP/半导体/先进出行）质量团队的 AI 根因调查平台（AI Root Cause Investigation Platform）**——它不做过程监控，也不做通用 BI，而是把"缺陷发生之后的那次调查"本身变成一个结构化的、可审计的、由 agentic 推理引擎（The Conductor）驱动的系统，最终产出能扛住审计的 8D/CAPA/鱼骨图报告。公司自我定义为给制造业构建"reasoning layer"（推理层基础设施）。

关键划界：它**不是 SPC/实时监控**（我们场景的上游），而是**异常发生后的调查与结案系统**——恰好覆盖 spc_dsh 工单诊断闭环的全域。

## 3. 核心能力拆解（按官网结构）

### 3.1 The Conductor：agentic 推理引擎

调查的执行主体。官方描述其职责为：
- **识别证据缺口**（identifies evidentiary gaps）并主动发起数据请求；
- **综合人类证据与数字证据**——示例："acts funny after lunch"（操作工的口语化观察）→ 被引擎转化为 13:00–14:00 时间窗查询 → 关联西墙日照 → 2°C 机柜温升。这个例子是全站最能体现其产品哲学的一个；
- **维护跨案调查记忆**（investigation memory），逐案复利积累；
- **呈现概率化因果图**而非单一结论；
- 内置 SQL 查询、图像分析等工具，并带**对抗性逻辑审查**（adversarial logic review）——对自身假设做反驳式检查。

对照我们的框架：这相当于 spc_dsh 里"诊断支"的完整画像（推理 + 工具调用 + 证据链 + 自检），而它的"调查记忆跨案复利"正是我们 feedback 飞轮"诊断支→完善故障树"的 SaaS 版表述。

### 3.2 Lattice Root Cause：方法论（产品最重要的差异化）

博客研究文（2026-02-13）提出了对传统 RCA 的系统性反驳，值得完整记录，因为它直接挑战我们的故障树决策（spc_dsh Q20）：

- **"根因是一个方便的虚构（convenient fiction），故障拓扑才是工程现实"**——线性 RCA（5-Whys、单链鱼骨图）是对复杂系统的有损压缩；失败往往不是某个"坏节点"，而是**多个各自合规的因素构成的轨迹**（catheter 胶接案例：低粘度胶粘剂 + 55% 湿度尖峰 + 4 号线位于 HVAC 出风口下——三个因素单独都合规，组合才致失效，操作工被洗清嫌疑）。
- **反驳 GIGO 教条**："the system cannot doubt"——垃圾进垃圾出的前提是系统对输入无判别力；而专家的判别力（discernment）能把噪声当证据。**"不需要先解决数据质量问题，才能解决诊断问题。"** 这一条对我们的 Q21 数据充分度门禁是一个必须正面回应的反方论点（见 §8）。
- **Capacity Trap（容量陷阱）**：质量团队只来得及调查灾难性事件，弱信号积累成 FDA Warning Letter——48% 的警告信重复引用同一类问题的论断（另一篇博文标题）。
- **三受约束推理机制**：① Governance of Priors（先验治理：0.05 秒灌满 500 加仑罐被流体力学先验直接否决；垃圾从输入变成调查对象）；② Active Inference（不确定性驱动的可测试查询：放热曲线与阀门"Closed"信号物理不自洽 → 去验证信号链完整性）；③ Cross-Modal Verification（跨模态互证：泵的电信号 + 振动 + 下游压力三角验证）。
- **诊断能力即竞争优势**：CDMO 用 24 小时 vs 3 周的调查速度赢得技术转移合同——诊断容量"可直接兑现为收入"。

方法论落点：**failure topology 是树→图、root→topology、单路径→系统性遍历**的范式主张，产品形态上对应"multi-factor causal topology / non-linear causal modeling / probabilistic dependency mapping"。

### 3.3 触发与自治调查

- **Autostart**：基于触发器的调查自动发起（Jira 事件 / 文件出现 / webhook）——即"异常→工单→自动开始调查"零人工链路；
- **Autonomous Investigations 收件箱**：调查分 Running / Needs attention 两态在收件箱中运行，人只在需要时介入；
- 工程师始终在环：FAQ 明示 "Do our engineers remain in control? Yes."

### 3.4 证据连接层

- 系统：Slack（自动摄取线程上下文）、Jira（agentic 遍历+标签）、SharePoint（SOP/图纸/历史 8D）、Email（别名接入）；
- 运营：MES/QMS webhook 触发调查、SQL 原生连接器、**Supplier Portal（向供应商/操作工发起数据请求）**；
- 证据：批量上传（Excel/PDF/CSV/专有日志）、浏览器扩展截图、**图像与视频 CV**（缺陷照片/显微图/产线录像）——多模态是其明确卖点。

### 3.5 交付物与反馈闭环

- **报告导出**：PDF/DOCX 的 8D/CAPA/鱼骨图，带 TIME SAVED（示例 9h48m）与 FINANCIAL IMPACT（示例 $100,000）字段——即每案结案即出价值量化；
- **Living FMEA**：调查结论以 inline diff 写回 FMEA（新失效模式 / SEV/RPN 更新 / Approve All 审批）——这是我们"诊断支→知识库写回"的直接同形物；
- **跨批次/产线/工厂的模式检测**与 living process maps（复用调查记忆做横向预警）。

### 3.6 安全与合规架构

四层声明：租户隔离（严格 tenant-scoped DB 策略）；私有调查记忆（跨案复利但绝不外训 LLM）；防篡改审计链（immutable + cryptographic provenance）；企业合规（AES-256 / TLS 1.3 / **SOC 2 Type II 尚 In Progress**）。

### 3.7 商业交付（三阶段）

1. **Phase 01 免费试用（10 个工作日）**：两条路径——A. 引导式自助（给定裁剪数据集+工程师指南）；B. **重跑一个已结案（closed case）**，产出 side-by-side 对比报告；
2. **Phase 02 PoC（30 天，付费、按范围报价）**：接 QMS+沟通工具，接照片/显微/视频，接供应商+操作工请求，**做 baseline ROI 测量**；
3. **Phase 03 生产部署（企业合同）**：调查 system of record、审计就绪、跨厂模式检测。

## 4. 与相邻产品的差异（官网对照 + 我们视角）

| 维度 | Spreadsheets/QMS（ETQ、MasterControl） | ChatGPT | Lattice | spc_dsh（我们） |
|---|---|---|---|---|
| 结构化记录 | ✔ | ✘ | ✔ | ✔（工单/evi_record 业务表） |
| 主动取证 | ✘ | 部分 | ✔（agentic 数据请求） | ✔（诊断支工具调用） |
| 找"根因" | 表单模板 | 单轮叙事 | **拓扑+概率图** | 树形故障树（Q20） |
| 证据可追溯 | ✘ | ✘ | ✔（claim→evidence） | ✔（event_id 血缘） |
| 审计可用 | ✔（人工凑） | ✘ | ✔ | 设计目标 |
| 跨案学习 | ✘ | ✘ | ✔（investigation memory/Living FMEA） | ✔（feedback 三支飞轮） |
| 数据形态 | — | 文本 | **多模态（含 CV）** | SPC 数值为主 |
| 部署形态 | 混合 | 公有云 | **SaaS 多租户**（SOC2 进行中） | **私有部署**（PG/DSH 自持） |
| 触发源 | 人工 | 人工 | Jira/文件/webhook | SPC 判异自动触发 |
| 实时监控/前置预警 | ✘ | ✘ | 部分（模式检测） | ✔（SPC 主职） |

与 spc_dsh 的本质分野：
1. **上下游不同**：Lattice 接"缺陷已发生"的下游调查；我们自"判异触发"起，监控与诊断一体；
2. **部署信任模型不同**：Lattice 把客户质量数据放它的多租户云（SOC 2 还没拿下来）；我们私有部署、数据不出厂——这在国企/半导体客户处是结构性优势；
3. **因果建模不同**：Lattice 押注"拓扑/图"，我们当前押注"Pack 内树形故障树"——这是最需要正视的分歧（§8）。

## 5. 优势（就公开材料判断）

1. **方法论叙事极强且自洽**：从"root cause 是虚构"到三推理机制到 Capacity Trap，是一套能直接打动质量总监的完整叙事——卖的是"诊断容量"而非"软件功能"；
2. **价值口径内建于交付物**：每份报告带 TIME SAVED / FINANCIAL IMPACT，把 EVI 类经营归因做成了结案报告的原生字段，而不是事后的分析项目；
3. **销售动线设计老辣**：免费 10 天"重跑已结案例"的试用路径——零风险、可对比、自带 ROI 证明，比给沙盒 demo 强一个量级；PoC 阶段就做 baseline ROI 测量，把价值验证前置进销售流程；
4. **人机分工清晰**：工程师 in control、调查自治运行、Needs attention 收件箱——HITL 的产品化表达成熟；
5. **多模态证据**：显微图/视频 CV + 口语化操作工观察的融合，覆盖了纯数值系统看不见的证据面；
6. **团队配置对口**：CEO 管 agentic 推理，产品负责人是 15 年质量老兵+黑带——"AI+领域"双核齐备。

## 6. 短板与未验证点

1. **无公开客户案例**：全站无具名客户、无 logo 墙、无第三方评价；ROI 计算器（$460,800/年、3,840 工程小时）为自算示例；
2. **SOC 2 Type II 仅 In Progress**：对以"审计就绪"为核心卖点的受监管客户，这是当下硬伤；
3. **无私有化部署证据**：对半导体/国防类客户（其团队背景明显瞄准的方向）多租户 SaaS 形态存疑，未见 any on-prem/VPC 选项披露；
4. **方法论未经独立验证**：catheter/CDMO 案例均出自其博客叙事；"48% 警告信"数字未给原始出处链接（可能来自其另一篇博文，未见 FDA 数据引用）；
5. **与 QMS 的写回关系不明**：报告导出为 PDF/DOCX，但 CAPA 在 ETQ/MasterControl 里的回写闭环（而非导出）未见描述——Living FMEA 是其自家对象，不是客户 QMS 里的对象；
6. **中国制造业语境缺位**：连接器全是 Slack/Jira/SharePoint/Email，无 MES 国产生态（如我们在 lads/连山语境里的对接面）；供应商门户对国内供应链协同习惯的适配未知；
7. **极早期**：发布于 2026 年 1 月，两位高管规模的团队要同时支撑四条行业线，交付深度存疑；
8. **定价不透明**：无公开价格，PoC 报价 "scoped with team"，对中小制造企业门槛可能偏高。

## 7. 适用场景（判断）

- **高度匹配**：出口型医疗器械/制药 GMP 企业（审计压力真实、英文工具链齐备、愿为调查时长付费）；CDMO（调查速度直接换订单）；
- **中度匹配**：半导体失效分析（其内容营销明显在瞄准，7nm FinFET 案例文案存在，但数据出域可能卡在合规）；
- **低匹配/是我们的机会面**：国内制造业（工具链/语言/合规均不适配）；需要私有化与数据不出厂的客户；需要"监控→诊断"一体而非只做事后调查的客户。

## 8. 对我们当前项目的启发（重点）

按对 spc_dsh / 平台计划的冲击强度排序：

1. **Q20 故障树形态需重新审视（方法论级挑战）**：Lattice 的核心主张是"树是有损压缩，拓扑才是现实"。我们已决策树形故障树放 Pack YAML——短期不必推翻（树可解释、可治理、可被工艺工程师维护，是 v1 的正确选择），但应当：① 在 schema 里允许一个节点挂多个父因（即预留 DAG 化的演进路径，不必现在实现）；② 在 Q20 登记一条 known-open："故障树→因果拓扑"的升级问题，把 catheter 三合规因素案例作为反例测试用例——若 v1 树形无法表达，记录为树的已知边界而非视而不见。
2. **Q21 数据充分度门禁要正面吸收"判别力"论点**：Lattice 对 GIGO 的反驳（"不是先治数据再诊断，而是让系统有判别力，把噪声当证据"）直接质疑"等数据够了才开始"的门禁设计。我们的门禁不应是"数据不充分→拒绝诊断"，而应是"数据不充分→降级诊断+生成显式数据请求清单"。spc_dsh 的 fail-closed 用在写回和执行是对的，但**读侧诊断应该 fail-open with disclosure**（结论带置信度与缺口声明）。这一条建议落进 03 号计划的诊断支设计说明。
3. **价值口径做成结案原生字段（EVI 实操参考）**：TIME SAVED / FINANCIAL IMPACT 直接印在报告上，比"事后算 ROI 表"更有说服力。我们的 evi_record 应在工单关闭时同步生成一行"本单节省工时/影响金额"初值（人工可修正），而不是月度汇总才可见。
4. **"重跑已结案例"是值得抄袭的销售动线**：我们的三列表/production-evidence 策略可吸收：拿客户历史已关闭的 SPC 异常工单，用 spc_dsh 重跑一遍，产出 side-by-side 对比（当时的结案结论 vs 系统给出的证据链与拓扑）。这比 demo 沙盒可信得多，且不需要客户先接入实时数据。
5. **调查记忆跨案复利**：与我们的 feedback 飞轮同构，但其表述（investigation memory "compounds"）提醒我们：飞轮的价值不在"存了样本"，而在**下次调查能检索到上次的相关证据**。诊断支的检索面（相似工单/相似判异模式的历史调查）应作为 backlog 显式登记。
6. **对抗性逻辑审查**：Conductor 对自身假设做反驳式检查——对应我们诊断支可加一个廉价但高效的环节：结论生成后强制一轮"找出推翻本结论所需的最小证据集"自检，作为报告的附录字段。DSH 的 Skill/插件形态可以低成本承载这个。
7. **HITL 的产品化表达**："Running / Needs attention"收件箱 + "engineers remain in control" FAQ——我们的五 gate 设计在 UI 表达上可借鉴：工单不是"等审批的死状态"，而是"自治运行中，需要你时才亮灯"。
8. **多模态是中期护城河缺口**：Lattice 能读显微图和产线视频，我们不能。短期内 SPC 数值+事件流够用，但应在平台计划的知识层登记"缺陷图像证据"为中期输入类型（lads/计算支已有图像类算法基础）。

## 9. 后续需要实测/跟踪的问题

1. 试用申请实际能拿到什么（Phase 01 路径 A 的 guided dataset 内容）；**建议用非敏感裁剪数据集走一遍免费试用，直接体验 Conductor 的工具调用与报告质量**——这是性价比最高的下一步；
2. PoC 报价量级与合同结构（30 天 scoped proposal 的典型价位）；
3. Jira/SharePoint 之外的 MES 直连能力到底多深（SQL 连接器是否覆盖时序库/专有 MES）；
4. 拓扑图是否可导出为机器可读格式（对我们 Pack 故障树的互译可能性）；
5. SOC 2 进度与私有化/VPC 部署的 roadmap（其 NVIDIA Inception + 半导体叙事下，大概率会被客户倒逼出私有化选项——若出现，需重估其对我们目标市场的威胁）；
6. 是否进入中国市场或本地化（当前无任何迹象，时间窗口属于我们）；
7. 其"调查记忆绝不外训 LLM"承诺的合同化程度（受监管客户会问到，我们做私有部署销售时可用作对照话术）。

---

> 结论一句话：Lattice 用"故障拓扑+判别力"方法论把工业根因调查做成了 SaaS，其叙事与销售动线（结案即价值、重跑已结案例试用）值得我们直接吸收；其树形故障树之辩、数据充分度门禁之辩，恰好打在 spc_dsh 的 Q20/Q21 两个已知决策上——不必推翻 v1，但都应以"known-open + 演进路径"的方式登记在案。
