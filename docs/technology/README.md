# Technology Research Plan

这个目录用于沉淀知识复利系统、RAG、知识图谱、Agent 知识底座和大模型工程化相关的技术研究。

技术研究不只围绕某个工具展开，而是围绕“知识复利系统需要哪些技术能力”展开。

---

## 1. 大模型技术体系

目标：系统梳理通用大模型及其行业化适配、工程化部署、轻量化和应用编排能力，区分“必须掌握”“需要理解”“暂时只需知道”的能力边界。

覆盖内容：

- 通用大模型原理与能力边界；
- DeepSeek、文心一言、通义千问等主流大模型的应用差异；
- 大模型行业化适配技术；
- 有监督微调 SFT；
- 人类反馈强化学习 RLHF；
- Prompt 工程；
- 思维链 CoT 设计；
- 大模型量化；
- 模型剪枝；
- 模型蒸馏；
- 私有化部署技术储备。

重点问题：

- 哪些能力是知识复利工程师必须掌握的？
- 哪些能力更偏算法工程师或平台工程师？
- 行业化适配到底是靠微调、RAG、知识工程，还是业务流程重构？
- SFT / RLHF / Prompt / CoT 分别适合解决什么问题？
- 量化、剪枝、蒸馏和私有化部署对普通团队意味着什么？

计划产出：

```text
01-llm-technology-system.md
```

## 2. Prompt 工程与 CoT 设计

目标：单独研究 Prompt 工程和思维链 CoT 在知识复利系统中的作用。

之所以单拉出来，是因为 Prompt / CoT 更贴近业务人员和知识复利工程师的日常工作，不一定需要训练模型，但会直接影响 Agent 的行为边界、输出质量和流程稳定性。

重点问题：

- Prompt 如何表达角色、任务、约束、输入、输出和拒答边界？
- CoT 是否应该显式输出，还是只用于内部推理结构？
- 如何为不同业务场景设计稳定 Prompt 模板？
- 如何避免 Prompt 成为不可维护的“咒语”？
- Prompt、知识库、工具调用、评测集之间如何协同？

计划产出：

```text
02-prompt-and-cot-design.md
```

## 3. 行业化适配：SFT / RLHF / RAG / 知识工程的边界

目标：区分行业化适配中不同技术路线的适用场景，避免把所有问题都归结为“微调模型”。

重点问题：

- 什么问题适合 Prompt？
- 什么问题适合 RAG？
- 什么问题适合结构化知识库或知识图谱？
- 什么问题才需要 SFT？
- RLHF 在企业内部业务场景里是否现实？
- 行业化适配的核心瓶颈是模型能力、数据质量，还是业务知识治理？


## 4. Query 扩写

目标：研究用户问题在进入检索前，如何通过改写、扩写、拆解提升召回质量。

重点问题：

- 用户原始问题如何改写成更适合检索的查询？
- 是否需要生成多个 query？
- 如何避免 query 扩写引入用户没有表达的意图？
- 在中文知识库里，如何处理同义词、简称、口语化表达？
- Query 扩写应该发生在向量检索前，还是混合检索前？

计划产出：

```text
04-query-expansion.md
```

## 5. BGE 重排

目标：研究 BGE Reranker 在 RAG 链路中的作用，尤其是召回后排序、去噪和提升最终上下文质量。

重点问题：

- BGE Reranker 适合放在检索链路的哪个阶段？
- 向量召回 top-k 应该给多少，再由 reranker 压到多少？
- 中文知识库下 BGE 系列模型的效果如何？
- Reranker 对成本、延迟、准确率分别有什么影响？
- WeKnora / LightRAG / Reme 是否内置或支持 rerank？

计划产出：

```text
05-bge-reranker.md
```

## 6. Chunk 过滤剪枝

目标：研究文档切块之后，如何过滤低价值 chunk，减少噪音，提高检索质量。

重点问题：

- 哪些 chunk 应该被过滤？
- 目录、页眉页脚、重复免责声明、空泛段落是否应剔除？
- 如何识别过短、过长、无信息量、重复的 chunk？
- 是否需要按知识类型使用不同 chunk 策略？
- 如何在保留召回率的同时降低上下文污染？

计划产出：

```text

```

## 10. 知识图谱工程工具：DeepKE / Nebula Graph

目标：把 DeepKE 和 Nebula Graph 纳入知识图谱工程调研范围，区分“知识抽取工具”和“图数据库/图存储底座”在知识复利系统中的位置。

初步定位：

- DeepKE：更偏知识抽取，重点关注实体识别、关系抽取、事件抽取，以及如何从非结构化文本中生成结构化知识；
- Nebula Graph：更偏图数据库和图计算底座，重点关注大规模实体关系存储、图查询、图分析和工程化部署；
- WeKnora / LightRAG / Reme：更偏知识库、RAG、图谱增强检索和应用层体验。

重点问题：

- DeepKE 适合解决哪些实体/关系/事件抽取问题？
- DeepKE 与大模型抽取、传统 NLP 抽取、规则抽取相比，各自边界是什么？
- Nebula Graph 与 Neo4j 在部署、查询语言、生态、可视化、运维复杂度上有什么差异？
- 个人或小团队是否真的需要 Nebula Graph，还是 Neo4j / 内置图谱能力已经足够？
- DeepKE 抽取出的实体关系，如何进入 WeKnora、LightRAG、Reme 或自建知识图谱系统？
- 知识图谱在 RAG 中到底承担什么角色：增强召回、关系推理、上下文组织，还是可解释性展示？

计划产出：

```text
10-knowledge-graph-engineering-deepke-nebula-graph.md
```

## 技术能力分层

为了避免把所有技术都混在一起，暂时按三层理解。

### 第一层：业务侧必须掌握

这些能力更贴近知识复利工程和业务 BP：

- Prompt 工程；
- CoT / 推理结构设计；
- Query 扩写；
- 知识库结构设计；
- Chunk 策略理解；
- 评测集构造；
- Agent 任务边界设计；
- 业务流程嵌入。

### 第二层：技术 BP / AI Ops 需要深入理解

这些能力需要理解原理和工程影响，不一定每个人都要从零实现：

- RAG 链路设计；
- Reranker；
- 混合检索；
- 知识图谱；
- 实体关系抽取；
- 图数据库选型；
- 模型网关；
- 私有化部署方案；
- 成本、延迟、权限、审计。

### 第三层：平台/算法团队主责

这些能力更偏模型和基础设施团队：

- SFT；
- RLHF；
- 模型量化；
- 模型剪枝；
- 模型蒸馏；
- 大规模推理优化；
- GPU 集群管理。

知识复利工程师不一定要亲自做第三层，但需要理解它们的适用边界，避免把所有业务问题都误判为“需要训练模型”。

---

## 研究原则

1. 不只做概念介绍，要结合知识复利系统的实际需求。
2. 每个技术点都要回答：它解决 RAG/Agent 链路里的哪个具体问题。
3. 区分业务侧必须掌握、AI Ops 需要理解、平台/算法团队主责的能力。
4. 优先关注可落地、可验证、可维护的方案。
5. 对工具对比要关注数据可控性、可导出性和长期维护成本。
6. 所有结论尽量能服务于后续 WeKnora 个人知识库、家庭营养师 Agent 和组织记忆系统建设。
