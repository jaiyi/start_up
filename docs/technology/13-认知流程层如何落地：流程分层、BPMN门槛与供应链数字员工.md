# 13 · 认知流程层如何落地：流程分层、BPMN 门槛与供应链数字员工

> 目标：回答企业级 Agent 落地时最现实的三个问题：认知流程会不会越来越多并失控？BPMN / Workflow 如果让业务维护，技术门槛会不会太高？如果要分步骤落地数字员工，尤其以供应链管理为例，应该优先选择什么样的认知流程？

---

## 1. 一句话结论

认知流程层一定会很多，但不能全部 BPMN 化。

更合理的落地方式是：

```text
低风险认知任务先 Skill 化；
高频协同任务轻量 Workflow 化；
真正写业务系统、需要审批和审计的任务再 BPMN / Durable Workflow 化。
```

同时，BPMN 不应该直接暴露给普通业务人员维护。

更适合的方式是：

```text
业务维护规则、模板、SOP 和确认点；
平台维护流程引擎、状态机、权限、幂等和审计；
AI 辅助把自然语言 SOP 转成流程草稿；
流程专家和技术团队负责审核、上线和治理。
```

如果以供应链管理为例，数字员工应该优先落地：

```text
供应链知识问答；
订单 / 库存 / 供应商状态解释；
缺料原因分析；
采购订单延期跟进；
供应商表现报告；
库存异常诊断；
供应商风险预警；
质量异常协同。
```

而不是一开始就做：

```text
自动下采购订单；
自动修改价格；
自动冻结供应商；
自动调整生产计划；
自动承诺客户交期。
```

---

## 2. 为什么认知流程层会变多

企业里的很多工作，表面上看是人在“操作系统”，实际上人一直在做大量认知劳动。

例如：

```text
查数据；
查制度；
看异常；
判断原因；
整理证据；
询问责任人；
比较方案；
写报告；
催办协同；
复盘沉淀。
```

这些动作过去大多不在正式系统里。

它们散落在：

```text
Excel；
邮件；
微信群；
会议纪要；
个人经验；
口头沟通；
临时截图；
人工复制粘贴。
```

企业做数字员工以后，这些原本隐藏在系统外的认知工作会逐渐显性化。

所以认知流程层变多是必然的。

这不是坏事。

真正的问题不是“认知流程多不多”，而是：

```text
哪些值得沉淀？
哪些应该轻量化？
哪些必须流程化？
哪些只能作为辅助建议？
哪些需要人工确认？
哪些根本不适合自动化？
```

---

## 3. 认知流程不能全部 BPMN 化

很多企业一听到“流程”，就容易想到：

```text
是不是所有任务都要画 BPMN？
是不是每个分支都要建模？
是不是每个异常都要提前定义？
是不是业务人员以后都要学流程建模？
```

如果这么做，一定会失败。

因为认知工作和传统审批流不一样。

认知工作通常具有这些特点：

```text
模糊；
多变；
上下文依赖强；
例外情况多；
需要解释和证据；
需要人类经验；
不一定每一步都能标准化。
```

所以正确思路不是：

```text
把所有认知动作都画成 BPMN。
```

而是：

```text
按风险、频率、标准化程度和执行后果分层治理。
```

---

## 4. 认知流程的四层治理模型

可以把企业 Agent 的认知任务分成四层。

```text
L1 问答型认知任务
L2 分析型认知任务
L3 协同型认知任务
L4 闭环型业务流程
```

这四层不是技术炫技，而是为了避免过度设计。

---

### 4.1 L1：问答型认知任务

典型问题：

```text
采购制度怎么规定？
供应商准入需要哪些材料？
安全库存是什么意思？
这个异常指标怎么解释？
某个流程应该找谁审批？
```

这类任务主要是“查知识 + 解释”。

推荐技术形态：

```text
RAG + Prompt + 权限过滤 + 引用来源
```

不需要 BPMN。

它的关键不是流程，而是：

```text
知识是否准确；
权限是否正确；
引用是否可追溯；
回答是否不编造。
```

---

### 4.2 L2：分析型认知任务

典型问题：

```text
帮我分析这个供应商为什么最近交付变差；
帮我解释这个物料为什么缺货；
帮我对比这三个供应商的风险；
帮我生成本周采购异常报告；
帮我判断库存预警的主要原因。
```

这类任务不只是问答，而是需要：

```text
查数据；
查知识；
做归因；
组织证据；
生成建议；
形成报告。
```

推荐技术形态：

```text
Skill + Tool Calling + 结构化输出 + 评测集
```

如果只是辅助人判断、没有直接写业务系统，可以先不做 BPMN。

它的关键是：

```text
分析路径稳定；
证据链完整；
不确定点清楚；
建议可执行；
结果可评测。
```

---

### 4.3 L3：协同型认知任务

典型问题：

```text
供应商交付延期，需要通知采购、计划、仓库、销售；
库存低于安全线，需要收集需求、在途和替代料信息；
质量异常需要召集质量、采购、供应商一起处理；
缺料风险需要持续跟踪责任人反馈。
```

这类任务开始涉及：

```text
多人；
多系统；
多时间点；
等待反馈；
超时升级；
责任人跟踪。
```

推荐技术形态：

```text
轻量 Workflow / 状态机 / 任务看板 / LangGraph Checkpoint / Temporal Workflow
```

不一定一开始就需要完整 BPMN，但必须有显式状态。

它的关键是：

```text
当前到哪一步；
谁需要反馈；
哪些信息已经收集；
下一步谁确认；
超时如何升级；
执行过程是否可追踪。
```

---

### 4.4 L4：闭环型业务流程

典型问题：

```text
创建采购订单；
变更供应商等级；
冻结供应商；
批准紧急采购；
调整安全库存；
发起索赔；
触发付款拦截；
关闭质量问题单。
```

这些动作会真实改变企业系统里的业务状态。

推荐技术形态：

```text
BPMN / 固定状态机 / Temporal / Camunda / Flowable / 企业现有 OA 或 ERP 流程引擎
```

必须具备：

```text
权限；
审批；
人工确认；
幂等；
审计；
恢复；
异常处理；
回滚策略。
```

这类流程不能让 LLM 自己决定怎么走。

LLM 可以提交 signal，但流程推进必须由 Workflow Engine 决定。

---

## 5. 一张表判断应该用什么技术形态

| 任务类型 | 典型动作 | 推荐形态 | 是否需要 BPMN |
|---|---|---|---|
| 看一看 | 查制度、查状态、解释口径 | RAG / Query Tool | 否 |
| 想一想 | 分析原因、生成报告、比较方案 | Skill / Agent Tool Chain | 通常否 |
| 推一推 | 通知、催办、收集反馈、跟踪责任人 | 轻量 Workflow | 视复杂度而定 |
| 写进去 | 创建订单、修改主数据、审批、冻结、关闭问题单 | BPMN / Durable Workflow | 是 |

可以记成：

```text
只读解释 → Prompt / RAG；
结构化分析 → Skill；
多人协同 → 轻量 Workflow；
写业务数据 → 严格 Workflow / BPMN。
```

## 6. BPMN 由业务维护，门槛为什么高

BPMN 是很强的流程建模语言，但它对普通业务人员并不天然友好。

业务人员熟悉的是：

```text
制度；
经验；
判断规则；
例外处理；
谁负责；
什么时候升级；
什么情况下不能做。
```

而 BPMN 需要理解：

```text
Start Event；
End Event；
User Task；
Service Task；
Exclusive Gateway；
Parallel Gateway；
Message Event；
Timer Event；
Boundary Event；
Compensation；
Error Event。
```

这已经是技术建模语言。

所以如果要求业务人员直接维护底层 BPMN，很容易出现：

```text
流程图画得出来，但跑不起来；
主路径清楚，但异常路径缺失；
审批节点有了，但权限和幂等没设计；
表面低代码，实际还是 IT 团队兜底；
流程版本混乱，线上问题难追溯。
```

因此，企业不应该简单把 BPMN 编辑器丢给业务人员。

更好的目标是：

```text
让业务维护业务语义；
让平台承接执行语义。
```

---

## 7. 降低 BPMN 门槛的六条路径

### 7.1 路径一：业务维护流程模板，而不是底层 BPMN

业务人员适合维护这种模板：

```yaml
流程名称: 供应商交付延期处理

触发条件:
  - PO 行项目预计交期晚于承诺交期
  - 延期天数 >= 3 天

处理步骤:
  - 收集订单、物料、供应商、在途库存信息
  - 判断是否影响生产计划
  - 如果影响生产，通知计划员和采购员
  - 如果延期超过 7 天，升级给供应链经理
  - 生成延期分析报告
  - 等待责任人确认处置方案

人工确认点:
  - 是否接受延期
  - 是否切换供应商
  - 是否发起索赔

禁止动作:
  - Agent 不能直接修改 PO 交期
  - Agent 不能直接冻结供应商
  - Agent 不能直接承诺客户交付时间
```

平台再把它转换成：

```text
BPMN；
状态机；
Workflow DSL；
工具调用链；
权限配置；
测试用例；
评测样例。
```

核心思想是：

> 业务维护“人能看懂的流程语义”，不是维护“引擎能执行的流程细节”。

---

### 7.2 路径二：流程骨架平台化，业务只配置变量

很多认知流程其实有相似骨架。

例如异常处理类流程：

```text
触发异常
  ↓
收集信息
  ↓
判断影响
  ↓
生成建议
  ↓
人工确认
  ↓
通知责任人 / 创建工单
  ↓
跟踪反馈
  ↓
关闭与复盘
```

平台可以沉淀为模板。

业务只配置：

```text
异常类型；
触发条件；
需要查询的数据；
判断规则；
通知对象；
升级阈值；
确认点；
允许动作；
输出报告模板。
```

这样比让业务从零画 BPMN 更现实。

---

### 7.3 路径三：DMN 交给业务维护，BPMN 由平台封装

很多时候，业务经常变化的不是流程骨架，而是判断规则。

例如供应链里经常变化的是：

```text
延期几天算严重；
金额超过多少要升级；
关键物料如何定义；
供应商风险评分多少要复核；
库存低于多少要预警；
什么客户订单优先保障。
```

这些更适合放在 DMN / 决策表里。

示例：

| 延期天数 | 物料等级 | 是否影响生产 | 处理等级 | 目标角色 |
|---|---|---|---|---|
| 1-2 天 | 普通 | 否 | 低 | 采购员 |
| 3-7 天 | 关键 | 是 | 中 | 计划员 + 采购员 |
| > 7 天 | 关键 | 是 | 高 | 供应链经理 |

推荐分工：

```text
BPMN 管大流程骨架；
DMN 管业务判断规则；
Prompt / Skill 管认知分析；
Tool 管数据查询和动作执行；
Policy 管权限；
Human Task 管关键确认。
```

这样业务人员主要维护“规则表”，而不是复杂流程图。

---

### 7.4 路径四：AI 辅助生成流程草稿，但不能直接上线

AI 可以帮助业务人员把自然语言 SOP 变成流程草稿。

例如业务输入：

```text
当供应商延期超过 3 天时，需要判断是否影响生产。
如果影响生产，通知计划员。
如果超过 7 天，需要升级给供应链经理。
```

AI 可以生成：

```text
候选流程步骤；
候选 BPMN；
候选 DMN；
需要的工具清单；
输入输出字段；
异常分支；
人工确认点；
评测样例。
```

但必须明确：

> AI 生成的是流程草稿，不是可直接上线的流程资产。

上线前必须经过：

```text
业务确认；
流程专家审核；
权限检查；
测试；
灰度；
回滚方案。
```

---

### 7.5 路径五：建立流程资产中心

如果没有统一资产中心，认知流程会很快失控。

流程资产中心至少要管理：

```text
流程目录；
流程版本；
适用场景；
负责人；
输入输出契约；
依赖工具；
依赖知识库；
依赖 DMN；
权限策略；
评测集；
上线状态；
历史执行效果；
失败案例。
```

每个流程上线前都应该回答：

```text
这个流程解决什么问题？
谁可以触发？
输入是什么？
输出是什么？
会调用哪些工具？
会不会写业务系统？
哪些节点需要人工确认？
失败后如何恢复？
如何评测效果？
谁对流程质量负责？
```

这就是把流程从“项目交付物”变成“组织资产”。

---

### 7.6 路径六：把流程分成 Draft / Pilot / Production 三种状态

不要让所有流程一创建就进入生产。

推荐流程生命周期：

```text
Draft：草稿，只用于讨论和内部测试；
Pilot：试点，只对小范围用户开放，关键动作人审；
Production：生产流程，具备权限、审计、恢复和评测；
Deprecated：废弃流程，只读保留历史记录。
```

每次版本升级都要记录：

```text
改了什么；
为什么改；
影响哪些用户；
评测是否通过；
如何回滚。
```

## 8. 业务和技术如何分工

推荐分工如下：

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 业务专家 | 业务规则、SOP、异常分类、判断标准、确认点 | 底层引擎实现 |
| 流程架构师 | 流程拆解、状态建模、异常分支、审批边界 | 具体业务数据接口 |
| AI / Agent 产品经理 | 数字员工角色、对话体验、任务边界、反馈闭环 | 直接写底层流程代码 |
| 平台工程师 | Workflow Engine、Tool Runtime、权限、审计、幂等 | 业务规则拍板 |
| 数据工程师 | 数据接入、指标口径、主数据、知识图谱 | 流程最终决策 |
| 安全 / 风控 | 权限边界、审计、合规、敏感动作 | 日常流程配置 |
| 一线用户 | 使用、反馈、标注失败案例 | 维护复杂流程模型 |

一句话：

```text
业务定义“应该怎么做”；
平台保证“只能这么做”；
Agent 帮忙“更快更自然地做”；
Workflow 负责“可靠地推进”。
```

## 9. 哪些认知流程适合优先落地

优先选择的流程应该具备这些特征：

```text
高频；
痛点明显；
人工重复；
数据相对可获得；
规则相对清楚；
输出容易验证；
动作风险可控；
可以先人审后执行；
失败代价不高；
能积累知识和样例。
```

不适合第一阶段落地的流程通常是：

```text
强谈判；
强博弈；
高金额自动决策；
高法律风险；
数据质量很差；
规则高度依赖个人关系；
组织权责不清；
系统接口缺失；
失败代价极高。
```

可以用下面的矩阵打分。

| 维度 | 高优先级特征 | 低优先级特征 |
|---|---|---|
| 频率 | 每天 / 每周大量发生 | 一年发生几次 |
| 人工耗时 | 需要大量查数、整理、沟通 | 几分钟就能完成 |
| 规则清晰度 | 有 SOP、制度、历史案例 | 完全靠个人经验 |
| 数据可得性 | 数据在 ERP / WMS / SRM / MES 中可查 | 数据靠口头沟通 |
| 风险 | 先生成建议，人确认后执行 | 自动执行高风险动作 |
| 价值 | 可减少等待、漏判、重复沟通 | 只是锦上添花 |
| 可评测性 | 有明确正确答案或专家标准 | 很难判断好坏 |
| 复用性 | 多部门、多物料、多供应商都能用 | 只适合极小场景 |

优先做总分高的流程。

## 10. 供应链为什么适合做数字员工

供应链管理天然适合做企业级 Agent，因为它具备几个特点：

```text
跨系统；
跨部门；
多角色；
多异常；
多规则；
大量人工协调；
大量数据查询；
大量经验判断。
```

供应链常见系统包括：

```text
ERP；
SRM；
WMS；
MES；
TMS；
PLM；
质量系统；
财务系统；
邮件 / IM / 工单系统。
```

传统 IT 系统擅长记录状态，但不擅长回答：

```text
为什么会这样？
影响有多大？
应该先找谁？
有哪些证据？
下一步应该怎么处理？
类似问题以前怎么解决？
这次处理结果能不能沉淀成知识？
```

这正是数字员工和认知流程层可以发挥价值的地方。

## 11. 供应链数字员工优先场景一：供应链知识问答

### 11.1 场景

用户问：

```text
供应商准入需要哪些材料？
紧急采购流程怎么走？
采购订单变更需要谁审批？
库存冻结是什么意思？
供应商绩效评分怎么算？
```

### 11.2 推荐形态

```text
RAG + 权限控制 + 引用来源 + 结构化回答
```

### 11.3 为什么适合先做

```text
风险低；
启动快；
用户容易接受；
可以快速验证知识库质量；
能减少重复咨询。
```

### 11.4 注意事项

```text
必须引用来源；
制度冲突时要提示冲突；
没有依据时不能编造；
不同角色看到的制度可能不同。
```

### 12.4 价值

```text
降低系统使用门槛；
把复杂状态解释清楚；
为后续异常诊断打基础。
```

## 13. 供应链数字员工优先场景三：缺料原因分析

### 13.1 场景

用户问：

```text
为什么这个物料今天又缺货？
这次缺料会影响哪些生产订单？
有没有替代料？
责任主要在供应商、计划还是库存？
```

### 13.2 认知工作

Agent 需要查询：

```text
当前库存；
安全库存；
库存占用；
在途采购；
采购订单 ETA；
供应商交付记录；
BOM；
生产计划；
替代料；
质检状态；
历史缺料记录。
```

### 13.3 推荐形态

第一阶段：

```text
Skill + 多工具查询 + 结构化诊断报告
```

第二阶段：

```text
缺料协同 Workflow + 人工确认 + 责任人跟踪
```

### 13.4 输出结构

```text
结论：
该物料缺货主要由供应商延期和质检未放行叠加导致。

关键证据：
1. PO-10023 原计划 9 月 10 日到货，当前预计 9 月 18 日。
2. 供应商 A 近 30 天准交率从 92% 降到 76%。
3. 当前仓库可用库存为 120 件，低于安全库存 300 件。
4. 有 80 件已到货但处于 IQC 待检状态。

风险：
如果 9 月 18 日前无法放行，将影响 9 月 20 日生产计划。

建议：
1. 催促供应商确认最新 ETA；
2. 通知 IQC 优先检验已到货批次；
3. 检查替代料是否可用；
4. 如延期超过 3 天，发起供应链异常协同流程。
```

## 14. 供应链数字员工优先场景四：采购订单延期跟进

### 14.1 场景

采购员每天需要跟进：

```text
哪些 PO 快到期？
哪些供应商没确认？
哪些订单延期？
哪些订单数量不一致？
哪些需要催办？
```

### 14.2 认知工作

Agent 可以：

```text
扫描 PO；
识别异常；
按供应商聚合；
判断风险等级；
生成催办话术；
提醒采购员；
记录跟进状态。
```

### 14.3 推荐形态

早期：

```text
定时任务 + Agent 分析 + 人工确认发送
```

成熟后：

```text
自动生成催办任务；
自动创建供应商协同工单；
超时自动升级；
进入 Workflow。
```

### 14.4 为什么适合

```text
频率高；
规则相对清楚；
动作可以先人工确认；
业务价值容易体现；
能快速减少采购员重复劳动。
```

## 15. 供应链数字员工优先场景五：库存异常诊断

### 15.1 场景

用户问：

```text
为什么账实不一致？
为什么安全库存一直报警？
为什么有库存但生产还是缺料？
为什么这批货被冻结？
```

### 15.2 认知工作

```text

人工确认。
```

## 16. 供应链数字员工优先场景六：供应商风险监控

### 16.1 场景

自动监控供应商表现：

```text
准交率下降；
质量不良率上升；
价格异常波动；
响应变慢；
投诉增加；
区域风险；
财务风险；
合规风险。
```

### 16.2 认知工作

Agent 可以：

```text
整合交付、质量、价格、投诉、外部风险；
生成供应商风险摘要；
识别风险趋势；
建议是否进入观察名单。
```

### 16.3 推荐形态

早期：

```text
周报 / 月报生成助手
```

成熟后：

```text
风险评分；
供应商预警；
供应商整改流程；
供应商冻结 / 替换建议。
```

其中，冻结供应商、替换供应商、调整采购份额必须走正式审批流程。

## 17. 供应链数字员工优先场景七：会议纪要与行动项跟踪

### 17.1 场景

供应链会议常见问题：

```text
会议结论没人沉淀；
行动项没人跟；
责任人不清；
历史决策找不到；
同样问题反复讨论。
```

### 17.2 数字员工可以做什么

```text
整理会议纪要；
抽取问题、责任人、截止时间；
关联订单、供应商、物料；
生成待办；
跟踪完成情况；
下次会议自动回顾。
```

### 17.3 为什么适合先做

```text
低风险；
高频；
用户容易接受；
可以积累组织知识；
非常适合知识复利。
```

## 18. 第一阶段不建议做什么

供应链里有些动作风险太高，不适合第一阶段自动化。

例如：

```text
自动下采购订单；
自动修改采购价格；
自动切换供应商；
自动冻结供应商；
自动承诺客户交期；
自动调整生产计划；
自动调整安全库存参数；
自动处理大额索赔；
自动批准付款。
```

这些可以作为长期目标，但早期应该采用：

```text
Agent 生成建议；
人确认；
Workflow 执行；
系统记录；
结果评测。
```

## 19. 供应链数字员工五阶段路线图

### 19.1 阶段一：只读型 Copilot

目标：

```text
先让数字员工会查、会解释、会总结。
```

典型能力：

```text
制度问答；
订单状态查询；
库存解释；
供应商表现总结；
异常原因初步分析；
会议纪要整理。
```

技术形态：

```text
RAG；
SQL / API 查询工具；
结构化报告 Prompt；
权限过滤；
引用来源。
```

核心价值：

```text
减少查资料和查系统时间。
```

---

### 19.2 阶段二：结构化分析型 Agent

目标：

```text
让数字员工能输出稳定的分析结果和建议。
```

典型能力：

```text
缺料原因分析；
订单延期归因；
供应商风险评分解释；
库存异常诊断；
质量异常初筛。
```

技术形态：

```text
Prompt + Skill；
结构化输出；
工具链；
规则表；
知识图谱；
评测集。
```

核心价值：

```text
减少人工分析时间；
提升判断一致性；
沉淀专家经验。
```

---

### 19.3 阶段三：人审型协同流程

目标：

```text
让数字员工能推动人协同，但关键动作仍由人确认。
```

典型能力：

```text
发起供应商延期处理；
生成催办任务；
创建异常工单草稿；
整理处理方案；
提醒责任人；
跟踪反馈。
```

技术形态：

```text
轻量 Workflow；
任务状态；
消息通知；
人工确认点；
幂等；
审计。
```

核心价值：

```text
减少跨部门沟通成本；
减少遗漏；
提升响应速度。
```

---

### 19.4 阶段四：受控闭环 Workflow

目标：

```text
让稳定流程自动推进，但关键节点保留审批。
```

典型能力：

```text
供应商延期闭环；
库存预警闭环；
质量异常闭环；
采购变更闭环；
供应商整改闭环。
```

技术形态：

```text
BPMN / Temporal / FixedWorkflow；
DMN 决策表；
Tool Runtime；
Policy Guard；
Human Task；
Trace；
回滚和恢复。
```

核心价值：

```text
把认知工作纳入正式流程资产。
```

---

### 19.5 阶段五：策略优化型数字员工

目标：

```text
让数字员工参与持续优化，而不是只处理单次任务。
```

典型能力：

```text
识别反复延期供应商；
发现安全库存参数不合理；
发现采购策略缺陷；
建议供应商分层；
建议备选供应商；
评估需求预测偏差。
```

技术形态：

```text
数据分析；
知识图谱；
评测反馈；
策略仿真；
人类专家审批；
长期记忆。
```

核心价值：

```text
从自动处理问题，升级为持续优化供应链能力。
```

## 20. 供应链场景优先级建议

| 优先级 | 认知流程 | 原因 |
|---|---|---|
| P0 | 供应链知识问答 / 制度问答 | 低风险，快速建立信任 |
| P0 | 订单 / 库存 / 供应商状态查询解释 | 高频，数据价值明显 |
| P1 | 缺料原因分析 | 痛点强，跨系统查询多 |
| P1 | PO 延期跟进助手 | 高频重复，容易产生业务价值 |
| P1 | 供应商表现周报 / 月报 | 稳定输出，适合评测 |
| P2 | 库存异常诊断 | 价值高，但数据口径要清楚 |
| P2 | 供应商风险预警 | 需要较好指标体系 |
| P2 | 质量异常协同 | 涉及多部门，适合 Workflow |
| P3 | 自动催办 / 自动建工单 | 需要权限和审计 |
| P3 | 供应商整改闭环 | 需要正式流程 |
| P4 | 自动采购决策 / 自动供应商切换 | 高风险，后期再做 |

## 21. 如果只能选第一个供应链数字员工

如果只能选一个，我建议先做：

> 供应链异常诊断与协同助手。

原因是它能覆盖多个高频痛点：

```text
缺料；
延期；
库存不足；
质检未放行；
供应商风险；
订单异常；
生产影响。
```

第一个版本不要追求全自动闭环。

推荐链路是：

```text
用户问问题
  ↓
Agent 查询订单 / 库存 / 在途 / 供应商 / 质检 / 计划
  ↓
生成结构化异常分析
  ↓
列出证据链
  ↓
给出建议动作
  ↓
用户选择是否发起协同流程
  ↓
Workflow 创建任务 / 通知责任人 / 跟踪状态
```

这样既有明显价值，又不会一开始就碰高风险自动决策。

## 22. 从“LLM 壳”到“认知流程资产”的差异

如果只是 LLM 壳，系统做的是：

```text
用户问一句；
模型答一句。
```

如果是认知流程层，系统沉淀的是：

```text
异常识别能力；
跨系统查证能力；
证据链组织能力；
专家判断模板；
协同流程；
处置结果；
失败样例；
知识更新；
评测数据。
```

这才是数字员工的真正价值。

它不是把旧系统包装得更会聊天，而是把原来散落在人脑、Excel、微信和会议里的认知劳动，逐步变成企业可复用、可审计、可改进的能力资产。

## 23. 落地时的治理清单

每个认知流程上线前，都应该检查：

```text
这个任务是否高频？
是否有明确业务价值？
是否有足够数据来源？
是否有清晰输出标准？
是否有专家可以评审？
是否能先只读或人审？
是否涉及写业务系统？
是否需要 Workflow？
是否需要 DMN？
是否需要人工确认？
是否有权限边界？
是否有审计日志？
是否有失败恢复机制？
是否有评测集？
是否有版本负责人？
```

如果这些问题都答不清楚，不要急着自动化。

## 24. 最终原则

第一：

```text
认知流程会很多，所以不能全部 BPMN 化，要按风险和标准化程度分层治理。
```

第二：

```text
BPMN 不应该直接暴露给普通业务人员，而应该通过业务模板、DMN 决策表、低代码配置、AI 辅助生成和平台审核来维护。
```

第三：

```text
数字员工应优先落地高频、只读或人审、跨系统信息整合多、人工认知负担重、可评测的流程。
```

第四：

```text
供应链数字员工最适合从异常诊断、PO 跟进、库存解释、供应商风险报告和会议行动项跟踪开始。
```

最后可以这样理解：

```text
Prompt / RAG 解决“会不会回答”；
Skill 解决“会不会分析”；
Tool 解决“能不能查证”；
Workflow 解决“能不能可靠推进”；
DMN 解决“判断规则能不能配置”；
BPMN 解决“正式流程能不能审计和恢复”；
数字员工解决“企业认知劳动能不能沉淀和复利”。
```
