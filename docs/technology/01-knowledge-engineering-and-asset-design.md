# 01 · 知识工程与知识资产设计

## 1. 这个模块解决什么问题

知识复利系统的起点不是模型，而是知识资产设计。

这个模块回答：

```text
什么知识值得进入系统？
知识应该如何分类、结构化、治理和更新？
如何让知识既能被人阅读，也能被 Agent 调用？
```

如果知识本身没有被设计好，RAG 和 Agent 只会更快地暴露混乱。

---

## 2. 它在知识复利系统中的位置

```text
业务现场
  ↓
一手信息 / 数据证据 / 经验案例
  ↓
知识资产设计
  ↓
RAG / 图谱 / Agent / Workflow
  ↓
反馈修正
```

知识工程位于所有 AI 应用之前，是把组织经验变成可复用资产的前置层。

## 4. 典型技术路线

| 路线 | 适合场景 | 风险 |
|---|---|---|
| 结构化 Markdown | 个人 / 小团队知识库、家庭知识库、轻量 SOP | 依赖人工规范，规模大后治理成本上升 |
| Wiki / 文档系统 | 团队知识沉淀、流程规范、培训材料 | 容易变成没人看的文档库 |
| 表格 / 数据库 | 业务对象、清单、状态、指标、反馈记录 | 容易割裂文本语境 |
| 知识卡片 | 菜谱、案例、问题、方案、规则等可复用单元 | 需要设计模板和元数据 |
| 知识图谱 | 实体关系复杂、需要关系查询和路径解释 | 容易过度设计 |
| Agent Memory | 个性化、长期偏好、任务状态 | 容易和正式知识库边界混乱 |

## 5. 推荐调研的开源框架 / 工具

| 类型 | 候选项目 | 背景/特点 | 后续验证点 |
|---|---|---|---|
| Wiki / 文档 | Outline | 现代团队 Wiki，开源，适合组织知识库 | 权限、导出、中文体验、部署成本 |
| Wiki / 文档 | Wiki.js | 开源 Wiki，生态成熟 | 权限模型、插件、导入导出 |
| Wiki / 文档 | BookStack | 结构清晰，适合手册型知识库 | 层级是否过强、移动端体验 |
| 静态文档 | Docusaurus / MkDocs Material | 适合工程化文档和版本管理 | 非技术人员维护成本 |
| 个人知识库 | Obsidian / Logseq | 本地优先、双链、Markdown 友好 | 团队协作和权限不足 |
| 数据资产 | OpenMetadata / DataHub | 面向数据目录、血缘、元数据治理 | 是否适合小团队、部署复杂度 |
| 文档解析 | Unstructured / LlamaIndex Readers / LangChain Document Loaders | 连接文档到 RAG 链路 | 中文文档、PDF、表格解析质量 |
| 知识库产品 | WeKnora / RAGFlow / Dify Knowledge | 可作为知识库产品形态参考 | 数据可导出、治理能力、Agent 连接 |

> 备注：后续调研时要补充 GitHub stars、维护活跃度、背后组织、最新 release 和社区成熟度。

## 6. 适合个人 / 小团队 / 企业的落地方式

| 场景 | 推荐起点 |
|---|---|
| 个人验证 | Markdown 知识卡片 + Obsidian / Git 管理 + 轻量 RAG |
| 家庭知识库 | 结构化 Markdown + 标签 + 反馈记录 |
| 小团队组织记忆 | Wiki / WeKnora / RAGFlow + 权限 + 反馈机制 |
| 企业知识复利系统 | 知识资产模型 + 数据证据 + 权限治理 + RAG / Agent / 评测闭环 |

## 7. 与其他模块的关系

- 是 RAG 链路的知识源；
- 是知识图谱建模的输入；
- 是 Agent 任务执行的上下文；
- 是评测集构造的依据；
- 是治理和权限设计的对象。
