# 07 · 知识图谱工程：DeepKE / Nebula Graph / Neo4j

## 1. 这个模块解决什么问题

知识图谱不是为了“看起来高级”，而是为了解决实体关系复杂、上下文依赖强、需要关系追踪和可解释展示的问题。

这个模块回答：

```text
什么时候需要知识图谱？
如何从文本中抽取实体、关系和事件？
图数据库在知识复利系统中到底承担什么角色？
```

---

## 2. 它在知识复利系统中的位置

```text
非结构化知识 / 业务数据
  ↓
实体、关系、事件抽取
  ↓
图数据库 / 图谱结构
  ↓
GraphRAG / 关系查询 / 路径解释
  ↓
Agent 调用 / 人工分析 / 可视化
```

知识图谱位于“知识资产结构化”和“RAG / Agent 增强”之间。

## 4. 典型技术路线

| 路线 | 适合场景 | 风险 |
|---|---|---|
| LLM 抽取 | 快速从文本中抽实体关系 | 稳定性、成本、幻觉 |
| DeepKE / NLP 抽取 | 专业抽取任务、可训练模型 | 数据标注和训练成本 |
| 规则抽取 | 格式稳定、规则明确 | 泛化能力弱 |
| Neo4j | 中小规模图谱、生态成熟、可视化友好 | 商业版能力、扩展成本 |
| Nebula Graph | 大规模图存储和图计算 | 运维和学习成本更高 |
| GraphRAG | 复杂关系增强检索 | 构图质量决定效果，成本较高 |

## 5. 推荐调研的开源框架 / 工具

| 类型 | 候选项目 | 背景/特点 | 后续验证点 |
|---|---|---|---|
| 知识抽取 | DeepKE | 浙江大学等背景，面向知识抽取 | 中文效果、维护活跃度、LLM 结合方式 |
| 知识抽取 | OpenNRE | 关系抽取经典开源项目 | 是否仍活跃、适合新场景吗 |
| 中文 NLP | HanLP | 中文 NLP 生态常用 | 实体识别和依存分析能力 |
| NLP | spaCy | 工业级 NLP 框架 | 中文模型和抽取效果 |
| 图数据库 | Neo4j | 图数据库生态成熟、Cypher 友好 | 社区版限制、企业使用成本 |
| 图数据库 | Nebula Graph | 国产开源图数据库，适合大规模图 | 运维复杂度、小团队适配 |
| 图数据库 | ArangoDB / HugeGraph / TuGraph | 多模型或图数据库候选 | 社区活跃度和生产案例 |
| 图计算 | NetworkX / GraphScope | 图分析和算法 | 是否适合生产链路 |
| GraphRAG | Microsoft GraphRAG | 微软背景，图谱增强检索代表 | 构图成本、中文效果、适用边界 |
| 图谱 RAG | LightRAG / LlamaIndex KG | 轻量图谱增强检索 | 与现有知识库集成 |

## 6. 适合个人 / 小团队 / 企业的落地方式

| 场景 | 推荐起点 |
|---|---|
| 个人验证 | LLM 抽取 + 简单 JSON / NetworkX / Neo4j Desktop |
| 家庭知识库 | 先用 WeKnora 内置图谱，不急着上重型图数据库 |
| 小团队 | Neo4j 或轻量 GraphRAG 验证具体问题 |
| 企业 | 根据规模和查询需求选择 Neo4j / Nebula Graph / 专用图平台 |

---

## 7. 与其他模块的关系

- 依赖知识工程定义业务对象和关系类型；
- 可增强 RAG 的召回和上下文组织；
- 可为 Agent 提供关系查询工具；
- 需要评测模块验证图谱是否真的提升结果；
- 需要治理模块管理图谱版本、权限和质量。
