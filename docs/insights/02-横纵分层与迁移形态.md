# 02 · 横纵分层与纵向的迁移形态

> 讨论稿 / 会更新 · 最近更新 2026-09-14
>
> **一句话结论**：横向基建（编排/训练推理/样本平台/前后端）会被云厂商和开源抹平，别镀金；
> 纵向（领域知识+反馈闭环+领域评价+样本）不该通用，是护城河——但在横向没成熟前，
> 纵向必须以**框架无关的数据资产**形态沉淀，用防腐层跟横向物理隔开，将来整层平移到成熟框架。

---

## 1. 为什么要分层

工业 Agent 想真正跑起来，底下是一整套软件工程底座：docker 环境、样本管理、模型训练/推理/评估体系、业务知识图谱、前后端展示、编排调度、可观测……这套东西的庞大程度类比像 Linux 或浏览器。**基建缺失，是当前落地乱象（demo 交付、无标准、烂尾）的重要技术根因。**

但这套底座不是铁板一块。必须拆成两层看，否则会在错误的地方下重注：

- **横向层**：与行业无关的通用工程能力——编排、训练推理、样本平台、评估工具、前后端、可观测。
- **纵向层**：不可迁移的领域资产——行业知识图谱、领域评价标准、生产反馈数据、标注样本。

---

## 2. 横向会被抹平，纵向不该通用

**横向 → 一定收敛到几个开源框架 + 云厂商。** 字节/阿里/云厂商有强动力把这层做成白菜价，因为他们要靠它卖 token 和算力。谁把重心押在通用编排上，大概率被抹平。**结论：横向能用、能被替换就行，别追求优雅，别在会消失的东西上追求镀金。**

**纵向 → 不会有大一统，也不该有。** 这层没有 HTML 那种标准接口，它的价值恰恰来自不可迁移。不会出现"行业智能体的 Linux"，只会**每个细分行业跑出几个把反馈闭环转起来的玩家**。什么时候出现、由谁推出，取决于谁的领域数据飞轮转得快，不取决于谁技术强。

⚠️ **反方观点（Bitter Lesson，必须自己记住）**：模型进步本身会吞掉一部分横向层——上下文窗口到千万级、模型原生具备 agentic 编排能力后，现在辛苦搭的编排层、部分评估层可能被模型自己吸收。所以横向层不仅会被云厂商抹平，还会被模型吞掉，**更加不值得重仓**。
模型吞不掉的只有三样：① 私有生产反馈数据；② 与物理设备的闭环/标定；③ 组织流程的嵌入。这三样正好都在纵向层——**再次印证重仓纵向**。

---

## 3. 关键问题：横向没成熟时，纵向以什么形态存在？

这是核心矛盾——纵向要搭在横向基础上，但横向现在既不成熟又会剧变。如果纵向沉淀跟当下这版临时横向框架长在一起，将来横向一换，纵向就得跟着重写，飞轮断裂。

**答案：纵向要以「数据/知识资产」形态存在，不要以「工程」形态存在。**

判断尺子（可直接拿去量任何一个模块）：

> **换掉整个横向框架，这东西还留得下来吗？**
> 留得下 = 纵向沉淀，重仓、隔离保护；
> 留不下 = 临时脚手架，够用就行、别镀金。

按这把尺子，纵向该沉淀成 4 类**框架无关**的资产：

| 纵向资产 | 该有的形态 | 为什么能迁移 |
|---|---|---|
| **领域知识** | 声明式知识图谱 / 规则库（数据，不是代码里的 if-else） | 换框架是搬数据，不是重写逻辑 |
| **反馈闭环** | 标准 schema 的轨迹日志：`输入 → 推理 → 输出 → 实际结果 → 人工修正` | 飞轮燃料，与谁编排无关 |
| **领域评价** | 评测集 + 评分标准（benchmark 数据 + rubric），不硬编码进某条 pipeline | 换模型/换框架照样跑分 |
| **标注样本** | 结构化样本库，带业务标签和版本 | 资产本身，与工具解耦 |

**关键设计动作**：用六边形架构 / 防腐层把两层物理隔开——
- 领域资产放 **core**（受保护，重仓）
- 横向基建（docker、编排、训练推理、前后端）全放 **adapter**（可替换，够用即可）
- 中间用接口挡住，**绝不让领域知识渗进编排代码**

等通用横向框架成熟，扔掉 adapter、把 core 平移过去，飞轮不断。这就是"在横向没成熟时积累纵向、将来快速迁移"的具体答案。

## 4. 产品诊断判据（等代码仓到位后逐模块套用）

对现有这版基建做诊断时，每个模块问三件事：

1. **换横向框架，它留得下吗？**（尺子）
2. **它在攒不可迁移的领域数据吗？**
3. **它的价值来自"独占的生产反馈"还是"通用的工程能力"？**

据此三分类：

- 🟢 **纵向核心资产**：重仓，用防腐层隔离保护
- 🟡 **临时横向脚手架**：够用即可，明知会被抹平就别镀金
- 🔴 **危险的耦合**：领域知识混进了横向代码——最该重构的对象
- ⚫ **以为是纵向、其实会被模型吞掉的**：部分编排、部分评估（Bitter Lesson 陷阱）——别投入

> 待办：拿到团队代码仓 + 技术栈/模块划分后，按此框架出详细诊断报告（哪些是临时横向、哪些是纵向沉淀该重点下功夫、哪些是危险耦合）。见 README 主线判断 #2/#3。
