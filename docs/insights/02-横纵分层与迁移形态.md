# 02 · 横纵分层与纵向的迁移形态

> 讨论稿 / 会更新 · 最近更新 2026-09-14
>
> **一句话结论**：横向基建（编排/训练推理/样本平台/前后端）会被云厂商和开源抹平，别镀金；
> 纵向（领域知识+反馈闭环+领域评价+样本）不该通用，是护城河——但在横向没成熟前，
> 纵向必须以**框架无关的数据资产**形态沉淀，用防腐层跟横向物理隔开，将来整层平移到成熟框架。

## 1. 为什么要分层

工业 Agent 想真正跑起来，底下是一整套软件工程底座：docker 环境、样本管理、模型训练/推理/评估体系、业务知识图谱、前后端展示、编排调度、可观测……这套东西的庞大程度类比像 Linux 或浏览器。**基建缺失，是当前落地乱象（demo 交付、无标准、烂尾）的重要技术根因**（详见 [01](./01-熵增阶段与乱象.md)）。

但这套底座不是铁板一块。必须拆成两层看，否则会在错误的地方下重注：

- **横向层**：与行业无关的通用工程能力——编排、训练推理、样本平台、评估工具、前后端、可观测。
- **纵向层**：不可迁移的领域资产——行业知识图谱、领域评价标准、生产反馈数据、标注样本。

这个"内外分层"的直觉，其实和软件架构里最经典的一条规则同源。Alistair Cockburn 的六边形架构（Ports & Adapters, 2005）把它讲得最干脆：

> "The asymmetry to exploit is not that between left and right sides of the application but between inside and outside of the application. The rule to obey is that code pertaining to the inside part should not leak into the outside part."
> （要利用的不对称不是应用的左右之分，而是内外之分；规则是：内部的代码不能泄漏到外部去。）
> —— Alistair Cockburn, *Hexagonal Architecture*

Robert C. Martin 的 Clean Architecture（2012）把同一件事表述为**依赖规则**：

> "source code dependencies can only point inwards. Nothing in an inner circle can know anything at all about something in an outer circle."
> （源码依赖只能指向内层；内层不能知道任何关于外层的事情。）

把这套三十年沉淀的架构原则翻译到工业 AI 语境：**领域资产是"内部/内层"，横向工程是"外部/外层"；依赖只能从横向指向纵向，绝不能反过来。** 下面两节论证的，就是在 AI 这个特定行业里，"内外"该怎么划、为什么这么划。

## 2. 横向会被抹平，纵向不该通用

### 2.1 横向 → 一定收敛到几个开源框架 + 云厂商

字节/阿里/云厂商有强动力把这层做成白菜价，因为他们要靠它卖 token 和算力。谁把重心押在通用编排上，大概率被抹平。这不是猜测，有三条正在发生的外部证据：

**证据一：价值本来就没沉在中间层。** a16z 2023 年的 *Who Owns the Generative AI Platform?* 直接给出资金流向的判断：

> "infrastructure vendors are likely the biggest winners in this market so far, capturing the majority of dollars flowing through the stack." 
> "Application companies are growing topline revenues very quickly but often struggle with retention, product differentiation, and gross margins."

钱要么流向底层算力/基础设施，要么被应用层的差异化留住；夹在中间、纯做通用工程能力的那层，最尴尬。

**证据二：编排框架自己正在被"退货"。** LangChain / LlamaIndex 这类编排中间件是横向层的典型代表。Octomind 工程师 Fabian Both 在 2024 年那篇被大量转载的 *Why we no longer use LangChain for building our AI agents* 里，讲的就是高层抽象（prompt 模板、output parser、LCEL chain）在复杂多智能体场景下"become a source of friction rather than productivity"，团队最终把它移除、退回到直接调 SDK + 模块化积木。**一个横向框架的价值，抵不过它强加的耦合成本时，就会被扔掉。**

**证据三：模型厂商正在把编排收进平台。** OpenAI 的 Agents SDK / Assistants API 已内置 agent loop、工具调用、会话状态、多智能体 handoff；Anthropic 2025 年 11 月的 *advanced tool use* 提供工具动态发现、按需加载、代码执行式编排。这些恰好就是过去要靠框架中间件补的能力——**编排正在从"第三方框架"下沉为"模型平台的原生能力"。**

**结论：横向能用、能被替换就行，别追求优雅，别在会消失的东西上追求镀金。**

### 2.2 纵向 → 不会有大一统，也不该有

这层没有 HTML 那种标准接口，它的价值恰恰来自不可迁移。不会出现"行业智能体的 Linux"，只会**每个细分行业跑出几个把反馈闭环转起来的玩家**。什么时候出现、由谁推出，取决于谁的领域数据飞轮转得快，不取决于谁技术强（谁攒住闭环见 [03](./03-几波力量与2030赢家.md)）。

需要给"纵向即护城河"打一个诚实的补丁：**"有数据"本身不等于护城河。** a16z 的 Martin Casado 在 *The Empty Promise of Data Moats*（2019）里泼了冷水：

> "we now wonder if there's practical evidence of data network effects at all … even the more straightforward data effect has limited value as a defensive strategy for many companies."
> "Treating data as a magical moat can misdirect founders from focusing on what's really needed to win."

这对本篇是校正而非反驳：**护城河不在"数据存量"，而在"数据飞轮的转速 + 领域嵌入的深度"**——独占的生产反馈、与物理设备的闭环、组织流程的嵌入，这些才是别人复制不了的。单纯攒一堆样本、不闭环、不嵌入流程，会掉进 Casado 说的"以为数据是魔法护城河"的陷阱。这也正是第 4 节诊断框架要区分"独占生产反馈"与"通用工程能力"的原因。

### 2.3 反方观点：Bitter Lesson 会吞掉一部分横向（必须自己记住）

模型进步本身会吞掉一部分横向层。Rich Sutton 的 *The Bitter Lesson*（2019）核心论断：

> "general methods that leverage computation are ultimately the most effective, and by a large margin … We have to learn the bitter lesson that building in how we think we think does not work in the long run."
> （利用算力的通用方法最终最有效，且优势巨大……我们必须学到这个苦涩的教训：把"我们以为的思考方式"硬编码进去，长期是行不通的。）

翻译到本篇语境：上下文窗口到千万级、模型原生具备 agentic 编排能力后，现在辛苦搭的编排层、部分评估层，可能被模型自己吸收。**所以横向层不仅会被云厂商抹平，还会被模型吞掉，更加不值得重仓。**

但 Bitter Lesson 有个关键边界，不能过度外推。Rodney Brooks 在 *A Better Lesson*（2019）指出其中的"偷换"（sleight of hand）：

> "Saying that in the future we will have viable training sets is shifting the human workload to creating massive training sets and encoding what we want the system to learn in the labels. This is just as much building knowledge in as it would be to directly build a color constancy stage. It is sleight of hand in moving the human intellectual work to somewhere else."
> （说"未来我们会有可用训练集"，只是把人的工作量转移到了构造海量训练集、并把要学的东西编码进标签里；这跟直接构造一个模块一样，也是在注入知识，只是把人的智力劳动挪到了别处。）

Brooks 的洞察正好落在本篇要点上：**算力吞掉的是"方法/how"，吞不掉的是"注入到数据和标签里的领域知识/what"。** Sutton 讲的是 search 与 learning 这两类"方法"会规模化，但"喂什么数据、标什么标签、用什么标准判对错"这件事，人的领域智力劳动只是被搬了家，没有消失——而它搬去的地方，正是纵向层。

由此，模型吞不掉的只有三样：

| # | 模型吞不掉的东西 | 为什么吞不掉 |
|---|---|---|
| ① | **私有生产反馈数据** | 不在任何预训练语料里，只在你的产线上产生 |
| ② | **与物理设备的闭环/标定** | 需要真实传感器、真实执行器、真实物理回路，算力模拟不出漂移和标定 |
| ③ | **组织流程的嵌入** | 嵌进特定组织的审批/工单/责任链，是社会技术系统，不是模型能力 |

这三样正好都在纵向层——**再次印证重仓纵向**。也正是 Brooks 说的"被搬去别处"的那些人类智力劳动的落点。

## 3. 关键问题：横向没成熟时，纵向以什么形态存在？

这是核心矛盾——纵向要搭在横向基础上，但横向现在既不成熟又会剧变。如果纵向沉淀跟当下这版临时横向框架长在一起，将来横向一换，纵向就得跟着重写，飞轮断裂。

**答案：纵向要以「数据/知识资产」形态存在，不要以「工程」形态存在。**

判断尺子（可直接拿去量任何一个模块）：

> **换掉整个横向框架，这东西还留得下来吗？**
> 留得下 = 纵向沉淀，重仓、隔离保护；
> 留不下 = 临时脚手架，够用就行、别镀金。

### 3.1 四类框架无关的纵向资产

按这把尺子，纵向该沉淀成 4 类**框架无关**的资产：

| 纵向资产 | 该有的形态 | 为什么能迁移 | 外部参照 |
|---|---|---|---|
| **领域知识** | 声明式知识图谱 / 规则库（数据，不是代码里的 if-else） | 换框架是搬数据，不是重写逻辑 | 工业因果知识图谱做质量根因分析，已有同行实践（CausalKGPT, 2024） |
| **反馈闭环** | 标准 schema 的轨迹日志：`输入 → 推理 → 输出 → 实际结果 → 人工修正` | 飞轮燃料，与谁编排无关 | data flywheel 概念（Amazon 飞轮，*Working Backwards*, 2021） |
| **领域评价** | 评测集 + 评分标准（benchmark 数据 + rubric），不硬编码进某条 pipeline | 换模型/换框架照样跑分 | eval-driven 迭代是产品成败关键（Hamel Husain, 2024） |
| **标注样本** | 结构化样本库，带业务标签和版本 | 资产本身，与工具解耦 | —— |

一句提醒（呼应 2.2）：这四类资产**只有转起来才是护城河**。知识图谱不更新、轨迹日志不回流训练、rubric 不随专家判断迭代、样本不带版本，那它们只是"数据存量"，会掉进 Casado 说的空头护城河陷阱。资产的价值在飞轮转速，不在体积。

### 3.2 关键设计动作：六边形架构 + 防腐层，把两层物理隔开

- 领域资产放 **core**（受保护，重仓）
- 横向基建（docker、编排、训练推理、前后端）全放 **adapter**（可替换，够用即可）
- 中间用接口挡住，**绝不让领域知识渗进编排代码**

这一步的理论依据是 DDD 的**防腐层（Anti-Corruption Layer, Eric Evans, 2003）**。微软架构模式文档对它的定义，几乎就是为这个场景写的：

> "Isolate the different subsystems by placing an anti-corruption layer between them. This layer translates communication between the two systems. By using this approach, you can keep one system unchanged without compromising the design and technological approach of the other."
> （用防腐层隔离不同子系统；这层负责翻译两个系统间的通信；这样你可以保持一个系统不变，而不牺牲另一个系统的设计与技术路线。）

注意 ACL 最经典的用法就是**"分阶段迁移遗留系统"**——这跟本篇的处境完全同构：当下这版横向框架就是那个"迟早要被替换的外部系统"，防腐层保证它被替换时，core 里的领域资产不受污染、不被牵连。

等通用横向框架成熟，扔掉 adapter、把 core 平移过去，飞轮不断。这就是"在横向没成熟时积累纵向、将来快速迁移"的具体答案。防腐层接口边界具体怎么切、rubric 怎么既是数据又能表达复杂判断、轨迹 schema 能否推成标准——这三个真正难的问题在第 5 节展开。

### 3.3 落到两家公司：顾问入驻怎么盘"纵向资产"

前面的"纵向资产"还是抽象名词。这一节换个身份：**假设你作为顶级智能化转型顾问入驻，第一周要交出的东西不是架构图，而是一张"这家公司的不可迁移资产在哪、现在断在哪、怎么接起来"的清单。** 拿两家性质完全不同的制造企业演示——一家整车厂（理想汽车）、一家半导体设计公司（兆易创新）。

> 说明：以下是顾问视角的资产盘点方法演示，制造/智驾/半导体的产线与质量链路属行业通识；具体到某家公司内部系统的落地细节属假设性推演，非其披露事实。

#### 先问三个"独占性"问题（判断什么才配叫纵向资产）

顾问进场不先看技术栈，先问三句话——它们直接对应 4.1 三问里的 Q3（价值来自"独占反馈"还是"通用能力"）：

1. **这条反馈，全世界还有谁能同时看到?** 只有你能看到 = 独占，是护城河候选；供应商/云厂商也能看到 = 通用，别当资产。
2. **这条反馈现在有没有从"结果"接回到"原因"?** 接上了 = 飞轮在转；断了（结果落在 A 系统、原因落在 B 系统，没人对得起来）= 只是"数据存量"，掉进 Casado 的空头护城河陷阱（见 2.2）。
3. **接起来靠的是数据结构，还是靠某位老工程师的脑子?** 靠脑子 = 没资产化，人一走飞轮就停。

带着这三问看两家公司，"纵向资产是什么"立刻具体。

#### 例一：理想汽车——整车厂的独占反馈是"生产参数 ↔ 全生命周期表现"

整车厂手里有两条独立飞轮，性质不同，别混为一谈：

- **智驾飞轮**（行业最出名的例子）：影子模式 / 车端回传的 corner case → 标注 → 训练 → OTA 下发。这条飞轮的护城河**不在积累了多少公里数据**（存量），而在**回流—标注—上车的转速**——这正是 2.2 "转速 > 存量" 的活样本。
- **制造飞轮**（更被低估、更是顾问该挖的）：焊装/涂装/总装/电池化成的工艺参数，接到下线检测（EOL）、售后三包、召回的实际结果上。**只有整车厂能同时看到"当时拧了多大扭矩/喷了多厚漆" 和 "这台车三年后在客户手里出了什么问题"**——Tier 1 供应商看不到售后，云厂商更看不到。这是教科书级的独占反馈。

按 3.1 的四类资产落到制造飞轮：

| 纵向资产 | 理想（制造侧）的具体形态 | 独占性来源 |
|---|---|---|
| 领域知识 | 工艺-缺陷因果图谱：焊点参数↔虚焊/气孔、涂装膜厚↔环境温湿度↔流挂、电池化成曲线↔一致性；挂在 BOM/工艺路线/设备台账上 | 图谱的"边"来自自家产线复盘，不在任何公开语料 |
| 反馈闭环 | `工艺参数快照 → 质量判定 → 下线复检 → 售后/召回实际结果 → 工艺工程师复盘` 的完整轨迹 | 生产端与全生命周期端只有主机厂能同时握住 |
| 领域评价 | "这条焊缝/这块漆面算不算合格"的判据 + 质量门 rubric，来自资深工艺与质量工程师 | 判据是自家工艺 know-how，随车型迭代 |
| 标注样本 | 焊缝/漆面缺陷图像库、振动/声学信号库，带缺陷码与工况标签 | 自家设备、自家工况下采的，别人复制不了 |

**顾问怎么帮它"收集和构建"**（这才是"如何"）：
1. **先做断点盘点，不急着上系统。** 十有八九，MES（生产参数）和售后/质量系统（实际表现）是两套库、两拨人，`车架号 ↔ 工艺参数快照` 这条追溯链是断的。**第一周的产出就是标出这条断链在哪一环丢的。**
2. **按 5.3 的最小骨架定死轨迹 schema**：`input=下线时的工艺参数快照`，`output=质量门判定`，`ground_truth=下线复检 + 售后回读`，`correction=工艺工程师复盘理由`，`domain_ext=缺陷码/工序/设备型号/批次`。先接一条产线（比如焊装）跑通，别全厂铺开。
3. **把"合格判据"从老师傅脑子里搬进 core**（5.2 的 L1/L2）：让工艺专家对历史案例做 Pass/Fail + 写 critique，沉淀成数据，而不是继续靠口传。
4. 这三步做完，制造飞轮才从"有一堆数据"变成"转起来的独占资产"。

#### 例二：兆易创新——Fabless 厂的独占反馈是"设计意图 ↔ 多家代工实测 ↔ 客户端失效"

兆易是设计公司（MCU、NOR Flash、DRAM、传感器），**制造外包给晶圆代工厂 + 封测厂**。这带来一个和整车厂不同、但同样关键的独占位置：

- 晶圆代工厂只看得到**自己那一段工艺**，看不到芯片到了客户手里怎么失效；
- EDA / 设计工具厂只有**前段设计意图**；
- 客户只有**后段失效现象**；
- **只有兆易这个 Fabless 厂，能把"我原本想怎么设计 → 在中芯/华虹等多家代工厂实测出的良率与失效 → 客户端返修（RMA）的真实失效"这三点连成一条线。** 这条三点连线，就是它别人复制不了的独占反馈。

按 3.1 的四类资产落地：

| 纵向资产 | 兆易的具体形态 | 独占性来源 |
|---|---|---|
| 领域知识 | 失效模式因果图谱：bit fail/漏电/latch-up ↔ 工艺角/版图/测试条件；Flash 擦写寿命 ↔ 工艺漂移 | 跨"设计-多代工-客户"的边，只有它能连 |
| 反馈闭环 | `设计版本+工艺角+测试条件 → CP(晶圆测试) → FT(成品测试) → 客退 RMA/FA → 反哺设计与测试程序` | 代工厂只有中间一段，兆易有全链 |
| 领域评价 | "可不可以出货"的良率/可靠性判据：老化(burn-in)、HTOL、温循的 Pass/Fail rubric | 判据是自家产品线的可靠性 know-how |
| 标注样本 | 失效分析(FA)案例库：每颗客退芯片的物理失效定位（切片/EMMI/OBIRCH）结论 + 失效码 | 自家 FA 实验室积累，行业最稀缺的结构化资产 |

**顾问怎么帮它"收集和构建"**：
1. **先查一个致命前提——die-level 可追溯性。** 每颗芯片能不能追回它在哪片 wafer、哪个 lot、哪组工艺参数？**追溯断了，反馈闭环就是断的，后面全白搭。** 这是半导体飞轮的燃料前提，第一优先级。
2. **把散落的失效知识资产化。** 半导体公司最典型的病：失效知识在老工程师脑子里 + 一堆零散 FA 报告 Word，没结构化成图谱。顾问的高价值动作是把历史 FA 报告抽成"失效码 ↔ 工艺/设计原因"的声明式知识图谱（放 core），而不是让它继续躺在共享盘里。
3. **按同一套 schema 接起三段**：`input=设计版本/工艺角/测试条件`，`output=良率/binning`，`ground_truth=可靠性测试 + 客退结果`，`correction=FA 结论 + 失效码`，`domain_ext=产品线/封装/代工厂`。注意 schema 主干和理想那条**完全同构**（5.3 的通用骨架），只是 `domain_ext` 填的是半导体字段——这正好印证 5.3 "主干标准化 + 扩展位留白"。

#### 两家一对照，抽象名词就落地了

| | 理想（整车厂） | 兆易（Fabless 半导体） |
|---|---|---|
| 独占反馈的连线 | 生产参数 ↔ 全生命周期表现 | 设计意图 ↔ 多代工实测 ↔ 客户失效 |
| 谁看不到这条线 | 供应商看不到售后、云厂商全看不到 | 代工厂只有工艺段、EDA 只有设计段 |
| 顾问的头号动作 | 打通 MES↔售后 的车架号追溯链 | 确认 die-level 可追溯性 + FA 知识图谱化 |
| 飞轮燃料的关键字段 | `ground_truth`=售后/召回回读 | `ground_truth`=可靠性+客退 FA |
| 最容易踩的坑 | 把"数据量大"当护城河（其实断链） | 失效知识锁在老工程师脑子里没资产化 |

**一句话收口**：所谓"纵向资产"，具体到公司就是**那条只有你能同时看到两端、且已经用数据结构接起来的独占反馈闭环**——不是数据库有多大，而是"结果能不能追回原因、且不依赖某个人的记忆"。顾问入驻的价值，八成不在教它上什么框架（横向，会被抹平），而在**找出这条独占反馈链断在哪、把它按 5.3 的 schema 接起来、并把判据从人脑搬进 core**。这就是 2.2 "转速 + 嵌入深度 > 数据存量" 的落地操作。

## 4. 产品诊断评分框架（拿到代码仓后逐模块套用）

这是本篇将来实际要用的工具。目标：把上面的判断尺子做成一张**可直接套用的评分卡**，对现有这版基建逐模块打分、给出重构优先级。

### 4.1 三问（每个模块必答）

| # | 问题 | 考察什么 |
|---|---|---|
| Q1 | **换横向框架，它留得下吗？** | 迁移性（3.1 的尺子） |
| Q2 | **它在攒不可迁移的领域数据吗？** | 是否在积累纵向资产 |
| Q3 | **它的价值来自"独占的生产反馈"还是"通用的工程能力"？** | 护城河来源（呼应 2.2 的 Casado 校正） |

### 4.2 四分类判据

据此把每个模块归入四类之一：

| 类别 | 判据 | 处置 |
|---|---|---|
| 🟢 **纵向核心资产** | Q1=留得下, Q2=是, Q3=独占反馈 | 重仓，用防腐层隔离保护 |
| 🟡 **临时横向脚手架** | Q1=留不下, Q2=否, Q3=通用能力 | 够用即可，明知会被抹平就别镀金 |
| 🔴 **危险的耦合** | 本该是 core 的领域知识，混进了 adapter/横向代码里 | 最该重构——先做隔离 |
| ⚫ **Bitter Lesson 陷阱** | 以为是纵向，其实是会被模型吞掉的"方法层"（部分编排、部分评估逻辑） | 别投入，等模型吞 |

区分 🔴 与 ⚫ 是这张卡最容易出错、也最值钱的地方：
- 🔴 是**位置错了**——东西本身是纵向资产，只是被写进了横向代码（比如领域规则硬编码进编排 pipeline）。修法是**搬家 + 隔离**，把它抽成声明式数据放进 core。
- ⚫ 是**性质错了**——东西本身就是会被算力吞掉的通用方法（比如手写的一套"让模型分步推理"的编排逻辑）。修法是**别修，别加码**，让位给模型原生能力。

判 ⚫ 时用 Brooks 的边界自检（见 2.3）：**这个模块凝结的是"人类的方法/how"，还是"人类注入的领域知识/what"？** 前者会被吞（⚫），后者搬个家就留得下（🔴→🟢）。

### 4.3 模块评分卡模板

对每个模块填一行，`is_core` 由三问推出，`action` 由四分类给出：

| 模块 | Q1 留得下? | Q2 攒领域数据? | Q3 价值来源 | 分类 | 当前位置(core/adapter) | 处置动作 | 优先级 |
|---|---|---|---|---|---|---|---|
| 知识图谱存储 | 是 | 是 | 独占反馈 | 🟢 | ？ | 确认在 core、加防腐层 | —— |
| 编排调度 | 否 | 否 | 通用能力 | 🟡/⚫ | ？ | 够用即可 / 让位模型 | —— |
| 领域评价 rubric | 是 | 是 | 独占反馈 | 🟢(注意退化成⚫) | ？ | 数据化，见 5.2 | —— |
| 反馈轨迹日志 | 是 | 是 | 独占反馈 | 🟢 | ？ | 定 schema，见 5.3 | —— |
| ……（逐模块补全） |  |  |  |  |  |  |  |

诊断的高价值产出有三个：
1. **一份 🔴 清单**（危险耦合），按"领域知识被埋得多深"排重构优先级；
2. **一份 🟢 清单**（纵向资产），确认是否都在 core 且被防腐层保护、飞轮是否真在转；
3. **一份 ⚫ 清单**（Bitter Lesson 陷阱），明确"停止投入、等模型"的模块，避免继续在会消失的东西上耗人力。

## 5. 三个真问题的展开

前一版把这三个当"待展开/存疑"挂着。它们是本方案能不能落地的关键，逐条展开。

### 5.1 防腐层的接口边界到底怎么切？

**难点**：切浅了，领域知识渗进 adapter，成了 🔴 危险耦合；切深了，接口太厚、每换一次横向都要重写一堆翻译代码，防腐层自己成了负担。

**判据一（用 Fowler 的 published vs public 区分）**：Martin Fowler 提醒过一个比"public/private"更重要的区分——**published interface**（被本代码库之外的东西依赖的接口）。他的原话：

> "the distinction between published and public is actually more important than that between public and private."

映射到这里：**凡是横向 adapter 要调用 core 的地方，那个接口就是 published interface，必须显式定义、版本化、当契约对待；core 内部的东西一律不 published。** 这条直接给出"哪些算 core 契约、哪些算 adapter 细节"的操作判据——被跨层调用的才是契约，其余都是可自由重构的内部细节。

**判据二（契约用领域语言，不用横向术语）**：ACL 的核心是"翻译"。所以接口签名里**只能出现领域概念**（`产线`、`工序`、`缺陷类别`、`标定参数`、`根因假设`），**绝不能出现横向术语**（`LangChain 的 AgentExecutor`、`某向量库的 collection`、`某训练框架的 checkpoint`）。一旦领域接口里出现了横向框架的类型，就是防腐层破了、耦合渗进来了——这也是第 4 节 🔴 的自动探测信号：**grep core 的接口定义，出现任何横向框架的类型名即报警。**

**建议切法（四条 published 契约，覆盖四类资产）**：

| core 侧 published 契约 | 职责（只用领域语言） | adapter 侧实现（可换） |
|---|---|---|
| `KnowledgeRepository` | 按领域概念查询/写入知识图谱与规则 | Neo4j / 某图库 / 内存 mock |
| `TrajectoryLog` | 追加一条标准 schema 的反馈轨迹（见 5.3） | Kafka / 数据湖 / 本地文件 |
| `Evaluator` | 输入案例，返回按 rubric 的评分与理由 | LLM-as-judge / 规则引擎 / 人工队列 |
| `SampleStore` | 按业务标签+版本存取样本 | 对象存储 / 特征平台 / DVC |

原则：**core 定义这四个接口 + 领域数据模型；adapter 提供实现。** 依赖方向永远是 adapter → core（符合 Clean Architecture 的依赖规则）。换横向框架 = 换这四个接口的实现，core 不动。

### 5.2 领域评价 rubric 如何既是数据、又足够表达复杂工业判断？

**难点（也是最真的存疑）**：纯声明式 rubric（"缺陷分类准确=+1，误报=-1"）在工业里往往不够——真实判断常是"如果这台设备近 72 小时有过标定漂移，且该缺陷出现在焊缝热影响区，则误报的容忍度更高"。这类判断带条件、带计算、带时序。要表达它，是不是又得把可执行逻辑塞进 rubric，从而把评价逻辑又耦合回代码里？

**外部证据给的方向，出人意料地是"往简单里走"**。Hamel Husain 在 *Creating a LLM-as-a-Judge That Drives Business Results*（2024）里明确反对复杂多维打分：

> "Arbitrary Scoring Systems: Using uncalibrated scales (like 1-5) across multiple dimensions, where the difference between scores is unclear and subjective. What makes something a 3 versus a 4? Nobody knows."

他主张：**领域专家做二元 Pass/Fail 判断 + 写下 critique（理由）**，再让 LLM judge 去逼近专家。学术侧也印证 judge 本身不可全信——MT-Bench 论文（Zheng et al., 2023）点名 LLM-as-judge 有 position bias / verbosity bias / self-enhancement bias；Cohere 的 PoLL（2024）建议用"多个小模型陪审团"替代单一大模型 judge 以降偏。

**综合成一个分层方案，既避免耦合、又留住复杂判断的表达力**：

| 层 | 内容 | 形态 | 是否可执行 | 放哪 |
|---|---|---|---|---|
| L1 判定 | 每个案例的 Pass/Fail + 专家 critique 文本 | 数据（JSON/表） | 否，纯数据 | core 资产 |
| L2 rubric 说明 | 判定标准的自然语言描述（含"什么情况容忍度更高"这类条件） | 数据（Markdown/文本） | 否，声明式 | core 资产 |
| L3 前置事实 | 判断依赖的客观量（标定漂移量、缺陷位置、时序窗口）由**领域特征函数**先算好，作为事实喂给评价 | 特征值（数据） | 计算发生在 core 的领域特征层，不在 rubric 里 | core |
| L4 judge | 把 L2 rubric + L3 事实 + 待评案例喂给 LLM-as-judge 或人工，产出评分 | adapter 实现 | 可换（LLM/规则/人工/陪审团） | adapter |

**关键设计**：把"需要计算的复杂条件"从 rubric 里**剥离到 L3 领域特征层**——rubric 本身回归声明式数据（"当漂移量>阈值时容忍度更高"这句话是文本，`漂移量`这个数由 core 的特征函数算好）。这样：
- rubric 保持是**数据**（可迁移、可 diff、可版本化）；
- 复杂工业判断的**计算**留在 core 的领域特征层（本来就是纵向资产，不算耦合）；
- 二者通过 5.1 的 `Evaluator` 契约对接，横向框架换了照样跑分。

结论：**不需要往 rubric 里嵌可执行片段**。真要嵌逻辑，说明那段逻辑是"领域特征计算"，它该作为一等公民放进 core 的特征层，而不是藏在评价脚本里。这既回答了"会不会又变耦合"（不会，因为计算归位到了本就属于 core 的地方），也守住了 rubric 的数据属性。

### 5.3 反馈闭环轨迹 schema 能推成行业标准吗？谁来推？

**分两问**。

**（a）schema 长什么样、能不能稳定下来？** 能，因为最小骨架其实是领域无关的，工业场景只是往里填领域字段。建议最小标准骨架：

```
trajectory:
  id, timestamp, tenant/site（哪条产线）
  input:      观测/传感器快照 + 触发上下文
  reasoning:  模型/agent 的中间推理与调用轨迹（可选留存）
  output:     系统给出的结论/动作（如"判为焊缝气孔，建议降速")
  ground_truth: 实际结果（复检结论/设备回读）——飞轮的关键燃料
  correction: 人工修正 + 修正者角色 + 理由（对应 5.2 的 critique）
  domain_ext: 领域扩展字段（缺陷码、工序、设备型号、标定态……）
```

`input→reasoning→output→ground_truth→correction` 这条主干是通用的，`domain_ext` 承载不可迁移的领域细节。**主干标准化 + 扩展位留白**，是让它既能跨厂复用、又不牺牲领域表达的现实做法。这条轨迹同时也是 5.2 L1（Pass/Fail+critique）和训练样本（4.1 样本库）的共同数据源——一份数据喂三个飞轮。

**（b）能推成行业标准吗？谁来推？** 诚实判断：**短期不会有中立的大一统标准，也不必等它**。理由：
- 标准的话语权跟着数据飞轮走（见 [03](./03-几波力量与2030赢家.md)）——谁在某细分行业攒住了最多闭环，谁的 schema 就成事实标准。这跟 2.2 的判断一致：**标准由领域数据飞轮转得最快的玩家事实上确立，不由技术最强或最中立的组织颁布。**
- 中立标准组织（行业协会、龙头联合体）推得动的前提，是先有一两家把闭环跑通、证明了 ROI，别人才有动力对齐。所以顺序是**先有事实标准，后有协商标准**，不是反过来。

**对本团队的行动含义**：不要花力气去"推行业标准"，那是果不是因。正确动作是——**先按上面的最小骨架把自己的轨迹 schema 定死、把飞轮转起来**（这是 🟢 核心资产），并把 `domain_ext` 设计得干净、可导出。等飞轮转出 ROI，你的 schema 自然具备成为该细分行业事实标准的资格；到那时"谁来推"就有了答案——**你来推，用既成事实推。** 这也正是 [03](./03-几波力量与2030赢家.md) 里"谁攒住反馈闭环谁赢"的具体落点。
