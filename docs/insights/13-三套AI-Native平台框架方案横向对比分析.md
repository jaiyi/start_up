# 13 · 三套 AI Native 平台框架方案横向对比分析

> 讨论稿 / 会更新 · 最近更新 2026-10-10
>
> **分析对象**：
> 1. `04-05-AI-Native任务闭环平台.md` —— 方法论 / 产品愿景蓝图
> 2. `docs/product-analysis/industrial-ai-platforms/lianshan/`（核心为 01 / 09 / 10 三份诊断）—— 连山现有产品体系
> 3. `spc_dsh/plans/`（v0.3.1，00 / 01 / 03 / 07 四份设计稿）—— SPC × DeepSeek Harness 重建架构
>
> **视角**：第三方 AI Native 转型开发架构师，横向对比三套框架方案，识别各自优劣势并给出针对性优化建议。
>
> **一句话结论**：三套方案不是竞争关系，而是同一平台三个缺失的侧面——方案一贡献商业与组织层（该卖什么、谁签字），方案三贡献平台机制层（AI 时代控制面怎么设计），方案二贡献交付与证据层（怎么落地、怎么取信）。正确路线是三合一，而不是三选一。

---

## 0. 先校准：三套方案各自回答什么问题

这不是三个平行竞标方案，而是三个不同抽象层次的架构主张——但正因如此，才值得作为"框架方案"横向比较，因为公司实际面临的是三选一或三合一的路线决策。

| | 方案一：AI-Native 任务闭环平台（04-05） | 方案二：连山现有产品体系 | 方案三：SPC × DeepSeek Harness（spc_dsh） |
|---|---|---|---|
| **性质** | 方法论 / 产品愿景蓝图（零实现） | 已有工程实体（7+ 仓库，工程证据充分） | 重建架构设计稿（v0.3.1，未实施） |
| **抽象层次** | 企业级：ERP/MES 之上的控制面 | 平台级：私有化底座 → 编译 → 运行时 → 工作站 → 场景 | 场景级：SPC 单场景 + 通用计算节点 |
| **核心主张** | 厚场景薄系统，八层任务控制面，不造烟囱 | PG-first + Bundle-first + HITL + EVI 的完整工程链 | AI Agent 宿主作管理面，计算节点自持运行，管理时发布 |
| **AI 位置** | 嵌入任务/决策/复盘/反馈节点（概念） | 事件触发的冷/热路径管线（实现） | **Agent 即管理面本身**（最激进） |
| **商业化内容** | 最丰富：EVI、付费分层、归因、激励 | 有机制（EVI L1-L2）、缺证据 | 完全缺失 |

## 1. 八个维度的横向对比

### 1.1 AI Native 程度（AI 在架构中的"原生性"）

- **方案一**：概念上最完整——AI 被定义为治理对象（Prompt/Skill/Tool/RAG Index 都是治理资产），这是三套中唯一把"Agent 治理失控"作为一等风险论证的。但停留在概念，`AI 能力层`没有回答 Agent 在哪运行、控制面与运行面怎么分。
- **方案二**：AI 嵌入事件触发链（SPC 判异触发、NG 反馈触发），比聊天机器人进步一个量级，但 Agent 本质上仍是"管线里的处理节点"，管理动作（配置、部署、建表）仍是传统工程行为。
- **方案三**：**三套中最 AI-Native 的**。DSH（Agent Harness）本身就是管理面：配置引导、诊断编排、回放对比全部由 Agent 会话承载；同时用"模型只产候选、专家审批发布"把不可信性显式建模进架构。`算子交付链`把"工程师经 DSH 做沙箱回放"设计成正式回路——这是真正把 AI 当作工程协作界面而非功能模块。

**结论**：AI 原生性上 方案三 > 方案二 > 方案一（方案一理念最深但无机制落地）。

### 1.2 治理与安全

- **方案一**：治理本体最丰富——七种血缘（数据/文档/知识/Prompt 版本/Agent 行为/人工确认/经营结果）、行/列/文档/工具级权限、写动作 L0-L3 风险分级。这是三套中最完整的治理理论。
- **方案二**：有意识（Bundle 生命周期、AcceptanceReport、HITL checkpoint、数据充分度门禁），但有 **P0 安全债**：inventory 明文密码、默认密码 `lisen`、auth token 跨 site 硬编码。诊断文档自己也承认这是大客户销售的前置阻碍。
- **方案三**：微观治理最锋利——确定性 event_id、写权限 owner 矩阵到列组、fail-closed 全链路、schema 迁移幂等、平台包版本纪律、gateway HMAC 签名。但**宏观治理缺失**：单租户、无 RBAC 细节、无审计导出、凭据管理只有一句"环境变量/secret，不进 Git"。

**结论**：方案一有理论、方案二有债务、方案三有微观纪律但缺宏观架构。三者没有一个同时具备"可销售级"的安全治理。

### 1.3 任务闭环与状态机

- **方案一**：Task 对象字段设计最全（`evidence_refs`/`feedback_records`/`value_impact_refs`），且强调跨场景同构。
- **方案二**：闭环器官已存在（execution_run / work_order / human_task_decision / alert_feedback），但**不同场景各自建模，SPC 散在四个仓库**，无统一任务语言。
- **方案三**：五-gate 状态机由 plugin-workorder 通用引擎承载、gate 数量可由 profile 声明——这是三套中唯一把"任务状态机通用化"落成具体机制设计的。且"一条告警事件就是一张工单 + 工单由后端落库、DSH 宕机照常累积"解决了方案二中 Agent 平台单点的问题。

**结论**：方案三在单场景内最扎实；方案一在同构抽象上最完整；方案二目前是"有器官、没身体"。

### 1.4 反馈与学习飞轮

- **方案一**：反馈→评估→蒸馏→专家审核→版本发布，四去向（知识库/规则/评测集/EVI 台账）设计完整。
- **方案二**：反馈数据最丰富（采纳/拒绝/修正/NG closure/diagnosis_outcome/info_gain），被诊断为"最有潜力的飞轮"，但口径分散。
- **方案三**：闭环只到"结论回流反馈表 → 驱动故障树迭代"，**四去向里只实现了一个**，且迁移策略的"可平移清单"里没有提到 feedback/EVI 表——有把方案二最值钱的反馈资产在重建中丢掉的风险。

### 1.5 经营归因（EVI）——**三套分歧最大的维度**

- **方案一**：EVI 是第 8 层，ValueImpact 对象有归因等级、可信等级、结算状态，直指付费模式。
- **方案二**：有 EVI 机制与分级路线（L0-L4），当前 L1-L2，被明确定位为商业化核心。
- **方案三**：**完全没有 EVI**。全部 8 份计划文档中，经营归因、价值证据、客户确认无一字涉及。这是一个纯工程视角的重建方案。

这是方案三最致命的战略级缺口：诊断文档 09/10 反复论证"连山最该证明的不是平台，而是经营收益"，而重建方案把这条主张丢了。

### 1.6 落地性与交付

- **方案一**：MVP 路径设计（先六件事、三阶段）合理，但无工程支撑，且有自己警告过的"大而全中台"幻觉风险——八层里语义层、治理层各自都是 Atlan/Alation 量级的产品。
- **方案二**：**交付链路最完整但最重**：53 个 Ansible role、11 个 PG 扩展、多 submodule、私有 PyPI/OSS/ACR——诊断明确指出"毛利被交付吞噬"的风险，以及工程证据与生产证据（连续 30/60/90 天运行）之间的鸿沟。
- **方案三**：首交付物收敛得当（后端 + PG + 假告警 + 单事件诊断链），有诚实的风险登记表。但**两大未决**：① 架构前提（DSH rc 版常驻 server + POST 唤醒）未验证，spike 失败则 gateway 形态重评；② **现场部署故事缺失**——Q2 只在 docker/compose/K8s/公司平台之间摇摆，完全没有回答"怎么部署到客户生产网"，而这是方案二用整个 lisen-infra 仓解决的问题。

### 1.7 复用与扩展模型

- **方案一**：场景模板中心 + 平台化抽象表（故障单→异常事件，工单→任务对象……），复用叙事最清晰。
- **方案二**：跨仓复用困难，SPC 对齐要四个仓库同步——这正是方案三立项的动因。
- **方案三**：**复用单位设计最精细**：平台资产（6 包独立版本化）+ profile（薄）+ 算子 + 流水线定义三层资产，后续拧紧/排产 profile 挂算子即可。且"为复用而结构化、不为复用而实现"是对过度设计的有效免疫。

### 1.8 组织与商业承接

- **方案一**：唯一把组织运营（谁确认/谁审批/谁签字认收益）和激励机制（贡献分成）产品化的方案。
- **方案二**：诊断 09/10 补上了这块（组织运营模板、人机权限矩阵、三列表、付费分阶段），但未进产品。
- **方案三**：五个 gate 是流程性人工节点，但**无 SLA、无角色矩阵、无月度复盘例会设计**——"系统跑起来但没人用"的风险在方案三中最高，因为它离业务方最远（单人执行、纯工程视角）。

## 2. 综合评分与各自定位

| 维度 | 方案一（蓝图） | 方案二（现有体系） | 方案三（DSH 重建） |
|---|---|---|---|
| AI 原生性 | ○（理念深、机制无） | ◐ | ● |
| 治理安全 | ●（理论）/ ✕（实践） | ✕（P0 债务） | ◐（微观强、宏观缺） |
| 任务闭环机制 | ○ | ◐ | ● |
| 反馈飞轮 | ●（设计） | ●（数据）/ ◐（口径） | ◐（只回流故障树） |
| 经营归因 | ● | ◐（L1-L2） | ✕（缺失） |
| 交付落地 | ✕（纯纸面） | ◐（重但完整） | ◐（前提未验证、部署故事缺） |
| 复用模型 | ◐ | ✕（跨仓困难） | ● |
| 组织商业承接 | ● | ◐（诊断有、产品无） | ✕ |

**一句话定性**：

- 方案一是"**该卖什么**"的答案（产品与商业理论）；
- 方案二是"**怎么交付**"的答案（私有化工程与证据纪律，附带安全债）；
- 方案三是"**AI 时代平台机制该怎么设计**"的答案（管理面/运行面分离 + 管理时发布，附带商业视角缺位）。

## 3. 针对性优化建议

### 3.1 对方案一（04-05 蓝图）的建议

**核心问题：它是一份"所有层都要自建"的隐含假设下的八层全景图，恰恰有自己第 7 节警告的中台幻觉风险。**

1. **定义"平台最小内核"**。八层中真正不可外包、构成第一天壁垒的只有三件：统一 Task 对象 + 受控写回网关 + 反馈/EVI 字段。语义层、治理层、知识层应有明确的 build/buy/integrate 决策（例如治理目录直接集成而非自研一个 Atlan）。建议为每层标注"自建 / 集成 / 暂缓"三档，把八层全景图改造成分层决策记录。
2. **吸收方案三已解决的问题**。04-05 对"AI 能力层"和"任务层"的运行时机制是含糊的。方案三的三个机制可以直接补进蓝图：① 管理面/运行面分离（Agent 平台宕机 ≠ 业务闭环停摆）；② 管理时发布而非运行时控制（生产知识只经版本化工件生效）；③ 模型只产候选 + 人工 gate 的对称治理。建议把这三条升格为平台产品原则，与"厚场景薄系统"并列。
3. **把 EVI 分级和证据三列表写进 MVP 验收标准**，而不是留在诊断文档里。04-05 的 10.2 节"六件事"里没有反馈口径和 EVI 字段的位置，应补上"第一天就有归因字段"的硬性要求（它自己在 6.7 里说了这句话，但 MVP 清单没有兑现）。
4. **版本治理自身**：04-05 已被 04-06 取代（修订说明写明），但 09/10 两份诊断仍引用 04-05。建议明确 04-06 为唯一规范源，避免三份愿景文档并存造成决策引用混乱。

### 3.2 对方案二（连山现有体系）的建议

1. **安全债单独立项、排最前**。明文密码/默认密码/硬编码 token 不是"后置优化"，是大客户私有化销售的否决项。建议：inventory 全部迁 vault 或至少 ansible-vault、默认密码强制首启轮换、token 按 site 独立签发，并把这套安全整改本身产品化为"安全交付检查表"（它同时是销售资产）。
2. **认可并拥抱方案三的收敛动作**。SPC 四仓合一（DSH 重建）方向正确——这正是诊断 10 §4.1/4.2 说的"平台能力分散、样板变不成模板"的解法。但要求方案三**不得丢弃三样资产**：① lads/dsruntime 中的 feedback 与 EVI 表结构（迁移"可平移清单"必须补上）；② lisen-infra 作为现场部署底座（见下条）；③ 60+ contract test 的"架构约束写成可执行断言"的工程文化。
3. **把"三列表"（工程/生产/商业证据）变成产品管理制度的强制字段**。每个能力没有生产证据就不允许对外宣称，没有商业证据就不进入 gainsharing 谈判。这张表比任何架构图都更接近商业化瓶颈的解药。
4. **停止横向能力的自发生长**。诊断已经指出 runtime/infra/iweb/edge 的横向工程会稀释纵向资产。建议设立一个裁决规则：任何横向能力立项，必须由一个已跑通的场景提出复用诉求（这与方案三"等第二个 profile 触发"的纪律同构）。
5. **数字员工绑定任务角色**（质量诊断员工/参数助手/知识维护员工），放弃"工业 Agent 工作台"的通用叙事——通用入口会被 Dify/Coze/飞书钉钉智能体抹平。

### 3.3 对方案三（spc_dsh）的建议

这是三套中机制设计质量最高、但战略盲区也最明确的方案，建议按优先级：

1. **【最高优先级】补上 EVI 最小闭环**。按方案一 6.7 的原则"不需要财务审计级精度，但第一天就要有经营归因字段"：在 `alert_events` / 闭环结果上加 EVI 最小字段（异常类型、估计损失口径、闭环时长、避免复发标记、客户确认状态），并把 EVI-L1 留痕做进 plugin-workorder 的闭环终点。现在加是几列 schema 的成本，跑了一年后补是重新对齐历史的成本。**没有这一块，方案三重建出来的系统在商业上不比旧系统多值一分钱。**
2. **明确计算节点的现场部署故事，优先复用 lisen-infra**。Q2 目前在 docker/compose/K8s/公司平台间摇摆，但目标客户是制造业私有化现场——方案二已经用 53 个 role 解决了"裸机→可运行工作站"的问题。建议：计算节点以受管服务身份注册进 dokku-admin/lisen-infra 体系（plugin-ops 的 deploy 描述符天然契合这个方向），而不是另起一套部署逻辑。否则方案三会重演"方案二交付复杂度吃毛利"的老问题，只是换了个地方。
3. **把 spike（Q1）设为一切投入的闸门**，且预先写死两条退出路径：唤醒失败 → 轮询扫描 `alert_events`（已设计，好）；DSH rc 版 API 破坏性变更 → 整体迁移评估（插件层薄 + 核心在 PG 的主张目前是断言，建议 spike 时顺带做一个"拔掉 DSH 重接另一个宿主"的成本验证，把这个主张变成被测过的结论）。建议同时锁定 DSH 版本并建立升级策略。
4. **给 SPC profile 加"组织运营模板"**。五个 gate 是状态机，不是运营制度。需要补：每个 gate 的默认责任人角色与 SLA、超时升级路径、误报复盘例会节奏、月度 EVI 报告产物。这部分是纯配置 + 文档，成本极低，但它决定"卡片有没有人点、工单有没有人关"——方案一/二都论证过这是落地成败点，方案三目前完全没有。
5. **平台资产版本纪律从第一天用 CI 强制**，而不是停在 00 §3.6 的文字约定——lisen-infra 的 contract test 模式（把架构约束写成可执行断言）可以直接平移过来，例如强制每个平台包有 changelog、profile 依赖声明在测试中校验。
6. **预定义"第二 profile 触发条件"**，把拧紧判异做成带 go/no-go 标准的具体计划（复用哪些平台资产、新增哪些算子、gate 是否同构），防止"结构先行"的目录划分在无人检验的情况下漂移成第二种纸面平台。
7. **补反馈四去向**：当前回流只指向故障树迭代。至少把"反馈进评测集"（回放对比的历史结论作为 Skill 评测语料）纳入 `05-diagnosis-and-learning.md` 的设计，这是三套方案公认的复利来源。
8. **降低单人依赖**：文档集已经是有意识的知识沉淀（好），但建议把 07-open-questions 的每个未决项指定决策 deadline 和决策人，并把 spike 结果与三轮评审决策同步给至少一名第二工程师。

## 4. 总判断：三合一才是正确路线

三套方案的真实关系不是竞争，而是同一平台三个缺失的侧面：

```text
商业与组织层（该卖什么、谁签字）      ← 方案一贡献：EVI、任务模板、组织运营、付费分层
平台机制层（AI 时代控制面怎么设计）   ← 方案三贡献：管理面/运行面分离、管理时发布、
                                        候选→审批→发布、算子/流水线复用
交付与证据层（怎么落地、怎么取信）    ← 方案二贡献：lisen-infra 私有化底座、PG-first、
                                        contract test 文化、（待治理的）安全整改
```

**建议的统一行动序列**：
