# 04-05a · 从理想 17 个内部案例反观任务闭环平台：需求框架与批判性复审

> 讨论稿 / 会更新 · 最近更新 2026-09-30
>
> **再复审**：本文把案例现状当作检验设计的证据，但**现状是约束条件下的产物——案例的形态混杂着被验证的选择与被迫的妥协**。区分二者的辩证分析见 `04-05b-选择还是妥协：草根与规划的双重批判与平台设计再修正.md`——结论：本文对 Task 对象的降级、对工作台的否定均需修正（案例作者的手工补丁恰恰证明这些模块是真需求）；MVP 收编路径与治理优先级维持，但收编动作增加"补丁升级为标准模块"，规则编译器升为 MVP 级模块。阅读顺序：`04-05`（设计）→ 本文（证据检验）→ `04-05b`（辩证再修正）。
>
> **一句话结论**：17 个一手案例证明 04-05 的核心方向（厚场景薄系统、资产复用、治理先行）大体正确，但其**威胁模型、入口假设和落地路径三处与现场事实错位**：现实发生的不是"业务流各造厚系统"的烟囱化，而是"草根各造薄资产"的碎片化；真实入口不是任务工作台而是飞书对话和终端；正确起点不是新场景从零搭建，而是收编已跑通的存量。平台定位应从"AI Native 任务闭环平台"修正为**"AI 公共品底座（语义、工具注册、资产治理、成本遥测）+ 任务闭环作为可选模板之一"**。

## 0. 这篇回答什么

`04-05` 设计了 AI Native 任务闭环平台的八层架构和九个产品模块，但它成文时手里只有一个设备维修案例（`04-04`）做验证——样本量 1，且是被数字化团队"做出来"的案例，不是业务人员"长出来"的。

现在证据变了。`docs/product-analysis/application-cases/` 已收录理想汽车把 Claude Code 开放给全体业务人员后，业务侧自发生长出的 **17 个案例**：确定性自动化平台（设变监控/耐久仿真/外观跟催）、专业工具 Agent 化（CATIA×2/TRACE32 调试）、知识资产化（流程库/品类/部门知识库/个人蒸馏）、数据分析智能体（质量/计划）、全流程常驻 Agent（研发）、销售门店工具。这些案例是同一政策环境（每人一个 Claude Code 账号 + 开放部分 MCP 与飞书接口 + 内部 AI 社区 / AI Market）的产物，构成一份罕见的**自然实验数据**。

本文做三件事：

1. 从 17 案例归纳企业智能化转型的**需求框架**（业务侧到底在要什么）；
2. 审视"账号 + 接口 + 社区"这种**草根供给模式**产出了什么、积累了哪些问题；
3. 用以上证据**批判性复审 04-05** 的平台设计——每个功能模块的适用性与必要性逐个判定，并给出修正案。

方法说明：所有判断都锚定到具体案例（编号沿用 application-cases 目录收录顺序，"案例四"= 设变断点监控，依次类推），不做无证据的推断。

## 1. 需求框架：17 个案例里业务侧真正在要什么

### 1.1 按用户意图分层的业务需求（L1→L5）

| 层级 | 用户意图 | 案例分布 | 占比感受 |
|---|---|---|---|
| **L1 执行自动化**：把手里的重复活干掉 | 案例四（设变监控）、五（仿真后处理）、六（外观跟催）、十六的九场景中大半（巡检/测试数据/部署） | **最大宗，接近一半** |
| **L2 专业判断辅助**：AI 帮我判定/校验 | 案例三（EHS）、七（装配校核）、九（品类判定）、十（CELN 校验）、十二（工艺合规）、十三（设变评审） | 第二大宗 |
| **L3 知识可及**：问得到、留得住 | 案例二（流程库）、九、十四（部门知识库）、十七（个人蒸馏） | 稳定存在 |
| **L4 分析与推演**：看现状、推未来 | 案例十一（质量分析）、十五（计划工作台）、一（稳定性分析） | 少数但最厚 |
| **L5 决策准备**：方案对比、值多少钱 | 案例十五（唯一，且一半是汇报愿景） | **仅 1 例** |

**第一个关键发现**：需求重心压倒性地落在 L1-L2（执行与判定），而非流行叙事中的"AI 决策"。业务人员要的是"我的活变快、我的判断有校验"，不是"AI 替我决策"。这其实是利好消息——L1-L2 恰好是可验证、可治理、风险可控的区间，四态结论（案例七）和"AI 建议 + 人确认"（几乎所有案例）是自然形成的安全边界。

**第二个关键发现**：L1 需求的满足形态高度分叉——同样的"把重复活干掉"，案例四选了数据工程+规则引擎（无 LLM）、案例五选了 AI Coding 自建平台、案例六选了多维表格零 Token、案例十二选了 Agent 直连。**选型判据已在案例间自发收敛**（确定性流程不用大模型 / 可预先编排用宏+静态门禁 / 假设-验证循环用 MCP 直连），这比任何平台预置的"最佳实践"都更可信——它是被真实成本和失败比出来的。

### 1.2 横切支撑需求（每个案例隐性要求、多数案例未解决）

| 编号 | 支撑需求 | 案例证据 | 解决情况 |
|---|---|---|---|
| D1 | **数据可及**：集成、字段字典、语义 | 案例四集成 154 项系统数据；十一注入 100+ 看板代码与字段说明；十五自述"前两年数据治理才有今天" | **最强的前置条件，也是最贵的**——十五用了两年 |
| D2 | **工具可连**：MCP / 接口封装 | 案例八（TRACE32 MCP 47 工具）、十二（CAA TCP 双通道）、十三（iframe 穿透——反面样本）、十七（lark-cli） | 各自封装，**无共享工具注册** |
| D3 | **知识可治理**：owner、版本、验证 | 案例十四（责任田+当场验证+来源标注——唯一样板）；九（制度 Skill 无更新机制——反面） | 17 案例中仅 1 例做全 |
| D4 | **行为可信**：验证协议、四态结论、权限分级 | 案例七（五步协议）、三（两轮定稿）、十六（prod 硬禁用）、十（本地推理不出门店）、十七（注入防御+脱敏） | 工程侧纪律已成文化，**制度侧（谁能写、写到哪）无机制** |
| D5 | **成本可见**：token / 算力账 | 案例十六因 token 成本限流"仅充电研发可用"——**全公司唯一露出的成本信号** | 无公开账本、无 per-Skill/per-user 口径 |
| D6 | **经验可沉淀**：Skill、剧本、图谱、案例库 | 案例十一（蒸馏剧本）、十六（自动规则）、十四（贡献排行）、八（Debug Skills） | 形态丰富但**无一有质检与版本治理** |

### 1.3 组织侧需求（决定采纳的隐性条件）

17 案例反复出现的组织机制，比技术机制更决定成败：

- **采纳机制**：大白话共创规则（十三）、贡献排行+来源标注（十四）、定期晒效果（十四）、场景驱动而非任务驱动（十四）；
- **责任机制**：责任田分工（十四）、领域 owner 审核（十四）、prod 禁用（十六）；
- **传播机制**：内部社区文章（17/17 全部经社区传播）、AI Market 上架（九、十七）——但阅读量 50~404，**发现靠文章不靠市场**；
- **诚实文化**：坑表（15/17 有）、口径自注（三、十一、十六）——这是这家公司最被低估的资产。

### 1.4 需求框架小结

```text
业务需求（L1 执行 > L2 判定 > L3 知识 > L4 分析 >> L5 决策）
        都压在六项支撑需求上（D1 数据 > D2 工具 > D4 可信 > D3/D6 治理沉淀 > D5 成本）
        而支撑需求的满足率取决于三项组织机制（采纳、责任、传播）
```

**对平台设计的直接含义**：平台的主战场应该是 D1-D6（支撑层）而不是 L 层（业务层）——业务层草根已经做得很好且会继续做好；支撑层是公共品，草根做不动也不该各自做。这是下文复审 04-05 的总纲。

## 2. 草根供给模式复盘：产出、问题、以及它的不可替代性

### 2.1 先公平地承认它赢了什么

"每人一个 Claude Code 账号 + 开放 MCP/飞书接口 + AI 社区"这个模式，在**探索阶段**的绩效超出任何自上而下规划可以达到的水平：

- **需求发现机制有效**：17 个案例全部对应真痛点、真使用（日均 15-25 次、周活 60+、单剧本自动跑 1485 例），没有一个是"为 AI 而 AI"的表演项目；
- **成本结构极优**：单人 + 3 个工作日级别的投入（案例十七 500 行 Python / 3 天）、零 Token 常态运行（案例六）、Level 1 新手即可产出平台级工具（案例五、九、十、十一、十三的作者都是 Level 1-2）；
- **物种谱系自然涌现**：选型判据（六案例谱系）、规则形态谱系（代码→五元组→自然语言）、工具控制两刻度——这些知识是被成本和失败**比出来的**，无法在设计室里预先写出；
- **文化飞轮已经转起来**：坑表文化、诚实口径自注、社区传播——隐性知识正在通过文章快速扩散。

**所以复审的前提立场是：不能因平台化诉求而杀死草根探索。任何"统一收口、统一开发"的修正案都是错的。**

### 2.2 七个正在积累的问题（按危险度排序）

**P1 · 资产碎片化（最严重的结构性问题）**

同域多套系统并存且互不复用：设变域（案例四规则引擎 vs 案例十三 OpenClaw 规则 Skills）、CATIA 域（案例七宏执行 vs 案例十二 CAA 直连——同一家公司的同一种软件接了两遍）、质量域（案例一 vs 案例十一）、知识投喂方法论（案例十四人工投喂 vs 十五自动图谱 vs 十七自动蒸馏——三种路线各自探索无人收敛）。

与 04-05 预言的"烟囱"不同之处在于：**碎的不是系统（都很薄、长在飞书/多维表格/O9 上），碎的是资产**——规则库 × 2（设变）、连接器 × 2（CATIA）、知识库 × N、判定框架 × N。资产才是复用价值的载体，所以碎片化的真实成本比"系统烟囱"更高，也更隐蔽。

**P2 · 治理真空（唯一可能爆雷的问题）**

案例十三的浏览器插件 iframe 穿透 + RPA 绕过系统鉴权取数，是审计事件级的灰区操作，但它作为一个"成功案例"被社区传播——**危险的做法正在被点赞**。案例十六"失败排查路径自动沉淀为 Skill 规则"没有审核环节，错误方法论会固化传染。案例九的品类判定 Skill 无更新机制，ISC 制度改版后 Skill 会静默脱钩——组织级分发的知识资产比纸面过时更危险（用户默认它是最新的）。17 案例中只有案例十七内置了注入防御。

**P3 · 单点维护：人走资产腐烂**

案例十四花了大力气解决"知识不随人走"，但**没有任何案例解决"工具不随人走"**——17 个作品几乎全是单人维护，作者调岗即腐烂。案例八意识到这个问题选择了开源（社区接棒），但这不能作为普遍答案。案例十六的 69K+ 节点代码图谱、案例十一的蒸馏剧本、案例四的 19 维差分规则，全都是"作者在=资产在"的状态。

**P4 · 成本盲区**

唯一的成本信号是案例十六"token 成本考虑仅限充电研发使用"——限流决策背后没有公开的数字。全公司无人知道：AI 用量的总盘子、哪个 Skill 烧钱最多、哪些场景的 ROI 是负的。限流靠拍脑袋意味着**预算辩护能力为零**——下次预算周期这是致命的。

**P5 · 可观测性缺失**

效果证据几乎全部是作者自述。只有案例十一给出了单周遥测明细、案例十四给出日均使用次数——两例诚实，其余十五例没有使用口径。"0.5 天完成小需求""2 分钟巡检 88 服务"无法复核，也就无法横向比较哪个场景该优先投入。

**P6 · 采纳长尾**

社区阅读量 50~404，AI Market 上架的 Skill（九、十七）传播效果未见数据。先锋用户集中（案例十一周活 60+，但活跃分布未知）。**发现机制是"读文章"而不是"搜资产"**——一个部门做了 设变规则，另一个部门做设变相关工具时要靠自己碰运气找到前者。

**P7 · 平台选型发散**

OpenClaw（六失败/十三成功/十四成功）、Coze/Dify（被否）、多维表格（六胜出）、自建（四、五）、本地 CLI（十）——选型判断散落在各案例正文里，靠社区文章传播。好消息是边界已经比出来了（飞书生态+Skill 叠加→OpenClaw；表单协同→多维表格；确定性→自建），坏消息是**这个选型知识还没有被制度化为公司级标准**，每个新项目仍要重新踩一遍。

### 2.3 草根模式的正确定位

```text
草根模式 = 卓越的探索机制（Explore）+ 零沉淀治理机制（Exploit）
17 个案例 = Explore 阶段的完整产出
```

它证明了需求、验证了物种、降低了成本、养成了文化——四件事任何平台都替代不了。它没做的（也没能力做的）是：资产注册、质量治理、成本记账、继任机制、横向复用。**这恰好就是平台该做的全部——不是替业务造场景，是给草根补公共品。**

## 3. 对 04-05 的总体批判：三处与现场事实的错位

### 3.1 错位一：威胁模型——"厚系统烟囱"没有发生，发生的是"薄资产碎片"

04-05 全篇的立论基点是"围绕每条业务流造一套管理系统"会导致烟囱化（§2 的三段论证）。但 17 个案例显示业务人员**根本不爱造系统**：

- 案例六明确拒绝自研，直接长在多维表格上（"零代码、零服务器、零 Token"），并明确论证"业务系统与个人 Agent 解耦"；
- 案例十五明确"不替代 O9/SAP，只做决策准备层"；
- 最重的案例十一也只是一个智能体 + 工具包，不是管理系统；
- 17 个案例的交付物形态是：Skill（3）、机器人（3）、薄平台（4）、MCP Server（1）、知识库（3）、CLI 工具（1）、多维表格（1）、蒸馏管线（1）。

**AI Coding 时代做"系统"太便宜了，以至于没人囤积系统——大家囤积的是资产**（规则库、知识库、图谱、剧本、判定框架）。所以 04-05 §2.1-2.2 论证的"数据重复、权限重复、流程重复"风险成立但位置错了：数据没有重复（都从数仓/O9/SAP 读），**重复的是规则、知识、连接器、判定框架**。

这个错位直接动摇 04-05 的产品重心：如果敌人是"厚系统"，解法是"任务闭环平台替代系统"；如果敌人是"薄资产碎片"，解法是"资产注册与治理底座"——平台不需要承载业务流（草根+飞书承载得很好），只需要承载资产。

### 3.2 错位二：入口假设——"任务工作台"没有用户，真实入口是飞书和终端

04-05 §9.2/9.3 把"任务工作台"和"Copilot 面板"设计为用户日常入口（"我的任务/待确认 AI 建议/待审批事项"看板）。但 17 个案例的入口事实是：

- **飞书对话**是绝对主入口：案例十四（群 @ 机器人）、十六（私聊+群聊 Sage，"全程飞书内完成"反复强调）、十三（OpenClaw 机器人推送）、三/四（飞书工单群）；
- **终端 CLI** 是重度用户入口：案例十（本地 Claude CLI）、七（Claude Code Skill）、十七（Claude Code）；
- **CATIA/SAP 等专业软件**本身是工程师的"工作台"：案例七/十二明确"让 CATIA 做判断，让 AI 做编排"；
- 案例十五的 Web 工作台是唯一例外，且它服务的是"计划员"这个无专业软件依托的岗位。

**没有一个人为新界面离开飞书。** 案例六的判断（"业务系统与个人 Agent 解耦，日报是唯一 LLM 触点"）和十四的选型理由（"群里 @ 就能用"）说明入口的竞争货币是**零迁移成本**。04-05 把交互形态做进平台核心模块，会直接把平台做成第 18 个"要用就得打开"的东西——在飞书生态里这等于死刑。

修正方向：工作台不是产品模块，是**协议能力**——平台应输出"任务上下文、AI 建议、确认动作"到飞书卡片 / 终端 / 现有系统界面，自身无界面或只有治理后台。

### 3.3 错位三：落地路径——MVP 不该"新场景从零搭建"，该"收编存量"

04-05 §10 的 MVP 路径是：选设备维修场景 → 按六件事从零搭建 → 跑通后抽象平台能力 → 扩场景。这条路径隐含"平台先于场景"的建设顺序，而且**完全忽略了已经存在的 17 个跑通场景**。

案例证据指向相反的路径：资产迁移比新建便宜，且已被验证。案例十一已经站在"100+ 看板代码 + 数仓字段字典 + 蒸馏剧本"的资产堆上（平台化只差治理与复用机制）；案例十六已经站在"代码图谱 + 40 Skill + 权限硬禁用"上；案例四已经站在"154 系统集成"的数据底座上。**收编 2-3 个存量案例做平台化改造，比新建一个设备维修场景更能证明平台价值**——因为它回答的问题正是草根回答不了的："你的资产能不能被我接住并变成全公司的？"

## 4. 逐模块复审：八层架构与九个产品模块的必要性判定

先给判定总表（证据强度：⭐=个别案例支持，⭐⭐=多案例支持，⭐⭐⭐=跨案例强收敛）：

| 04-05 模块 | 必要性判定 | 证据强度 | 核心修正 |
|---|---|---|---|
| 连接层（L0-L3 读写分级） | **必要，且应升格** | ⭐⭐⭐ | 工具注册与声明式权限应为一等公民（吸收十六 prod 禁用实践） |
| 语义层（本体/口径） | **最高必要性** | ⭐⭐⭐ | 全企业本体→域内生长+最小共享对象联邦 |
| 知识层（GraphRAG） | **必要，形态修正** | ⭐⭐ | RAG 已够用的案例占多数；图谱按域按需 |
| 任务层（Task 对象/状态机） | **有条件必要——降级为可选模板** | ⭐ | 17 案例中多数无任务状态机 |
| AI 能力层（Skill 市场） | **必要，补质量信号** | ⭐⭐⭐ | 缺使用遥测/评价回流，市场≠目录 |
| 治理层（权限/血缘/审计） | **必要，大幅裁剪** | ⭐⭐⭐ | 七种血缘→两种；绕鉴权必须先堵 |
| 反馈层（人审/采纳/蒸馏） | **必要，吸收野生形态** | ⭐⭐ | 十一/十四/十六已有三个野生变体 |
| 经营归因层（EVI） | **当前低必要，规模化后高必要** | ⭐ | 移出 MVP；定位为"预算辩护基建" |
| 9.2 任务工作台 | **不必要（独立形态）** | ⭐⭐ | 降级为飞书/终端的嵌入协议 |
| 9.3 Copilot 面板 | **不必要（独立形态）** | ⭐ | 同上 |
| 9.7 价值归因看板 | **延后** | ⭐ | 见经营归因层 |

### 4.1 连接层：判定"必要且应升格"——但重心从数据连接转向工具注册

04-05 §5.3 的 L0-L3 读写分级被案例强验证：案例十六（prod 部署在 Skill 中硬禁用=L2/L3 分界的实践）、四（自动建工单=L2 回写）、八（烧录真芯片=L3 风险）。

但案例暴露了一个 04-05 低估的点：**工具本身需要注册与声明**。案例八开源 47 个 MCP 工具无权限分级声明；案例十三用插件绕鉴权——说明"接口开放给谁、声明了什么权限、实际干了什么"没有任何登记处。十六的做法（权限写进 Skill 配置=代码级资产随分发生效）是最佳实践，应平台化为**MCP 工具注册中心：每个工具声明只读/写/环境级风险，Agent 调用策略从声明继承**，而不是依赖提示词自觉或个人插件技巧。

### 4.2 语义层：判定"最高必要性"——但本体要联邦不要中心

17 案例对语义层的验证是压倒性的：案例十五直言系统的快速搭建归功于"前两年集成计划建设把数据规范化"（两年尺度的治理前置）；案例十一把"数仓字段说明+看板分析代码"当知识注入（"分析代码即知识"）；案例四集成 154 项系统数据。**D1 数据可及是所有案例的第一道工序**——04-05 把语义层放第二层是对的，甚至可以 arguing 它是第一层。

修正：04-05 §6.1 的"业务对象与本体中心"若做成中心化建模器，将重蹈中台覆辙（§7 自己也警惕这一点）。案例的现实是：域内本体已自发出现——案例十二的 30+ SE 对象、十六的代码图谱、十的车型知识库。**正确形态是最小共享对象联邦**：全公司只统一四五个对象（人员/零件/供应商/车型/成本中心）的 ID 与口径，各域本体自生长、按需引用共享对象。案例十四的"知识联邦制"（各管各专业+审核负责人）就是这个模式在知识层的实践，可直接平移到本体层。

### 4.3 知识层：判定"必要但形态修正"——多数场景 RAG 已够，图谱按域按需

04-05 §6.4 的 GraphRAG 愿景（沿关系检索：报警码→设备型号→历史故障→SOP→专家）很美，但 17 案例的知识形态现实是：**RAG + 来源标注已覆盖大多数场景**（案例二/九/十四都是），图谱只有两例（十六代码域——可自动抽取所以先落地；十五业务域——仍在规划）。§7.3 的知识分类表（稳定规则/历史案例/动态状态/经营指标分治）被案例强支持，保留。

修正：图谱的可行性排序=数据结构化程度排序（代码>配置>制度文档>口头经验），平台不应提供"全企业知识图谱"，应提供**抽取与联邦的工具**，域内图谱按需生长。同时必须补 04-05 缺失的一环：**知识失效机制**——案例九的制度改版脱钩风险、十四的"标注日期版本"实践、十五的"设变联动标记受影响知识"设想，指向同一个需求：知识资产要与源系统事件（制度改版/设变/车型变更）建立触发式失效告警。

### 4.4 任务层：判定"有条件必要"——Task 对象只覆盖少数场景，不应是平台核心

这是对 04-05 **最实质的降级**。04-05 §6.2 把 19 字段的 Task 对象称为"平台的核心"，一切能力围绕任务状态机组织。但 17 案例的真实形态分布是：

- 有任务闭环的：案例一（受理→交付）、三（五场景闭环）、六（四阶段状态机）、四（监控→工单→回写）——4 例；
- **无任务状态机的：一次性分析（十一）、知识问答（二/九/十四）、工具编排（七/八/十二）、消息蒸馏（十七）、全流程伴随（十六，Sage 没有任务对象只有对话与 Skill 编排）——13 例**。

对这 13 例，强制 Task 化是过度工程——它们的自然形态是**对话 + Skill + 资产**，不是工单。04-05 §8 的"异常事件→任务闭环→知识资产→经营归因"抽象只对案例三/六这类管理流成立。

修正：Task 对象从"平台核心"降级为**场景模板之一**（管理流类场景用状态机，分析/知识/工具类场景用会话+资产）。平台的真正核心移到资产与治理层（见 §5）。

### 4.5 AI 能力层：判定"必要但缺了关键一环"——市场不是目录，是带质量信号的市场

AI Market 已存在（案例九/十七上架），但阅读量与上架效果说明**上架≈放进仓库**。04-05 §6.3 的 Skill 结构化注册（输入/输出 schema、评测集、owner、版本）设计很好且被案例支持（十四的来源标注、八的 Debug Skills），但缺的是**回流信号机制**：哪个 Skill 被调用多少次、命中多少、失败案例在哪、谁 fork 改进了。案例十一的遥测明细是唯一标杆口径，应平台化为所有 Skill 的默认遥测。没有这个，市场就只是目录，采纳长尾（P6）无法解决。

### 4.6 治理层：判定"必要但大幅裁剪"——先堵两个现实漏洞，再谈七种血缘

案例证明治理是刚需（P2 治理真空的三个证据：绕鉴权、无审核沉淀、制度脱钩），04-05 方向对。但 §6.5 的设计过度：**七种血缘**（数据/文档/知识/Prompt版本/Agent行为/人工确认/经营结果）在 17 案例中没有一种被实现或被需求过。真实发生过的治理需求只有三种：环境级禁用（十六）、数据出域（十的本地推理、十七的脱敏）、鉴权边界（十三的违规）。

修正：血缘从七种裁到**两种**（数据血缘+AI 调用审计），加上成本遥测。04-05 完全没提的**成本模块**（P4）必须补为治理层一等公民：per-Skill / per-user / per-scenario 的用量与成本口径——这是十六"限流靠拍脑袋"问题的唯一解，也是预算辩护的数据基础。

### 4.7 反馈层：判定"必要，且应吸收而非重造"——三个野生形态就是设计稿

04-05 §6.6 的反馈层（采纳/修正/结果回写/经验蒸馏+专家审核）被案例强支持，但最好的设计素材已经在案例里：

- **案例十一的三段演进**（知识注入→场景预设→蒸馏剧本进定时任务）= 反馈层的自动化形态；
- **案例十四的当场提问验证+贡献排行** = 反馈层的人审与激励形态；
- **案例十六的自动规则沉淀（无审核）** = 反馈层的**反面教材**——恰好验证 04-05"AI 自动总结的经验要经专家审核才能发布"这条红线是真实约束而非过度设计。

另一处需要修正：04-05 以"采纳率"为核心反馈指标，但案例十一的价值证据是"自动跑 1485 例"（自动化量）而非采纳率——**自动化程度与采纳率是两个正交维度**（全自动场景无"采纳"动作，其反馈指标应是结论进入决策的比例/失败率）。反馈层的指标体系应按自动化等级分档。

### 4.8 经营归因层：判定"当前低必要、规模化后高必要"——它是政治基建不是产品功能

17 案例无一实现经营归因，最接近的案例十五也停在规划。这不是因为案例作者不想证明价值，而是**草根模式下没人需要先证明 ROI 才能干活**（成本极低+自己受益）。04-05 §6.7"从第一天就有经营归因字段"对草根是伪需求。

但两个信号说明它迟早变成刚需：案例十六的 token 限流（预算压力已经出现）、案例十五作为汇报材料的性质（管理层投资需要账）。修正：归因层**移出 MVP**，定位改为"规模化阶段的预算辩护基建"——当 AI 用量需要年度预算辩护时启动，口径从案例十五的"这个决策值多少钱"（业务+财务双闭环）切入，而非 04-05 的 EVI 分成体系（对内部激励的适用性在 17 案例中零证据，反而是十四的"贡献排行"这种轻量荣誉机制被验证有效）。

### 4.9 场景应用层/工作台层（§5.2、§9.2、§9.3）：判定"不必要（作为独立产品形态）"

见 §3.2 的入口分析。修正：平台对场景的输出是**资产与协议**（模板包、规则库、Skill、飞书卡片协议、终端上下文注入），不是界面。案例六（长在多维表格）、十五（唯一例外，因计划员无专业软件依托）共同给出边界：只有"无既有系统依托的岗位"才需要新界面——这是少数派场景，做成模板选项而非平台标配。

## 5. 平台设计修正案

### 5.1 定位重述

```text
原（04-05）：AI Native 任务闭环平台
            ——用统一业务对象/任务状态/Skill/知识/权限/反馈/归因承载多条业务流

修正：      AI 公共品底座（主体）+ 任务闭环模板（选项之一）
            ——业务流留给草根和飞书；平台做草根做不动的四件公共品：
            ① 语义（最小共享对象联邦 + 字段字典）
            ② 工具（MCP 注册中心 + 声明式权限 + 鉴权正门）
            ③ 资产（规则/知识/Skill 的注册、版本、owner、失效、继任）
            ④ 账本（用量/成本/质量信号遥测）
```

### 5.2 新增模块（04-05 未设计、案例证明必需）

1. **成本与用量遥测**（堵 P4/P5）：per-Skill/per-user/per-scene 用量与成本，全公司账本公开化——案例十一遥测明细为默认口径；
2. **MCP 工具注册与安全分级**（堵 P2/D2）：工具声明式权限（只读/写/环境风险），调用策略继承声明，禁止未注册工具进生产——案例十三的绕鉴权立即收编进正门；
3. **资产继任与退出机制**（堵 P3）：每个 Skill/规则库/图谱/知识库强制登记 owner + 继任规则，owner 离岗触发移交或归档——"工具不随人走"与"知识不随人走"同等重要；
4. **知识失效联动**（堵 D3）：知识资产与源系统事件（制度改版/设变/车型变更）建立触发式告警——案例十四"标注日期版本"+ 案例十五"设变联动标记"的机制化；
5. **经验沉淀的质检通道**（堵 P2）：吸收十四"当场验证"与十一"蒸馏剧本"，所有自动沉淀（十六式）必须经审核入库；
6. **边缘推理选项**（D4）：本地 CLI/门店推理作为架构位（案例十），统一推理服务不能违反出域合规。

### 5.3 MVP 路径修正：从零搭建 → 存量收编

```text
第一刻（收编而非新建）：
  选 2-3 个已跑通案例做平台化收编——
  案例十一（资产最厚：看板代码+字段字典+剧本，缺治理与复用）
  案例十六（入口最真实：飞书+图谱+Skill，缺图谱同步与质检）
  案例四（数据底座最全：154 系统集成，缺规则版本化）
  收编动作只做四件事：资产注册进平台、接通工具注册与鉴权正门、
  挂上成本与质量遥测、登记 owner 与继任——业务功能一行不改

第二刻：用收编后的公共品支撑新场景（验证"草根用平台比不用快"）
第三刻：场景模板中心/联邦本体/归因看板按需启动
```

这条路径对 04-05 §10 的替换是本质性的：**平台的第一个用户不是新场景的业务方，而是已有资产的草根作者**——平台对他们的价值主张是"你的资产交给我，获得治理、复用、记账和继任，你的工具照旧跑"。

### 5.4 保留不变的部分（复审确认正确）

以下判断被 17 案例强验证，应原样保留：厚场景薄系统（§4.1，被案例六推到更极端）、数据不搬家语义统一（§4.3，D1 证据）、AI 必须受控不自由乱跑（§4.4，prod 禁用实践）、先闭环后智能（§4.2，三段演进实践）、不塞一个 RAG（§7.3 知识分类表）、不让 AI 绕过组织责任（§7.4，十六反面教材）、壁垒在资产不在页面（§12，与 P1 结论一致）。

## 6. 收束

17 个案例回答了 04-05 当年只能靠推理回答的问题，答案有三层：

1. **需求框架**：业务侧要的是执行与判定（L1/L2），不是决策；压在六项支撑需求上，其中数据可及（D1）最贵也最前置——这是两年前就该开始投的，现在开始也不晚；
2. **草根模式**：卓越的探索机制 + 零沉淀治理——七个问题里资产碎片化、治理真空、单点维护是结构性的，必须由平台层解决，但解决方式是补公共品不是收口开发；
3. **平台修正**：威胁从厚系统改为薄资产、入口从工作台改为飞书与终端、核心从 Task 对象改为资产与治理、路径从新建改为收编——**平台的第一个价值动作是接住 17 个案例已经长出来的资产，而不是证明自己能再长出第 18 个。**
