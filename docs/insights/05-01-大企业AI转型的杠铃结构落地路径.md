# 05-01 · 大企业 AI 转型的杠铃结构落地路径

> 讨论稿 / 会更新 · 最近更新 2026-09-15
>
> **一句话结论**：大企业 AI 转型不要从"建平台 / 改组织 / 买工具"开始，而要从一个高价值黑洞场景开始，用真实经营结果反推组织、平台、考核和 P&L。

---

## 0. 这篇回答什么

`05-企业侧转型.md` 已经解释了为什么企业 AI 转型需要"杠铃结构"：底部放开、顶部薄平台、中间不要。但如果只停留在结构边界，企业还是不知道第一步怎么走。

这篇只回答一个问题：

> 大型制造 / 能源 / 汽车 / 高端装备企业，如何从今天的 AI 混乱状态，一步步落地杠铃结构？

默认企业画像：

- 已有 IT / 数据 / 数字化团队；
- 已有 ERP / MES / QMS / PLM / 数据平台等基础系统；
- 已有局部 AI 试点、工具采购或一线野生 agent；
- 但还没有组织级反馈闭环、收编机制、经营归因和 P&L 对齐。

核心主线不是"先建 AI 中台"，而是：

```text
先选黑洞场景
  ↓
90 天跑通第一个闭环
  ↓
12 个月完成收编、治理、考核、P&L 对齐
  ↓
3 年形成 AI-native 组织常态
```

---

## 1. 起点不是组织架构，而是黑洞场景

大企业最常见的错误，是一上来就讨论组织架构：要不要成立 AI 委员会、要不要建 AI 中台、要不要全员发工具、要不要统一采购模型。

这些都不是第一步。第一步应该是选一个能吸住数据、任务、人才和管理注意力的**黑洞场景**。

黑洞场景的选择公式：

```text
黑洞场景 = 经营价值 × 数据闭环 × 组织可推动性
```

| 维度 | 判断问题 | 低分信号 | 高分信号 |
|---|---|---|---|
| 经营价值 | 能不能挂到库存、延期、产能、良率、报废、返工、客诉、现金流？ | 只是办公提效、报告生成、知识问答 | 能直接影响经营指标，业务一号位愿意关注 |
| 数据闭环 | 有没有输入、决策、执行、结果、反馈？反馈周期多快？ | 只有历史文档，没有结果回填 | 每次决策后都有执行和结果，可持续记录 |
| 组织可推动性 | 有没有明确业务 owner？是否能改流程？跨部门阻力有多大？ | 只有 IT 或数字化部门热 | 业务负责人愿意背指标，现场愿意配合改流程 |

不要选"听起来最 AI"的场景，要选能形成组织引力的场景。一个合格黑洞场景，会让数据、流程、专家经验、管理注意力和预算不断向它聚集。

---

## 2. 三类优先黑洞场景

### 2.1 供应链管理

典型问题：

- 供应商风险预警；
- 物料短缺；
- 交付延期；
- 库存积压；
- 质量风险前移；
- 采购、计划、物流、质量脱节。

为什么重要：

- 经营价值极高，能直接连到库存、交付、现金流、停线风险；
- 高层容易听懂，不需要把价值解释成抽象 AI 指标；
- 一旦跑通，会天然牵引采购、计划、质量、生产、财务协同。

最大难点：

- 跨部门严重；
- 数据分散在采购、计划、物流、质量、供应商体系；
- 责任归属复杂；
- 很多问题发生在企业边界之外，供应商不一定配合。

建议定位：

```text
供应链管理适合作为 12 个月扩展场景，不一定适合作为第一个 90 天场景。
```

如果第一步就从全局供应链优化切入，很容易陷入跨部门泥潭。更稳的方式是先从供应商质量风险、关键物料缺料、某一类交付延期等局部切口开始。

### 2.2 排产 / 计划优化

典型问题：

- 订单优先级；
- 产能约束；
- 设备瓶颈；
- 换型成本；
- 计划频繁变更；
- 人工排产经验不可复制。

为什么重要：

- 反馈周期短；
- 结果可衡量；
- 与产能、交付、库存直接相关；
- 很适合智能体辅助决策。

最大难点：

- 约束复杂；
- 现场真实约束常常不在系统里；
- 人工经验强，老计划员未必愿意把判断逻辑外化；
- 如果只做算法最优，可能与现场执行相冲突。

建议定位：

```text
排产适合作为第一批黑洞场景，但要控制范围：先从一个产线 / 一个车间 / 一个产品族开始。
```

不要一上来做全厂 APS 重构。先把某个局部场景中的约束、决策、人工修正和实际结果沉淀下来。

### 2.3 生产良率 / 质量闭环

典型问题：

- 良率波动；
- 工艺参数异常；
- 设备状态影响质量；
- 报废 / 返工；
- 客诉；
- 根因分析靠专家经验。

为什么重要：

- 数据闭环相对清晰；
- 与质量损失、报废、返工、客诉直接相关；
- 很适合沉淀"结果 + 推理过程 + 实际结果"；
- 容易把 AI 价值讲成经营语言。

最大难点：

- 需要打通工艺、设备、质量、检验、供应商数据；
- 根因归因难；
- 现场可能不愿意把经验外化；
- 如果考核仍按人工处理量，专家没有动力教会 AI。

建议定位：

```text
生产良率 / 质量闭环最适合作为 90 天启动场景之一。
```

它通常比供应链更局部，比全局排产更容易形成反馈闭环，也更容易用 EVI 证明价值。

---

## 3. 90 天启动：先跑通一个最小闭环

90 天的目标不是"上线一个 AI"，而是回答：

```text
这个场景有没有资格成为组织级黑洞？
```

### 第 0–2 周：选场景

动作：

1. 用"经营价值 × 数据闭环 × 组织可推动性"打分；
2. 只选一个场景；
3. 明确业务 owner；
4. 明确一个经营指标；
5. 明确数据范围；
6. 明确 90 天不追求大而全，只追求闭环。

输出物：

```text
黑洞场景立项单
```

立项单至少写清：

| 字段 | 内容 |
|---|---|
| 场景 | 例如某产线良率波动、某产品族排产、某类关键物料风险 |
| 业务 owner | 对经营指标负责的人，不是 IT 项目经理 |
| 经营指标 | 良率、报废、返工、延期、库存、停线、现金流等 |
| 数据范围 | 输入数据、人工决策记录、执行结果、业务结果 |
| 90 天目标 | 跑通反馈闭环，而不是追求全自动 |

### 第 3–6 周：建最小反馈闭环

动作：

1. 梳理输入数据；
2. 梳理当前人工决策过程；
3. 记录 AI / 人的建议；
4. 记录执行结果；
5. 记录实际业务结果；
6. 记录人工修正理由。

关键规则：

```text
每次 AI 介入，都必须留下：
输入 → 判断/推理 → 建议动作 → 人工修正 → 执行结果 → 业务结果
```

这条链路比模型本身更重要。没有它，系统不会学习，组织不会沉淀，项目结束就归零。

### 第 7–10 周：引入 Agent / 工作流

不要一上来做全自动。顺序应该是：

```text
先做人机协同
再做局部自动
最后再提高 AI 自主运营比例
```

每个 agent 都要标清：

- 决策权限：建议、需授权执行、可自动执行；
- 人类监督档位：in-the-loop、on-the-loop、out-of-the-loop；
- 失败兜底机制：谁接管、多久接管、如何回滚；
- 数据记录方式：是否记录输入、推理、动作、修正、结果；
- 业务指标：它到底影响哪个经营数字。

### 第 11–12 周：做 EVI 复盘

90 天结束时不要只问"AI 好不好用"，要问：

1. 经营指标有没有变化；
2. 哪些收益可归因；
3. 哪些只是相关不是因果；
4. 哪些流程必须改变；
5. 哪些 agent / 工具值得收编；
6. 哪些不值得继续；
7. 业务 owner 是否愿意继续背指标；
8. 数据闭环是否能持续自动记录。

如果这 8 个问题答不上来，就不是黑洞场景，只是一个 AI 试点。

---

## 4. 12 个月扩展：从试点到杠铃结构

12 个月目标是从"一个试点"进入"组织结构变化"。这里才真正开始落地杠铃。

### 4.1 收编机制

把野生 agent 分四类：

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 个人效率工具 | 写邮件、总结会议、生成周报 | 允许存在，只做轻治理 |
| 小团队工作流 | 班组质量复盘、计划员辅助排程 | 登记、监控、共享模板 |
| 影响业务决策的 agent | 供应商风险建议、排产建议、质量异常判断 | 必须进入收编流程 |
| 影响经营结果 / 风险 / 合规的 agent | 自动拦截批次、自动调整计划、自动触发采购动作 | 必须产品化、审计、设兜底 |

收编流程：

```text
发现 → 登记 → 评分 → 加固 → 产品化 → 复用 → 下放
```

评分维度：

| 维度 | 高分信号 |
|---|---|
| 经营价值 | 已经影响经营指标 |
| 复用潜力 | 不只一个人或一个班组能用 |
| 数据闭环 | 输入、推理、动作、结果、修正都能记录 |
| 风险等级 | 权限边界清楚，有兜底机制 |
| 业务 owner | 有人愿意背结果 |

### 4.2 薄顶部平台团队成型：交付企业 AI 控制面

顶部团队不是产能中心，而是管"规则和复利"。这句话如果只停在原则层，会很空；真正的落地形态不是 Excel 台账，而是一套轻量的**企业 AI 控制面**（AI Operating Platform / AI Control Plane）。

可以借用云计算的 control plane / data plane 区分：

| 层 | 谁负责 | 具体含义 |
|---|---|---|
| **业务运行面（data plane）** | 业务一线 / BU | 真正使用和运营 agent：发现需求、配置工作流、审核建议、反馈结果、背经营指标 |
| **AI 控制面（control plane）** | 顶部薄平台团队 | 不替业务干活，但统一模型入口、权限、登记、评估、审计、可观测、复用、收编和 EVI 口径 |

所以顶部团队交付的不是"更多 agent"，而是让业务能**安全、低成本、可复用地长出 agent** 的平台能力。

最小 AI 控制面至少包括十个模块：

```text
企业 AI 控制面
├── 1. Model Gateway：统一模型 / token 入口
├── 2. Agent Registry：agent 资产目录
├── 3. Agent Manifest：agent 标准描述文件
├── 4. Permission Layer：人 / agent / 数据 / 工具权限
├── 5. Evaluation Pipeline：上线前和迭代时评估
├── 6. Observability & Audit：成本、质量、调用、审计、反馈闭环
├── 7. Asset Catalog：复用组件、连接器、模板、评估集
├── 8. EVI Playbook：价值归因方法、指标口径、实验模板
├── 9. Knowledge Gateway：企业知识访问层，含轻量 ontology / semantic layer
└── 10. Channel Adapter：钉钉 / 企业微信 / 飞书 / 邮件 / 会议入口
```

#### 4.2.1 Model Gateway：统一模型和 token 入口

企业不能让每个部门自己拿 Claude、OpenAI、DeepSeek、通义、火山、私有模型的 key 到处接。否则会出现：成本不可控、数据边界不可控、调用不可审计、出问题不知道哪个 agent 干的。

顶部平台应该提供统一模型网关：

```text
业务 agent
  ↓
企业 Model Gateway
  ↓
Claude / OpenAI / DeepSeek / 通义 / 火山 / 私有模型 / 行业模型
```

它管的不是"发 token"，而是：

| 能力 | 具体管什么 |
|---|---|
| 模型路由 | 什么任务用外部强模型，什么任务必须走私有模型，什么任务可用低成本模型 |
| 成本控制 | 每个 BU、项目、agent 的 token 配额、预算、限流和异常告警 |
| 数据策略 | 哪些字段必须脱敏，哪些数据不能出企业边界，哪些场景禁止调用外部模型 |
| fallback | 主模型不可用、质量下降或成本过高时切到哪个备用模型 |
| 调用日志 | 记录调用时间、agent、模型、成本、延迟、错误、输入输出摘要 |
| 成本归因 | token 成本归属到具体场景和业务 owner，而不是 IT 大锅饭 |

业务方感受到的不是"自己申请 API key"，而是：我申请一个 agent 项目，平台给我一条受控的模型调用通道、预算和权限。

#### 4.2.2 Agent Registry：登记不是表格，而是 manifest

agent 登记可以有表格视图，但底层不应是 Excel，而应是标准化的 `Agent Manifest`。每个进入业务场景的 agent 至少要写清：

```yaml
agent_id: quality-defect-diagnosis-agent
name: 质量异常诊断 Agent
owner:
  business_owner: 质量部负责人
  platform_owner: AI 控制面负责人
scenario: 生产良率
business_metric:
  primary: 一次良率
  secondary:
    - 返工率
    - 报废率
    - 异常定位时间
model:
  default: claude-sonnet
  fallback: deepseek
risk_level: high
data_access:
  - MES
  - QMS
  - SPC
  - 设备传感器数据
tools:
  - query_quality_records
  - query_equipment_logs
  - generate_root_cause_report
human_supervision:
  mode: human-on-the-loop
  required_approval_before:
    - 调整工艺参数
    - 停线建议
eval_suite:
  - historical_defect_cases_v1
  - false_alarm_regression_v1
logging:
  trajectory_log: enabled
  human_correction: required
evi:
  baseline_period: 2026-Q1
  target_metrics:
    - 异常定位时间下降 30%
    - 报废率下降 5%
status: pilot
```

manifest 的意义不是"留档"，而是让平台知道：谁负责、解决什么问题、能访问什么数据、能调用什么工具、风险等级是什么、有没有人类审核、通过了哪些评估、成本归到哪里、经营效果怎么算。

#### 4.2.3 Permission Layer：权限要拆成人、数据、工具三层

企业 agent 的风险不只是"说错话"，而是可能读错数据、调错系统、代表人执行了不该自动执行的动作。所以权限要拆成三层：

| 权限层 | 管什么 | 示例 |
|---|---|---|
| 人能不能用 agent | 用户、角色、组织、班组、岗位 | 只有质量工程师能用质量诊断 agent |
| agent 能不能看数据 | 数据源、字段、行列级权限、脱敏策略 | 可读 MES/QMS/SPC，但不能读薪酬和无关财务数据 |
| agent 能不能执行动作 | 工具调用、写回系统、审批、回滚 | 可生成排产建议；写回 APS 前必须人工确认 |

最关键的是第三层。动作权限应显式分级：

| 动作类型 | 默认策略 |
|---|---|
| 查询数据 | 可自动执行，但必须记录日志 |
| 生成建议 | 可自动生成，并标注依据摘要和置信度 |
| 改写业务系统 | 必须人工确认 |
| 影响客户、财务、生产安全的动作 | 必须审批和留痕 |
| 停线、调价、改工艺参数、自动下单 | 默认禁止自动执行，只能建议 |

这才是 human-in-the-loop / human-on-the-loop 的工程化落地：不是写一句"人在回路中"，而是在平台上配置哪些动作只能建议、哪些动作需授权、哪些动作可自动执行。

#### 4.2.4 Evaluation Pipeline：上线前必须过评估流水线

业务会说"这个 agent 挺好用"，但企业需要知道它是不是稳定、是不是幻觉严重、是不是只在 demo 里好用、是不是成本过高、是不是比人工更好。

顶部平台要提供类似 AI CI/CD 的评估流水线：

| 评估项 | 例子 |
|---|---|
| 准确性 | 对历史缺陷 / 缺料 / 排产冲突案例，判断是否接近专家结论 |
| 稳定性 | 相同输入、相近输入下输出是否一致，是否容易漂移 |
| 可解释性 | 是否提供决策依据摘要，而不是只给结论 |
| 风险 | 是否会建议明显不合理的采购量、停线动作或工艺调整 |
| 成本 | 单次建议消耗多少 token，是否有低成本模型替代方案 |
| 人工接管 | 异常情况下是否提醒人介入，是否能回滚 |
| 业务收益 | 是否减少缺货、库存、报废、返工、延期或定位时间 |

对应平台能力包括：历史 case 集、golden dataset、regression test、prompt / workflow / agent 版本管理、评估报告、上线门槛。

#### 4.2.5 Observability & Audit：沉淀反馈闭环，而不是只留聊天记录

agent 跑起来后，顶部平台必须能回答：谁用了它、用在哪个场景、花了多少钱、访问了什么数据、调用了什么工具、给了什么建议、人有没有采纳、后来结果怎么样、有没有人工纠错。

建议记录的是业务治理所需的轨迹，而不是原始模型思维链：

```text
输入快照
→ 使用的数据源
→ 调用的工具
→ 输出结果
→ 决策依据摘要
→ 人工采纳 / 驳回
→ 人工修正原因
→ 实际业务结果
→ 成本、延迟、错误
```

这条链路就是 `05` 总论里说的"反馈数据"。没有它，就没法审计、复盘、评估、训练、EVI 归因，也没法判断哪个野生 agent 值得收编。

#### 4.2.6 Asset Catalog：复用的不是 prompt，而是一组资产

顶部管"复利"，复利来自复用。可复用资产不只是 prompt，而是一整个 AI 资产目录：

| 复用资产 | 示例 |
|---|---|
| 数据连接器 | MES、ERP、CRM、WMS、QMS、PLM |
| 工具调用 | 查库存、查订单、查工艺参数、查设备日志 |
| prompt / workflow 模板 | 质量异常分析、供应商风险分析、排产冲突解释 |
| 评估集 | 历史缺陷案例、历史排产冲突、历史供应商延期 |
| guardrail | 敏感信息脱敏、禁止自动下单、禁止输出价格策略 |
| UI 组件 | 审核面板、追溯面板、人工修正面板 |
| EVI 模板 | 库存优化、良率提升、排产效率提升的价值归因模板 |

业务不是从零做 agent，而是在控制面里选择连接器、工具、模板、评估集和审批流，拼出自己的场景。

#### 4.2.7 收编流程：用数据决定谁从野生变官方

顶部不要一开始就管死所有创新，而是让野生 agent 在安全边界内先跑；当它出现复用价值和经营价值，再进入收编。

收编触发条件可以包括：

- 月活用户或关键岗位使用频率超过阈值；
- 被多个团队重复使用；
- 人工采纳率高、错误率低；
- 有明确 EVI 或经营指标改善；
- 访问的数据和工具稳定；
- 有跨 BU / 跨工厂复用价值。

收编后要做的是产品化，而不是把创新收走：

| 野生阶段 | 收编后 |
|---|---|
| 某个业务人员自己的 prompt / workflow | 变成官方 agent 或官方模板 |
| 数据连接临时写死 | 变成标准 connector |
| 没有评估集 | 补历史 case 和 regression test |
| 没有权限边界 | 加 RBAC / ABAC / 审批 / 回滚 |
| 没有日志 | 接入统一观测和审计 |
| 成本没人管 | 接入 Model Gateway 和预算 |
| 只在一个部门可用 | 产品化成跨部门组件 |
| 作者离职就没人维护 | 设 owner、版本、SLA 和下线机制 |

#### 4.2.8 EVI Playbook：业务背结果，财务认数字，平台管口径

EVI 不是顶部团队替业务算所有账，而是提供统一方法，让业务和财务一起算。顶部平台应交付：

```text
EVI 模板 + 数据口径 + 实验设计 + 仪表盘
```

以生产良率 agent 为例：

| 字段 | 内容 |
|---|---|
| baseline | 过去 3 个月一次良率、报废率、返工率、异常定位时间 |
| intervention | 上线质量异常诊断 agent |
| treatment group | 使用 agent 的产线 / 产品族 |
| control group | 暂未使用 agent 的产线 / 产品族 |
| primary metric | 一次良率提升 |
| secondary metric | 异常定位时间、返工率、报废金额 |
| attribution window | 上线后 30 / 60 / 90 天 |
| finance sign-off | 财务确认节省金额是否成立 |
| business owner | 质量负责人背经营结果 |
| platform owner | 平台负责数据口径、日志和计算方法 |

一句话：**业务背结果，财务认数字，顶部平台管口径**。

#### 4.2.9 Knowledge Gateway：企业知识访问层，不能只是向量库

AI 控制面还必须提供通用知识层。没有企业知识，agent 只能做通用问答；有了受控知识访问，agent 才能理解企业自己的 SOP、会议决策、工艺规则、历史异常、供应商记录和业务系统上下文。

但 Knowledge Gateway 不能等同于"把 PDF 丢进向量库"。它应当是企业知识的受控访问层：

| 子能力 | 管什么 | 为什么重要 |
|---|---|---|
| Source Connectors | 文档、Wiki、SOP、会议、IM、工单、ERP、MES、QMS、PLM、CRM | 知识来自真实工作流，不只来自静态文档 |
| Permission Filter | 继承原系统权限，并叠加用户权限与 agent 权限 | 防止 agent 通过知识库越权看数据 |
| Hybrid Retrieval | 关键词、向量、元数据、时间线、实体关系混合检索 | 料号、批次、缺陷码不能只靠语义相似 |
| Citation & Evidence | 返回来源、版本、时间、证据片段和依据摘要 | 企业决策需要证据链，不接受"AI 觉得" |
| Knowledge Feedback | 人工修正、采纳、驳回、实际结果反哺知识库 | 知识库要随着业务反馈变新，而不是静态档案馆 |
| Knowledge API | 给 agent 调用的统一检索接口 | agent 不直接绕过权限去搜原始系统 |

权限规则可以简化成一句话：

```text
用户权限 ∩ agent 权限 ∩ 知识源权限 = 实际可检索范围
```

这层尤其适合从黑洞场景开始做最小版本。例如生产良率场景，不需要先接全公司知识，只需接入质量 SOP、历史缺陷案例、MES/QMS/SPC 相关数据、设备日志、异常复盘和质量群里的正式决策。

#### 4.2.10 Ontology / Semantic Layer：从黑洞场景长出业务语义层

Knowledge Gateway 里还需要一层轻量 ontology / semantic layer。原因很简单：企业里同一个对象有很多叫法，不同系统字段互相对不上，agent 如果只做向量检索，会把"相似文本"当知识，却未必理解这些东西在业务上怎么连接。

ontology 在这里不是学术工程，而是一套关键业务对象、属性、关系和口径的语义标准：

| 问题 | 没有 ontology | 有 ontology |
|---|---|---|
| 同物异名 | MES 叫 `line_id`，QMS 叫 `production_line`，报表叫"产线" | 统一映射到 `ProductionLine` |
| 同名异物 | "批次"在采购、生产、质检里含义不同 | 区分 `MaterialLot`、`ProductionBatch`、`InspectionBatch` |
| 关系不清 | agent 不知道缺陷和设备、工艺、供应商之间的关系 | 明确 `Defect -> occurs_in -> ProcessStep` |
| 归因困难 | EVI 只能说"上线 AI 后指标好像变了" | 建立 `Action -> affects -> KPI` 的关系 |

三类黑洞场景可以先定义最小 ontology：

| 场景 | 核心实体 | 核心关系 |
|---|---|---|
| 供应链 | Supplier、Material、MaterialLot、PurchaseOrder、Delivery、Inventory、QualityIssue、RiskEvent | Supplier supplies Material；Delivery fulfills PurchaseOrder；RiskEvent affects Delivery |
| 排产 | CustomerOrder、ProductionOrder、Product、BOM、Routing、ProcessStep、WorkCenter、Equipment、Constraint、Schedule | Product follows Routing；Schedule assigns ProductionOrder to WorkCenter；Constraint limits Schedule |
| 生产良率 | Product、ProductionBatch、MaterialLot、Supplier、ProcessStep、Equipment、EquipmentParameter、Inspection、Defect、RootCause、CorrectiveAction、KPI | ProductionBatch consumes MaterialLot；Defect occurs_in ProcessStep；CorrectiveAction mitigates RootCause；CorrectiveAction affects KPI |

Agent Manifest 也应声明自己使用的领域 ontology：

```yaml
ontology:
  domain: manufacturing-quality
  version: v1.2
  entities:
    - ProductionBatch
    - MaterialLot
    - Supplier
    - ProcessStep
    - Equipment
    - Defect
    - RootCause
    - CorrectiveAction
    - KPI
  relations:
    - ProductionBatch consumes MaterialLot
    - MaterialLot supplied_by Supplier
    - Defect occurs_in ProcessStep
    - CorrectiveAction mitigates RootCause
    - CorrectiveAction affects KPI
```

注意，不要一上来做覆盖全公司的大一统 ontology。正确路径是：

```text
从黑洞场景定义统一词表
→ 抽出核心实体 schema
→ 定义关键关系
→ 沉淀实例和反馈
→ 多个场景之间逐步合并
```

早期用 YAML / JSON Schema / 数据字典 / 主数据编码就够了；中后期再考虑 property graph、RDF/OWL/SHACL。ontology 的目标不是炫技，而是让 agent 能检索、理解、引用、归因和审计。

#### 4.2.11 Channel Adapter：接入钉钉 / 企业微信 / 飞书

AI 控制面还必须进入员工日常工作的地方。大多数员工不会每天打开一个新的 AI 平台；agent 要真正改变流程，就要进入钉钉、企业微信、飞书、邮件、会议、OA、工单系统。

但接入协作平台不能让每个 agent 自己直连，否则会长出新的"影子 AI"。正确架构是统一 Channel Adapter：

```text
钉钉 / 企业微信 / 飞书 / 邮件 / 会议 / 工单
        ↓
Channel Adapter
        ↓
AI 控制面：身份、权限、Agent Registry、Model Gateway、Knowledge Gateway、Tool Gateway、Audit Log
        ↓
Agent Runtime
```

Channel Adapter 至少要管：

| 能力 | 具体管什么 |
|---|---|
| 身份映射 | 钉钉 / 企微 / 飞书用户映射到企业 IAM 用户 |
| 群 / 频道权限 | agent 能不能进某个群，能不能读取历史消息 |
| 上下文边界 | 只读本次 @ 后上下文，还是允许读取特定范围历史 |
| 卡片交互 | 审批、确认、驳回、修改、人工修正原因 |
| 主动推送 | 异常预警、待审批动作、任务提醒 |
| 数据脱敏 | 发给模型前脱敏客户、合同、价格、个人信息 |
| 审计日志 | 谁在什么群调用了什么 agent，访问了什么知识，输出了什么建议 |
| 知识沉淀 | 哪些会议纪要、群聊决策、工单结论可进入 Knowledge Gateway |

例如生产良率场景，最小可行版本不是全公司 bot，而是只接一个"质量异常作战群"：agent 被 @ 后读取指定质量知识、查 MES/QMS/SPC、生成诊断建议、让质量工程师确认或修正，再把结果写入反馈日志。

通讯平台不是知识库本身，而是知识入口和人机协同界面：

```text
群聊 / 会议 / 审批 / 工单
  ↓
清洗、结构化、权限过滤
  ↓
Knowledge Gateway
  ↓
可检索、可引用、可审计的知识资产
```

一句话：**Knowledge Gateway 解决 agent 知道什么，Channel Adapter 解决 agent 在哪里和人协作，ontology 解决这些知识在业务上是什么意思。**

#### 4.2.12 最小可行路径：先做控制面，不要先造大平台

最怕的是把"AI 控制面"又做成三千万、一年期的大平台项目。正确顺序应该是：

| 阶段 | 要做什么 | 不做什么 |
|---|---|---|
| 控制面 MVP（伴随第一个黑洞场景的 90 天闭环） | 统一模型网关、agent manifest、基础权限、基础日志、1–2 个评估集、token 成本归因、人工修正入口；Knowledge Gateway 只接该场景必要知识源，ontology 只做统一词表和核心实体 | 不做大而全门户，不追求覆盖全公司，不先做全企业知识图谱 |
| 5–10 个 agent 后 | 做内部 AI 控制台：我的 agent、可用模型、可用连接器、评估报告、成本、待审核动作、修正反馈；抽象 Channel Adapter 接入一个协作平台 | 不把所有需求都收回顶部做，不让每个 agent 自己接钉钉 / 企微 / 飞书 |
| 12 个月后 | 形成企业 AI 操作系统：申请、配置、评估、审批、上线、观测、EVI、收编、下线全流程；逐步扩展 Knowledge Gateway、ontology 和多平台 Channel Adapter | 不让平台团队按工单量扩张，不为平台完整性牺牲黑洞场景闭环 |

因此 4.2 的核心结论是：

```text
顶部集中的是控制面，不是产能；交付的是平台能力，不是替业务做项目。
```

不该管：

- 替业务想需求；
- 替业务承包所有交付；
- 以工单量证明自己价值；
- 把所有野生创新都卡成审批流程；
- 为了平台完整性先做一年基础建设。

顶部团队的 KPI 应该是 agent 复用率、收编成功率、反馈数据完整率、高风险事件数、token 成本 / 业务价值比、EVI 被财务认可的项目数、业务自助完成率、从野生 agent 到正式 agent 的周期。

### 4.3 业务一号位开始背 P&L

从第一个黑洞场景扩展到多个场景时，必须明确：

```text
AI 转型不是 IT 项目，是业务经营项目。
```

责任转移：

| 阶段 | 谁主责 | 背什么 |
|---|---|---|
| 试点期 | 业务 owner + 顶部平台共担 | 单场景闭环和指标变化 |
| 扩展期 | 业务一号位 | 经营结果和流程改变 |
| 常态期 | 业务部门 | AI 作为自己的生产方式 |

CDO / CIO / 顶部平台负责人不应该替业务背 P&L。他们背的是治理、标准、数据资产、安全和收编机制。

### 4.4 考核从"人干了多少"改成"人机系统贡献多少"

旧考核奖励"人自己多干活"，新考核要奖励"人把 AI 管好、训好、用好"。

| 旧考核 | 新考核 | 目的 |
|---|---|---|
| 个人处理量 / 工单数 | 人机联合产出 | 让人愿意把活交给 AI |
| 人工准确率 | 审核质量、漏审率、拦截率 | 奖励会监督 AI 的人 |
| 故障后补救 | 兜底成功率、接管时效 | 奖励 on-the-loop 能力 |
| 项目上线数 | agent 复用贡献、收编贡献 | 奖励沉淀和复用 |
| 部门局部 KPI | 可归因经营增量 | 避免虚荣指标 |

任何单一指标都会被博弈，所以必须成组使用。拦截率要和漏审率一起看，接管次数要和故障率一起看，agent 数量要和经营增量一起看。

## 5. 3 年目标态：AI-native 组织常态

3 年后不应只是"上线了很多 AI 应用"，而是形成一种新常态：

```text
业务部门自己会发现高价值场景
一线能长出野生 agent
顶部能快速收编
数据能持续反馈
考核奖励人机协同
P&L 能证明 AI 价值
```

可观察指标：

| 指标 | 含义 | 警惕 |
|---|---|---|
| AI 自主运营比例 | 多少业务动作由 AI 独立或半独立完成 | 不能脱离风险等级盲目追高 |
| 硅基员工占比 | AI agent 在组织中的有效劳动占比 | 不能变成"上了多少机器人"的虚荣 KPI |
| 黑洞场景数量 | 已经形成反馈飞轮的核心场景数量 | 宁可少而深，不要多而散 |
| Agent 收编率 | 野生 agent 中有多少进入受支持产品 | 收编不是审批一切 |
| 反馈数据质量 | 是否沉淀输入、推理、动作、结果、修正 | 没有实际结果回填就不算闭环 |
| 可归因经营增量 | AI 对库存、良率、交付、成本等指标的贡献 | 必须能区分因果和相关 |

目标不是让 AI 替代所有人，而是让组织从"人直接干活"逐步变成"人设计、监督、兜底、优化人机系统"。

## 6. 三类场景的落地路线差异

| 场景 | 适合作为 90 天启动？ | 适合作为 12 个月扩展？ | 最大难点 | 建议路径 |
|---|---|---|---|---|
| 生产良率 | 高 | 高 | 根因归因、现场经验外化 | 先做单产线 / 单产品族质量闭环，再扩展到供应商和工艺 |
| 排产 | 中高 | 高 | 约束复杂、计划频繁变化 | 先做人机协同排产建议，再逐步自动化局部约束 |
| 供应链 | 中 | 极高 | 跨部门、跨公司、责任边界复杂 | 先从关键物料 / 供应商风险切入，再扩展到全链路协同 |

大企业最稳路径通常不是先做最大场景，而是：

```text
先用良率 / 局部排产跑通闭环
再扩展到供应链这种经营价值更大但组织阻力更高的场景。
```

## 7. 行动清单

### 7.1 CEO / 业务一号位

- [ ] 选一个黑洞场景，而不是同时铺开十个 AI 试点。
- [ ] 指定业务 owner，而不是只让 IT 负责。
- [ ] 明确一个经营指标。
- [ ] 接受 90 天先跑闭环，不追求全自动。
- [ ] 允许流程和考核被试点反推修改。

### 7.2 CDO / CIO / 顶部平台负责人

- [ ] 建最小治理护栏，而不是大而全 AI 中台。
- [ ] 建 agent 登记和收编机制。
- [ ] 规定反馈数据链路：输入、推理、动作、修正、结果。
- [ ] 建 EVI 复盘模板。
- [ ] 不以工单量证明团队价值。

### 7.3 一线业务团队

- [ ] 把人工决策过程记录下来。
- [ ] 记录为什么采纳或修正 AI 建议。
- [ ] 反馈实际业务结果。
- [ ] 把有复用价值的野生 agent 上报收编。
- [ ] 从"自己干活"转向"监督 AI 干活"。

## 一句话收口

```text
大企业自建杠铃，不是先画组织图，而是先让一个黑洞场景转起来。
```

黑洞转起来之后，组织、平台、考核、P&L 才有真实抓手；否则所有 AI 转型都会退化成工具采购、PPT 中台或一线散兵。
