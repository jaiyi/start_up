# 航天总体能力地图与数字化转型路线图

## 开篇摘要

航天总体不是单一专业，也不是普通项目管理。它是型号研制中的系统中枢，负责把任务目标、用户需求、轨道/环境/任务剖面、载荷、平台、分系统、性能指标、成本周期、风险、试验验证和交付运维组织成一个可研制、可验证、可交付、可运行的完整航天系统。

一句话判断：

> 航天总体数字化转型的主线，不是先做一个“大平台”或“AI 总体工程师”，而是先把总体能力对象化，再把对象关系数字线程化，再把专业工具流程化，最后让受控 Agent 嵌入任务流。

这篇文档先给第一版框架，重点回答三个问题：

```text
1. 航天总体有哪些典型能力？
2. 航天总体任务流通常如何展开？
3. 数字化转型应该按什么路线推进？
```

适用范围优先覆盖：

```text
通用航天型号总体
+ 航天器总体
+ 总体院 / 总体部能力体系
```

后续可以按具体方向继续细化：卫星、深空探测器、空间站载荷、运载火箭、导弹/飞行器、地面运控系统等。

## 1. 航天总体的角色定位

航天总体的核心职责不是替代各专业，而是组织多专业共同收敛。

它要回答的问题包括：

```text
任务为什么要做？
系统边界在哪里？
顶层能力如何分解？
哪些指标是刚性的，哪些可以 trade-off？
平台、载荷、分系统如何分工？
接口如何定义和冻结？
仿真和试验如何证明系统满足需求？
风险如何识别、接受、关闭？
技术状态如何受控？
运行经验如何反哺下一代型号？
```

所以，航天总体能力可以概括为：

```text
任务理解能力
+ 系统架构能力
+ 多专业协同能力
+ 指标闭环能力
+ 接口管控能力
+ 仿真验证能力
+ 风险决策能力
+ 型号工程治理能力
+ 知识复用能力
```

从数字化视角看，总体工程师不是“文档生产者”，而是型号数字线程的组织者。

可以把航天总体能力拆成十个一级能力域。

```text
航天总体能力地图
├── 1. 任务论证与需求工程能力
├── 2. 系统架构与总体方案设计能力
├── 3. 指标分解与预算闭环能力
├── 4. 多专业协同设计能力
├── 5. 接口与构型管控能力
├── 6. 仿真分析与数字样机能力
├── 7. 可靠性、安全性与风险控制能力
├── 8. 试验验证与 V&V 能力
├── 9. 型号工程管理与配置管理能力
└── 10. 运行支持、在轨运维与知识沉淀能力
```

## 3. 能力域一：任务论证与需求工程

这是总体工作的起点。

典型任务：

| 能力 | 说明 |
|---|---|
| 任务目标分析 | 明确任务目的、用户价值、使用场景、成功判据 |
| 任务剖面设计 | 定义发射、转移、在轨、任务执行、退役等全过程 |
| 轨道 / 弹道 / 飞行任务分析 | 根据任务目标设计轨道、窗口、覆盖、重访、能量需求 |
| 用户需求捕获 | 从用户语言转成工程需求 |
| 需求分解 | 从任务级需求分解到系统级、分系统级、设备级 |
| 需求确认 | 判断需求是否完整、一致、可验证 |
| 约束识别 | 识别成本、周期、质量、发射条件、环境、接口等约束 |

典型输入：

```text
任务背景
用户需求
应用 / 作战场景
轨道与环境约束
发射条件
历史型号经验
标准规范
预算与周期约束
```

典型输出：

```text
任务需求说明
任务剖面
系统需求规格说明
初步技术指标
关键约束清单
任务成功判据
需求追踪矩阵初稿
```

数字化转型重点：

```text
需求结构化
需求追踪
需求一致性检查
需求变更影响分析
需求-指标-方案-试验闭环
```

## 4. 能力域二：系统架构与总体方案设计

| 关键技术识别 | 找出系统成败依赖的关键技术和风险点 |

## 5. 能力域三：指标分解与预算闭环

航天总体有大量“预算”工作。这里的预算不是财务预算，而是系统资源预算。

典型预算包括：

```text
质量预算
功率预算
热预算
数据率预算
存储预算
时间预算
精度预算
可靠性预算
指向预算
姿控预算
推进剂预算
通信链路预算
结构刚度 / 强度裕度预算
安全裕度预算
```

典型任务：

| 能力 | 说明 |
|---|---|
| 顶层指标分解 | 从任务指标分解到分系统指标 |
| 资源预算建立 | 建立质量、功率、热、数据、推进剂等预算表 |
| 裕度管理 | 设置设计裕度、增长裕度、验证裕度 |
| 闭环更新 | 随设计迭代持续更新预算 |
| 超差预警 | 发现某项资源超限或趋势恶化 |
| 指标权衡 | 当一个指标超差时，通过其他指标或方案调整平衡 |
| 需求-指标-方案追踪 | 每个指标都有来源、分配对象和验证方式 |

典型输出：

```text
质量预算表
功率预算表
热控预算表
数据链路预算表
推进剂预算表
可靠性分配表
指标分解矩阵
指标闭环状态表
超差问题清单
```

数字化转型重点：

```text
预算数据结构化
指标自动汇总
跨专业影响分析
版本化预算基线
指标超差预警
设计更改影响自动传播
```

这类工作非常适合数字化和 Agent 化，因为当前大量工作仍依赖 Excel、人工汇总和专家经验。

## 8. 能力域六：仿真分析与数字样机

航天总体离不开仿真，但总体关注的不是单一 CAE 工具，而是仿真是否能够支撑系统级决策。

典型仿真类型：

```text
轨道仿真
姿态控制仿真
通信链路仿真
热仿真
结构强度 / 模态仿真
动力学仿真
电源能量平衡仿真
任务覆盖仿真
可靠性仿真
故障传播仿真
系统级联合仿真
```

总体关注点：

```text
仿真输入是否来自受控设计状态；
仿真模型是否可信；
仿真工况是否覆盖需求；
仿真结果是否能支撑决策；
仿真结论是否进入指标和风险闭环。
```

典型任务：

| 能力 | 说明 |
|---|---|
| 仿真任务定义 | 明确仿真目的、输入、工况、输出 |
| 仿真模型管理 | 管理模型版本、适用范围、校核状态 |
| 工况管理 | 管理载荷、边界、轨道环境、热环境等工况 |
| 仿真执行协调 | 调度专业工具和计算资源 |
| 结果判读 | 判断结果是否满足指标 |
| 结果追踪 | 把结果关联到需求、指标、设计状态和评审 |
| 模型可信度评估 | 判断模型是否经过验证、误差范围如何 |

数字化转型重点：

```text
仿真流程自动化
仿真模型版本管理
仿真工况库
结果结构化解析
CAE Agent
仿真证据链
数字样机 / Digital Twin
```

这和前面讨论的 CAE Simulation Agent 是同一条主线。

## 13. 航天总体典型任务流

可以把航天总体任务流分成八个阶段。

```text
0. 任务机会识别
1. 任务论证与概念方案
2. 系统需求与总体方案
3. 初步设计
4. 详细设计
5. 生产集成与试验验证
6. 发射交付与在轨测试
7. 在轨运行与经验回灌
```

### 13.1 阶段 0：任务机会识别

目标：判断任务是否有价值、是否可行、是否值得立项。

主要活动：

```text
应用场景分析
用户需求访谈
任务价值评估
初步技术可行性分析
约束条件识别
竞争方案分析
成本周期粗估
```

主要交付物：

```text
任务设想
应用场景说明
初步需求清单
技术可行性判断
立项建议
```

数字化机会：

```text
历史任务案例检索
需求相似性分析
任务价值模型
成本周期类比估算
```

### 13.2 阶段 1：任务论证与概念方案

目标：形成可比较的多个总体概念方案。

主要活动：

```text
任务剖面设计
轨道 / 弹道初步分析
载荷能力分析
平台能力估算
资源预算粗分配
关键技术识别
风险识别
方案 trade-off
```

主要交付物：

```text
任务论证报告
概念方案
初步总体指标
初步资源预算
关键技术清单
风险清单
方案对比矩阵
```


主要活动：


## 15. 数字化转型的核心目标

航天总体数字化转型应该从以下五个目标展开。

### 15.1 需求到验证的数字闭环

```text
任务目标
→ 系统需求
→ 分系统需求
→ 设计方案
→ 指标预算
→ 接口
→ 仿真分析
→ 试验验证
→ 验证证据
```

每一个结论都能追溯来源和证据。

### 15.2 从文档中心转向模型中心

传统模式：

```text
Word / Excel / PPT 是主线，模型和数据只是附件。
```

目标模式：

```text
结构化需求、架构模型、指标模型、仿真模型、验证模型是主线，文档从模型和数据自动生成。
```

### 15.3 从单专业工具转向系统级数字线程

不是让所有专业使用同一个工具，而是建立跨专业的数据连接。

```text
需求工具
MBSE 工具
CAD / CAE 工具
PLM
试验数据系统
问题归零系统
知识库
运控系统
```

通过统一 ID、接口、数据标准和 trace link 串起来。

### 15.4 从人工经验复用转向知识资产复用

把历史型号经验从“老专家脑子里”和“文档库里”释放出来。

```text
历史方案
典型问题
故障模式
评审意见
仿真案例
试验异常
归零报告
设计准则
```

沉淀成可检索、可推荐、可校验的知识资产。

### 15.5 从人工辅助工具转向受控 Agent 协同

Agent 不是替代总体工程师，而是承担：

```text
资料检索
需求初筛
一致性检查
预算汇总
接口冲突提示
仿真任务编排
试验证据整理
评审材料生成
风险相似案例召回
```

关键工程判断、技术状态批准、风险接受必须由人负责。

## 16. 数字化转型路线图

建议采用五阶段路线。

```text
阶段 1：数据和文档治理
阶段 2：需求、指标、接口结构化
阶段 3：MBSE + 多专业协同
阶段 4：仿真与试验数字闭环
阶段 5：AI / Agent 驱动的智能总体
```

### 16.1 阶段 1：数据和文档治理

目标：先把分散资料管起来、找得到、分得清、控得住。

建设内容：

```text
型号文档库
知识库
统一目录体系
文档元数据
权限体系
版本管理
标准模板
历史资料清洗
```

阶段成果：

```text
文档不再散落个人电脑；
历史资料可以检索；
关键文档有版本；
知识库可以支撑问答和案例检索。
```

### 16.2 阶段 2：需求、指标、接口结构化

目标：把总体最核心的三类对象结构化：需求、指标、接口。

建设内容：

```text
需求管理
指标预算管理
接口管理
配置项管理
问题风险管理
评审结论管理
```

阶段成果：

```text
需求可以追踪；
指标可以汇总；
接口可以查询；
变更可以分析影响；
评审问题可以闭环。
```

这是航天总体数字化最关键的一步。

### 16.3 阶段 3：MBSE + 多专业协同

目标：用模型表达系统架构、功能、行为、接口和状态。

建设内容：

```text
系统架构模型
功能分解模型
任务模式模型
接口模型
参数模型
专业模型注册
模型间 trace link
```

阶段成果：

```text
总体方案不再只存在 PPT；
功能、接口、指标、模式可以在模型中表达；
专业设计可以和总体模型产生连接。
```

注意：MBSE 不应一开始追求“大而全建模”。建议从三个最有价值的场景切入：

```text
需求-功能-系统架构追踪
接口模型
指标预算模型
```

### 16.4 阶段 4：仿真与试验数字闭环

目标：把仿真和试验从单次分析报告，变成可追踪、可复用、可验证的数字证据。

建设内容：

```text
仿真任务管理
仿真模型库
仿真工况库
仿真结果解析
CAE 流程自动化
试验数据管理
验证证据链
```

阶段成果：

```text
某个指标为什么满足，可以追溯到仿真/试验证据；
某个仿真结果来自哪个模型、哪个工况、哪个版本；
试验异常可以和历史问题关联；
报告可以自动生成大部分草稿。
```

### 16.5 阶段 5：AI / Agent 驱动的智能总体

目标：用受控 Agent 辅助总体工程师完成高频、复杂、跨专业工作。

```text
总体工程 Agent

接口 Agent / Skill
CAE Agent / Skill
V&V Agent / Skill
风险 Agent / Skill

```

前提：

```text
必须有结构化数据；

必须有人审 workflow；
必须有工程规则和验证证据；
不能让 Agent 直接成为最终责任主体。
```

## 18. 优先落地场景

不建议一开始做“大而全数字总体平台”。建议先选高价值、高频、可闭环的场景。

### 18.1 第一优先级：需求-指标-验证闭环

为什么优先：

```text
这是总体工作的主线；
结构化难度适中；
价值非常明确；
后续所有数字线程都依赖它。
```

MVP：

```text

指标预算表
验证矩阵
trace link
评审问题闭环
```

### 18.2 第二优先级：指标预算自动汇总与超差预警

为什么优先：

```text
质量、功率、热、数据率等预算是总体日常高频工作；
Excel 人工汇总容易错；
很适合自动化和 Agent 辅助。
```

MVP：

```text
质量预算
功率预算
数据率预算
预算版本
裕度规则
超差预警
变更影响分析
```

### 18.3 第三优先级：接口管理和 ICD 结构化

为什么优先：

```text
接口问题是型号研制中的高频风险源；
接口冲突常常跨专业、跨单位；
结构化后价值很大。
```

MVP：

```text
接口对象
接口双方
接口类型
接口参数
接口状态
接口变更
接口验证证据
```

### 18.4 第四优先级：CAE / 仿真流程数字化

为什么优先：

```text
仿真是设计决策的重要证据；
但当前工具链复杂、不确定性大；
适合从受控小场景做 MVP。
```

MVP：

```text

工况检查
solver 调用
结果解析
裕度计算

```

### 18.5 第五优先级：评审材料和设计报告自动生成

为什么优先：


## 20. 关键风险与实施建议

### 20.1 风险一：只做文档电子化，不做对象结构化

表现：

```text
系统上线了，但还是上传 Word / PDF；
数据不能联动；
无法做影响分析；
Agent 只能问答，不能执行。
```

建议：

```text
优先建 Requirement / Metric / Interface / Evidence 等核心对象模型。
```

### 20.2 风险二：MBSE 过度建模

表现：

```text
一开始就追求完整 SysML；
工程师负担重；
模型和真实设计脱节；
最终变成演示工程。
```

建议：

```text
从需求-功能-接口-指标三个高价值闭环切入。
```

### 20.3 风险三：AI 越权

表现：

```text
Agent 自动改需求；
Agent 自动批准仿真结论；
Agent 自动关闭风险；
Agent 自动生成正式报告并发布。
```

建议：

```text
Agent 只做建议、检查、草稿、编排；
正式技术状态必须人审；
所有动作必须审计。
```

### 20.4 风险四：工具集成优先级错误

表现：

```text
先集成大量 CAD / CAE / PLM 工具；
但没有统一对象模型；
最后接口复杂、数据不一致。
```

建议：

```text
先定义核心数据对象和 ID，再做工具适配。
```

### 20.5 风险五：没有配置基线

表现：

```text
需求版本、模型版本、仿真版本、报告版本互相对不上。
```

建议：

```text
建立数字基线：
需求基线 + 架构基线 + 指标基线 + 模型基线 + 验证基线。
```

```text
Requirement
```

## 22. 总结判断

从资深总体设计工程师 + 数字化转型视角看，航天总体数字化的主线应该是：

```text
先把总体能力对象化；
再把对象关系数字线程化；
再把专业工具流程化；
再把仿真和试验证据闭环化；
最后再引入 Agent 做智能协同。
```

不要反过来一开始就做“AI 总体工程师”。正确路径应该是：

```text
结构化数据
→ 数字线程
→ 模型协同
→ 流程自动化
→ 人机协同 Agent
```

最推荐的第一批落地场景：
