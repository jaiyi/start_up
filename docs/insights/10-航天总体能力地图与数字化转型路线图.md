# 航天总体能力地图与数字化转型路线图

## 开篇摘要

航天总体不是单一专业，也不是普通项目管理。它是型号研制中的系统中枢，负责把任务目标、用户需求、轨道/环境/任务剖面、载荷、平台、分系统、性能指标、成本周期、风险、试验验证和交付运维组织成一个可研制、可验证、可交付、可运行的完整航天系统。

一句话判断：

> 航天总体数字化转型的主线，不是先做一个“大平台”或“AI 总体工程师”，而是先把总体能力对象化，再把对象关系数字线程化，再把专业工具流程化，最后让受控 Agent 嵌入任务流。

这篇文档先给第一版框架，重点回答三个问题：

```text
1. 航天总体有哪些典型能力？
2. 航天总体任务流通常如何展开？
3. 数字化转型应该按什么路线推进？
```

适用范围优先覆盖：

```text
通用航天型号总体
+ 航天器总体
+ 总体院 / 总体部能力体系
```

后续可以按具体方向继续细化：卫星、深空探测器、空间站载荷、运载火箭、导弹/飞行器、地面运控系统等。

---

## 1. 航天总体的角色定位

航天总体的核心职责不是替代各专业，而是组织多专业共同收敛。

它要回答的问题包括：

```text
任务为什么要做？
系统边界在哪里？
顶层能力如何分解？
哪些指标是刚性的，哪些可以 trade-off？
平台、载荷、分系统如何分工？
接口如何定义和冻结？
仿真和试验如何证明系统满足需求？
风险如何识别、接受、关闭？
技术状态如何受控？
运行经验如何反哺下一代型号？
```

所以，航天总体能力可以概括为：

```text
任务理解能力
+ 系统架构能力
+ 多专业协同能力
+ 指标闭环能力
+ 接口管控能力
+ 仿真验证能力
+ 风险决策能力
+ 型号工程治理能力
+ 知识复用能力
```

从数字化视角看，总体工程师不是“文档生产者”，而是型号数字线程的组织者。

可以把航天总体能力拆成十个能力域，并作为能力地图下的二级编号展开。

```text
航天总体能力地图

├── 2.3 指标分解与预算闭环能力
├── 2.4 多专业协同设计能力
├── 2.5 接口与构型管控能力

├── 2.7 可靠性、安全性与风险控制能力
├── 2.8 试验验证与 V&V 能力
├── 2.9 型号工程管理与配置管理能力
└── 2.10 运行支持、在轨运维与知识沉淀能力
```

### 2.1 任务论证与需求工程

这是总体工作的起点。它的核心价值是把“用户想要什么”翻译成“工程系统必须满足什么”。如果这个阶段做得粗，后面所有方案、指标、接口、试验都会被反复返工。

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 任务目标分析 | 明确任务目的、用户价值、使用场景、成功判据 | 不是简单记录“做一颗卫星/一个载荷”，而是要说清楚它服务什么业务或任务，例如覆盖、观测、通信、导航、验证新技术，成功和失败如何判定。 |
| 任务剖面设计 | 定义发射、转移、在轨、任务执行、退役等全过程 | 任务剖面是后续轨道、能源、热控、通信、运控、试验设计的共同上下文。比如低轨遥感、地球同步通信、深空探测的剖面完全不同。 |
| 轨道 / 弹道 / 飞行任务分析 | 根据任务目标设计轨道、窗口、覆盖、重访、能量需求 | 这一步把任务目标变成可计算的工程约束，例如轨道高度、倾角、重访周期、测控可见性、太阳入射条件、变轨能量等。 |
| 用户需求捕获 | 从用户语言转成工程需求 | 用户经常说的是业务语言，比如“要更清楚”“要更快响应”“要覆盖某区域”。总体要把它转成分辨率、时效、覆盖率、可靠性、数据量等工程语言。 |
| 需求分解 | 从任务级需求分解到系统级、分系统级、设备级 | 顶层需求不能直接交给单机研制，需要分解为平台、载荷、测控、数传、热控、电源、结构、软件等可承接的指标。 |
| 需求确认 | 判断需求是否完整、一致、可验证 | 好需求必须可验证。例如“系统应具有高可靠性”不够，应转成可靠性指标、任务寿命、单点故障约束、验证方式。 |
| 约束识别 | 识别成本、周期、质量、发射条件、环境、接口等约束 | 约束往往比目标更决定方案。比如发射包络、质量上限、功率上限、频率资源、地面站能力、已有平台复用都会影响总体方案。 |

典型输入：

| 输入 | 说明 |
|---|---|
| 任务背景 | 为什么要做这个任务，来自战略、业务、科研、验证或型号体系需求。 |
| 用户需求 | 用户对能力、性能、交付、使用方式的原始表达，通常需要二次澄清和结构化。 |
| 应用 / 作战场景 | 系统真实使用方式，例如观测区域、任务频次、响应时间、协同对象、应急场景。 |
| 轨道与环境约束 | 包括轨道条件、空间环境、热环境、辐照、发射窗口、测控弧段等外部条件。 |
| 发射条件 | 运载能力、整流罩包络、发射场流程、力热环境、入轨精度等。 |
| 历史型号经验 | 类似任务、类似平台、类似载荷的成功经验、失败教训和风险提示。 |
| 标准规范 | 军标、国标、行业规范、型号体系规范、接口约束和安全要求。 |
| 预算与周期约束 | 经费、研制周期、试验资源、人员资源和供应链成熟度。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 任务需求说明 | 把用户目标、使用场景、能力要求、边界条件系统化表达，是后续需求规格的上游。 |
| 任务剖面 | 描述系统从发射到退役的全生命周期工作过程，为后续模式设计、能源分析、热分析和运控设计提供基础。 |
| 系统需求规格说明 | 把任务目标转成系统级功能、性能、接口、环境、可靠性、安全性和验证要求。 |
| 初步技术指标 | 给出分辨率、覆盖、重访、寿命、质量、功率、数据率、可靠性等初步目标值和约束值。 |
| 关键约束清单 | 列出不能突破或突破代价很高的约束，例如质量上限、功率上限、频段、发射窗口、接口边界。 |
| 任务成功判据 | 明确什么叫任务成功、部分成功、失败，为后续 V&V 和验收提供判断依据。 |
| 需求追踪矩阵初稿 | 初步建立“用户需求 → 系统需求 → 验证方式”的追踪关系，防止需求丢失或无来源扩张。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 需求结构化 | 把 Word 里的自然语言需求拆成带 ID、类型、来源、优先级、约束、验证方式的对象，后续才能追踪和自动检查。 |
| 需求追踪 | 建立用户需求、系统需求、分系统需求、设计对象、验证证据之间的 trace link，支持影响分析。 |
| 需求一致性检查 | 自动发现冲突、重复、不可验证、过度模糊的需求，例如同一指标在不同章节数值不一致。 |
| 需求变更影响分析 | 当需求变化时，自动提示受影响的指标、接口、模型、试验、报告和责任人。 |
| 需求-指标-方案-试验闭环 | 让每条需求都有指标承接、有方案落实、有仿真或试验证据关闭，而不是停留在需求文档里。 |

### 2.2 系统架构与总体方案设计

这是总体能力的核心。它决定系统“长什么样”“怎么工作”“各部分如何协同”。总体方案一旦方向错，后面专业再努力也只是局部优化。

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 系统边界定义 | 明确系统、外部系统、地面系统、发射系统之间边界 | 边界定义决定哪些问题由本系统负责，哪些依赖外部系统。例如星上处理和地面处理如何分工，发射服务和航天器之间接口如何划分。 |
| 功能架构设计 | 定义系统必须完成哪些功能 | 先从功能视角描述系统，而不是一上来定设备。比如“获取目标数据、压缩存储、下传、健康管理、异常处置”都是功能。 |
| 物理架构设计 | 把功能分配到平台、载荷、设备、软件和地面系统 | 同一个功能可以由不同物理方案实现。总体要决定哪些放在星上、哪些放在地面、哪些由载荷实现、哪些由平台保障。 |
| 任务架构设计 | 定义不同阶段、不同模式下系统如何工作 | 例如发射段、入轨段、展开段、标定段、正常任务段、应急段，各阶段的功能开关、约束和优先级不同。 |
| 方案 trade-off | 在性能、成本、周期、风险之间做多方案权衡 | 总体方案不是单指标最优，而是多目标折中。比如更高分辨率可能带来更大载荷、更高功耗、更高数据率和更高姿控要求。 |
| 总体布局设计 | 组织舱段、设备、载荷、天线、能源、热控、结构布局 | 布局不仅是空间摆放，还影响质心惯量、热路径、视场遮挡、天线覆盖、线缆长度、装配和测试可达性。 |
| 模式设计 | 定义发射段、入轨段、正常工作、故障安全、应急模式等 | 模式设计把系统行为固化下来，后续软件、运控、试验大纲都要围绕模式展开。 |
| 关键技术识别 | 找出系统成败依赖的关键技术和风险点 | 关键技术可能是新载荷、新材料、新机构、新算法、新热控、新能源或新工艺，需要提前安排攻关和验证。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 总体方案报告 | 描述系统方案、组成、任务模式、关键指标、风险和取舍，是型号方案评审的重要材料。 |
| 系统架构说明 | 说明系统边界、功能分解、物理组成、外部接口和运行逻辑。 |
| 功能架构模型 | 用结构化模型表达功能分解和功能之间的输入输出关系，避免仅靠 PPT 表达。 |
| 物理架构模型 | 表达平台、载荷、分系统、设备、软件、地面系统之间的组成关系和分配关系。 |
| 任务模式说明 | 描述不同阶段和模式下的状态、触发条件、允许动作、异常处置策略。 |
| 总体布局方案 | 给出设备、舱段、天线、太阳翼、载荷、散热面等布局及主要约束。 |
| 技术状态基线 | 固化某一阶段认可的方案、指标、接口和构型，作为后续更改控制基础。 |
| 关键技术清单 | 列出需要攻关、验证、降风险的关键技术，并关联负责人、计划和验证方式。 |
| 方案权衡报告 | 记录为什么选择某方案，为什么放弃其他方案，避免后续重复争论或丢失决策依据。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| MBSE 建模 | 用模型表达功能、接口、模式、指标和关系，让总体方案从 PPT 走向可查询、可校验、可追踪。 |
| 系统架构模型库 | 沉淀可复用的平台架构、载荷架构、通信架构、运控架构，减少每个型号从零开始。 |
| 方案对比自动化 | 把质量、功率、成本、周期、风险、成熟度等评价维度结构化，支持多方案快速比较。 |
| 多专业参数联动 | 让一个关键参数变化能自动提示受影响专业，例如轨道变化影响热、能源、测控、覆盖和数据回传。 |
| 数字样机 | 在实物制造前，用数字模型集成结构、热、机、电、软件、任务流程，提前暴露问题。 |
| 设计决策知识库 | 记录历史方案取舍、评审意见、失败教训和适用条件，支撑后续型号复用。 |

### 2.3 指标分解与预算闭环

航天总体有大量“预算”工作。这里的预算不是财务预算，而是系统资源预算。预算管理的本质是把有限资源分配给各分系统，并持续监控是否还能闭合。

典型预算包括：

```text
质量预算、功率预算、热预算、数据率预算、存储预算、时间预算、精度预算、可靠性预算、指向预算、姿控预算、推进剂预算、通信链路预算、结构刚度 / 强度裕度预算、安全裕度预算
```

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 顶层指标分解 | 从任务指标分解到分系统指标 | 例如任务要求成像分辨率，会分解到轨道高度、载荷口径、姿态稳定度、数据处理、平台稳定性等多个专业。 |
| 资源预算建立 | 建立质量、功率、热、数据、推进剂等预算表 | 预算表不是静态 Excel，而是型号状态的核心账本，每个条目都应有来源、版本、责任人和裕度。 |
| 裕度管理 | 设置设计裕度、增长裕度、验证裕度 | 航天研制中质量、功率、热耗等会不断增长，必须在早期预留裕度，并随阶段逐步收敛。 |
| 闭环更新 | 随设计迭代持续更新预算 | 分系统设计变更后，总体预算要同步更新，不能等评审前临时汇总，否则风险发现太晚。 |
| 超差预警 | 发现某项资源超限或趋势恶化 | 超差不只是超过上限，也包括增长趋势不健康。例如某设备功耗持续上升，会提前压缩电源和热控余量。 |
| 指标权衡 | 当一个指标超差时，通过其他指标或方案调整平衡 | 例如质量超限时可能调整结构、载荷、轨道、发射方案或任务指标，不是简单要求某专业“降重量”。 |
| 需求-指标-方案追踪 | 每个指标都有来源、分配对象和验证方式 | 这样才能回答某个指标为什么存在、分配给谁、如何验证、变更后影响哪里。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 质量预算表 | 汇总平台、载荷、结构、电源、热控、线缆、裕度等质量分配和当前状态。 |
| 功率预算表 | 描述不同模式下设备功耗、峰值功耗、平均功耗、电源余量和太阳翼/电池约束。 |
| 热控预算表 | 汇总热耗、散热能力、温度范围、热控裕度和关键热路径。 |
| 数据链路预算表 | 包括数据产生、压缩、存储、下传速率、链路裕度、地面站可见性等。 |
| 推进剂预算表 | 管理轨道控制、姿态控制、任务机动、离轨处置等推进剂消耗和余量。 |
| 可靠性分配表 | 把系统可靠性目标分配到分系统和关键设备，并关联冗余和验证策略。 |
| 指标分解矩阵 | 展示顶层任务指标如何分解到分系统、设备和验证项。 |
| 指标闭环状态表 | 记录每个指标当前是否满足、证据是什么、是否存在风险、责任人是谁。 |
| 超差问题清单 | 汇总超出预算或趋势异常的问题，并关联处理措施、责任人和关闭状态。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 预算数据结构化 | 把预算表中的每个条目变成对象，包含数值、单位、模式、版本、来源、责任人和状态。 |
| 指标自动汇总 | 自动从分系统数据汇总到系统级预算，减少手工复制粘贴和口径不一致。 |
| 跨专业影响分析 | 当某指标变化时，自动提示影响的热控、电源、结构、姿控、通信、试验等对象。 |
| 版本化预算基线 | 每次阶段评审形成预算基线，后续变化必须可追溯，可比较，不覆盖历史。 |
| 指标超差预警 | 对超限、裕度不足、增长趋势异常进行自动预警，并形成问题闭环。 |
| 设计更改影响自动传播 | 更改单批准后，自动更新相关预算、接口、仿真任务和验证状态。 |

这类工作非常适合数字化和 Agent 化，因为当前大量工作仍依赖 Excel、人工汇总和专家经验。

### 2.4 多专业协同设计

航天总体需要组织多个专业共同收敛。协同的难点不在“大家开会”，而在不同专业使用不同模型、不同口径、不同版本数据，导致问题发现晚、返工代价高。

典型专业包括：

```text
轨道 / 弹道、总体布局、结构、机构、热控、电源、测控、通信、数传、姿轨控 / GNC、推进、载荷、软件、地面系统、电磁兼容、可靠性、安全性、试验、AIT / AIV、发射场、运控
```

典型协同关系：

```text
载荷需求影响功率、热控、数据率、姿态稳定度；
轨道选择影响能源、热环境、测控可见性、任务覆盖；
结构布局影响质心、惯量、模态、热路径、线缆布局；
姿控精度影响载荷成像质量、执行机构选型、功耗；
通信链路影响天线布局、功率、数据管理、地面站资源；
热控方案影响结构布局、材料、功率、任务模式。
```

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 专业接口协调 | 明确输入输出、约束、责任 | 例如结构专业需要设备质量和安装位置，热控需要功耗和热耗，电源需要模式功耗，数传需要数据产生率。 |
| 设计冲突识别 | 发现专业之间指标冲突 | 例如天线布置满足通信但遮挡载荷视场，热控散热面满足温度但影响太阳翼布局。 |
| 协同评审组织 | 组织跨专业方案评审 | 总体要把专业意见变成可决策议题，而不是简单收集每个专业报告。 |
| 问题闭环 | 对设计问题建立 owner、措施、期限、状态 | 每个跨专业问题都要有责任人、关联对象、处理措施和验证证据，否则容易在会议纪要中丢失。 |
| 数据一致性维护 | 保证不同专业使用同一版本的需求、参数、模型 | 如果结构用 A 版质量表、热控用 B 版功耗表、软件用旧任务模式，协同就会失效。 |
| 专业模型集成 | 将轨道、热、结构、电源、通信等模型联动 | 不要求所有专业用同一工具，但要能交换关键参数、模型版本和分析结果。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 跨专业协调纪要 | 记录议题、决策、待办、责任人和关闭条件，不能只是会议过程描述。 |
| 专业输入输出清单 | 明确每个专业需要什么输入、产出什么输出、何时交付、使用哪个版本。 |
| 设计冲突清单 | 汇总跨专业冲突及其影响范围，例如布局冲突、功耗冲突、热控冲突、接口冲突。 |
| 协同评审材料 | 把各专业方案、冲突、风险和建议组织成可决策材料。 |
| 问题闭环台账 | 管理跨专业问题的状态、措施、证据和关闭记录。 |
| 专业模型关联表 | 记录各专业模型之间的依赖关系、版本关系和关键参数映射。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 跨专业数据中台 | 建立统一的关键参数、模型索引、版本状态和问题状态，让协同不再靠人工传文件。 |
| 统一参数源 | 对质量、功耗、热耗、尺寸、接口、模式等关键参数建立权威来源，避免多份表格互相冲突。 |
| 协同评审空间 | 在线组织评审议题、材料、意见、结论、待办和证据，形成可追溯决策链。 |
| 问题闭环系统 | 把问题从“会议纪要里的描述”变成可跟踪对象，支持 owner、期限、状态、证据和影响范围管理。 |
| 模型联邦 | 不强迫所有专业迁移到同一工具，而是通过模型注册、元数据和接口实现联邦协同。 |
| 专业模型接口标准化 | 约定模型输入输出、文件格式、参数命名、单位和版本规则，为后续自动化仿真和 Agent 调用打基础。 |

### 2.5 接口与构型管控

航天系统复杂度很大，本质上是大量接口的集合。很多型号问题不是单个设备能力不足，而是接口理解不一致、变更未同步、验证证据缺失。

典型接口包括：

```text
机械接口、电气接口、热接口、数据接口、软件接口、射频接口、地面接口、发射接口、运控接口、人机接口、外部系统接口
```

总体需要保证：

```text
接口被定义；
接口被双方确认；
接口变更被控制；
接口状态被追踪；
接口验证有证据。
```

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 接口识别 | 找出系统内外所有需要约束的交互关系 | 不只是设备之间的机械连接，还包括数据流、指令、供电、热耦合、安装维护和地面支持。 |
| ICD 编制与维护 | 形成接口控制文件并持续更新 | ICD 要描述接口双方、参数、协议、容差、状态、验证方式和变更历史。 |
| 接口确认 | 组织接口双方对接口定义达成一致 | 接口不能单边定义，需要供方、需方、总体和相关专业共同确认。 |
| 接口变更控制 | 控制接口参数、协议、安装关系等变化 | 接口变化通常影响多个专业，必须走影响分析和批准流程。 |
| 构型基线管理 | 固化某阶段系统组成、接口、版本和状态 | 没有构型基线，就无法判断当前设计、仿真、试验和交付是否对应同一状态。 |
| 接口验证 | 证明接口实际满足定义 | 例如机械安装检查、电气连通测试、协议联调、热接口验证、射频链路测试。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 接口控制文件 ICD | 正式定义接口双方、接口参数、容差、协议、验证方法和责任边界。 |
| 接口矩阵 | 从全局视角展示系统内外接口关系，便于发现遗漏接口和跨专业依赖。 |
| 设备安装关系 | 描述设备安装位置、安装面、连接件、包络、可达性和装配约束。 |
| 电缆网关系 | 描述设备之间供电、信号、数据、电连接关系，是电测和总装的重要依据。 |
| 数据流关系 | 描述数据从产生、处理、存储、下传到地面处理的路径和速率。 |
| 机械安装约束 | 包括尺寸、孔位、载荷、刚度、热变形、装配顺序等约束。 |
| 软件接口协议 | 定义指令、遥测、数据格式、时序、异常码和兼容性要求。 |
| 接口问题清单 | 汇总接口冲突、未确认项、变更项和验证未关闭项。 |
| 构型基线 | 固化某阶段认可的产品组成、版本、接口、文件和模型状态。 |
| 更改影响分析 | 说明接口或构型变化会影响哪些需求、指标、模型、试验和交付物。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| ICD 结构化 | 把 ICD 从 Word 表格变成接口对象，支持查询、比较、校验和自动生成文档。 |
| 接口图谱 | 用图关系表达设备、分系统、地面系统、外部系统之间的接口网络，便于影响分析。 |
| 构型树 | 建立系统、分系统、设备、软件、文件、模型的层级和版本关系。 |
| 接口变更影响分析 | 接口参数变化时，自动找出受影响的设备、专业、试验、文档和责任人。 |
| 接口一致性检查 | 自动检查 ICD、模型、线缆表、软件协议、试验记录之间是否一致。 |
| 接口验证证据管理 | 将接口验证结果和证据绑定到接口对象，支持验收时快速确认接口关闭状态。 |

接口管理是非常适合数字化的重点场景，因为接口错误常常是跨专业、跨单位、跨阶段问题的源头。

### 2.6 仿真分析与数字样机

航天总体离不开仿真，但总体关注的不是单一 CAE 工具，而是仿真是否能够支撑系统级决策。仿真必须从“报告附件”升级为数字线程中的证据节点。

典型仿真类型：

```text
轨道仿真、姿态控制仿真、通信链路仿真、热仿真、结构强度 / 模态仿真、动力学仿真、电源能量平衡仿真、任务覆盖仿真、可靠性仿真、故障传播仿真、系统级联合仿真
```

总体关注点：

```text
仿真输入是否来自受控设计状态；
仿真模型是否可信；
仿真工况是否覆盖需求；
仿真结果是否能支撑决策；
仿真结论是否进入指标和风险闭环。
```

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 仿真任务定义 | 明确仿真目的、输入、工况、输出 | 要说明仿真是为了关闭哪个需求、验证哪个指标、支撑哪个设计决策，而不是泛泛“做一次分析”。 |
| 仿真模型管理 | 管理模型版本、适用范围、校核状态 | 同一模型可能只适用于某个阶段、某类工况或某种精度要求，需要标明可信边界。 |
| 工况管理 | 管理载荷、边界、轨道环境、热环境等工况 | 工况决定仿真结论的有效性。例如结构静力、模态、热真空、发射载荷、在轨极端工况都不同。 |
| 仿真执行协调 | 调度专业工具和计算资源 | 包括准备输入、提交 solver、监控运行、收集结果、处理失败和保存日志。 |
| 结果判读 | 判断结果是否满足指标 | 总体关注的是结果是否支撑需求闭环，例如最大应力、最大位移、频率、温度、链路裕度是否满足判据。 |
| 结果追踪 | 把结果关联到需求、指标、设计状态和评审 | 仿真结果必须能追溯到模型版本、工况版本、输入文件、solver 版本和评审结论。 |
| 模型可信度评估 | 判断模型是否经过验证、误差范围如何 | 模型是否和试验校核过、网格是否收敛、边界条件是否合理，都会影响结论可信度。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 仿真任务书 | 明确仿真目的、需求来源、输入模型、工况、输出指标、判据和责任人。 |
| 仿真模型包 | 包括模型文件、版本、适用范围、假设条件、网格/参数说明和校核状态。 |
| 工况定义表 | 结构化描述载荷、边界、环境、模式、时间段和极限条件。 |
| solver 运行记录 | 记录执行时间、工具版本、输入文件、日志、错误、资源消耗和运行状态。 |
| 结果数据集 | 保存可结构化读取的数值结果、云图、曲线、表格和关键指标。 |
| 仿真分析报告 | 解释结果、给出是否满足判据、风险点和建议措施。 |
| 仿真证据链 | 把仿真任务、模型、工况、结果、报告、评审结论串成可追溯证据。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 仿真流程自动化 | 将模型检查、工况校验、solver 提交、结果解析、报告生成变成可复用流程。 |
| 仿真模型版本管理 | 让每次仿真都能追溯到具体模型版本、文件 hash、工具版本和参数配置。 |
| 仿真工况库 | 沉淀发射、在轨、极限温度、载荷组合、故障模式等标准工况，减少重复定义。 |
| 结果结构化解析 | 自动从 OP2、ODB、F06、log、CSV、图像等结果中提取关键指标和异常。 |
| CAE Agent | 让 Agent 协助准备任务、检查模型、调用工具、解释结果、生成报告草稿，但不自动批准工程结论。 |
| 仿真证据链 | 将仿真结果绑定到需求、指标、模型、工况、评审和验证矩阵，支持验收追溯。 |
| 数字样机 / Digital Twin | 在设计阶段形成可计算的系统模型，在试验和运行阶段持续校正，支撑预测和决策。 |

这和前面讨论的 CAE Simulation Agent 是同一条主线。

### 2.7 可靠性、安全性与风险控制

航天系统必须高可靠、高安全、可验证。这一能力域的核心是提前识别系统可能如何失败，并在设计、验证和运维中闭环控制。

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 可靠性指标分配 | 将系统可靠性目标分配到分系统和设备 | 例如整星任务可靠性需要分配到电源、姿控、测控、热控、载荷、软件等对象。 |
| FMEA / FMECA | 分析故障模式、影响和危害性 | 关注每个部件或功能如何失效、失效后影响什么、是否可检测、是否可隔离。 |
| FTA | 用故障树分析顶事件的成因 | 适合分析“任务失败”“失去姿态控制”“通信中断”等顶层风险事件。 |
| 单点故障识别 | 找出一个故障即可导致任务失败的薄弱点 | 单点故障需要通过冗余、降级、保护、监测或风险接受来处理。 |
| 冗余设计 | 设计备份、交叉备份、降级模式 | 冗余不是越多越好，会增加质量、功耗、复杂度和故障模式，需要权衡。 |
| 安全性分析 | 分析对人员、设备、发射、在轨和地面的安全风险 | 包括火工品、压力容器、电池、推进剂、射频、软件控制、发射场操作等。 |
| 故障模式与处置策略 | 定义故障检测、隔离、恢复和应急处置 | 这会影响星上软件、运控流程、遥测设计和地面预案。 |
| 风险识别 | 识别技术、进度、供应链、试验、接口等风险 | 风险不仅来自技术，也来自资源、周期、组织协同和外部依赖。 |
| 风险分级 | 按概率、影响、可检测性、可恢复性分级 | 分级的目的是决定哪些风险必须降级，哪些可以接受，哪些要上升决策。 |
| 风险闭环 | 跟踪措施、责任人、验证证据和关闭状态 | 没有闭环的风险登记册只是清单，不能降低型号风险。 |
| 质量问题归零 | 对发生的问题做定位、机理、复现、措施、验证和举一反三 | 航天问题不能只修现象，必须形成归零结论和复用经验。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 可靠性分配报告 | 说明可靠性目标如何分配、依据是什么、各分系统如何承接。 |
| FMEA / FMECA 表 | 结构化记录故障模式、影响、危害度、检测方式、处置措施和责任对象。 |
| FTA 故障树 | 展示顶层故障事件的逻辑原因链，支持薄弱环节识别。 |
| 单点故障清单 | 列出不可由冗余或降级覆盖的关键风险点及处置策略。 |
| 风险登记册 | 管理风险描述、等级、责任人、措施、期限、状态和证据。 |
| 风险燃尽图 | 展示风险随研制阶段是否下降，帮助判断型号是否真正收敛。 |
| 故障处置策略 | 定义故障检测、隔离、恢复、降级和地面处置流程。 |
| 安全性分析报告 | 记录安全风险、控制措施、验证方式和剩余风险接受结论。 |
| 归零报告 | 对质量问题形成原因定位、措施验证、举一反三和关闭证据。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 风险知识库 | 沉淀历史风险、问题、措施、验证结果和适用条件，支持新型号早期识别。 |
| 故障模式知识图谱 | 将设备、功能、故障模式、影响、处置策略、案例关联起来，支持推理和检索。 |
| FMEA 自动辅助 | 根据历史型号、设备类型和功能架构推荐潜在故障模式，但最终仍由工程师确认。 |
| 风险相似案例检索 | 当出现新风险或异常时，快速找历史类似问题、归零报告和处理措施。 |
| 问题归零闭环 | 把问题从发现、定位、措施、验证、关闭到复用全部数字化，避免经验丢失。 |
| 可靠性指标追踪 | 将可靠性分配、冗余设计、故障分析、试验验证和在轨表现持续关联。 |

这类能力适合结合知识库和 Agent，但必须保持“辅助决策”定位，不能让 Agent 自动给最终安全结论。

### 2.8 试验验证与 V&V

航天总体最终要回答：系统是否满足需求，证据在哪里，未验证项如何处置。V&V 是把设计承诺变成验收证据的过程。

典型验证层级：

```text
分析验证、仿真验证、单机试验、分系统试验、系统联试、环境试验、电测、热真空、振动、冲击、EMC、发射场测试、在轨测试
```

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| V&V 策略制定 | 决定哪些需求用什么方式验证 | 有些需求适合试验，有些适合分析或仿真，有些需要多种证据组合。 |
| 验证矩阵管理 | 建立需求-验证方式-证据闭环 | 每条需求都应有验证方法、验证阶段、责任人、判据和证据状态。 |
| 试验项目定义 | 明确试验目的、条件、判据 | 试验不是“做了就行”，必须说明验证哪个需求、使用什么工况、通过标准是什么。 |
| 试验结果判读 | 判断是否通过 | 不只是读取测试数据，还要结合判据、误差、边界条件和异常情况形成工程判断。 |
| 偏差处理 | 对异常和偏差进行归零 | 试验结果不满足或数据异常时，要判断是设计问题、测试问题、模型问题还是操作问题。 |
| 证据管理 | 保存报告、数据、照片、记录、签署 | 验收时需要可追溯证据，不能只靠报告结论。原始数据、处理脚本、签署记录也应保存。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 验证计划 | 描述总体 V&V 策略、验证层级、阶段安排、资源和责任分工。 |
| 验证矩阵 | 将需求、验证方法、验证项目、判据、证据和状态关联起来。 |
| 试验大纲 | 规定试验目的、条件、流程、测点、设备、判据、安全注意事项。 |
| 试验报告 | 记录试验过程、数据、结果判读、异常、结论和签署。 |
| 问题归零报告 | 对试验异常进行原因分析、措施验证和闭环确认。 |
| 验证证据包 | 将报告、原始数据、照片、曲线、日志、签署记录和评审结论打包。 |
| 验收状态表 | 汇总每条需求是否关闭、证据是否充分、是否存在豁免或未关闭项。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 需求-验证矩阵 | 让验证不再靠人工翻文档，而是可查询每条需求的验证状态和证据。 |
| 试验数据平台 | 管理原始测试数据、处理结果、曲线、日志、测点、设备和版本。 |
| 自动生成验证证据包 | 从需求、试验、仿真、报告和签署记录自动组装验收证据，减少人工整理。 |
| 异常归零知识库 | 沉淀试验异常、原因、措施、验证结果和复用建议，支持后续快速诊断。 |
| 试验 Agent | 辅助生成试验大纲草稿、检查数据完整性、摘要试验结果、发现异常模式。 |
| V&V Review Agent | 辅助检查验证矩阵是否有遗漏、证据是否充分、结论是否和数据一致。 |

### 2.9 型号工程管理与配置管理

总体院 / 总体部还承担很强的工程治理职责。这一域关注“型号是否按受控状态推进”，避免技术状态失控、问题失控、交付物失控。

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 计划管理 | 管理型号阶段、任务、资源和进度 | 航天型号周期长、依赖多，计划管理要关注关键路径和跨单位依赖。 |
| 里程碑管理 | 管理 SRR、PDR、CDR、TRR、FRR 等节点 | 每个里程碑都应有进入条件、退出条件、交付物和未关闭项要求。 |
| 技术状态管理 | 管理当前被认可的设计状态 | 技术状态包括需求、指标、方案、接口、构型、模型、软件和试验状态。 |
| 配置管理 | 管理配置项、版本、基线和变更 | 配置管理保证大家讨论的是同一个对象、同一个版本、同一个状态。 |
| 更改控制 | 控制需求、设计、接口、软件、试验等变更 | 更改必须有原因、影响分析、审批、实施和验证，不应口头变更。 |
| 问题闭环 | 管理设计问题、试验问题、质量问题和评审问题 | 问题要有责任人、措施、期限、状态和关闭证据。 |
| 供应商协同 | 管理外协单位、供应商、外部接口和交付状态 | 外部交付物也要纳入配置、质量和进度控制。 |
| 评审管理 | 管理评审材料、意见、结论和整改 | 评审不是一次会议，而是进入条件、问题关闭和技术状态确认过程。 |
| 交付物管理 | 管理文档、模型、软件、硬件、数据包等交付物 | 每个交付物都应有版本、责任人、审批状态和关联对象。 |
| 质量过程管理 | 管理质量门禁、审签、检查、归零和过程证据 | 质量不只是最终检验，而是贯穿需求、设计、生产、试验全过程。 |

典型评审节点：

```text
任务论证评审、方案评审、SRR 系统需求评审、PDR 初步设计评审、CDR 详细设计评审、TRR 试验准备评审、QR 质量评审、FRR 飞行准备评审、交付评审、在轨评估
```

典型输出：

| 输出 | 说明 |
|---|---|
| 型号计划 | 描述阶段目标、关键任务、里程碑、资源、交付物和关键路径。 |
| WBS | 将型号工作分解到任务包、责任单位、交付物和进度计划。 |
| 技术状态基线 | 固化某阶段的需求、方案、指标、接口、模型、软件和试验证据。 |
| 配置项清单 | 列出受控硬件、软件、文档、模型、数据和接口对象。 |
| 更改单 | 记录变更原因、变更内容、影响分析、审批、实施和验证结果。 |
| 评审材料 | 汇总阶段状态、指标闭合、风险问题、验证证据和决策事项。 |
| 问题清单 | 管理设计、试验、质量、接口、进度等问题的闭环状态。 |
| 风险清单 | 管理风险等级、措施、责任人、期限和剩余风险接受情况。 |
| 交付物清单 | 管理各阶段应交付的文档、模型、数据、软件、硬件和证据包。 |
| 阶段总结 | 总结阶段完成情况、未关闭项、经验教训和下一阶段关注点。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 型号数字主线 | 将需求、方案、指标、接口、模型、试验、问题、风险、交付物串成一条可追溯主线。 |
| 配置基线管理 | 对每个阶段形成可冻结、可比较、可回溯的基线，避免版本混乱。 |
| 工程状态驾驶舱 | 汇总指标闭合、问题风险、交付物、评审状态和进度状态，支持管理决策。 |
| 评审材料自动生成 | 从结构化数据自动生成 PDR、CDR、TRR、FRR 等材料草稿，减少人工汇总。 |
| 问题风险闭环 | 把问题和风险做成可追踪对象，自动提醒超期、影响范围和关闭证据。 |
| 跨单位协同平台 | 让总体、分系统、供应商、试验单位在统一规则下交付、审签和追踪状态。 |

### 2.10 运行支持、在轨运维与知识沉淀

航天总体不应只关注研制阶段，还要关注运行和反馈。在轨表现是检验设计假设和工程质量的最终来源，也是新型号知识复利的关键输入。

典型任务：

| 任务 | 做什么 | 进一步说明 |
|---|---|---|
| 在轨测试 | 对发射入轨后的系统功能和性能进行验证 | 包括平台健康、载荷性能、通信链路、姿态控制、热控、电源、任务模式等。 |
| 健康状态监测 | 持续监控遥测和关键状态 | 关注温度、电压、电流、姿态、存储、通信、执行机构、载荷状态等趋势。 |
| 异常诊断 | 对在轨异常进行定位和处置 | 需要结合遥测、指令历史、模式状态、环境条件和历史案例判断原因。 |
| 任务规划 | 安排观测、通信、机动、维护等任务 | 任务规划要平衡用户需求、能源、热、存储、测控窗口和姿态约束。 |
| 运控支持 | 支撑地面运控指令、流程和应急处置 | 总体需要确保运控流程和设计模式一致，并能处理异常场景。 |
| 在轨性能评估 | 评估系统实际性能是否达到设计预期 | 包括载荷性能、能源平衡、热控效果、姿控精度、通信链路和寿命消耗。 |
| 寿命预测 | 根据健康状态和消耗趋势预测剩余寿命 | 例如推进剂、电池、机构寿命、器件退化、热循环影响等。 |
| 经验反馈 | 将运行问题和表现反馈到设计改进 | 运行数据能暴露设计假设偏差，是下一代型号优化的重要来源。 |
| 新型号复用 | 把成熟方案、问题教训、运控经验复用到后续型号 | 复用不只是复制文档，而是复用经过验证的设计对象、参数、规则和案例。 |

典型输出：

| 输出 | 说明 |
|---|---|
| 在轨测试报告 | 记录入轨后各项功能和性能测试结果，以及与设计指标的对比。 |
| 健康状态报告 | 汇总关键遥测趋势、异常、裕度和健康等级，支持运行决策。 |
| 异常处置记录 | 记录异常现象、时间线、诊断过程、指令处置、结果和复盘。 |
| 任务规划方案 | 描述任务安排、约束满足情况、资源使用和冲突处理。 |
| 性能退化分析 | 分析关键性能随时间变化趋势，例如电池容量、热控裕度、载荷性能。 |
| 寿命评估报告 | 根据消耗、退化、故障和任务计划评估剩余寿命和风险。 |
| 经验教训库 | 沉淀在轨问题、有效措施、无效尝试、设计改进建议和适用条件。 |
| 设计改进建议 | 将运行反馈转化为新型号需求、设计、验证或运控流程改进。 |

数字化转型重点：

| 重点 | 说明 |
|---|---|
| 运行数据回灌 | 将遥测、任务、异常、处置、性能评估回写到型号知识库和设计数据中。 |
| 异常知识库 | 把异常现象、原因、处置、证据和结果结构化，支持后续快速诊断。 |
| 数字孪生 | 用在轨数据校正设计模型和仿真模型，支撑状态评估和预测。 |
| 健康管理 | 建立健康指标、阈值、趋势分析和预警机制，提前发现退化。 |
| 运维 Agent | 辅助检索历史异常、摘要遥测趋势、生成处置建议草稿，但关键指令必须人审。 |
| 型号经验复用 | 把在轨经验转成新型号可复用的需求、规则、检查项、设计模式和验证项。 |

## 3. 航天总体典型任务流

能力域回答“总体长期要具备什么能力”，阶段任务流回答“一个具体型号如何从不确定逐步走向可交付”。

可以把航天总体任务流分成八个阶段。

```text
0. 任务机会识别
1. 任务论证与概念方案
2. 系统需求与总体方案
3. 初步设计
4. 详细设计
5. 生产集成与试验验证
6. 发射交付与在轨测试
7. 在轨运行与经验回灌
```

### 3.1 阶段 0：任务机会识别

目标：判断任务是否有价值、是否可行、是否值得立项。这个阶段还不是严格工程设计，更像是在一堆潜在任务机会里筛选“值得进一步论证”的方向。

主要活动 / 互动：

| 活动 | 说明 |
|---|---|
| 应用场景分析 | 先理解任务服务的业务、科研或作战场景，例如看什么目标、服务谁、在什么条件下使用。没有场景，后面的指标容易变成空泛数字。 |
| 用户需求访谈 | 和用户、任务方、应用方反复沟通，把“想要更快、更清楚、更可靠”这类表述拆成可讨论的能力诉求。 |
| 任务价值评估 | 判断任务带来的战略价值、业务价值、科研价值或体系贡献，避免只因为技术可做就立项。 |
| 初步技术可行性分析 | 粗略判断现有平台、载荷、轨道、地面系统、供应链和团队能力是否支撑该任务。 |
| 约束条件识别 | 提前识别经费、周期、发射机会、频率资源、政策边界、外部接口等硬约束。 |
| 竞争方案分析 | 比较是否可以用地面系统、航空平台、已有卫星、商业服务或其他技术路径解决同一问题。 |
| 成本周期粗估 | 给出量级判断，不追求精确，但要能判断任务是不是明显超出资源边界。 |

主要交付物：

| 交付物 | 说明 |
|---|---|
| 任务设想 | 用简洁方式描述任务目标、服务对象、主要能力、预期效果和初步边界。 |
| 应用场景说明 | 说明系统未来如何被使用，包含典型用户、任务频次、地理/空间范围、响应要求和特殊场景。 |
| 初步需求清单 | 记录尚未完全工程化的用户诉求，为后续需求工程提供原始材料。 |
| 技术可行性判断 | 给出“可行 / 有条件可行 / 风险较高 / 暂不建议”的判断，并说明依据。 |
| 立项建议 | 给出是否进入下一步任务论证的建议，包含价值、风险、资源和优先级判断。 |

数字化机会：

| 机会 | 说明 |
|---|---|
| 历史任务案例检索 | 根据任务关键词、场景和指标自动检索历史型号、类似任务和经验教训，帮助早期判断少走弯路。 |
| 需求相似性分析 | 将新需求与历史需求做相似匹配，提示哪些需求曾经出现过、如何分解、最后如何验证。 |
| 任务价值模型 | 将覆盖能力、响应时效、用户数量、体系贡献、成本周期等因素结构化，辅助任务优先级判断。 |
| 成本周期类比估算 | 基于历史型号、载荷复杂度、平台成熟度和试验强度，给出早期成本周期区间。 |

### 3.2 阶段 1：任务论证与概念方案

目标：形成可比较的多个总体概念方案。这个阶段的重点不是锁死最终设计，而是把任务目标和约束转成若干可比较的技术路径。

主要活动 / 互动：

| 活动 | 说明 |
|---|---|
| 任务剖面设计 | 定义从发射、入轨、展开、标定、任务执行到退役的全过程，明确每个阶段系统要做什么。 |
| 轨道 / 弹道初步分析 | 评估轨道高度、倾角、覆盖、重访、能量、测控可见性等，判断不同轨道方案对任务的影响。 |
| 载荷能力分析 | 粗略判断载荷类型、性能边界、体积质量功耗、数据产生率和技术成熟度。 |
| 平台能力估算 | 判断平台在质量、功率、热控、姿控、通信、推进、寿命等方面能否支撑任务。 |
| 资源预算粗分配 | 对质量、功率、热、数据率、推进剂、可靠性等做第一版粗预算，判断方案是否大体闭合。 |
| 关键技术识别 | 识别任务成败依赖的核心技术，例如新型载荷、高精度姿控、大功率电源、新材料或自主控制。 |
| 风险识别 | 识别技术、周期、经费、试验、供应链、外部接口等风险，并判断是否可接受。 |
| 方案 trade-off | 在多个概念方案之间做权衡，明确性能、成本、风险、周期和成熟度的取舍。 |

主要交付物：

| 交付物 | 说明 |
|---|---|
| 任务论证报告 | 说明任务必要性、可行性、主要方案、关键指标、风险和建议路径。 |
| 概念方案 | 给出若干候选总体方案，通常包括轨道、平台、载荷、地面系统和任务模式的初步组合。 |
| 初步总体指标 | 形成分辨率、覆盖、时效、寿命、质量、功率、数据率、可靠性等顶层指标初稿。 |
| 初步资源预算 | 形成质量、功率、数据、热、推进剂等粗预算，用来判断方案是否可能闭合。 |
| 关键技术清单 | 列出需要提前攻关或验证的技术，并说明风险等级和成熟度。 |
| 风险清单 | 记录早期风险、影响、概率、处置思路和是否影响立项。 |
| 方案对比矩阵 | 将多个方案按性能、成本、周期、风险、成熟度、可扩展性等维度对比。 |

数字化机会：

| 机会 | 说明 |
|---|---|
| 任务剖面建模 | 用结构化模型表达任务阶段、模式、事件、约束和资源消耗，支撑后续仿真和方案比较。 |
| 方案空间自动生成 | 基于可选轨道、平台、载荷、通信和地面资源组合，生成可比较的候选方案集。 |
| 多指标 trade-off 分析 | 将性能、成本、周期、风险、成熟度等指标量化或半量化，辅助方案选择。 |
| 知识库辅助风险识别 | 根据类似任务和历史问题自动提示潜在风险，例如某类载荷的热控风险、某类轨道的测控风险。 |

### 3.3 阶段 2：系统需求与总体方案

目标：把任务目标转化为稳定的系统级需求和总体方案。这个阶段开始从“概念可能性”进入“工程承诺”。

主要活动 / 互动：

| 活动 | 说明 |
|---|---|
| 系统需求定义 | 把任务目标转成系统必须满足的功能、性能、接口、环境、可靠性、安全性和验证要求。 |
| 需求分解 | 将系统级需求分配给平台、载荷、分系统、设备、软件和地面系统。 |
| 系统架构设计 | 定义系统边界、功能架构、物理架构、信息流、任务模式和外部接口。 |
| 分系统职责分配 | 明确各分系统负责哪些功能、承接哪些指标、提供哪些接口和交付物。 |
| 总体布局 | 初步确定设备、载荷、天线、太阳翼、推进、散热面、结构舱段等总体布局。 |
| 接口初步定义 | 识别并定义主要机械、电气、热、数据、软件、地面和发射接口。 |
| 指标预算分解 | 将质量、功率、热、数据、可靠性、姿控、通信等预算分配到分系统。 |
| V&V 策略制定 | 初步明确每类需求如何验证，是分析、仿真、试验、检查还是在轨验证。 |

主要交付物：

| 交付物 | 说明 |
|---|---|

## 4. 两种拆分视角的底层逻辑

前面分别用了两种方式拆航天总体：

```text
按能力域拆：看总体组织长期要具备什么能力；
按阶段拆：看一个型号从立项到在轨如何逐步推进。
```

这两个视角不是替代关系，而是正交关系。能力域更像“职能结构”和“能力资产”，阶段更像“时间流程”和“状态演化”。

### 4.1 两者的底层逻辑差异

| 维度 | 能力域拆 | 分阶段拆 |
|---|---|---|
| 底层问题 | 总体要具备什么能力？ | 型号按什么顺序推进？ |
| 组织视角 | 职能 / 专业 / 能力资产 | 生命周期 / 里程碑 / 流程 |
| 时间属性 | 长期存在、跨型号复用 | 随型号阶段推进 |
| 关注对象 | 方法、数据对象、工具、知识、平台模块 | 阶段目标、输入输出、评审、状态转换 |
| 数字化落点 | 建能力平台、数据模型、知识库、Agent Skill | 建流程编排、阶段门禁、交付物管理、状态看板 |
| 典型问题 | “接口管理能力怎么建设？” | “PDR 前要关闭哪些接口问题？” |

最关键的底层差异是：

```text
能力域是稳定能力；
阶段是状态演化。
```

例如“接口管理”是一项长期能力，它会贯穿论证、方案、初设、详设、集成试验、发射和在轨反馈多个阶段；而“PDR”是一个阶段门禁，它会同时调用需求、架构、指标、接口、仿真、风险、V&V、工程管理等多类能力。

### 4.2 能力域做纵向资产，阶段做横向流程

所以，数字化平台不能只按阶段做流程表单，也不能只按能力域做孤立专业系统。正确形态应该是矩阵：

```text
能力域提供对象、规则、知识、工具和专业能力；
阶段流程定义这些对象在某个生命周期节点应该达到什么状态。
```

画成结构就是：

```text
                        型号阶段 / 生命周期流程
                论证 → 方案 → 初设 → 详设 → 集成试验 → 发射 → 在轨
能力域
需求工程          ●      ●      ●      ○       ○          ○      ●
指标预算          ○      ●      ●      ●       ●          ○      ●
接口构型          ○      ●      ●      ●       ●          ●      ●
仿真分析          ○      ○      ●      ●       ●          ○      ●
试验验证          ○      ●      ●      ●       ●          ●      ●
风险控制          ●      ●      ●      ●       ●          ●      ●
工程管理          ●      ●      ●      ●       ●          ●      ●
知识沉淀          ○      ○      ○      ○       ●          ●      ●
```

这里的 `●` 表示该阶段强相关、强投入，`○` 表示该阶段有参与但不是主战场。数字化系统要做的是这个矩阵，而不是只做其中一条轴。

如果只做横向阶段流程，系统容易变成“电子化评审表单”；如果只做纵向能力平台，系统又容易变成互相割裂的专业工具。真正有价值的是：

```text
用纵向能力资产保证专业能力可复用；
用横向阶段流程保证型号状态可推进；
用矩阵关系把能力、对象、状态、证据和责任人连接起来。
```

### 4.3 对应到 AI / Agent 体系：能力域是 Skill，阶段是 Workflow

落到 AI / Agent 架构里，可以进一步简化为：

```text
能力域 → Skill / Tool / Knowledge / Data Object
阶段流程 → Workflow / State Machine / Human Approval / Audit
```

例如：

```text
Requirement Skill、Budget Skill、Interface Skill、CAE Simulation Skill、V&V Review Skill
```

是按能力域沉淀的可复用能力；而：

```text
任务论证 Workflow、SRR Workflow、PDR Workflow、CDR Workflow、TRR Workflow、FRR Workflow、问题归零 Workflow
```

是按阶段或工程过程编排的受控流程。

因此，航天总体数字化和 Agent 化的一个关键设计原则是：

```text
先把能力域对象化和 Skill 化，
再把阶段流程 Workflow 化和门禁化。
```

否则，如果没有结构化能力对象，Workflow 只能流转文档；如果没有阶段 Workflow，Skill 只能做零散辅助，不能推动型号状态演化。

## 5. 为什么航天总体数字化转型非做不可

航天总体数字化转型不是因为“要上系统”或“要用 AI”，而是因为传统总体组织方式正在同时面对复杂度、周期、成本和质量责任四类压力。它真正要解决的，不是文档是否电子化，而是复杂型号在研制全过程中能不能被看清、控住、追溯、验证和复用。

### 5.1 核心判断

型号复杂度已经超过传统文档、会议、人工汇总和专家记忆能够稳定驾驭的范围。数字化转型的根本目的，是把高度依赖个人经验和静态文档的总体组织方式，升级为组织级、可追踪、可计算、可审计、可复用的系统工程能力。

一句话说：

```text
当型号复杂度、研制周期和成本压力持续上升，数字化与智能化就不再只是辅助效率工具，而是总体能力进入新时代的基础设施与载体。
```

### 5.2 四类压力

| 压力 | 具体表现 | 如果不转型会怎样 |
|---|---|---|
| 复杂度压力 | 多星协同、天地一体、载荷-平台-地面强耦合、软件定义任务增加 | 系统关系网络超过人工稳定维护能力，设计影响容易遗漏。 |
| 周期压力 | 任务节奏加快，评审、试验、交付窗口更紧 | 靠人工汇总、会议协调和临时排查会拖慢型号收敛。 |
| 成本 / 资源压力 | 返工、试验重做、发射窗口错过、跨单位协调成本上升 | 问题越晚发现，修正成本越高，型号边际成本难以下降。 |
| 质量与责任压力 | 航天系统高风险、高成本、不可轻易返工，结论必须有依据 | 如果状态、证据和责任边界不可追踪，质量风险会被后移到试验、交付甚至在轨阶段。 |

> **成本 / 资源压力补充说明：** 这里的成本压力不只是经费压缩，而是复杂型号研制中的系统性成本上升。航天型号的问题发现越晚，修正成本越高；状态越不透明，跨专业协调成本越高；变更影响越靠人工判断，遗漏和返工风险越高；试验资源越昂贵，越不能让试验承担发现低级状态问题的职责；历史经验如果不能复用，后续型号的边际成本也难以下降。
>
> 因此，数字化转型的成本价值不是简单“少花钱”，而是通过早发现、早预警、早闭环，降低返工成本、协调成本、试验重做成本、变更扩散成本和经验不能复用带来的重复投入。

### 5.3 As-Is vs To-Be：传统总体方式与数字化总体方式的差异

| 维度 | As-Is：传统总体方式 | 典型问题 | To-Be：数字化总体方式 | 转型价值 |
|---|---|---|---|---|
| 型号状态 | 状态分散在文档、表格、会议纪要和个人认知里 | 难以实时判断需求、指标、接口、风险、验证是否真正闭合 | 需求、指标、接口、风险、验证、评审形成统一状态视图 | 从“问人找状态”变成“系统呈现状态” |
| 设计关系 | 需求、方案、指标、接口、仿真、试验之间主要靠人工维护 | 关系容易断，影响分析不完整 | 建立对象之间的 trace link 和数字线程 | 从“文档集合”变成“关系网络” |
| 变更管理 | 变更通过会议、邮件、表格扩散 | 影响对象容易遗漏，后期返工成本高 | 变更自动关联受影响需求、接口、预算、模型、试验和责任人 | 从“经验判断影响”变成“系统辅助影响分析” |
| 跨专业协同 | 各专业使用不同工具、表格、模型和口径 | 数据不一致，版本不一致，冲突发现晚 | 关键参数、接口、模型、问题和风险统一注册与关联 | 从“会议协调”变成“对象协同” |
| 指标预算 | 质量、功率、热、数据等预算靠 Excel 汇总 | 人工复制容易错，裕度变化不及时 | 预算对象结构化，支持自动汇总、趋势分析和超差预警 | 从“静态表格”变成“动态账本” |
| 接口构型 | ICD、构型清单、图纸、模型分散维护 | 接口变更未同步，构型状态对不上 | 接口和构型对象版本化、基线化、可追踪 | 从“文件受控”升级为“状态受控” |
| 仿真分析 | 仿真报告作为阶段材料附件存在 | 不清楚仿真对应哪个模型、工况、构型和需求 | 仿真任务、模型、工况、结果、报告与需求和指标关联 | 从“报告结论”变成“可追溯证据” |
| 试验验证 | 试验数据、报告、问题、需求关闭关系分散 | 验收时证据链不完整，未关闭项难追踪 | 验证矩阵、试验数据、证据包、问题归零形成闭环 | 从“做过试验”变成“证据闭环” |
| 评审交付 | PDR / CDR / TRR / FRR 材料靠人工汇总 | 材料好看但未必反映真实技术状态 | 评审材料从受控数据生成，评审问题进入闭环 | 从“材料评审”变成“状态评审” |
| 风险问题 | 风险、问题、评审意见分散在清单和纪要中 | 关闭状态不清，举一反三困难 | 风险和问题对象化，关联措施、证据、责任人和影响范围 | 从“问题记录”变成“风险闭环” |
| 知识复用 | 经验沉淀在专家、历史报告和个人文件夹里 | 新型号重复踩坑，专家经验难迁移 | 历史方案、问题、规则、检查项与对象关联 | 从“个人经验”变成“组织资产” |
| AI / Agent | Agent 只能问答、摘要、写材料 | 缺少结构化对象和权限边界，难进入工程闭环 | Agent 基于对象、流程、权限和审计参与检查、编排和生成 | 从“文档助手”变成“受控工程助手” |
| 成本控制 | 成本主要在后期通过压缩资源、压缩周期处理 | 返工成本、试验重做成本、协调成本高 | 通过早发现、早预警、早闭环降低后期返工和试验浪费 | 从“事后控成本”变成“前置控成本” |

### 5.4 关键结论：目标不是工具上线，而是让复杂型号可控、让组织进化可落地

数字化转型真正解决的是复杂型号研制中的状态、关系、变更、证据、风险、成本和知识复用问题。它的目标不是把文档搬到线上，也不是堆砌工具，而是把型号总体从“文档驱动、会议协调、人工追踪”升级为“对象驱动、数字线程连接、状态受控、证据闭环”的系统工程能力，让复杂型号可控，也让组织能力的沉淀、复用和进化真正落地。

## 6. 转型目标：从复杂型号可控到组织进化可落地

第 5 章回答“为什么非做不可”，这一章回答“转型最后要得到什么”。航天总体数字化的目标不是建设一组信息系统，也不是把既有文档流程搬到线上，而是形成两类能力结果：

```text
对型号：复杂状态可见、关系可追踪、变更可控制、证据可闭环；
对组织：方法可沉淀、知识可复用、流程可复制、能力可进化。
```

也就是说，数字化转型的真正目标，是让总体能力从“专家个人能力 + 文档流程能力”，升级为“组织级系统工程能力”。

### 6.1 目标分层

| 层级 | 转型目标 | 具体含义 | 判断标准 |
|---|---|---|---|
| 型号控制层 | 让复杂型号可控 | 需求、指标、接口、构型、风险、验证状态能够被持续掌握 | 能回答“当前型号是否具备进入下一阶段的条件” |
| 工程闭环层 | 让设计结论有证据 | 每个关键结论都能追溯到需求来源、设计依据、仿真/试验证据和评审结论 | 能回答“这个结论凭什么成立” |
| 协同治理层 | 让跨专业协同受控 | 多专业围绕统一对象、统一口径、统一状态协同，而不是围绕文件版本反复对齐 | 能回答“这次变更影响哪些专业和对象” |
| 成本控制层 | 让问题前置暴露 | 通过早发现、早预警、早闭环降低返工、试验重做和变更扩散成本 | 能回答“哪些风险如果现在不处理，后期成本会放大” |
| 组织进化层 | 让能力沉淀复用 | 历史型号的方法、规则、问题、案例和决策变成可检索、可调用、可复用资产 | 能回答“这次型号经验如何进入下一次型号” |
| 智能协同层 | 让 Agent 有工程落点 | Agent 基于结构化对象、受控流程、权限审计和人审机制参与工程辅助 | 能回答“Agent 能在哪些边界内安全地帮忙” |

### 6.2 五类转变路径

围绕上述目标，数字化转型可以压缩为五类关键转变：

| 转变 | 从什么转出 | 转向什么 | 为什么重要 |
|---|---|---|---|
| 文档中心 → 对象中心 | Word / Excel / PPT 是事实来源 | Requirement、Metric、Interface、Evidence 等对象成为事实来源 | 没有对象化，就无法追踪、分析和自动化。 |
| 静态台账 → 动态状态 | 评审前临时汇总状态 | 型号状态持续更新、可查询、可预警 | 总体管理从“阶段性看材料”变成“持续看状态”。 |
| 专业孤岛 → 数字线程 | 专业各自维护模型和表格 | 需求、架构、指标、接口、仿真、试验被 trace link 连接 | 跨专业影响分析不再只依赖会议和专家记忆。 |
| 事后评审 → 过程证据 | 到评审点再整理材料 | 证据在研制过程中持续积累、持续绑定 | 评审从“材料评审”变成“状态评审”和“证据评审”。 |
| 个人经验 → 组织智能 | 经验沉淀在专家和历史报告里 | 规则、案例、检查项、Agent Skill 可持续复用 | 组织能力不随个人流失而流失，后续型号边际成本下降。 |

## 7. 建设主线：对象、线程、流程、证据、智能

如果只从系统模块出发，容易做成一堆孤立平台；如果只从 AI 出发，又容易停留在文档问答和报告润色。更稳的建设主线应该是：

```text
核心对象模型
→ 数字线程
→ 阶段 Workflow / 门禁
→ 仿真试验证据链
→ 受控 Agent 协同
```

这五层之间是递进关系，不能倒置。

### 7.1 先对象化：把总体工作中的“关键名词”变成系统对象

对象化的意义不是建数据库字段，而是明确总体工作的核心承载物。至少要把以下对象从文档中抽出来：

```text
任务、需求、指标、预算、接口、构型、模型、仿真任务、试验项目、证据、风险、问题、评审、决策、经验。
```

只有对象化之后，才能给每个对象建立 ID、版本、状态、责任人、来源、去向和审计记录。

### 7.2 再线程化：把对象关系连成数字线程

单个对象没有太大价值，真正有价值的是对象之间的关系：

```text
Mission
→ Requirement
→ Function / System Architecture
→ Metric / Budget / Interface
→ Model / Simulation / Test
→ Evidence / Review
→ Baseline / Decision / Risk
→ Operation / Lessons Learned
```

数字线程的目标，是让总体工程师可以从任意一个对象出发，追踪它的来源、影响、证据和状态。

### 7.3 再流程化：把阶段推进变成状态门禁

阶段流程不是简单审批流，而是型号状态演化的控制机制。例如 PDR、CDR、TRR、FRR 不应只是会议节点，而应成为状态门禁：

```text
进入条件是什么？
必须提交哪些对象？
哪些指标必须闭合？
哪些接口必须确认？
哪些风险允许带入下一阶段？
哪些证据必须具备？
评审结论如何改变技术状态？
```

这样，流程才不是“电子表单流转”，而是“型号状态推进”。

### 7.4 再证据化：把仿真和试验变成可追溯证据链

航天型号最终靠证据交付。仿真和试验不能只是报告附件，而要成为需求闭环和评审门禁的一部分：

```text
需求 / 指标
→ 仿真或试验任务
→ 模型 / 工况 / 样机 / 设备状态
→ 执行记录
→ 原始数据 / 结果
→ 判据 / 结论
→ 评审确认
→ 验证关闭状态
```

这一步是从“设计状态可见”走向“工程结论可信”的关键。

### 7.5 最后智能化：让 Agent 进入受控工程流程

Agent 应该建立在对象、线程、流程和证据之上。否则它只能做文档问答；有了前面的基础，它才能参与：

```text
需求一致性检查、指标超差预警、接口影响分析、仿真任务编排、试验证据检查、评审材料生成、风险相似案例召回。
```

但 Agent 的定位必须是“受控工程助手”，不是最终责任主体。关键技术状态批准、风险接受、正式结论发布仍然必须由人负责。

## 8. 航天总体数字化的核心数据对象

核心数据对象是总体能力的载体。它们不是孤立字段，而是承载状态、关系、证据、责任和复用的工程对象。

| 对象域 | 核心对象 | 主要作用 |
|---|---|---|
| 任务对象 | Mission、Scenario、Orbit / Trajectory、Mission Phase、Success Criteria | 承载任务背景、使用场景、轨道剖面和成功判据。 |
| 需求对象 | Requirement、Constraint、Assumption、Verification Method、Trace Link | 承载用户需求、系统需求、约束条件和验证方法。 |
| 系统对象 | System、Subsystem、Equipment、Function、Mode | 承载系统组成、功能分配、任务模式和责任边界。 |
| 指标对象 | Metric、Budget、Margin、Allocation、Threshold | 承载质量、功率、热、数据率、可靠性等预算和裕度状态。 |
| 接口构型对象 | Interface、Configuration Item、Baseline、Change Request | 承载接口定义、产品组成、版本基线和变更影响。 |
| 模型仿真对象 | MBSE Model、CAD Model、CAE Model、Simulation Case、Analysis Result | 承载模型版本、仿真工况、运行结果和分析结论。 |
| 验证证据对象 | Test Item、Test Case、Test Data、Evidence、V&V Status | 承载验证计划、试验数据、证据包和需求关闭状态。 |
| 工程治理对象 | Review、Risk、Issue、Decision Record | 承载评审、风险、问题、决策和责任闭环。 |
| 运行知识对象 | Telemetry、Health Status、Anomaly、Operation Plan、Lessons Learned | 承载在轨状态、异常处置、运行经验和新型号回灌。 |

对象化之后，最重要的不是“建了多少表”，而是能否建立以下关系：

```text
需求有来源；
指标有分配；
接口有双方；
构型有版本；
仿真有模型和工况；
试验有数据和判据；
证据有关联需求；
风险有措施和关闭条件；
决策有依据和影响范围；
经验有适用场景和复用入口。
```

如果这些关系没有建立，数字化转型就会停留在“文档电子化”和“系统堆叠”。

## 9. 路线图：以能力闭环推进，而不是以系统模块堆叠

航天总体数字化不适合一开始做“大而全平台”。更稳的路径，是围绕能力闭环逐步推进：先建立事实来源，再连接关系，再嵌入流程，再形成证据，最后引入智能协同。

| 阶段 | 核心目标 | 建设重点 | 阶段成果 | 不建议做什么 |
|---|---|---|---|---|
| 阶段 1：文档与知识治理 | 先让资料找得到、分得清、控得住 | 文档库、知识库、元数据、版本、权限、模板 | 形成统一资料入口和历史经验检索能力 | 不急于重构全部业务流程 |
| 阶段 2：核心对象结构化 | 把总体主线对象从文档中抽出来 | 需求、指标、接口、问题、风险、评审结论 | 建立可查询、可追踪、可统计的对象底座 | 不先追求完整 MBSE 大模型 |
| 阶段 3：数字线程与阶段门禁 | 把对象关系和阶段状态连接起来 | trace link、影响分析、基线、PDR/CDR/TRR/FRR 门禁 | 形成型号状态视图和阶段进入/退出条件检查 | 不把流程系统做成简单审批流 |
| 阶段 4：仿真与试验证据闭环 | 把工程结论变成可追溯证据 | 仿真任务、模型版本、工况、结果、试验数据、证据包 | 支撑需求关闭、评审判断和验收追溯 | 不让仿真报告继续只是附件 |
| 阶段 5：受控 Agent 协同 | 在受控边界内提升协同效率和知识复用 | Agent Runtime、Workflow、Tool Gateway、人审、审计、Skill Registry | 形成需求、指标、接口、CAE、V&V、评审等可复用智能能力 | 不让 Agent 越权做最终工程判断 |

这条路线的关键不是“先买什么工具”，而是每一阶段都要沉淀可复用能力资产。

## 10. 推荐技术架构：围绕状态与证据的分层架构

技术架构应该服务于“复杂型号可控”和“组织进化可落地”，而不是简单罗列系统组件。可以按六层理解：

| 层级 | 作用 | 关键组件 / 能力 |
|---|---|---|
| 业务工作台层 | 面向总体工程师呈现状态、任务、问题和评审材料 | 总体设计工作台、需求管理、指标预算、接口管理、V&V 管理、评审交付、状态驾驶舱 |
| 流程控制层 | 管理型号阶段、状态门禁、问题闭环和人审流程 | Workflow Engine、Temporal、状态机、Human-in-the-loop、审批与审计 |
| 工程对象层 | 承载需求、指标、接口、构型、模型、证据等核心对象 | PostgreSQL、对象模型、配置基线、版本管理、权限模型 |
| 数字线程层 | 管理对象之间的 trace link、影响分析和关系查询 | Graph Database、Trace Link、知识图谱、影响分析引擎 |
| 模型与证据层 | 管理 MBSE、CAD、CAE、试验数据和验证证据 | MBSE Model、CAD / CAE Model、Simulation Case、Test Data、Evidence Package、MinIO / Data Lake |
| 智能协同层 | 在受控边界内提供 Agent / Skill / Tool 编排 | Agent Runtime / Harness、MCP / Tool Gateway、Skill Registry、RAG、规则库、Prompt Registry |

一个更贴近工程落地的结构是：

```text
业务工作台
→ 阶段 Workflow / 状态门禁
→ 核心工程对象
→ 数字线程 / 影响分析
→ 模型、仿真、试验、证据
→ Agent / Skill / Tool Gateway
→ 权限、审计、配置基线、可观测性
```

其中 Agent 不是独立一层“智能外壳”，而是嵌入到对象、流程和证据链中的协同能力。

## 11. 优先落地场景：先做高价值、高频、可闭环的小回路

优先级不应按“哪个系统最炫”排序，而应按四个标准选择：

```text
是否贴近总体主线；
是否高频发生；
是否能闭环验证价值；
是否能沉淀为后续数字线程和 Agent 的基础。
```

### 11.1 第一优先级：需求-指标-验证闭环

这是数字主线的骨架，建议作为第一批 MVP。

```text
Requirement
→ Metric
→ Verification Method
→ Evidence
→ Review Status
```

最小建设内容：

```text
需求库、指标对象、验证矩阵、证据索引、评审问题闭环、trace link。
```

价值判断：能够回答“每条需求由谁承接、用什么指标衡量、用什么证据关闭”。

### 11.2 第二优先级：指标预算自动汇总与超差预警

这是总体工程日常最高频的管理对象之一。

```text
Mass / Power / Thermal / Data / Reliability Budget
→ Allocation
→ Margin
→ Exceedance
→ Change Impact
```

最小建设内容：

```text
质量预算、功率预算、数据率预算、预算版本、裕度规则、超差预警、变更影响分析。
```

价值判断：把预算从“静态 Excel”变成“动态账本”，提前暴露超差和趋势风险。

### 11.3 第三优先级：接口 / ICD 与构型闭环

接口问题是型号研制中的高频风险源，且天然跨专业、跨单位。

```text
Interface
→ Interface Party
→ Parameter
→ Change
→ Verification Evidence
→ Baseline
```

最小建设内容：

```text
接口对象、接口双方、接口类型、接口参数、接口状态、构型基线、接口变更、接口验证证据。
```

价值判断：能够回答“这个接口是否被双方确认、是否对应当前构型、变更会影响哪里”。

### 11.4 第四优先级：CAE / 仿真流程与证据闭环

仿真是设计决策的重要证据，但工具链复杂、不确定性大，应从受控小场景切入。

```text
Simulation Request
→ Model File
→ Load Case
→ Solver Run
→ Result
→ Margin
→ Report
→ V&V Evidence
```

最小建设内容：

```text
已有模型文件、模型检查、工况检查、solver 调用、结果解析、裕度计算、报告草稿、人审确认。
```

价值判断：能够回答“这个仿真结论来自哪个模型、哪个工况、哪个版本，关闭了哪条需求或指标”。

### 11.5 第五优先级：评审材料与阶段状态门禁

评审材料自动生成不应独立先做，而应建立在前面对象和状态已经结构化之后。

```text
Controlled Data
→ Review Checklist
→ Open Issues
→ Evidence Package
→ Review Decision
→ Baseline Update
```

最小建设内容：

```text
PDR / CDR / TRR / FRR 模板、数据自动填充、风险问题自动汇总、指标状态自动生成、证据引用、人工审阅确认。
```

价值判断：把评审从“材料评审”变成“状态评审”，减少临时拼材料和口径不一致。

## 12. Agent 体系：先 Skill 化能力，再 Workflow 化阶段

航天总体 Agent 不应从“万能总体工程师”开始，而应从可控 Skill 和可审计 Workflow 开始。

### 12.1 Agent 能力成熟度

| 等级 | 形态 | 能做什么 | 边界 |
|---|---|---|---|
| L1 文档助手 | 基于知识库问答、摘要、检索 | 找资料、总结报告、生成草稿 | 不接触受控工程状态 |
| L2 对象检查助手 | 读取结构化需求、指标、接口、证据对象 | 检查缺项、冲突、重复、不可验证表述 | 只能提示，不能修改基线 |
| L3 流程编排助手 | 嵌入 Workflow 和任务流 | 分派任务、跟踪状态、提醒超期、汇总问题 | 关键节点必须人审 |
| L4 跨专业协同助手 | 结合数字线程做影响分析 | 提示变更影响、关联风险、推荐历史案例 | 不能替代工程决策 |
| L5 组织学习助手 | 从型号过程和结果中沉淀知识 | 生成规则、检查项、复用建议、经验索引 | 复用规则必须经过专家确认 |

### 12.2 能力域是 Skill，阶段是 Workflow

```text
能力域 → Skill / Tool / Knowledge / Data Object
阶段流程 → Workflow / State Machine / Human Approval / Audit
```

例如：

```text
Requirement Skill、Budget Skill、Interface Skill、CAE Simulation Skill、V&V Review Skill
```

是按能力域沉淀的可复用能力；而：

```text
任务论证 Workflow、SRR Workflow、PDR Workflow、CDR Workflow、TRR Workflow、FRR Workflow、问题归零 Workflow
```

是按阶段或工程过程编排的受控流程。

### 12.3 第一批最有价值的 Agent / Skill

| Agent / Skill | 优先能力 | 人审点 |
|---|---|---|
| Requirement Agent / Skill | 需求解析、歧义识别、完整性检查、验证方式建议、变更影响分析 | 需求基线发布、需求删改、验收判据确认 |
| Budget Agent / Skill | 质量/功率/数据预算汇总、裕度检查、超差预警、趋势分析 | 预算基线发布、裕度接受、超差豁免 |
| Interface Agent / Skill | 接口识别、ICD 草稿、接口一致性检查、接口变更影响分析 | ICD 发布、接口变更批准、接口关闭确认 |
| CAE Simulation Agent / Skill | 仿真任务理解、模型检查、工况检查、solver 调用、结果解析、报告草稿 | 仿真计划批准、关键结果确认、报告发布 |
| V&V Review Agent / Skill | 验证矩阵检查、证据完整性检查、试验数据摘要、未关闭项识别 | 验证结论、验收结论、风险接受 |
| Review Material Agent / Skill | 评审材料草稿、指标状态汇总、风险问题汇总、证据引用 | 所有正式评审材料发布 |

## 13. 实施风险与治理原则

数字化转型失败通常不是技术栈不够先进，而是建设逻辑错位。

| 风险 / 反模式 | 表现 | 治理原则 |
|---|---|---|
| 只做文档电子化 | 系统上线后仍然只是上传 Word / PDF | 优先建 Requirement / Metric / Interface / Evidence 等核心对象模型。 |
| 一开始追求大而全 MBSE | 建模负担重，模型和真实设计脱节 | 从需求-功能-接口-指标三个高价值闭环切入。 |
| 先集成工具、后定义对象 | CAD / CAE / PLM 接了很多，但数据口径不一致 | 先定义核心对象、ID、状态和版本规则，再做工具适配。 |
| 流程系统变成审批系统 | 只流转表单，不改变型号状态 | 阶段 Workflow 必须绑定进入条件、退出条件、证据和基线变化。 |
| 没有配置基线 | 需求、模型、仿真、报告版本互相对不上 | 建立需求基线、架构基线、指标基线、模型基线、验证基线。 |
| AI 越权 | Agent 自动改需求、批结论、关风险、发报告 | Agent 只做建议、检查、草稿、编排；正式技术状态必须人审。 |
| 忽视组织机制 | 系统有了，但责任、流程、考核、复用机制没变 | 数字化必须同步改变职责分工、评审机制、知识沉淀机制。 |

核心治理原则：

```text
先对象，后流程；
先状态，后报表；
先证据，后结论；
先小闭环，后大平台；
先受控协同，后自主智能。
```

## 14. 总结判断

从资深总体设计工程师 + 数字化智能化转型视角看，航天总体数字化的主线不是“建设更多系统”，而是围绕复杂型号可控和组织进化落地，逐步形成一套新的总体能力载体：

```text
对象化总体能力
→ 数字线程连接关系
→ 阶段 Workflow 控制状态
→ 仿真试验证据支撑结论
→ Agent / Skill 嵌入受控协同
→ 组织知识持续复用和进化
```

第一阶段最建议抓住三个闭环：

```text
1. 需求-指标-验证闭环
2. 指标预算-变更影响闭环
3. 接口构型-问题闭环
```

第二阶段再推进：

```text
4. CAE 仿真流程与证据闭环
5. 评审材料与阶段状态门禁
```

最后再引入受控 Agent，把它作为对象、线程、流程和证据链上的协同能力，而不是脱离工程状态的通用问答工具。
