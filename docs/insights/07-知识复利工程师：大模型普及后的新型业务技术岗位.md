# 知识复利工程师：大模型普及后的新型业务技术岗位

## 开篇摘要

大语言模型已经基本成型，像“发电机”已经出现；但围绕它的应用操作系统、组织流程、知识沉淀方式和岗位分工，还没有完成稳定化。很多 AI 应用仍停留在“拿着发电机到处接线”的阶段。

在这个阶段，真正值得关注的不是一次性搭建多少小平台，而是：

> 如何理解一个组织如何把知识、流程、反馈变成可复用的智能生产力。

这篇文档讨论的“知识复利工程师”，不是传统知识管理员，也不是单纯数据分析师、产品经理或算法工程师，而是一种把业务经验、数据证据、流程动作、反馈修正和 Agent 协作组织成长期复利系统的新型能力。

---

# 第一部分：时代背景与核心命题

## 1. 背景判断：发电机已经出现，但工厂还没有完成流水线改造

现在的大语言模型已经基本成型，类似于“发电机已经出现”。

但是，围绕大模型的应用通用操作系统、组织流程、知识沉淀方式、岗位分工和管理机制，还远没有稳定下来。这更像是：

```text
电力已经出现，
但工厂还没有完成电气化和流水线改造。
```

在这个阶段，很多 AI 应用建设还停留在“拿着发电机到处接线”的状态。典型表现是：

- 搭一个简单 RAG 问答库，但知识来源、更新机制、权限边界、反馈修正和真实使用场景都不清晰；
- 给某个部门做一个临时 Prompt 或 Agent Skill，可以完成局部任务，但交付后没有持续评测、反馈和迭代；
- 局部做一个预测、分类或判异模型，但很难说清楚它如何影响收入、成本、风险或效率；

把 AI 能力停留在“工具可用”层面，而没有进一步沉淀为业务知识、流程机制和组织能力。

> 一个组织如何把知识、流程、反馈变成可复用的智能生产力。

这可能是大模型普及之后，普通知识工作者、业务骨干和企业内部 AI 推动者最值得投入的方向之一。

---

## 2. 知识与数据的关系：数据是知识系统中的证据模态

讨论知识复利时，必须先重新理解“数据”和“知识”的关系。

数据当然重要，但数据不是知识系统的全部。更准确地说：

> 数据是知识的一种重要形式，但它主要擅长表征现象。大模型时代，结构化数据不再是孤立的中心，而是知识系统中的一种证据模态。真正产生业务结果的，不是数据本身，而是数据、语境、规则、流程、反馈和行动之间的闭环。

可以把业务判断拆成五层：

```text
数据 → 信息 → 知识 → 判断 → 行动
```

### 2.1 数据擅长回答“发生了什么”

数据是对现象的记录。

例如：

例如本月销售额 120 万、毛利率 28%、客户流失率 12%、某工单平均处理时长 18 小时、某菜品本周做了 3 次、孩子两次反馈牛肉太硬，这些都只是事实。

数据的优势是：

```text
客观、可计量、可比较、可追踪、可聚合
```
但数据本身通常不直接告诉你“为什么”和“怎么办”。

### 2.2 知识解释数据背后的业务含义

比如经营分析里，数据告诉你：

```text
毛利率下降 5 个点
```
但业务知识要进一步判断：

真正要追问的是：是采购成本上升，低价订单增多，产品结构变化，某个销售为了冲业绩牺牲利润，统计口径变化，还是一次性异常订单？

这些判断往往不在数据表里，而在：

```text
会议纪要、销售反馈、客户沟通记录、采购记录、历史复盘、老板经验、业务规则、异常案例
```
所以，数据表格只是业务报告的一部分，不是业务报告本身。
如果只有数据，没有解释，它只是报表；如果只有观点，没有数据，它可能是拍脑袋。

真正有价值的是：

```text
数据支撑判断 -> 知识解释数据 -> 行动验证判断 -> 反馈更新知识
```

### 2.3 大模型让文本、流程、反馈、案例重新变得可计算

在传统数据化管理里，组织最容易机器化的是：
```text
结构化数据、指标、表格、数据库、BI 报表
```

但很多真正重要的业务知识存在于：
```text
会议记录、项目复盘、销售跟进、客服对话、工单备注、SOP 文档、老板点评、专家经验、失败案例、微信群讨论、邮件往来
```
过去这些内容很难被计算系统有效利用。大模型爆发后，文本、案例、流程、反馈、经验开始可以被机器理解、组织和调用。

所以更准确的判断是：

> 在大模型时代，结构化数据从“唯一主要可计算对象”，变成了“多模态知识系统中的一种高价值证据”。它需要和文本、案例、规则、流程、反馈一起被组织，才能产生业务结果。

### 2.4 数据、知识、流程和反馈必须耦合

可以用四句话概括：

```text
数据回答：发生了什么。
知识回答：这意味着什么。
流程回答：接下来怎么办。
反馈回答：这样做有没有用。
```

如果只有数据，会变成报表系统；
如果只有知识，会变成文档库；
如果只有流程，会变成机械 SOP；
如果只有 Agent，会变成聊天玩具。

只有它们结合起来：

```text
数据发现现象 -> 知识解释现象 -> 流程推动行动 -> 反馈修正知识
```
才会形成智能生产力。

这也是知识复利工程师区别于传统数据分析师和知识管理员的地方：他需要把数据表、业务文档、流程记录、用户反馈、专家经验、Agent 输出和评测结果组织成一个可持续迭代的业务系统。

## 3. 为什么单纯“搓小平台”未必有长期复利

在大模型能力快速提升、长程智能体开始展现能力、开源框架和云厂商持续成熟的背景下，AI 项目的价值重心正在发生变化。

过去，一个项目如果能做到：

传统交付常常是接一个模型、做一个页面、上传一些文档、跑一个问答，交付后结束。
看起来就已经像是一个 AI 应用了。但当模型本身越来越强，Agent 能够执行更长链路任务之后，单纯做“模型调用”“简短问答”“局部小工具”，已经远远不够。

老板和业务方真正期待的，往往不是一个问答机器人，而是某种意义上的“数字员工”：

```text
它理解业务对象；
知道当前上下文；
能调用企业知识；
能遵守流程规则；
能根据反馈修正判断；
能和人一起完成一段真实工作。
```

这背后其实是人机协作关系的变化：从 **human in the loop** 走向 **human on the loop**。

```text
human in the loop：
人仍然在每个关键步骤中亲自操作、确认和推动，AI 只是辅助生成、检索或建议。

human on the loop：
AI 能在被授权的业务边界内连续执行一段工作，人更多负责设定目标、定义变量/边界、监督过程、处理异常和最终负责。
```

如果 AI 只是问答机器人，人必须把上下文整理好、问题拆清楚、答案再搬回流程里，本质上仍然是人在流程中驱动 AI。

但如果 AI 要成为数字员工，它就需要理解企业上下文，知道自己正在处理哪个客户、哪张订单、哪个项目、哪条规则、哪一次异常，并能在流程中持续推进任务。此时人的角色不再只是反复提示 AI，而是站在流程之上，监督、纠偏和治理 AI 的工作。

这里的 harness，不只是技术框架，而是围绕 AI 协作的一整套业务运行环境，包括：

- 真实业务对象：客户、订单、项目、合同、工单、菜谱、家庭成员、库存等；
- 组织知识资产：制度、经验、案例、话术、SOP、复盘、专家判断；
- 流程和权限边界：谁能让 Agent 做什么，哪些动作必须人工确认；
- 数据证据：指标、交易记录、行为记录、反馈结果、历史表现；
- 工具和系统接口：CRM、ERP、知识库、表格、文档、IM、审批系统；
- 反馈和评测机制：输出是否有用，哪里错了，是否带来业务结果改善。

同样的大模型，有的公司只是用成了一个问答机器人；有的公司却借它重构了人与 AI 的协作关系。差距并不主要来自模型参数，而是来自企业的知识工程能力。

也就是说，真正决定 AI 应用上限的，往往不是：

```text
我会不会调用某个模型 API；
我会不会搭一个 RAG；
我会不会写一个 Agent demo。
```

而是：

```text
我能不能把企业的知识、数据、流程、权限、工具和反馈，组织成一个可被 Agent 持续调用和改进的业务系统。
```

这也是为什么单纯“搓小平台”很难形成长期复利。小平台可以交付一个功能，但很难天然获得完整的企业上下文；可以满足一个需求，但不一定能沉淀组织能力；可以演示一次智能效果，但不一定能持续进入真实工作流。

更关键的是，这件事很难完全通过甲乙方项目制落地。

这里涉及一个长期主义问题。知识复利不是一次性交付，而是在同一个业务场域里，围绕同一批业务对象、流程节点、异常案例和反馈结果，持续观察、修正和沉淀。它需要时间让知识被反复使用，也需要时间让错误暴露出来，再通过反馈进入下一轮迭代。

但甲乙方项目制天然更偏短周期交付：

```text
需求确认 -> 方案设计 -> 开发实施 -> 验收上线 -> 项目结束
```

这个节奏适合交付系统功能，却不一定适合运营组织知识。因为知识复利真正发生在上线之后：发生在使用、反馈、纠错、复盘、再编排的过程中。

项目制还有一个更现实的缺陷：信任边界。

企业最有价值的上下文，往往也是最不容易开放给外部团队的部分：

- 真实客户沟通记录；
- 真实经营数据和利润结构；
- 内部决策过程和妥协逻辑；
- 一线人员的非正式经验；
- 历史失败案例和责任边界；
- 权限关系、组织关系和灰度流程；
- 尚未公开的战略、产品和客户信息。

外部团队即使技术能力很强，也常常只能看到经过脱敏、整理和包装后的需求材料。这不是哪一方故意隐瞒，而是由商业信任、数据安全、组织边界和项目周期共同决定的。

因为在外部项目制里，很多需求已经经过了一层甚至多层转化：

```text
一线真实问题
→ 业务负责人理解
→ 产品/项目经理整理
→ 需求文档表达
→ 乙方理解
→ 技术方案
```

经过这种转化后，很多关键信息会失真：

- 真正的异常情况没有被表达出来；
- 一线人员的实际操作习惯被隐藏；
- 需求被包装成“功能点”，而不是业务摩擦；
- 决策依据、妥协过程、失败案例没有进入需求；
- 用户说出来的是“想要什么”，不是“为什么现在做不好”；
- 企业最真实的数据、权限关系和流程细节，也很难完整开放给外部团队。

所以，从职业复利角度看，单纯做乙方项目交付并不一定能积累足够深的业务知识壁垒。真正有复利的项目，不只是交付一个 AI 功能，而是逐步沉淀出：

- 领域对象；
- 业务规则；
- 判断标准；
- 异常案例；
- 流程节点；
- 权限边界；
- 数据证据；
- 决策依据；
- 反馈样本；
- 可复用模板；
- Agent 任务边界；
- 可评测样例。

否则项目结束后，经验也会很快散掉。下一次遇到类似问题，仍然只是重新接模型、重新写页面、重新拼流程，而不是在已有的组织知识系统上继续生长。

# 第二部分：知识复利系统到底是什么

## 4. 知识复利不是“多写文档”，而是让知识进入生产循环

知识复利不是简单地：

知识复利不是多写文档、多建知识库、多上传资料、多做 RAG。

这些只是知识资产化的第一步。

真正有复利的知识系统，至少需要满足四个条件：

真正的复利来自知识被使用、被反馈、被修正、被编排进流程。

如果知识只是存在知识库里，但没有进入日常任务流，它很容易变成新的知识坟场。

一个有复利的知识系统，应当能够做到：

- 在真实工作中被调用；
- 在任务完成后收到反馈；
- 在发现错误后被修正；
- 在流程中形成默认动作；
- 在下一次类似任务中复用；
- 在复用过程中继续积累新的判断。

因此，“知识复利”至少应拆成四层：

```text
知识资产化
+
知识流程化
+
知识反馈化
+
知识治理化
```

只做第一步，价值有限。

### 4.1 知识资产化

把分散在个人经验、聊天记录、会议纪要、项目文档、表格和操作习惯里的知识，转化为可被检索、引用、维护的资产。

包括：

- 规则；
- 案例；
- 模板；
- 流程；
- 决策标准；
- 异常处理；
- 常见问题；
- 成功与失败复盘。

### 4.2 知识流程化

让知识不是孤立存放，而是进入实际工作流。

例如：

- 新人 onboarding 时调用；
- 销售写方案时调用；
- 客服处理问题时调用；
- 项目复盘时调用；
- Agent 执行任务时调用；
- 管理者做决策时调用。

### 4.3 知识反馈化

知识必须能接受真实使用后的反馈。

例如：

- 这个回答是否有用；
- 这个方案是否被采纳；
- 这个规则是否过时；
- 这个流程在哪一步卡住；
- Agent 是否引用了错误知识；
- 一线人员是否补充了新情况。

### 4.4 知识治理化

知识越积越多，如果没有治理，就会变成知识债务。

治理包括：

- 来源可信度；
- 版本管理；
- 权限边界；
- 过期机制；
- 冲突处理；
- 人工确认；
- 审批机制；
- 安全和合规；
- 哪些知识可以自动更新，哪些必须人工确认。

---

## 5. 真实一手信息是知识复利的前提

知识复利的前提，不只是有知识库，而是知识获取渠道足够贴近真实使用。

也就是说，知识不能只来自二手需求文档，而应尽可能来自：

- 一线操作；
- 实际对话；
- 真实交付；
- 用户反馈；
- 失败案例；
- 异常处理；
- 决策过程；
- 任务结果；
- 复盘材料。

知识必须贴近使用现场，然后经过合理治理，才可能变成可复用的智能生产力。

如果知识来源已经被层层转述和包装，那么 Agent 学到的可能只是“组织想象中的流程”，而不是真实流程。

这也是为什么内部业务人员、长期嵌入业务的 AI 推动者，可能比纯外部交付者更适合做知识复利工程。

# 第三部分：组织结构与岗位迁移

## 6. 大模型普及后的组织结构：平台集中，知识分散，治理半集中，应用贴近业务

未来公司内部的 AI 能力，很可能不会是传统 IT 完全消失，也不会是业务部门完全自治。

更可能出现三层结构。

### 6.1 第一层：公司级 AI 基础设施

这一层由 IT、平台团队或企业级 AI 中台负责，提供：

```text
模型
权限
存储
审计
计费
安全
合规
MCP 网关
Token 管理
服务器运维
模型网关
基础数据连接
```

这部分偏基础设施和治理，适合集中建设。

### 6.2 第二层：业务部门内嵌 AI 能力

这一层更贴近业务，由懂业务的人维护：

```text
知识库
Agent
流程
Prompt
评测样例
业务规则
异常案例
反馈闭环
```

这些内容必须贴近业务现场，很难完全由远离业务的 IT 部门包办。

### 6.3 第三层：少量专家型中台 / AI Ops

这一层负责制定标准、处理复杂集成、治理风险，并做跨部门复用。

包括：

```text
知识治理标准
Agent 安全边界
跨系统集成
复杂工作流设计
评测体系
日志和审计
权限模型
高风险场景把关
```

因此，更可能形成的组织形态是：

理想组织形态是平台集中、知识分散、治理半集中、应用贴近业务。

这与“轻量半托管杠铃路径”是一致的：

- 上层有轻量平台、治理和基础设施；
- 下层有业务部门内生探索；
- 中间避免形成沉重、脱离业务的“大平台幻觉”。

---

## 7. 应用类算法工程师不会简单消失，但会发生迁移

“大模型普及后，应用类算法工程师会消失”这个判断需要拆开看。

如果指的是传统 NLP 场景下，为每个业务单独做文本分类、意图识别、信息抽取、摘要、问答等小模型的岗位，那么这类岗位确实会被压缩。

但 AI 应用能力不会消失，而是迁移到新的方向：

```text
AI 应用系统工程
知识工程
评测工程
流程编排
领域智能运营
```

未来更稀缺的，可能不是“会调一个小模型”的人，而是能回答这些问题的人：

- 业务知识应该如何结构化？
- 哪些知识适合进入 RAG？
- 哪些知识应该是硬规则？
- 哪些知识只是弱偏好？
- Agent 什么时候可以执行？
- 什么时候必须问人？
- 输出结果如何评测？
- 错误如何回流到知识库？
- 知识冲突如何处理？
- 权限和审计如何设计？

所以，岗位不是简单消失，而是从“应用算法”迁移到“AI 应用系统”和“业务知识系统”的设计、维护和运营。

---

## 8. 知识复利工程师的核心定义

可以把这个新型角色暂时称为：

```text
知识复利工程师
```

或者更职业化地表达为：

```text
AI Knowledge Systems Engineer
Knowledge Operations Engineer
Business AI Systems Engineer
Domain AI Ops
组织记忆工程师
业务知识系统工程师
```

它的核心工作不是简单维护文档，而是：

> 把业务中的经验、规则、案例、反馈、流程、异常处理方式，沉淀成可被人和 Agent 共同使用、持续更新、可评测、可治理的知识系统。

这个角色关心的不是一次性 AI 工具交付，而是长期的组织智能复利。

它要让组织从：

过去组织主要靠人记住、靠老人带新人、靠群聊翻历史、靠重复问答、靠临时拍脑袋。

转向：

```text
经验可沉淀
知识可调用
流程可复用
反馈可回流
Agent 可协作
新人可快速上手
组织少重复犯错
```

# 第四部分：能力模型

## 9. 这个角色需要的能力结构

### 9.1 领域建模能力

```text
对象
关系
规则
流程
角色

异常
反馈
指标
```

### 9.2 知识资产设计能力

```text
Wiki

知识图谱
Prompt
Agent 记忆
评测集
操作手册
```

不是所有东西都应该丢进 RAG。

### 9.3 数据证据组织能力

这个能力包括：

- 识别关键业务指标；
- 理解数据口径；
- 把数据挂到业务对象上；
- 区分事实、解释和判断；



### 9.7 组织推动能力

```text
记录
反馈
修正
复用
遵守流程
```

因此，这个岗位带有明显的组织协作和流程推动属性。

# 第五部分：风险与反面

## 10. 风险一：知识复利也可能变成知识债务

知识不会天然产生复利。

如果缺少治理，知识越积越多，可能变成负资产：

```text
业务变化了
规则过期了
文档没人维护
知识互相冲突
搜索结果不可信
没有来源
没有版本
没有责任人
没有反馈机制
Agent 引用旧知识导致错误
```

所以未来真正稀缺的不是“会积累知识”的人，而是：

```text
会设计知识生命周期的人。
```

这包括：

- 哪些知识值得沉淀；
- 哪些知识只适合临时记录；
- 哪些知识要定期失效；
- 哪些知识需要审批；
- 哪些知识可以由 Agent 自动更新；
- 哪些知识必须人工确认；
- 哪些知识能作为硬规则；
- 哪些知识只是弱偏好。

没有这套治理，知识库越大，Agent 越危险。

---

## 11. 风险二：方向有潜力，但不天然有壁垒

知识复利工程是一个有潜力的方向，但不能把它想象成天然安全、天然有壁垒、天然会被组织认可的路线。

### 11.1 概念太抽象，不容易被市场识别

“知识复利工程”“组织记忆工程”“业务知识系统化”这些表达，在认知上是成立的，但在现实招聘和组织预算里，未必马上能被识别。

很多老板和业务负责人更容易理解的是：

```text
降本
提效
少犯错
新人更快上手
客户响应更快
方案质量更稳定
交付经验可复用
```

而不是：

```text
我要建设知识复利系统。
```

所以，这个方向如果要变成职业机会，必须能被翻译成业务结果：

- 新人培训时间降低；
- 重复问答减少；
- 方案生成时间缩短；
- 客服或销售响应更一致；
- 项目复盘能进入下一次交付；
- 关键经验不再只依赖某个老员工；
- Agent 输出质量可以被持续评测和改进。

如果没有这些可感知结果，知识复利容易变成自嗨式概念。

### 11.2 低端部分会被工具平台吞掉

未来很多平台都会自动提供：

```text
文档上传
RAG 检索
权限管理
Agent 编排
知识图谱
工作流
基础评测
模型网关
```

所以，如果一个人的能力只是：

```text
会搭一个知识库
会配置一个 RAG
会做几个 Prompt
会接一个 Agent 平台
```

那么这部分能力很可能会被平台商品化。

真正不容易被吞掉的是平台之上的能力：

- 业务结构设计；
- 知识治理策略；
- 流程重构；
- 反馈闭环设计；
- 评测样例建设；
- 权限和风险边界定义；
- 跨角色协作机制设计。

也就是说，壁垒不在工具配置，而在业务知识系统的设计和运营。

### 11.3 知识维护很苦，长期更像园丁而不是建筑师

知识复利不是一次性建设，而是长期维护。

它需要持续做很多不性感但重要的工作：

```text
清理旧知识
合并重复知识
处理冲突知识
标记过期内容
修正错误引用
补充来源依据
维护版本记录
沉淀使用反馈
把一次性经验升级为规则
把过度总结的规则降级为案例
```

这类工作更像园丁：持续修剪、除草、浇水、更新土壤。

它不像一次性工程那样，做完一个平台就可以交付结束。

因此，这个方向适合愿意长期贴近业务、持续维护知识系统的人；不适合只喜欢搭建新工具、不愿意做长期运营的人。

### 11.4 业务部门未必愿意配合

知识复利工程不是纯技术问题，它会触碰组织里的真实权力结构。

很多隐性知识本身就是个人壁垒：

- 老员工的经验；
- 销售的客户判断；
- 运营的异常处理技巧；
- 项目经理的协调经验；
- 某些人对流程漏洞的掌握。

当你试图把这些经验外部化、结构化、系统化时，可能会遇到阻力。

因为对某些人来说：

```text
知识沉淀 = 个人不可替代性下降
流程透明 = 操作空间减少
经验共享 = 权力重新分配
```

所以，知识复利工程不仅需要技术能力，也需要组织沟通能力和利益协调能力。

### 11.5 过度结构化会压死真实业务弹性

还有一个容易被忽视的风险：不是所有知识都适合立刻结构化成规则。

有些业务判断本来就是情境性的：

- 客户关系；
- 谈判节奏；
- 风险偏好；
- 特殊个案；
- 临时妥协；
- 人情和组织政治。

如果过早把这些复杂判断固化为规则，Agent 可能会输出看似规范、实际僵硬的建议。

所以，知识复利工程需要区分：

```text
硬规则
软偏好
经验案例
临时判断
待验证假设
```

不是所有经验都应该立刻升级为标准流程。

---

# 第六部分：个人职业规划与阶段性结论

## 12. 对个人职业规划的启发

对于不在大厂的知识工作者来说，追逐每一个 AI 框架和小平台，未必是最有复利的路线。

工具会变：

```text
RAG 框架会变
Agent 框架会变
工作流平台会变
模型 API 会变
知识库产品会变
```

但以下问题不会消失：

```text
业务知识如何结构化？
业务数据如何变成证据？
组织经验如何外部化？
Agent 的任务边界如何定义？
知识如何进入流程？
反馈如何沉淀？
质量如何评测？
权限如何治理？
哪些场景不适合自动化？
```

因此，更有复利的个人定位不是：

```text
我会部署某个 AI 框架。
```

而是：

```text
我能把一个业务部门的隐性知识变成可运行、可维护、可复利的 AI 工作系统。
```

这可能会成为大模型普及后，普通知识工作者值得长期投入的一种新型职业能力。

---

## 13. 阶段性结论

在大模型成为基础设施之后，真正有复利的可能不是一次性 AI 应用交付，而是围绕业务知识、数据证据、流程反馈、组织记忆和 Agent 协作机制的长期工程能力。

这个方向可以概括为：

```text
把真实业务现场中的知识、数据、流程、反馈和异常处理经验，
沉淀成可被人和 Agent 共同使用的智能生产系统。
```

这不是传统意义上的知识管理，也不是单纯的应用开发。

它更接近一种新型能力：

```text
业务知识系统化能力
+
数据证据组织能力
+
AI 应用系统工程能力
+
组织记忆运营能力
```

未来公司里的 IT 部门可能更偏向基础设施和治理，业务部门则需要内生 AI 能力。应用类算法工程师的一部分工作会被大模型压缩，但 AI 应用系统工程、知识工程、评测工程、流程编排和领域智能运营会扩张。

因此，“知识复利工程建设与维护”很可能成为大模型普及后的关键技能之一。

但它的壁垒不在于会不会建知识库，而在于能否长期、贴近真实业务地完成：

```text
知识资产化
知识流程化
知识反馈化
知识治理化
数据证据化
```

只有这些环节同时存在，知识才可能产生复利。
