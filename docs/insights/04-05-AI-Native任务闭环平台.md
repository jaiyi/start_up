# 04-05 · AI Native 任务闭环平台

> 讨论稿 / 会更新 · 最近更新 2026-09-23
>
> **一句话结论**：AI Native 组织转型的合理产品形态，不是围绕每条业务流重造一套管理系统，而是在企业现有系统之上建设一层“AI Native 任务闭环平台”：用统一的业务对象、本体语义、任务状态、AI Skill、知识资产、权限审计、反馈回写和经营归因，把多个高价值业务流变成可治理、可复用、可进化的任务闭环。
>
> 更短地说：**厚场景，薄系统；不要造一堆烟囱系统，要造一层能承载多条业务流的 AI 任务控制面。**

---

## 0. 这篇回答什么

`04-04` 的设备维修案例非常有启发：它把设备、故障、工单、AI 诊断、复盘、知识库、技能矩阵和 SLA 上报串成闭环，已经不是普通 AI 问答，而是在重构制造现场任务流。

但它也引出一个更关键的问题：

> 难道未来每个业务流都要造一套管理系统吗？

例如：

```text
设备维修 → 造设备维修系统
质量复盘 → 造质量问题闭环系统
采购降本 → 造采购降本系统
项目毛利 → 造项目经营管理系统
库存优化 → 造库存清理系统
客户投诉 → 造客诉闭环系统
```

这条路看起来很自然，但风险很大。

如果每个场景都重新造系统，最后企业会得到一堆新的烟囱：数据重复、权限重复、流程重复、AI 能力重复、知识资产重复、审计口径重复、运维压力爆炸，IT 部门无法横向治理，Agent 访问边界失控，新一轮信息孤岛形成。

所以本篇要回答：

1. 为什么“围绕每条业务流造一套系统”不可持续？
2. 合理的 AI Native 产品形态应该是什么？
3. “AI Native 任务闭环平台”应该长什么样？
4. 它如何结合 `09` 里的 AI 原生数据治理、本体、业务文档和数仓？
5. 它如何吸收 product-analysis 里 Atlan、Alation、Databricks、数澜、明略、WorkBuddy、WeKnora 等产品调研的启发？
6. 它如何从设备维修这样的单点案例，变成可复制的平台能力？

## 1. 先区分：业务管理系统 vs AI Native 任务闭环平台

设备维修案例看起来像一套管理系统。

它有故障列表、维修工单、复盘任务、技能矩阵、知识库、SLA 上报和 AI 诊断助手，所以很容易得出一个结论：

> AI 要进入业务，就要围绕每条业务流造管理系统。

这个结论只对了一半。

对的是：AI 确实不能只停留在聊天框，必须进入业务流、任务流和结果闭环。

错的是：进入业务流不等于每条业务流都从零造一套独立系统。

更合理的区分是：

| 类型 | 传统业务管理系统 | AI Native 任务闭环平台 |
|---|---|---|
| 核心目标 | 管流程、留记录、做报表 | 改善经营结果、组织人机协同、沉淀可复用能力 |
| 建设方式 | 每个业务域一套系统 | 一套通用任务闭环底座 + 多个场景模板 |
| 业务对象 | 绑定在单个系统内 | 跨系统统一建模，映射到本体和经营对象 |
| 数据来源 | 系统自己录入为主 | 接入 ERP / MES / EAM / PLM / CRM / OA / 数仓 / 文档 |
| AI 位置 | 页面上的助手按钮 | 嵌入任务节点、决策节点、复盘节点、反馈节点 |
| 知识形态 | 附件、制度、说明文档 | 可调用 SOP、Skill、Prompt、案例、知识图谱、评测集 |
| 权限治理 | 各系统各自管 | 统一权限、审计、血缘、策略和 Agent 工具边界 |
| 结果评价 | 看流程完成率 | 看经营指标改善和可归因贡献 |
| 扩展方式 | 再开发一套系统 | 复制任务模板、对象模型、Skill 和治理策略 |

因此，表面形态可以有业务应用界面，但底层逻辑应该是平台化的。

一句话：

> **用户看到的是垂直任务应用，企业需要建设的是横向任务闭环平台。**

## 2. 为什么“造一堆系统”是错路

### 2.1 IT 部门无法无限横向做数据治理

每造一套系统，就会新增一组治理问题：这套系统里的数据从哪里来，是否是权威数据，字段口径是什么，谁能看，谁能改，谁审批，谁维护，和数仓怎么同步，和文档怎么关联，和知识库怎么同步，和 Agent 权限怎么绑定，出了错谁负责。

如果每个业务流都单独解决这些问题，IT 部门会被拖入无穷无尽的系统集成和权限运维。

最后不是 AI Native，而是 AI 加速了新系统烟囱的产生。

这会把企业重新带回数据中台时代的老问题：重平台、轻业务；重数据汇聚、轻闭环；重一次性交付、轻资产运营；建了很多表，但业务不会用；建了很多应用，但互相不通。

`09` 里已经讲过：“拆中台”拆掉的不是数据治理本身，而是低价值平台化幻觉。

AI 时代不能再重复这个错误。

### 2.2 每个系统独立接 AI，会导致 Agent 治理失控

如果每套业务系统都自己接大模型、自己建知识库、自己管权限、自己做工具调用，会出现同一个人有多套 AI 权限、同一份数据被多个 Agent 以不同口径使用、同一个指标被不同系统解释成不同含义、AI 输出无法统一审计、Prompt / Skill / RAG 索引无法复用、敏感数据访问边界混乱、错误经验扩散后没人负责等问题。

Agent 时代，治理对象不只是表和字段，还包括 Prompt、Skill、Tool、Agent、Workflow、RAG Index、Embedding、Model、Evaluation Dataset、Human Feedback 和 AI Output。这已经超出传统单系统权限模型，所以必须有一层横向的 AI 任务控制面。

### 2.3 重复造业务系统，会稀释真正的产品壁垒

AI Coding 让“做页面、做表单、做审批、做 CRUD”越来越便宜。

未来企业软件的壁垒不会来自“我能快速造一个列表页、审批流、台账或大模型按钮”，因为这些都会越来越低价值。真正有壁垒的是业务对象模型、任务流方法论、行业知识资产、本体语义层、AI Skill 编排、权限和审计体系、反馈闭环、经营归因模型和资产运营机制。

所以产品化方向不能是“更多系统”，而应该是“更强底座 + 更好的场景模板”。

## 3. 正确定义：AI Native 任务闭环平台

我倾向于把目标产品定义为：

> **AI Native 任务闭环平台：连接企业现有系统、数据资产、业务文档、AI Skill 和人类专家，围绕高价值经营任务构建可执行、可审计、可反馈、可归因、可复用的任务闭环层。**

它不替代 ERP、MES、EAM、PLM、CRM、OA、数仓和知识库，而是位于它们之上：

```text
业务用户 / 一线员工 / 管理者 / AI Agent
        │
        ▼
AI Native 任务闭环平台
        │
        ├── 任务流编排
        ├── 人机分工
        ├── AI Skill 调用
        ├── 知识资产调用
        ├── 审批确认
        ├── 执行留痕
        ├── 反馈回写
        └── 价值归因
        │
        ▼
既有企业系统 / 数据 / 知识
        ├── ERP / 财务 / 成本
        ├── MES / 产线 / 设备
        ├── EAM / 设备资产
        ├── PLM / 工艺 / BOM
        ├── CRM / 客户 / 商机
        ├── OA / 飞书 / 审批
        ├── 数仓 / 湖仓 / 数据集
        ├── 文档 / SOP / 复盘 / 视频
        └── 模型 / 特征 / 向量 / 图谱
```

它的核心不是“存所有数据”，而是组织：

```text
谁在什么业务对象上，基于什么数据和知识，调用了什么 AI 能力，完成了什么任务，经过谁确认，产生了什么结果，这个结果如何反馈和归因。
```

## 4. 平台的产品原则

### 4.1 厚场景，薄系统

场景必须厚，要深入到设备、故障、工单、维修、备件、产线、技能、复盘、停机损失、OEE 和老师傅经验这些真实业务细节；但系统要薄，不要重造 MES、ERP、EAM、PLM、HR、OA、文档系统、BI 和数据治理平台。平台真正应该做的是薄薄的一层：连接已有系统，组织任务流，嵌入 AI 能力，沉淀知识资产，记录反馈结果，计算经营影响。

### 4.2 先任务闭环，后智能升级

不要一开始就追求全自动 Agent。

更稳妥的路径是：

```text
先把任务流跑通
→ 再把 AI 嵌进去
→ 再记录人机协同反馈
→ 再优化 AI 推荐
→ 再做价值归因
→ 再尝试更高自动化
```

设备维修案例就是比较好的顺序：先有故障单、工单、复盘、技能矩阵，再嵌入 AI 诊断和知识 Skill。

### 4.3 数据不搬家，语义要统一

平台不应该把所有业务数据复制一份，变成新的数据仓库。

更合理的是：

```text
权威数据留在原系统；
任务平台保存任务状态、引用、快照、反馈和审计；
语义层统一业务对象、指标口径和关系；
必要时通过 MCP / API / 数据服务受控访问。
```

也就是说，ERP 仍然是财务和成本 source of truth，MES 仍然是产线和设备事件 source of truth，EAM 仍然是设备资产 source of truth，文档平台仍然是 SOP 和协作文档 source of truth，数仓仍然是分析数据 source of truth，任务闭环平台则是“业务任务状态、AI 参与、反馈和归因”的 source of truth。

### 4.4 AI 必须被治理，而不是自由乱跑

Agent 不能直接拿数据库 owner 权限，也不能绕过权限系统查数。

平台要让 AI 通过受控接口行动：

```text
Agent / Skill
→ Tool / MCP / API
→ 权限策略
→ 数据质量 / 血缘 / 审计
→ 业务系统 / 数仓 / 知识库
```

每一次 AI 行动都应该回答：用了什么数据，调用了什么工具，基于哪个知识版本，输出给了谁，是否经过人工确认，是否写回业务系统，以及结果后来是否被证明有效。

### 4.5 平台价值来自复用，不来自单点项目

单点场景一定要做，但每做一个场景，都要沉淀对象模型、任务模板、Skill、Prompt、本体关系、指标口径、评测集、治理策略、复盘模板和经营归因方法，否则每个项目都会退化成重交付。

## 5. 平台总体架构

可以把 AI Native 任务闭环平台设计成八层。

```text
AI Native 任务闭环平台
├── 1. 连接层：以 API / MCP / Connector 受控读写已有系统、数据资产和协同工具
├── 2. 语义层：统一业务对象、本体、指标口径和术语
├── 3. 知识层：管理文档、案例、SOP、视频、复盘和知识图谱
├── 4. 任务层：定义任务对象、状态机、人机分工和执行留痕
├── 5. AI 能力层：Prompt、Skill、Agent、Tool、模型和评测
├── 6. 治理层：权限、血缘、质量、审计、敏感数据和策略
├── 7. 反馈层：人审、采纳、修正、结果回写和经验蒸馏
└── 8. 经营归因层：指标影响、成本动因、EVI、贡献和分成
```

这八层和现有产品调研可以对应起来：

| 平台层 | 外部产品启发 | 关键借鉴 |
|---|---|---|
| 连接层 | Databricks / 数澜 / 星环 | 不只读表，还要通过 API / MCP / Connector 受控读取上下文、创建任务、更新状态、提交审批、生成文档、同步知识和推送消息 |
| 语义层 | 数澜 / 明略 / Alation | 本体、业务术语、指标口径、对象关系 |
| 知识层 | WeKnora / 飞书 / WorkBuddy / 明略 | 文档数据化、知识图谱、RAG / GraphRAG、产物沉淀 |
| 任务层 | 设备维修案例 / 工单系统 / 飞书流程 | 任务状态、责任人、SLA、审批、闭环 |
| AI 能力层 | Agent Beacon / WorkBuddy / WeKnora | Skill、Agent 运行轨迹、经验蒸馏、MCP 工具 |
| 治理层 | Databricks Governance Hub / Atlan / Alation | 权限、血缘、质量、审计、主动元数据 |
| 反馈层 | Agent learning systems | 人工修正、采纳率、复盘、轨迹评估 |
| 经营归因层 | 04 / 04-01 EVI | 经营账本、成本动因、反事实基线、价值归因 |

### 5.1 传统软件在平台里的位置

传统软件没有消失，也不应该被任务闭环平台整体替代。更准确的位置是：ERP、MES、EAM、PLM、CRM、HR、OA、飞书、数仓、BI 和知识库仍然是企业的权威系统和动作落点；AI Native 任务闭环平台位于这些系统之上，通过连接层读取权威上下文、发起受控动作、记录任务过程、沉淀反馈结果，再把需要回写的状态、文档、审批、知识和指标写回原系统或平台自身的任务库。

可以把整体产品位置理解为五层：最底层是传统软件 / 权威系统，负责记录财务、生产、设备、人员、订单、客户、审批、文档和指标等权威事实；其上是连接层，负责 API、MCP、Webhook、ETL、消息队列和写回连接器，把“读上下文”和“写动作”都纳入权限、Schema、幂等和审计；中间是 AI Native 任务闭环平台，负责业务对象模型、任务流引擎、AI Skill、知识资产、治理、反馈和经营归因；再上面是场景应用层，例如设备维修工作台、质量问题闭环工作台、采购降本工作台、项目毛利改善工作台和客户投诉处理工作台；最上层才是一线员工、工程师、主管、业务负责人、管理层、IT、数据治理和 AI Ops 等不同角色的实际使用入口。

因此，传统软件在这个体系里有三种身份：第一，它是权威数据源，例如 MES 记录设备报警，ERP 记录成本，HR 记录人员和技能，飞书记录协作文档，数仓沉淀经营指标；第二，它是动作执行系统，例如任务平台可以在人工确认和权限校验后向 EAM 创建维修工单、向 OA 发起审批、向飞书推送复盘、向知识库提交候选 SOP、向数仓写入结果快照；第三，它仍然可能提供原生操作界面，供财务、生产、设备、采购、质量等角色处理原系统主流程。任务闭环平台不是把这些系统吞掉，而是把跨系统任务、AI 协同、知识调用、反馈学习和经营归因组织起来。

### 5.2 各层用户和产品形态

| 层级 | 主要用户 | 产品形态 | 核心价值 |
|---|---|---|---|
| 传统软件 / 权威系统层 | 财务、生产计划、设备工程、质量、采购、销售、HR、IT 运维、数据团队 | ERP 页面、MES 页面、EAM 工单、OA 审批、飞书文档、BI 报表、数仓表 | 记录权威事实、承载原有主流程、满足合规和稳定性 |
| 连接层 | IT 集成工程师、平台工程师、数据工程师、安全管理员、AI 工程师 | 连接器市场、API 配置台、MCP Tool Registry、字段映射、权限映射、写回动作配置、接口日志、失败重试队列 | 让平台既能读上下文，也能受控写任务、改状态、录反馈、生成文档和推送消息 |
| 治理层 | 数据治理团队、IT 安全团队、业务数据 owner、知识管理员、流程管理员、审计人员 | 数据资产目录、知识资产目录、Agent 可访问资产目录、权限策略、敏感字段标注、血缘图、AI 调用审计、质量问题队列 | 回答 Agent 能看什么、为什么能看、谁批准、用了什么、输出给谁、是否写回、出错后能否追溯 |
| 语义层 | 业务架构师、行业专家、数据产品经理、流程 owner、AI 产品经理 | 业务对象建模器、本体编辑器、术语表、指标口径管理、对象关系图、字段映射表、业务规则配置台 | 把“设备、工单、人员、技能、SOP、停机损失”等业务概念转成 AI 和系统都能理解的语义结构 |
| 任务层 | 业务流程 owner、部门负责人、一线主管、运营负责人、设备 / 质量 / 采购 / 项目负责人 | 任务模板配置器、流程编排器、状态机配置、SLA 配置、任务看板、异常事件中心、审批节点配置 | 把业务流变成可执行、可追踪、可升级、可复盘、可归因的任务流 |
| AI Skill / Agent 层 | 一线使用者、AI 产品经理、业务专家、Prompt 工程师、知识工程师、模型评估人员 | Skill 市场、Prompt 管理台、Agent 编排器、MCP 工具注册、评测台、运行轨迹查看器、版本管理 | 把 AI 从聊天框嵌入任务节点，提供检索、诊断、推荐、生成、归因、预警等可治理能力 |
| 知识资产层 | 老师傅、业务专家、知识管理员、培训负责人、质量 / 工艺 / 设备专家 | SOP 管理、案例库、复盘库、故障模式库、视频资料库、知识图谱、RAG / GraphRAG 管理台、知识审核流 | 让知识有 owner、版本、适用范围、审核状态、调用记录、贡献指标和失效机制 |
| 场景应用 / 工作台层 | 维修技术员、班组长、质量工程师、采购人员、项目经理、客服、业务负责人、管理层 | 设备维修工作台、质量闭环工作台、采购降本工作台、项目毛利工作台、客诉处理工作台 | 用户每天真正操作的薄应用；看起来像业务系统，但底层复用统一任务、权限、AI、知识和归因能力 |
| 反馈 / 评测 / 学习层 | AI Ops、业务专家、流程 owner、知识管理员、模型评估人员 | AI 建议采纳率看板、人工修改记录、失败案例池、Skill 效果评估、任务复盘队列、经验蒸馏工作台 | 把“AI 建议是否有用、人怎么改、结果是否变好、知识是否过期”转化为持续学习数据 |
| 经营归因 / 智力资产层 | 业务负责人、经营管理层、财务、HR、绩效负责人、数字化负责人 | 经营 AI 账本、EVI 看板、AI ROI 看板、知识资产贡献榜、Skill 贡献分析、内部积分 / 分成配置 | 证明任务流是否真的改善经营结果，并把人、团队、Skill、知识资产的贡献变成可见资产 |

### 5.3 连接层必须既能读，也能受控写

如果连接层只能读，它最多把平台做成智能查询层或分析看板，无法构成真正的任务闭环。读能力让 AI 理解业务，例如从 MES 读取设备报警，从 EAM 读取设备台账和维修履历，从 HR 读取人员排班和技能等级，从飞书 / WeKnora / Liwork 读取 SOP、维修案例、复盘报告和故障指导；写能力让 AI 进入业务，例如创建故障单、创建维修工单、更新工单状态、填写维修处理记录、提交验收结果、创建复盘任务、生成复盘报告、提交审批、写入问题专项、同步知识库、更新技能矩阵、记录 AI 建议采纳 / 驳回和回写停机时长。

但“能写”不等于“随便写”。写能力应该按风险分级：L0 是只读连接，只允许诊断建议、相似案例检索、风险提示和草稿生成；L1 是写平台自己的任务状态，例如记录 AI 建议、人工采纳、复盘草稿和反馈结果；L2 是通过正式 API / MCP 回写业务系统，例如更新 EAM 工单状态、向飞书创建复盘文档、向 MES 回写处理结果、向知识库提交候选知识；L3 才是受控自动执行，例如停机超过阈值自动创建复盘任务、故障触发自动推荐派工、复盘审批通过后自动归档知识库、SLA 超时自动推送主管。关闭重大故障单、确认维修完成、改变关键设备状态、修改正式 SOP、提交质量结论、触发财务归因等高风险动作，仍然必须有人类责任人确认。

更准确地说，连接层不是简单的数据连接器，而是企业系统的受控读写与动作执行层。它应该具备权限校验、Schema 校验、动作策略判断、人工确认、幂等控制、审计日志、失败补偿和敏感动作拦截能力，保证 Agent 可以发起动作，但每个动作都有明确边界、责任人和追溯链路。

### 5.4 用设备维修串起全链路

发生设备故障时，MES 先产生报警，EAM 提供设备台账和历史工单，HR 提供维修人员技能和排班，飞书 / 知识库提供 SOP 和历史复盘，数仓提供 MTTR、MTBF、OEE 等指标；连接层把这些上下文读入平台，并在权限允许时创建任务或更新状态；语义层识别这是某台设备、某条产线、某类故障码、某类技能要求和某类经营影响；任务层生成故障处理任务，设置责任人、SLA、审批规则和复盘规则；AI Skill 层调用相似案例检索、维修方案推荐、风险提示和复盘生成；工作台层让维修人员在“我的工单”里看到 AI 建议、相关 SOP、历史案例和一键采纳 / 修改 / 驳回入口；写回层在人确认后更新工单状态、写入维修记录、提交验收、必要时创建问题专项；知识层在复盘后生成候选知识，经专家审核后归档；反馈层记录 AI 建议是否被采纳、人工改了哪里、结果是否有效、是否复发；经营归因层再计算 MTTR 是否下降、停机损失是否减少、AI 推荐节约了多少时间、哪条知识资产被复用、哪个班组贡献了有效经验。

这个例子说明：传统软件负责记录权威事实和执行原有主流程，AI Native 任务闭环平台负责跨系统组织任务、嵌入 AI 能力、调用知识资产、控制权限审计、记录人机协同过程、沉淀反馈并计算经营价值，场景应用负责让具体角色完成具体任务。用户看见的是维修工作台，企业真正复用的是底层的任务、权限、AI、知识、反馈和归因能力。

## 6. 核心模块设计

### 6.1 业务对象与本体中心

这是平台的“语义骨架”。

它要定义企业里的关键对象，例如制造业里的设备、产线、工序、产品、物料、供应商、客户、订单、项目、故障、缺陷、工单、措施、人员、技能、知识资产、AI Skill 和经营指标；并且每个对象都要维护唯一 ID、来源系统、owner、权限等级、关键属性、对象关系、对应文档 / 数据资产，以及它可以被哪些任务引用。

设备维修场景里，`设备 E-001` 不只是一个编号，而是一个可被任务和 AI 共同理解的对象：它属于 `Line-A` 产线，关联“定子压装”工序，设备型号为 `XXX`，历史故障包括 `F-101 / F-209 / F-311`，关联 `SOP-设备点检-001` 和“电机压装异常诊断 Skill”，技能要求是电气二级 + 机械一级，经营指标包括停机时长、OEE 和维修成本，权限上只有维修组、设备工程和产线主管可见。

这就是 `09` 里说的：

```text
数仓字段 / 指标
↔ 业务术语 / 本体概念
↔ 文档实体 / 事件 / 规则
↔ Agent 可理解的任务语义
```

没有这层，本质上还是一堆系统和文档。

### 6.2 任务流引擎

任务流引擎是平台的核心。

它不是传统 OA 审批流，而是 AI Native 任务对象。

一个任务应该结构化为 `Task` 对象，包含 `task_id`、`task_type`、`business_object_refs`、`trigger_event`、`expected_outcome`、`input_context`、`human_owner`、`ai_participants`、`required_skills`、`tool_permissions`、`status`、`sla_policy`、`review_policy`、`evidence_refs`、`output_artifacts`、`feedback_records` 和 `value_impact_refs` 等字段。

举设备维修例子，任务类型是“维修工单处理”，触发事件来自 MES 设备故障报警，业务对象指向设备 `E-001`、产线 `Line-A` 和故障 `F-209`，期望结果是恢复设备运行并沉淀维修记录；AI 参与者包括诊断助手和历史案例检索 Skill，人类责任人负责接单、确认方案和执行维修，高风险故障需要设备工程师确认；SLA 可以设为 10 分钟接单、30 分钟初步诊断、超过 60 分钟升级；输出物包括维修记录、采用方案、停机时长和是否复发；反馈记录包括方案是否有效、AI 推荐是否采纳；价值影响则关联停机损失、维修工时和备件消耗。

这个任务对象可以复用到质量问题闭环、采购降本、项目毛利异常、库存清理、客户投诉根因分析等场景。差异在业务对象和模板，不在底座。

### 6.3 AI Skill 与工具注册中心

平台需要一个 AI 能力市场，但它不是简单的 Prompt 列表。

每个 Skill 都应该有结构化注册信息，至少包括名称、适用任务类型、输入 schema、输出 schema、可调用工具、可访问数据范围、依赖知识资产、适用边界、风险等级、评测集、版本、owner、审核状态和运行日志。

例如“设备故障相似案例检索”这个 Skill，适用任务是维修工单处理和维修复盘，输入包括设备型号、故障描述、报警码、产线和时间，输出包括相似案例、相似度、处理方案、风险提示和引用来源，可调用知识库检索、图谱查询和维修履历查询工具；权限边界是只能访问当前工厂授权设备数据，审核要求是输出仅供参考且高风险设备必须人工确认，评测指标可以用 Top-3 命中率、技术员采纳率和错误推荐率。

这吸收了 product-analysis 里的几个判断：WorkBuddy 强在 Agent 产物沉淀，但不能替代数据层；WeKnora 强在 RAG / Wiki / MCP，但不能直接承担动态状态 source of truth；Agent Beacon 这类系统提醒我们，Agent 轨迹可以被评估、蒸馏和沉淀为 Skill；Databricks / Atlan / Alation 提醒我们，Skill 和 Agent 也应该被治理。

### 6.4 知识资产与 GraphRAG 层

知识层不能只是上传文档。

它要把业务文档数据化：SOP 要抽取适用设备、步骤、风险点、工具和备件；复盘报告要抽取故障现象、根因、处置措施和预防措施；维修视频要抽取操作步骤、关键动作和注意事项；会议纪要要抽取责任人、决议、待办和风险；案例文档要抽取故障类型、处理方案、停机影响和是否复发。

然后映射到业务对象和本体：文档片段先做实体抽取、关系抽取和事件抽取，再关联设备、故障、工序、人员和任务，最后进入知识图谱和向量索引。

GraphRAG 的作用不是炫技，而是让 Agent 能同时使用图谱关系、文档证据、结构化指标、本体约束和历史任务结果。

维修诊断时，Agent 不应该只找相似文本，而应该沿关系检索：从当前故障报警码出发，关联设备型号、历史故障、相同工序、曾采用方案、复发情况、SOP、负责专家和备件库存。这才是企业级知识可用。

### 6.5 权限、血缘与审计控制面

这是平台能不能被企业真正使用的关键。

Agent 时代，权限不是一个附属功能，而是产品内核。

平台至少要记录：谁发起了任务，Agent 用了哪些数据，调用了哪些工具，读取了哪些文档，引用了哪个知识版本，输出了什么建议，谁确认了建议，是否写回业务系统，以及后续结果如何。

它要吸收 Databricks Governance Hub、Atlan、Alation 的启发，形成覆盖统一资产目录、owner / steward、权限继承、敏感分类、行级 / 列级 / 文档级 / 工具级访问控制、数据质量信号、认证数据集、业务术语、血缘影响分析、审计日志和主动治理任务的控制面。

在任务闭环平台中，血缘要从单纯数据血缘扩展成数据血缘、文档血缘、知识血缘、Prompt / Skill 版本血缘、Agent 行为血缘、人工确认血缘和经营结果血缘，这样 AI 的每个建议都可以被追溯。

### 6.6 反馈与学习层

AI Native 平台必须有反馈层，否则知识不会复利。

每个任务结束后，都应该记录 AI 建议是否被采用、人改了什么、为什么改、实际结果如何、是否复发、哪条知识有效、哪条知识过期、是否产生新 SOP、是否需要更新 Skill、是否进入评测集。

这对应 Agent learning systems 的启发：运行轨迹先被评估，再筛选高信号经验，随后蒸馏成技能、规则或 SOP，并跨任务复用。

但企业场景里必须多一层治理：AI 自动总结的经验要经过专家审核、适用边界标注、版本发布，之后才能被任务流调用，不能让模型自己把所有经验自动发布成组织知识。

### 6.7 经营归因层

这是 `04` 和 `04-01` 的核心。

任务闭环平台最终要回答：这条任务流有没有改善经营结果，哪个 AI Skill 有贡献，哪个知识资产有贡献，哪个人类专家有贡献，这个贡献能不能用于绩效、分成或供应商结算。

因此平台需要经营归因对象：

```text
ValueImpact
├── 经营对象：设备 / 项目 / 产品 / 客户 / 订单
├── 指标：停机时间 / OEE / 成本 / 毛利 / 周期 / 质量
├── 基线：历史均值 / 对照组 / 预算 / 目标 / 预测
├── 实际：任务后结果
├── 差异：改善或恶化
├── 归因等级：相关 / 采纳 / 反事实估算 / 已审计
├── 贡献对象：人 / 团队 / AI Skill / 知识资产 / 流程模板
├── 可信等级：临时估算 / 业务确认 / 财务确认 / 审计确认
└── 结算状态：不可结算 / 可纳入绩效 / 可进入奖金池 / 可分成
```

设备维修场景里可以从简单公式开始：停机损失估算 = 停机时长 × 产线单位小时产出 × 单位贡献毛利。

然后逐渐纳入是否瓶颈设备、是否影响订单交付、是否影响良率、是否造成返工、是否产生外协维修、是否消耗关键备件、是否因为 AI 推荐缩短处理时间、是否因为某 SOP 避免复发等因素。

不需要第一天就达到财务审计级精度，但必须从第一天就有“经营归因字段”。

## 7. 平台如何避免变成“大而全中台”

这点非常重要。

AI Native 任务闭环平台不是旧中台复活。

它必须坚持几个边界。

### 7.1 不替代权威业务系统

不替代 ERP、MES、EAM、PLM、CRM、HR 和财务系统，这些系统仍然管理权威数据和主流程。

任务闭环平台做的是跨系统任务编排 + AI 能力嵌入 + 反馈回写 + 经营归因。

### 7.2 不做无业务入口的平台

平台不能先建一堆抽象能力，再等业务来用。

正确路径是从 1-2 个高价值场景切入，抽象对象、任务、Skill、知识、治理、归因的共性，再扩到相邻场景。

设备维修可以是一个起点，但平台能力要能扩到质量问题闭环、工艺异常分析、采购降本、项目毛利改善、库存清理、客户投诉根因分析等相邻高价值场景。

### 7.3 不把所有知识都塞进一个 RAG

企业知识不是“所有文档切片进向量库”。

要区分：

| 资产 | 合理处理方式 |
|---|---|
| 稳定规则 / SOP | 版本化、审核、权限、RAG + 结构化抽取 |
| 历史案例 | 关联业务对象、标记结果和适用边界 |
| 业务文档 | 抽取实体、事件、关系，进入图谱 |
| 动态状态 | 留在业务系统 / 数据库，通过受控接口访问 |
| 经营指标 | 留在数仓 / 经营账本，带口径和血缘 |
| AI 产物 | 沉淀为报告、任务记录、候选知识，经审核后发布 |

这也是 WorkBuddy、WeKnora、飞书文档调研给出的共同启发：知识库 / 资料库 / 云文档都不应该替代数据库或数仓。

### 7.4 不让 AI 绕过组织责任

所有 AI 建议都要有责任边界：AI 可以推荐，人必须确认，高风险动作必须审批，写回业务系统必须留痕，错误建议必须可追溯，经验沉淀必须有人审核。AI Native 不是无人负责，而是责任更清晰。

## 8. 以设备维修为例的平台化抽象

从 `04-04` 设备维修案例，可以抽象出一组通用平台能力。

| 设备维修里的功能 | 平台化抽象 | 可迁移到其他场景 |
|---|---|---|
| 故障单 | 业务事件 / 异常事件 | 质量异常、库存异常、毛利异常、客诉事件 |
| 维修工单 | 任务对象 | 降本任务、整改任务、复盘任务、客户响应任务 |
| 自动派发 | 任务分派策略 | 按 owner、技能、权限、SLA、负载分派 |
| AI 诊断助手 | 诊断 / 推荐 Skill | 质量根因、采购替代、毛利归因、客诉分析 |
| 一键采用方案 | AI 建议采纳机制 | 任何人机协同任务都需要采纳 / 驳回 / 修改 |
| 问题专项管理 | 长周期措施闭环 | 质量 8D、降本项目、供应商整改、工艺优化 |
| 自动复盘任务 | 规则触发任务 | 超阈值异常、重大损失、客户升级、复发问题 |
| 复盘报告 | 结构化经验资产 | 案例库、SOP、故障模式、最佳实践 |
| 技能矩阵 | 人员能力模型 | 销售能力、工艺能力、质量能力、采购能力 |
| SLA 上报 | 任务治理策略 | 交付延期、质量超时、客户响应、审批积压 |
| 知识图谱 | 本体 / 关系层 | 设备-故障、产品-缺陷、客户-订单、供应商-物料 |

这说明：

> 设备维修系统不应该只沉淀成“设备维修产品”，而应该沉淀成“异常事件 → 任务闭环 → 知识资产 → 经营归因”的平台模板。

## 9. 一个更具象的平台功能地图

如果把这个平台做成产品，我会设计成以下模块。

### 9.1 场景模板中心

用于快速配置一条业务任务流。

模板可以包括设备维修闭环、质量问题 8D 闭环、采购降本闭环、项目毛利异常闭环、库存清理闭环、客户投诉根因分析等类型。每个模板都要定义业务对象、触发事件、任务节点、角色权限、AI Skill、知识资产、指标口径、SLA、复盘规则和价值归因方式。

### 9.2 任务工作台

任务工作台是用户日常使用入口，通常包括我的任务、待确认 AI 建议、待审批事项、超时预警、关联对象详情、证据和引用、一键采纳 / 驳回 / 修改 AI 输出、复盘生成、知识沉淀建议等功能。关键不是“聊天”，而是“在任务中使用 AI”。

### 9.3 AI Copilot / Agent 面板

嵌在任务里的 AI Copilot / Agent 面板应该知道当前任务上下文：当前业务对象是谁，任务处于什么状态，用户是谁，用户有什么权限，当前可以调用哪些工具，哪些数据可信，哪些知识适用，哪些输出必须人工确认。

### 9.4 知识资产库

知识资产库不是普通文档库，而是可调用资产库。资产类型可以包括 SOP、案例、Prompt、Skill、Workflow、检查清单、故障模式、指标口径、评测集和复盘模板；每个资产都要有 owner、版本、适用任务、适用对象、权限、质量等级、使用次数、采纳率、贡献结果和失效机制。

### 9.5 业务对象图谱

业务对象图谱用于组织实体和关系。例如制造场景里，设备属于产线、设备执行工序、工序影响产品质量、物料来自供应商、缺陷发生于工序、故障影响停机时间、SOP 适用于设备型号、人员具备技能、Skill 适用于故障类型。这层让 AI 不只是“读文档”，而是理解业务拓扑。

### 9.6 治理运营台

治理运营台给 IT、数据治理和流程 owner 使用，功能包括数据资产目录、知识资产目录、Skill 目录、权限策略、敏感数据识别、访问审计、AI 输出审计、血缘追踪、质量监控、过期资产治理和风险任务队列。这就是 Atlan / Alation / Databricks Governance Hub 启发下的平台控制面。

### 9.7 价值归因看板

价值归因看板给业务负责人和管理层看。不要只看用了多少次 AI、生成了多少报告、节省了多少分钟，更要看任务闭环率、AI 建议采纳率、复盘完成率、知识资产复用率、MTTR 改善、故障复发下降、停机损失减少、采购降本金额、质量损失减少、项目毛利改善和高风险任务拦截。这才是经营层面的 AI 转型。

## 10. 最小可行产品：不要一开始做大平台

虽然这里讲的是平台，但落地不能一开始就做大平台。

MVP 应该从一个高价值业务流切入，例如设备维修。

### 10.1 MVP 场景选择标准

优先选择高频、高损失、强协同、强经验依赖、有数据基础、有知识沉淀、结果可量化且业务 owner 明确的场景，设备维修非常符合。

### 10.2 第一阶段只做六件事

第一阶段只做六件事：定义设备、故障、工单、人员、技能、知识、指标等业务对象；接入 MES 故障、维修工单、SOP、复盘、人员技能等关键数据；配置报修、派工、处理、复盘、升级等任务流；嵌入相似案例检索、维修建议、复盘生成等 2-3 个 AI Skill；记录采纳、修改、结果、复发、停机时长等反馈；最后做一个简单价值账，先跟踪 MTTR、停机时长、AI 采纳率和知识复用率。

先不要做全企业本体、全量知识图谱、完整经营 EVI、全自动 Agent 和全场景平台。

### 10.3 第二阶段抽象平台能力

当设备维修跑通后，再抽象异常事件模型、任务状态机、AI 建议采纳模型、复盘任务模板、知识资产元数据、Skill 注册与评测、权限和审计模式、基础价值归因模型，然后迁移到第二个场景，例如质量问题闭环。

### 10.4 第三阶段进入多场景平台化

当 2-3 个场景跑通后，才开始建设真正的平台化能力，包括场景模板中心、业务对象图谱、跨场景知识资产库、统一 Skill 市场、统一治理运营台、经营归因看板和智力资产贡献机制，这样可以避免“大平台先行”的失败。

## 11. 从产品定位看，它不是哪一类现有产品

这个平台会借鉴很多产品，但不能简单等同于某一种。

### 11.1 它不是普通知识库

知识库回答的是“哪里有资料、这个问题怎么查”；任务闭环平台回答的是“这个任务该如何完成、谁负责、AI 能做哪部分、知识怎么被调用、结果有没有改善”。

### 11.2 它不是普通数据治理平台

数据治理平台回答的是“数据在哪里、谁能访问、质量如何、血缘是什么”；任务闭环平台要进一步回答“这些数据如何支撑某个任务、AI 用这些数据做了什么判断、这个判断是否被采纳、任务结果如何回写”。

### 11.3 它不是普通低代码 / BPM

低代码 / BPM 回答的是“怎么搭表单和流程”；任务闭环平台回答的是“怎么让任务流承载 AI、知识、反馈、归因和资产复用”。

### 11.4 它不是普通 Agent 工作台

Agent 工作台回答的是“人和 Agent 如何协作完成任务、Agent 产物如何沉淀”；任务闭环平台还要回答“Agent 任务如何嵌入企业业务对象、权限治理、经营指标和组织激励”。

所以它更像一个交叉层：任务流平台 + AI 原生数据平台 + 数据治理控制面 + 知识图谱 / GraphRAG + Agent Skill 市场 + 经营归因账本。

## 12. 未来产品的核心壁垒

这个平台的壁垒不应该是页面，而是资产。

### 12.1 行业任务模板

例如制造业里的设备维修闭环、质量 8D 闭环、工艺参数异常、采购降本、库存清理、项目毛利改善等模板，数量越多，交付越快。

### 12.2 业务对象本体

制造业本体可能包括：

```text
工厂、车间、产线、设备、工序、工装、模具、物料、供应商、产品、批次、缺陷、故障、维修、人员、技能、订单、客户、成本、指标、措施。
```

这比单个系统功能更难复制。

### 12.3 Skill 和评测集

真正可复利的是设备故障诊断 Skill、质量根因分析 Skill、项目毛利归因 Skill、采购替代料建议 Skill、库存清理建议 Skill、复盘报告生成 Skill，并且每个 Skill 都要有评测集、采纳率和失败案例。

### 12.4 反馈数据

谁拥有真实任务执行反馈，谁就拥有飞轮。

反馈包括 AI 建议是否被采纳、人怎么改、结果是否变好、是否复发、哪条知识有效、哪个专家贡献高。这些数据比模型本身更有壁垒。

### 12.5 治理和归因方法论

企业级 AI 最后一定会问：能不能审计，能不能解释，能不能控制权限，能不能证明价值。谁能把治理和归因做成产品，谁就比单纯 Agent 应用更有护城河。

---

## 13. 一句话收束

不要围绕每条业务流重造一套管理系统。

要围绕高价值经营任务，建设一层可复用的 AI Native 任务闭环平台：业务对象统一、任务流可配置、AI Skill 可插拔、知识资产可调用、权限审计可治理、反馈结果可回写、经营价值可归因、智力贡献可激励。这才是从单点 AI 应用走向 AI Native 组织的合理产品形态。
