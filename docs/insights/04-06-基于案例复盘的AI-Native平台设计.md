# 04-06 · 基于案例复盘的 AI Native 平台设计

> 讨论稿 / 会更新 · 最近更新 2026-09-30
>
> **一句话结论**：17 个一手案例（理想汽车开放 Claude Code 给全体业务人员后的自发生长实践）验证并修正了 `04-05` 的平台设计。最终形态：**平台做公共品底座（语义、工具注册、资产治理、成本遥测）+ 任务闭环作为模板之一，业务流留给草根和飞书**；判定各模块取舍的方法是"选择 vs 妥协"分析——案例作者在现状形态上自发打的补丁（补偿行为），就是该升级为平台标准件的路标。

---

## 1. 证据基础与分析方法

### 1.1 证据：17 个案例 = 一场自然实验

同一政策环境（每人一个 Claude Code 账号 + 开放部分 MCP/飞书接口 + 内部 AI 社区）下，业务侧自发生长出 17 个案例：确定性自动化平台、专业工具 Agent 化（CATIA/TRACE32）、知识资产化（流程库/部门知识库/个人蒸馏）、数据分析智能体、全流程研发 Agent、销售门店工具。全部对应真痛点、真使用，多数为单人 3 个工作日级投入。

### 1.2 方法：现状 ≠ 应然，区分选择与妥协

案例呈现的形态混杂着两类东西：

- **选择**：约束解除后仍应保留的形态（被验证的合理设计）；
- **妥协**：资源约束下的近似解，约束解除后应升级。

区分的判据不是立场，是**补偿行为检测**：观察案例作者自发打的补丁——手工维护的映射表、人工执行的验证环节、绕过缺陷形态的变通做法。补丁指向的方向就是目标形态的方向。**草根手工搭出的雏形，恰恰证明该模块是真需求。**

## 2. 需求框架：业务侧真正在要什么

### 2.1 业务需求分层

| 层级 | 意图 | 案例分布 | 判定 |
|---|---|---|---|
| L1 执行自动化 | 把重复活干掉 | 近半案例 | **选择**——重心压倒性在此 |
| L2 判定辅助 | AI 帮我校验判断 | 六案例 | **选择**，且自然形成"AI 建议 + 人确认"边界 |
| L3 知识可及 | 问得到、留得住 | 四案例 | **选择**，治理是妥协 |
| L4 分析推演 | 看现状、推未来 | 三案例 | 选择 |
| L5 决策准备 | 方案对比、值多少钱 | 一案例（半为规划） | **未成熟非不存在**——案例十五主动规划财务闭环 |

流行叙事的"AI 决策"没有需求，业务要的是"活变快、判断有校验"。这是利好：L1/L2 可验证、可治理、风险可控。

### 2.2 六项支撑需求（公共品，草根做不动）

| # | 需求 | 案例证据 | 现状满足度 |
|---|---|---|---|
| D1 | 数据可及：集成、字段字典、语义 | 154 项系统数据集成；100+ 看板代码注入；"前两年数据治理才有今天" | 最贵最前置，两年尺度 |
| D2 | 工具可连：MCP/接口注册与分级 | TRACE32 47 工具、CAA 双通道、（反面）插件绕鉴权 | 各自封装，无共享注册 |
| D3 | 知识可治理：owner、版本、验证 | 责任田+当场验证（唯一样板）；制度 Skill 无更新机制（反面） | 17 例仅 1 例做全 |
| D4 | 行为可信：验证协议、权限分级 | 四态结论、prod 硬禁用、本地推理、注入防御 | 工程纪律已成文化，制度机制空白 |
| D5 | 成本可见：token/算力账 | 唯一信号："token 成本仅限充电研发可用" | 无账本，限流靠拍脑袋 |
| D6 | 经验可沉淀：Skill/剧本/图谱 + 质检 | 蒸馏剧本、自动规则沉淀（无审核——反面） | 形态丰富，无一有质检 |

### 2.3 供给模式的定位

草根模式 = **卓越的探索机制 + 零沉淀治理**。它不可替代的优势：需求真伪检验（17/17 真痛点）、并行试错的搜索带宽（选型判据是被成本与失败比出来的）、暴露失败的文化土壤。它结构性供给不足的：全局一致性（CATIA 接了两遍）、跨年时间尺度的资产建设、妥协的制度化风险（危险做法被当成功案例传播）。

结论：**草根与规划是两个正交维度——空间上的并行探索 vs 时间上的纵深建设，必须组成旋转门，不是二选一。** 补偿行为的出现是收编时机的探测器。

## 3. 平台定位

### 3.1 定位声明

```text
AI 公共品底座（主体）+ 任务闭环模板（选项之一）

业务流留给草根和飞书；平台只做草根做不动的四件公共品：
① 语义：最小共享对象联邦 + 字段字典
② 工具：MCP 注册中心 + 声明式权限 + 鉴权正门
③ 资产：规则/知识/Skill 的注册、版本、owner、失效、继任
④ 账本：用量/成本/质量信号遥测
```

不替代 ERP/MES/PLM/O9/飞书/数仓（权威系统不动）；不做独立入口（工作台仅作为重场景模板，默认入口是飞书与终端）；不替业务造场景（探索是平台的供给源头）。

### 3.2 对 04-05 原设计的三处修正

1. **威胁模型**：担心的"厚系统烟囱"没有发生（AI Coding 时代做系统太便宜，没人囤系统），实际发生的是**薄资产碎片**——碎的是规则库、连接器、知识库、判定框架。所以平台的核心是资产治理，不是业务流承载；
2. **入口假设**：案例的入口事实是飞书对话与终端 CLI（零迁移成本是竞争货币），"任务工作台"零用户。修正为协议优先——平台向飞书卡片/终端/现有系统输出任务上下文、AI 建议、确认动作；信息密度高的岗位（计划员、管理者）保留工作台模板（案例十五资源充足时确实选择了 Web 工作台）；
3. **落地路径**：MVP 不做新场景从零搭建，做**存量收编**——接住已跑通案例的资产，且收编动作包括"把作者的手工补丁升级为标准模块"。

## 4. 模块设计：必要性 × 时机 × 目标形态

### 4.1 总表

| 模块 | 必要性 | 建设时机 | 依据 |
|---|---|---|---|
| 语义层（联邦本体+字段字典） | ★★★ 最高 | 立即（收编时同步） | D1 是所有案例第一道工序；域内本体已自发出现（SE 30+ 对象、代码图谱），只统一四五个共享对象（人员/零件/供应商/车型/成本中心） |
| MCP 工具注册与安全分级 | ★★★ | 立即（收编级） | 各案例重复封装连接器；绕鉴权插件已出现；权限应写进工具声明（吸收 prod 硬禁用实践）而非提示词自觉 |
| 成本与质量遥测 | ★★★ | 立即（收编级） | 唯一成本信号是拍脑袋限流；遥测更深目的是**妥协检测**（盯"错的做法有没有被后来者复制"） |
| 资产注册与继任机制 | ★★★ | 立即（收编级） | "工具不随人走"无人解决，17 作品几乎全是单人维护；强制登记 owner+继任规则 |
| 规则编译器 | ★★★ | **MVP 级**（与工具注册并列） | 三个案例共同指向、无单案例能独立完成：NL 输入（大白话共创）→ AI 编译为五元组 → 人确认 → 规则库（版本/owner/适用域）→ 确定性执行。同时解决设变域两套规则库分裂 |
| 反馈蒸馏通道 | ★★★ | 第一批 | 蒸馏剧本已被自发运行（单剧本自动跑 1485 例）；平台内建"对话→剧本"蒸馏 + **审核入库**（堵无质检的自动沉淀） |
| 知识质检与失效联动 | ★★ | 第一批 | 当场提问验证是手工质检（规模化后不可持续）；制度改版/设变/车型变更应触发知识失效告警 |
| Task/决策对象 | ★★ 目标态必需 | 后置——收编时为已运行流程补挂 | Sage 的"写入飞书文档+关联 Issue"、责任人图谱、"分析结论无人读"都是任务层缺失的补偿行为；但不要求新场景先建状态机——13 例自然形态是对话+Skill+资产，强制 Task 化是过度工程 |
| 证据分级 | ★★ | 与知识质检同期 | `[推断]` 标注是手工版；AI 生成资产应有平台级证据分级（数据支撑/推断/待验证） |
| 入口协议（飞书卡片/终端上下文） | ★★ | 第一批 | 默认入口是飞书与终端，平台输出协议而非界面 |
| 经营归因层 | ★（当前）→高（规模化后） | 字段收编时埋、看板按触发器 | 草根模式无人需先证 ROI 才能干活；但字段埋在 Task 对象和遥测里几乎零成本（详见 5.2）。触发器：AI 年度预算需专项辩护、第三个部门 token 限流、或管理层开始问"AI 挣了多少钱"。口径从"这个决策值多少钱"切入，轻量贡献排行优先于 EVI 分成 |
| 场景工作台 | ★ | 按需模板 | 仅无既有系统依托的岗位需要 |
| 全企业知识图谱 | ★ | 未到时候 | 图谱可行性=数据结构化排序（代码>配置>制度文档>口头经验），按域按需生长 |
| 七种血缘 | 裁剪 | — | 裁到两种：数据血缘 + AI 调用审计 |

### 4.2 两个设计要点的展开

**遥测的灵魂是妥协检测**。成本/用量/质量遥测不只是账本，要回答三个问题：哪里出现高频手工操作（该自动化的没自动化）；用户在平台外打了什么补丁（飞书文档手工关联、Excel 手工对账 = 补偿行为信号）；哪些妥协开始被后来者复制（新案例抄了老案例的绕行做法 = 妥协制度化，最优先处理）。

**规则编译器是平台存在必要性的最佳证明**。它的每一环都有案例实证（共创机制、五元组技术、当场验证、规则引擎），但没有任何单案例能独立完成整条链——这正是"公共品"的定义。

## 5. MVP 路径：存量收编

```text
第一刻（收编，不做新建）：
  选 2-3 个已跑通案例做平台化收编——
  · 质量数据分析平台（资产最厚：看板代码+字段字典+剧本，缺治理与复用）
  · 研发全流程 Agent（入口最真实：飞书+图谱+Skill，缺图谱同步与质检）
  · 设变断点监控（数据底座最全：154 系统集成，缺规则版本化）
  收编动作六件：资产注册 / 接工具注册与鉴权正门 / 挂成本与质量遥测 /
  登记 owner 与继任 / 补挂标准模块替换手工补丁（如 Issue 关联→Task 对象）/
  业务功能一行不改

第二刻（验证公共品 + 经营层发题）：
  用收编后的底座支撑新场景，验证"草根用平台比不用快"；
  规则编译器在此刻上线，吞并设变域两套规则库；
  同时启动发题模式（见 5.1），刻意选一个能算钱的新场景
  （EOP 呆滞拦截 / 质量成本挽回 / 设变 avoided cost，三者都有现成数据基础），
  撬动归因层的建设理由

第三刻（按需平台化）：
  场景模板中心 / 联邦本体扩展 / 归因看板（按触发器）
```

**平台的第一个用户不是新场景的业务方，是已有资产的草根作者。** 对他们的价值主张：

> 你的资产交给我，换四样你自己拿不到的东西：**升级**（手工补丁换标准模块）、**复用**（别人用得上你的资产，你获贡献信用）、**记账**（成本与效果不再靠文章自述）、**继任**（你调岗资产不死）。作为交换只要三件事：资产登记、走鉴权正门、接受遥测。平台永远不要求你停止探索。

### 5.1 两种供给模式的分层：草根探索 vs 产品线拆解

与"草根先行→收编"并列的另一种模式是"基于产品线任务拆解→分配实现"。二者不是竞品，是**按任务属性分层的互补结构**，判定标准是两个问题：任务可分解吗？信息在谁手里？

| 维度 | 草根先行→收编 | 产品线拆解→分配 |
|---|---|---|
| 隐含假设 | 不知什么值得做，需并行探索 | 最佳路径已知，缺执行 |
| 信息优势方 | 执行者（痛在一线） | 管理层（账在上层） |
| 利润距离 | 远（17 案例集中在提效层的实证） | 近（其独有价值） |
| 需求真伪 | 自带验证（提出者即用户） | 携带翻译失真风险 |
| 失败模式 | 碎片化、治理真空、妥协制度化 | 需求失真、建完没人用、挤占草根 |
| 案例证据 | 16/17 | 案例十五（唯一，且成功） |

案例十五的成功恰好给分配模式划出**有效条件**：结构已知（四模块是业务自然结构，非拆解发明）+ 方法已知（OR-Tools 排产是成熟技术）+ 账本可验收（两年前置数据治理）。不满足这三条而硬拆（如"拆 20 个 AI 场景分给各团队"），就是经典企业 IT 失败模式。

分层组合：

```text
经营层（利润、呆滞、毛利）→ 拆解分配模式   ——账在管理层手里，有信息优势
执行层（排查、对账、知识）→ 草根模式     ——痛在一线手里，有探测优势
两层之间 → 平台做资产交换层 + 发题模式做转换器
```

**发题模式**是中间形态：管理层出题（带经营目标，如"EOP 呆滞拦截能否算出省了多少钱"），草根揭榜（带自己的痛点和工具能力）——方向自上而下、贡献自下而上（开源基金会的运作方式）。它导入利润视角，又避免摊派的毒性。

两个都要防的陷阱：

1. **伪草根**：管理层摊派创新指标让基层"自发"产出——两头的信息优势全丢，是最坏形态；
2. **分配挤占探索**：一旦"任务分下去了"，自发探索就停（"这不归我管"）。分配任务必须限定在已验证的确定性领域，不许越界到探索区。

分配模式还有一个硬前置：**可验收性依赖账本**（D5 遥测 + 归因字段）。验收不了的分配必然退化成进度剧场。所以两种模式都指向同一个平台底座——草根需要它做收编，分配需要它做验收，发题需要它做出题人和揭榜者的资产对接。这也是 04-06 定位的又一佐证。

### 5.2 利润断层的风险注记

17 个案例与组织利润关系不大，集中在执行层提效（时间节省 ≠ 成本降低 ≠ 利润增加，无一案例做了这个换算）。成因四分：**账本基建缺失**（没有归因口径时即使真省了钱也证不出来——鸡生蛋问题）、**采样偏差**（利润是管理层的痛，而管理层不写 Skill）、**行业结构**（单 Agent 能碰到的利润杠杆本来就少：料和价需要系统级/销售域视角）、**阶段使然**（与感知→分析→方案→决策四层图的当前阶段自洽，不必焦虑）。

校准动作两条（不改原设计）：

1. **归因字段前置埋设**：§4.1 归因层时机修正为"收编第一刻就埋字段、暂不建看板"——字段埋在 Task 对象和遥测里几乎零成本，看板和分成机制才贵。真正要防的政治风险：当管理层开始问"AI 到底挣了多少钱"而答不上来时，账本缺失从技术债变成危机；
2. **第二刻的算钱场景**：第一个用平台建的新场景不应顺其自然是下一个提效场景，而应刻意选能算钱的——用一个能回答"值多少钱"的场景，撬动归因层的建设理由。

## 6. 设计原则（收束）

1. **厚场景，薄系统**——业务流与界面留给草根和飞书，平台做四件公共品；
2. **补丁即路标**——案例作者的手工补偿行为是模块必要性与收编时机的探测器；
3. **旋转门节律**——草根探索（空间并行）与平台建设（时间纵深）正交互补，收编太早管死探索、太晚妥协制度化；
4. **妥协检测先于效率度量**——遥测盯的不是"用得好不好"，是"错的东西有没有被传下去"；
5. **AI 建议人确认**——权限分级写进工具/Skill 声明（代码级资产）而非提示词；绕鉴权零容忍，立即收编正门；
6. **资产有 owner 才有生命**——无主的知识库/规则库/图谱必然腐烂，继任机制与登记是资产入平台的准入条件；
7. **价值主张对齐激励**——平台对草根只提供增量（升级/复用/记账/继任），不索取控制权，否则探索枯竭、平台断粮；
8. **按地层分配供给模式**——账所在的地层（经营层）用拆解分配，痛所在的地层（执行层）用草根探索，发题模式做两层转换器；防伪草根、防分配挤占探索；
9. **壁垒在资产不在页面**——平台自身的护城河是规则库、本体、评测集、反馈数据和治理方法论，不是界面。
