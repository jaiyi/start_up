# 04-05b · 选择还是妥协：草根与规划的双重批判与平台设计再修正

> 讨论稿 / 会更新 · 最近更新 2026-09-30
>
> **一句话结论**：`04-05a` 用 17 个案例检验了 `04-05` 的设计，但它隐含了一个未经审视的假设——**案例的现有形态就是合理形态**。本文指出这是 is-ought 谬误：现状是约束条件下的产物，案例呈现的形态里，一部分是被验证的**选择**，一部分是被迫的**妥协**——识别二者的方法是观察案例中自发长出的"补偿行为"（人们在妥协形态上打的补丁，恰恰指向真正的 AI native 形态）。基于此重新平衡草根型与规划型：**草根赢在空间上的并行探索，规划赢在时间上的纵深建设，二者必须组成旋转门而非二选一**；平台设计随之再修正——Task 对象等被 04-05a 降级的模块恢复"目标态必需"地位，但按触发条件排期而非立即建设。
>
> 阅读顺序：`04-05`（平台设计）→ `04-05a`（17 案例证据检验）→ 本文（辩证再修正）。

## 0. 对 04-05a 的方法论批评

04-05a 的贡献是把平台设计从推理锚定到了证据，但它有一个系统性偏差：**凡是案例没有的，它就判定"不必要"；凡是案例已有的，它就判定"被验证"**。这个推理在两个方向都会出错：

- "17 案例中 13 例无任务状态机，故 Task 对象降级为可选模板"——也可能 13 例是因为单人、3 天投入、无平台支撑**做不动**状态机，而不是不需要。症状与病因混淆了；
- "真实入口是飞书，故任务工作台无用户"——也可能飞书入口是零迁移成本约束下的**占位**，而不是终局判断。

更关键的反证来自 04-05a 自己：它列出的 P1-P7 七个问题（资产碎片、治理真空、单点维护、无人读的分析、推送后无闭环跟踪……）中，**至少四个恰好是任务层、归因层缺失的症状**。用"现状没有 X"论证"不需要 X"，同时抱怨"现状有 X 缺失的症状"——这是 04-05a 内部的不自洽。

所以需要一层新的分析：把 17 个案例当作**约束条件下的实验数据**而不是**设计规范**，先回答每个形态是选择还是妥协，再谈平台该怎么设计。

## 1. 方法论：如何区分选择与妥协

三个可操作的判据，全部从案例内部取证：

### 1.1 判据一：约束解除测试

问：如果该案例的作者获得平台级资源（团队、时间、权限、预算），他会保留当前形态吗？

- 会保留 → 选择（该形态在约束解除后仍最优）；
- 会重构 → 妥协（该形态只是当前能力下的近似解）。

案例十五是最直接的证据：计划员工作台的作者**已经获得了团队和资源**，他们的选择是建 Web 工作台而非纯飞书机器人——因为计划员要同时看四模块仪表盘、做方案模拟对比，对话界面装不下这个信息密度。这说明"飞书入口"在信息密度低的场景是选择，在信息密度高的场景是妥协。

### 1.2 判据二：补偿行为检测（本文核心方法）

问：案例作者在当前形态上，有没有自发长出**绕行/补丁/手工补偿**？

如果存在补偿行为，说明作者自己已经感知到当前形态的不足——**补偿行为的方向，就是目标形态的方向**。这是最有价值的判据，因为它不需要假设，只需要观察。17 个案例里至少有六个显著的补偿行为，§2 逐一分析。

### 1.3 判据三：自然演化方向

问：案例随时间自然长出了什么？自发演化出的形态比初始形态更接近真实需求。

案例十一的三段演进（对话调优 → 场景预设 → 蒸馏剧本进定时任务）就是典型：如果对话式分析是终态，就不会自发长出"蒸馏剧本"——剧本化意味着用户要的是**确定性产出**而非对话体验。

### 1.4 一个先行立场

即便识别出妥协，也不意味着妥协是错误的。**在约束下选择可快速落地的妥协形态，本身是正确的工程判断**（案例六拒绝自研、长在多维表格上，是清醒而非将就）。方法论要回答的不是"妥协好不好"，而是：

```text
哪些形态应该在约束解除后升级（值得平台投资的妥协）
哪些形态应该在约束解除后保留（被验证的选择）
```

## 2. 逐项重审：17 案例关键形态的选择/妥协判定

### 2.1 判定总表

| 现状形态（04-05a 的解读） | 判定 | 证据 | 对平台的含义 |
|---|---|---|---|
| 飞书对话为主入口 | **混合：轻场景是选择，重场景是妥协** | 案例十五建了 Web 工作台；十六 Sage 把方案"写入飞书文档关联 Issue"（对话存不住结构化决策） | 入口协议化正确，但工作台保留为重场景模板 |
| 13 例无 Task 状态机 | **妥协为主** | 见 2.2 的四个补偿行为 | Task 恢复"目标态必需"，按触发条件排期 |
| L1/L2 需求压倒 L5 决策 | **前半是选择，后半是未成熟** | L1/L2 先行是自然顺序；但案例十五主动规划财务闭环（"这个决策值多少钱"）说明 L5 需求存在，只是数据/权限/责任制度未到位 | 归因层维持后置，但设启动触发器 |
| 知识用 RAG+来源标注 | **现阶段选择，规模化后妥协** | 案例十四的融合回答无准确性追踪；十七的 `[推断]` 标注是手工补质量管理 | RAG 保留；质量抽检与失效联动必须平台化 |
| 单人维护资产 | **纯妥协** | 无人会选择单点；案例八开源、十四设计继任（"离职知识不随人走"），都是在补偿这个妥协 | 资产继任机制维持 04-05a 判断 |
| 效果自述、无遥测 | **纯妥协** | 案例十一/十四给出遥测后立刻成为最有说服力的两例——**没有人不想要遥测，只是没有基建** | 遥测维持最高优先级 |
| 选型发散（判据散落各案例） | **探索期选择，复制期妥协** | 判据比出来是收获；但每个新项目重踩是浪费 | 判据制度化为选型标准 |
| 绕鉴权取数（案例十三） | **违规，不参与选择/妥协分类** | —— | 收编正门，无讨论空间 |

### 2.2 补偿行为清单：妥协的裂缝里长出来的路标

这是本文最重要的证据集。六个补偿行为，每个都指示一个平台模块的目标形态：

**补偿一：Sage 的"写入飞书文档 + 关联 Issue"（案例十六）。**
Sage 的日常形态是对话，但方案确认后它**把方案结构化写入飞书文档并关联 Issue（IDD）**。这是作者自己在补偿"对话存不住决策"——决策需要版本、需要被引用、需要与任务绑定。对话是输入界面，不是决策的存储形态。**指示：Task/决策对象是真实需求，作者已经手工搭了一半（Issue 系统 + 飞书文档），平台要做的就是把这一半标准化。**

**补偿二：案例十三的大白话规则共创。**
"帮我加个规则：车型既有 X11 又有 X01 时提醒核查新旧同步设变——一句话生效"。这个机制广受欢迎，但它本质上是一个**等待被发明的规则编译器的人肉版**：业务人员用自然语言表达规则 → 熟手把它配置成 Skill。案例十二的路线（NL → AI 编译为五元组 → 人确认 → 确定性执行）才是它的完成态。**指示：规则资产需要"自然语言输入层 + 形式化编译层 + 确定性执行层"三段式架构，案例十三的人肉中转是过渡形态。**

**补偿三：案例十一的"蒸馏剧本"。**
对话式分析好用来探索，但用户最终要的是**每天自动跑、结论固定、可直接引用的产出**——所以高频分析被自发蒸馏成剧本进定时任务（单剧本自动跑 1485 例）。**指示：对话是探索界面，资产是沉淀形态；平台必须内建"对话 → 剧本"的蒸馏通道，而不是让用户手工搬。**同时注意 1485 例的"最后一公里"问题（结论进入决策的比例未知）——蒸馏解决了产出，没解决承接，承接需要任务对象。

**补偿四：案例十四的"当场提问验证"。**
投喂者必须当场提问确认 AI "真的吃进去了"。这是**没有知识质检基建时手工做的质检**——每一条知识入库都消耗投喂者一次互动成本。规模化（百人部门）后这个手工环节必然不可持续。**指示：知识资产入库需要平台化的质检通道（自动出题验证 + 人工抽检），案例十四的手工版恰好验证了质检是真需求。**

**补偿五：案例十七的 `[推断]` 标注。**
作者要求 LLM 重写时"缺失的因果关系做推断并标注"。这是**没有来源分级机制时手工做的证据分级**——事实与推断的边界靠作者自律维护。**指示：AI 生成资产应有平台级的证据分级（数据支撑 / 推断 / 待验证），不能依赖每个作者的自觉。**

**补偿六：案例四/十六的"找责任人"图谱。**
案例四建审批树责任人图谱精准推送，案例十六的工单群自动拉对人。两个案例都在手工维护"谁该被通知/谁该确认"的映射——这是**人机分工对象（human_owner）的人工维护版**。**指示：任务对象中的人机分工字段（owner/confirm_policy）是真实需求，当前靠各案例自建映射表。**

### 2.3 重审结论

六个补偿行为指向的模块——**Task/决策对象、规则编译器、蒸馏通道、知识质检、证据分级、人机分工字段**——全部是 04-05 原设计中已有、而 04-05a 降级或淡化的模块。这不是巧合：草根在资源约束下手工搭出了这些模块的雏形，恰恰证明它们是真需求；04-05a 看到"没有平台化的 X"就判定"X 不必要"，把草根的手工补丁误读成了"不需要 X 的证据"。

**修正后的判定：17 个案例不是对 04-05 的否定，而是对它的分阶段验证——每一块被降级的模块，都能在案例里找到手工雏形。**

## 3. 草根型 vs 规划型：去掉浪漫化的双重批判

### 3.1 草根型的真实优劣

**真优势（不可替代，规划型永远做不到）：**

1. **需求真伪的检验能力**——17/17 案例对应真痛点，因为提出者就是用户本人，用错了自己先疼。规划型的需求清单永远混有"想象需求"（04-05 的任务工作台就是）；
2. **并行试错的搜索效率**——选型判据（确定性流程不用 LLM / 宏+门禁 vs MCP 直连两刻度）是被 17 个案例的成本与失败**比出来的**。规划型做单点设计，搜索带宽差一个数量级；
3. **组织文化的养成**——坑表文化、诚实口径、贡献排行，这些"敢于暴露失败"的土壤只能在自下而上的环境里长出来。规划型项目报告天然倾向报喜。

**真劣势（结构性，靠草根自身无法解决）：**

1. **局部最优陷阱**——每个案例在自己的约束半径内最优，全局次优。案例七和案例十二各接了一遍 CATIA，各自都"对"，但公司为此付了两遍连接成本。草根没有全局视野，也不该有——全局是平台的职责；
2. **时间视野短路**——单人 3 天投入的形态，天然只能承载 3 天视野的资产。需要两年建设的语义层（案例十五亲证）、需要持续运营的知识治理（案例十四的审核会），草根模式结构性供给不足。**这不是能力问题，是投入产出的时间尺度错配**；
3. **妥协的制度化风险**——这是最隐蔽的一条：妥协形态活得越久、越成功，越容易被后来的建设者当成标准抄走。绕鉴权的插件被写成成功文章传播（04-05a 已指出），单人维护被默认为常态，手工质检被当成"我们部门的特色做法"。**不升级的妥协会沉淀为技术债 + 文化债**；
4. **组织学习靠文章传播**——发现机制是"读文章"（阅读量 50~404），知识扩散慢且失真，且文章里只有结论没有失败过程。

### 3.2 规划型的真实优劣

**真优势：**

1. **公共品投资能力**——语义层、工具注册、成本遥测、继任机制，这些 D 类支撑需求没有单点受益者愿意付钱，只能规划投资；
2. **时间纵深的资产建设**——本体、归因口径、治理制度需要跨年度的持续投入与维护，规划型是唯一能承诺这种时间尺度的模式；
3. **全局一致性**——统一 ID、统一权限、统一口径，只能在横向视角下产生。

**真劣势（04-05 本身就是标本）：**

1. **需求假设未经验证**——任务工作台、七种血缘、EVI 分成体系，都是设计室产物。规划型的每一行设计都携带想象需求的风险，且组织越大、修正越慢；
2. **建设周期与窗口期的错配**——平台按年建设，业务窗口按季度变化。建成之日往往需求已迁；
3. **政治成本**——"谁的平台"必然引发地盘之争，治理条款容易被异化为控制工具（审批越多、探索越死）。**这是规划型最危险的失败模式：不是建设失败，而是把草根探索管死了**；
4. **过度设计的诱惑**——设计者按"完备性"而非"必要性"堆模块（七种血缘是典型），而完备性在真实组织里几乎从不兑现。

### 3.3 辩证结论：旋转门，不是二选一

两种模式的真优劣势恰好互补且不可互相替代：

```text
草根型 = 空间维度的优势（并行探索、真需求检验、文化）
         + 时间维度的劣势（视野短、无治理、妥协制度化）
规划型 = 时间维度的优势（纵深资产、公共品、一致性）
         + 空间维度的劣势（单点假设、无搜索带宽、管死风险）

正确形态 = 旋转门（revolving door）：
  草根探索（Explore）→ 补偿行为出现（信号）→ 平台收编该能力（Exploit）
  → 收编后的公共品降低下一轮草根探索的成本 → 更快的下一轮探索
```

旋转门的关键节律是**时机**：收编太早（补偿行为未出现、形态未收敛）会把探索管死；收编太晚（妥协已制度化、资产已碎片化）成本翻倍。**补偿行为就是收编时机的探测器**——§2.2 的六个补偿行为中，规则编译（案例十二已有完成态技术）和蒸馏通道（案例十一已自发运行）的时机已经成熟；全企业本体（仅案例十五在规划）则明显未到。

## 4. 平台设计再修正（对 04-05a 修正案的修正）

### 4.1 修正总表

| 04-05a 的判定 | 04-05b 再修正 | 理由 |
|---|---|---|
| Task 对象降级为"可选模板" | **恢复"目标态必需"，建设时机后置**——按"收编存量时为已运行流程补挂 Task 对象"的节奏，不要求新场景先建状态机 | Sage 的 Issue 关联、案例四的责任人图谱、案例十一的最后一公里问题，都是任务层的补偿行为 |
| 工作台"不必要（独立形态）" | 修正为"协议优先 + 重场景例外"——飞书/终端为默认入口，信息密度高的岗位（计划员、管理者）保留工作台模板 | 案例十五的反例：资源充足时作者选择了工作台 |
| 经营归因层"移出 MVP" | 维持后置，但**增设启动触发器**：AI 年度预算需专项辩护、或第三个部门出现 token 限流时启动 | L5 需求存在但未成熟（案例十五主动规划财务闭环） |
| 反馈层"吸收野生形态" | 维持，并明确三通道：蒸馏通道（十一）、质检通道（十四手工版 → 平台化）、证据分级（十七 `[推断]` → 平台级） | 补偿行为二/三/四/五 |
| 治理层"血缘裁到两种" | 维持裁剪，但**把"妥协检测"列为遥测的显式目的** | 见 4.2 |
| MVP 路径"存量收编" | 维持，但收编动作增加一项：**为每个被收编案例补挂其手工补丁对应的标准模块**（如 Sage 的 Issue 关联 → 标准 Task 对象） | 收编不只是登记资产，是升级形态 |

### 4.2 新增设计原则：妥协检测是遥测的灵魂

04-05a 把成本/质量遥测定位为"账本"，这不够。遥测更深层的用途是**持续区分选择与妥协**：

```text
遥测数据 → 回答三个问题：
① 这个 Skill/资产的使用是稳定态还是逃逸态？
   （高频手工操作反复出现 = 该自动化的地方没自动化 = 妥协信号）
② 用户在平台外打了什么补丁？
   （飞书文档手工关联、Excel 手工对账、群里的口头确认 = 补偿行为信号）
③ 哪些妥协开始被后来者复制？
   （新案例抄了老案例的绕行做法 = 妥协制度化信号，最优先处理）
```

问题 ③ 尤其重要：**遥测要盯的不是"用得好不好"，而是"错的东西有没有被传下去"**。这要求平台运营者持续观察新资产的生产过程（而非只看结果指标），把 17 案例复盘时用的人工判读方法（本文 §1 的三个判据）变成轻量的例行审查。

### 4.3 规则编译器：从 04-05a 的"新增模块建议"升级为第二个 MVP 级模块

04-05a 只把 MCP 工具注册列为收编级动作。基于补偿行为二的分析，**规则编译器应并列进入第一批建设**：

```text
自然语言规则（业务人员大白话输入，案例十三的共创机制）
    → AI 编译为形式化规则（五元组，案例十二的完成态技术）
    → 人确认（案例十四的当场验证）
    → 入规则库（版本、owner、适用域，堵 P1 资产碎片：设变域两套规则库合并）
    → 确定性执行（代码/引擎，案例四路线）
```

这条链同时解决 P1（设变规则资产分裂）、P7（选型判据制度化）和 D3（规则治理），且每一环都有案例实证——**它是 17 个案例共同指向、但没有任何单案例能独立完成的模块，是平台存在必要性的最佳证明**。

### 4.4 平台价值主张的再表述

给草根作者的承诺需要更新。04-05a 的版本是"你的资产交给我，获得治理、复用、记账和继任，你的工具照旧跑"——这个版本偏保守，容易滑向"平台=仓库"。

再修正的版本：

> 你的资产交给我，获得四样你自己拿不到的东西：**升级**（你的手工补丁换成标准模块——Sage 的 Issue 关联变成真正的 Task 对象，十四的手工验证变成自动出题质检）、**复用**（别人能找到并用上你的规则/知识/连接器，你获得贡献信用）、**记账**（成本与效果不再靠文章自述）、**继任**（你调岗资产不死）。
>
> 作为交换，平台只要求三件事：资产登记、走鉴权正门、接受遥测。
>
> **平台永远不要求你停止探索——探索是平台的供给源头。**

## 5. 收束

对"现状是选择还是妥协"这个问题的最终回答：

1. **17 个案例的形态是混合物**——轻入口、RAG、选型判据、坑表文化是被验证的选择；任务对象、遥测、知识质检、规则编译是需要平台补齐的妥协。区分二者不能靠立场，要靠补偿行为检测：**案例作者自己打的补丁，就是通往 AI native 的路标**；
2. **草根与规划不是光谱上的两个点，是两个正交维度**——空间上的并行探索与时间上的纵深建设。任何"统一收口"或"任其自流"都是把二维问题压成一维的错误；
3. **真正的 AI native 形态不在 17 个案例里，也不在 04-05 的设计图里，而在两者的旋转门里**——草根长出补丁，平台把补丁变成标准件，标准件降低下一轮探索的成本。平台设计的第一性目标不是"承载业务流"，而是**把这个旋转门转得更快、且不错过收编时机**。

04-05a 结尾说"平台的第一个价值动作是接住已长出来的资产"——保留，但补上半句：**接住之后，第二动作是识别资产里哪些形态该升级，并只升级那些补偿行为已经出现的地方。**
