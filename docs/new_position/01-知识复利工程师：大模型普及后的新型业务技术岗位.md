# 知识复利工程师：大模型普及后的新型业务技术岗位

## 1. 背景判断：发电机已经出现，但工厂还没有完成流水线改造

现在的大语言模型已经基本成型，类似于“发电机已经出现”。

但是，围绕大模型的应用通用操作系统、组织流程、知识沉淀方式、岗位分工和管理机制，还远没有稳定下来。这更像是：

```text
电力已经出现，
但工厂还没有完成电气化和流水线改造。
```

在这个阶段，很多 AI 应用建设还停留在“拿着发电机到处接线”的状态：

- 套壳一个聊天界面；
- 做一个简单 RAG；
- 做一个内部问答机器人；
- 拼接几个 API；
- 为某个临时需求交付一个小平台。

这些事情可以解决短期问题，但未必能给个人或组织留下长期经验壁垒。

真正值得关注的问题是：

> 如何理解一个组织如何把知识、流程、反馈变成可复用的智能生产力。

这可能是大模型普及之后，普通知识工作者、业务骨干和企业内部 AI 推动者最值得投入的方向之一。

---

## 2. 为什么单纯“搓小平台”未必有长期复利

在大模型能力快速提升、开源框架快速成熟、云厂商持续托管化的背景下，很多轻量 AI 项目的技术封装会迅速贬值。

如果一个小项目只是：

```text
接一个模型
做一个页面
上传一些文档
跑一个问答
交付后结束
```

那么它的长期价值有限。

这类经验很容易变成：

```text
我会搭一个现在流行但明年可能过时的技术栈。
```

而不是：

```text
我理解一个业务系统如何沉淀知识、嵌入流程、形成反馈闭环，并持续提高组织生产力。
```

不过，小项目并非完全没有意义。它的价值取决于是否能暴露真实业务摩擦，并把这些摩擦转化为可沉淀的知识资产和流程资产。

但这里有一个重要限制：

> 作为乙方或外部交付者，很难真正观察和识别到业务现场的细节。

现实中，很多需求已经经过了一层甚至多层转化：

```text
一线真实问题
→ 业务负责人理解
→ 产品/项目经理整理
→ 需求文档表达
→ 乙方理解
→ 技术方案
```

经过这种转化后，很多关键信息会失真：

- 真正的异常情况没有被表达出来；
- 一线人员的实际操作习惯被隐藏；
- 需求被包装成“功能点”，而不是业务摩擦；
- 决策依据、妥协过程、失败案例没有进入需求；
- 用户说出来的是“想要什么”，不是“为什么现在做不好”。

所以，从职业复利角度看，单纯做乙方项目交付并不一定能积累足够深的业务知识壁垒。

真正有复利的小项目，必须能沉淀出：

- 领域对象；
- 业务规则；
- 判断标准；
- 异常案例；
- 流程节点；
- 决策依据；
- 反馈样本；
- 可复用模板；
- Agent 任务边界；
- 可评测样例。

否则项目结束后，经验也会很快散掉。

## 3. 知识复利不是“多写文档”，而是让知识进入生产循环

知识复利不是简单地：

```text
多写文档
多建知识库
多上传资料
多做 RAG
```

这些只是知识资产化的第一步。

真正有复利的知识系统，至少需要满足四个条件：

```text
被使用
被反馈
被修正
被编排进流程
```

如果知识只是存在知识库里，但没有进入日常任务流，它很容易变成新的知识坟场。

一个有复利的知识系统，应当能够做到：

- 在真实工作中被调用；
- 在任务完成后收到反馈；
- 在发现错误后被修正；
- 在流程中形成默认动作；
- 在下一次类似任务中复用；
- 在复用过程中继续积累新的判断。

因此，“知识复利”至少应拆成四层：

```text
知识资产化
+
知识流程化
+
知识反馈化
+
知识治理化
```

只做第一步，价值有限。

### 3.1 知识资产化

把分散在个人经验、聊天记录、会议纪要、项目文档、表格和操作习惯里的知识，转化为可被检索、引用、维护的资产。

包括：

- 规则；
- 案例；
- 模板；
- 流程；
- 决策标准；
- 异常处理；
- 常见问题；
- 成功与失败复盘。

### 3.2 知识流程化

让知识不是孤立存放，而是进入实际工作流。

例如：

- 新人 onboarding 时调用；
- 销售写方案时调用；
- 客服处理问题时调用；
- 项目复盘时调用；
- Agent 执行任务时调用；
- 管理者做决策时调用。

### 3.3 知识反馈化

知识必须能接受真实使用后的反馈。

例如：

- 这个回答是否有用；
- 这个方案是否被采纳；
- 这个规则是否过时；
- 这个流程在哪一步卡住；
- Agent 是否引用了错误知识；
- 一线人员是否补充了新情况。

### 3.4 知识治理化

知识越积越多，如果没有治理，就会变成知识债务。

治理包括：

- 来源可信度；
- 版本管理；
- 权限边界；
- 过期机制；
- 冲突处理；
- 人工确认；
- 审批机制；
- 安全和合规；
- 哪些知识可以自动更新，哪些必须人工确认。

---

## 4. 真实一手信息是知识复利的前提

知识复利的前提，不只是有知识库，而是知识获取渠道足够贴近真实使用。

也就是说，知识不能只来自二手需求文档，而应尽可能来自：

- 一线操作；
- 实际对话；
- 真实交付；
- 用户反馈；
- 失败案例；
- 异常处理；
- 决策过程；
- 任务结果；
- 复盘材料。

知识必须贴近使用现场，然后经过合理治理，才可能变成可复用的智能生产力。

如果知识来源已经被层层转述和包装，那么 Agent 学到的可能只是“组织想象中的流程”，而不是真实流程。

这也是为什么内部业务人员、长期嵌入业务的 AI 推动者，可能比纯外部交付者更适合做知识复利工程。

---

## 5. 大模型普及后的组织结构：平台集中，知识分散，治理半集中，应用贴近业务

未来公司内部的 AI 能力，很可能不会是传统 IT 完全消失，也不会是业务部门完全自治。

更可能出现三层结构。

### 第一层：公司级 AI 基础设施

这一层由 IT、平台团队或企业级 AI 中台负责，提供：

```text
模型
权限
存储
审计
计费
安全
合规
MCP 网关
Token 管理
服务器运维
模型网关
基础数据连接
```

这部分偏基础设施和治理，适合集中建设。

### 第二层：业务部门内嵌 AI 能力

这一层更贴近业务，由懂业务的人维护：

```text
知识库
Agent
流程
Prompt
评测样例
业务规则
异常案例
反馈闭环
```

这些内容必须贴近业务现场，很难完全由远离业务的 IT 部门包办。

### 第三层：少量专家型中台 / AI Ops

这一层负责制定标准、处理复杂集成、治理风险，并做跨部门复用。

包括：

```text
知识治理标准
Agent 安全边界
跨系统集成
复杂工作流设计
评测体系
日志和审计
权限模型
高风险场景把关
```

因此，更可能形成的组织形态是：

```text
平台集中
知识分散
治理半集中
应用贴近业务
```

这与“轻量半托管杠铃路径”是一致的：

- 上层有轻量平台、治理和基础设施；
- 下层有业务部门内生探索；
- 中间避免形成沉重、脱离业务的“大平台幻觉”。

## 6. 应用类算法工程师不会简单消失，但会发生迁移

“大模型普及后，应用类算法工程师会消失”这个判断需要拆开看。

如果指的是传统 NLP 场景下，为每个业务单独做文本分类、意图识别、信息抽取、摘要、问答等小模型的岗位，那么这类岗位确实会被压缩。

但 AI 应用能力不会消失，而是迁移到新的方向：

```text
AI 应用系统工程
知识工程
评测工程
流程编排
领域智能运营
```

未来更稀缺的，可能不是“会调一个小模型”的人，而是能回答这些问题的人：

- 业务知识应该如何结构化？
- 哪些知识适合进入 RAG？
- 哪些知识应该是硬规则？
- 哪些知识只是弱偏好？
- Agent 什么时候可以执行？
- 什么时候必须问人？
- 输出结果如何评测？
- 错误如何回流到知识库？
- 知识冲突如何处理？
- 权限和审计如何设计？

所以，岗位不是简单消失，而是从“应用算法”迁移到“AI 应用系统”和“业务知识系统”的设计、维护和运营。

## 7. 知识复利工程师的核心定义

可以把这个新型角色暂时称为：

```text
知识复利工程师
```

或者更职业化地表达为：

```text
AI Knowledge Systems Engineer
Knowledge Operations Engineer
Business AI Systems Engineer
Domain AI Ops
组织记忆工程师
业务知识系统工程师
```

它的核心工作不是简单维护文档，而是：

> 把业务中的经验、规则、案例、反馈、流程、异常处理方式，沉淀成可被人和 Agent 共同使用、持续更新、可评测、可治理的知识系统。

这个角色关心的不是一次性 AI 工具交付，而是长期的组织智能复利。

它要让组织从：

```text
靠人记住
靠老人带新人
靠群聊翻历史
靠重复问答
靠临时拍脑袋
```

转向：

```text
经验可沉淀
知识可调用
流程可复用
反馈可回流
Agent 可协作
新人可快速上手
组织少重复犯错
```

## 8. 这个角色需要的能力结构

### 8.1 领域建模能力

能把混乱业务拆成：

```text
对象
关系
规则
流程
角色
输入
输出
异常
反馈
指标
```

### 8.2 知识资产设计能力

知道什么应该放进：

```text
Wiki
结构化表
知识图谱
Prompt
Agent 记忆
评测集
操作手册
流程系统
```

不是所有东西都应该丢进 RAG。

### 8.3 Agent 任务边界设计能力

知道 Agent 应该：

```text
建议什么
执行什么
不能执行什么
什么时候问人
什么时候停止
什么时候写回
什么时候只生成草稿
```

### 8.4 评测和反馈能力

能持续判断：

```text
Agent 是否真的有用
有没有误导
有没有重复错误
知识有没有命中
业务结果有没有改善
```

### 8.5 轻量工程实现能力

不一定要成为大厂算法工程师，但要具备基础工程能力：

```text
API
数据格式
Markdown
JSON
脚本
自动化
权限
日志
Docker
基础数据库
模型调用
```

### 8.6 组织推动能力

知识复利不是一个人的文档工程，它需要别人愿意：

```text
记录
反馈
修正
复用
遵守流程
```

因此，这个岗位带有明显的组织协作和流程推动属性。

## 9. 风险与反面：知识复利也可能变成知识债务

知识不会天然产生复利。

如果缺少治理，知识越积越多，可能变成负资产：

```text
业务变化了
规则过期了
文档没人维护
知识互相冲突
搜索结果不可信
没有来源
没有版本
没有责任人
没有反馈机制
Agent 引用旧知识导致错误
```

所以未来真正稀缺的不是“会积累知识”的人，而是：

```text
会设计知识生命周期的人。
```

这包括：

- 哪些知识值得沉淀；
- 哪些知识只适合临时记录；
- 哪些知识要定期失效；
- 哪些知识需要审批；
- 哪些知识可以由 Agent 自动更新；
- 哪些知识必须人工确认；
- 哪些知识能作为硬规则；
- 哪些知识只是弱偏好。

没有这套治理，知识库越大，Agent 越危险。

## 10. 但这个方向也有风险

知识复利工程是一个有潜力的方向，但不能把它想象成天然安全、天然有壁垒、天然会被组织认可的路线。

它至少有四类现实风险。

### 10.1 风险一：概念太抽象，不容易被市场识别

“知识复利工程”“组织记忆工程”“业务知识系统化”这些表达，在认知上是成立的，但在现实招聘和组织预算里，未必马上能被识别。

很多老板和业务负责人更容易理解的是：

```text
降本
提效
少犯错
新人更快上手
客户响应更快
方案质量更稳定
交付经验可复用
```

而不是：

```text
我要建设知识复利系统。
```

所以，这个方向如果要变成职业机会，必须能被翻译成业务结果：

- 新人培训时间降低；
- 重复问答减少；
- 方案生成时间缩短；
- 客服或销售响应更一致；
- 项目复盘能进入下一次交付；
- 关键经验不再只依赖某个老员工；
- Agent 输出质量可以被持续评测和改进。

如果没有这些可感知结果，知识复利容易变成自嗨式概念。

### 10.2 风险二：低端部分会被工具平台吞掉

未来很多平台都会自动提供：

```text
文档上传
RAG 检索
权限管理
Agent 编排
知识图谱
工作流
基础评测
模型网关
```

所以，如果一个人的能力只是：

```text
会搭一个知识库
会配置一个 RAG
会做几个 Prompt
会接一个 Agent 平台
```

那么这部分能力很可能会被平台商品化。

真正不容易被吞掉的是平台之上的能力：

- 业务结构设计；
- 知识治理策略；
- 流程重构；
- 反馈闭环设计；
- 评测样例建设；
- 权限和风险边界定义；
- 跨角色协作机制设计。

也就是说，壁垒不在工具配置，而在业务知识系统的设计和运营。

### 10.3 风险三：知识维护很苦，且长期看更像园丁而不是建筑师

知识复利不是一次性建设，而是长期维护。

它需要持续做很多不性感但重要的工作：

```text
清理旧知识
合并重复知识
处理冲突知识
标记过期内容
修正错误引用
补充来源依据
维护版本记录
沉淀使用反馈
把一次性经验升级为规则
把过度总结的规则降级为案例
```

这类工作更像园丁：持续修剪、除草、浇水、更新土壤。

它不像一次性工程那样，做完一个平台就可以交付结束。

因此，这个方向适合愿意长期贴近业务、持续维护知识系统的人；不适合只喜欢搭建新工具、不愿意做长期运营的人。

### 10.4 风险四：业务部门未必愿意配合

知识复利工程不是纯技术问题，它会触碰组织里的真实权力结构。

很多隐性知识本身就是个人壁垒：

- 老员工的经验；
- 销售的客户判断；
- 运营的异常处理技巧；
- 项目经理的协调经验；
- 某些人对流程漏洞的掌握。

当你试图把这些经验外部化、结构化、系统化时，可能会遇到阻力。

因为对某些人来说：

```text
知识沉淀 = 个人不可替代性下降
流程透明 = 操作空间减少
经验共享 = 权力重新分配
```

所以，知识复利工程不仅需要技术能力，也需要组织沟通能力和利益协调能力。

### 10.5 风险五：过度结构化会压死真实业务弹性

还有一个容易被忽视的风险：不是所有知识都适合立刻结构化成规则。

有些业务判断本来就是情境性的：

- 客户关系；
- 谈判节奏；
- 风险偏好；
- 特殊个案；
- 临时妥协；
- 人情和组织政治。

如果过早把这些复杂判断固化为规则，Agent 可能会输出看似规范、实际僵硬的建议。

所以，知识复利工程需要区分：

```text
硬规则
软偏好
经验案例
临时判断
待验证假设
```

不是所有经验都应该立刻升级为标准流程。

## 11. 对个人职业规划的启发

对于不在大厂的知识工作者来说，追逐每一个 AI 框架和小平台，未必是最有复利的路线。

工具会变：

```text
RAG 框架会变
Agent 框架会变
工作流平台会变
模型 API 会变
知识库产品会变
```

但以下问题不会消失：

```text
业务知识如何结构化？
组织经验如何外部化？
Agent 的任务边界如何定义？
知识如何进入流程？
反馈如何沉淀？
质量如何评测？
权限如何治理？
哪些场景不适合自动化？
```

因此，更有复利的个人定位不是：

```text
我会部署某个 AI 框架。
```

而是：

```text
我能把一个业务部门的隐性知识变成可运行、可维护、可复利的 AI 工作系统。
```

这可能会成为大模型普及后，普通知识工作者值得长期投入的一种新型职业能力。

---

## 12. 阶段性结论

在大模型成为基础设施之后，真正有复利的可能不是一次性 AI 应用交付，而是围绕业务知识、流程反馈、组织记忆和 Agent 协作机制的长期工程能力。

这个方向可以概括为：

```text
把真实业务现场中的知识、流程、反馈和异常处理经验，
沉淀成可被人和 Agent 共同使用的智能生产系统。
```

这不是传统意义上的知识管理，也不是单纯的应用开发。

它更接近一种新型能力：

```text
业务知识系统化能力
+
AI 应用系统工程能力
+
组织记忆运营能力
```

未来公司里的 IT 部门可能更偏向基础设施和治理，业务部门则需要内生 AI 能力。应用类算法工程师的一部分工作会被大模型压缩，但 AI 应用系统工程、知识工程、评测工程、流程编排和领域智能运营会扩张。

因此，“知识复利工程建设与维护”很可能成为大模型普及后的关键技能之一。

但它的壁垒不在于会不会建知识库，而在于能否长期、贴近真实业务地完成：

```text
知识资产化
知识流程化
知识反馈化
知识治理化
```

只有四者同时存在，知识才可能产生复利。
